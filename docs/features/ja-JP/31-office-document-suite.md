# オフィスドキュメントスイート

4つのオフィススキルは会社レイヤー `<home>/skills/` に一度だけインストールし、新しい従業員ごとにコピーしません。既存のコピーは保持します。任意のプログラミングスキルと整理方法は[スキルライフサイクル](15-skill-lifecycle.md)を参照してください。

> ファイルを説明する段落ではなく、本物の.docxを手渡すエージェント——マーカープロトコル、フェイルクローズのパスフェンス、そしてモデルがマーカーを忘れた日のためのセーフティネット付き。

## Office スクリプトの信頼境界

`office_script` が実行するのは、稼働中のバイナリに埋め込まれた Python スクリプトだけです。各スクリプトをコンパイル時の SHA-256 マニフェストで検証し、バイナリのバージョンとハッシュで版を識別します。個人・部門・会社のスキルが上書きできるのは **SKILL.md のプロンプト本文のみ**です。同名のスクリプトがあっても実行しません。

呼び出しごとに gateway／MCP プロセスが `<home>/.office-execution/` 配下に、自身の uid が所有する権限 `0700` の専用ディレクトリを作成します。検証済みコードは排他的な no-follow 作成で権限 `0500` に設定します。入力は各パス要素をリンクをたどらずに開き、正規パスの範囲を確認して専用ディレクトリにコピーします。既存の文書リソース検査もこのスナップショットに適用します。Python は継承環境を消去した状態で専用ディレクトリ内で実行し、従業員のプロジェクト設定やモジュールを読み込みません。

引数はスクリプト別のスキーマで検証します。入力は一つ、`create` は `--out` が必須、`to_pdf` は `--outdir` を指定可能で、`--format` は各スクリプトで定義された値のみです。`"--out", "report.pdf"` のように別々の引数で渡してください。`--out=/path`、未知・重複フラグ、余分な入力は拒否します。入力は呼び出し元のディレクトリまたは `<home>/attachments/` に限定します。出力は**呼び出し元のディレクトリ内の新規ファイル**に限定し、文書形式に合った拡張子と既存の親ディレクトリが必要です。既存ファイル、保護対象名、シンボリックリンク、ハードリンク、パストラバーサルは拒否します。PDF 変換で `--outdir` を省略すると元の入力の親ディレクトリを使いますが、これも呼び出し元のディレクトリ内でなければなりません。Python は一時出力のみを書き、成功後に Rust が出力先を再検査して専用領域でコピーと同期を完了したファイルを、no-follow で開いた出力先へ上書き禁止の排他的 rename で保存します。一時領域と出力先は同じファイルシステムにある必要があり、失敗しても不完全な出力先ファイルは残しません。

スキル層のルートと各パス要素でシンボリックリンクを拒否します。部門プロンプトは権威ある `org.toml` の登録と `agent.toml` のミラーが一致する場合のみ読み込みます。取得不能・不一致の場合は部門層を除外します。会社層の四つのスキルがスクリプトマニフェストに合格して初めて移行完了マーカーを書きます。不一致のコピーは保存したまま実行対象から除外し、ログと `duduclaw doctor` に表示します。古い移行マーカーは検証の代わりにはなりません。

既存の MCP 権限・承認・スキル無効化・文書制限は維持します。`office_script` は Linux と macOS のみを対象とし、ファイルシステム・ネットワーク・メモリの隔離がすべて成立しなければ既定で拒否します。Linux は bwrap による読み取り専用のシステム／runtime／入力マウント、専用出力／キャッシュの書き込み、ネットワーク／PID namespace と 2 GiB RLIMIT_AS を必須とします。macOS は deny-by-default の sandbox-exec profile でネットワークを禁止し、ファイルアクセスを制限します。DATA／RSS 上限を試し、超過割り当ての拒否も確認します。適用不能・無効なら拒否します。CPU／ファイル／プロセス／fd 制限と process group の終了処理は維持します。ホストの warm 処理はユーザーファイルを含まない別の一時ディレクトリで、検証済み wrapper を固定の `--help` 引数だけで実行します。この処理だけが依存関係を `<home>/.office-execution/uv-base-v1/` にダウンロードできます。sandbox は base を読み取り専用にし、`UV_CACHE_DIR` を `<専用作業領域>/uv-cache` の独立コピーに設定して、`UV_LINK_MODE=copy` とオフラインモードで実行します。キャッシュ内リンクはコピー先に変更し、実行環境はオフラインで再構築します。作業領域、出力ステージング、キャッシュは公開または失敗後に削除します。以前の parser が書き込めるキャッシュは trusted base に昇格させず、明示的な unsandboxed fallback は従来の動作を維持します。既存の `config.toml [container.sandbox] script_when_unavailable = "run_unsandboxed"` を明示した場合だけ、隔離不能時の fallback を許可し、ホストプロセスごとに一度警告します。`sandbox_enabled = false` は暗黙の免除ではありません。同じ UID の pathname／キャッシュ競合と、推移的依存関係の完全な hash lock がない残存リスクは[セキュリティ説明](../05-security-defense.md)に記載しています。Linux／macOS の隔離成功経路、実際の LibreOffice、gateway／CLI の統合検証は別途必要です。この開発環境は sandbox-exec を拒否したため、隔離成功の検証にはなりません。

Linux のマウントまたは macOS profile の生成前に、home、作業／出力ディレクトリ、入力、スクリプト、base／実行別キャッシュ、および存在するすべての runtime 許可ルートの canonical path を解決します。専用パスと runtime ルート（元の別名と解決先を含む）が等しい場合、またはどちらかが他方の祖先である場合は隔離を拒否します。解決失敗も拒否します。base と書き込み可能な作業領域の重複を拒否し、実行別キャッシュはその作業領域内に限定します。これにより `/usr/local` や `/opt/homebrew` 配下のカスタム home、移設された専用作業領域／キャッシュから他の従業員のデータが公開されることを防ぎます。既存の `script_when_unavailable = "run_unsandboxed"` による明示的な免除のみが、同じ警告付きで fallback を許可します。

実行時は直接依存を固定し、公開日時の上限を適用して source build と Python の自動ダウンロードを禁止します。ユーザー入力を含まないホスト warm 処理の後、uv はオフラインで実行し、system Python でも直接依存の版を確認します。Unix リソース制限と stdout／stderr 各 32 KiB の上限により、超過・タイムアウト時にプロセスグループを終了します。起動直前にパスと hash を再検証しますが、推移的依存の完全な hash 固定と同一 UID のホストプロセスの隔離は対象外です。明示的な unsandboxed fallback では通信遮断も保証しません。制限とキャッシュ復旧は [Security Defense](../05-security-defense.md#office-parser-limits-and-remaining-trust-boundary) を参照してください。

## これは何か

DuDuClawのエージェントは実際のオフィスファイル——Word (`.docx`)、Excel (`.xlsx`)、PowerPoint (`.pptx`)、PDF——を生成し、リクエストが届いたチャットチャネルへネイティブ添付ファイルとして届けられます。同梱の4つのドキュメントスキルが各フォーマットの作り方をエージェントに教えます。ファイルが存在した後のすべて——検証、チャネル配送、アーカイブ、ダッシュボードプレビュー——はゲートウェイが担います。

このスイートは受信方向でも機能します。メッセージにドキュメント添付が付いている場合、決定論的な拡張子テーブル(`office_docs.rs`)が適切なスキルへマッピングし——`doc`/`docx` → docx、`xls`/`csv`/`xlsx` → xlsx、`ppt`/`pptx` → pptx、`pdf` → pdf——プログレッシブスキルランカーのアクティブセットにそのスキルを強制投入します。純粋なルックアップであり、ドキュメントが添付されていなければコストはゼロです。

## 📎DELIVERプロトコル

ファイルを生成した後、エージェントは返信にファイルごとに1行のマーカーを追加します:

```
📎DELIVER:/home/u/.duduclaw/agents/sales/q3-report.docx
```

ゲートウェイは次を行います:

1. ユーザーに見えるテキストからすべてのマーカー行を除去します。
2. パスを**フェイルクローズ**で検証します:絶対パスであること、通常ファイルとして存在すること、そして`..`とシンボリックリンクを解決する正規化(canonicalization)の後、エージェント自身のディレクトリまたは共有`attachments/`フォールバックの内側にあること。`agents/me/../victim/secret`のようなトラバーサルは、正規化するとエージェントルートの外に出るため拒否されます。
3. バイト列を読み取り、チャネルの`send_document`を通して送信します。

マーカーのない返信はバイト単位でそのまま返されます——最も一般的なケースは、プロンプトキャッシュとフォーマットの安定性を保ったままです。検証・読み取り・送信のいずれの失敗も正直にデグレードします:ファイルの場所を示すテキスト注記が追加されるため、成果物がどこへ行ったのかユーザーが分からなくなることはありません。サイレントドロップという結末はありません。

## 推測ではなくマーカーを使う理由

返信テキストは、すべてのランタイム——Claude CLI、Codex、direct API——が共有する唯一の受け渡しポイントです。返信内のマーカーによって、*モデル*が意図を宣言しつつ、実際にサンドボックスの外へ出るものについての権限は*ゲートウェイ*が握り続けます。その代替案——ゲートウェイが散文から成果物を推測する——こそ、このプロトコルが避けるために存在する失敗モードです。

このプロトコルは元々オフィススキルのSKILL.mdファイルにしか書かれておらず、実際のインシデント(2026-07-28)がその隙間を露呈しました:エージェントは本物の`.docx`を生成して`~/Desktop`に書き込みましたが、マーカーを一度も出力しませんでした。ユーザーが受け取ったのはファイルが存在すると主張する散文だけで、ゲートウェイには送信もアーカイブもするものがありませんでした。2つの修正が実装されました:

- **常時有効なシステムルール**(`channel_reply.rs`の`deliver_rules`):すべてのチャネルシステムプロンプトに含まれる、静的でプロンプトキャッシュに優しいブロック——ファイルは作業ディレクトリ内に保存しなければならず、各ファイルは自分の`📎DELIVER:`行を持ち、「テキストでファイルを説明する」ことは配送に数えられません。姉妹の常時有効ブロック(`pacing_rules`)は関連する現場報告を修正します:重いタスクのターンの後、単なる挨拶には短い返信を返すべきであり、前のタスクを再実行してはなりません。
- 下記の**スイープ**:プロンプトルールでは保証できない残り半分のために。

## スイープのセーフティネット

`sweep_undeclared_deliverables`は、「作業ディレクトリにファイルを書いたがマーカーを忘れた」場合のための決定論的なネットです。生成されたドキュメントに*言及している*マーカーなしの返信(キーワードゲート:拡張子、"Word"/"Excel"/"PowerPoint"、檔案/簡報/報表などのzh-TW用語)の後、ゲートウェイはエージェントディレクトリをスキャンし、見つけたものを宣言されていたかのようにそのまま配送します:

| 制約 | 値 |
|---|---|
| ファイルタイプ | `docx xlsx pptx pdf csv odt ods odp`のみ——`.md`/`.txt`/`.json`は決して対象外(エージェントはこれらを内部状態として書くため) |
| 新しさのウィンドウ | mtimeが15分以内 |
| 再帰の深さ | ≤ 3、`attachments/`、`sessions/`、`logs/`、`memory/`、隠しディレクトリはスキップ |
| 返信ごとの上限 | 3ファイル、新しい順 |
| 重複排除 | サニタイズ済みの名前+サイズがすでにアーカイブに存在するファイルは、以前のターンで配送済み——スキップ |

キーワードゲートは配送のヒューリスティックであり、セキュリティ判断ではありません。フェンスはあくまで`validate_deliver_path`です。スイープの失敗はログに記録されてスキップされます——このネット自体が返信の新たな失敗モードになることは決してありません。

## アーカイブ、ファイルページ、プレビュー

配送されるすべてのファイルは、チャネル送信の**前に**エージェントの`attachments/`ディレクトリへコピーされます。そのため送信が失敗しても、成果物はダッシュボードのファイルページで閲覧可能なままです(すでに`attachments/`内にあるファイルは重複コピーされません)。

ファイルページは`GET /api/files/preview`経由でオフィスドキュメントをブラウザ内でプレビューします:

- PDFと画像はネイティブにインラインでストリームされます。
- `docx/xlsx/pptx/odt/ods/odp/csv` は、検証済みスナップショットから LibreOffice（`soffice --headless`）で PDF に変換します。リクエストごとの専用ディレクトリと独立した LO プロファイルを使用し、タイムアウトは 60 秒です。変更可能な添付パスや従来の mtime キャッシュは使用しません。変換元と変換結果はそれぞれ 2 MiB まで、ダウンロードは 20 MiB までです。通常のダウンロードと直接プレビューも、返すバイト列そのものの内容と権限を検証します。これらの添付操作には Unix の no-follow ディレクトリハンドルが必要で、他のプラットフォームでは拒否します。
- LibreOfficeが見つからない場合→明示的な503 JSONメッセージを返し、壊れたバイトストリームは決して返しません。
- ダウンロードエンドポイントと同じJWT認証とパスフェンスが適用されます。

## Provenance (I-2b)

`attachments/`に置かれるすべてのファイルは、以前はフラットなディレクトリ一覧の中の匿名の1行にすぎませんでした——顧客からの受信添付と、エージェントがgoal taskのために生成したレポートは区別がつきませんでした。provenance台帳(`artifacts.jsonl`。`tool_calls.jsonl`や`task_changes.jsonl`と並ぶ場所にあります)が、各ファイルがどこから来たのかを記録するようになりました。**書き込まれたその場で**記録され、後から推測されることは決してありません:

| 由来 | 意味 |
|---|---|
| `declared` | エージェントが`📎DELIVER:`を通じて手渡しで配送したもの。 |
| `swept` | `sweep_undeclared_deliverables`が回収したもの——ファイルは存在するが、マーカーが忘れられていた。 |
| `uploaded` | 人間がチャネル経由で送ってきたもの(受信添付)。 |
| `produced` | タスク自身のchange ledgerから読み取り時に導出されるもの——artifactsファイル自体には永続化されない。 |
| `unknown` | 証拠がそこまで届かず判断できないもの。誠実な保留であり、推測ではない。 |

タスクへの帰属も同じ考え方で二層に分かれています:その行(またはタスク自身のchange ledger)がタスクを直接名指ししていれば`exact`、claim→reviewの時間窓の慣例(`tasks.changes`が使うのと同じ窓)だけでそこに置かれた場合は`inferred`です——ダッシュボードは推論を事実として提示することは決してありません。マージに使うkeyはファイルの実際のbasenameであり、CJKでサニタイズ済みの表示名ではありません。そのため由来の異なる2つのファイルがたまたま同じ文字列にサニタイズされても、1行に統合されることはありません。起動時のbackfillが、台帳が存在する前のファイルの履歴を埋めますが、それも既存の証拠(declared/sweptの記録、`task_changes.jsonl`)が届く範囲までです——判断できないものは方向を決めつけず`unknown`のままにされます。

この台帳を読む画面は2つあります:

- **タスク詳細 → 成果物(產物)タブ**:タスクに紐づく各ファイルを、由来・ラウンドとともに一覧表示し、(アーカイブ済みコピーがある`uploaded`/`declared`/`swept`の行には)ダウンロードリンクを添えます。エージェントが書き込んだがアーカイブされなかったファイルは、切れたダウンロードリンクの代わりに書き込まれたパスを表示します。
- **ファイルページ**:由来(來源)列とタスクフィルターがあり、「先週の成果物を探す」がスクロールではなくフィルター操作になります。

**既知の制限**:goal-loopのディスパッチ経路は、生成したファイルのダウンロード可能なコピーをまだアーカイブしません——これらの行は`produced`として現れても、背後に添付ファイルがない場合があります。このギャップを埋める作業は今後のwaveで追跡されています。

### 会話履歴の添付ファイル

Unix gateway では、閲覧可能な添付ファイルを名前・サイズ・種類・ダウンロードボタン付きのカードで表示します。PNG、JPEG、GIF、WebP はサムネイルを表示します。PDF と Office はダウンロード後に文書ビューアーで開きます。履歴画面では LibreOffice 変換を行わず、ファイル画面の既存プレビューはそのまま利用できます。

既存の Markdown リンクはサーバー側で解析します。作業フォルダーを指す DELIVER は、同じ社員の添付フォルダーへの一意で正確なアーカイブ記録がある場合のみ利用できます。削除済みファイル、移行前の別ホストのパス、版を特定できない再利用パス、安全でないパスにはダウンロードカードを出しません。ブラウザーにはホストのパスを渡さず、不透明な参照 ID を返します。

リクエストは現在のログイン JWT を Authorization ヘッダーで送信し、URL にトークンを含めません。会話履歴と既存のファイル所有者・閲覧者の権限を毎回確認します。外部会話のマスク表示では原本を公開しません。制限付き閲覧者には信頼できる WebChat 所有記録または既存タスクの権限が必要で、手入力のパスだけではアクセスできません。ID は 30 分または gateway 再起動で失効するため、履歴を再読み込みしてください。非 Unix gateway はディレクトリ記述子を使った安全な読み取りが未実装のため、この新しい配信経路を拒否します。

ダウンロードは 20 MiB、画像プレビューは 2 MiB が上限です。大きい画像はダウンロードのみとなり、カードが画面に近づいても自動取得しません。Gateway は開いたファイルのサイズを確認して上限付きスナップショットを作成し、そのハッシュを出所記録と必要なワークフロー受領記録に照合してから、同じ内容を返します。応答には `Content-Length` を付け、ブラウザーも長さを確認して上限を超えたら読み取りを中止します。アップロードには予測できない UUID 名と排他的な新規作成を使うため、同名ファイルを同時に送っても上書きされません。

履歴は SQL `LIMIT` で最新のメッセージを直接取得します。リクエストごとに永続権限索引を開き、アーカイブ名と元パスで検索します。各応答はメッセージ本文の合計 2 MiB、1 件あたり 1 MiB、添付 32 件、参照の検査 256 件が上限です。履歴投影はユーザーごとに同時 2 件、毎分 30 回、全体では同時 4 件までです。ダウンロードはユーザーごとに同時 2 件、全体で同時 4 件までです。ユーザーごとの毎分 120 MiB の枠は、実際の転送量ではなくリクエストのサイズ上限で予約します。制限を超えたリクエストは利用不可となるため、時間を置いて再試行してください。

添付 ID は独立したキャッシュを使い、ユーザーごとに最大 512 件を LRU 方式で保持します。使用頻度の低い ID は通常の 30 分より早く失効する場合があります。全体のキャッシュに保持できないときは、使えない ID を発行しません。内容ハッシュを持たない旧成果物は制限付き閲覧者に提供せず、Admin／完全履歴モードの従来の旧ファイル規則は維持します。Windows など非 Unix gateway はこの経路を拒否します。本修正のリモート builder での Rust gateway テスト、ネイティブ環境の挙動、実際のブラウザーでのダウンロード受け入れ確認は未実施です。

WebChat は書き込みや処理の開始前にアップロード全体を検証します。1 回につき添付は最大 8 件、デコード後の合計は 20 MiB、ファイル名は 255 bytes、MIME ラベルは 128 bytes までです。WebSocket メッセージとフレームは 28 MiB に制限し、添付パーサーは巨大な配列を作る前に件数超過を拒否します。Base64 が不正な場合や上限超過では全件を拒否します。ユーザーごとに毎分 8 回、32 ファイル、80 MiB までです。永続的な予約により、新規アップロードをユーザーごとに 512 MiB／2,048 ファイル、全体で 4 GiB／16,384 ファイルに制限します。空ファイルも件数に含み、失敗や中断した予約も計上します。手動で削除しても割り当ては自動回復しません。

ダウンロード応答の総期限は 30 秒です。クライアントが本文を一度も読まなくても、独立したタイマーがスナップショットと同時実行枠を解放します。転送層には最大 64 KiB の独立したコピーを渡すため、一つのチャンクを保持してもスナップショット全体は残りません。期限切れの応答は失敗し、再試行には改めて権限確認と通常のリクエスト枠が必要です。

履歴添付の権限確認には、アーカイブ名、所有者、内容ハッシュ、サイズ、元パスを保存する索引付きの永続 SQLite 記録を使います。表示・監査用 JSONL のローテーションや切り詰めで既存の権限記録が失われることはありません。データベース障害時は制限付きアクセスを拒否し、WebChat アップロードは権限記録の保存後に成功を返します。信頼できる内容の結び付きがない旧ファイルは、引き続き制限付き閲覧者には提供しません。

初回利用時は、保持されている直前と現在の監査ファイルを一つのトランザクションで移行します。合計上限は 32 MiB、1 行は 64 KiB です。読み取り不可、不正形式、上限超過では部分的な権限を作らず移行を中止します。保持された記録を修復してから再試行してください。以前のローテーションですでに失われた記録は自動復元できません。移行後の監査ファイル変更は権限データベースを上書きしません。
