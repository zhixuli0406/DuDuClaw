# セキュリティ防御

管理者以外のメンバー（Employee、Manager）は、サイドバー、会話フィルター、コマンドパレット、WebChat の `@` 候補、その他のスタッフ選択欄で、`agents.callable` が選択可能と明示したスタッフだけを表示します。メイン AI は、その応答が明示的に選択を許可した場合を除き表示しません。全一覧は、`agents.callable` が現在の Admin 権限に基づいて `unrestricted: true` を返した場合のみ表示します。Personal のローカル管理者も含みます。初回読み込み中や取得失敗時は、すべてのアカウントで空になります。ページ表示中は 60 秒ごと、再表示時、および選択メニューを開く際に権限を更新します。更新中は同じユーザーの確認済み一覧を保持し、失敗した場合は消去します。ファイルと設定の選択欄には直接のアクセス権も必要で、チームの呼び出し権はファイルや設定の権限を追加しません。新しい会話は引き続きサーバーが担当を決定します。この dashboard の表示制限は RPC の認可を変更しません。

## `code_map` は社員自身のディレクトリだけを走査（v1.81）

v1.81 より前の `code_map` は、MCP サーバーが読めるあらゆるディレクトリ（既定は作業ディレクトリ）を走査できたため、呼び出し元はホスト上のどこのソースでもマップを作り、シグネチャを読めました。現在は次のとおりです。

- 呼べるのは識別できた AI 社員だけです。共有の内部キーには `DUDUCLAW_AGENT_ID`、社員専用キーには対応する `agents/<id>/agent.toml` が必要です。外部キー、管理者キー、スコープだけを持つ単体モードのキーは説明付きで拒否されます。`code_map` は「社員として動くツール」にも加わり、これらの呼び出し元の `tools/list` には表示されません（単体モードの一覧は 24 から 23 ツールになります）。
- `root` の既定は社員自身のディレクトリで、相対パスもそこから解決します。`..` は拒否します。解決後のディレクトリは、データファイル系ツールと同じルート（`<home>/agents/<id>`、その `attachments`、`<home>/attachments`、`config.toml [files] allowed_roots`）の内側でなければなりません。
- 各ファイルは、検査済みのルートからファイルディスクリプタで 1 階層ずつ（各階層 `O_NOFOLLOW`）開いて読みます。シンボリックリンク、通常ファイル以外、ハードリンク数が 2 以上のファイル、サイズ上限を超えるファイルは飛ばし、内容は検査したその記述子から読みます。走査はマウントをまたぎません。各階層の `st_dev` が一致する必要があり、Linux ではカーネルのマウント id も比較するため、同じファイルシステム上の別ディレクトリの bind mount（`st_dev` が同じ）も拒否します。Linux はカーネルが対応していれば `openat2`（`RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS | RESOLVE_NO_XDEV`）を使い、常に `statx` の `STATX_MNT_ID`（または `/proc/self/fdinfo` の `mnt_id`）を比較します。どちらからもマウント id が得られない場合は走査を拒否します。macOS は `st_dev` と各階層のリンク非追従オープンに依存し、Windows はすべての reparse point（シンボリックリンク、ジャンクション、ボリュームマウントポイント）と多重リンクのファイルを拒否します。
- 拒否のたびに `tool_calls.jsonl` に 1 行（`refused: true`、要求されたルートと理由）を書き、それ以外は記録しません。

## 社員を作成できるのは誰か（v1.81）

`[permissions] can_create_agents` の既定が `true` になるのは `main` 社員だけになりました。それ以外のロール、およびロールを識別できない社員では、キーがなければ `false` です。MCP の権限ゲートは `create_agent` と `spawn_ephemeral` にこの実効値を適用するため、キーを書いたことのない main 以外の社員はもう社員を作成できません。明示した設定は `true`・`false` のどちらでも優先されます。

- 新しい社員：ダッシュボードと `duduclaw agent create` は `role = "main"` のときだけ `true` を書きます。evaluator テンプレートと有料チームキットは main 以外のすべてのロールに `false` を書きます。
- 社員が MCP `create_agent` で作成した社員は常に `can_create_agents = false` です。そこで `role = "main"` の社員を作れるのは、`can_create_agents` が有効な現在の main 社員だけで、それ以外の呼び出し元は何も書き込む前に拒否されます。
- v1.68 の起動時マイグレーションは、main 以外の社員の `can_create_agents = false` を `true` に変えなくなりました。
- `agents.update` の管理者専用フィールド検査も同じ実効値を比較するため、管理者でない Owner が、キーのない main 以外の社員に `true` を書いて作成権限を有効にすることはできなくなりました。

**動作の変更：** `agent.toml` に `can_create_agents` キーがない main 以外の社員は、v1.81 より前は社員を作成できましたが、現在は拒否されます。維持するには、管理者がダッシュボードの「工具與權限」で有効にしてください。

## 顧客の会社情報（v1.80.0）

会社名とロゴは署名検証済みの販売代理店ブランドから分離されています。`company.get` と `company.update` は明示的な管理者 RPC です。`company.update` は名前と任意のロゴ削除だけを受け付け、旧 `logo_base64` フィールドを拒否します。会社名では制御文字、行区切り文字、Unicode 書式文字（`Cf`、双方向上書き・分離制御文字を含む）を拒否します。更新時は既存の設定書き込みロック内でも現在の本人情報を再確認します。`company_info` 監査は実行者、メソッド、結果を記録し、画像と会社名は含みません。詳細設定のナビゲーションとルートも管理者専用で、移動した設定の RPC 権限は緩和しません。

ロゴのアップロードは `POST /api/company/logo` のみを使用し、本文は 1 MiB 以下の PNG、JPEG、WebP の生バイナリーです。接続元 IP の制限を通過した後、本文を読む前に `Authorization: Bearer` access token を検証し、現在の管理者アカウントを再確認します。未認証・権限不足の場合は本文を読まずに 401／403 を返し、Cookie 認証は受け付けません。ルート専用の `DefaultBodyLimit` とストリーム読み取り時のハード上限でサイズを制限します。各アカウントと各 TCP 接続元 IP につき 60 秒間で六回までです。IP 制限は JWT 検証より先に適用し、超過時は個別の監査記録を作らず 429 を返すことで、未認証リクエストによる監査記録の大量生成を防ぎます。この制限を通過したリクエストと結果を監査します。アカウント制限は JWT と現在の管理者権限の検証後に適用します。転送ヘッダーを信用しないため、プロキシ配下の利用者はその IP の枠を共有します。本文読み取りは 30 秒でタイムアウトし、同時アップロード処理は二件までです。全体の WebSocket メッセージ上限は 1 MiB のままです。

宣言された Content-Type は実際のマジックバイトと一致する必要があります。gateway は画像コンテナー全体を検査し、末尾の追加データ、SVG、GIF、アニメーションを拒否します。ヘッダーや寸法の読み取りも含め、デコーダーを初期化する前に 4096 × 4096 の寸法上限と 64 MiB の割り当て上限を設定し、メタデータを除いた 256 × 256 以内の PNG に再エンコードします。画像は内容ハッシュで命名して原子的に公開し、参照は既存のロック付き設定保存処理で記録します。ロック内での管理者再確認と監査も維持します。

公開 `/api/company` は会社名とロゴ URL だけを返します。`/api/company/logo/{sha256}.png` は固定の小文字ハッシュ名だけを受け付けます。ファイルを一度だけ開き（Unix では `O_NOFOLLOW`）、同じファイル記述子で通常ファイル、リンク数が一つ、サイズ制限内であることを確認してから、上限付きで読み取ります。PNG の検証でもデコーダー初期化前に 256 × 256 の寸法上限と 1 MiB の割り当て上限を設定します。内容とハッシュを検証した後に限り、`image/png`、`X-Content-Type-Options: nosniff`、1 年間の immutable キャッシュで配信します。公開会社リクエストは TCP 接続元ごとに制限されます。ロゴ削除後も旧画像をキャッシュと招待メール用に保持するため、非公開ファイルやデータ削除の機能ではありません。招待 HTML は会社名をエスケープし、検証済み招待 URL の origin とベースパスだけを画像 URL に使用します。社員の権限と代理店の署名検証は変更しません。

実際のブラウザー・メールの受け入れ検証はまだ実施していません。実装だけでプラットフォームや外部サービスの検証済みとはしません。
すべてのビルドの管理機能は検証済みライセンスを上限とします。`DUDUCLAW_EDITION` と組み込みホストのエディション設定は権限を狭めることしかできず、昇格要求は無視され、入力元ごとにプロセス内で一度だけ警告します。有効なライセンスがなければ個人版となり、`users.*`、`departments.*` などの管理 RPC も拒否されます。本番の判定処理は Debug assertions が有効でも昇格を許可しません。専用テスト API は非デフォルトの `test-edition-override` feature と Debug assertions の両方を必要とし、release ビルドではこの feature を拒否します。
公式 GitHub 更新は minisign の trusted comment `duduclaw v{version} {archive-file-name}` をプラットフォーム・アーキテクチャまで厳密に照合します。Pro 更新は `duduclaw-pro` と独自の固定公開鍵を使います。ペイロード署名とコメントを保護する global signature の両方が必要です。すべてのアーカイブ導入経路で、検証器が生成した `VerifiedReleaseIdentity` が必須となり、アーカイブのダイジェスト、版、ファイル名、署名済みコメントを結び付けます。整合性確認だけでは導入できません。置換前に実行ファイルの版も確認します。保護アップグレードでは root でダウンロードしたコードを実行せず、ビルド時の固定形式レコードを読みます。ヘッダー `NUL + DUDUCLAW_RELEASE_ID:V1:`、安定版 `X.Y.Z`、末尾 `NUL + DUDUCLAW_RELEASE_END + NUL` の完全なレコードが正確に一つ必要です。すべての `DUDUCLAW_RELEASE_ID` がこの形式に一致しなければなりません。欠落、不正、重複、競合、マーカーのない旧版は拒否します。署名前に実際のアーカイブ内の実行ファイルを解析し、tag と照合します。Pro のパッケージ作成にも適用します。通常更新は `version` 出力を確認します。不一致は置換および保護版の intent/floor 更新前に中止します。この検査には修正済みの更新プログラムが必要です。旧版の更新プログラムは管理者が確認した手動導入で先に更新してください。

Provider は `verify_release_archive_with_pubkey(bytes, checksum, signature, pinned_key, expected_version, expected_file)` の結果を `install_verified_binary(bytes, &identity)` に渡してください。期待する版とファイル名は選択したリリース情報から取得し、ダウンロードした署名から流用しないでください。旧来の一引数の導入 API は廃止しました。
Google Cloud 会議文字起こしは管理者が別途保存した暗号化サービスアカウントキーを使い、社員や Workspace の認証を継承しません。認証情報の保存・削除専用 RPC は拡張へのディスパッチ前に現在の管理者権限を確認し、汎用設定更新は該当フィールドを拒否します。生の設定エディターではマスクの維持か削除のみ可能です。音声の送信前にファイルロック付きの削除記録を永続化します。削除失敗時は回数上限付きでバックオフし、起動時と定期処理で成功または HTTP 404 まで再試行します。有効な認証情報とバケット権限が必要であり、ライフサイクル期限も追加の備えとなります。送信前の音声マスキングは行いません。[会議文字起こし](73-meeting-transcripts.md)を参照してください。

文字起こし設定と生の設定の書き込みはコミットロック内で現在の管理者権限を再確認し、ユーザー DB が利用できない場合は拒否します。認証情報の保存・削除操作は操作者、操作、結果のみを監査に残し、秘密は記録しません。削除は現在設定されているバケットに限定し、不一致の記録は保持して件数のみ警告します。Unix の削除記録ディレクトリは 0700、通常の記録・ロックファイルは 0600 とし、シンボリックリンクをたどりません。OAuth トークン応答は型付きの消去可能な領域で処理し、所有する応答バッファも消去します。
## Gateway A2A アクセス（v1.80.0 から）

`POST /a2a` は Dashboard Bearer JWT 認証を再利用し、アカウントの有効状態、認証情報の失効、強制パスワード変更を確認します。旧共有管理者 token や MCP HTTP-server API key は受け付けません。タスク操作にはメソッド認可表、現在の社員権限、入力スキャン、接続元 IP と呼び出し元ごとのレート制限、安全監査を適用します。`[a2a] exposed_agents` は初期状態で空であり、アクセス範囲を狭めるだけです。不正または読み取れない設定ではアクセスを拒否します。

署名付き公開カード `/.well-known/agent-card.json` は、明示的に公開された社員の有効なスキルだけを記載します。署名はカードの完全性を検証し、呼び出し元に権限を付与しません。`GetExtendedAgentCard` は認証が必要で、アクセス権も増えません。A2A の取得・一覧・取消には、同じ認証済みアカウントが A2A 経由で作成したタスクであること、社員が現在も公開されていること、現在の社員 ACL とタスク閲覧対象の確認が通ることが必要です。所有者はタスクに永続保存され、子タスクにも引き継がれます。通常の Dashboard のタスク一覧・読み取り・編集・削除・停止・コメント・添付・活動記録・プッシュイベントにも同じ所有者制限を適用します。Admin の例外や別の管理者上書き経路はありません。削除後も所有者記録を保持し、残存する証跡を保護します。Dashboard 所有者の主体を持たない外部 MCP 呼び出し元は拒否し、認証済みで実行担当に指定された社員には必要なタスクアクセスを残します。取消は既存のタスクツリー停止機構を使います。停止が保留中または不確かな状態は、外部プロセスや副作用の物理的な停止を証明しません。これらは製品の入口での制限であり、ホストやデータベースへの直接アクセスは対象外です。

公開探索、認証失敗、認証済み RPC は、それぞれ独立した IP ごとの毎分 120 件の枠を使います。全体の上限も分離し、順に毎分 600、600、1,200 件です。RPC には呼び出し元ごとの毎分 60 件の制限も適用します。匿名の通信は認証済み RPC の枠を消費しません。各 IP／呼び出し元 limiter は最大 10,000 キーを保持し、満杯では新規キーを拒否します。期限切れキーの削除にも実行頻度の上限があります。

`forward.recent` と `forward.chain` は削除済み A2A タスクを含め、保持された所有者記録を確認します。Admin も他の呼び出し元の所有権を回避できません。`tasks.flow_metrics` は他の A2A 所有者のタスクを除外してから件数・時間・ラウンド数を集計します。A2A 以外のタスクのアクセス規則は変わりません。

タスク DB のスキーマ移行前に、A2A 構造や再送記録が存在する場合は、読み取り可能な `task_access_principals` テーブルを必須とします。欠落または読み取り不能なら DB を開かず、残存タスクから空の登録表を再作成しません。一貫したバックアップから完全な所有者記録を復元してください。新規 DB と A2A の痕跡がない旧 DB は引き続き移行できます。

既存の `keys/a2a-signing.ed25519` はシンボリックリンクではない通常ファイルである必要があります。Unix では gateway の実効ユーザーが所有し、モードが正確に `0600` であることも確認します。Windows では Unix の所有者・モード確認を省略します。不正なファイルは上書きや権限の自動変更をせず拒否します。接続元 IP の枠を先に確認・記録し、通過した要求だけがグローバル枠を消費します。接続元で拒否された要求は他の接続元向けの容量を消費しません。

`trusted_proxy_cidrs` の初期値は `[]` で、有効な IPv4／IPv6 CIDR を最大 32 件指定できます。管理下の直接接続プロキシだけを設定してください。一致したプロキシは `X-Forwarded-For` を単一の client IP に上書きする必要があります。欠落、重複、IP の連鎖、不正値は拒否します。それ以外の接続元が送るヘッダーは無視します。未設定では、同じプロキシ配下の client が通信種別ごとにプロキシ IP の枠を共有します。例えば `192.0.2.10` が直接接続プロキシの場合に限り、`trusted_proxy_cidrs = ["192.0.2.10/32"]` を指定します。この設定は呼び出し権限を付与しません。

認証済みアカウントと `messageId` を永続的な一意キーとして扱います。同じ完全な `params` を再送すると元のタスクを返し、同じ id で異なるパラメーターを送ると拒否します。JSON オブジェクトのキー順序は判定に影響しません。タスクを削除しても id は再利用できず、再送による再作成も行いません。再送時も現在の認可が必要です。

バージョンは `1.0` のみ受け付けます。欠落・空・非対応のバージョンには `-32009` を返します。ストリーミング、プッシュコールバック、完了まで待機する応答、タスク継続は非対応です。設定とリクエスト例は [ACP と A2A](19-agent-client-protocol.md) を参照してください。
WebChat は socket が書き込み可能になってから、実際に回答した AI 社員へのアクセス権を再確認します。短い `BEGIN IMMEDIATE` トランザクションで ACL の世代を確認し、同期的な `start_send` までを保護することで、権限変更とフレームの受け渡しに明確な順序を設けます。トランザクション中に socket の準備や非同期 flush を待ちません。権限の失効や読み取り失敗時は配信を拒否します。それより前に配信を認めたデータは、後の失効で取り戻せません。

Admin 以外の Dashboard 応答では、同じ最終フェンス内で設定更新処理と共通の `config.toml.lock` の共有ロックと registry の読み取りロックも取得します。現在の既定の従業員、ロール、状態、呼び出し権限を再確認し、`start_send` またはアシスタント履歴の公開が完了するまで保持します。ロック競合時は待機せず配信を拒否します。別の policy リビジョンを追加せず、共有ロック内の再検証で保護します。`config.toml` が存在しない、または無効な場合、非 Admin の対象認可は拒否されます。新規環境では有効な最小設定を明示的に作成します。Admin と匿名 widget の既存ルールは変更しません。この保証はロック規約に従う製品の書き込み経路が対象であり、ロックを無視する外部編集は対象外です。

アシスタントの履歴行は確認待ちの非表示マーカー付きで保存し、最後の権限・ソース検査を通過してから公開します。配信を拒否した行は本文の消去に失敗しても非表示を維持し、後で権限を戻しても表示しません。通信の失敗だけでは認可済みの返信を取り消しません。ユーザー行には `client_msg_id` を保存するため、`turn_accepted` が失われても、正確な session とユーザーメッセージの識別子で復元できます。本文や前方一致で推測しません。
**Codex の外部設定検査（v1.80.0 から）：** 外部設定がないか MCP を定義していなければ、通常の社員、Explore、utility、Task Sandbox、Discovery は実行できます。MCP の検出、既存設定の読み取り・解析失敗ではソース名を示して拒否します。明示した Codex judge の拒否は判定失敗となり、既定の judge では再試行しません。起動前のローカル／キャッシュのスナップショット検査であり、その後のクラウド更新を完全に隔離する保証はありません。[検査対象と制限](../../architecture/extension-gates.md)。

Enterprise [チーム履歴 API](68-manager-team-history.md)（v1.76.0）は、既存のスタッフ権限とは独立して現在の報告関係を確認します。外部本文は閲覧時にマスクし、開示ごとに永続的なハッシュチェーン監査が必要です。設定オフ、出所不明、導入済みモデルの故障、監査失敗では本文を返しません。regex のみなら `ner: false` を明示し、氏名や住所が残る場合があります。ホスト／DB への直接アクセスは製品経路の保護対象外です。

## リモート MCP OAuth 認可（v1.80.0）

OAuth コード交換、更新、access token 検証では、元の同意キーと設定を再確認します。削除、期限切れ、変更、読み取り失敗では認可を維持できず、無効な更新や使用済み refresh token の再利用でファミリー全体を削除します。権限は同意キーや直前の更新トークンを超えません。紐づけ情報のない旧認証情報は再認可が必要です。RFC 7009 `/oauth/revoke` は既存の公開クライアント方針を使い、クライアントとの紐づけを確認して access token を含むファミリー全体を取り消します。一覧・取り消しは Admin 専用で、変更は発行処理と同じトランザクションロックを使い、一覧は認証情報を返しません。実行中のツールは中止しません。CLI の `ddc_refresh_*` は stdio 専用で、HTTP と SSE は拒否します。[リモート MCP](../../guides/ja-JP/remote-mcp.md) を参照してください。共通ストアのテストは成功し、CLI／gateway／ブラウザー検証は未実施です。

OAuth は承認ごとに使用済み更新トークンのダイジェストを含むアクセス／更新レコードを最大 2,048 件、全体でトークン 16,384 件、承認 1,024 件、保存容量 16 MiB に制限します。上限到達時は現在の更新トークンを消費せず発行を拒否します。使用済みダイジェストは期限まで保持し、再利用検出とローテーション済みトークンによる失効を維持します。HTTP 認証前に TCP 接続元 IP ごとに毎分 120 回、Bearer 値ごとに毎分 60 回を制限し、認証直後に既存のクライアント制限を適用します。転送 IP ヘッダーは信頼せず、プロキシ配下のクライアントは接続元枠を共有します。トークン交換にはクライアントごとに毎分 12 回の枠もあります。制限テーブルと保存用バックグラウンド処理数も有界です。アクセス検証は読み取り専用で、許可された利用の最終使用時刻はブロッキング処理用ワーカーで毎分最大 1 回更新します。承認一覧の設定エラーは空の一覧ではなく利用不可として返します。ダッシュボードの失効は操作者、承認 ID、アプリ名、権限、結果を監査し、認証情報やダイジェストは記録しません。監査書き込みに失敗すると、失効が適用済みの場合もエラーを報告します。
## MCP スタッフの本人性確認

`DUDUCLAW_AGENT_TOKEN` は HMAC-SHA256 で申告された `DUDUCLAW_AGENT_ID` をインストール環境の `identity.key` に結び付けます。`[delegation] require_identity_token` のデフォルトは `true` に変更され、設定を省略した既存環境にも適用されます。トークンの欠落や不正は MCP 起動を拒否します。設定ファイルを読めない、TOML が不正、値が真偽値でない場合も、有効なトークンがあっても拒否します。共通検証層はシステム送信者と予約済みキュー送信者を拒否するため、署名済みの `dashboard` や `cron` でも社員の名前空間や MCP 起動は許可されません。

**委任コンテキスト。** 監査の帰属と認可を分離します。一時社員は検証済みの実行社員の権限を継承し、チームの引き継ぎと共同操作も実行社員として認可します。ホスト署名は版、実行社員、委任者、起点、深さ、取得可能な実行／タスク／ターン識別子、有効期限、ランダム nonce を結びます。システム名と予約名は社員として扱いません。署名の起点に既知のシステム名を使えるのは、深さがゼロで委任者と実行社員が同じ場合だけです。チャネルとダッシュボードの起点はホストが解決した依頼者から決めます。最初の委任をキューに入れる前に CLI が起点を実行社員へ正規化し、後続の停止・リース検査で社員チェーンの起点を維持します。欠落・改ざん・期限切れ・再利用された証明では追加の委任を拒否し、通常のツールは実行社員として利用できます。nonce は一つの MCP プロセスだけが取得でき、そのプロセス内の複数の呼び出しでは期限まで有効です。MCP 子プロセスの再起動後は社員を再起動して新しい証明を取得してください。取得記録は `delegation-context-claims/` に保存し、自動削除はまだありません。証明は秘密の環境変数で渡し、引数には含めません。第三者 MCP の上流には証明も委任情報も渡しません。Claude は DuDuClaw MCP 子プロセスだけに注入し、安全な環境変数転送に非対応の旧 Codex では委任できません。gateway の OS アカウントや署名鍵に無制限にアクセスできるプロセスの隔離は対象外です。

ソフトモードには `require_identity_token = false` と `[delegation] identity_token_grace_until` の両方が必要です。期限は引用符付き RFC3339 UTC（`Z` または `+00:00`）で、現在より後かつ 30 日以内に限定します。未指定、不正、非 UTC、期限切れ、上限超過では厳格モードへ戻り、プロセスごとに一度エラーを記録します。検証時に期限を再確認するため、キャッシュ済みの false でも延長されません。Unix では開いた descriptor の所有者が実効 UID と一致し、ハードリンク数が 1 であることも要求します。macOS は拡張 ACL の全エントリーを拒否し、ACL 取得エラーも拒否します（ENOENT は ACL なし）。他の Unix の拡張 ACL は検査しません。一度でも home の期限切れ・不正を検出すると、そのプロセスでは同じ home の厳格モードを維持し、時計の巻き戻しや期限の変更でも解除しません。この状態はプロセス再起動後には保存されません。

**ネイティブのリモート MCP ブリッジ。** `mcp-remote-bridge` は猶予期間中でも、`--agent` と一致する署名済みの `DUDUCLAW_AGENT_ID` / `DUDUCLAW_AGENT_TOKEN` を必須とします。リモートストアの読み取り前、入力フレームごと、refresh lock の待機後、HTTP 送信直前に検証します。トークンの欠落・偽造や別の社員の有効な身分を拒否します。ホストは proxy が不要な場合も、起動ごとの有効な bridge 設定に署名済みの身分を追加します。元の第三者設定からホスト身分を指定することはできません。アップグレード後は既存の社員プロセスを再起動し、有効な設定を再生成してください。

旧ソフトモードは `require_identity_token = false` と有効な猶予期限を明示した場合だけ有効で、ゲートウェイは起動のたびに警告します。正常なキーがある場合、このモードは未署名や無効な社員 ID の申告を受け入れるため、なりすましの危険が残ります。キーと初期化マーカーが両方ない場合だけ検証を無効とします。起動時、既存キーと新規キーの両方に `identity.key.initialized` を記録します。記録後にキーが失われた場合は両モードで拒否し、再生成しません。読めない、通常ファイルでない、形式や権限が不正なキーは常に拒否し、初期化できなければゲートウェイの起動を停止します。

キーの作成はプロセス間ロックの下で行い、予測不能な名前で一時ファイルを排他的に作成します。作成時点で権限を制限し、内容をディスクに同期してから、既存の宛先を上書きしない原子的操作で公開します。Unix は `0600` を要求し、最終パス要素のシンボリックリンクを拒否し、親ディレクトリも同期します。Windows は `FILE_FLAG_OPEN_REPARSE_POINT` で最終要素を開き、開いた handle の種類、reparse 属性、所有者、DACL を検証します。許可 ACE の対象は現在の所有者、SYSTEM、Administrators に限定します。既存の Windows キーが広い ACL を継承している場合、起動前に権限を修復してください。自動で書き換えません。

**アップグレードと復旧**：元の 32 バイトのキーと初期化マーカーを一緒にバックアップしてください。ゲートウェイを再起動して社員の MCP 設定を再発行し、古い社員プロセスも再起動します。設定を省略した環境は直ちに厳格モードになります。短い移行期間が必要なら `false` と有効な猶予期限を明示し、再起動完了後に `true` に戻すか設定を削除してください。キーの紛失や破損では、マーカーを削除せず元のキーと権限を復元します。新規キーの公開前にマーカーを同期するため、その間の中断は管理者による復旧を必要とします。未使用と確認できた新規環境だけ、管理者が孤立したマーカーを削除して再試行できます。既存環境の復旧には使わないでください。

マーカーとロックファイルも身元ファイル hook で保護します。ただし OS アカウントの隔離ではありません。ゲートウェイと同じアカウントで無制限のファイル権限を持つプロセスは、両ファイルの変更、キーの読み取り、トークン生成が可能です。本修正で Windows reparse／ACL テストはクロスコンパイル済みですが、ネイティブでは未実行です。
## リモート MCP と OAuth の境界

両世代の MCP クライアントは既存のツール制限と第三者ツールの効果分類を維持します。
不正な `x-mcp-header` schema は一覧から除外します。初回の探測では対応する旧バージョンを
選択できますが、接続後に bridge が `-32022` を受けると操作を拒否し、再送せず接続を
無効にします。会話の再起動後に再協商、ツール一覧の取得、権限検査をやり直します。
API クライアントも `tools/call` で `-32022` を受けた場合は呼び出しを終了し、そのクライアントの
後続リクエストをすべて拒否します。host は再接続、ツール一覧の取得、権限検査をやり直します。
初回のハンドシェイクと独立した一覧取得時のバージョン復旧は維持します。
旧 HTTP+SSE の endpoint は認証先と同一 origin に限定します。新しい API HTTP 接続は
毎回独立して探測し、URL をキーとしたグローバルなバージョンキャッシュを使いません。
bridge は自身の接続の協商状態だけを保持します。

OAuth はコード交換やエラー表示の前に callback の issuer を検証します。CIMD は管理者が
設定した公開 HTTPS 文書を使い、正確な client ID と許可された callback URI を要求します。
選択した文書が不正なら拒否します。探測時と保存済みの OAuth resource は、path を含む
MCP エンドポイントの canonical resource と完全に一致し、query と fragment を含まない
必要があります。同一 origin の別パスも拒否し、不一致の古い認証情報は再接続が必要です。
PKCE、サーバーごとの暗号化された認証情報、送信先 URL の検査を維持します。

API クライアントの MRTR 入力は host が宣言した機能に限り、利用者の同意を自動で代行しません。
bridge は modern の対話機能を宣言せず、状態だけの応答を含むすべての `input_required` と、
下流からの `requestState` または `inputResponses` を含むリクエストを拒否します。
継続データ全体の外部送信・承認検査を元の承認済み呼び出しに結び付ける保護が整うまで、
bridge の MRTR は利用できません。[MCP プロトコル](../../guides/ja-JP/mcp-tools.md)も参照してください。
## 会社テンプレートの管理（v1.80.0）

管理者は両エディションでスタッフとチームのテンプレートを閲覧できます。詳細と必須の確認画面には、全メンバーの `SOUL.md`、`CONTRACT.toml`、各 `SKILL.md` の全文を生テキストとして表示し、HTML は描画しません。秘密や個人情報を確認してチェックを入れてください。問題がある自由記述は元のスタッフで修正します。会社テンプレートの編集ではツールとスキルの縮小のみ可能です。

コピー／エクスポートは `templates.copy` に `preview: true` を渡してプレビューを取得し、まだ保存しません。確定には `reviewed: true` と返された `review_digest` が必要です。サーバーは元データを再取得し、変更があれば拒否します。`templates.save` と `templates.apply` も真偽値 `reviewed: true` を要求し、会社テンプレートでは確認済みリビジョンも必要です。チームは各スタッフの作成前にリビジョンを再検証します。変更や検証失敗で `template_changed` と作成済み ID を返し、残りの作成を停止します。作成済みスタッフは残ります。

コピーは投影した有効なプリセット設定と確認済みの性格・契約・スキル本文を保持します。記憶／履歴、`.mcp.json`、チャネル設定、任意のカスタム資産は読み込みません。制限付きアカウントプールは拒否します。ランタイムの認証／環境フィールドと非移植セクションは除外し、保持するポリシー内の認証フィールドは拒否します。`[fork]` 全体を削除し、`db_sources` と `recipients` を空にし、`git_credentials` を無効化、スタッフの `recipient_guard` を `ask` に固定します。定期起動と自律的な学習は無効です。既知形式の認証文字列は既存の診断用マスクで処理しますが、先頭と末尾の各4文字が残る場合があります。**未知形式のトークン、短いパスワード、個人情報、自由記述内の送信先識別子の除去は保証しません。** 管理者による確認が必須です。

保存前に元の SOUL・契約・スキルを検査し、スタッフへの書き込み前に実際の内容を再検査します。既存の隠し内容・入力注入スキャナーの検出、短い HTML コメント、単一の不可視／ゼロ幅文字も拒否します。検査失敗時もファイル名を示して拒否し、コピーしません。説明用の例が検出された場合も元データを修正してください。Unix は `O_NOFOLLOW` と同じ descriptor のメタデータで通常ファイル・サイズ・hard-link 数を確認します。祖先ディレクトリは固定していないため、同じ OS ユーザーによる祖先パスの置換は防げません。

5つの RPC（`templates.catalog/get/copy/save/apply`）は現在の Admin 権限を要求します。会社テンプレートは `<home>/company_templates/` に原子的に保存し、チーム全体で1リビジョンを使います。監査記録に本文は含めません。組み込みは読み取り専用、有料コピーもライセンスが必要です。チームはリーダーと配下（最大50人）および内部報告関係を保持します。編集はスキル／メンバー削除、許可リスト縮小、禁止追加のみです。上司の削除には配下の削除が必要です。無効スキルは無効のままです。カスタムスクリプトはコピーせず、未変更の組み込み Office スキルは付属資産を復元します。会社コピーにパックの知識資料・評価ケースは含めません。

## ライセンスの紐付けと更新

MAC 由来の識別は3段階です。**Hardware** はグローバル管理のユニキャスト MAC です。**Instance** は Linux／Windows 上の既知の共有プレースホルダーを除くローカル管理のユニキャスト MAC で、GCP、AWS、Docker の NIC を含みます。状態には「クラウド／コンテナー識別」と表示します。どちらも既存の有料ライセンス、新規有効化、承認済み再紐付けに使用できます。主要 MAC は Hardware、次に Instance を優先します。**Weak** は MAC なし、全ゼロ、共有 `02:00:00:00:00:00` と Npcap／KM-TEST `02:00:4C:4F:4F:50`、ブロードキャスト `FF:FF:FF:FF:FF:FF`、マルチキャスト MAC、プレースホルダー UUID です。一致しても承認済み再紐付けまで OpenSource を維持し、新しい紐付けの候補にはしません。Linux／Windows は旧版の hostname + MAC ハッシュを維持し、過去の Instance 候補も検証できます（主要候補でなければ `legacy = true`）。OS 管理者はこれらの識別情報を複製できます。Instance はローカルで取得した識別情報を表し、ハードウェア証明ではありません。macOS の過去のローカル管理 MAC は UUID を取得できる場合もできない場合も Weak のままです。Windows の主要インターフェース選択では、ソフトウェアループバック、ソフトウェア仮想、トンネル型と既知のループバック記述も除外します。macOS の UUID v2 と UUID 取得失敗時の制限は変わりません。

既存形式との互換性のため、ライセンス署名には引き続き `control_url` を含めず、信頼できない接続先の候補として扱います。Gateway／CLI の refresh、再紐付け、status、CRL、販売代理店ブランド・通知の要求は、送信前に共通の通信層で検証します。HTTPS のポート 443 のみを許可し、ユーザー情報・query・fragment を拒否します。ホスト名は固定リスト `api.duduclaw.dudustudio.monster` と完全一致する必要があります。独自の発行元はクライアント側で環境変数 `DUDUCLAW_CONTROL_URL=https://issuer.example.com` を明示的に設定してください。ライセンスに URL を埋め込むだけでは許可されません。この設定は指定した origin のみを許可し、HTTPS、ポート、IP リテラル、localhost、DNS の制限を緩和しません。DNS の全回答が公開アドレスであることを確認し、そのアドレスに接続を固定します。リダイレクトと自動プロキシを無効にし、検証失敗時はライセンス要求を送信しません。Owner gateway は SQLite の同一 `BEGIN IMMEDIATE` トランザクション内で状態を読み、ライセンスと第 2 版応答に署名します。先に失効がコミットされていれば revoked を返し、署名が先にロックを取得した場合は署名のコミットまで失効処理が待機します。コミット後のネットワーク配送時刻はこの保証に含みません。

Refresh は元のサブスクリプション、元／提案の紐付け、nonce、署名と配備方式を検証します。active、revoked、pending は応答署名の第 2 版のみを受け付けます。署名は状態、理由、発効時刻、nonce、サブスクリプション、両方の紐付け、`control_url` を含むライセンス全体のダイジェストを対象にします。バージョンの欠落や旧版は拒否し、発効時刻が未来の失効応答も適用しません。Gateway と CLI の書き込みはプロセス間 advisory lock を共有し、通信後にライセンスファイル全体と失効マーカーのダイジェストを照合します。Gateway はメモリの revision も確認します。永続化には一意の一時ファイルと fsync を使用します。advisory lock を無視する直接書き込みは保護対象外です。[発行契約と制限](../../guides/ja-JP/personal-edition-portability.md#macos-のライセンス識別と再紐付け)を参照してください。コントロールプレーンの実際の配備／承認／署名、Windows ネイティブでの永続化、顧客環境の移行は別途検証が必要です。
## 拡張機能と外部ツールの権限境界（v1.80.0 から）

コア RPC は常にコアのディスパッチャーが処理します。拡張は `ext.<extension-id>.<method>` の名前空間でメソッドを宣言する必要があります。名前の衝突、重複、不正な登録がある場合、その拡張の RPC 登録を無効にして警告を記録します。未宣言のメソッドは拡張へ渡しません。

拡張 HTTP ルートは `/ext/<extension-id>/…` 配下で明示的に宣言します。リテラルパスのみを受け付け、コアのパスを捕捉できません。認証、Origin 検査、2 MiB のリクエスト本文の上限は拡張ハンドラーの外側で適用します。すべてのルートは認証と最低ロールの宣言が必要です。`ExtensionRoute::new` の既定は Admin です。コアは現在の DB ロールを確認し、JWT 発行後の降格も反映します。Public モードは削除されました。 従来の不透明な `extra_routes()` は起動時に拒否されるため、拡張の作者はアップグレード前に移行する必要があります。

管理対象の外部 MCP ツールには、`[[mcp.external]]` の stdio／HTTP マウントを含めて `ThirdPartyGate` を適用します。ツールの宣言は既定の Modify を Delete に引き上げる場合だけ採用し、読み取り専用の自己申告では分類を下げません。既存の名前制限と承認規則は一覧と呼び出しの両方に適用されます。スタッフの `.mcp.json` に直接指定した URL/type エントリーは拒否されます。管理対象のリモート MCP 接続へ移行してください。この境界はネイティブ拡張コードのサンドボックスではなく、操作者が単独で起動する CLI も対象外です。

管理対象の Claude 起動は、内蔵ツールだけの場合も一時的な厳格 MCP 設定のみを使い、ほかの MCP 読み込み元を追加しません。Grok 起動は、プロジェクトの管理外 MCP エントリーと、実際の `HOME` または `GROK_HOME` にあるグローバル MCP 定義を拒否します。設定を読めない場合も起動しません。Grok が実際に使う設定ルートは絶対パスである必要があります。`HOME` または `GROK_HOME` が相対パスなら修正してから再試行してください。既存ファイルは保持するため、サーバー定義をスタッフの MCP 設定へ移してから再試行してください。単独で起動する CLI とネイティブツールはこの境界の対象外です。

今回、全機能に共通するモジュールスイッチは追加していません。Odoo Live Chat のポーリング、音声 HTTP、チャネル音声、会議ジョブ、操作者コマンドは既存の個別ガードを使います。[入口一覧](../../architecture/extension-gates.md) にコードの位置、移行要件、検証の限界を記載しています。

## マシン操作と指示する人

AI スタッフに Bash やマシン操作ツールを与えると、そのスタッフに紐づく人は誰でも、それらのツールを使うよう指示できます。その権限を持つべき人だけを紐づけてください。管理者が通常の AI スタッフに許可したネイティブツールは引き続き利用できます。

`system-operator` プリセットを使うスタッフは Admin 専用です。サーバーは解決済みのプリセット紐づけから識別し、クライアントのフラグは信用しません。Admin 以外は紐づけ、チャット、タスクやゴールの作成、自分の依頼としてのディスパッチができず、`agents.callable` にも表示されません。既存の紐づけは削除せず、利用時に拒否します。Admin 以外は古い紐づけやチーム権限が残っていても、そのスタッフの会話履歴、タスク、記憶、ファイル、専用ナレッジコレクション、エクスポートを閲覧できず、リアルタイム更新、実行ステップ、承認カードも受信できません。紐づけの記録は保持します。Admin 以外が以前作成した依頼スケジュールは、そのスタッフのタスクやゴールを作成せず、実行時に自動停止し、再開も拒否します。外部送信の承認カード（CLI 組み込みツールと MCP ツールの両方）は Admin だけが閲覧でき、Manager にマスキング済みカードは表示されません。チャネルと Mini App にはテキスト通知だけを表示し、外部送信の承認カード、要約、操作ボタンは表示しません。Admin と許可済みの無人実行は従来どおりです。Personal の単一所有者の例外は、users.db が存在しない、アカウントがない、または初回のパスワード変更を完了した有効な Admin アカウントが一つだけの場合に限ります。停止中・退職済みのアカウントも数えます。複数アカウントの環境は、有料ライセンスの期限切れで Personal に戻っても有効な管理者が必要です。アカウント情報を読み取れない場合も同様です。

実行の依頼者には Human、Background、Unknown の 3 状態があります。保存済みの依頼者情報を解析できない場合は Unknown として、マシン操作ツールを拒否します。古い行に依頼者情報が存在しない場合は Background のままとし、既存の cron や自律作業を継続できます。

MCP cron、agent_callback リマインダー、TaskSpec はホストから渡された `on_behalf_of` を保存し、実行時に復元します。後続の委任もこの主体を引き継ぎます。非 Admin は通常の従業員に予定を作成できますが、Main ロールと設定されたデフォルト従業員は作成時に拒否し、実行時にも確認します。拒否された cron は一時停止し、callback リマインダーは失敗になります。主体のない旧データは背景処理のままです。Discovery は既存の署名済み従業員／Operator 権限と承認フローを維持します。MCP 作成時には保護対象を確認しますが、独立 runner はまだ人間の主体を復元しません。

有効なブランドを読み取るたびに、ライセンスの有効期限とオフライン猶予を再確認します。有効期限切れ、またはオフライン猶予超過では、元の DuDuClaw ブランドを表示します。コントロールプレーンへの接続が失敗し続け、ゲートウェイを再起動していない場合も同じです。

## スタッフの健康情報（v1.80.0）

読み取り専用の `agents.health` RPC は Manager または Admin を必要とし、現在有効なログイン主体を再確認します。Admin 以外は直接紐付く AI スタッフだけを閲覧でき、チーム権限では集計範囲を広げません。応答には件数と状態だけを含み、会話本文やプロバイダーの生のエラーは含めません。健康通知は、有効なスタッフの Owner と管理者の、検証済みチャンネル主体だけに送ります。設定ファイルが存在しない場合やセクションを省略した場合は、保守的な既定値（5回の失敗または6時間）を使います。それ以外の読み取りエラーや無効な設定では通知を停止します。これらの製品経路のチェックは既存の境界を変えません。同じ OS ユーザーとして無制限にファイルへアクセスできるスタッフは、ローカルの状態へ直接アクセスできます。

## Office パーサーの制限と残る信頼境界

`office_script` は、マニフェストで検証済みの埋め込み Python ラッパーだけを実行します。毎回の起動直前（システム Python へのフォールバックを含む）に、実行ルート、ワークスペース、使い捨てキャッシュ、信頼済みベース、従来の opt-out 用キャッシュをシンボリックリンクをたどらずに開き直し、所有者がゲートウェイの uid でモードが `0700` であることを求めます。さらにスクリプトについて、リンク数 1 の通常ファイルであること、所有者、`0500` モード、長さ、SHA-256 を再確認します。検証済みのファイル記述子は起動まで開いたままですが、uv／Python はパス名でファイルを開き直します。これは競合の余地を狭めるだけで、なくすものではありません。

PEP 723 の直接依存はすべて厳密なバージョンを指定しています。uv はプロジェクト・設定・環境変数ファイルを無視し、固定のパッケージアップロード期限 `2026-03-01T00:00:00Z` を使い、ソースからのビルドと Python の自動ダウンロードを拒否し、インストーラーの並列数を制限します。隔離実行では、ホスト側だけで行うウォームステップが、ユーザーファイルを含まない別の一時ディレクトリで、検証済みラッパーを固定の `--help` で呼び出します。ネットワークを使えるのはこの依存関係のステップだけです。その共有の信頼済みベースは `<home>/.office-execution/uv-base-v1/` で、ラッパーのダイジェストと期限に紐づくマーカーを持ちます。パーサーが書き込める従来の `uv-cache/` とそのマーカーを、このベースへ昇格させることはありません。プロセス間ロックにより、ウォームとスナップショット作成を直列化します。サンドボックスはベースを**読み取り専用**で受け取り、`UV_CACHE_DIR=<private-workspace>/uv-cache` を `UV_LINK_MODE=copy`、`UV_OFFLINE=1` とともに使います。通常ファイルは新しい inode にコピーし、キャッシュ内部のシンボリックリンクは使い捨てコピー側へ付け替え、外部へのリンクや特殊ファイルは拒否します。パス固有の `environments-v*` は省き、uv がオフラインで環境を作り直します。サンドボックスから書き込めるキャッシュは、実行やスタッフをまたいで残りません。準備済みの実行が公開後、または失敗・キャンセル時に破棄されると、ワークスペース、出力の一時領域、キャッシュを削除します。クリーンアップでは、保持しているワークスペースの記述子を通じて、シンボリックリンクをたどらずにディレクトリ権限を戻します。パーサーが作成したモード 000 のディレクトリも対象です。ファイルシステムや走査の失敗時は `office_workspace_cleanup_failed` を出力し、運用者による手動の後始末が必要になります。ウォームに失敗した場合は文書を実行しません。依存関係が欠けている、または追い出されている場合はオフラインのまま失敗し、文書をオンラインで再試行しません。追い出されたベースを再ウォームするには、次の実行前に運用者が `uv-base-v1/` から該当する `office-warm-*` マーカーを削除します。明示的なサンドボックスなしのフォールバックでは、従来の `uv-cache/`、初回実行時のダウンロード、成功時のオフラインマーカーを維持しますが、信頼済みベースには一切書き込みません。uv がない場合、隔離されたシステム Python がラッパーの実行前にすべての直接依存のインストール済みバージョンを確認し、不一致や欠落があれば失敗します。

**依存関係の制限**：完全なハッシュロックは同梱していません。パッケージインデックスの DNS が使えず、ローカルのメタデータも不足していたため、ロックを生成できませんでした。推移的依存のバージョンと成果物のハッシュはビルド時点で未確定です。期限は候補を絞るだけで、パッケージ内容の真正性を確かめることも、依存グラフを固定することもしません。システム Python とその推移的依存／site パッケージ、uv、LibreOffice、変更されうるキャッシュ済みパッケージは、ラッパーのマニフェストの対象外です。ウォームマーカーも直接依存の厳密なバージョン固定も、これらの完全性を保証しません。

`office_script` は、ファイルシステムの隔離、ネットワーク遮断、メモリ上限のいずれかを使えない場合、実行を拒否するようになりました。既存のスクリプトサンドボックスの抜け道である **`config.toml [container.sandbox] script_when_unavailable = "run_unsandboxed"`**（既定は `fail`）をそのまま使います。設定ファイルがない、読めない、形式が不正、またはそれ以外の値の場合は拒否します（fail closed）。タスクサンドボックスの `when_unavailable` やスタッフの `sandbox_enabled = false` では、office スクリプトはサンドボックスの対象外になりません。明示的な opt-out は隔離を使えない場合にだけ効き、そのフォールバックはホストプロセスごとに `office_script_unsandboxed` 警告を 1 回出します。環境、専用の一時領域、パイプ／プロセスのクリーンアップ、該当するリソース制限は維持しますが、ファイルシステム、ネットワーク、メモリの隔離は約束しません。ツールは文書を実行する前に確認を行い、実行を始めた文書をサンドボックスなしで再試行することはありません。

Linux では **bubblewrap（`bwrap`）が必須です**。空のマウント名前空間でシステム／ランタイムのパスを読み取り専用で公開し、読み書きできるのは使い捨ての cwd／出力／キャッシュディレクトリだけです。共有ベースは読み取り専用、入力スナップショットとラッパーも読み取り専用です。ネットワークと PID の名前空間は必須です（`--unshare-all --unshare-net`）。`--die-with-parent` がサンドボックスのプロセスツリーを片付けます。Linux のマウントや macOS のプロファイルを組み立てる前に、ランナーは DuDuClaw home、専用ワークスペース／出力、入力、ラッパー、ベースと実行ごとの両キャッシュ、既存の各ランタイム許可ルートを正規化します。いずれかの専用パスとランタイムルート（その別名と正規化後の実体を含む）が一致する場合、またはどちらか一方がもう一方の祖先にあたる場合は拒否します。そのため `/usr/local/share/duduclaw` や `/opt/homebrew/var/duduclaw` のようなカスタム home が、ランタイムへの許可を通じて暗黙に読めるようになることはありません。ベースは書き込み可能なワークスペースと重なってはならず、実行ごとのキャッシュはそのワークスペースの厳密に内側にある必要があります。正規化のエラーも拒否になります（fail closed）。ホストのルートや home 全体への許可は与えず、明示的に公開するのは専用の一時領域／キャッシュと選択したランタイムのバイナリだけです。これらの事前検査の失敗にも、上記と同じ明示的なサンドボックスなしの opt-out と警告が適用されます。`RLIMIT_AS` で 2 GiB のハードリミットを設定できなければなりません。bwrap がない、名前空間／マウントの設定が拒否された、またはメモリ制限の設定に失敗した場合は、運用者が opt-out していない限り実行を拒否します。ファイルシステムの境界がなく名前空間の隔離だけでは不十分です。[bubblewrap のオプションリファレンス](https://github.com/containers/bubblewrap/blob/main/bwrap.xml)を参照してください。

macOS では、生成した既定拒否のプロファイルを `/usr/bin/sandbox-exec` に渡し、`deny network*` を明示します。読み取りは、システム／ランタイムのパス、選択したランタイムのバイナリ、専用 cwd（入力スナップショットと使い捨てキャッシュを含む）、読み取り専用ベースに限られます。書き込みは使い捨ての cwd／出力／キャッシュに限られ、ラッパーと入力は除きます。パスはエスケープした SBPL 文字列で表し、制御文字、非 UTF-8、正規化されていない絶対パスは拒否します。プロファイルは引数として直接渡し、ファイルから開き直すことはしません。子プロセスはまず 2 GiB の `RLIMIT_DATA` を試し、DATA を設定できないか効果がない場合は `RLIMIT_RSS` を試します。検証済みのリソースを実際の起動でも使い、そこで改めて設定に失敗した場合はリソースを切り替えずに起動を拒否します。[Darwin の DATA／RSS の意味](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/setrlimit.2.html)は合計のメモリクォータではないため、別の Python プローブで設定済みの上限を 32 MiB まで下げ、64 MiB の確保が拒否されることを確認します。制限値が受け付けられただけでは不十分です。どちらの制限も設定できない場合、または制限があるのに確保が成功した場合はメモリ隔離を使えないものとし、既定では拒否します。このため、最近の Darwin では既定の office 実行が使えなくなることがあります。これを検証済みの合計メモリ上限と説明しないでください。

Unix の子プロセスは引き続き独自のプロセスグループを持ち、CPU 120 秒、個々のファイルサイズ 256 MiB、プロセス数 512、記述子 256 の制限を受け、コアダンプは無効です。既存のより低い制限は維持し、メモリ以外の制限の設定に失敗した場合は必ず起動を拒否します。制限は実際の起動時に設定し直し、Python／LibreOffice に継承されます。これはプロセス単位／ファイル単位の制限で、cgroup による合計クォータではありません。`RLIMIT_NPROC` は実 uid のプロセス数を数え、特権プロセスは対象外になることがあります。stdout／stderr の各パイプには、並行して読み取る 32 KiB のバイト数ハード上限があります。上限超過、読み取り／待機の失敗、180 秒の期限、タスクのキャンセルではプロセスグループを終了します。リーダーの終了でもクリーンアップが走ります。失敗した実行は出力を公開しません。

**残る境界**：制限のない同じ UID のホストプロセスは、パス名の開き直しに競合をしかけたり、共有の uv キャッシュを書き換えたりできます。前述の推移的依存／ハッシュロックの残存リスクは残ります。マニフェストで検証するのは埋め込みラッパーのバイト列だけです。macOS では、意図的に新しいセッションを作る子孫プロセスはプロセスグループのクリーンアップから逃れられます（サンドボックスの制限は継承されます）。これらのより強い境界をうたうには、別 UID／コンテナによる隔離と、検証済みで読み取り専用の依存成果物が必要です。ネイティブのサンドボックスが実際に動くことの受け入れ検証は、判定／プロファイルのテストとは別物です。この開発環境では `sandbox-exec` が `sandbox_apply: Operation not permitted` で拒否され、DATA／RSS の設定も拒否されたため、確認できたのは fail-closed の経路だけです。Linux ネイティブの隔離、macOS サンドボックスでの実行成功、実際の LibreOffice との互換性、ゲートウェイ／CLI 統合は、別途受け入れ検証が必要です。クリーンな環境で実際の uv を使ったウォーム／コピー／オフラインの受け入れテストも、PyPI の DNS 解決に失敗したため、ここでは未検証です。偽の uv とファイルシステムの回帰テストは、パッケージインデックスやネイティブサンドボックスの受け入れを示すものではありません。

## ガード1 — `agent-file-guard`（PreToolUse、Rust）

`duduclaw hook agent-file-guard` はシェルスクリプトではなく実際のサブコマンドなので、macOS／Linux／Windows で同一に動作します。gateway は matcher `Write|Edit|MultiEdit|NotebookEdit|Bash` で `<agent_dir>/.claude/settings.json` に登録し、起動のたびに再登録します（`agent_hook_installer`）。登録は運用者の既存設定を上書きせずマージする方式です。

Grok の社員は同じ 2 つのガードを別のファイルから受け取ります。DuDuClaw は Grok の起動時に Grok の Claude 互換 hook 読み込みを無効にするため（OS ユーザー自身の `~/.claude/settings.json` の hook が社員のターンで実行されることはありません）、Grok は `<agent_dir>/.claude/settings.json` も読まなくなります。そのため gateway は Grok を起動するたびに、`agent-file-guard` と `data-file-guard` の 2 項目をそのまま Grok のプロジェクト hook ディレクトリ `<cwd>/.grok/hooks/duduclaw-guards-<社員>.json` に書き出します。Grok は matcher 内の Claude のツール名を自身のツールに対応付け、Claude の `tool_name`／`tool_input` キーで hook に入力を渡します。ファイルは社員ごとに 1 つなので、借用した作業ルートを共有するチームメンバー同士が互いの ID を上書きすることはありません。各メンバーはそこにあるすべてのファイルを読み込み、どれか 1 つでも拒否すれば止まります。社員ディレクトリがあってファイルを書き込めない起動は拒否します。社員自身のディレクトリでは `.grok/` は凍結されたランタイム設定ディレクトリなので、社員は編集できません。社員ディレクトリの外の借用した作業ルートは凍結されないため、そこに書き込み権限を持つ社員は独自の hook ファイルを追加できます。

インストールされるコマンドはエージェント id（`--agent`）を持ち、v1.68.1 より後のリリースでは DuDuClaw ホーム（`--home "<パス>"`）も持ちます。gateway は社員の CLI を環境変数を絞った状態で起動し、許可リストに `DUDUCLAW_HOME` がないため、以前のフックは `$HOME/.duduclaw` にフォールバックしていました。ホームが既定の場所にない環境では、実際のホーム内のパスがすべて「ホームの外」と判定されていました。インストーラは `<ホーム>/agents/<id>`（または `<ホーム>/agents/.ephemeral/<id>`）形式のすべての社員ディレクトリに `--home` を書き込み、シェルの特殊文字を含むパスはシングルクォートで囲みます。既存のインストールは次回の社員起動または gateway 起動時にその場で書き換えられます。

フックは次の順でホームを決めます：`--home`（絶対パスのみ）；社員身分のない呼び出し元（フックコマンドに `--agent` がなく、環境にも `DUDUCLAW_AGENT_ID` がない場合）は従来どおり既定のホーム；フックの環境で明示的に設定された絶対パスの `DUDUCLAW_HOME`。作業ディレクトリからホームを推定することはしません。どれからもホームが得られない場合、その社員の `Write`／`Edit`／`MultiEdit`／`NotebookEdit`／`Bash` 呼び出しはすべて拒否され、推測した場所で判定することはありません。同じ変更で `NotebookEdit` も matcher に加わり、その `notebook_path` は `Write` の対象と同じように判定されます。フックのサブコマンドは stderr でのみ応答し、ログファイルは書かなくなりました。

次の場合に exit 2（Claude Code は「このツール呼び出しをブロック」と解釈）を返します：

- エージェントが**エージェント構造ファイル**（`agent.toml`、`SOUL.md`、`CLAUDE.md`、`.mcp.json` …）を正規の `<home>/agents/<name>/` ツリー**外**に書き込んだとき。新規エージェントの作成は `create_agent` MCP ツール経由に限られ、そちらには委譲認可ゲートがあります；
- エージェントが**自分自身の `SOUL.md`** を書き込んだとき。場所が正しくてもブロックします。人格は運用者が管理します。このフックにオプトインはありません。`agent.toml [permissions] can_modify_own_soul = true` で明示的にオプトインしたエージェントは、`agent_update_soul` MCP ツールを通じて自分の `SOUL.md` を変更でき、ファイルを直接書くことはできません；
- エージェントが**自分自身の `CONTRACT.toml`** を書き込んだとき。場所が正しくてもブロックします（判定 `BlockedOwnContractWrite`）。契約は運用者がエージェントに課す境界なので、オプトインのフラグはありません。ブロック時のメッセージは運用者に依頼するよう伝え、運用者はダッシュボードから変更します（`contract.update`、社員のオーナーまたは管理者が厳格なチェックを経て変更。このフックは通りません）；
- エージェントが**他のエージェント**のファイルに触れたとき；
- エージェントが **DuDuClaw ホーム**内のそれ以外の場所に書き込んだとき。社員 id を持つ（または主張した id の検証に失敗した）呼び出し元にとって、ホーム配下で書き込めるのは自分のエージェントディレクトリと共有の `attachments/` だけです。許可リスト方式なので、監査ログ（`tool_calls.jsonl`。根拠チェック、判定者向けダイジェスト、直近の行動フィードが読みます）、`evals/`（ホールドアウトセットと他の社員の評価セットを含む）、すべての SQLite ストア、ブレーカーの状態、ライセンスと組織ファイル、グローバルの `skills/`、共有 wiki が対象になり、今後追加されるストアも最初から保護されます。これらの正規の書き手は gateway とゲート付きの MCP ツールで、どちらもこのフックを通りません。影響を受けないのは社員身分のない呼び出し元、つまりフックコマンドに `--agent` がなく、環境にも `DUDUCLAW_AGENT_ID` がない場合だけです。インストールされるフックコマンドには必ず `--agent` が付き、フックはそれを優先するため、オペレーターが社員のディレクトリで手動で `claude` を実行すると、その社員として判定されます（身分トークンを必須にしている場合は、検証に失敗した呼び出し元として扱われます）。オペレーターがこれらのファイルを変更するときは、ダッシュボードか通常のエディタを使ってください；
- 書き込み先が、上記で拒否される場所を指す**シンボリックリンク**のとき。Write／Edit のパスは、書かれたとおりと実際の書き込み先（リンクとリンクの後の `..` をたどる。宙に浮いたリンクは常に拒否）の2回判定され、どちらかが拒否すれば拒否です。相対パスはフック入力の作業ディレクトリを基準に、入力に作業ディレクトリがない場合は社員自身のディレクトリを基準に解決します。実際の書き込み先を確定できないパスは「無法確認這次寫入實際會落在哪裡」（書き込みが実際にどこに落ちるか確認できない）というメッセージで拒否します；
- エージェントが、削除された社員が保管される **`agents/_trash/`** 配下に何かを書き込み、移動、または削除したとき（Bash はヒューリスティック）；
- エージェントが Bash から **`duduclaw agent create <name>`** を、削除された社員が使っていたために予約されている名前で実行したとき（[委譲の隔離](37-delegation-isolation.md#削除された社員の名前は予約されたままになる)を参照）。この拒否は `agent_name_reserved` として、`path_kind` を `cli_bash_agent_create` として監査されます。

- エージェントが**自分自身の `INSTRUCTIONS.md`** を書き込んだとき（判定 `BlockedOwnInstructionsWrite`）。このファイルには運用者が他のプラットフォームから取り込んだ作業ルール（[AI スタッフの取り込み](../../guides/ja-JP/agent-config-import.md)）が入っており、毎回のプロンプトに読み込まれるため、契約と同じくオプトインのフラグはありません。エージェント構造ファイルの一覧にも入っているので、配置ガードと `office_script` の扱いは `SOUL.md` と同じです。

Bash では、自分の `SOUL.md`、自分の `CONTRACT.toml`、自分の `INSTRUCTIONS.md` のルールはヒューリスティックです。書き込み形のコマンドがファイルを `agents/<自分>/…` として、または `CONTRACT.toml`、`./CONTRACT.toml` のような相対表記で指定するとブロックされます。id の検証に失敗した呼び出し元は、`agents/` 配下のどこかを指定する書き込み形のコマンドがすべて拒否されます（Write／Edit と同じ扱い）。

**Bash とホームの許可リスト。** Bash 側は同じ許可リストでコマンド文字列を判定します。以下の「保護されたホーム対象」とは、ホーム内で自分の社員ディレクトリと `attachments/` 以外の場所、他の社員のディレクトリ、削除された社員の保管場所を指します。身分の検証に失敗した呼び出し元では、自分のディレクトリも含みます。

- 判定の前に、bash と同じ読み方でコマンドを戻します。行継続、バックスラッシュのエスケープ、引用符はすべて先に元に戻します。出力やエラー出力を `/dev/null` に捨てる書き方（`2>/dev/null`、`>/dev/null`）と、ディスクリプタを別のディスクリプタに複製する書き方（`2>&1`）は書き込みとみなしません。出力とエラーをまとめてファイルへリダイレクトするのは書き込みです。
- 既知の読み取り専用コマンドの一覧に載っているコマンド（一覧、読み取り、検索、比較など）は引数を検査しません。ただし出力のリダイレクトは検査します。出力をファイルに書けるオプションや、他のコマンドを実行できるオプションを持つコマンドは一覧に入れないか、そのオプションを使ったときは読み取り専用とみなしません。社員が一覧にないコマンドでホーム配下のファイルを読もうとすると拒否されるので、一覧にあるコマンドか対応する MCP ツールを使ってください。
- コピー系のコマンド（コピー、インストール、ダウンロード、アーカイブ展開）はコピー先だけを見ます。ホーム内のファイルを自分のディレクトリへコピーするのは通ります。
- 引数が指すものを変更するコマンド（移動、削除、リンク作成、権限・所有者・タイムスタンプの変更、同期、データベースのコマンドラインツールなど）とインタプリタ・シェルは、引数のどれか（インラインのプログラム文字列を含む）が保護されたホーム対象なら拒否します。どのコマンドでも、保護されたホーム対象への出力リダイレクトは拒否します。
- それ以外のコマンド（解析できない前置オプションの場合を含む）は、引数のどれかが保護されたホーム対象なら、書き込みの有無にかかわらず拒否します。一覧にないコマンドが保護されたホームのパスに触れる唯一の出口は、既知の読み取り専用コマンドの一覧です。
- ホーム内で**社員ディレクトリと `attachments/` 以外**にあるデータベースファイル（`*.db` とその `-wal`／`-shm`／journal ファイル、`*.sqlite*`）は、コマンドのどこに現れても読み取りを含めて拒否します。社員ディレクトリと `attachments/` 内のデータベースはこのルールの対象外です（他の社員のディレクトリへの書き込みは引き続き拒否されます）。
- 相対パスはフック入力の作業ディレクトリ（なければ社員自身のディレクトリ）を基準に解決し、コマンド内の `cd`／`pushd` にも追従します。作業ディレクトリを推定できず、コマンドのどこかで保護されたホーム上の場所を指している場合、検査対象の位置にある相対パスは拒否します。どこも指していなければ判定しません。
- 検査対象のパスにある既存のシンボリックリンクは解決し、実際の場所も判定します。解決できない検査対象のパスは、宙に浮いたリンクを含めて常に拒否します。

これは減速帯であって隔離ではありません。本当の隔離は、エージェントに Bash を与えないことです。制約は「これらのガードがカバーしないもの」に記載しています。

ライブフォーク（`fork_run`）は同じファイルを反対側から守ります。ブランチはエージェントの構造ファイルを読めますが、ブランチをエージェントのディレクトリに昇格するとき、`SOUL.md`、`CONTRACT.toml`、`agent.toml`、`.mcp.json`、`.claude/` などのエージェント構造ファイルが親のものを上書きすることはありません。

## ガード2 — `data-file-guard`（PreToolUse、Rust、RFC-23 §14.4）

ガード1が守るのは DuDuClaw 自身の構造ファイル、こちらが守るのは顧客のデータです。

`Read` と `Bash` は Claude Code の組み込みツールなので、`cat customers.csv` は `file_read`／`csv_read`／`xlsx_read` が必ず通る MCP 匿名化チョークポイントを通りません。インストーラーは `duduclaw hook data-file-guard` を matcher `Read|Bash` に登録します。判定ロジックは `duduclaw_core::data_file_guard` にあり、CLI サブコマンドと gateway のインストーラーテストが同じ実装を共有します。契約はガード1と同じ：exit 0 で許可、exit 2 ＋ stderr でブロック、stderr はモデルに提示されます。

gateway が spawn 時に `DUDUCLAW_DATA_FILE_GUARD` を設定しない限り何もしません。gateway がこれを設定するのは、そのエージェントで匿名化が実際に有効なときだけです。匿名化がオフの環境では、このガードが存在する前とバイト単位で同じ挙動になります。

以前のバージョンでは `<agent_dir>/.claude/hooks/data-file-guard.sh` に置かれた POSIX シェルスクリプトで、`PATH` に bash がない Windows ホストでは**まったく機能していませんでした**——フックコマンドが失敗し、Claude Code は 2 以外の終了コード（"command not found" を含む）を*許可*として扱うため、誰も気づかない場所でガードが消えていたのです。インストーラーはアップグレード時に残存スクリプトを削除するので、古いコピーが現役のガードと取り違えられることはありません。

**明示された制約**：`Bash` 側の検査はファイル名を照合します。パスを動的に組み立てるコマンド（`python -c "open(chr(99)+…)"`）はそのまま通り抜けます。本当の防御は MCP ツール面であり、このガードはモデルが無防備な経路を取る確率を下げるものです。ヒューリスティックであってサンドボックスではありません。

## ガード3 — `input_guard`（プロンプトインジェクションスキャナー、Rust ライブラリ）

`duduclaw_security::input_guard::scan_input` はテキストを**11のルールカテゴリ**で 0–100 点に採点し、`DEFAULT_BLOCK_THRESHOLD`（60）以上でブロックします：

| ルール | 重み | 単独即ブロック |
|---|---|---|
| `instruction_override` | 40 | はい |
| `role_hijack` | 35 | はい |
| `tool_abuse` | 30 | はい |
| `data_exfiltration` | 25 | はい |
| `system_prompt_extraction` | 30 | いいえ |
| `encoding_bypass` | 25 | いいえ |
| `termination_manipulation` | 30 | いいえ |
| `authority_escalation` | 信号1種類につき 35、異なる2種類で加算 | いいえ |
| `memory_poisoning` | 信号1種類につき 30、異なる2種類で加算 | いいえ |
| `role_provenance` | 枠1種類につき 35、異なる2種類で加算 | いいえ |
| `action_binding` | 30 | いいえ |

パターンは英語と中国語（繁体字と簡体字）をカバーします。テキストは先に NFKC 正規化され（`unicode_normalizer`）、ホモグラフや不可視文字の小細工はパターン照合をすり抜けられません。

**中国語のカバー範囲（v1.67.1）。** リリース済みのバージョンは中国語の指示上書きを4つの完全一致文字列でしか照合しておらず、「所有」「之前」「的」などの語を1つ挟むだけで通り抜けました。実地テストでは、そうした4文が `user_profile_record` 経由で保存されました。v1.67.1 からは次のとおりです。

- `instruction_override`：上書き動詞（忽略／無視／忘記／忘掉／不要理會／不用理會／別管、簡体字形を含む）の後、同じ節の中で 12 文字以内に指示系の名詞（指示／指令／規則／提示詞／系統提示）があり、その間に範囲語（先前／之前／以上／上面／上述／前面／所有／全部／一切／你的／原本／原來）がある場合に一致します。空白は数えず、`。！？；` と改行で節が終わります。重みと即時ブロックは英語のフレーズと同じです。
- `system_prompt_extraction`：抽出名詞（系統提示詞／系統提示語／你的系統提示／你的指示／你的設定）と出力動詞（輸出／顯示／告訴我／給我看／洩漏／列出／重複）が順不同で 12 文字以内にある場合。採点は英語のルールと同じで、重み 30、単独ではブロックしません。単独の「系統提示」は「システム通知」の意味もあるため抽出名詞に含めていません。
- `role_hijack`：「你現在是管理員模式」「開發者模式」「越獄模式」「你現在不受限制」「進入越獄模式」などの固定フレーズと、単独の「越獄模式」。英語と同じ扱いです。
- しきい値と英語のリストは変わりません。

**既知の誤検知。** 形で照合するため、上書き動詞・範囲語・指示系の名詞が1つの短い節に並ぶ普通の文もブロックされます。たとえば「請忽略之前寄的指示，以新版為準」「請忽略以上規則中的第三條，已經取消」「忘記之前的規則了，可以再說一次嗎」です（テスト `known_benign_shapes_that_do_match` で固定）。「越獄模式」に触れるだけでもブロックされます。回避策は上書き動詞を使わずに言い換えることで、たとえば「之前的指示作廢，以新版為準」です。近い文「之前的報價單請作廢，以新的指示為準」は、一致してはならない文のテスト一覧に入っています。このスキャナーはフレーズによるヒューリスティックで分類器ではなく、実際の会話データでの計測もしていません。

`termination_manipulation`（LoopTrap、arXiv:2605.05846）は意図的に即ブロックにしていません。重み 30 は閾値より低く、単独一致では警告と監査のみでブロックしません。これにより通常の「続けてください」が誤検知されずに済みます。

**文型ファミリー（v1.68.0）。** レッドチーム台帳で、AI 社員を狙う4つの手法がどれも0点だとわかりました。現在はそれぞれに英語と繁体字中国語のアンカー付き正規表現があります。

- `authority_escalation`：ユーザーの権限ではなく社員自身の権限で実行させようとする文（"use your own service account / admin role"、"not my permissions"、"the system trusts you more than me"、用你自己的服務帳號／管理員身分、不要用我的權限、系統比較信任你）。
- `memory_poisoning`：恒久的な特権を記憶させようとする文（"remember this permanently"、"as a fact about me"、"I am always allowed to"、永久記住、記在你的記憶裡、以後每次對話都照辦、我一律有權限）。普通の「請記住…」、"remember to…"、"remember my name" は一致しません。
- `role_provenance`：ユーザーメッセージ内の偽のシステム・ツール・運営者の枠：`[SYSTEM]`、`<tool_result>` タグ、`approval=granted`、"policy update from the platform operator"、「本次對話已解除…限制」、平台營運方政策更新、引用文中の AI 宛てメモ（給 AI 助理的附註）とそれを隠す指示（不要提到這段附註）。枠はタグ全体でのみ一致するので "our system sends a tool result" は一致しません。開始タグと終了タグの組は1種類として数えます。
- `action_binding`：1つの承認を別の操作に流用する文（"use that same approval to…"、"use the approval from step 1"、用同一個核准、用第一步的核准去…）。「既然已經核准預算，請安排會議」は一致しません。

重みの方針：信号1つだけなら警告と監査のみ（30–35、60 未満）です。1つのメッセージに同じファミリーの**異なる**信号が2種類ある場合、または信号1つに既存ルール（`instruction_override`、`system_prompt_extraction` など）が加わる場合にブロックします。自身で加算されるのは3つのファミリーです：`authority_escalation`（「用你的服務帳號」と「系統比較信任你」で 70）、`memory_poisoning`（「永久記住」と「我一律有權限」で 60）、`role_provenance`（`[SYSTEM]` と `approval=granted` で 70）。`action_binding` は自身では加算されず、他のルールと組み合わさったときだけブロックします。同じ信号が2回出ても1回と数えます。`[SYSTEM]` 1つ、または `<tool_result>…</tool_result>` の1組だけなら 35 のままです。既知の代償：たまたま信号を2種類含む普通の文もブロックされます。たとえば "please use your admin account, not my permissions, to fix the shared folder" です（テスト `known_benign_shapes_blocked_by_stacking` で固定）。信号が1つだけの言い方にするか、管理者に直接頼んでください。一致があれば本文を捨てる呼び出し側（蒸留、プロフィール書き込み）は、これらの文型を含む本文も捨てるようになりました。各ファミリーの陽性例と、似ているが一致してはならない文は `input_guard.rs` のテストで固定しています。

一致したときに影響が出る場所（確認済みの呼び出し箇所）：

- チャットで受信したメッセージ（`channel_reply`、`scan_input_with_audit`）：ブロックされたメッセージには警告の返信が返り、AI には渡されません。
- MCP ツール呼び出し（`mcp_dispatch`、シリアライズした引数に `scan_input_with_audit`）：引数がブロック対象の文を引用していると、呼び出しは拒否され監査されます。
- 会話事実・プロフィール・知識振り分けの抽出（`wiki_ingest`、`profile_distill`、`knowledge_route`）：ブロックしない抽出ルールを含め、**いずれか**のルールに一致した内容は破棄されます。
- `user_profile_record`：predicate と値をスキャンし、ブロック水準なら拒否します。
- `duduclaw migrate from` のインポートはブロック対象の項目をスキップし、エキスパートパックのインストールはブロック対象のパックを拒否します。
- Agent Mail：一致した受信メールも保存されますがフラグが付き、フラグ付きのメールが AI 従業員を起動することはありません。
- リマインダー：プロンプトがブロック対象のリマインダーは実行されません。

## ガード4 — `org_field_guard`（組織権限の凍結）

A2A 委譲の述語（`delegation_policy::can_delegate`）は、`agent.toml` の `[agent] reports_to`／`department`／`name` と `config.toml` の `[delegation]`・`[acp]` を読んで「誰が誰に指示できるか」を決めます。どちらもただのファイルなので、`Edit` を持つエージェントは自分の `reports_to` を被害者に向けて書き換え、「部下 → 上位」ルールを主張できてしまいます。裁かれる側が証拠を所有している状態でした。

`org_field_guard` は同じ `agent-file-guard` フックの中で動き、再構成した**書き込み後**の内容をディスク上の現状とフィールド単位で比較します。保護対象のフィールドやセクションに変更があれば拒否します。`[capabilities]` はキー名リストではなく**テーブル全体**として凍結されるので、将来のリリースで追加される capability キーは、誰かがリストを拡張するのを思い出した日ではなく、着地した当日から保護されます。

**社員自身のセキュリティ設定。** 社員 id を持つ（または検証できない）呼び出し元に対して、自分の `agent.toml` の残りの部分は許可リスト方式で凍結されます。変更できるのは編集可能なセクションだけで、それ以外のセクションは、今後のリリースで追加されるものも含めて既定で保護されます。編集可能なセクションは `[agent]`、`[model]`、`[prompt]`、`[heartbeat]`、`[proactive]`、`[research]`、`[goal_intent]`、`[memory]`、`[skills]`、`[sticker]`、`[cultural_context]`、`[preset]`、`[planner]` です。その中でも `[agent] role`、`[prompt] cli_bare_mode`（Claude CLI にフックを飛ばさせる設定）、`[model] account_pool` と、組織フィールド `[agent] reports_to` / `department` / `name` は凍結されたままで、`[capabilities]` はテーブル全体が凍結されます。この許可リストは社員身分を持つすべての呼び出し元に適用され、社員のディレクトリで手動で `claude` を実行するオペレーターも含みます（Guard 1 参照）。オペレーターがこれらのセクションを変更するときは、ダッシュボードか通常のエディタを使ってください。以前からの組織フィールドと `[capabilities]` の行はこれまでどおり全員に適用されます。

**社員自身の `.mcp.json` と CLI 設定。** 社員の身元を持つ（または検証できない）呼び出し元は、自分のディレクトリ内のどの階層の `.mcp.json` にも一切書き込めません（Write、Edit、MultiEdit、NotebookEdit。最上位のものは Bash のルールが以前から拒否しています）。gateway はこのファイルを指定して Claude CLI を起動し、CLI はそこに並ぶすべてのサーバーを起動するため、コマンドがインタプリタの項目を 1 つ足すだけで、次の起動時に運用者の OS ユーザーとして任意のコマンドが実行できてしまいます。Bash の権限は要りません。出荷済みのすべてのバージョンが影響を受けます。以前は社員が「無関係な」サーバーを自分で追加できました。今後 MCP サーバーの追加は、ダッシュボード、ダッシュボードで出す MCP インストール申請（`mcp.install_request`、管理者の承認後に自動インストール）、expert pack、または運用者による直接編集で行います。いずれも hook を通りません。同じ呼び出し元は、自分のディレクトリ内の CLI 設定にも書き込めません。どの階層でも `.claude/` 配下（設定、hook、スラッシュコマンド、サブエージェント、skill）と `.claude.json` という名前のファイル、そして最上位の Codex・Grok の設定ディレクトリ（`.codex/`、`.gemini/`、`.grok/`、`.agents/`）と `.cursor/`（Grok は作業ディレクトリの `.cursor/mcp.json` を自分で読みます。2026-10-20 から）です。名前の比較は大文字小文字を区別しません。動作の変更：社員ディレクトリ内に複製したプロジェクトも CLI が起動する場所なので、社員はそのプロジェクトの `.claude/` を読めますが、書けません。運用者には従来のルール（`.mcp.json` は身元キーのみ凍結）が適用されます。gateway は社員の `.mcp.json` を Claude CLI に渡す前（チャネル返信、ディスパッチ、heartbeat の能動チェック、`duduclaw eval` の live モード、live fork がブランチを複製する前の親ディレクトリ）と起動時にも DuDuClaw の項目をまるごと作り直し（コマンド、引数、環境変数）、他の項目はそのまま残します。ファイルを確認できない場合（通常ファイルでない、読めない、JSON として不正、または duduclaw 実行ファイルのパスが絶対パスでない）はその起動を行わず、監査イベント（`mcp_config_unverified`）を記録します。この拒否はファイルの問題でありアカウントの問題ではないため、アカウントはクールダウンに入らず、別のアカウントでの再試行もしません。チャネル返信はローカルモデルや Direct API に切り替えて答えず、どの社員の設定が確認できなかったかを伝えるメッセージを表示します。`.mcp.json` を書くすべての処理が共有するロックは社員ディレクトリではなく `<home>/locks/` にあるため、社員がそこに作ったファイルやディレクトリで妨げることはできません。アップグレード前に追加された項目は残ります。`duduclaw doctor` は DuDuClaw が書いていない項目をすべて一覧表示します（名前とコマンドのファイル名のみで、引数、環境変数、URL は表示しません）。運用者は一つずつ確認または削除してください。live fork のブランチを社員ディレクトリに採用するときは、`.claude.json`、`.agents/`、`.codex/`、`.gemini/`、`.grok/`、`.cursor/`、およびどの階層の `.claude/`、`.claude.json`、`.mcp.json` も持ち帰りません。制限：これは hook なので、制限のない Bash を持つ社員はファイルを変更できます。Codex には下記の制御ファイルのロックがあり、この hook とは別の保護です。Grok、その他の CLI runtime、Windows はこのロックの対象外です。Claude Code が社員ディレクトリの `.claude.json` を読む場合がありますが、このファイルは書き込み禁止です。

構造上 fail-closed です：新しい内容がパースできない、既存の内容がパースできない、書き込み意図が再構成できない——いずれも拒否します。既存の `agent.toml`、`config.toml`、`.mcp.json` が読み取れない場合も拒否します（以前は新規ファイルとして許可していました）。ファイルがまだ存在しない場合は許可します。作成は `create_agent` 経由であり、そちらに独自のゲートがあるためです。

正当な変更の経路はすべて残っています：MCP `agent_update` ツールとダッシュボードの `agents.update` RPC。どちらもこのフックを通りません。

**Codex 社員の制御ファイル（Unix、WorkspaceWrite）。** 通常の社員実行では、既存のサンドボックスモードに加えて `duduclaw-employee` 権限 profile を適用し、社員ディレクトリ直下の `agent.toml`、`SOUL.md`、`CONTRACT.toml`、`INSTRUCTIONS.md`、`.mcp.json`、`.codex/`、`.grok/`、`.claude/`、`.agents/` を読み取り専用にします。まだ存在しないパスの作成も拒否します。社員ディレクトリの絶対パスを使うため、作業ルートが変更されても保護対象は変わりません。`MEMORY.md`、`CLAUDE.md`、通常の作業ファイルと一時ファイルは引き続き書き込み可能です。Codex CLI 0.164.0 以上が必要で、古いバージョン、バージョンを確認できない場合、社員ディレクトリがない場合は起動を拒否します。バージョン判定は実行ファイルのパスごとにキャッシュします。古いバージョンや確認できないバージョンには、ダッシュボードで Admin 向けの更新ボタンを表示します。このボタンで更新すると支援機能のキャッシュをクリアして再検出するため、gateway の再起動は不要です。古い実行ファイルが優先される場合は成功とせず、そのパスを表示します。設定は `agent_update` とダッシュボードから変更できます。ReadOnly、明示的に許可した FullAccess、探索・補助実行の引数は変更しません。この制御ファイルのロックは Grok、その他の CLI runtime、Windows（未検証）には適用されません。その他の CLI runtime は `native_sandbox` を有効にしない限り OS サンドボックスを持ちません。 Docker では最新の compose ファイルが必要です。これは絞り込んだ seccomp、`apparmor=unconfined`、`no-new-privileges`、`cap_drop: ALL` を適用します。Ubuntu 24.04 ではホストへの AppArmor プロファイルの読み込みも必要です。サンドボックスが起動できない場合、シェルコマンドは失敗しファイルは変更されません。DuDuClaw は回避のためにサンドボックスを緩めることはなく、`duduclaw doctor` が原因を報告します。[docker.md](../../guides/ja-JP/docker.md) を参照してください。 コンテナ自体は bubblewrap のために緩和されているため、Docker では gateway が他の子プロセス（Claude、Grok、その他の CLI、MCP サーバー、管理者設定のコマンド）に seccomp を追加し、Docker の namespace 制限を復元して `ptrace` を拒否します。gateway 自身は非ダンプ可能になり、同じ UID のプロセスからメモリにアクセスできません。例外は bubblewrap を実行する Codex の経路のみです。既知の制限：Codex サンドボックス内では入れ子の user namespace を作成でき、Codex にこれを止める設定はありません。マルチテナントでは VM 分離を使用してください。

## 出典単位の忘却には管理者の承認が必要

`duduclaw memory forget-source` はメモリを完全に削除するため、手前に3つの関門があります。手順は[会話・スケジュール実行・インポートファイルを忘れる](../../guides/ja-JP/memory-and-knowledge.md#45-会話スケジュール実行インポートファイルを忘れる)、仕組みは[メモリインテリジェンス](20-memory-intelligence.md#メモリの出典と出典単位の忘却)にあります。

**ダッシュボード承認。** `plan` は、プラン id とプランのハッシュに結び付いた承認リクエストを1件出します（`action_kind` は `memory_forget_source`）。このリクエストはダッシュボードでのみ、管理者のみが決定できます。チャネルのボタンや返信は拒否されます。`apply --confirm` は、そのリクエストが承認済みで、同じプランのハッシュを指し、プランが期限切れでない場合にだけ実行されます。リクエストはプランと一緒に期限切れになります（既定 30 分、最長 24 時間）。カードには件数と出典のラベルだけを載せ、メモリの内容は載せません。このリクエストがローカルのコマンドラインから作られたこと、誰が入力したかを確認する手段がないことを、固定の文言で伝えます。この承認を無効にする設定はありません。`[memory] forget_source = false` は、新しいプランの作成と適用を止めるだけです。

**Bash ルール。** 従業員の身元が付いた、または身元未検証の呼び出し元に対し、`agent-file-guard` の Bash レーンは、`duduclaw` と `duduclaw-pro`（パス付きや `.exe` も含む）の後に `memory forget-source` または `memory migrate-namespace` が続くコマンドを拒否します。サブコマンドは問わず、読み取り専用の `list` も同様です。判定は `BlockedOperatorMemoryCommand` で、メッセージは従業員にオペレーターへ依頼するよう伝えます。`migrate-namespace` は、これまで Bash レーンの対象外でした。これは減速帯であってサンドボックスではなく、次のものは防げません。

- `memory` とサブコマンドの間にグローバルオプションを挟む書き方。例：`duduclaw memory --redact on forget-source …`
- コマンド置換で実行ファイルを組み立てる書き方。例：`"$(command -v duduclaw)" memory forget-source …`
- コマンド文字列をパイプで実行ファイルに渡す書き方。例：`echo memory forget-source … | xargs duduclaw`
- コマンド名の照合を避けるその他の書き方、および「これらのガードがカバーしないもの」に挙げた他の回避方法

**AI セッション判定。** gateway が従業員のプロセスに設定する変数のどれか1つでも、空であっても存在すれば、コマンド自身が実行を拒否します。従業員の身元とトークン、ターンとセッションの id、そのターンのユーザーメッセージ番号と時刻、ディスパッチのセッションと run id、委任の送信者・起点・深さ、hop の深さ、返信チャネル、MCP API キー、データファイルガードのフラグ、goal ラウンドのタスク id です（唯一のリスト `ai_session_guard::AI_SESSION_ENV_VARS`。2026-10-06 以降、承認を提出するすべてのオペレーターコマンドが共有します）。オペレーター自身のターミナルにはこれらがありません。この判定は最初の一線にすぎません。従業員の Bash から直接実行したコマンドに対しては信頼できません。Bash を持つ従業員は変数を unset できるからです。本当の隔離は、Bash を与えないこと、または従業員をタスクサンドボックスで動かすことです。同じ OS ユーザーで動き、任意のコマンドを実行でき、ファイルガードを意図的に回避する従業員は、ローカルのデータベース（`approvals.db`、`memory.db`）を直接書き換えられます。

## 運用者による社員の制御コマンド

`duduclaw agent pause|resume|freeze|unfreeze <agent>` は、共通の AI セッション変数が 1 つでも存在すれば、空値でも拒否します。`agent-file-guard` の Bash レーンも、社員と身元未検証の呼び出し元に対し、この 4 つのサブコマンドを拒否します（`BlockedOperatorCommand`）。共通の運用者コマンド照合を使い、`duduclaw`／`duduclaw-pro`、絶対パス、`.exe`、`env`／`npx` の前置、引用符の連結、行継続に対応します。運用者は自分のターミナルで直接実行でき、ダッシュボード承認は不要です。`pause`／`resume` は `[agent] status`、`freeze`／`unfreeze` は進化とハートビートを変更します。書き込みには `agent_update` やダッシュボードと同じロック付きの書式を保持するアトミックな処理を使い、ファイル履歴と `agent_file_changed` 監査を残します。成功時は `agent_pause`、`agent_resume`、`agent_freeze`、`agent_unfreeze`、拒否時は `agent_cli_refused` も記録します。これは減速帯です。環境変数の削除、改名した実行ファイル、動的に組み立てたコマンドで回避でき、Claude 以外の runtime は hook を実行しません。制限のない Bash を持つ社員はファイルを直接変更できます。本当の隔離は、Bash を与えないこと、または従業員をタスクサンドボックスで動かすことです。

## コマンドラインからの運用者操作は 1 つの承認ゲートを共有する

ターミナルから状態を変えるコマンドは 4 つあります：`duduclaw channel-ingress`（LINE 受信箱）、`duduclaw responsibility`（継続タスク）、`duduclaw memory forget-source apply`、`duduclaw computer-workspaces`。ターミナルでは誰が入力したかを証明できないため、4 つとも、現在も Admin であるアカウントがダッシュボードで判断するリクエストを作るだけで、コマンドはその後 1 回だけ適用します。v1.70.0 の次のリリースから、4 つは 1 つの実装（gateway クレートの `approval/operator_cli_gate.rs`）と 1 つの種別表を共有します。ダッシュボードでの判断だけが有効で、同じリクエストかつ同じ状態（LINE の一括処理を除く）に限られます。待機中に対象の状態が変わるとカードは取り下げられ（`state_changed`）、新しいリクエストが作られます。その場で書き換えることはありません。承認は 1 回の条件付き更新で消費され、競合に負けた実行は何もせず、新しいリクエストも作りません。待機できるのは操作と対象の組ごとに内容違いで 3 件、種別ごとに 20 件までで、通知は対象ごとに 1 時間 2 回までです（忘却リクエストは AI 従業員ごと）。`approvals.decide` は 1 つのチェックで Admin 以外の判断を拒否します。4 つのコマンドは AI 従業員のセッション環境変数の一覧も共有します（CLI クレートの `ai_session_guard.rs`）。制限は変わりません。Bash を制限なく持つ従業員はローカルのデータベースを直接書き換えられます。

**アップグレード時の注意。** このゲートは結び付け情報をリクエスト内容の `gate` オブジェクトに保存します。v1.70.0 以前に作られたリクエストにはこのオブジェクトがないため、新しいバージョンは照合も件数への算入もしません。アップグレード前に作られたリクエストは、承認済みで未適用のものでも、アップグレード後には適用されません。コマンドをもう一度実行すると新しいリクエストが作られ、改めて承認が必要です。古い待機中のカードには期限切れまで通常どおりリマインダーの通知が届きます（継続タスクのリクエストはもともと送りません）が、承認しても何も起きません。

## 操作ルール、探索レーン、操作レビュー

2026-10 追加（v1.72.0）。3 つのレイヤーはいずれも社員にできることを狭めるだけで、他のゲートが課す承認や拒否を外すことはありません。

**操作の種類（effect）。** DuDuClaw の MCP ツールにはそれぞれ 1 つの副作用の種類があります（`duduclaw_core::tool_effect::effect_of_builtin`）：`read`、`draft`、`send`、`publish`、`purchase`、`delete`、`modify`、`admin`。`read` と `draft` は応答以外に何も残さず、残りの 6 つは副作用を持ちます。引数で効果が変わるツールは厳しいほうの種類になります（`wiki_write` はどちらの scope でも `modify`）。`mail_send` は人の承認が必要な下書きを作るだけですが、最終的な効果は送信なので `send` です。`gmail_create_draft` は決して送信しないので `draft` です。表にないツール名は `admin` として扱われ（fail closed）、公開されている全ツールを調べるテストがあるため、分類されていない新しいツールは出荷できません。組み込みツールカタログ（`tools.catalog`）は種類を `effect` として返します。

**操作ルール。** `agent.toml [capabilities] action_rules` で種類ごと、またはツールごとに `allow`、`ask`、`block` を設定します。

```toml
[capabilities]
action_rules = [
  { effect = "send", verdict = "ask" },
  { tool = "mail_send", verdict = "block" },
]
```

`tool` ルール（他の `[capabilities]` ツール一覧と同じアンカー付きの照合なので、`mcp__duduclaw__mail_send` や `wiki_*` も使えます）は `effect` ルールより優先され、同じ種類のルール同士では最も厳しい判定が採用されます。`block` は MCP の dispatch ゲートで `denied_tools` と同じ場所で拒否し（JSON-RPC `-32003`、監査 `error_class` `action_rule`）、`tools/list` からも隠します。`ask` は承認ゲートの静的な「常に確認」の集合に加わるため、`approval_required_tools` と同様に ApprovalBroker の流れになります。`allow` は「このレイヤーでは何も足さない」という意味だけで、`denied_tools`、承認リスト、機能スイッチ、scope を外すことはありません。9 つの `computer_*` ツールと 3 つの `computer_workspace_*` ツールは、セッションを持つ gateway の computer-use ルートで同じ判定を適用します。このキーは意図的に `[capabilities]` に置いています。`org_field_guard` がこの表全体を社員自身の書き込みから凍結するためです。一覧やエントリの形式が不正な場合（未知の判定や種類、`effect` と `tool` の両方またはどちらもない、余分なキー、配列でない値）でもファイル全体は失敗せず、書かれたまま保持され、副作用のある呼び出しはすべて少なくとも「先に確認」になります。有効な `block` ルールは引き続き拒否します。`agent.toml` が存在するのに読めない、または正しい TOML でない場合も同じ扱いです。ダッシュボードでは社員の編集ページ（操作の種類ごとのルールと個別ツールの例外）から、管理者専用の `agents.update` の capabilities 経路で編集します。各エントリは検証され、変更は `agent_authority_changed` として監査されます。

**Claude Code の組み込みツール（2026-10-08 の仕上げ）。** `action_rules` は起動時に Claude CLI 自身のツールにも適用されます。組み込みツールは名前の完全一致で分類されます（`duduclaw_core::effect_of_cli_builtin`）：`Read`、`Glob`、`Grep`、`WebFetch`、`WebSearch` は `read`、`TodoWrite` は `draft`、`Write`、`Edit`、`MultiEdit`、`NotebookEdit` は `modify`、`Bash`、`Task`、`Agent` とそれ以外の名前は `admin` です。組み込みツールの呼び出しは ApprovalBroker を通らないため、組み込みツールに対する `ask` は守れず、`block` として扱います（fail closed）。そのツールは `CapabilitiesConfig::disallowed_tools()` を通じて `--disallowedTools` に加わり `--tools` から外れます。`denied_tools` を既に反映しているすべての Claude CLI 起動がこれを読みます（`claude_runner` のディスパッチ、cron、goal とハートビートの起床、`channel_reply/cli_env.rs` のチャネル返信、ハートビートの能動チェック、eval、チームのロールメンバー）。そのため形式の誤ったルール一覧では副作用のある組み込みツール（`Write`、`Edit`、`Bash` など）がすべて外れ、読み取り系は残ります。挙動の変更：MCP ツール向けに `{ effect = "modify", verdict = "ask" }` を書いていた運用者は、Claude CLI の `Write`／`Edit` も使えなくなります。

**削除されたツール名。** v1.69.0 で削除された名前（`shared_wiki_write`、`schedule_task`、`skill_bank_search` など）に書かれた `tool` ルールは、それを置き換えた呼び出し（`scope = "shared"` の `wiki_write`、cron の `schedule` 付き `tasks_create`、`source = "bank"` の `skill_search`）に引き続き適用されます。ディスパッチの `block` と承認ゲートの `ask` の両方で、`denied_tools` と同じです（`ActionRules::resolve_for_call`、`tool_catalog::removed_name_for_call`）。削除された名前を追うのは `tool` ルールだけで、結果は厳しくなる方向にしか変わりません。

**探索レーン。** `DUDUCLAW_LANE=explore` で起動した MCP サーバーは `read` と `draft` のツールだけを一覧に出し、実行します。それ以外の呼び出しは `-32003`、監査 `error_class` `explore_lane` で拒否されます。変数が他の値（空文字列を含む）で存在する場合はすべての呼び出しを拒否します。gateway はハートビートの能動チェック（proactive check）でこの変数を設定し、その Claude CLI の組み込みツールも `Read`、`Glob`、`Grep`、`WebFetch`、`WebSearch`（から社員自身の `denied_tools` を除いたもの）だけになります。チェックが送ると決めた通知は、引き続きハートビートが応答から送ります。変数は CLI が継承する環境を通じて MCP の子プロセスに届き、`.mcp.json` のエントリでは設定しません。能動チェックは Claude CLI でしか動かないため、他のランタイムは関係しません。2026-10-08 から、2 種類のディスパッチ作業もこのレーンで動きます：MCP Events の配信で始まる作業（購読で通常モードを許可していない場合）と、契約に `lane = "explore"` を持つ継続タスクの各ラウンドです。どちらも同じ 1 つのフラグ（`duduclaw-gateway/src/explore_lane.rs`）を立て、規則も同じです：実行できるのは Claude CLI、Codex、OpenAI 互換ランタイムの社員だけで（Codex は権限レベルにかかわらず `-s read-only` と `approval_policy=never`、DuDuClaw サーバーはレーン変数付きで登録。Codex はそのモードですべての MCP 呼び出しを拒否します）、ほかのランタイム（Grok、汎用 CLI）やタスクサンドボックスは開始前に拒否され、MoA モデルとローカル推論のみの設定も拒否されます。レーン内のプロセスが書き出す委任（`spawn_agent`、`spawn_ephemeral`、`send_to_agent`）は `bus_queue.jsonl` のエントリや `message_queue` の行に `lane` を持ち、ディスパッチャーはイベントのレーンと同様に守ります。レーンはもともとそれらのツールを拒否するので、これは第二の防御線です。`DUDUCLAW_LANE` は運用者コマンドが拒否する AI セッション変数の一覧にも入っています。

**制限された補助実行。** Claude の補助呼び出しは CLI の認証情報を使い、アカウントローテーションには入りません。通常の会話はローテーションを維持します。Claude はツールを無効にし、OpenAI 互換 API はツールなしで一度だけ呼び出します。Codex の補助呼び出しは `--sandbox read-only`、`--ignore-user-config`（認証は引き続き `CODEX_HOME` を使用）、`--ephemeral`、`--ignore-rules`（execpolicy `.rules` のみ）、`--skip-git-repo-check`、`-c approval_policy=never` を使います。プラットフォームの MCP 設定を追加せず、所有者だけがアクセスできる新しい空の一時ディレクトリで実行し、成功・エラー・タイムアウト後に削除します。システムプロンプトは prompt 内で渡し、`AGENTS.md` は書きません。プロセスには spawn-env の許可リストと Codex 認証に必要な情報だけを渡し、社員 token は渡しません。社員がネイティブ OS サンドボックスを有効にしている場合も、一時ディレクトリに読み取り専用で適用します。Codex を明示した judge と verifier も同じモードを使います。Grok、汎用 CLI の社員は対応するグローバル補助モードに切り替わり、非対応のグローバルプロバイダーや明示指定は拒否します。

補助処理と内部 runtime 呼び出しはタイムアウトした部分出力を拒否し、先に出力された `PASS` を評価結果にしません。完了済みの部分本文を表示できるのはチャネル返信だけです。Claude 補助プロセスは共通環境許可リストと既存の Anthropic 認証情報取得を使い、他社のキーやプラットフォームの社員／MCP token を継承しません。Windows の管理対象 CLI は停止状態の子を再開する前に Job Object に追加し、親の終了後もツリー全体を終了できます。Windows のネイティブ実行動作は保証されません。

**Codex に残るリスク。** このモードはすべての内蔵ツールの除去を保証しません。読み取り可能な内蔵ツールが残る場合があり、プロンプトインジェクションを受けた補助呼び出しが OS ユーザーの読めるローカルファイルを読み、その内容を出力する可能性があります。Codex のソースでは読み取り専用ポリシーがツールコマンドのネットワークを無効にします。プロバイダーへのモデルリクエストは別で、ネイティブ OS による強制は保証されません。`--ignore-user-config` はユーザー設定を省略し、空の作業ディレクトリは社員のプロジェクト設定を避けます。外部設定検査は MCP サーバーを含む設定と、既存の読み取り・解析不能な設定を拒否します。CLI help とソースの確認は、 検証元: [tool registry](https://github.com/openai/codex/blob/970111f6cb62cc02fe36a82ea7d71b37a2889c97/codex-rs/core/src/tools/spec_plan.rs#L1425-L1428), [read-only network policy](https://github.com/openai/codex/blob/970111f6cb62cc02fe36a82ea7d71b37a2889c97/codex-rs/protocol/src/protocol.rs#L1315-L1319), [system config loader](https://github.com/openai/codex/blob/970111f6cb62cc02fe36a82ea7d71b37a2889c97/codex-rs/config/src/loader/mod.rs#L274-L293).

**操作レビュー。** `config.toml [action_review] mode = "off" | "shadow" | "enforce"`、既定は `off` で、呼び出しのたびに読み直します（`system.update_config` は `action_review.mode` を受け付け、変更を保護キーとして監査します）。すべての静的ゲートが自動実行と判定し、かつツールに副作用がある場合だけ適用されます。レビュー担当はクローズドな選択肢の `decide()`（`duduclaw-gateway/src/decide.rs`）を通した utility モデルです。応答は厳密な JSON 契約のもとで `{"choice":"allow"|"ask"|"block"}` そのものでなければならず、それ以外は判定なしとして扱います。入力は構造化された情報だけです：ツール名、種類、引数のキー（識別子らしくないキーは数だけ）、ActionGuard のクローズドな finding トークン、社員の `CONTRACT.toml` の `must_not`。引数の値はプロンプトに入りません。`shadow` は結果を変えず、`tool_calls.jsonl` に `action_review` が判定または `unavailable` の行を追加します。`enforce` は `block` なら拒否し、`ask` または判定がない場合は ApprovalBroker で人に確認します。未知の mode 値や、存在するのに読めない・解析できない `config.toml` は `enforce` として扱います。2026-10-08 の仕上げ以降、レビューは OS 操作ツール（状況分類器が実行を許したあと）、`skill_hub_install`（セキュリティスキャン後の独自のインストール承認の手前）、そして gateway のコンピューター操作ルートで承認リストが人に回さなかった `computer_*`／`computer_workspace_*` ツールにも適用されます。それ以外は同じです（構造化された入力のみ、`shadow` は記録だけ、`enforce` は `block` で拒否しそれ以外は人に確認）。固定のレビュー回答（block、ask のあと承認、ask のあと拒否、判定なし）で、実際のプロセス内承認ストアに対して `enforce` を通しで動かす dispatcher テストがあります。

**サードパーティの MCP ツール（2026-10-08）。** 社員のほかの MCP サーバーのツールは、DuDuClaw がその経路上にある場所で分類されます：`duduclaw mcp-proxy`（`.mcp.json` から起動するサーバー）と `duduclaw mcp-remote-bridge`（リモートサーバー）で、どちらも gateway 内の同じ外部ツールゲートを通ります。分類の既定は `modify` で、`destructiveHint: true` は `delete` に引き上げます。上流の `readOnlyHint` はリスクを下げません。旧 `trusted_read_hint_servers` 設定も分類に影響しません。ホスト管理の読み取り例外は未実装で、探索レーンではサードパーティツールを利用できません。`action_rules` は DuDuClaw 自身のツールと同じく適用されます（ツールルールは `<サーバー>.<ツール>`、`mcp__<サーバー>__<ツール>`、`<サーバー>.*`）。`block` は社員が見る一覧からツールを隠し、呼び出しはサーバーに届く前に `-32003` で返します（監査 `third_party_tool_refused`）。`ask` は ApprovalBroker の判断まで呼び出しを保留し、承認ストアの停止、申請の失敗、拒否、期限切れはすべて拒否です（監査 `third_party_tool_approval`）。探索レーンでは `read` のツールだけを一覧化・呼び出しできます。管理対象の全ランタイムは、秘匿化や `action_rules` の有無にかかわらず `.mcp.json` の stdio サーバーをプロキシに通します。管理対象のリモート接続はブリッジを使い、直接の `url`／`type` エントリーは拒否します。`[[mcp.external]]` の stdio／HTTP マウントはプロセス内レジストリで同じゲートを使い、annotations を保持して一覧と実行を検査します。utility と探索レーンでは従来どおり `[[mcp.external]]` をマウントしません。ダッシュボード（`mcp.tool_effects`）は、サーバーごとの最後の一覧を現在の設定で再計算した種類と判断付きで表示します。ガイド：[MCP エコシステム](../../guides/ja-JP/mcp-ecosystem.md) 第 4 節。

## AI従業員の操作に対する 1 回限りの承認（ActionGrant）

2026-10-08 追加（v1.72.0）。この変更前から、人の承認が必要なツール呼び出しはそれぞれ自分のリクエストを作りその決定を待つため、承認が後の呼び出しに再利用されることはありませんでした。欠けていたのは「結び付け」です。カードには引数が表示されず、決定と実際に実行される呼び出しが結び付いていませんでした。現在は、ツールが `send` または `purchase` 類（例：`mail_send`、`odoo_sale_confirm`）の呼び出し、または `action_rules` の `ask` によって人の承認に回った呼び出しのリクエストが `payload.action_grant`（`duduclaw-gateway/src/approval/action_grant.rs`）を持ちます：

- 従業員、ツール、操作の種類、従業員＋ツール＋正規化した引数（オブジェクトのキーを整列）の SHA-256 指紋、および最大 8 行の `キー = 値` 要約（識別子の形のキーとスカラー値のみ。機密らしいキーと値は `tool_calls.jsonl` と同じ方法で伏せ字、文字列は 60 文字まで、入れ子の値は件数のみ）。カードの文面と受信箱の詳細パネル（「この承認の対象」）に表示されます。
- 承認後、保存された結び付けが実行直前の呼び出しと一致すること（同じ従業員・ツール・指紋）を確認し、呼び出しの前に 1 回だけ消費します（`approved → invalidated`、理由 `consumed:action_grant:<uuid>`）。不一致、取得競争での敗北、2 回目の使用はすべて拒否です。

2026-10-08 の仕上げ以降、人の承認が必要な経路があと 3 つ、常に（`send`／`purchase` に限らず）同じ方法で結び付けられます：MCP ディスパッチゲートの PolicyKernel `ask`、OS 操作ツールの状況ゲート（`anomaly`／`sensitive`、または操作レビューの `ask`）、gateway のコンピューター操作ルートにおける `computer_*`／`computer_workspace_*` の承認リスト。コンピューター操作ツールは gateway が組み立てた操作のスナップショットに結び付きます（入力テキストと URL はハッシュのみなので、カードには文字数か検証済みのホストだけが表示され、本文は表示されません）。gateway は承認を消費したあとツールゲートを再実行します。チャットでのコンピューター操作の高リスク確認は、もともと 1 回限りで結び付いています（`ExecutionBinding` が操作ハッシュ、スクリーンショットのハッシュ、ポリシーの版、決定のコンテキストを結び、`claim_operation`／`begin_execution` で 1 回だけ取得し、新しいスクリーンショットと照合し直します）。ワークフローは独自の結び付けを持ちます：人が必要なステップは結び付き付きのリクエストでのみ承認でき、そのペイロードと `ExecutionBinding` はステップの呼び出しと一致しなければならず、操作はフェンスのもとで取得されるため、もともと 1 ステップだけを対象にしています。インストール承認は変わりません。対象外：指紋は承認ゲート時点の引数に対して計算され、その時点で PolicyKernel の書き換えと機密の復元はすでに行われています。データベースにアクセスできる人は保存内容とカードを同時に書き換えられます。テストは単体と broker レベルのみです。

## ダッシュボードの権限は呼び出しごとに最新を読む（v1.76）

v1.76 より前は、ダッシュボードの WebSocket 接続はハンドシェイク時に読んだロールと従業員の割り当てを使い続け、アクセストークンの有効期間も 30 分あるため、割り当ての解除、降格、停止は相手が次にログインするまで反映されませんでした。現在は RPC ディスパッチの単一の入口が呼び出しのたびに `users.db` から呼び出し元のコンテキストを作り直します。トークンは「誰か」を証明するだけです。ロール、直接の割り当て、パスワード変更必須のフラグ、下記の上長関係から導く権限はすべてデータベースの値を使います。これらを変える書き込み（割り当て、解除、ロールまたはパスワードの変更、状態の変更、上長の変更、チャネル ID、メールアドレスの変更、退職処理）は同じトランザクションの中でカウンター（`auth_meta.acl_generation`）を 1 つ進め、呼び出しごとのキャッシュはこのカウンターをキーにするため、キャッシュの結果が最後のそうした書き込みより古くなることはありません。アカウントが存在しない、または在籍中でない場合は `account is suspended or offboarded` で拒否します。データベースを読めない場合はその呼び出しを `authentication service unavailable` で拒否し、トークンの内容は一切使いません。起動後に何回起きたかは `system.doctor` に表示されます。データベースの読み取りとログイン時のパスワード確認はブロッキング用スレッドプールで実行するため、ログインが集中しても他の接続の呼び出しは待たされません。ゲートウェイの管理トークン（`system`）とロック画面の接続は変わりません。

アカウントには直属の上長を 1 人設定できるようになりました（`users.manager_user_id`、複数人チーム版のみ、`users.create`／`users.update` で設定）。1 回の `users.create`／`users.update` のすべての項目は 1 つのトランザクションで書き込まれ、上長や降格が拒否された場合はその要求の他の変更も適用されません。書き込みは循環（`manager_cycle`）、最上位を含めて 8 人を超える上長の連なり（`manager_too_deep`）、上長のロールが Manager 未満または在籍中でない場合（`manager_role`、`manager_inactive`）を拒否し、直属の部下がいる人を従業員に降格することも拒否します（`manager_has_reports`）。退職時は部下を `transfer_to` または退職者の上長の下に移し、移動ごとに `user.reparent` を監査ログに残します。`transfer_to` に移す割り当ては、受け取る人がすでに同じ従業員を割り当てられている場合、高い方のレベルを残します。上長が部下に割り当てられた従業員に Operator まで届くことは計算されますが、このリリースではまだどこでも使っていません。ルーティング、`agents.list`、Operator レベルの RPC（記憶、会話履歴、設定）は引き続き直接の割り当てだけを見ます。

## 誰のための作業か（`on_behalf_of`、v1.76.0）

人が始めた作業（会話の 1 ターン、`/assign` による依頼、ダッシュボードで作ったタスク）について、ゲートウェイはその人が誰かを、作業が生み出すものすべてに引き継ぐようになりました。従業員のランタイムには `DUDUCLAW_ON_BEHALF_OF` が渡り（Claude だけでなく全ランタイム）、`send_to_agent`／`spawn_agent` はキューの行（`message_queue.on_behalf_of`、`bus_queue.jsonl` のフィールド）に書き込み、ディスパッチャーが受け取る側の実行に引き継ぎます。目標タスクの各ラウンドと heartbeat の起動はタスク行（`tasks.on_behalf_of`）から写し、`tasks_create` は新しいタスクに記録し、実行中に出た承認依頼にも保存されます（`approvals.on_behalf_of`）。値は WebChat アカウントか検証済みチャネル ID なら `user:<アカウント id>`、アカウントのない送信者なら `unmapped:<チャネル>:<ダイジェスト>`（`@` ルーティング監査と同じ鍵付き HMAC。プラットフォームの生 id は出ません）。出所はゲートウェイが書いたものだけです。起動時に設定する環境変数と、ゲートウェイまたは MCP サーバー（その環境変数から）が書いた行です。ツール引数は読みません。システム送信者名（`dashboard`、`cron` など）、予約 id、形式の誤った値は拒否し、`on_behalf_of_rejected` として監査に残します。最初に設定された値が優先され、後の段階で上書きされません。ゲートウェイ自身の環境は渡りません。起動時の許可リストにこの変数はなく、各ランタイムは継承した値を消してから、そのターンの値を設定します。

このリリースでの働き：

- **記録**（既定、`[delegation] human_principal = "record"`）：その実行の `tool_calls.jsonl` の各行、`delegation_denied` の各行、各承認依頼にこの値が付き、チャネルの承認カードには「由 ○○ 交辦」（表示名を優先し、読めない場合は短いアカウント識別子）が表示されます。これを理由に拒否されることはありません。
- **強制**（`human_principal = "enforce"`、明示的に有効化。認識できない値や読めない `config.toml` も強制扱い）：従業員の組織ツリーが委任を許可した後、その人にも権限が必要になります。`send_to_agent`／`spawn_agent` とディスパッチャーの委任ゲートでは、その人が対象を呼び出せること（Admin、直接の割り当てまたはマネージャーのチーム権限〈レベル不問〉、または `public_trigger` の従業員）。`tasks_create`（従業員が自分に割り当てる場合も含む）、`create_task`、スケジュール、他の従業員のメールボックスや記録の変更には Operator 以上が必要です。アカウントのない送信者は `public_trigger` の従業員にだけ届き、作業を依頼することはできません。存在しない・無効なアカウント、形式の誤った値、読めない `users.db` は拒否されます（`human_principal_not_permitted`）。目標タスクのラウンド、heartbeat の起動、cron は作成時の委任認可を引き継ぎます。main/default 対象の制限は実行時にも確認します。

強制モードでは、別プロセスの MCP が実行中のゲートウェイに依頼者の権限確認を求めます。渡すのはホストが発行し、従業員と home に結び付けた不透明な参照だけです。ゲートウェイは現在のアカウント情報で権限を確認します。チーム権限には署名検証済み Enterprise ライセンスと、その home でゲートウェイが解決した Enterprise エディションの両方が必要です。どちらかが Personal または不明ならチーム権限は使えません。本文で指定された人物や Enterprise 環境変数を証明として使いません。バックグラウンド呼び出しにも、ホストが明示的に登録した None context が必要です。欠落、別の従業員／home、期限切れ、解放済みの参照や MCP の身分表示との不一致は拒否されます。参照はランタイムの終了時または 24 時間後に無効となり、同時登録は最大 4096 件です。既定の記録モードはこの経路を必要としません。この context は知識ベースの requester とは別で、文書の閲覧権限を増やしません。

- `[approval] forbid_self_approval = true`（既定オフ）：従業員がある人のために作業中に出した承認依頼は、同じ人が承認できません（ダッシュボードでもチャネルのボタンでも。拒否は可能）。バインド付きの依頼は変わらず、バインドされた本人だけが決定します。

コンピューター操作 start／action の承認は、認証済み従業員と `turn_id` をキーにホストが登録した実行中の会話から本人を取得します。要求本文で本人を指定したり他の従業員の会話を借用したりできません。turn がない・未登録の場合は本人情報なしとなるため自己承認者を識別できません。turn のない workspace・screenshot・stop 要求も本人情報を記録しません。

本人の確認は従業員の権限を狭める方向にだけ働きます。記録モードはホストの身元情報を記録するだけで、権限を強制しません。強制モードでは、本人の環境変数だけを変えても gateway の context に登録された人は変わりません。OS による隔離ではないため、同じ OS アカウントで無制限の Bash を持つ従業員は、プロセスの認証情報を読んだりローカル DB を書き換えたりできます。`tasks_create` で作ったスケジュールの後の実行には本人情報が引き継がれません。`spawn_ephemeral` とその待機キューもまだ本人情報を引き継ぎません。Grok と非推奨 Gemini CLI は、起動環境を MCP 子プロセスへ引き継ぐことを保証しません。

## 補助レイヤー

**社員の予算。** `[budget] daily_cap_cents` と `monthly_limit_cents` は、それぞれ直近 24 時間と 30 日間の記録済み費用を比較し、`hard_stop = true` で上限に達すると次のモデル呼び出しを拒否します。0 は上限なしで、実行中の呼び出しは上限を超える場合があります。Claude とその他の社員ランタイム、委任・定期実行、リマインダー、メール、ハートビート、補助処理、CLI の fork／評価を対象とします。一時社員の記録済み費用も親社員に含め、ミリセントで合算してからセントに換算します。社員設定ファイルを読み取れる場合、`[budget] when_unavailable = "allow"`（省略時の既定値）は費用データベースや照会を利用できないときに警告と監査記録を残して続行し、`"deny"` はモデル呼び出し前に拒否します。設定ファイル自体の読み取りや解析に失敗すると方針を確認できないため、必ず拒否します。未知の方針の値は警告して `"deny"` として扱います。確認不能には独自の説明と監査イベントがあり、上限到達やブレーカーの状態変更として通知しません。予算による拒否はアカウントローテーションやフェイルオーバーを起こしません。社員 id のない呼び出しはこの方針の対象外です。 社員ディレクトリを指定した補助呼び出しは、処理名が渡されても有効設定の `[agent].name` で予算を確認し、今後の費用を記録します。過去に処理名のみで記録された費用を社員ごとに正確に割り当て直すことはできません。

**MCP 認可ゲート** — すべての MCP ツールはスコープ表に列挙されており、表にないツールは既定で Admin スコープを要求します。スコープ、エージェント単位の capability 付与、`denied_tools` はそれぞれディスパッチのフロントドアで強制され、拒否はすべて `error_class` 付きで監査されます。

**SOUL.md ドリフト検知** — `soul_guard` は起動時と各ハートビートティックで `SOUL.md` の SHA-256 フィンガープリントを取り、`.soul_history/` に最大10世代のバックアップを保持し、Agent Stability Index とともにドリフトを報告します。

**監査証跡** — `tool_calls.jsonl` はすべてのツール呼び出しを記録し、`result_text`／`input_text` はマスク済み（3パスのシークレットマスキング、切り詰めより先にマスク）、パーミッションは `0600`、行はハッシュチェーンで連結され、16 MB でローテーションします。`security_audit.jsonl` はセキュリティイベントを別に保持します。このログはグラウンディング事前チェックと受け入れ判定者が読む証拠源でもあるため、弱めれば検証も弱まります。

**エージェント単位の鍵分離** — MCP API キーとコネクタ認証情報はエージェント単位で、`secret_ref` 経由で解決されます。1つのエージェントの漏洩がプラットフォーム全体の漏洩にはなりません。チャネルの認証情報は2種類に分かれます。LINE、WhatsApp、Feishu、Google Chat、Teams、WeCom、DingTalk は `config.toml [channels]` にあるデプロイ全体共通の認証情報を使い、社員専用の bot トークンがあるのは Telegram、Discord、Slack だけです（自分のトークンがない社員は `reports_to` をたどって上位を探し、最後にグローバルのトークンを使います）。

**Google Chat Pub/Sub（v1.80.0 から）** — Pub/Sub 通知は Chat 送信者の認証には使いません。gateway はメッセージのリソース名を検証し、アプリの `chat.bot` で Chat API から読み直してからターンを作成します。送信者、スペース、本文、添付、スレッドは API 応答のみを使い、名前とスペースがリソースおよび通知のスペースと一致する必要があります。既存の送信者アクセス・ペアリング・承認ルールは維持します。読み取り失敗（403／404 を含む）やメッセージのないイベントはターンを作成しません。インポート時と起動時に、サブスクリプションがサービスアカウントのプロジェクト内の指定トピックを指すことを検証します。pull トークンは `pubsub` のみです。Unix 専用の永続 inbox はリソース参照のみを保存し、本文・送信者情報・添付は保存しません。イベント種別とリソース名で 7 日間重複を除去し、API の作成時刻が 7 日より古いメッセージは記録削除後も拒否します。アプリ stream（社員／共有アプリとプロジェクト番号）ごとに 1,000 行、pending／queued／running 10 件に制限し、単一 stream による容量の占有を防ぎます。全体の上限は引き続き 10,000 行、処理待ち・実行中 100 件、参照 2 KiB、データベース 64 MiB です。実行中・待機中の記録は削除せず、中断された実行は uncertain として自動再実行しません。キュー満杯時は ACK して破棄し、ターンを開始しません。データベースと付属ファイルの非公開権限を検証し、他のプラットフォームは同等の保護が整うまで Pub/Sub を拒否します。Pub/Sub 作成スクリプトはクラウドリソースを検証後にキーを作成し、破壊的な復旧コマンドは手動用に表示するだけです。[設定と配信の制限](../../guides/ja-JP/channels-googlechat-teams.md)を参照してください。 インポート時と worker 起動時は exactly-once 配信が有効なサブスクリプションを拒否するため、Google Cloud で無効にしてください。無効・期限切れ ACK（HTTP 400）では古い配信バッチのみを破棄して再取得し、永続重複除去記録は保持します。一時的な ACK 失敗ではバッチを保持して再試行します。

**チャネル上のチャットコマンド（v1.68.0）** — `!STOP`、`!STOP ALL`、`!RESUME`、`/model <名前>` には管理者が必要です。WhatsApp、Feishu、Teams、WeCom、Google Chat、DingTalk では以前、すべての送信者に `is_admin = true` を渡していたため、bot にメッセージを送れる人なら誰でも停止や再開ができました。現在これらのチャネルは、送信者 id または会話 id をチャネルの `admin_users` 設定（グローバル範囲。Google Chat と Teams も設定可能になりました）と完全一致で照合し、一覧がなければ誰も管理者になりません。WebChat では、有効なダッシュボードアカウントで役割が管理者のものだけが該当し、Web サイト用ウィジェットの訪問者は該当しません。

**キルスイッチのしきい値（v1.68.0）** — `KILLSWITCH.toml [triggers]` の4つのしきい値には以前は読み取り側がありませんでした。現在はファイルに書かれていて範囲内のキーだけが有効になり、セキュリティ設定ページではしきい値ごとにチェックボックスがあります（チェックを外すと `null` を送り、キーを削除します）。ファイルが変わると読み直します。`cost_limit_usd` は全社員の24時間の支出と比べ、達するとグローバルの failsafe レベルを制限状態にし、failsafe が自然に回復するか誰かが `!RESUME` を送るまで続きます。`max_replies_per_minute` は会話ごとに数え、超過分は黙って破棄します。`max_consecutive_errors` と `error_rate_threshold`（直近20回、最低10回）はその会話の failsafe レベルを1段階上げます。発動ごとに `killswitch_trigger` として監査されます。`KILLSWITCH.toml` の `[audit]` セクションは読まれなくなりました。

**返信サーキットブレーカーと、何通かに分けて書く人** — すべてのチャネル返信の前にある会話ごとのブレーカー（`KILLSWITCH.toml [circuit_breaker]`）は、人にとってごく普通の 3 つの場面でメッセージを黙って捨てていました。直近の返信よりずっと長い返信の次のメッセージ（`token_explosion_multiplier`。これはこちらの出力の性質です）、返信を待つ間の「在嗎？」のような似たメッセージの 3 連続、`frequency_window_secs` 内に `frequency_max_replies` を超えるメッセージです。作動すると会話全体が `cooldown_secs` の間沈黙し、failsafe レベルも 1 段上がるため、繰り返すと制限応答やミュートになっていました。現在は、長すぎる返信は記録だけにします。20 文字未満のメッセージは重複とみなしません。頻度の上限を超えたメッセージはウィンドウに空きができるまで待ってから返信します。30 秒待っても空きがない場合（大量送信）は返信しませんが、件数には数え、送信者には 1 分に 1 回だけ知らせます。引き続きブレーカーが作動するのは 3 つです。こちらの直前の返信をそのまま返してきたメッセージ、長くてほぼ同じメッセージの 3 連続、そして新しいハード上限です。同じ会話で `hard_window_secs`（既定 60 秒）内に `hard_max_messages`（既定 30）件を超えると作動し、ボット同士が短く内容の違うメッセージを送り合うループを止めます。チャネルがボットと示す送信者（Telegram の `is_bot`）は、短いウィンドウで頻度を超えると従来どおりすぐ作動します。既存の設定の名前と範囲は変わりません。2 つの新しい値は、管理者がセキュリティページのキルスイッチカード（詳細：サーキットブレーカーのしきい値）で変更できます。`killswitch.update` は共通の設定書き込み処理で `KILLSWITCH.toml` を書くようになりました（ファイルロック、読み込み後に変更された場合や解析できない場合は拒否、コメントは保持）。

**秘匿化のデータソース保護（v1.68.0）** — 「プライバシー / 秘匿化」タブの「資料來源保護」スイッチが機能するようになりました。`user_input` はチャネルのメッセージを AI に渡す前に、`system_prompt` は組み立て済みのプロンプトを（既定では `apply_to_system_prompt` が付いたルールだけ）、`cron_context` は条件スクリプトのトリガーメッセージを秘匿化します。エラー時は秘匿化されていない内容を送らず、そのターンを止めます。`sub_agent`（同じタブ、または `config.toml [redaction.sources]` で設定します）は、委任先のエージェントの返信をゲートウェイが委任元エージェントの会話履歴に書き込む経路を対象にします（`send_to_agent`・`spawn_agent`・`spawn_ephemeral` の返信、チェーンを始めたエージェントへ中継される分を含む）。`on` にすると、返信は受け取る側のエージェントのルールで秘匿化されてから保存され、そのエージェントがユーザーに答えるときにトークンが元に戻ります。既定の `inherit` は返信をそのまま残します。サブエージェントは同じ `[redaction]` ルールの下ですでに動いているためです。秘匿化に失敗した場合は、返信の代わりに固定の通知文を保存します。対象外：ユーザーのチャネルに送られる返信（ユーザー自身が見るもの）、エージェントが `check_responses` で自分から取得する返信（ツール結果なので `tool_results` に従います）、Team-as-Agent の役割間の受け渡し、Agent Mail。`purge_after_expire_days` は保管庫の掃除に使われるようになりました。

**権限フラグ（v1.68.0）** — `agent.toml [permissions]` の `can_create_agents`、`can_send_cross_agent`、`can_modify_own_skills`、`can_schedule_tasks` が `false` と書かれていると、MCP のディスパッチゲートで対応するツールが拒否されます（`permission_denied` として監査）。アップグレード後の最初の起動で古いテンプレートの `false` を `true` に移行します。[ダッシュボード設定の対応表](../../guides/ja-JP/dashboard-settings.md#ai-社員の編集ページ)を参照してください。

**rootless コンテナエンジン（DuDuClaw OS v0.4.0）** — DuDuClaw OS v0.4.0（プラットフォーム v1.73.4 を同梱）から、ゲートウェイは root ではない `duduclaw` アカウントで動き、コンテナは rootless Podman で動きます。ゲートウェイは `DOCKER_HOST`／`CONTAINER_HOST` で接続します。v0.3.0 以前のイメージでは、ゲートウェイと Docker は今も root で動きます。プラットフォーム側の対応は次のとおりです。環境変数を空にして起動するコンテナクライアント（タスクサンドボックス、Discovery の試行と採点、後片付け）は、ゲートウェイにこの 2 つが設定されているときだけ、その 2 つを引き継ぎます。AI CLI の許可リストには入れません。スクリプトサンドボックスは `mcp-server` 内で動くため、ゲートウェイは各社員の MCP 設定にある自分の `duduclaw` 項目にもこの 2 つを書き込みます。エンジンが rootless と報告した場合、タスクサンドボックス、スクリプトサンドボックス、コンピュータ操作、Discovery の試行と採点のコンテナは、メモリ 32 MiB・プロセス 32 個の上限を付けた使い捨てコンテナで自身の `memory.max` と `pids.max` を読み、`max`（cgroup コントローラが委譲されていないと、エンジンは上限を受け付けたうえで黙って無視します）や要求と異なる値が返った場合、または確認が終わらなかった場合は、上限なしで動かさずに理由付きで利用不可になります（タスクサンドボックスのコードは `resource_limits_unenforced`）。通常の（rootful）Docker では確認しません。結果は 10 分間（確認に失敗した場合は 1 分間）使い回し、エンジンが利用不可から復帰した時点で破棄します。

**`duduclaw-sysd` の呼び出し元（DuDuClaw OS v0.4.0）** — DuDuClaw OS v0.4.0 はこのヘルパーの許可 uid をゲートウェイの uid に切り替えました。その uid は AI 社員の CLI の実行ユーザーでもあるため、uid の照合だけでは任意の社員がソケットを直接開き、ゲートウェイ側の承認をすべて迂回できます。これは可用性だけの問題ではありません。`update_rollback` は 1 つ前のシステムスロットで起動し、非 root への最初のアップグレード後はゲートウェイ（と社員）がまだ root で動いていた古いイメージになります。`ssh_service_start` はネットワークサービスを開きます。そこでヘルパーに `--require-main-pid-of <unit>` を追加しました。呼び出し元はその systemd ユニットのメインプロセスである必要があり、ゲートウェイ再起動後に再利用された pid がなりすませないよう pidfd（`SO_PEERPIDFD`、Linux 6.5 以降）で確認し、さらにユニット自身の cgroup にいることを求めます。同時に実行する確認は最大 4 件、各 2 秒までで、どこかで失敗すれば拒否します（Linux 以外ではこのフラグはすべて拒否）。古い OS イメージが動き続けるようオプトインで、v0.4.0 はゲートウェイの非 root 化と同じ版でこれを有効にしています。前提は yama の `ptrace_scope` が 1 以上であること（社員のプロセスはゲートウェイの子孫で、ゲートウェイを ptrace できてはいけない）と、ゲートウェイが sysd への接続を子プロセスに渡さないこと（呼び出しごとに接続を開き、close-on-exec で作成）です。時刻設定を変える運用者向け端末コマンド（`duduclaw os system timezone-set`／`ntp-set`）も別プロセスで動くため、フラグを有効にするとダッシュボードのシステム設定を使うよう案内して失敗します。そのため、別の `mcp-server` プロセスで動く `os_*` MCP ツールは自分でソケットを開かなくなりました。端末上では自身のチェックを通したうえで、ゲートウェイの署名付きループバックルート（`/api/internal/sysd`）経由で送り、このルートはそれらのツールに必要なコマンドだけを受け付け（SSH、ネットワーク、ホスト名、タイムゾーン、ローカルモデルは不可）、ゲートウェイ自身が sysd を呼び出します。ゲートウェイの鍵ファイルを読める同じユーザーのプロセスはこのルートに署名付きで要求できますが、できることは上記のコマンドに限られ、その中のロールバックが安全なのは sysd が古い対象を拒否するからです（次の段落）。値を受け取るコマンドも呼び出し元を信頼しない前提で見直しました。ホスト名は 64 バイト以下の RFC 1123 名になりました（これまでは長さしか確認しておらず、`-` で始まる値が `hostnamectl` のオプションとして渡っていました）。タイムゾーンとインターフェース名は英数字で始まる必要があり、こうした値は `--` の後に置きます。ヘルパーには固定のローカルモデル用コマンド（1 つのモデルサービスの停止と再起動だけ）を追加し、ゲートウェイが自分で `systemctl` を実行することはなくなりました。工場出荷時リセットは「ネットワーク設定も消去」の選択を含む 1 つのコマンドになりました。`duduclaw-factory-reset.service` という oneshot を持つイメージでは `/data/system/factory-reset.pending` を書いて再起動し、ゲートウェイが起動する前に oneshot がゲートウェイのデータ、キオスクのホーム、ゲートウェイのコンテナストア、（選んだ場合は）Wi-Fi を消去します。古いイメージでは従来どおりすぐに消去し、それを root 側で行います。ゲートウェイは古いヘルパーに当たると何も削除せずにリセットを拒否し、ヘルパーに接続できない端末でも同様です。ゲートウェイとヘルパーは同じ版の OS イメージから出荷する必要があります。

**非 root のゲートウェイで防げること、防げないこと（DuDuClaw OS v0.4.0）** — DuDuClaw OS v0.4.0 以降では、シェルを持つ AI 社員はゲートウェイのユーザーとして動きます。ゲートウェイの鍵を読めるため、ゲートウェイの署名付き内部リクエストやダッシュボードのセッションの偽造を含め、ゲートウェイにできることは何でもできます。ゲートウェイを root から外すのは、そうした社員を root から遠ざけるためで、ゲートウェイ自身の権限から遠ざけるものではありません。これまでのルールは変わりません。本当の隔離は Bash を与えないこと、または作業をタスクサンドボックスで動かすことです。そのため root を取り戻させないための関門は呼び出し元を信用しません。`duduclaw-sysd --min-rollback-version <バージョン>`（非 root ゲートウェイの最初のリリースである v0.4.0 が、自身のイメージバージョン `1.73.4-y1-bringup` に設定）は、ロールバックで起動しうるエントリのどれかがそれより古い場合、またはエントリのバージョンを統合カーネルイメージ自体（埋め込まれた `os-release` をファイル名と照合）から読めない場合にロールバックを拒否します。Type #1 エントリ（`loader/entries/*.conf`）は同じ厳密さで確認できないため、1 つでもあればロールバックを拒否します。更新のインストールも root に戻る経路でした。システム更新ツールはソースディレクトリにあるものを検査せずにインストールし、そのディレクトリはゲートウェイ自身のダウンロードフォルダだったため、同じユーザーのプロセスが任意のイメージ（高いバージョン名に変えた古い署名済みイメージを含む）を置けました。インストールはヘルパーの新しいコマンド経由になりました。root として、ヘルパーに組み込んだ OS 署名鍵でリリースの署名付きチェックサム一覧を検証し、一覧にあるファイルだけを（リンクをたどらず、通常ファイルのみ、コピーしながらハッシュを照合して）root 専用のステージングディレクトリにコピーし、宛先スロットに結び付いたカーネルイメージを選び、そのイメージに埋め込まれたバージョンが実行中より新しく、ロールバック下限以上の場合にだけインストールします。ゲートウェイ側のチェックは、より早くわかりやすいエラーのために残します。従来のインストールコマンドはゲートウェイの内部ルートから呼べなくなりました。使い切ったエントリの消去は削除するだけです。ヘルパーの外に残る点として、ブートローダー自身のブートカウントは、新しいエントリが正常と記録される前に 3 回続けて起動に失敗すると別のエントリに戻るため、v0.4.0 は最初の起動が正常と記録された後、下限より古いエントリを削除します。このためアップグレードは一方向です。v0.4.0 のイメージが一度正常に起動すると、デバイスは v0.3.0 以前に戻れません。後の版に問題があれば、より新しいイメージを入れるかレスキューエントリを使います。最初の起動が正常と記録されるまでは、古い root ゲートウェイのエントリがまだブートローダーの退避先で、新しいイメージ上の社員は試行起動をわざと失敗させてそこへ戻せます。この窓は数回の起動分です。

**専用アカウントと一時鍵によるメンテナンス SSH（ヘルパー側、v1.75.0、まだ使えません）** — ヘルパーに `ssh_maint_open` と `ssh_maint_status` の 2 つのコマンドを追加しました。ポートを開けるだけでなく、専用アカウント（`duduclaw-maint`、uid／gid 4800）とウィンドウごとに 1 つの公開鍵でメンテナンスログインするためのものです。ゲートウェイは AI 社員と同じユーザーで動くため、鍵を決めるのはヘルパーだけです。受け付けるのは 1 つの鍵（Ed25519、ECDSA P-256／P-384／P-521、2 種類の FIDO セキュリティキー、または 3072〜8192 ビットで指数が奇数かつ 64 ビット以下の RSA）だけで、デコードしてすべての欄と長さを確認し、`authorized_keys` のオプション、証明書、秘密鍵（OpenSSH、PEM、PuTTY）、RFC 4716 ブロック、複数の鍵や行を拒否します。ファイルに書くのは固定のオプション（`no-port-forwarding,no-agent-forwarding,no-X11-forwarding`）とデコードしたバイト列の標準エンコードだけです。鍵ファイルは tmpfs 上（`/run/duduclaw-maint-ssh/authorized_keys`、root:duduclaw-maint 0640）にあり、シンボリックリンクをたどらないディレクトリハンドル経由で書き、既存の鍵を置き換えない rename で配置し、読み戻して照合します。書き込む前に、ヘルパーは実際に有効な設定（systemd のマージ後のユニットと読み込まれた nftables ルールセット）を確認します。OS の準備完了マーカー、アカウントの uid と gid、dropbear のマージ後のコマンドラインが期待値とトークン単位で一致すること、dropbear のユニットがヘルパーに束縛されていること（`BindsTo=`）、このアカウントのループバック通信を拒否するファイアウォールルールとそこへのジャンプ、22 番ポートを LAN／VPN の送信元に限る集合です。どれか 1 つでも合わなければウィンドウを開きません。ウィンドウは、ヘルパー自身の期限（最大 24 時間、`CLOCK_BOOTTIME` で計るため時計を変えても延びません）、ゲートウェイによるクローズ、ヘルパー再起動時の残留検出、ヘルパーが止まっている場合は開くときに仕掛けた systemd の一時タイマー（閉じるときに取り消します）のいずれかで終わります。ヘルパーは 15 秒ごとに journal からログインとログアウトを読み、journald 自身が埋める欄（`_SYSTEMD_SLICE=system-dropbear.slice`、`_UID`）だけを信用して、root だけが読み書きできる監査ファイル `/data/system/maint-ssh-audit.log` に追記します。ゲートウェイを通さないため、ゲートウェイが止まっても乗っ取られても、この記録は止まりません。ヘルパーが監査ファイルのロックを待つのは数秒までで、書けなければウィンドウは開かず、クローズ時は問題を報告したうえで記録（とまだ読めていない journal のイベント）を保留し、書けるまで再試行します。ウィンドウの状態と journal の読み取り位置は永続ストレージ上の root 専用ディレクトリ（`/data/system/maint-ssh/`）に置くため、ウィンドウ中に再起動してもログインの記録は消えません。次回起動時の後片付けが保存した位置から journal を読み直し、トリガー `reboot` でクローズの記録を書きます。ウィンドウが開いている間は、確認のたびにファイアウォールのメンテナンス用送信ルールも読み直し、なくなっていればウィンドウを閉じます。オープンには頻度制限があります（5 秒以上の間隔、1 時間に最大 12 回）。イベントの文字列は 128 文字に切り詰め、制御文字を除きます。各ウィンドウの最初の 50 件のログインは 1 件ずつ書き、それ以降は数だけを数え、ファイルのローテーション時にはそのウィンドウを開いた記録を新しいファイルの先頭に書き直します。このアカウントを持つイメージでは、ポートを開けるだけの従来の `ssh_service_start` は拒否されます。どちらのコマンドも、`os_*` ツール用のゲートウェイ内部ルートからは呼べません。OS イメージがこのアカウントを同梱し、ゲートウェイとダッシュボードの部分が揃うまでは使えません。

## ドキュメントナレッジベース

[ドキュメントナレッジベース](63-knowledge-base.md)は、アップロードした文書のコレクションを AI 社員が検索できるようにします。ガードは次のとおりです。

- **コレクション単位・既定拒否の権限**を 1 つの関数が SQL で判定します。読み取りには社員（またはその部門）への付与と、ターンの相手への付与の両方が必要で、グループ会話では `personal` と `restricted` を除外します。読めない付与は無効とし、存在しない段落と権限のない段落には同じ `permission denied` を返します。
- **解析は別プロセス**：各文書は `duduclaw knowledge-extract` が読み、時間上限、CPU 上限、Linux のアドレス空間上限、macOS と Linux では書き込みとネットワークを禁止し読み取りをファイル・解析プログラム・システムライブラリに限るサンドボックスを適用します。サンドボックスがなければ、管理者が明示的に許可しない限り拒否します。Office ファイルは先に zip ボム検査を通り、`.xlsx` はセル単位で上限付きで読みます。パーサーが落ちても終わるのはその子プロセスだけです。
- **文書の内容はデータ**：取り込み時にインジェクションらしい文言を検査して印を付け、ツールの結果では各行が `│ ` で始まる印付きブロックに入れ、文書が結果の見出しを偽造できないようにします。ゲートウェイが登録していないターンからのツール呼び出しは何も読めません。返信のプロンプトに入れる段落は `<knowledge_passages>` ブロック内で XML エスケープし、指示らしい段落は自動挿入せず、システムプロンプトで段落はデータだと明示します。最後の点はプロンプト上の規則でモデルが従わない可能性があるため、`answer_mode = "kb_only"` を用意しています。
- **返信が誰のためか**はモデルではなくゲートウェイが判定します。WebChat はログイン中のアカウント、メッセージアプリの送信者は**検証済み**のチャネル紐付けがある場合だけアカウントとして扱い、それ以外（公開ウィジェットやサイトのライブチャットの訪問者を含む）はチャネルとしてだけ扱います。公開訪問者は public のコレクションだけを読めます。スケジュールはシステムターンで、社員に付与された public／internal のコレクションに限られます。人のターンから出たディスパッチはその人の範囲を引き継ぎ（未紐付けの送信者からの依頼はチャネルの付与のみ）、認識できないセッションからの返信は何も読めません。
- **グループでの引用は仕様**：紐付け済みの送信者本人と部門のコレクションはグループで引用されることがあり、回答と出典フッターはメンバー全員に見えます。personal と restricted はグループでは使いません。
- **ダッシュボード以外からの追加には必ず人の承認が必要**：`knowledge_add_source` とチャットコマンド「加入知識庫」はダッシュボード専用の承認カードを作るだけで、決定時点で管理者またはそのコレクションの編集者である人が決めます。カードには内容のハッシュ、テキストのプレビュー、依頼元を保存し、ファイルが変わっていれば承認時に拒否します。チャネルがその送信者のために保存したファイルだけが対象で（入力されたファイル参照は無効）、訪問者と未紐付けの送信者は提案できず、保留中のカード数は社員ごと・提案者ごとに上限があります。
- **URL ソース**は公開ページ取得の規則（内部アドレス・ユーザー情報・リダイレクト不可、5 MB）に従います。
- **監査**：読み取りはすべてナレッジのアクセスログに記録し、コレクション・権限・削除の変更は `security_audit.jsonl` にも記録します。
- **ベクトルも同じ権限に従う**：類似度を計算する前にベクトルのリストを許可されたコレクションへ絞り込むため、読めないコレクションが top-k の枠を取ることはありません。
- **埋め込みモデルは固定**：各モデルファイルと ONNX Runtime のアーカイブはサイズと SHA-256 付きで 1 つのコミットに固定されています。一致しないダウンロードやオフラインパッケージは拒否し、完全に検証されたインストールだけが有効です。展開した ONNX Runtime ライブラリ自体もハッシュが固定されており、読み込む前に照合するため（秘匿化の AI 検出でも同様）、手で置かれたライブラリは拒否されます。オフラインパッケージはリリース鍵で minisign 署名され、展開前に署名を確認し、展開時は想定した通常ファイルだけを書き込みます。独自のクラウドエンドポイントは、管理者が `allow_private_endpoint` を設定しない限り公開の `https` アドレスでなければならず（リクエストのたびに解決し直して接続先を固定）、開示の確認記録は設定ファイルの詳細編集で追加・変更できません。ローカルモデルでは文書のテキストがマシンの外に出ません。
- **クラウドの埋め込みはオプトインで、失敗時は何も送らない**：どのベンダーとホストが段落を受け取るかを管理者が確認する必要があります（プロバイダー、ホスト、モデルに紐付き、変更するたびに再確認が必要）。段落と質問は先に `[redaction]` ルールを通り、該当した箇所はカテゴリのマーカーに置き換わります。秘匿化がオフ、ルールがコンパイルできない、またはルールがない場合は何も送信せず、検索はキーワードのみになります。`restricted` と `local_only` のコレクションは送信されません。エンドポイントは `https` 必須（平文の `http` は `127.0.0.1` 宛てのみ）で、リダイレクトは辿らず、プロバイダーのエラー本文は保存しません（ステータスコードのみ）。32 MB を超える応答は拒否します。秘匿化の強制オフスイッチは送信を即座に止め、実行中の埋め込みジョブはバッチごとにプロバイダー、確認、秘匿化を確認し直します。プロバイダーを切り替えると、前のプロバイダーのエンドポイントとモデル設定はリセットされます。インストール、削除、プロバイダーの切り替えは `security_audit.jsonl` に記録されます。

未対応：Windows の解析にはサンドボックス（そのため既定では拒否）もメモリ上限もありません。ハートビートにはターン ID も実行 ID もないため、そのツール呼び出しは何も読めません。ルールベースの秘匿化は、クラウドの埋め込みプロバイダーへ送る段落に含まれるすべての氏名を認識できるわけではありません（AI 検出モデルのほうが精度は高いものの、完全ではありません）。
## @ によるスタッフ呼び出しは送信者の権限に従う（v1.76）

v1.76 より前、`[agent] trigger` の照合は送信者を見ない部分文字列一致でした。1 人のスタッフにしか紐付いていない WebChat アカウントでも、他のスタッフのトリガーを打てば呼び出せ、LINE の友だちも同様でした。現在は先に送信者（WebChat はダッシュボードアカウント、メッセージアプリは**確認済み**の `channel_identities`、なければ未紐付け）を解決し、その送信者が呼べるスタッフだけを照合します。管理者は全員。誰でもその会話の既定のスタッフと `[channels] public_trigger = true` のスタッフ（管理者のみ変更可、スタッフ自身は変更不可）を呼べ、ダッシュボードアカウントと紐付けのあるメッセージアプリの送信者はさらに紐付いたスタッフを呼べます。それ以外への呼び出しはモデルを呼ぶ前に拒否され、`trigger_route_refused` として `security_audit.jsonl` に記録されます（アカウント、またはインストールごとの鍵 `trigger_audit.key` によるプラットフォーム ID の HMAC）。停止中のアカウントの紐付けは数えません。照会に失敗した場合は未紐付けとして扱います。呼ばれたスタッフは専用のセッションで答えるため、履歴や機密がスタッフ間で混ざりませんが、グループでは回答がメンバー全員に見えます。詳細は [@ で AI スタッフを呼び出す](62-calling-ai-staff.md)。

## 人による AI 社員の設定ファイル編集（v1.76.0）

人格設定、自己紹介、作業ルール、行動の境界（`SOUL.md`、`IDENTITY.md`、`INSTRUCTIONS.md`、`CONTRACT.toml`）は、社員のオーナーと管理者がダッシュボードで編集でき、保存のたびに有効になる前にチェックされます（決定 D7）。書き込める人は呼び出しのたびに `users.db` から読み直され、書き込み直前にファイルロック内でもう一度確認されるため、チェック中に紐付けが解除されれば書き込みは止まります。まず固定ルール（サイズと制御文字、境界の厳密な解析、隠れた・見えない内容、追加行のインジェクションの型、キーのような文字列、人格設定の大部分の削除、境界の削除）。次にデプロイのユーティリティモデルが差分を確認します。編集された文字列はランダムな nonce 付きのタグで囲み、隠れた内容を除いてから渡し、返答は固定の形式に完全に一致しなければなりません。モデルは結果を厳しくする方向にしか変えられません。確認が完了しなければ少なくとも警告で、合格扱いにはならず、無効にもできません。管理者以外が高リスクに当たった場合は管理者に送るだけです（`agent_file_change`、ダッシュボードでのみ判断、チャネルにはボタンのない通知のみ）。このチェックは人が送った内容が対象で、社員自身による書き込みは引き続き `agent-file-guard` が止めます。書き込みごとに社員フォルダーの外に版を残して `agent_file_changed` を、拒否は `agent_file_change_refused` を記録します。INSTRUCTIONS.md にも SOUL.md と同様の承認済み指紋ができました。同じリリースで管理者専用の `agent.toml` 項目も広がりました（bot トークン、`[odoo]`、`[runtime] provider`／`fallback`、`[prompt] cli_bare_mode`、`[os_watch]`、`[model] account_pool`、`role = "main"`、予算の緩和）。[ダッシュボード設定](../../guides/ja-JP/dashboard-settings.md#設定ファイルv1760)を参照。

## 特定の人の認証情報をシステムのキーチェーンに置く（v1.76.0）

AI 社員が特定の人（例：同僚の Google アカウント）として動けるようになると、認証情報が盗まれたときの影響が大きくなるため、その種の認証情報には専用のキーを使います。この「保護キー」は 32 バイトの AES-256 キーです。対応するデスクトップ OS では OS の認証情報ストアに、Docker／ネイティブ Linux の保護サービスでは root 専用キーで包み、特定の人の認証情報はこれで封印されます（`pk:v1:<キー ID>:…`）。home 全体の認証情報（`.keyfile` とそれで復号する `*_enc` の値）は変わりません。

- **既定はオフ。** 管理者が「セキュリティ」ページの「認証情報の保護」カードで有効にします（RPC `security.credential_protection_enable`）。`duduclaw credentials status` も同じ 1 行を表示します。オフの間はほかに何も変わらず、特定の人として動く機能は実行を拒否します。
- **macOS：** 項目はログインキーチェーンに置かれ、復号の権限は作成した `duduclaw` 実行ファイル（コードハッシュで識別）だけを信頼します。Claude の `Read`、`cat`、バックアップ、`security`、Python スクリプトでキーを読もうとしても失敗し、Mac の前に人がいれば macOS が先に確認します。gateway 自身の読み取りではダイアログは出ません。`duduclaw` プロセスに注入されたコードも `duduclaw` として扱われます。テストでは ad-hoc 署名の作成元にコードを注入するとキーを確認なしで読め、hardened runtime を有効にすると防げました。そのため、実行中の実行ファイルが hardened runtime を持つときだけカードは「DuDuClaw のプログラムだけが読み取り可能」と表示します。リリース版の CLI はまだ持たないため「同じユーザーアカウントのプログラムは読み取り可能」と表示し、注入の可能性を説明します。アップグレード後は実行ファイルのハッシュが変わるため、Mac の前で誰かが `duduclaw credentials authorize` を実行して一度許可するまで個人アカウントは停止します。ほかの機能は止まりません。
- **Windows：** キーは資格情報マネージャーにあり、ファイルやバックアップには含まれませんが、同じ Windows ユーザーで動くプログラムはすべて読めます。シェルを使える AI 社員も含みます。ダッシュボードはその旨を表示します。
- **通常の Docker と Linux ユーザーサービス：** 隔離された鍵を持たないため個人アカウントは拒否します。下記 Docker オーバーレイまたは[ネイティブ Linux の保護システムサービス](../../guides/ja-JP/linux-protected-service.md)を利用してください。鍵を受け取るのは gateway だけで、端末の認証情報ステータスは gateway の状態を示しません。
- **ネイティブ Linux の保護サービス：** ガイドに従って検証済みのリリースを root 管理の場所からインストールし、専用システムアカウント、root 所有の実行ファイルと systemd ランチャーを配置します。non-dumpable の gateway は、正確な cgroup v2 ユニット、実行ファイル所有者、空の補助グループ、既知のエンジンソケットへのアクセス拒否を確認してルートキーを受け取ります。sudo と linger は禁止です。Bash／ツールは同じ uid を使い、未知の abstract socket 名、その他の権限昇格経路、ホスト root の侵害は保護対象外です。既知の abstract 名を含む一般的なエンジンソケットと補助グループを毎分再検査し、失敗するとルートキーを消去し、再起動まで個人接続を無効にします。ホストはこのアカウントに特権ブローカーへのアクセスを付与しないでください。更新には `sudo /opt/duduclaw/bin/duduclaw service upgrade --protected-linux` を使います。移行、更新、アンインストールと検証の制限はガイドを参照してください。
- **Docker と person-credentials オーバーレイ：** `docker compose -f docker-compose.yml -f docker-compose.person-credentials.yml up -d` で起動します（手順は [Docker ガイド](../../guides/ja-JP/docker.md#74-個人アカウントperson-credentials-オーバーレイ)）。コンテナは root で起動し、`cap_drop: ALL` に `SETUID`、`SETGID`、`SETPCAP` だけを戻します。短い起動スクリプト（`container/protected-key-launcher.sh`）が 32 バイトのルートキーを root だけが読めるボリューム `/var/lib/duduclaw-protected` に置き、初回セットアップを `duduclaw` として実行し、そのとき残ったプロセスをすべて終了させ、ファイル記述子 3 でキーを開いて、`duduclaw` として全ケーパビリティを空にし `no_new_privs` を付けて gateway を起動します。gateway は PID 1 なので、止まるとコンテナ内のほかのプロセスもすべて終わります。gateway はキーを読む前に自分を non-dumpable にし、読んだら記述子を閉じ、次を確認します：PID 1、ユーザーとグループが root でない、全ケーパビリティが空、`NoNewPrivs`、non-dumpable、自分ではキーのパスを開けない、Docker や Podman のソケットがない、`DOCKER_HOST` がない。どれか一つでも合わなければキーを捨て、個人アカウントは無効のまま、カードに理由を表示します。保護キーは home の中ではルートキーで包んだ形（`protected/container-wrapped-key.json`）でしか存在しません。包んだファイルが変更されたり別の場所のものだったりすると「保護キーが置き換えられました」と表示されます。カードの表示は「独立した鍵（AI 社員は読み取れません）」です。
  - 実測環境は Docker Desktop 7.0（arm64、Yama なし）です。同じコンテナ内の uid 1000 から、さらに `unshare -Ur` の中からも試しました。キーファイル、`/proc/1/mem`、`environ`、`fd`、`root`、`maps` を開くこと、`ptrace`、`process_vm_readv` はすべて拒否され、コンテナ内から送った SIGKILL と SIGSTOP では PID 1 は止まりませんでした。Docker ソケットのマウント、`--init`、`SETPCAP` の不足はそれぞれ拒否されます。未実測：完全なサーバーイメージ、Windows の Docker Desktop、Podman、rootless Docker。
  - トレードオフ：キーを持っている間、gateway は自分のプロセスで ONNX モデルを読み込みません。社員がモデルファイルを書き換えられ、そのファイルがネイティブのパーサーに届くためです。AI プライバシー検出（NER）による匿名化、ローカルのナレッジベース埋め込み、Kokoro 音声が止まり、ナレッジ検索はキーワード検索になります。**このとき NER の匿名化ルールはモデル未導入と同じ動作になり、そのルールではテキストが伏せられません。**NER の匿名化が必須の環境では正規表現ルールを使うか、このモードを使わないでください。
  - 防げないこと：シェルを使える社員は、許可された範囲で gateway を通じて Google を使う、自分のターンに発行されたアクセストークンを読む、gateway を止める、再起動後に古い home のファイルを戻す、ことができます。最後の一つはダッシュボードの「キーを新しくする」では防げません。ルートキーが変わらないからです。漏えいが疑われるときはキーボリュームのルートキーを交換してください（Docker ガイド）。Docker ホストやキーボリュームに触れられる人はルートキーを読めます。キーボリュームとデータボリュームの両方を含むバックアップには、認証情報を開くのに必要なものがすべて入っています。
- **置き換えられたキーは使わずに拒否します。** macOS では同じユーザーのどのプログラムも、確認なしでキーチェーン項目を上書き・削除できます（使い捨てのキーチェーンで実測）。そのため gateway は、有効化時に記録したキー ID と暗号化した検査値でキーを照合し、プロセスで最初に読み込んだキーを終了まで固定し、封印値のキー ID が違う場合もキーが変わったものとして扱います。いずれの場合も個人アカウントを停止して「保護キーが置き換えられました」と表示します。キーと記録を一緒に置き換えてから gateway を再起動させると前の 2 つの検査は通り、古い封印値が合わないことだけが手がかりになります。「キーを新しくする」（問題がないときも押せます）で新しいキーが作られ、全員が再接続します。
- **封印を解くのは gateway だけ。** キーを受け取れるのは `<home>/locks/gateway.lock` を保持するプロセスだけで、MCP サーバーと CLI サブコマンドは受け取りません。
- **監査：** `security_audit.jsonl` には `credential_protection_enabled`（以前の状態付き、キーの作り直しは Critical）、`credential_protection_enable_failed`、`credential_protection_disabled`、そして gateway がキーの欠落・置き換え・記録の破損を初めて見たときの `credential_protection_broken` が残ります。各行は状態、レベル、バックエンド、キー ID を記録し、キーは記録しません。

防げないもの：シェルを使える社員はキーを置き換えること（上記のとおり検出されます）、gateway を止めて自分で起動し直すこと、リリース版の macOS CLI が hardened runtime を持たない間は `duduclaw` 実行ファイルにコードを注入することがまだできます。本当の分離は、Bash を与えないこと、タスクサンドボックス、または gateway を別の OS ユーザーで動かすことです。

## 同僚の Google アカウントとして動く（v1.76.0）

組み込みメールツールと Gmail の検索／読取結果は、AI 従業員に渡す前にスキャンされます。ログインリンクと近くにあるワンタイムコードは通知文に置き換え、メール ID と日時は保持します。この境界は組み込みメールと Gmail の結果フィールドのみを対象とし、Gmail は OAuth、サービスアカウント、Apps Script ブリッジのすべてに適用されます。サードパーティ MCP、Remote MCP、Bash 経由で読んだ内容は対象外です。検出はルールベースのため、特殊な書き方のコードは見逃す場合があります。

会社の委任では、AI 社員が指定した同僚として Google を使えます。どの関門も失敗時は拒否します：

- **証明された社員だけ。** 身元は `DUDUCLAW_AGENT_ID` + `DUDUCLAW_AGENT_TOKEN` で証明された社員から決まり、ツールの引数は使いません。証明できない社員を名乗るプロセスは既定の身元しか使えず、名乗った社員がそれ以外に設定されていれば何も使えません。
- **発行するのは gateway だけ。** MCP サーバーは `POST /api/internal/google-token`（ループバック、署名付きの身元、nonce、レート制限。ナレッジのルートと同じ認証）にトークンを求めます。gateway は社員の `[google]` を自分で読み、そのターンが誰のためかを自分の登録から調べ、`person_identity_gate()` が通ったとき（資格情報の保護が最低レベル以上。通常の Linux ユーザーサービスと Docker は拒否、ネイティブ保護サービスと Docker person-credentials オーバーレイは通過可能）だけ委任の鍵を開封します。トークンはそのターンの間、MCP サーバーのメモリにだけ残ります。
- **鍵は封印されている。** サービスアカウントの鍵は保護鍵で封印した `pk:v1` の形でだけ保存します。現在の保護鍵で開けない場合は鍵が差し替えられたものとみなし、委任を止め、`google_delegation_key_unreadable`（Critical）を 1 回記録します。管理者が保護をリセットして鍵を取り込み直します。記録が黙って上書きされることはありません。
- **誰の依頼か。** 既定では、この社員に紐づく人、管理者、システムの作業だけが同僚のアカウントを使えます。公開の訪問者はどの設定でも使えません。依頼者の拒否や設定の誤りで共用アカウントに切り替えることはなく、それ以外の失敗でも社員に `fallback = "home"` があるときだけ切り替え、返答でその旨を伝えます。
- **人の状態は毎回読み直す。** 同僚の DuDuClaw アカウントが停止・退職になれば、次の呼び出しから拒否します。
- **設定は管理者だけ。** `[google]` は社員自身の Write/Edit では変更できず（社員ファイルのガード）、権限項目でもあります。管理者でない担当者は狭める方向にしか変えられません。

制限：`gmail.compose` があればトークンを持つ人はメールを送れます。制限のないシェルを持つ社員は自分の同僚向けのトークンで Google を直接呼べ、gateway と同じ OS ユーザーで動きます。HTTP Google MCP マウント（`oauth://google`）は社員の選択アカウントを使い、呼び出しごとに依頼者権限を再確認します。個人アカウントの stdio マウントは拒否します。[接続手順](../../guides/ja-JP/google-setup.md)も参照してください。[AI 社員ごとに別の Google アカウントを使う](../../guides/ja-JP/google-workspace.md#ai-社員ごとに別の-google-アカウントを使う会社の委任v1760)を参照してください。

## これらのガードがカバーしないもの

これを明言すること自体が防御の一部です。

- **フックが見るのは Claude Code 自身のツール呼び出しであり、MCP ツール呼び出しではありません。** MCP には独自のゲート（スコープ、付与、`denied_tools`）があります。フックは組み込みの `Write`／`Edit`／`Read`／`Bash` 面に対する2つ目の鍵です。
- **`agent-file-guard` の Bash 側はヒューリスティックです。** コマンド文字列を読むだけなので、次のものはすり抜けます：変数（`$DUDUCLAW_HOME` と、ホームが既定の場所にある場合の `~/.duduclaw`／`$HOME/.duduclaw` を除く）、コマンド置換、その他の計算で組み立てたパス；エンコードしたコマンド；いったんスクリプトとして書いてから実行するもの；インタプリタに渡す here-document；エイリアスと関数；環境変数を使って後から起動するシェルにファイルを読み込ませるもの；一覧にある読み取り専用コマンドの、想定していなかった書き込みオプション；展開先や保存先を明示しない展開・ダウンロード系コマンド（現在の作業ディレクトリに書き込みますが、この経路は現在のディレクトリを判定しないため、先にホームへ移動してから実行すると止められません）；同じコマンド内でリンクを作ってからそれを通じて書き込むもの；ハードリンク；そしてチェックと実際の実行の間の時間差。
- **Bash 側は無害なコマンドを誤って止めることもあります。** 検査対象の位置にあるパスの解決に失敗すると、ホームの外のパスでも拒否します。宙に浮いたシンボリックリンクも、ホームの外を指していても拒否します。
- **オペレーター専用のメモリコマンドは、減速帯と承認で守られており、サンドボックスではありません。** `memory forget-source` と `memory migrate-namespace` の Bash ルールは、サブコマンドの前のグローバルオプション、コマンド置換で組み立てた実行ファイル名、パイプで渡したコマンドを防げず、AI セッション判定も変数の unset で回避できます。関門はダッシュボード承認です。[出典単位の忘却には管理者の承認が必要](#出典単位の忘却には管理者の承認が必要)を参照してください。
- **`agent-file-guard` は `Read` を対象にしません。** ホールドアウトセットと監査ログは社員から読めたままで、フックが止めるのは書き込みだけです。
- **システムのキーチェーンは社員と gateway を分離しません。** どちらも同じ OS ユーザーで動きます。macOS では保護キーはほかのプログラムからの読み取りには耐えますが、置き換えには耐えません。Windows では同じユーザーのどのプログラムも読めます。Docker の person-credentials モードではルートキーを持つのは gateway プロセスだけですが、gateway は社員と同じ OS ユーザーのままです。社員は許可された範囲で gateway に代行を頼めますし、止めることもできます。[特定の人の認証情報をシステムのキーチェーンに置く](#特定の人の認証情報をシステムのキーチェーンに置くv1760)を参照。
- **これらの hook と Codex の制御ファイルのロックは別の保護です。** Unix の Codex WorkspaceWrite は上記の権限 profile を使います。Grok、その他の CLI runtime、Windows はこのロックの対象外で、その他の CLI runtime は `native_sandbox` を有効にしない限り OS サンドボックスを持ちません。
- **社員自身のディレクトリ内の状態ファイルは保護されません。** 保護されるのは `SOUL.md`、`CONTRACT.toml`、`INSTRUCTIONS.md`、識別ファイル（`.mcp.json`、`.claude/settings.json`）と `agent.toml` だけです。共有の `attachments/` はどの社員も書き込めます。
- **`data-file-guard` はヒューリスティックです。** `Bash` コマンドライン中のファイル名を照合するため、動的に組み立てたパスは通り抜けます。（Windows で無効になる問題は Rust サブコマンド化で解消済みです。）
- **脅威レベルステートマシンは存在しません。** `~/.duduclaw/threat_level` は、computer use オーケストレーターがポーリングする運用者制御のキルスイッチとして残っています（`RED` で停止、`YELLOW` で一時停止）が、ワークスペース内にこれを書くものはもうありません。ファイルが無い場合は `GREEN` 扱いです。ファイルはあるのに読めない場合、または中身が `GREEN`／`YELLOW`／`RED` のどれでもない場合は、50 ミリ秒間隔で 2 回読み直してもそのままなら `RED` として扱います（fail closed）。先頭の UTF-8 BOM と前後の空白は無視します。
- *（2026-09に削除。）* 本節はかつてPTYセッションプールが匿名化リライトの対象外であることを注記していました。そのプールはもう存在せず、Claudeのspawnはすべて呼び出しごとのspawn——まさにリライトがフックする形です。

## まとめ

失効モードを明示した4つのガードは、もう裏にコードのない3層の物語に勝ります。防御を取り除いたらドキュメントも一緒に取り除かねばなりません。存在しないシェルスクリプトを説明するページは、ページが無いより悪いのです——運用者がそこで探すのをやめてしまうからです。

## チャネル確認の保存と照合

高リスク Computer Use の確認は元のアカウントと会話・スレッドへ送信されます。`確認 <完全 UUID>` または `取消 <完全 UUID>` で返信します。質問は `回答 <完全 UUID> <回答>` で回答し、ツール実行を許可しません。単独の yes/A/B は要求を選択しません。実行前に画面、ウィンドウ、ポリシーとキャンセル状態を再確認します。再起動後は古い画面の承認を失効させ、レシートのない実行は `uncertain` として Admin が照合します。[対応経路と制限](../../guides/durable-channel-decisions.md)を参照してください。

## 送信ガードの再起動時の保護（v1.77.0）

ターンの情報源はメモリ内だけですが、送信 lease は `<home>/egress_leases.db`（SQLite WAL、Unix 0600）に保存してから許可します。Gateway は loopback ルート公開前に復元し、再起動のたびに単調時計で新たに六時間、そのスタッフの全ターンの非公開読み取りを保護します。UTC 時刻や時計の変動で短縮しません。古い応答では復元された lease を解放できません。ストアを読めない間は `ask`／`block` で全スタッフの非公開読み取りと新規送信を拒否し、`shadow` は許可して監査します。五秒ごとに再試行し、エラーログは一分に一回までです。追加失敗は強制モードの送信を拒否し、削除失敗は fence を保持します。この永続 lease は MCP のみが対象です。CLI 事前検査は下の 詳細を参照してください。ターンをまたぐコピーは対象外です。[送信ガード](69-egress-guard.md)を参照してください。

Store は存続中に `<home>/egress_leases.lock` の排他ファイルロック（Unix 0600）を保持します。同じ home を使う二つ目の gateway は強制モードで読み取りと新規送信を拒否して再試行し、取得後に全 lease を復元してから読み取りを許可します。`shadow` は許可して監査します。Gateway の実行中はロックファイルを削除しないでください。有効な lease ID の重複は挿入前に拒否し、他のスタッフを停止しません。

## CLI 送信検査

Claude/Grok の Web ツールと Bash のリテラルなネットワークコマンドに gateway 承認 hook を追加し、Codex の強制モードは起動時にネットワークと検索を制限します。バックグラウンド実行も host ターンを登録します。Security ページは Bash、ask/block、タスク sandbox 無効のスタッフを表示します。Bash は減速帯とテレメトリのみで、ネイティブ読み取り、同一 OS ユーザーによる変更、検査後の並行読み取りは隔離しません。ネイティブ検査は実行全体の MCP lease を保持しません。強制モードは Claude bare mode と Grok 共有 cwd を拒否します。汎用 CLI のネイティブツールは対象外です。[送信ガード](69-egress-guard.md)を参照してください。

## 依頼者による元の会話でのメール確認

`mail_send` が宛先またはデータ送信ガードで承認待ちになると、そのターンを開始した確認済みの社内アカウントが一対一の会話または認証済みダッシュボード WebChat でのみ確認カードを決定できます。gateway が依頼者の身元を証明し、決定時にも `users.db` のアカウントとして存在し、その AI スタッフへの Operator 権限を持つ必要があります。グループ会話、外部・未確認の送信者（LINE OA や `odoolivechat:` の訪問者を含む）、別の AI スタッフ、cron、heartbeat は対象外です。ダッシュボードの Admin も引き続き承認できます。

カードには完全な宛先アドレス、件名、本文の要約、このターンで非公開データを読んだかどうかを表示します。カードはボタンのないテキストメッセージです。決定の動詞と完全なリクエスト UUID で返信してください。AI スタッフが「承認済み」と述べても承認にはなりません。最終引数に結び付く一回限りの ActionGrant を再利用し、送信直前にポリシーの版と宛先を再確認します。引数の変更は再承認が必要で、二度目の使用と期限切れは拒否します。記録には決定した依頼者またはダッシュボードの Admin が残ります。

`config.toml [security] mail_requester_approval` は真偽値で、所有者の決定により既定値は `true` です。ファイルやキーがない場合は既定値を使います。設定を読めない、構文や値が不正、または `false` の場合は、ダッシュボードの Admin だけが決定できます。管理者はセキュリティ設定で無効にできます。この例外は `mail_send` のみです。メッセージ、カレンダー、サードパーティ MCP、CLI の外部送信、ワークフローの有効化は従来どおり Admin の送信承認が必要です。 対象はチャネルが証明した一対一の会話または認証済みダッシュボード WebChat のみです。グループ会話と種類不明の会話には引き続きダッシュボード Admin の承認が必要で、公開 WebChat ウィジェットの訪問者は対象外です。対象外のチャネル通知に宛先、件名、本文は含めず、完全な内容はダッシュボードにのみ表示します。

認証済みダッシュボード WebChat は audience の条件を満たしますが、非 Admin 向けの WebChat 確認 UI と決定入口はまだ接続されていません。現在は Admin による承認が必要です。

## 接続解除の削除承認と受領記録

接続解除後の記憶忘却計画は、有効期間 7 日の 1 つのバッチにまとめます。カードは 1 枚で、管理者のみがダッシュボードで承認できます。社員ごとの件数を示し、記憶の内容は含みません。計画が失敗しても、完了した接続解除には影響しません。`[memory] forget_source` が無効、設定が読めない、値が不正のいずれかなら、新しい計画も適用も行いません。

ターンの台帳は既存の汚染元と並べて接続参照を記録し、外送ポリシーは変更しません。チャネルと Remote MCP ブリッジの参照は gateway が生成します。MCP サーバー内のネイティブツールは参照を申告し、gateway が接続の存在と認証された社員への権限を検証します。不明な参照は破棄して数え、接続の印として保存しません。Google の個人認証情報は、実際に選ばれたユーザーの `google:person:<user_id>` を使います。台帳を読めない場合、接続を推測せず `unknown` を記録します。

**残るリスク：** Bash を使える社員は、自分が権限を持つ接続の印を偽造できます。影響はその社員自身の記憶に限られ、削除には社員ごとの件数を示す管理者カードの承認が必要です。接続の印は、同じ OS ユーザーとして動く社員に対する隔離にはなりません。

承認結果の永続化前に、インラインで削除を行うことはありません。承認後はリース付きの永続ジョブをバックグラウンド worker が再試行し、起動時にも復元します。適用前に再計画し、純粋な縮小は適用できますが、拡大には再承認が必要です。記憶エンジンは引き続き即時トランザクション内で DB インスタンス、epoch、期限、hash を確認し、削除した行の再挿入を防ぎます。全処理の成功後にのみ受領記録を作り、セキュリティ監査イベントを記録します。

全体チャネルの削除は、社員専用 bot の `#agent:` 会話を除外します。社員の bot を削除する場合は、その bot だけが対象です。システム由来の記録は保持し、古い印のない記憶や台帳を読めない記憶は帰属不明として数えます。受領記録は社員と保存先ごとの実際の削除件数、保持したシステム記録、帰属の欠落を示します。**対象外**：会話の原文、`tool_calls.jsonl`、wiki、バックアップ。古いバックアップを復元すると、削除済み記憶が戻り、新しい削除済み印が失われる場合があります。管理者は `memory.forget_receipts_list` / `memory.forget_receipts_get` とセキュリティ画面から記録を参照し、JSON を取得できます。

旧式の dedicated Google 実行が選択済みアカウントの記録を返さず、委任先から別アカウントへフォールバックする可能性がある場合は `unknown` とします。接続または権限の削除後に届いた申告も拒否し、不明として数えます。接続の印はターン開始時刻を保持するため、忘却済みターンの遅延取り込みが帰属可能な記憶を復活させることを防ぎます。

接続の出所マークは出所と役割を保持します。単なる再確認は削除の所有権になりません。他の接続中の出所も同じ記憶を提供している場合、その記憶は保持され、計画・管理者の承認カード・受領書に従業員別の `retained_shared` 件数が表示されます。所有する接続がすべて切断済みで、他に有効な直接の出所がない場合のみ削除します。そのため、共有されていた記憶は二つ目の接続の切断時に対象になる場合があります。所有権が不明な記憶（役割を復元できない旧マークを含む）は保持し、帰属不明として数えます。派生した記憶も個別に確認します。計画・適用の前に接続状態を再確認し、プラットフォームで再接続する場合は接続を公開する前に古い切断記録を無効にします。

承認は孤立したエンティティ埋め込みの件数だけでなく、並べ替えた識別子にも結び付けます。同数でも別の識別子への入れ替えには再承認が必要です。未完了ジョブは試行回数と次回実行時刻を保存し、60／120／240／480 秒の待機を入れ、実行時刻を迎えたジョブを公平に処理します。連続五回の失敗または中断で隔離します。管理者は「データ削除受領書」で記憶内容を含まない失敗理由を確認し、「再試行」を選択できます。再試行は既存の承認を保持して範囲を再確認し、範囲が広がった場合は再承認を求めます。

切断記録には固有のリビジョンがあり、作成時は未検証です。接続状態の確認は読み取った同じリビジョンだけを検証し、遅れて届いた切断通知が古い確認結果を再利用することを防ぎます。

## 会話の認証情報監査

[認証情報監査](70-credential-audit.md)は検出結果のメタデータだけを登録します。パスワードと接続文字列には指紋がなく、高エントロピーの種類も保護機構が利用可能な場合だけ鍵付き指紋を計算します。アカウントは先頭文字とドメインだけです。登録はメッセージごとに 5 件、送信者ごとに毎時 50 件、全体で 100,000 件までとし、超過を集約イベントに記録します。両モードで派生ストアの検出値をマスクしますが、既定の `audit` は会話の平文を残し、`mask` は新しいメッセージを配信前にマスクします。文脈のない単独のパスワードは検出できず、実値代入は時期未定の計画です。Admin 専用 RPC と doctor は監査チェーンを検査でき、Read ファイルガードは台帳ディレクトリを拒否します。

## 二要素ログイン

Gateway は [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238) SHA-1 TOTP（160ビットのランダムな秘密鍵、6桁、30秒、前後1周期）とトランザクション内のリプレイ防止に対応します。秘密鍵はチャネルと同じ AES-256-GCM とホストの `.keyfile` で暗号化し、鍵を `users.db` に保存しません。10個の使い捨てリカバリーコードは一度だけ表示し、Argon2ハッシュを保存します。リカバリーコードの検証にTOTPの復号は不要です。有効または登録待ちのMFAデータがある場合、鍵の紛失時に代替鍵を生成しません。元の鍵を復元するかホスト復旧を行います。鍵ローテーションは対象外です。

Dashboard の `mfa.enroll_begin {password}` は現在のパスワードをblocking poolで検証し、ログイン同様に試行を制限します。返す `enrollment_token` はユーザー、JWTの `jti`、今回のパスワード検証と5分間の期限に結び付きます。`mfa.enroll_confirm {enrollment_token,code}` は同じセッションでのみ使えます。盗まれたJWTだけでは開始できません。秘密鍵の置換は新しい要素で無効化した後、パスワードを再検証して登録します。有効な鍵をbeginで上書きできません。

エディションを問わずMFAの強制中は初回登録にも独立した証明が必要です。強制開始より前に検証・記録されたチャネルがあれば専用OTPを既存配信サービスで送り、`proof_code` として提出します。なければ別の現在有効なAdminが `users.mfa_enrollment_code {user_id,challenge_ref}` で一度限りの登録コードを発行し本人に渡します。コードはユーザーと指定の未完了challengeに限定し、ハッシュ保存、5分間有効、一度だけ表示、監査対象です。自己発行は禁止です。最後のAdminはホスト上の `duduclaw ops users mfa-enrollment-code <email> <challenge_ref>` を使います。証明は第一要素challengeに限定され、同時に失効し、最大5回まで試行でき、他のchallengeに再利用できません。チャネルOTPを第一要素にした場合は現在の `password` も必要です。

強制中の未登録ログインは `mfa_enrollment_required`、`enrollment_token`、12文字の `challenge_ref` のみを返します。`/api/mfa/enroll/begin {enrollment_token,proof_code}` の後、`/api/mfa/enroll/confirm {enrollment_token,code}` を呼びます。チャネル第一要素では両方に `password` が必要です。Dashboardでの強制登録は最初のbeginが `proof_required` とtokenを返すので、パスワード、token、`proof_code` を付けて再度beginを呼び、`secret` と `otpauth_uri` を取得します。Confirmだけが有効化します。登録tokenは `/ws`、refresh、通常HTTP認証には使えず、Dashboard登録tokenもHTTP登録ルートで交換できません。

登録済みアカウントのパスワード／チャネルOTPログインは `mfa_required`、`challenge_id` と認証方法の情報を返します。`/api/mfa/verify` にchallengeと `code` または `recovery_code` を送ります。ユーザーと第一要素に限定し、永続化、成功1回、5分間有効、試行5回までです。`mfa.status` は本人の状態、`mfa.recovery_regenerate {code}` は全コードの置換、`mfa.disable {code,password}` は現在のパスワード（登録時と同じパスワード試行制限）も必要な無効化です。後二者は新しいTOTPまたは未使用コードが必要で、強制中は最後の認証方法を削除できません。要素の誤入力はアカウントごとに15分で5回までです。

新規のチームインストールでは `[auth] mfa_enforced=true` が既定です。既存環境は、MFAポリシー記録のない旧版を含め、現在の設定を維持します。Adminはダッシュボードの「ユーザー → 二要素ログイン管理」の専用スイッチで強制を有効・無効にできます（`system.update_config` と `expected_state`）。通常の設定書き込み、設定エディター、インポートでは変更できません。新規チームの最初のAdminがアカウントとパスワードを設定してログインすると、MFA登録が必要になります。ホスト操作員が `duduclaw ops users mfa-enrollment-code <email> <challenge_ref>` で登録コードを発行し、ログイン画面でコードを入力して認証アプリの登録を完了するとセッションを取得できます。最初の登録はダッシュボードだけでは完了できません。既存の強制無効環境では任意登録を続けられます。有効化前に `mfa.overview`、チャネル配信、ホスト復旧を確認してください。強制なし・登録歴なしでは既存応答とepoch 0 JWT内容は変わりません。すべてのエディションで保存済みのポリシーに従います。ライセンス失効、検証失敗によるフォールバック、明示的なPersonal指定では強制を解除せず、Adminによる意図的な解除だけが無効にします。ポリシーストアのない新規Personalは引き続き強制無効です。ローカル自動ログインでも強制中のMFAを回避できません。

強制設定の変更だけでは既存access tokenを直ちに失効させません。未登録者のrefreshを拒否し、元のaccess tokenは自然に期限切れになります（既定30分）。すべてのエディションのMFAソケットは期限後の次の心拍（最大30秒）で閉じ、実行中の作業は取り消しません。強制中は旧共有tokenの `/ws` 認証とRPCを拒否し、既存接続も次の心拍で閉じてpush購読を終了します。登録、無効化、リセットはユーザーのcredential epochを増やし、その後のパスワード変更／リセットも増やします。古いaccess／refresh tokenを拒否し、開いているDashboard接続も次の既存のライブ身分確認で拒否します。追加のフレームごとのDB読取はありません。claimなしはepoch 0、登録歴のないアカウントはパスワード変更でも0を維持します。どのパスワード変更も登録待ちchallengeを無効にします。

設定は起動時の検証済みメモリスナップショットを使い、Dashboard設定保存後と外部変更確認（30秒ごと）で更新します。読取／解析失敗は前の有効値を保持し、`mfa.overview.policy` と `system.status.mfa_policy` に degraded と警告を表示します。有効値を一度も取得していない場合は全エディションで拒否します。起動時に既存のポリシーストアを読み取れない場合や破損している場合も拒否します。`[auth]` または設定キーがない場合は永続ポリシーを維持し、新規チームの初期化ではtrueを明示します。ログイン時のファイル読取／解析はありません。

`users.mfa_reset {user_id,code}` は自己リセットを拒否し、同じトランザクションで現在有効なAdmin権限と操作者自身の新しいTOTP／リカバリーコードを確認し、対象の要素とchallengeを削除、epochを増やし監査します。全エディションでホストの人間は `duduclaw ops users mfa-reset <email>` で任意のアカウントを復旧できます。鍵紛失時の複数Adminも対象です。両ホストコマンドはAIセッションと従業員／未検証Bashを拒否し、操作者は未検証として監査します。任意のホストファイル書込に対するOS隔離ではありません。登録、証明／登録コード発行、無効化、コード使用、検証失敗を秘密値なしで監査します。

強制開始前に `mfa.overview` の各アカウントの `channel_bindings.verified_at` と `enforced_at`（Unixマイクロ秒）を確認します。不明な過去の時刻はnullで、登録証明には使えません。再バインドも新しい時刻を記録します。強制中の未登録アカウントの自己バインドは禁止し、別の有効なAdminまたはホスト担当者の承認が必要です。パスワード保有者が強制開始前に仕込んだバインドは検出できません。短い `challenge_ref` をAdminに読み伝え、登録bearer tokenは渡しません。コードは一致するユーザーとchallengeでのみ使用・削除します。

JWT epochは完全一致が必要です。Dashboardは毎心拍、WebChatは心拍と各メッセージ前に確認します。共通の身分読取器と2秒のsocketキャッシュを使い、心拍はgenerationを再確認、期限はメッセージごとに確認します。画面表示・操作引継ぎticketは元JWTのepochと期限を保持し、入場と30秒ごとの再確認で失効を拒否し、JWT期限を延ばしません。設定保存はロック内でも現在のAdmin権限を確認します。最後の有効値がfalseなら読取失敗でもfalseを保ち警告します。通常の `system.status` フィールドは変わりません。

### メール確認コード、パスキーとログイン状態の保持（v1.80.0 から）

「設定 → アカウント」で既存の認証アプリを残し、メール確認コードや名前付きのパスキーを複数追加できます。追加・削除には現在のパスワードが必要です。メール設定ではアカウントのメールアドレスに 6 桁のコードを送り、確認成功後に有効にします。管理者は既存の `[channels.email]` SMTP 送信設定（`smtp_host`、`from_addr` と必要な認証情報）を構成してください。送信設定が利用できない場合、メール認証は利用不可と表示します。認証方法の変更を監査し、メール設定済みなら本人にも通知します。

パスワード入力後に登録済みの認証方法を選択できます。前回成功した方法を既定で選びます。メールコードは一度だけ使用でき、10 分で失効し、一つのログインチャレンジにつき最大 5 回試行できます。再送は 1 分に 1 回、アカウントごとに 1 時間で最大 5 回です。パスキーは端末の画面ロック、生体認証またはセキュリティキーを使用します。管理者は `[dashboard] public_url` に公開 URL を設定し、その完全一致する HTTPS オリジンで開いてください。HTTP は localhost のみ利用できます。各キーに名前を付けて個別に削除できます。端末を失った場合に備えて別の方法も残してください。パスキーだけを初めて登録した場合はリカバリーコードを発行しません。既存の認証アプリのリカバリーコードは維持します。初回メール登録ではリカバリーコードを一度だけ表示し、保存確認後に続行します。

認証の必須化は登録済みのいずれの方法でも満たせますが、最後の方法の削除は拒否します。既存の認証アプリとリカバリーコードは再登録不要です。必須の初回メール登録は受信コードでメールボックスへのアクセスを証明します。認証アプリとパスキーは独立したチャンネル／管理者コードを引き続き要求します。チャンネルコードで最初のログインを行った場合は現在のパスワードも必要です。管理者のリセットはすべての認証方法と保持されたログインを取り消します。操作者は現在のパスワードまたは新しい認証アプリ／リカバリーコードで確認でき、パスキーのみを使う管理者も実行できます。

ログイン画面の「ログイン状態を保持」は既定で未選択です。選択するとローテーションする Cookie で既定180日間保持し、更新が成功するたびに、その利用時点から設定日数分だけ有効期限を更新します。管理者は「セキュリティ → ログイン状態の保持」で1～365の整数を保存できます（既定180日）。設定は `users.db` に永続保存され、読取失敗や不正な値では180日に戻り、無期限にはなりません。変更時点では既存の有効期限を維持し、次回の更新成功時に、その利用時点と新しい日数から計算し直します。日数を短縮した場合も同じです。開発版の `[auth] remember_days` 設定は読み取られません。未選択では従来のセッション動作を維持します。アカウント設定の「ログイン中の端末」は保持中の端末、作成日、最終利用日、記録済み IP を表示し、個別の取消と「すべての端末からログアウト」に対応します。パスワード、認証方法、アカウント状態・役割の変更、認証のリセット、アカウント削除で保持されたセッションを取り消します。ログアウトは現在の端末を取り消します。

管理者は「メンバー」のアカウント詳細で「このユーザーのすべての端末からログアウト」を選び、確認すると通常ログインと保持ログインをすべて取り消せます。アカウントの無効化・削除でも取り消されます。既存のアクセストークンは拒否され、接続中の WebSocket は既存の取消確認（次のハートビートを含む）で停止し、180日の期限を待ちません。管理者専用の `sessions.policy`、`sessions.policy_update`、`users.revoke_sessions` は現在の権限を再確認し、変更では操作者・対象・結果を認証監査ログに記録します。認証情報は記録しません。

Cookie 認証のセッション要求には `X-DuDuClaw-CSRF: 1` と、スキーム・ホスト・実効ポートを含む完全一致の Origin が必要です。組み込みの HTTP loopback Origin はゲートウェイの待受ポートのみを許可します。リバースプロキシでは `[gateway] allowed_origins`（または `DUDUCLAW_ALLOWED_ORIGINS`）に完全な `https://host[:port]` Origin を指定してください。これらのエンドポイントではホスト名だけの設定は不十分です。更新とログアウトは、別ポートのページと通常の HTML フォームを状態変更前に拒否します。

更新には認証済みの family 世代番号を使い、family ごとに現在のトークンハッシュを一件だけ保存します。正当な旧世代の再使用は端末を取り消し、偽造した世代番号では取り消せません。所有者のみ読み書き可能な署名鍵 `users.remember-key` は `users.db` と一緒にバックアップ・復元してください。世代セッションがある状態で鍵を失った場合や鍵が破損した場合、認証データベースは開けません。世代機能より前の開発版セッションは移行時に取り消されます。アカウントごとに有効端末は最大20台、取消済みを含む family 記録は最大100件です。記録上限では通常ログインを使い、古い記録の期限切れを待ってください。最後に更新した有効期限の七日後以降、次の保持ログイン成功時に記録を削除します。アカウント認証のダッシュボードと WebChat 接続は最長24時間で再接続・再認証が必要です。既存の短い MFA 期限も適用され、古い接続が取消記録の保持期間を超えて残ることを防ぎます。


長期認証情報は localStorage に保存せず、JavaScript からも読み取れません。Cookie は HttpOnly、SameSite=Strict、`/api/session` に限定し、HTTPS では Secure を設定します。サーバーはハッシュだけを保存し、使用ごとに更新します。古い認証情報の再使用は同じファミリーをすべて無効にします。Cookie を使うエンドポイントとダッシュボードの WebSocket アップグレードは Origin を検証します。

実際の SMTP 配信、各プラットフォームでのブラウザーのパスキー登録・ログイン、Rust の各 OS ビルド、依存関係の監査、完全な gateway 統合テストは未検証です。UI 実装とテストコードの作成だけでは受け入れ完了にはなりません。

### ダッシュボードの二要素ログイン

Enterprise と強制中の Personal では「設定 → アカウント」で「二要素ログインを設定」を選び、現在のパスワードを入力し、認証アプリで QR コードをスキャン（またはシークレットを手動入力）して、6 桁のコードで確認します。10 個のリカバリーコードをコピーまたはダウンロードし、「リカバリーコードを保存しました」にチェックして続行します。シークレットとコードはコンポーネントのメモリだけに保持し、画面を離れると破棄します。コピーとダウンロードは明示的な操作です。登録と無効化では現在のセッションのトークンを更新して接続を維持し、ほかのセッションは無効になります。保存を確認するか画面を離れるまで、リカバリーコードを表示します。トークン発行と MFA の変更は同じトランザクションで確定し、発行に失敗した場合は登録や無効化を適用せず、再試行できます。再発行と無効化には新しい認証コードまたは未使用のリカバリーコードが必要で、必須化中は無効にできません。

パスワードとチャンネルコードのログインは、gateway が二要素認証を要求するまで従来のフォームを維持します。認証アプリのコードまたは一度限りのリカバリーコードを使えます。ログイン要求は 5 分間有効で最大 5 回試行できます。必須登録には独立したチャンネル／管理者コードと現在のパスワード（チャンネルログイン時に必須）が必要です。管理者には表示された登録識別番号だけを伝え、登録トークンを渡さないでください。

Admin は「ユーザー → 二要素ログイン管理」で登録状況とチャンネル認証日時を確認し、自分の新しい認証要素で他のアカウントをリセットしたり、相手の登録識別番号に対するワンタイムコードを発行できます。自分へのリセットと発行はできません。必須化のスイッチは未登録数とログイン制限の警告を示し、表示された確認文の入力を要求します。設定の再読み込みが縮退状態の場合は警告してスイッチを無効にします。新規チームでは最初から強制が有効です。既存の無効環境では、登録、チャネル配信、ホスト復旧を確認してからAdminが有効にしてください。Personal でも登録が必須、または登録済みならアカウントのMFA設定を表示します。強制無効かつ未登録なら引き続き非表示です。強制中のPersonalでは、Adminが「システム → セキュリティ → 二要素ログイン管理」から同じ管理画面と専用スイッチを使い、意図的に強制を解除できます。全エディションでホスト操作員の `duduclaw ops users mfa-reset <email>` による復旧を利用でき、アカウントのリセットは強制ポリシーを解除しません。
Enterprise では「設定 → アカウント」で「二要素ログインを設定」を選び、現在のパスワードを入力し、認証アプリで QR コードをスキャン（またはシークレットを手動入力）して、6 桁のコードで確認します。10 個のリカバリーコードをコピーまたはダウンロードし、「リカバリーコードを保存しました」にチェックして続行します。シークレットとコードはコンポーネントのメモリだけに保持し、画面を離れると破棄します。コピーとダウンロードは明示的な操作です。登録と無効化では現在のセッションのトークンを更新して接続を維持し、ほかのセッションは無効になります。保存を確認するか画面を離れるまで、リカバリーコードを表示します。トークン発行と MFA の変更は同じトランザクションで確定し、発行に失敗した場合は登録や無効化を適用せず、再試行できます。再発行と無効化には新しい認証コードまたは未使用のリカバリーコードが必要で、必須化中は最後の認証方法を削除できません。

パスワードとチャンネルコードのログインは、gateway が二要素認証を要求するまで従来のフォームを維持します。認証アプリのコードまたは一度限りのリカバリーコードを使えます。ログイン要求は 5 分間有効で最大 5 回試行できます。必須登録には独立したチャンネル／管理者コードと現在のパスワード（チャンネルログイン時に必須）が必要です。管理者には表示された登録識別番号だけを伝え、登録トークンを渡さないでください。

Admin は「ユーザー → 二要素ログイン管理」で登録状況とチャンネル認証日時を確認し、自分の新しい認証要素で他のアカウントをリセットしたり、相手の登録識別番号に対するワンタイムコードを発行できます。自分へのリセットと発行はできません。必須化のスイッチは未登録数とログイン制限の警告を示し、表示された確認文の入力を要求します。設定の再読み込みが縮退状態の場合は警告してスイッチを無効にします。新規チームでは最初から強制が有効です。既存の無効環境では、登録、チャネル配信、ホスト復旧を確認してからAdminが有効にしてください。Personal でも任意登録が可能で、ローカル自動ログインは変わりません。

呼び出した接続は登録／無効化の成功応答とともに新しいトークンを受け取り、通常の送信チェックの前に認証情報を引き継ぎます。HTTP 登録もトランザクションの確定前にトークンを発行します。リリースの受け入れ確認では実際のブラウザー／WebSocket で、ハートビート後もコードが表示され、別のセッションが無効になることを確認する必要があります。プロセス内のハンドラーとフロントエンドの単体テストは、この受け入れ確認の代わりにはなりません。

## 外部 MCP の環境変数資格情報

外部 MCP のキーは社員の設定ファイルから移されます。`.mcp.json` には `secret://mcp/<server>/<ENV_NAME>` 参照だけを残し、値は既存の `.keyfile` で暗号化して `<home>/secrets/mcp/<agent_id>.enc` に保存します。外部サーバーのすべての `env` が対象で、例外は `PATH`、`HOME`、`NODE_ENV`、`LOG_LEVEL` と既存の `secret://` 参照だけです。DuDuClaw 自身のサーバー項目と、その `DUDUCLAW_*` 変数は変更しません。

組み込みとして扱うのは、名前が `duduclaw`、`duduclaw-pro` または現在のインスタンスのキーと完全一致し、command と args がホストの生成値と一致する項目だけです。`duduclaw-evil` は外部サーバーです。起動時に生の設定内の proxy 項目と proxy 専用環境変数を拒否し、社員の ID を持つ組み込み項目はホストが生成する定義全体との一致を要求します。秘密の読み出しには保管先の社員に対する有効な `DUDUCLAW_AGENT_TOKEN` HMAC が必要で、緩い delegation 設定や既定の社員へのフォールバックでは許可しません。

移行は鍵、暗号化バックアップ、保管庫、設定の順に、各段階で親ディレクトリの fsync 完了を待ちます。失敗した社員の移行は中止し、設定を置換した後の失敗では元の内容を復元します。復元も失敗した場合はエラーを報告し、永続化済みの暗号化バックアップを残します。

Proxy は自分の社員に属する参照だけを、上流サーバーの起動直前に解決します。参照が存在しない、不正、または復号できない場合、そのサーバーは起動しません。エラーにはサーバー名と変数名だけを含め、値は含めません。秘密の解決が必要な設定を proxy 用に書き換えられない場合、Claude／Grok は元のファイルを直接読み込む経路へ戻りません。エクスポートでは変数名と空のプレースホルダーだけを残し、インポートする人が値を再入力します。

Gateway の起動時に既存の平文 env を移行します。まず元のファイルを `<home>/backups/mcp-migrate/<agent>-<timestamp>.enc` に暗号化して保存し、資格情報ストアへの書き込みと読み戻し検証を終えてから、設定をアトミックに置き換えます。ある社員の移行が失敗した場合は処理を中止し、ほかの社員を処理します。設定の復元も失敗した場合の回復方法は上記のとおりです。クリーンアップ後の移行バックアップは社員ごとに最大三つです。I/O エラーで削除できなかった場合は記録し、次回の走査で再試行します。サーバーや社員の削除時にはストアの該当項目を削除します。削除した社員を復元した場合はキーの再入力が必要です。

Read ガードは `<home>/secrets` への読み取りを拒否します。これは Bash に対する隔離ではありません。同じ OS ユーザーで動く社員が Bash を持つ場合、`.keyfile` を含む gateway のファイルを読めます。実際の隔離には Bash を与えないか、タスクサンドボックスを使う必要があります。対象は `env` のみで、`args`／`url` 内のキーや、キーを返すツール結果は対象外です。既存の平文エクスポートやバックアップを遡って消すことはありません。
## Web サイトのログイン情報

管理者は **システム → セキュリティ** で `website_credentials.list`、`.upsert`、`.delete` を通じてログイン情報を管理します。Upsert はオリジンの代わりに正規化される HTTPS `login_url` と、任意の `allowed_paths`（同じオリジンの二段階目用の正確なパス、既定値は空）を受け取り、オリジンとログインパスを URL から導出します。一覧にはパスワードを含めません。レコードは `CryptoEngine` と gateway の `.keyfile` で暗号化し、`<home>/secrets/website_credentials.enc` に保存します。書き込みはファイルロックとアトミックな置換を使い、権限は 0600 です。一覧、ログイン検索、すべての変更は既存の全レコードの復号と検証を必要とし、失敗すると利用不可のエラーを返してファイルを変更しません。旧形式のオリジンのみのレコードも対象です。管理操作の監査に認証情報の値を含めず、外側の ACL 拒否はパラメータなしで記録し、削除結果は `deleted`、`noop`、`refused` に分けます。利用ごとに認証情報 ID、スタッフ、オリジン、結果を記録します。

`computer_login` はラベルのみを受け取ります。Gateway は検証済みのスタッフを空でない `allowed_agents` リストと照合し、独立したツール名でツールとセッションのゲートを適用します。既存のナビゲーション検査で保存済みのログイン URL を最初に開きます。秘密は stdin でコンテナのヘルパーへ送り、コマンドライン引数やモデルへの結果には含めません。入力前に正確なオリジンとログインパスの一致が必要です。`allowed_paths` はヘルパーの最初の送信後に到達し、パスワード欄が表示された二段階目にのみ使えます。入力前、同期 input/change イベント後、submit ハンドラー後に有効な送信方法が POST であることを確認します。ネイティブの `requestSubmit` と代替経路の両方で、選択した送信ボタンの `formmethod` を検査します。ネットワーク側でもデコードしたクエリ値が完全なユーザー名またはパスワードと一致する非 POST リクエストを拒否します。CDP Fetch は別オリジンへのリクエストとリダイレクトをすべて中止し、処理中はサービスワーカーも迂回します。インターセプトを解除する前に、ヘルパーは `Network.requestWillBeSent`、`Network.loadingFinished`、`Network.loadingFailed` を追跡し、リクエストの終了を確認します。最大 3 秒待機し、保留リクエストも新しい活動もないコマンド往復が 2 回連続することを要求します。完了を確認できない場合は `failed_uncleared` とし、Fetch の制限を維持したまま `Browser.close` を呼び出して、その後 Gateway がセッションとコンテナを削除します。スクリーンショットを抑止し、消去を確認できない場合はセッションとコンテナを停止・削除して、新しいセッションを要求します。

同一オリジンの JavaScript による入力済みフィールドの読み取りは防げません。また、gateway と同じ OS ユーザー権限を持つプロセスからのファイル隔離を提供するものでも、ネットワーク許可リストの代わりでもありません。対象は保存した HTTPS オリジンと許可されたログインパスのみで、localhost も HTTPS が必要です。二要素認証や CAPTCHA は既存の引き継ぎ機能で人が処理します。`duduclaw-fill-login` の追加には Computer Use イメージの再ビルドが必要です。結果の意味と設定は[ブラウザ自動化](08-browser-automation.md)を参照してください。

## 一般的な自己更新のファイル置換

既存の署名・実行チェック後、Unix の自己更新はハードリンクまたは同期済みコピーで旧版を保存し、同じディレクトリの新ファイルを同期して、一度のリネームでインストール先を置き換え、ディレクトリも同期します。復元も一度のリネームで行い、独立した復旧用コピーを復元後のディレクトリ同期が成功するまで保持します。Windows はバックアップ付きのネイティブ API を使用します。実行中ファイルを退避してから新版を移動するフォールバックは、返されたエラーから復元しますが、二つの移動の間にクラッシュの窓が残ります。削除できない実行中の旧ファイルは固定名で保持し、プロセス終了後の次回更新で削除します。まだロック中なら更新を拒否します。復元失敗時は保持した復旧用ファイルの場所を報告します。これは中断への保護であり、インストール先に書き込めるプロセスからの隔離ではありません。保護された Linux サービスとデスクトップ版は別の処理です。[デプロイガイド](../../guides/ja-JP/deployment-guide.md#8-自動アップデート)を参照してください。
## 会話履歴の添付ファイル保護

履歴の添付エンドポイントは、現在のアカウント、社員、会話、成果物の閲覧権限を再確認します。添付参照だけでは任意のパスを読めません。Unix ではディレクトリ記述子を使い、各階層でシンボリックリンクをたどらずに開き、パスの逸脱や複数のハードリンクを拒否します。アップロードはランダムな UUID 名で排他的に新規作成します（`create_new`、Unix では `O_NOFOLLOW` も使用）。別のユーザーが同名ファイルを同時に送っても内容を上書きしません。

権限確認は、すでに開いたファイルから取得した上限付きスナップショットに結び付きます。その SHA-256 ハッシュが永続的な成果物出所記録と必要なワークフロー受領記録に一致してから、同じ内容を返します。開いた後にパスを置き換えても応答内容は変わりません。内容ハッシュを持たない旧出所記録は制限付き読み取りを拒否し、Admin／完全履歴モードの従来の旧ファイル規則は維持します。同じ OS アカウントで gateway のファイルと台帳を書き換えられるプロセスを隔離する機能ではありません。Windows など非 Unix システムはこのエンドポイントを拒否します。

高負荷の処理に入る前と、実際の読み取り中の両方に制限を設けます。

| 操作 | 上限 |
|---|---|
| 履歴データベース | SQL `LIMIT` で最新行を直接選択。メッセージ本文は 1 件 1 MiB、応答合計 2 MiB |
| 添付投影 | リクエストごとに永続権限索引を開き、アーカイブ名と元パスで検索。参照の検査 256 件、返す添付 32 件 |
| 履歴リクエスト | ユーザーごとに同時 2 件、毎分 30 回。全体で同時 4 件。同期処理は semaphore で制限 |
| ダウンロード | ユーザーごとに同時 2 件、全体で同時 4 件。ユーザーごとに毎分 120 MiB、リクエストのサイズ上限で予約 |
| ファイル読み取り | 開いたファイルの metadata を確認し、`take(max + 1)` でスナップショットを制限。ダウンロード 20 MiB、プレビュー 2 MiB |
| 添付 ID | 独立したキャッシュでユーザーごとに 512 件を LRU 保持。全体の容量不足では発行を拒否し、使えない ID を返さない |

応答に `Content-Length` を付け、identity エンコーディングと `nosniff`、sandbox CSP、private/no-store を使用します。ブラウザーは長さの欠落、不正値、超過を拒否し、ストリームも上限付きで読み、実際の長さが違う場合は拒否します。2 MiB を超える画像プレビューは自動取得しません。内容を実行できる形式はダウンロードのみです。期限切れや削除済みの ID は、容量が空いた後に履歴を再読み込みして取得できます。

本修正のネイティブ環境の挙動と実際のブラウザーでのダウンロード受け入れ確認は未実施で、フロントエンドの単体テストだけでは確認済みと扱いません。[オフィスドキュメントスイート](31-office-document-suite.md)も参照してください。

WebChat は書き込みや処理の開始前にアップロード全体を検証します。1 回につき添付は最大 8 件、デコード後の合計は 20 MiB、ファイル名は 255 bytes、MIME ラベルは 128 bytes までです。WebSocket メッセージとフレームは 28 MiB に制限し、添付パーサーは巨大な配列を作る前に件数超過を拒否します。Base64 が不正な場合や上限超過では全件を拒否します。ユーザーごとに毎分 8 回、32 ファイル、80 MiB までです。永続的な予約により、新規アップロードをユーザーごとに 512 MiB／2,048 ファイル、全体で 4 GiB／16,384 ファイルに制限します。空ファイルも件数に含み、失敗や中断した予約も計上します。手動で削除しても割り当ては自動回復しません。

ダウンロード応答の総期限は 30 秒です。クライアントが本文を一度も読まなくても、独立したタイマーがスナップショットと同時実行枠を解放します。転送層には最大 64 KiB の独立したコピーを渡すため、一つのチャンクを保持してもスナップショット全体は残りません。期限切れの応答は失敗し、再試行には改めて権限確認と通常のリクエスト枠が必要です。

履歴添付の権限確認には、アーカイブ名、所有者、内容ハッシュ、サイズ、元パスを保存する索引付きの永続 SQLite 記録を使います。表示・監査用 JSONL のローテーションや切り詰めで既存の権限記録が失われることはありません。データベース障害時は制限付きアクセスを拒否し、WebChat アップロードは権限記録の保存後に成功を返します。信頼できる内容の結び付きがない旧ファイルは、引き続き制限付き閲覧者には提供しません。

初回利用時は、保持されている直前と現在の監査ファイルを一つのトランザクションで移行します。合計上限は 32 MiB、1 行は 64 KiB です。読み取り不可、不正形式、上限超過では部分的な権限を作らず移行を中止します。保持された記録を修復してから再試行してください。以前のローテーションですでに失われた記録は自動復元できません。移行後の監査ファイル変更は権限データベースを上書きしません。

Unix の添付書き込みは各ディレクトリ要素のシンボリックリンクを拒否し、固定したディレクトリハンドルを基準にファイルを作成します。権限・クォータ DB の親は gateway ユーザー所有の実ディレクトリで、グループや他ユーザーが書き込めないことが必要です。DB 本体と既存の journal／WAL／SHM は同ユーザー所有、ハードリンク数 1 の通常ファイルに限定します。SQLite は `SQLITE_OPEN_NOFOLLOW` で開き、新しい DB は `0600` で作成します。DB から `/` までの祖先は実効ユーザーまたは root の所有で、グループ・他ユーザーによる書き込みは禁止します。書き込み可能な root 所有の sticky ディレクトリは、直下の要素が実効ユーザー所有の場合のみ許可します。home は一度だけ正規化し、macOS のシステムルート別名（`/var`、`/tmp`、`/etc`）以外のシンボリックリンクを拒否します。添付パスは引き続き実パスが必要です。新規 home は `0700` で作成し、既存の権限は変更しません。CLI とダッシュボードの健診は書き込み可能な home を警告し、操作者向けの `chmod 700` コマンドを表示します。対応できないプラットフォームでは添付へのアクセスとアップロードを拒否します。生成する添付ラベルの Markdown 区切り文字と改行を無害化し、壊れた旧参照はホストパスを表示しないよう保守的に隠します。
### メンバー追加と初回案内（v1.80.0）

`users.create_members` と `invitation.get/update/preview` は明示的な Admin 権限で、現在の有効なアカウントを確認します。メンバー追加と招待文の書き込みでは、取引内で認証情報の世代も再確認します。各人のアカウント、紐付け、主担当、任意の招待、進捗、監査記録は一括で保存します。SMTP は保存後に実行し、送信失敗でもアカウントは残ります。コピーと再送は管理者のみです。招待文はすべてエスケープし、太字と改行のみを解釈します。講座 URL は HTTPS のみで埋め込みの認証情報を拒否します。プレビューはトークンを発行しません。`onboarding.get/update` はログイン中の本人と認証情報の世代を使用し、更新時の他人 ID 指定を拒否します。接続はサーバーの記録から確認し、案内の完了で権限は増えません。[ガイド](../../guides/ja-JP/user-management-and-first-login.md)を参照してください。

招待・オンボーディング・メンバー作成 RPC 名前空間の未知のメソッドは、コアへの振り分け前に Admin を要求し、extension には渡しません。メイン設定の読み書きには直接の Owner／Operator 権限が必要です。ダッシュボードの会話候補と再開先は Viewer のみの権限を拒否します。招待・コースの URL は localhost も含め HTTPS 必須で、認証情報は埋め込めません。メールヘッダーの制御文字は除去されます。
## AG-UI 外部フロントエンド

[AG-UI HTTP/SSE エンドポイント](74-ag-ui.md)はダッシュボードの access JWT のみを受け付け、現在のアカウント／二要素認証状態と WebChat のスタッフ権限を確認します。Admin 以外は割り当てまたは有効なチーム権限が必要で、メイン／デフォルトスタッフにはアクセスできません。サーバーの会話キーは呼び出し元、スタッフ、thread を分離し、WebChat 所有者名前空間内の独立した AG-UI 区画を使います。`/ws/chat` からの再開は拒否します。既存の保護された応答処理へ入るのは最後の user テキストだけです。client history、tools、context、state、forwarded properties は権限を追加せず、フロントエンド定義のツールも実行しません。

承認の中断は broker が永続保存する会話／ターンの発生元で関連付けます。有効な Admin だけが、通常の、特定の実行主体に束縛されていない `mcp_call` または `mcp_install` を決定でき、有効期限、所有者、ダッシュボード専用制限、`forbid_self_approval` を検査します。その他の種類は通知のみで、ダッシュボード専用の要求はここでは決定できません。表示用 metadata は認証情報ではありません。本文サイズ、同時実行、保持時間、イベントバッファに上限があります。切断時は進行中の配信をキャンセルし、そのターンの未決定承認を撤回します。正常に interrupt を送信した場合も期限内だけ保持します。承認レコードは再起動後も残りますが、メモリ内の runtime 継続状態は復元しません。SQLite の受付記録は 24 時間の run ID 再使用を防ぎ、最大 4,096 件を保持します。再起動後、未完了 thread は元の 15 分の期限まで拒否し、その後の新しい run は旧ターンの未決定承認を先に撤回します。同じプロセス内の resume 受領確認はツールを再実行せず、実行成功も証明しません。

一つの resume の決定は原子的に確定し、競合時はそのリクエスト全体をロールバックします。元の画面で承認・拒否されたカードは、現在もスタッフへのアクセス権を持つ利用者（Admin 以外も含む）が新しい接続で同じ結果を確認して再開できます。元の要求とターン発生元を再確認し、外部の決定者を保持します。不明な孤立 resume は受付記録を作成しません。アカウントごとにスタッフと thread を横断して最大 256 行の run／thread 記録、直近 60 秒で最大 32 回の受付に制限します。受領確認も集計し、再起動後も保持して、超過は HTTP 429 を返します。不明な JSON フィールドは名前や値を記録せず、件数のみ debug レベルで各 gateway プロセスにつき 1 分に最大 1 回記録します。

## 企業版コンプライアンス報告の出力

企業版の管理者は **監査ログ → コンプライアンス報告** で CSV、XLSX、印刷用 HTML を生成できます。ゲートウェイは現在の管理者権限と解決済みの版を確認し、既定で個人情報をマスクします。元の値を含めるには明示的な選択が必要です。出力は返す前に監査へ記録し、失敗時は拒否します。対象は記録済みの外部送信判断、承認、行動レビュー、データソースアクセスのみです。判断は送信成功の証明ではなく、不明な項目は空欄、0件もアクセスがなかった証明にはなりません。ダウンロードしたコピーは組織の保存方針に従って管理してください。期間、上限、マスクの範囲は [企業版コンプライアンス報告](75-compliance-reports.md) を参照してください。

報告の読み取りと監査の書き込みは、ローテーションと追記を含むプロセス間ロックを共有し、出力中の世代切り替えによる読み落としを防ぎます。保持されたツール監査の両世代は、報告に使うサイズ制限付きの同じスナップショットでハッシュチェーンを検証します。チェーン破損、不正なレコード、読み取りやロックの失敗時は出力を拒否します。有効な旧形式の接頭レコードは読み取れますが、個別の真正性は検証できません。ハッシュチェーンは末尾の完全性や外部の信頼できる基準に対する真正性を証明しません。
## 個人 Drive 録画の取り込み

Enterprise の会議ページは、ログイン済みダッシュボードの本人が自分の Google 接続でファイルを選び、確認した取り込みだけを受け付けます。社員の MCP トークンや公開アップロードリンクでは呼び出せず、Drive 閲覧・取り込み用 MCP ツールも追加しません。受け取る社員には既存のアップロードの最新認可、ツール、承認、外部送信、プライバシー検査を適用します。追加承認が必要な方針ではダッシュボード取り込みを拒否します。

Drive／Meet は段階的認可を使い、本人が録画アクセスを有効にしたときだけ `https://www.googleapis.com/auth/drive.file` と `https://www.googleapis.com/auth/meetings.space.readonly` を要求します。通常の初回接続は Drive／Meet 権限を要求しません。既存の広い権限は取消まで残ります。別の **従業員の Drive ツールを有効にする** 同意で、既存ツールと Google リモート MCP 用の `https://www.googleapis.com/auth/drive.readonly` を追加できます。従業員の利用同意とロール検査は維持され、録画取り込みにはこの広い権限は不要です。未共有のファイルは Google Picker で選びます。`drive.file` 自体は選択したファイルへの書き込みも許可しますが、取り込みは GET だけを実行します。ブラウザーは過去の範囲を含めず `drive.file` のみの短期 Picker トークンを別途取得し、永続化しません。Gateway の資格情報は保護された個人ストアに保持します。

Gateway はファイル ID を検証し、古い広い認可があっても Drive の `isAppAuthorized=true` を要求します。この Google フラグは以前の認可を示す場合があり、今回の Picker のクリックを証明しません。取り込みには、下記の利用者・社員・ファイルに結び付いた確認レシートも必要です。固定の公式 Google API エンドポイントを使い、リダイレクトを拒否します。メタデータ応答を制限し、既存の分割アップロード経路で保存して、同じサイズ・一時保存容量・録音時間の上限を適用します。転送中とジョブ登録前に接続の本人、実際の権限、ローカル認可を再確認し、接続解除や取消の検出で以後のアクセスを停止します。ローカルの出所記録はアップロードを選択した利用者、Google アカウント、Drive ファイル ID、バージョンに関連付けます。監査には識別子のハッシュを使い、トークン・内容・機密性のある名前を含めません。

Gateway は基本サービス、会議録画、従業員の Drive ツールへのローカル同意を別々に保存し、暗号化した資格情報と認可記録に結び付けます。各機能には Google の実際の範囲と対応するローカル用途への同意の両方が必要です。会議の認可で `drive.readonly` や `drive` が追加で返されても、従業員の Drive ツールは有効になりません。追加認可は以前の用途同意を維持し、以前の Google 範囲をすべて保持する必要があります。保存時には元の資格情報のバージョンも照合し、範囲の欠落や同時更新があれば既存の資格情報を置き換えません。ローカル用途同意のない旧記録は再接続が必要です。基本サービスの再接続では用途を基本サービスに戻すため、会議録画と従業員の Drive ツールは改めて個別に有効にしてください。

取り込みにはサーバー発行の確認レシートが毎回必要です。これは JWT で認証されたダッシュボード利用者が、過去 5 分以内にこの正確な Drive ファイル ID を、この受け取り先の社員に渡すことを明示的に登録・確認したと証明します。社員／MCP トークンでは登録できません。レシートは一回限りで、利用者、社員、ファイル ID に結び付き、同じ利用者と社員への新しい確認は以前のレシートを置き換えます。ダッシュボードは利用者が取り込みを確認した時点でファイルを登録します。欠落、期限切れ、再使用、結び付きの不一致は拒否します。取り込み処理に入ると後続の検査が失敗してもレシートを消費するため、再試行には新しい確認が必要です。サーバーはさらに、その利用者の Google 接続で Drive メタデータの `isAppAuthorized=true` を検査します。レシートもこの Google フラグも Google Picker 内のクリックを証明しません。ダッシュボード呼び出し元は、既知の ID を使って以前にアプリへ認可したファイルを明示的に確認できます。

ダッシュボード専用の `POST /api/meeting-drive/selection` は `agent_id`、`file_id`、`confirm: true` を必須とし、`selection_receipt` と `expires_in` を返します。登録リクエストは利用者ごとに毎分 20 回まで、有効なレシートは最大 8 件です。`POST /api/meeting-drive/import` はそのレシートを送信する必要があります。

`google_status` はアカウント、状態、ローカル用途で絞り込んだ範囲メタデータだけを読み取り、資格情報の復号、トークンの更新、bearer の返却は行いません。Token エンドポイントは明示的なツール許可リストを使い、個人資格情報には対応するローカル用途と Google 範囲の両方を要求します。状態照会と未知のツールは bearer を取得できません。

ローカルの Drive 出所記録には、選択したアカウント、Google メール、ファイル ID、バージョンを保存します。取消、失敗、アップロードの失効では、対応する状態変更と同じデータベーストランザクションで出所記録を削除します。それ以外の記録（成功した取り込みを含む）は `imported_at` から 30 日間保持し、期限後は Gateway 稼働中に 60 秒間隔で動く既存の清掃処理で削除します。停止後は次の清掃で処理します。文字起こしファイルと監査ログの保持規則は別で、この出所メタデータの清掃では削除しません。

`user.google_connect` の監査には認可用途、返された範囲集合のハッシュ、想定外の範囲を記録します。Drive／Meet 一覧の読み取りと早期の拒否も記録します。トークンやファイル内容は保存せず、取り込み識別子はハッシュ化します。

取り込み済みコピーと完成した文字起こしは接続解除で回収されません。Google 側の取消は API の拒否や更新後の権限情報で検出し、即時通知ではありません。これは製品経路の認可であり、gateway と同じ OS ユーザーで動く無制限のプロセスからの隔離ではありません。実際の OAuth／Picker と提供元の処理は別途確認が必要です。[会議の文字起こし](73-meeting-transcripts.md)と[個人接続の設定](../../guides/ja-JP/google-personal-connections.md)を参照してください。

最近のスキルにはアカウント、対象スタッフ、スキル名だけを1アカウント最大100件保存し、メッセージやスキル本文は保存しません。送信の受理後に記録し、チップの選択だけでは記録しません。実行成功を保証する履歴ではありません。組織図の表示は会話や設定へのアクセスを広げません。従業員の自動化編集では shell コマンド、条件スクリプト、任意の通知先、ワークフロー管理を許可しません。作成者を確認できない既存記録には直接の紐付けでのみアクセスできます。

Cron admission は `on_behalf_of`、`created_by_user_id`、`scoped_by_user_id` を持つ全記録の共通 store 制約です。MCP の追加・更新・再開も同じ `BEGIN IMMEDIATE` トランザクションで検査・保存します。有効な予定は帰属する利用者ごとに 20 件、AI スタッフごとに 50 件（既存 Admin 予定を含む）までで、Dashboard と MCP を合算します。作成・新たな引き受けは利用者ごとに直近一時間 20 件まで。記録は削除・再起動後も残り、通常の編集では再加算しません。単純な停止・削除は可能です。由来マーカーのない Admin 予定は従来どおりですが、人間の由来を持つ MCP 記録は Admin の場合も制限されます。最短間隔は 15 分で、日付条件にかかわらず連続日とみなし、深夜をまたぐ間隔も検査します。Scheduler の読み込み時と実行直前にも不適合の記録をスキップし、件数だけをログに記録します。

従業員の `cron.run_now` は spawn 前に判定します。直近 10 分間で予定ごとに 3 回、利用者ごとに 10 回、未完了は利用者ごとに 2 件、全体で 4 件までです。Semaphore の空きがなければ busy を返し、待機 task は作りません。拒否は回数を消費せず、受理後の失敗は回数に含めます。完了・キャンセル・panic で未完了枠を解放します。状態は容量制限のあるプロセスメモリーに保存され、再起動でリセットされます。ロック異常時は拒否します。従業員の cron 式は正規化・解析前に 256 bytes に制限し、store と runtime の検査にも適用します。

非 Admin の追加・更新は結果の name＋task のモデルプロンプト全文にチャットと同じ `scan_input_with_audit` を適用し、拒否時は保存せず `security_audit.jsonl` に記録します。再開・手動実行でも既存 task を検査し、agent_id の変更は禁止です。H2 は host 実行対象を制限する方式です。追加、編集、再開、手動実行には既存の代理と `[container] sandbox_enabled = false` が必要で、registry とディスク上の有効な型付き設定を検査します。設定を読めない場合は拒否します。保存された `created_by_user_id`／`scoped_by_user_id` と手動呼び出し元により実行直前にも再検査し、サンドボックス有効化や対象不明時は停止して skipped を記録します。既存 host runner の runtime、capabilities、native sandbox 設定は維持します。コンテナ内 cron は今回実装せず、社員マーカーのない既存 Admin 予定は従来どおり host で実行します。設定の読み取りからプロセス起動までを覆う原子的なロックはありません。

社員 cron は UTC のみ（ゼロ時差の UTC／GMT 別名も可）です。DST による実時間の間隔短縮を避けるため、他のタイムゾーンを使う既存予定の編集・再開・手動実行は拒否します。閲覧と権限に基づく停止・削除は可能で、タイムゾーン付き予定は Admin が管理します。

人間由来の MCP 予定は UTC が既定で、由来マーカーのない Admin／バックグラウンド予定はローカル時間帯の検出を維持します。
