# データソースとネイティブ・データベースコネクタ

> 遮蔽ルールが隠せるのは、見つけられた項目だけです。自分の MCP サーバーでも、顧客の MCP サーバーでも、DuDuClaw が自ら接続するデータベースでも——見つけ方はここに書いてあります。

---

## 埋めた穴

2026-09 まで、`db_field` ルール（`fields = ["res.partner.name", "hr.employee.*"]`）が効くのは Odoo だけでした。`model.field` という書き方は `json_path` ルールの糖衣構文にすぎず、その展開先——どのツールがどのテーブルのレコードを返すか、JSON のどこに入っているか、項目名が mapper を経ても残るか——は `ODOO_TOOLS` というハードコードされた一枚の表でした。`db_field` を Odoo 以外に向ける手段はありませんでした。

その下にはもう一段深い穴がありました。遮蔽が横取りするのは DuDuClaw 自身の MCP サーバー、つまり `duduclaw mcp-server` 内の単一の絞り込み点だけです。顧客が**自分で用意した** MCP サーバー（Postgres MCP、MySQL MCP、鼎新 ERP ブリッジなど、エージェントの `.mcp.json` に書かれたもの）は Claude CLI が直接起動するので、そのツール結果はそもそもパイプラインに一度も届いていませんでした。Odoo の表を差し替え可能にするだけでは、これらのサーバーには一つも効きません——データが遮蔽まで到達していなかったのです。

この機能は両方を埋めます。`db_field` ルールがどこでも参照できる**レジストリ**、そしてデータソースの行が実際に遮蔽を通るようにする二つの経路——すでにある MCP サーバー向けの**プロキシ**と、MCP サーバーを持たないデータベース向けの**ネイティブコネクタ**です。

---

## データソースの二種類

| 種類 | 表すもの | 行の出どころ | 設定 |
|---|---|---|---|
| ツール経由のレジストリ項目 | どの MCP ツールがどのテーブルのレコードを返すか、返る JSON のどこにレコードがあるか | どの MCP サーバーでも——DuDuClaw 自身のものでも、MCP プロキシ経由の外部サーバーでも | `[redaction.data_sources.<name>]` |
| ネイティブなデータベース接続 | DuDuClaw が自ら開く PostgreSQL / MySQL / SQLite の生きた接続 | DuDuClaw 自身の `db_select` / `db_query` MCP ツール——外部サーバー不要 | `[db_sources.<name>]` |

どちらも呼び名は同じです。`db_field` ルールの `source` 欄、そしてダッシュボードの「データソース」カード一枚が両方を一覧します。

---

## レイヤー 1：データソースレジストリ

`[redaction.data_sources.<name>]` は、`db_field` ルールが必要としながら自分では持てない三つの事実を記述します。どのツールがテーブルの行を返すか、呼び出しごとにテーブルをどう決めるか、レコードが JSON のどこにあるか、です。

```toml
[redaction.data_sources.crm_pg]
label = "客戶 CRM 資料庫"
tools = ["pg_query", "pg_select"]          # 1 個以上、完全一致か末尾 * の glob
table_arg = "table"                        # 固定の `table = "customers"` と排他
record_paths = ["$.rows[*]", "$[*]", "$"]  # これが既定値そのもの
key_alias = { name = "customer_name" }     # ツールが項目名を変える場合だけ
```

`db_field` ルールはこう参照します。

```toml
[redaction.rules.crm_customers]
type = "db_field"
source = "crm_pg"          # `connector` は非推奨の別名として今も使える
fields = ["customers.name", "customers.address", "orders.*"]
category = "DB_FIELD"
```

内蔵で二つ出荷され、定義し直すことはできません。`odoo`（元の `ODOO_TOOLS` 表をレジストリの binding として表現し直したもの——9 個のツール、固定／動的テーブルの混在、mapper struct を経由するツールごとの key alias）と、`duduclaw_db`（`db_select` を束ねる、後述）です。`source` も `connector` も省略すると引き続き `odoo` が既定になるので、レジストリ導入前の設定は意味が変わりません。

テーブル名はもうドット区切りである必要はありません。`db_field` の検証は Odoo の `model.model` 形式に加えて、素の SQL 識別子（`customers`、`public.customers`）も受け付けるよう緩和されました。それ以外の `db_field` の fail-closed な挙動は変わっていません。未知の `source`、空の `tools`、壊れた `record_paths`、パターンに合わない `table.column` 文字列——いずれも黙ってスキップせず読み込みを拒否します。

## レイヤー 2a：MCP プロキシ——自分で書いていないサーバーも遮蔽する

`duduclaw mcp-proxy --server <name> -- <cmd> [args…]` は隠しサブコマンドです。Claude CLI と一つの外部 MCP サーバーの間に立つ、stdio の JSON-RPC パススルーです。エージェントのターンで遮蔽が有効なとき、ゲートウェイはそのエージェントの spawn ごとの `.mcp.json` を書き換え、`duduclaw` 以外の**stdio** サーバーを直接ではなくこのプロキシ経由で起動させます——チャンネル返信の Claude CLI spawn（通常 spawn と one-shot PTY フォールバック、どちらも `channel_reply.rs`）と、dispatch／cron／heartbeat／goal-loop のターンの spawn（`claude_runner.rs` の `prepare_claude_cmd`、同じ共有ヘルパー `mcp_proxy_cli_args` 経由）の両方を対象とします。プロキシは内蔵の絞り込み点とまったく同じ二つの処理を適用します。

- `tools/call` リクエストの `arguments` は同じ egress 判定を通ります（`Deny` はその場で JSON-RPC のエラーとして返し、呼び出しは upstream に届きません。`Allow` は許可されたツールに対して `<REDACT:…>` トークンを実値に復元することがあります）。
- 対応するレスポンスの `result` は同じ `redact_value` パイプラインを通ります。ツール名は `<server>.<tool>` の名前空間になるので、`match_tool = "crm_pg.pg_select"` が同名の DuDuClaw ツールを誤って捕まえることはありません。

それ以外——`initialize`、`tools/list`、通知、upstream 発のリクエスト、JSON として解釈できない行——はすべてそのまま転送されます。ラップされたサーバー本来の `env` にある資格情報は、`argv` ではなく環境変数 `DUDUCLAW_MCP_PROXY_ENV`（JSON の塊）を通して渡されます。Linux では `/proc/<pid>/cmdline` は誰でも読めますが `/proc/<pid>/environ` はそうではないからです。fail-closed もここで同じく効きます。プロキシは `duduclaw mcp-server` と同じ `McpRedactionLayer::try_init` の三択の結果に従います——遮蔽が無効なら純粋なパススルー、設定が壊れていれば何も転送せずプロキシ自体が起動を拒否します。

**まだ対応していないもの：**

- **HTTP/SSE の MCP サーバー。** ラップする子プロセスが存在しないため、書き換えの対象から外れ、警告だけをログに残します。そのツール結果は遮蔽されないままモデルに届きます。
- **PTY セッションプール**（`[runtime] pty_pool_enabled`、デフォルト off、ドキュメント上はスタンバイ経路）。プールされた対話型 REPL セッションは一回の spawn 呼び出しをまたいで生き続けるので、この書き換えが前提とする「spawn ごとの一時 `--mcp-config`」を差し込む場所がありません——毎回の呼び出しごとではなく、セッション自身が持つ書き換えガードが必要で、まだ実装されていません。上記の通常 spawn と one-shot PTY は影響を受けません。
- **codex / gemini / antigravity。** これらのランタイム自身の MCP 登録は、まだ一切このプロキシを経由しません。

## レイヤー 2b：direct-API のツールループ（openai-compat）

CLI 系のバックエンドは `duduclaw mcp-server` か `duduclaw mcp-proxy` から遮蔽を得ますが、`duduclaw-llm` の `run_tool_loop`（openai-compat ランタイム——API モードの Grok / DeepSeek / MiniMax エージェントなど）で動くモデルは、プロセス内の `ToolRegistry` と直接話すので、横取りするサブプロセスがありません。`duduclaw-llm` はこのためだけに `ToolInterceptor` トレイトを新設しました。`before_call(server, tool, args)` は dispatch 前に引数を拒否・書き換えでき、`after_call(server, tool, args, &mut result)` はモデルが見る結果を後から書き換えられます。ゲートウェイの `RedactionToolInterceptor` は、パイプラインの他の部分と同じ `RedactionManager` に対してこれを実装しているので、一度書いたルールは、モデルがそのツールに `duduclaw mcp-server` 経由で届いても、MCP プロキシ経由で届いても、このプロセス内経路で届いても、同じように振る舞います。もう一つ、どちらの仕組みもまだ届かないツール派遣経路があります——ローカル推論のツールループ（`local_llm.rs`）、ローカルでホストされたモデルがツールを呼ぶ経路で、その結果も遮蔽されません。

## ネイティブコネクタ（`duduclaw-db`）

MCP サーバーを一切持たない顧客——ただ PostgreSQL / MySQL / SQLite のデータベースがあるだけ——のために、`duduclaw-db` クレートは自前の 4 個の MCP ツールを持つ、ファーストパーティの読み取り専用 SQL コネクタです。DuDuClaw 自身の MCP サーバーを通して dispatch されるため、結果は遮蔽の絞り込み点に直接届き、プロキシを経由する必要がありません。

### 三つの独立したレイヤーで読み取り専用を保証する

1. **ステートメントガード**——一番安価で、単独では一番信用しない層。単一の文で、`SELECT` か `WITH` で始まらなければなりません。文字列リテラルの外に `;` は許しません。データを書き換える CTE（`WITH x AS (DELETE … RETURNING *) SELECT * FROM x`）はわざとこの層を通過します——それは単一の `WITH` 文そのものだからです。実際に止めるのは層 2 です。
2. **ドライバレベルの read-only**——PostgreSQL は `BEGIN READ ONLY`、MySQL は `START TRANSACTION READ ONLY` を実行し、SQLite は読み取り専用のファイルハンドルで開きます。書き込みを本当に不可能にしているのはこの層で、その上のパーサーではありません。
3. **上限**——`max_rows`（既定 200、上限 1000）と `timeout_ms`（既定 10 秒、下限 100 ミリ秒、上限 120 秒）が、一回の呼び出しにかけられるコストを縛ります。

### ソースの設定

```toml
[db_sources.crm_pg]
label = "客戶 CRM 資料庫"
driver = "postgres"                       # postgres | mysql | sqlite
url = "secret://env/CRM_PG_DSN"           # または url_enc = "<暗号文>"
allowed_tables = ["customers", "orders"]  # 必須、空不可。["*"] は全テーブル許可
max_rows = 200
timeout_ms = 10000
```

`url` はプロジェクトの `secret://<backend>/<name>` という資格情報の作法を通ります。平文の接続文字列は `driver` が `sqlite` でない限り読み込み時に拒否されます（`sqlite` だけは値がファイルパスであって資格情報ではないため）。パスワード入りの DSN が `config.toml` に平文で座っている理由はどこにもありません。

`allowed_tables = ["*"]` は受け付けられますが、これが唯一 `db_query`（後述）を解禁する設定でもあります。実在のテーブル一覧があるということは「`db_select` を通してのみ到達可能で、テーブルは検証済みの束縛された識別子」を意味します。自由形式の SQL は本物の SQL パーサーなしにテーブル allowlist と突き合わせることができないので、allowlist を持つどのソースでも丸ごと拒否されます。

### エージェントへの許可

他のすべての capability と同じく、既定は拒否です。

```toml
# agent.toml
[capabilities]
db_sources = ["crm_pg"]
```

二つの関門があり、どちらも必須です。`Scope::DbRead`（`db:read`——23 番目の MCP スコープ）とこの空でない許可リストは、どのツールハンドラが動く前にも MCP dispatch の絞り込み点で一度だけ検証されます。具体的な `source` 名はハンドラの中でもう一度検証されるので、`["crm"]` への許可がたまたま同じドライバを使う `payroll` ソースに届くことはありません。

### 4 個のツール

| ツール | 引数 | 戻り値 |
|---|---|---|
| `db_sources` | なし | `[{name, label, driver}]`——このエージェントが許可され**かつ**実際に読み込めるソースだけ。許可はあるが壊れているソースは、黙って省くのではなく理由付きで報告される |
| `db_tables` | `source` | `{tables: [{name, columns: [{name, type}]}]}`、`allowed_tables` で絞り込み済み |
| `db_select` | `source`、`table`、`columns?`、`filter?`（`[{column, op, value}]`、`op` は `= != < <= > >= like in` のいずれか）、`order_by?`、`limit?` | `{rows, row_count, truncated}`——識別子は検証・クオートされ、値はすべてパラメータとして束縛される |
| `db_query` | `source`、`sql`、`limit?` | 同じ形。**ソースの `allowed_tables` が厳密に `["*"]` のときだけ使える**。それ以外では接続すら開かずに拒否される |

行の値は、ドライバがたまたまデコードした形をそのまま返すのではなく、意図的に対応付けられます。真偽値はそのまま真偽値、整数と浮動小数点は JSON の数値に、`NUMERIC`/`DECIMAL` は**文字列**になります（浮動小数点にすると金額の端数が丸まるため）。タイムスタンプは ISO-8601 文字列、`bytea`/`BLOB` は base64、JSON 型の列は二重エンコードせずパース済みで返ります。どの規則にも当てはまらない型は、推測したり黙って落としたりせず、正直なプレースホルダー `"<unsupported type: NAME>"` になります。黙って落とすと、その列を狙った遮蔽ルールが誰にも気づかれずに何にも一致しなくなるからです。

プールはキャッシュせず呼び出しのたびに新しく開きます。資格情報のローテーションや `[db_sources.…]` の編集が、再起動を待たず次の呼び出しから効くようにするためです。

### 内蔵の `duduclaw_db` レジストリソース

`duduclaw_db` は `db_select` という一つのツールだけを束ね、テーブルは呼び出し自身の `table` 引数から読み、レコードは `$.rows[*]`、項目名はそのまま通します。つまり `[db_sources.*]` の**どの**接続に対する `db_field` ルールも、この一つの内蔵ソースを使い回せます——`source = "duduclaw_db", fields = ["customers.name"]` と書くだけで、別途レジストリに登録する必要はありません。binding が見ているのは `table` 引数だけで、どの `db_sources` 接続が呼ばれたかではないからです。もし二つの異なる接続がたまたまどちらも `customers` という名前のテーブルを持っていて、片方だけを隠したい場合は、代わりに明示的な `json_path` ルールを書き、`match_args = { source = "crm_pg", table = "customers" }` のように指定してください（`source` も `table` もどちらも `db_select` のトップレベル引数なので、どちらか一方でも両方でも条件にできます）。`db_query` はレジストリでわざと未束縛のままです。生の SQL 結果の列がどのテーブルに属するかは、実際のパーサーなしには呼び出しから分かりません。

## 地端ファイル(CSV／Excel／テキスト)

`db_field` ルールが Postgres や Odoo の項目を隠せるのは、どちらの経路も最終的に MCP ツール呼び出しに行き着くからです——遮蔽が key 名を見られる唯一の場所です。エージェント自身のディスク上のファイルには、デフォルトではこの絞り込み点がありません。Claude CLI 組み込みの `Read`（と `Bash` 経由の `head`／`cat`）は MCP ツールではないため、そうやって開いた `customers.csv` はまるごとモデルのコンテキストに入り、どのルールにも見えません。チャンネル添付はこの穴をさらに悪化させます——`format_attachment_ref` はメッセージ本文に保存済みファイルのパスを付け加えるだけなので、エージェントは結局 `Read` でそれを開きます。`office_script`／`sheets_read` はすでに絞り込み点を通っていますが、持っているのはパターンルールだけで、ここにも項目という概念はありません。しかも PostToolUse フックはツール結果を後から書き換えられないので、「出口で隠す」という選択肢はそもそも存在しません。唯一の入り口は、読み込み自体を MCP 呼び出しにして、組み込みの経路をふさぐことです。

### 三つのツール、一つのパスの柵

| ツール | 引数 | 戻り値 | 上限 |
|---|---|---|---|
| `file_read` | `path`、`max_bytes?` | `{path, table, text, truncated}` | 512 KiB、プレーンテキストのみ |
| `csv_read` | `path`、`delimiter?`、`has_header?`（デフォルト `true`）、`limit?`（デフォルト 200）、`offset?` | `{path, table, columns, rows, row_count, truncated}` | ディスク上 64 MiB、`limit` は 2000 が上限 |
| `xlsx_read` | `path`、`sheet?`、`limit?`、`offset?` | 同じ形に加えて `sheet` と `sheets` | ディスク上 32 MiB（表計算パーサーはディスクサイズをはるかに超えて展開するため、CSV より厳しい上限） |

`table` は常にファイル自身の拡張子付きベース名です——`customers` ではなく `customers.csv`。すべてのパスは 1 バイトも読む前に一つの柵を通ります。canonicalize したうえで、エージェント自身のディレクトリ、`<agent_dir>/attachments`、`<home>/attachments`、あるいは operator が `config.toml [files] allowed_roots` で宣言したエントリのいずれかに含まれていることを要求します。柵から逃れる `..` セグメントやシンボリックリンクは canonicalize が走る前に拒否されるので、エラーは「許可範囲外です」という曖昧な言い方ではなく、本当の問題を名指しします。（`db_sources` と違って）柵の上にエージェント単位の capability ゲートはありません——柵自体がすでに「これは誰のデータか」に答えているからです。したがって三つのツールは常に `tools/list` に載り、`files:read` スコープ（`Scope::FilesRead`、24 番目の MCP スコープ）だけが門番です。

`csv_read` はワークスペースに既にある `csv` クレートで読み、ヘッダー行がなければ `c1..cN` という列名にフォールバックします。`xlsx_read` は `calamine`（新規依存、純粋な Rust 実装、`dates` フィーチャのみ）で xlsx／xlsm／xls／ods を読み、セルは順に JSON の数値、真偽値、null（空）、ISO-8601 文字列（日付時刻）、文字列のいずれかに対応付けられます。どちらのツールも監査記録にセルの内容は残さず、`path`／`table`／`row_count`——読み込みの「形」だけを残します。`mcp_db.rs` がフィルタ値について守っているのと同じルールです。

### 内蔵の `duduclaw_files` ソース

レジストリには、二つの構造化リーダーにあらかじめ束ねられたソースが用意されています。`table` は引数ではなくツールの**戻り値**から読み（`table_result = "/table"`）、レコードは `$.rows[*]`、`free_form_names = true` です——ファイルのテーブル名や項目名は識別子である必要がありません。このフラグがあるからこそ、次のようなルールが書けます。

```toml
[redaction.rules.customer_files]
type = "db_field"
source = "duduclaw_files"
fields = ["customers.csv.name", "客戶清單.xlsx.地址"]
category = "DB_FIELD"
```

各エントリは**最後のドット**で分割されます——`customers.csv.name` はテーブル `customers.csv` の `name` 列です。テーブルはシート情報を含まないファイル名そのものなので、`客戶清單.xlsx.地址` というルールは `xlsx_read` がどのシートを開いたかに関わらず発火します。シート単位で照合する対象がそもそも存在しないため、そのワークブックの全シートをまとめてカバーします。CJK の列名は内部で引用符付きのパス形式（`$.rows[*]['地址']`）にコンパイルされます——JsonPath 文法に追加された `['key']` セグメントは、引用符と改行以外の任意の Unicode 文字を受け付け、まさにこのケースのために作られました。素の `.key` 形式は ASCII のままです。`file_read` は何にも束縛されていません。返すのは非構造化テキストなので、そこで効くのはパターン照合パスだけで、項目ルールは決して効きません。

### データファイルガード

`[redaction] data_file_guard = "on" | "read_only" | "off"`、デフォルト `on`。呼び出し元のエージェントで遮蔽が実際に有効なときにのみ効きます。これは PreToolUse フック（`data-file-guard.sh`、既存のセキュリティフックと並べてインストールされます）で、`DUDUCLAW_DATA_FILE_GUARD` を読みます——ゲートウェイが spawn 時に設定する環境変数で、エージェント自身が読んだり書き換えたりできる設定値ではありません。`on` は `.csv/.tsv/.xlsx/.xlsm/.xls/.ods` パスへの組み込み `Read` をブロックし、コマンド文字列がそのいずれかの名前を含む `Bash` もブロックします。`read_only` は `Read` だけをブロックし、`off` は何もブロックしません。ブロックされると「此檔案受去識別化保護、請改用 csv_read／xlsx_read／file_read」という拒否メッセージが返ります。

二つの限界は曖昧にせず、はっきり書いておきます。`Bash` の検査はファイル名のヒューリスティックにすぎず、動的にパスを組み立てるコマンド（`python -c "open(chr(99)+...)"`）はまっすぐすり抜けます。そしてこのフックはシェルスクリプトです。Windows でも動くようにと意図的に Rust サブコマンドとして書かれた兄弟の `agent-file-guard` とは違い、`bash` が `PATH` にない Windows ホストではフックのコマンド自体が失敗し、Claude Code は非 2 の終了コードを許可として扱うので、そこではガードが単純に存在しないのと同じになります。どちらの穴も後で直すべきバグというより、PreToolUse フックが約束できることの本質的な限界です。モデルが誤って未遮蔽の経路に迷い込む確率を下げているにすぎません。本当の保護面は MCP ツールそのものです。`duduclaw_files` に束ねられたルールは、値がすでに `$.rows[*]` の中に入ってはじめて見えるのであって、上流でガードが何かを捕まえたかどうかとは関係ありません。

### 添付ファイルのヒント

`format_attachment_ref`——ゲートウェイがチャンネル添付の参照行に付け加える一文——は、csv/tsv/xlsx/xls/ods/txt/md/json についてもう一文を追加するようになりました。「請用 csv_read／xlsx_read／file_read 讀取」。それ以外の拡張子（画像、音声、動画）は以前とバイト単位で同じままです。これは強制層ではなく、あくまで後押しです。実際に誤ったツールの発火を止めているのは、前段のガードのほうです。

### なぜ `file_read` は表計算ファイルを拒否するのか

`file_read` は一つのテキストの塊を返しますが、`duduclaw_files` に対する `db_field` ルールは**構造化**された結果の中の `$.rows[*].<column>` に束縛されます。表計算ファイルの生バイトを `file_read` に通してしまうと、`客戶清單.xlsx.地址` のような項目ルールは照合すべき `.rows[*]` を一度も見つけられず、パターンルールだけに守られたまま素通りしてしまいます。そこで `file_read` はまず拡張子を確認し、csv/tsv/xlsx/xlsm/xls/ods はその場できっぱり拒否して、呼び出し元を黙って無防備な読み込みを返す代わりに `csv_read`／`xlsx_read` へ誘導します。

## ダッシュボード

**設定 → 匿名化** では、以前は別々だった「外部システム」カードと「データソース」カードが一つの「外部システムとデータソース」に統合されています。

- **テーブル項目ルール**カード。形は変わっていません。ルールごとに 1 枚のカード（id、カテゴリ、種類バッジ、一行のカバレッジ要約）。「追加」は二つのモードを切り替えます。**テーブル項目（簡易）**は `source` のドロップダウン、複数値の項目リスト（`*` に対応、`id` が残る旨の注記付き）、カテゴリ、誰が復元できるかを問います。**JSON パス（高度）**は `match_tool`、`match_args`、`paths`、`exclude_keys` で、簡易フォームで表せないものを指定します。ドロップダウンは表示名だけを示すようになりました。Odoo ERP、地端ファイル、そして自分で定義した各システム名です。三つの内蔵レジストリ id（`odoo`/`duduclaw_db`/`duduclaw_files`）が生の値として現れることはありません。生きたデータベース接続を持つソースを選ぶと、テーブル欄は今まで通り `db_sources.tables` を裏付けとするテーブル・項目ピッカーに変わります。保存のたびに解決済みルール一式をまず dry-compile し、パスの誤りや未知のソースはその場でインライン表示され、何も書き込まれません。「試験実行」ボタンは、貼り付けた JSON サンプル（模擬のツール名と引数付き）を実際のパイプラインに通し、ヒット表（pointer、rule id、category、token）を表示します。元の値は表示しません。
- **外部システムとデータソース**カード。以前は別々だった「外部システム」と「データソース」の二枚を統合したものです。鼎新／Salesforce／HubSpot のテンプレートプリセットは廃止され、汎用の「カスタム MCP ツール」種別が同じ役割を担います。行は固定順で並びます。**Odoo ERP**（`odoo.status` による接続状態表示。未接続なら統合ページへのリンクのみを表示し、実際の接続設定はそちらで行う）、`db_sources` の接続ごとに一行、カスタムの `data_sources` レジストリ項目ごとに一行、そして設定不要の固定行「地端ファイル（CSV／Excel）」です。三つの内蔵レジストリ名(`odoo`/`duduclaw_db`/`duduclaw_files`)がそれ自体の行として描画されることはなく、上記四種類の行の裏側にある配管です。各行は二列固定です。**読み込み**(平易な要約。Odoo の固定テーブル一覧や、データベース接続の許可テーブル一覧)と**書き戻し**(三択の復元ポリシーのドロップダウンと監査開示のチェックボックス。データベース接続と地端ファイルは読み取り専用で「該当なし」と表示)です。クリックできる「N 件の項目ルール」バッジは、該当システムで絞り込んだ状態でテーブル項目ルールカードへ移動します。

  書き戻しキーは `tool_egress` に自動的に導出され、operator には見えません。Odoo は常に `odoo_*` に書き込みます。カスタムツールソースは、`tools` が `duduclaw mcp-proxy` 形式の共通プレフィックスを持てば単一の `<server>.*` グロブにまとめられ、そうでなければツールごとに厳密一致キーになります。どちらの場合も、導出された全てのキーに同一のルールが書き込まれるので、operator から見れば一つの方針のままです。この UI 以前から残っていた `tool_egress` の項目は、カード下部の折りたたみ式「その他の書き戻しルール（詳細設定）」に収まり、無言で消えることはありません。

  **データソース追加ウィザード、固定 4 ステップ。** ステップ 1「**種類**」はデータベース／Odoo／カスタム MCP ツールの三択です（Odoo を選ぶと説明と統合ページへのリンクだけが表示されます。地端ファイルは説明のみで選択不可で、上の無料行がそれに当たります）。ステップ 2「**接続／ツール**」はその種類に必要な項目だけを尋ねます。データベースなら表示名、driver、接続文字列、許可テーブル。カスタムツールなら表示名、ツール一覧、テーブルの識別方法(引数から／固定／結果から)です。`record_paths`/`table_result`/項目エイリアス/タイムアウトは、既定値がすでに機能する「詳細設定」の折りたたみに収められています。ステップ 3「**テスト**」はデータベース種別なら実際に接続してテーブル一覧を取得し、チェックして選びます。カスタムツール種別ならサンプルを貼り付けてドライランします。このステップはカスタムツールソースではスキップできます(ボタンの文字が「次へ」ではなく「スキップ」になります)。新しいソースには通常まだそれを参照するルールがないためです。ステップ 4「**書き戻し**」はデータベース接続なら「該当なし」(読み取り専用)と表示します。カスタムツールなら復元ポリシーと監査チェックボックスを選びます。既存のソースを編集する場合は常にステップ 2 から始まり、ステップ 1 の種類選択は作成後には変更できません。内部識別子は表示名から自動生成され（ASCII を含まない表示名は `source_xxxxxx`／`db_xxxxxx` 形式）、「詳細設定」に読み取り専用で表示されます。UI では常に表示名を使います。

  **既知の制限。** カスタムソースには永続化された「検証済み」状態がありません。ステップ 3 のテスト結果はダイアログが開いている間だけ存在し、保存自体は接続が実際に確認済みであることを記録しません。カスタムツールソースのステップ 3 ドライランは、少なくとも一つの項目ルールがそれを参照するまでは 0 件ヒットと表示されます。これは想定どおりの挙動(まだ一致するルールがない)であり、接続の失敗を意味しません。すべてのデータベース接続は単一の汎用ソース `duduclaw_db` を経由するため、テーブル項目ルールのフォームには、どの接続のテーブル一覧を候補として出すかだけを決める接続選択のサブピッカーが追加されています。保存されたルール自体には、どの接続が使われたかの記録は残りません。
- **保護未起動バナー**。ゲートウェイの遮蔽マネージャが、構文は正しいが壊れた `[redaction]` 設定（あるいは設定自体がパースできない場合）から構築できなかったとき、カードの一番上に破壊的トーンのバナーが出ます。タイトルは「匿名化保護の起動に失敗しました」、その下に元のエラー理由をそのまま表示（翻訳せず、元のエラーメッセージがどの言語であってもそのまま）、最後に「\<time\> から発生・監査ログとアクティビティに記録済み」の行が続きます。ゲートウェイはチャットの応答は続けます（ツールを使わないので露出はありません）が、設定が直されて保存されるまで、すべての MCP ツールは使えません。保存されるとバナーは消え、再起動なしでパイプラインがホットリロードされます。

## 手順：ゼロから PostgreSQL の `customers.name` を隠すまで

1. **接続を登録する。** ダッシュボードの「外部システムとデータソース → データソースを追加 → 種類:データベース」で入力する（ウィザードのステップ 3 で接続をテストします）か、`config.toml` に直接書きます。

   ```toml
   [db_sources.crm_pg]
   label = "客戶 CRM 資料庫"
   driver = "postgres"
   url = "secret://env/CRM_PG_DSN"
   allowed_tables = ["customers", "orders"]
   max_rows = 200
   timeout_ms = 10000
   ```

   `CRM_PG_DSN` はゲートウェイのプロセス自身の環境変数に、実際の `postgres://user:pass@host/db` という文字列として設定します。`config.toml` に平文で触れることはありません。

2. **エージェントに許可する。** そのエージェントの `agent.toml` に：

   ```toml
   [capabilities]
   db_sources = ["crm_pg"]
   ```

3. **項目ルールを書く。** 内蔵の `duduclaw_db` レジストリソースを使い回します（よくあるケースでは別途レジストリ登録は不要です）。

   ```toml
   [redaction.rules.crm_customer_names]
   type = "db_field"
   source = "duduclaw_db"
   fields = ["customers.name"]
   category = "DB_FIELD"
   restore_scope = { kind = "owner" }
   ```

   これは読み込み時に、`db_select` に束縛され `args.table == "customers"` を条件とする一つの `json_path` ルールへ展開され、`$.rows[*].name` を隠します。

4. **実際に効くことを確かめる。** ダッシュボードの「試験実行」ボタンにサンプルを貼る（ツール `db_select`、引数 `{"table": "customers"}`）か、シェルから：

   ```bash
   duduclaw redaction verify sample.json --tool db_select --arg table=customers
   ```

   レポートには、ヒットごとの JSON pointer、rule id、マスク済みだが判別できる元値（`王**`）、token、category、そして往復の復元確認が並びます。遮蔽パイプラインの他の場所と同じ証跡の形式です。

5. **`customers` に触れる質問をエージェントに投げる。** `name` 列はモデルには token として届き、チャンネルへの返信では信頼された egress 境界で復元され、本人には実名のまま見えます。他の遮蔽対象の項目と同じです。

### 添付 CSV を三ステップで

チャンネル添付には `db_sources` の許可も接続文字列も要りません。ファイルはもともとディスク上にあり、最初から柵の内側です。

1. **ルールを書く。** 内蔵の `duduclaw_files` ソースを使い回すので、レジストリへの登録は不要です。

   ```toml
   [redaction.rules.attachment_customers]
   type = "db_field"
   source = "duduclaw_files"
   fields = ["customers.csv.name", "customers.csv.email"]
   category = "DB_FIELD"
   ```

2. **ファイルを送る。** ユーザーがチャンネルで `customers.csv` を添付すると、エージェントが見る添付行には「請用 csv_read／xlsx_read／file_read 讀取」というヒントが付き、ガードが `on` であればそのパスへの `Read` はきっぱり拒否されます。
3. **エージェントが `csv_read` を呼ぶ。** `name` と `email` の二列はモデルには token として届き、チャンネルへの返信ではファイルの所有者に対して、他の遮蔽対象の項目と同じ信頼された egress 境界で実値に復元されます。

## 境界

- **正直に挙げると、まだ四つの穴があります。** HTTP/SSE の MCP サーバー（ラップする子プロセスがなく、警告をログに残す）。PTY セッションプール（`[runtime] pty_pool_enabled`、デフォルト off、ドキュメント上はスタンバイ経路）——この機能が持つ「呼び出しごと」のガードではなく、セッション自身が持つ書き換えガードが必要で、まだ実装されていません。codex / gemini / antigravity ランタイム——自分自身の MCP 登録がこのプロキシを一切経由しません。そしてローカル推論のツールループ（`local_llm.rs`）——ローカルでホストされたモデルのツール呼び出しは、プロキシにも `ToolInterceptor` にも届きません。チャンネル返信（通常 spawn と one-shot PTY）と dispatch／cron／heartbeat／goal-loop のターンはカバー済みです。この四つはまだです。
- **レジストリが記述するのは形であって意味ではありません。** `record_paths` や `table_arg` の誤字が、こっそり保護を弱めることはありません。誤った項目は読み込みを拒否する（fail-closed）か、何にも一致しません。後者は「試験実行」で 0 件のヒットとして見えます。
- **`db_query` は、operator が明示的に `allowed_tables = ["*"]` と書いたソースにしか存在しません。** 自由な SQL に対して allowlist を部分的・best-effort で効かせる仕組みはなく、設計はフィルタするふりをするのではなくツールごと拒否します。
- **プールは呼び出しごとに開く**、キャッシュしません。エージェントが 1 ターンに数回しか呼ばないツールとしては妥当な代償で、資格情報のローテーションや設定編集が、ゲートウェイの再起動なしにすぐ効くという利点があります。
- **データファイルガードは後押しであって、サンドボックスではありません。** `Bash` の検査はファイル名のヒューリスティックで、動的にパスを組み立てるコマンド（`python -c "open(chr(99)+...)"`）はまっすぐすり抜けます。`bash` が `PATH` にない Windows ホストでは、このフックはシェルスクリプトなのでそもそも動かず、Claude Code はフックの実行失敗を許可として扱います。どちらの限界も後から発覚したものではなく、フック自身のソースコードにそのまま書かれています。地端ファイルの項目値を実際に遮蔽の射程内に留めているのは MCP ツール面（`file_read`／`csv_read`／`xlsx_read`）であって、その前段のガードではありません。

## まとめ

`db_field` はかつて「Odoo だけ」を意味していました。今は「どのツールを通しても、このエージェントが見てよいどのテーブルでも」を意味します。顧客自身の MCP サーバー（プロキシ越しに、少し距離を置いて遮蔽される）でも、DuDuClaw が自ら接続するデータベース（自前の MCP ツールを通して、出どころで直接遮蔽される）でも。どちらの経路も同じレジストリ、同じダッシュボードカード、ルールの同じ `source =` 欄に収まるので、operator はマスキング方針を一度書けばよく、データが実際にどちらの経路を通ったかを知る必要も気にする必要もありません。
