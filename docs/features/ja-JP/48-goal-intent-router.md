# ゴール意図ルーター

> チャットチャネルでエージェントに実際の仕事を頼むと、いまはそれに気づいて、追跡可能なゴールに変えることを提案します——ただし裏で勝手にゴールを作ることは決してありません。確認の言葉を送るか、ボタンを押すことで初めて作成されます。

## これは何か

これまで、自律ゴール(エージェントが受け入れ基準に向かって作業し、行き詰まったら人間へエスカレーションするループ)を開始できるのはダッシュボードだけでした。どのチャットチャネルでも、明示的な`/goal`コマンドでなければ、すべて通常の会話として扱われていました。そのため「今四半期の請求書をまとめてレポートにしてメールで送って」——明らかに質問ではなく仕事の依頼——のようなメッセージも、ただのチャット返信で終わり、何も追跡されませんでした。

ゴール意図ルーターはこのギャップを埋めます。届いたメッセージを1件ずつ読み、タスクの委任らしいかどうかを判定し、該当すれば小さなメニューで返信します:タスク開始、先に計画(承認を待つ計画を生成する)、このまま会話。ゴールの作成はトークンを消費し、自走するループを開始してしまうため、ルーターは決して自動では実行しません——ヒットしても、あなたが確認するための提案が生成されるだけです。この確認ステップがあるおかげで、誤判定のコストは低く抑えられます:最悪でも、あなたが読み流す1通の余計なメッセージで済みます。

## 判定の仕組み

3つの層を、コストが低い順に——知識ルーターと同じ形です:

1. **ハード除外(コストゼロ)。** コマンド、極端に短いメッセージ、質問、インジェクションスキャンのヒット、そして大部分が引用返信であるメッセージは、そのまま通常のチャットへ通過します。
2. **シグナルスコア(LLM不要)。** 決定論的なテーブルが、委任を示す動詞・成果物を示す名詞・複数ステップの言い回し・期限に加点し、疑問符・雑談マーカー・短い相槌・手紙やメール、メッセージの下書きや返信など単発の文章作成依頼で減点します。明らかに低ければチャットのままです。高いスコアだけで提案することはありません。
3. **モデルによる確認。** 高いスコアも中間のスコアも、言語モデルに1つのYes/No質問を投げます:これは複数ステップを要する仕事の委任か?ローカル推論バックエンドが設定されていればオンデバイスで動作しクラウドコストはゼロ、設定されていなければエージェントがどのみち生成する予定だった返信にこの判定を組み込むため、これも追加コストはかかりません。ローカルモデルが利用できない、または回答を解析できない場合は、返信を生成するモデル自身が判定します。その返信に有効な提案がなければ通常のチャットを続け、返信をブロックしません。

## 提案の確認

Telegram、Discord、Slack、LINEでは、🎯 タスク開始／🧭 先に計画／💬 このまま会話の3つのボタンが付きます。すべてのチャネルでテキストメニューも使えます。「タスク開始」でタスクを作成し、「先に計画」で作業前に計画を確認できます。「このまま会話」と返信するか、そのまま話し続けると提案を取り下げます。メニューとボタンの言語は `[general] default_language` に従います。繁体字中国語は 開始任務／先給計畫／繼續聊、英語は start task／plan first／keep chatting です。設定にかかわらず3言語の確認語を受け付け、引用符や末尾の句読点も使えます。英語は大文字と小文字を区別しません。`1`、`2`、`3` は従来のショートカットとしてのみ残りますが、AI の返信自体に番号付きリストがある場合は無視され、通常のチャットの回答として扱います。下書きの選択をタスク作成と取り違えないためです。

「タスク開始」は自分で `/goal` と入力した場合と同じ作成チェックを通るため、アクセスチェックと承認ゲートはすべて適用されます。「先に計画」は計画を生成し、作業を始める前にタスクを承認待ちにします。それ以外の返信、または10分間の無応答は、提案を取り下げます。

作成後の返信では、どの返信やボタン操作で作成されたか、依頼内容、AI 社員が順番に作業して完了時や行き詰まったときにここで報告することを説明します。取り消すにはダッシュボードの「ゴールタスク」ページで停止します。自動実行が無効なら、作成済みでも自動では始まらないことと、管理者への相談を案内します。計画を先に確認する場合も、同じページで承認、修正、停止を行います。これらの返信にタスク ID、コマンド、設定の案内は含まれません。手入力の `/goal` の返信は変わりません。

ボタンを押す、`/goal`と打つ、ダッシュボードを使う——どの経路も最終的には1つの作成パスに合流するため、受け入れ基準はどの場合も作成の瞬間に同じように凍結されます。

## 設定

`agent.toml`でエージェントごとに(または`config.toml`でグローバルに)、`[goal_intent]`セクション配下で設定します:

| キー | デフォルト | 意味 |
|-----|---------|---------|
| `enabled` | `true` | マスタースイッチ。すべてのヒットが確認待ちでゲートされるため、オンのままにしておいて安全です。 |
| `mode` | `"auto"` | `auto`(ローカルモデルがあればそれを使用、なければ返信に組み込む)、`local`、`reply_tag`、`off`のいずれか。 |
| `t_goal` | `65` | 高スコアの判定基準。この場合も提案にはモデルの確認が必要です。 |
| `t_gray` | `30` | このスコア未満はチャットのままです。以上のスコアはすべてモデルの確認を通ります。 |
| `cooldown_minutes` | `30` | 同じ会話内で提案と提案の間に空ける最小間隔。 |
| `daily_cap` | `20` | エージェントごとの、UTC1日あたりの提案上限。 |
| `suggest_ttl_minutes` | `10` | 保留中の提案があなたの返信を待つ時間。 |

ルーターはアクセスゲートと引き継ぎ割り込みの後に実行されるため、メッセージに許可される範囲を広げることは決してありません——もともと手動で辿れたはずの経路へのショートカットを提供しているだけです。
