# マルチランタイムエージェント実行

**Codex の外部設定検査（v1.80.0 から）：** 外部設定がないか MCP を定義していなければ、通常の社員、Explore、utility、Task Sandbox、Discovery は実行できます。MCP の検出、既存設定の読み取り・解析失敗ではソース名を示して拒否します。明示した Codex judge の拒否は判定失敗となり、既定の judge では再試行しません。起動前のローカル／キャッシュのスナップショット検査であり、その後のクラウド更新を完全に隔離する保証はありません。[検査対象と制限](../../architecture/extension-gates.md)。

> 1つのプラットフォームに 11 のランタイム ID：10 の CLI バックエンド（Claude、Codex、Grok、Qwen Code、Kimi Code、GitHub Copilot CLI、Kiro、Cursor、Mistral Vibe、OpenCode）と、任意の OpenAI 互換エンドポイントに HTTP で接続する `openai_compat` です。

管理対象の Claude 起動は、内蔵ツールだけの場合も一時的な厳格 MCP 設定のみを使い、ほかの MCP 読み込み元を追加しません。Grok 起動は、プロジェクトの管理外 MCP エントリーと、実際の `HOME` または `GROK_HOME` にあるグローバル MCP 定義を拒否します。設定を読めない場合も起動しません。Grok が実際に使う設定ルートは絶対パスである必要があります。`HOME` または `GROK_HOME` が相対パスなら修正してから再試行してください。既存ファイルは保持するため、サーバー定義をスタッフの MCP 設定へ移してから再試行してください。単独で起動する CLI とネイティブツールはこの境界の対象外です。

## 失敗の発生元と明示的なフォールバック

`[runtime] fallback` が未設定または無効なら Claude を自動で試しません。明示したフォールバックは従来のヘルス、ポリシー、互換モデルの検査を使います。アカウント切替、モデルのフォールバック、設定済みのローカル推論は維持します。Claude 以外の応答失敗後に Anthropic Direct API を追加呼び出ししません。

診断は元のバックエンド、明示的なフォールバック、未実行の理由を区別します。GPT/Codex や API の認証エラーで Claude へのログインを案内しません。実際の Claude CLI 認証失敗だけがその障害を記録し、実際の成功だけが解除します。OpenAI 互換エンドポイントは別の事業者の場合もあります。暗黙の Claude フォールバックに依存していた設定では、管理者が `fallback` を明示してください。

## 予備エンジンが動くとき（v1.84.0）

メインのエンジンが失敗した後に、明示的に設定した `[runtime] fallback` を実行するかどうかは、一つのルールで決まります（`failover/fallback_rule.rs`）。まず拒否の条件を確認し、次に型付きの失敗の種類、続いて DuDuClaw 自身が書くエラーの先頭部分を見ます。それ以外のテキストは v1.83.0 の判断を維持します。型付きの失敗の種類（`failover/failure_kind.rs`）を出すのは現在 OpenAI 互換ランタイムだけで、CLI エンジンは先頭部分と v1.83.0 のテキストルールで判断します。

| 予備エンジンを実行する | 予備エンジンを実行しない |
|---|---|
| 型付きの種類か DuDuClaw が書く先頭部分で確認できたログイン・認証情報の失敗（API エンジンの HTTP 401／403、Grok の認証失敗メッセージ、「CLI is not logged in」） | 作業そのものの上限：ステップ上限（`max_turns`）、合計時間の上限（`timeout_total`）、進展なしの上限（`timeout_no_progress`）。Grok、汎用 CLI、OpenAI 互換エンジンも Claude、Codex と同じ扱いになりました |
| プロバイダーが型付きのコード `model_not_found` でモデルの不在を返した場合 | 予算、製品ポリシー、自律作業の一時停止による拒否 |
| レート制限やサーバーエラー（429、5xx） | コンテンツポリシーによる拒否と課金のハードリミット |
| 起動や実行のエラー、空の応答 | 社員自身のツール設定が起動前チェックに通らない場合（`.mcp.json`）と、Codex のプロジェクト信頼の上書き |
| 接続タイムアウトを含むネットワークエラー（OpenAI 互換エンジンが返信の途中で読み取りタイムアウトした場合は合計時間の上限として扱い、切り替えません） | エンジンがリクエストを拒否した場合（HTTP 400／404／422） |
| エンジンが未インストール、またはクールダウン中 | 型がなく、`401 `、`403 `、`invalid_api_key`、`400 `、`404 `、`422 `、コンテンツポリシー違反、`billing_hard_limit` に触れているだけのエラーテキスト（v1.83.0 の一覧を維持。ログインエラーらしいが確認できないことを伝え、メインのエンジンのログイン状態の確認を求めます） |
| エンジン自身の設定が拒否された場合。理由コードは `engine_config_refused`：Codex の外部設定、データディレクトリそのものかそれを含む Codex の作業フォルダー、Grok のグローバル MCP 設定、単一引数のエンジンに収まらない会話内容（最後のものは Claude、Codex、OpenAI 互換エンジンにだけ切り替え） | |
| 右の列にないそのほかのエラーテキスト（接続拒否など） | |

メインのエンジンのヘルスに数えるのはプロバイダー側の失敗だけで、拒否やエンジン設定の拒否ではクールダウンに入りません。エンジン設定の扱いはビルド定数 `ENGINE_LOCAL_CONFIG_REFUSAL_FALLS_BACK` で決まります（現在は `true`。`false` にすると v1.83.0 と同じくそこで停止します）。

ログイン済みのメンバーと管理者には、試したエンジンを順に並べて各結果を示し、予備を設定していたのに使わなかった場合はその理由を説明します。これらの文は現在、繁体字中国語のみで、Web サイトの訪問者向けのメッセージには付けません。訪問者には引き続き汎用メッセージと参照番号だけを表示します。監査記録にはエンジンと理由を含む `fallback_skipped` が入ります。

**会話の引き継ぎ。** 予備エンジンはメインのエンジンと同じ会話履歴を受け取ります。v1.84.0 より前は、Claude が予備エンジンになった場合と、Claude 社員の Direct API へのフォールバックでは、最新のメッセージしか渡していませんでした。

**予備で使うモデル。** モデルの系統を宣言している予備エンジンは、現在のモデルがそのエンジンのものだと確定できる場合だけそれを使い、それ以外はエンジンのカタログの既定モデルを使います。名前の分からないモデルも同様です。系統を宣言していないエンジン（`openai_compat`、複数ベンダー対応の CLI）には、設定どおりのモデルを渡します。`opus`、`sonnet`、`haiku`、`fable` の短い名前は Claude のモデルとして扱います（大文字小文字を区別しない完全一致。`vendor/opus` や `opus-foo` は該当しません）。モデルの接頭辞を宣言しているほかのエンジンでこうした名前を保存した社員は、そのエンジンの既定モデルで実行し、社員ページとシステムチェックに「這位 AI 員工設定的模型（…）不屬於它的執行引擎（…），已改用該引擎的預設模型。請到員工設定重新選擇模型。」と表示します。Codex はこの文で「ChatGPT」と表記されます。ほかのエンジンに `claude-*` の正式名を設定した社員は、管理者が設定を保存し直すまで引き続き拒否します。製品ポリシーは価格表と明示的な `provider/` 接頭辞でモデルを判断し、DuDuClaw が自動で置き換えたカタログの既定モデルだけ、そのエンジンのベンダー（Claude → Anthropic、Codex → OpenAI、Grok → xAI）も確認します。

**後からインストールしたエンジン。** ダッシュボードからインストールすると、すぐにエンジン一覧を更新します。`runtime.detect` は、検出したエンジンが一覧を作ったときと異なる場合だけ作り直し、データディレクトリごとに最大で 1 分に 1 回です。社員のメインまたは予備のエンジンが見つからない場合は、最大で 1 分に 1 回検出し直します。実行中の呼び出しは開始時の一覧を使い続けます。

**Codex への指示と呼び出し用フォルダー。** Codex の呼び出しごとに `<home>/run/codex/` の下に専用フォルダー（`call-<16 進 32 桁>/`、バックグラウンド処理は `utility-<16 進 32 桁>/`、権限 0700）を作り、その呼び出し専用の `CODEX_HOME` を置きます。中には社員の指示の全文を書いた所有者のみ読める `AGENTS.md` と、出力形式ファイル `output-schema.json` が入ります。会話は標準入力で渡し、`-c project_doc_max_bytes=0` で作業ディレクトリや上位ディレクトリの `AGENTS.md` を取り込まないようにします。フォルダーは呼び出しの終了時に削除し、15 分を超えて残ったものは起動時と最大 1 時間に 1 回削除します。Codex の権限プロファイルは `<home>/run`、`<home>/run/codex`、ホストの Codex 認証情報フォルダーを Codex のツールから読み取り専用にし、`-c shell_environment_policy.exclude=["CODEX_HOME"]` でツールの環境変数から `CODEX_HOME` を除きます。v1.84.0 より前は、Codex のプロジェクト文書の上限 32 KiB を超えた部分が切り捨てられ、会話の要約や固定された指示が失われることがありました。DuDuClaw は社員ディレクトリに `AGENTS.md` を書かなくなりました。既存のファイルは削除しません。作業フォルダーがデータディレクトリそのもの、その上位フォルダー、またはそれを含むフォルダーの場合は拒否します（「Codex 不會啟動：這位員工的工作資料夾包含了 DuDuClaw 的系統資料夾。…」）。Windows では `C:\` のようなドライブのルートや、同じフォルダーを別の書き方で指すパスも対象で、確認から起動までの間にフォルダーが入れ替わった場合も同じ文を表示します。Windows では、作業フォルダーが完全なパスでない場合（例：`C:` や `\work`。「為保護系統資料夾，這位員工的工作資料夾必須是完整路徑（例如 C:\Work\project），已停止啟動 Codex。」）や、ネットワークフォルダー、Windows がローカルと報告しないドライブ（UNC パスや割り当てたネットワークドライブなど。「網路資料夾或無法確認為本機的磁碟不能用作 Codex 的工作資料夾，已停止啟動 Codex。」）の場合も Codex を起動しません。いずれもエンジン自身の設定の拒否（`engine_config_refused`）で、`ENGINE_LOCAL_CONFIG_REFUSAL_FALLS_BACK` が `true` の間は設定した予備エンジンが返信します。対処方法：ローカルディスク上にあり、完全なパスで書かれ、DuDuClaw のデータディレクトリを含まない作業フォルダーを社員に指定してください。Codex の外部設定は、次の場合に起動を拒否します（理由コード `engine_config_refused`。予備エンジンには切り替えられます）：ファイル内のいずれかのテーブル（プロファイルを含む）が空でない `mcp_servers` を定義している場合（空のテーブルは可）、または存在するファイルを確認・読み取り・解析できない場合（ファイルがないのは問題ありません）。プロファイルの設定ファイル、管理・クラウド設定のキャッシュ、macOS の強制設定にも同じルールを適用します。メッセージにはどの層か（主機層、專案層、員工資料夾）とファイル名だけを示します：「Codex 外部設定（{layer}）{ファイル名}：{理由}；拒絕啟動。請由管理者移除原生 MCP 設定，改用 DuDuClaw 的代理設定。」。完全なパスはログにだけ記録します。Codex に渡すプロジェクト信頼の上書き（`-c projects…`、`--config=projects…`、管理下の `.codex/config.toml` 内の `[projects]`）は社員の起動前チェックで拒否し、予備にも切り替えず、理由コードは `unknown` です。プロジェクト層の `.codex/config.toml` は作業ディレクトリから最も近い git ルートまでだけを確認し、これは Codex 自身が読む範囲と同じです。システム、プロファイル、クラウドキャッシュ、MDM の各ソースは従来どおり確認します。[拡張ゲート](../../architecture/extension-gates.md)を参照してください。

**Grok と汎用 CLI のプロンプトサイズ。** これらのエンジンは指示と会話履歴を一つのコマンド引数で受け取り、上限は 120,000 バイトです。必須の内容は、要約、固定された指示、履歴の注記、ナレッジのルール、ターンごとの指示、最新の 3 件のメッセージ、新しいメッセージです。これだけで上限を超える場合は呼び出しを拒否し、「這段對話必要的內容太大（…），{エンジン} 無法一次送出。請開始新的對話，或縮短固定指示後再試。」と返します（理由コード `engine_config_refused`。Claude、Codex、OpenAI 互換エンジンには切り替えられますが、ほかの単一引数のエンジンには切り替えません）。上限内に収められる場合は、古い会話を最新の 3 件まで削り、次に優先度の低いセクション（重要な事実、過去の失敗、プレイブック、最近の行動、ユーザープロフィール、作業状態、未決事項、プリセット）を短くし、続いて残った最近の会話を古い順に削り、最後に基本のプロンプトを末尾から短くします。上限内の内容は以前とまったく同じです。

## モデルとランタイムの整合性

エージェント作成、編集済みテンプレート、モデル保存、管理者の `/model` は同じモデル系統の判定を使います。確実な不一致は保存時に修正され、従来の管理者権限と製品ポリシーの制限を受けます。明示された API 互換バックエンド、フォールバック設定、不明なカスタムモデルは維持します。同じモデルの保存でも古い不一致を修復でき、応答は反映済みと再読み込み失敗を区別します。

未保存の古い設定に確実なモデル／provider 不一致がある場合、モデル実行前に拒否します。管理者が設定を保存してから再試行してください。読み取りやルーティングで設定を書き換えたり、不一致を Claude のログインエラーとして案内したりしません。名前の部分一致ではランタイムを推測しません。

**`agent.toml` を直接編集した場合（v1.84.0）。** チャットのターン（各チャネルと WebChat）の実行エンジンとモデルは、社員の設定ファイルを 1 回だけ厳密に読み込んで決めるようになりました（プリセットを解決した設定があればそれを、なければ `agent.toml` を読みます）。そのため、ディスク上で `[runtime] provider` と `[model] preferred` の両方を変えると、再起動や社員一覧の再読み込みなしで次のメッセージから反映されます。v1.86 からは、バックグラウンド処理（ディスパッチ、cron、リマインダー、ハートビート）も同じ厳密な読み込みを使い、設定に誤りがあれば Claude の既定値で実行せずに拒否します。[セキュリティ防御](05-security-defense.md)を参照してください。次の 2 つの場合、そのターンはモデルを呼ぶ前、会話記録を書く前に拒否され、新しい WebChat の会話では即時の案内だけが表示されます。

- `model_provider_mismatch`：モデルがそのエンジンのものではない場合（Claude の短い名前をエンジンの既定モデルに置き換えた後も一致しない場合）。案内：「モデルと実行エンジンの設定が一致しません。管理者に対応するモデルの選択を依頼してください。」（英語、繁体字中国語、簡体字中国語もあり）。
- `agent_config_unreadable`：設定ファイルがない・読めない、解析できない、`[runtime]`／`[model]` の型が誤っている、不明なエンジンを指定している、モデルの指定が必須のエンジン（OpenAI 互換）でモデルを指定していない場合。Kiro のモデルは `kiro-cli settings` で決まるため、指定がなくてもそのまま実行されます。案内：「この従業員の設定を読み取れなかったため、今回は実行しませんでした。管理者に設定の確認を依頼してください。」ファイルのパスと解析エラーはゲートウェイのログにだけ記録します。

Web サイトの訪問者には訪問者向けの汎用メッセージだけを表示します。v1.83.0 では不一致のとき理由コードのない英語の文を表示し、設定を読めない場合や不明なエンジンの場合は通知なしに Claude の既定値で実行していました。エンジンの切り替えは引き続きダッシュボードからを推奨します。保存時にエンジンとモデルを検証し、その社員をすぐに読み込み直します。

**ターンごとに表示するモデル。** WebChat の会話情報には実際に動いたモデルを表示します。Claude の短い名前を置き換えた場合はエンジンの既定モデル、予備エンジンに切り替えた場合は予備エンジンのモデルに「（備援）」を付けて表示します。CLI が報告したモデル名は、英数字と `. _ : / @ + - [ ]` だけからなる 1〜128 文字の ASCII である場合だけ表示し、それ以外は要求したモデルを表示します。

## Discord の社員選択

通常のメッセージ、`/model` などのテキストコマンド、`/ask` は同じ明示的な選択順を使います。社員専用 Bot のバインド、サーバーまたは DM の選択、全体設定の順です。スコープの空値は全体設定を継承します。指定した社員が削除・改名されている場合は拒否し、メイン社員へ黙って切り替えません。

明示的な選択がない通常会話は、従来のチャンネル／スレッドのバインド、許可チャンネルと既定社員のルート、その後の送信者権限付き `@` 呼び出しを維持します。テキストコマンドは従来の既定ルートで操作対象を決め、コマンドを社員呼び出しとして解釈しません。`/agent` と社員切替メニューでサーバーのバインドを変更するには、引き続き「サーバー管理」権限が必要です。返信の表示名には、バインドや `@` 呼び出しを含め、返信処理が実際に選択した社員を使います。ファイル送信もその社員の既存ディレクトリ検査を使い、応答社員が未確定ならメイン社員のファイルを走査しません。

## たとえ話：多言語オフィス

翻訳者が必要なオフィスを想像してください。フランス語しか話せない翻訳者を1人雇う代わりに、翻訳デスクを構築します——フランス語、ドイツ語、日本語の翻訳者、またはクライアントの言語を話せるフリーランサーに仕事を割り当てられます。

翻訳デスクは*どの*翻訳者が仕事を処理するかは気にしません——翻訳の品質を気にします。フランス語翻訳者が忙しければ、次の対応可能な人にルーティングします。

DuDuClawのMulti-Runtimeアーキテクチャはその翻訳デスクです——ただしAIバックエンド用です。

## 仕組み

### AgentRuntime Trait

コアは全バックエンドが実装する統一インターフェース（`AgentRuntime`）です：

```
AgentRuntime trait:
  fn execute(prompt, tools, context) → Response
  fn stream(prompt, tools, context) → Stream<Event>
  fn health_check() → Status
```

すべてのバックエンド——Claude、Codex、またはOpenAI互換エンドポイント——は同じインターフェースを実装します。システムの残りの部分は、どのバックエンドが特定のリクエストを処理しているか知る必要も、気にする必要もありません。

### ランタイムカタログ

各バックエンドの記述は 1 か所だけ、単一のコンパイル時テーブル（`crates/duduclaw-core/src/runtime_catalog.rs`）にあります。検出、ワンクリック インストール、モデル探索、CLI ログイン、モデル↔プロバイダー推論はすべてこのテーブルを読みます——「インストールできるのに検出されない」「設定できるのにログインできない」ランタイムは構造的に発生しません。

**ダッシュボードのワンクリックログイン**は Claude、Codex、Grok、Kimi、Copilot、Kiro、OpenCode に対応します。Codex はデバイスコード方式です。CLI に表示される認証ページとコードをブラウザで使い、CLI の完了を待ってください。OAuth コールバック URL の `code` をダッシュボードに貼り付ける必要はありません。Cursor はランタイムとして残りますが、ブラウザコールバックをリモートのダッシュボードから確実に完了できないため、ワンクリックログインには表示しません。Qwen と Mistral Vibe は API キーを使います。アカウントページの API Token カードから、アカウント id を確認して保存済みアカウントを削除できます。プロバイダー側のキーは失効しません。

Gemini CLI は DuDuClaw のランタイムと Docker パッケージから削除されました。既存の `runtime = "gemini"` 設定では別のランタイムと互換モデルを選んでください。別の Gemini API プロバイダーは引き続きサポートします。[削除と移行](../../guides/ja-JP/deprecations.md)を参照してください。

モデル指定の書き方はベンダーごとに異なり、カタログはどの形式かも記録します：独立したフラグ（`--model <id>`）、Copilot が文書化している等号形式（`--model=<id>`）、フラグを持たない CLI 向けの環境変数（Mistral Vibe の `VIBE_ACTIVE_MODEL`）、あるいは無し（Kiro は呼び出しごとではなく `kiro-cli settings` でモデルを選びます）。

- **Kiro**——AWS の FAQ には、Kiro のネイティブ インターフェース以外へリクエストを流すサードパーティ製自動化ハーネス経由の利用は許可されないと明記されています。DuDuClaw から Kiro を駆動することはこれに該当します。自身の CI から `kiro-cli` を直接呼び出すことは許可されています。Kiro のインストール経路が手動なのはこのためです——判断はあなたが明示的に行ってください。
- **Anthropic**——[法務・コンプライアンスページ](https://code.claude.com/docs/en/legal-and-compliance)には、サードパーティの開発者が自社アプリで Claude.ai ログインを提供すること、Free・Pro・Max プランの認証情報でユーザーの代わりにリクエストを中継すること、Claude.ai の認証情報やセッショントークンを収集・保存・仲介することは認められないと書かれています。認められているのは、自分のサブスクリプションで改変されていない Claude Code にサインインすることで、Pro と Max の利用上限は通常の利用を前提としています。Anthropic は事前の通知なく執行できるとしており、アカウント停止の報告もあります。製品向けに案内されているのは Claude Console の API キーです。

- **Qwen**——無料 OAuth ティアは 2026-04-15 に終了しました。API キー（ModelStudio / DashScope）のみです。
- **OpenCode**——MIT で独自の制限はありませんが、上記の理由により 1.3.0 で Anthropic サブスクリプション プラグインを削除しました。プロバイダーの API キーをご利用ください。
- **OpenAI**——OpenAI には公式の Sign in with ChatGPT プログラムがあります（[規約](https://openai.com/policies/sign-in-with-chatgpt-terms/)、2026-09-29 版）。[クイックスタート](https://developers.openai.com/siwc/quickstart)には、Sign in with ChatGPT は現在、限定トライアルとして選ばれた商用パートナーに提供されていること、ChatGPT プランの利用はすべてのオープンソースのパートナーと選ばれたプライベートクライアントに提供されていることが書かれています。[ヘルプ記事](https://help.openai.com/en/articles/20001542-using-your-chatgpt-plan-in-other-apps-and-sites)では、サポート対象のオープンソースツールは引き続き使え、商用パートナーは申請フォームから申し込むとしています。つまり商用製品には OpenAI の承認が必要です。規約ではさらに、ユーザーがパートナーへの支払いやプランのアップグレードなしに自分の ChatGPT プランを使えること、認証トークンを永続的に保存する場合はユーザーが管理するローカル環境に限り、リモートやマネージド環境には置かないこと、ほかのツールや無関係なリクエストのための汎用 API アクセスを提供しないことを求め、違反すると Sign in with ChatGPT の利用を停止される場合があるとしています。OpenAI の Codex 責任者は 2026-09-08 に、あるサードパーティのアプリについて「Sorry, but this is not an approved use of Sign in With ChatGPT. We support pure OSS clients and others we have partnerships with, but you need to reach out and talk to us for that.」と[投稿](https://x.com/thsottiaux/status/2097131394199896166)しています。DuDuClaw をリモートのホストやコンテナで動かす場合、Codex のトークン（`~/.codex/auth.json`）もそこに保存されます。[利用規約](https://openai.com/policies/terms-of-use/)は引き続き適用されます。安定して使うなら API キーです。
- **xAI**——サードパーティ製品が SuperGrok / X Premium+ のサブスクリプションを操作することについての公開された立場は見つかりませんでした。[利用規約](https://x.ai/legal/terms-of-service)は引き続き適用されます。

ダッシュボードは該当する注意事項を表示し、サブスクリプション ログインを開始または保存する前に明示的な同意を求めます。gateway も同意フラグのない呼び出しを拒否します（[サブスクリプションログインのリスク開示](#サブスクリプションログインのリスク開示)を参照）。

### バックエンドの駆動方法

3 つの CLI バックエンド（`claude`、`codex`、`grok`。`runtime/mod.rs` の `BESPOKE_RUNTIME_IDS`）は専用のランタイム モジュールを持ちます。共有できないベンダー固有の配線——アカウント ローテーション（Claude）、各 CLI 独自形式での MCP 設定注入、ケーパビリティ→サンドボックス フラグの変換——があるためです。それ以外はすべて、カタログ エントリーからそのまま組み立てられる**単一の**汎用 print-mode ランタイム（`runtime/generic_cli.rs`）が駆動します：テンプレート argv でバイナリを起動し、プロンプトを引数または stdin で渡し、text / JSON / JSONL を最終応答テキストへ解析し、非ゼロ終了や認証要求のマーカーをフェイルオーバー チェーンが理解できる型付きエラーへ対応付けます。残り 7 つの CLI（Qwen Code、Kimi Code、GitHub Copilot CLI、Kiro、Cursor、Mistral Vibe、OpenCode）はこの汎用ランタイムを通ります。`openai_compat` は CLI ではなく、独自の HTTP モジュール（`runtime/openai_compat.rs`）を持ちます。手書きのモジュールは合計 4 つです。

### 主なバックエンド

以下では Claude、Codex、OpenAI 互換エンドポイントを説明します。Grok は後のセクションで説明します。

**Claude Runtime** — Claude Code CLI（`claude`）をJSONLストリーミング出力で呼び出します。ネイティブMCPツールサポート、bash実行、Web検索、ファイル操作が組み込まれた最も機能豊富なバックエンドです。

```
Agent設定：runtime = "claude"
     |
     v
起動：claude --json --print ...
     |
     v
JSONLストリーミングイベントを解析
     |
     v

```

**Codex Runtime** — OpenAI Codex CLIを`--json`フラグで呼び出し、構造化ストリーミングイベントを取得します。

```
Agent設定：runtime = "codex"
     |
     v
起動：codex --json ...
     |
     v
JSONL STDOUTイベントを解析
     |
     v

```

**OpenAI互換Runtime** — OpenAI chat completions APIを話す任意のHTTPエンドポイント（MiniMax、DeepSeek、ローカルサーバーなど）を呼び出します。

            api_url = "http://localhost:8080/v1"

     |

### RuntimeRegistry：自動検出

DuDuClaw起動時、**RuntimeRegistry**はシステム上の利用可能なCLIツールをスキャンします：

```
起動スキャン（ランタイムカタログを1周するループ）：
     |
     v
  バイナリを持つカタログエントリーごとに：
     PATH → ~/.local/bin、Homebrew、bun/volta/npm-global/asdf shim、
     /opt/duduclaw/runtimes/bin、/usr/bin、/bin
       見つかった？ → 登録（専用モジュールがあればそれ、なければ汎用 print-mode）
     |
     v
  常に：OpenAI互換（バイナリではなくAPIキーで判定するHTTPエンドポイント）
     |
     v
Registryは利用可能なバックエンドを把握
```

`/opt/duduclaw/runtimes/bin` は DuDuClaw OS アプライアンス イメージが同梱 CLI を配置する場所です。ゲートウェイが対話的な `PATH` を引き継いでいなくても、イメージ同梱のランタイムは検出されます。

エージェントは`agent.toml`で使用するruntimeを指定します：

```toml
[runtime]
provider = "claude"          # プライマリバックエンド
fallback = "codex"     # プライマリが利用不可時のフォールバック
```

`provider` がない場合、エージェントは Claude で動作します。認識できない値は警告を記録し、同じく Claude にフォールバックします。

### 実行時間の上限とバックグラウンドモデル

`agent.toml [runtime] timeout_secs` は Codex、Grok、その他の CLI ランタイムの 1 回の実行、および OpenAI 互換 API の各リクエスト（通常、ストリーミング、ツールループ）の時間上限です。Claude にも適用されます。従業員またはグローバルの上書きがなければ、すべてのランタイムで **1800 秒**です（v1.84.0 から。それまで Claude 以外は **300 秒**）。**30 秒**から `[runtime] max_timeout_secs` まで指定できます（最大上限の既定は **3600**、設定範囲は **60〜14400**）。`[runtime] default_timeout_secs` でランタイムの既定値を上書きできます。手動編集した整数が範囲外なら最も近い境界に補正して警告を記録し、型が違う値は警告を記録して無視し、ランタイム／グローバルの既定値を使います。ダッシュボードでの保存は不正な値を拒否します。コンテナのタスクタイムアウトとは別の設定です。

`timeout_secs` の実効上限を増やすには管理者権限が必要です。Owner は上限を下げられます。設定を空にするとグローバル既定値か 1800 秒に戻り、現在の実効上限より増える場合は管理者が必要です（Claude を含め、空にした後に適用される既定値より低い値を設定していた社員では、空にすると引き上げになります）。


Windows の管理対象 CLI は停止状態で生成し、kill-on-close Job Object への割り当て成功後に再開します。親が先に終了しても Job 全体を終了でき、割り当てに失敗した子は終了させてエラーを返します。このラウンドでは Windows ネイティブ実行は未検証です。会話 owner が `_` または `.` で始まる場合は内部ディレクトリとしてバックグラウンド処理を拒否します。

Grok のパイプモードで応答が空の場合、PTY で再実行しません。この経路ではタイムアウト後にプロセスツリー全体の終了を保証できないため、空応答のエラーを返します。

バックグラウンドの決定確認、指示抽出、事実抽出、会話圧縮が社員自身のランタイムを使うのは Claude、Codex、OpenAI 互換 API の場合です。空白ではない `[model] utility` が優先し、未設定なら Claude は `claude-haiku-4-5`、Codex と OpenAI 互換 API は `[model] preferred` を使います。両方が空白なら Codex は CLI の既定モデルを使い、API は呼び出しを拒否します。Grok、汎用 CLI の社員は下記のルールに従います（v1.84.0）。明示した補助モデルとランタイムのベンダー系統が異なる場合はダッシュボードに警告します。

Claude の補助呼び出しは継承した環境をクリアし、共通の spawn 許可リストを適用してから、通常のローテーションなし Claude 起動と同じ取得元の Anthropic API key だけを追加します（OAuth は従来の HOME／キーチェーン／設定ディレクトリを使用）。軽量パスを実行し、アカウントローテーションには入りません。通常の会話は既存のローテーションを維持します。

分類と評価を含む補助呼び出しは、専用の実行モードを使います。Claude はツールなしの単一ターンの軽量パス、OpenAI 互換 API はツールなしの単一 completion を使い、ツールループには入りません。Codex は制限モードで実行します：読み取り専用サンドボックス、プラットフォームの MCP 設定を追加しない、毎回新規作成する所有者だけがアクセスできる空の一時作業ディレクトリ、ユーザー設定の無視、セッション保存なし。一時ディレクトリはエラーやタイムアウトを含め呼び出し終了後に削除します。システムプロンプトは prompt 内で渡し、`AGENTS.md` は書きません。Codex を明示した judge とチーム verifier も同じモードです。Grok、汎用 CLI は補助実行に非対応です。v1.84.0 からは、こうした社員のバックグラウンド処理に社員の `agent.toml [runtime] utility_provider`（`claude`、`codex`、`openai_compat`。管理者のみ設定可）を使い、未設定なら `config.toml` に全体の `[runtime] utility_provider` が実際に書かれている場合だけそれを使い、それ以外はエラー接頭辞 `[utility_unavailable]` でスキップします（v1.84.0 より前は内蔵の Claude／`claude-haiku-4-5` を通知なしに使っていました）。スキップされる処理：固定指示と重要な事実の抽出、決定事項の記録、履歴の圧縮（履歴はそのまま保持）、会話の要約とタイトル、会話の整理とナレッジ作成、状況分類（異常として扱う）、能動メッセージの判定（メッセージを保留）。システムチェックに該当する社員が表示されます。グローバルでは Claude、Codex、OpenAI 互換 API が使えます。非対応のグローバルプロバイダーや明示指定は拒否します。上位の評価処理が非対応の指定なしで再試行する場合も同じモードを適用します。Codex には内蔵の読み取りツールが残る可能性があります。残るリスクは[セキュリティ防御](05-security-defense.md)を参照してください。

定期的な会話要約と自動タイトルも、会話の所有者に同じ補助プロバイダー選択のルールを適用します。保存された所有者はシステム予約名でない実在の社員で、ID が一致する `agent.toml` が必要です。ディレクトリはシンボリックリンクでなく、正規化した `<home>/agents` の直接の子である必要があります。空でない無効な所有者はエラーとして補助処理を中止します。所有者が空の場合だけグローバル設定を直接使います。要約の保護セクションはモデルに送らず、既存の上限内で原文を維持します。明示された補助モデルが非互換でも値は保持し、エージェントとモデルの組み合わせにつき一度警告します。担当者のない処理の `[runtime] utility_provider` / `utility_model` は「設定 → 詳細 → システム」で変更できます。

### Per-Agent設定

異なるエージェントが異なるバックエンドを同時に使用できます：

```
Agent "dudu"（カスタマーサポート）→ Claude（最高の推論能力）
Agent "coder"（コード生成）    → Codex（コードに最適化）
Agent "analyst"（データ分析）   → Codex
Agent "local"（プライバシー重視）→ OpenAI互換（ローカルエンドポイント）
```

つまり、単一のDuDuClawインストールで複数のAIプロバイダーにまたがるエージェントを統括でき、それぞれがタスクに最適なバックエンドを使えます。

## Effort

最近の推論モデルには、モデルの選択とは別に**深さ**のダイヤルがあります。この 1 回の呼び出しでどれだけ深く考えるか、という設定です。ベンダーごとに書き方が異なり、受け付ける値も同じではありません。DuDuClaw はこれを 1 つの設定にまとめ、変換を引き受けます。

エージェントに設定します。

```toml
# <home>/agents/<id>/agent.toml
[model]
preferred = "claude-opus-5"
effort    = "high"          # low | medium | high | xhigh | max
```

未設定がデフォルトで、*フラグを一切渡さない*ことを意味します。spawn の内容はこの機能のない DuDuClaw とバイト単位で同一で、プロバイダー自身のデフォルトの深さが適用されます。

### ランタイムごとのフラグ対応

インストール済みのバイナリに対して 2026-09-24 に実測した結果です（社内の実測メモに記録、非公開）。ドキュメントからの推測ではありません。

| ランタイム | 実測バージョン | effort の表現方法 | CLI が受け付ける値 |
|---|---|---|---|
| `claude` | 2.1.258 | `--effort <v>` | `low` `medium` `high` `xhigh` `max` |
| `codex` | 0.156.1 | `-c model_reasoning_effort=<v>`（設定オーバーライド、専用フラグなし） | `low` `medium` `high` `xhigh` |
| `grok` | 1.0.41 | `--reasoning-effort <v>`（別名 `--effort`） | *`--help` では列挙されていません* |
| `openai_compat` | — | リクエストボディの `reasoning_effort` | `low` `medium` `high` |

### クランプ表

受け付ける値の集合が異なるため、設定値は対象ランタイムが受け付ける値まで**下方向に**クランプされます。黙って捨てられることも、CLI が拒否する値が送られることもありません。

| 設定値 | claude | codex | grok | openai_compat |
|---|---|---|---|---|
| `low` | `low` | `low` | `low` | `low` |
| `medium` | `medium` | `medium` | `medium` | `medium` |
| `high` | `high` | `high` | `high` | `high` |
| `xhigh` | `xhigh` | `xhigh` | **`high`** | **`high`** |
| `max` | `max` | **`xhigh`** | **`high`** | **`high`** |

Grok を意図的に `high` で頭打ちにしているのは、`--help` がフラグ名には触れていても値を列挙していないためです。`xhigh`/`max` を渡すと "unexpected value" で spawn 全体が落ちるおそれがあります。`openai_compat` も、8 つの異質なプリセットにまたがるため同じ理由で上限を設けています。どちらの上限も 1 か所（`duduclaw-core/src/effort.rs`）にあり、実機での動作確認が取れた時点で引き上げられます。

### Direct-API の対応

API レベルの経路（`duduclaw-llm`）は、同じ値を各ベンダーのネイティブなフィールドへ載せます。

| プロトコル | フィールド |
|---|---|
| Anthropic Messages | `output_config.effort`（GA、beta ヘッダー不要） |
| OpenAI Responses | `reasoning.effort` |
| OpenAI-compat chat/completions | `reasoning_effort`（トップレベル） |
| Gemini `generateContent` | `generationConfig.thinkingConfig.thinkingLevel`。**未検証**、下記参照 |

> Gemini のキーは、**確認が取れていない**唯一の対応です。入れ物としての `thinkingConfig` は検証済みで（既存の `thinkingBudget` が使っていて、すでに出荷されています）、同じ階層の `thinkingLevel` キーは確認できませんでした。ai.google.dev を 2 回取得しましたが、どちらも `GenerationConfig` のリファレンスが途中で切れていて、このキーに触れていませんでした。Interactions API では `generation_config.thinking_level` と書かれているため、`generateContent` 側の camelCase 版は推測です。フィールドが設定されたときだけ送られるので、effort が未設定ならこのキーが送られることはありません。頼る前に再検証してください。

### コストとキャッシュ

引き上げる前に知っておくことが 2 つあります。

- **effort はトークンを消費します。** キャッシュやプロンプトの整理といった無料の改善の次に来る、品質とコストを交換する最初のレバーで、範囲の最上位は本当に難しい作業でだけ元が取れます。コーディングや長時間のエージェントタスクでは効果が大きく、チャット、分類、大量処理のルートでは `low` で十分なことが多くあります。
- **会話の途中で effort を変えると、多くのモデルでプロンプトキャッシュが無効になります。** effort はキャッシュされるプレフィックスの一部になるためです。エージェントごとに値を 1 つ決めたらそのままにし、ターンごとに調整しないでください。

effort を意図的にエージェント主導にしていない場所が 1 つあります。Claude の軽量な抽出経路（セッション圧縮、GVU、wiki 取り込み）で、`medium` に固定されています。機械的な抽出が、会話エージェントを `max` に上げたせいで高くなるべきではないからです。

### PTY プール

*（2026-09 に削除。）* 以前、effort は PTY プールの**セッションキャッシュキー**の一部で、異なる effort を求める 2 つの呼び出しには、別々のプール済みセッションが割り当てられていました。プールはなくなり、すべての spawn が自分自身の `--effort` フラグを持ちます。

## クロスプロバイダーフェイルオーバー

バックエンドが利用不可になった場合（レート制限、ダウン、エラー）、**FailoverManager**が自動的に次の利用可能なバックエンドに切り替えます：

```
Claude runtime：レート制限中（クールダウン：2分）
     |
     v
FailoverManagerがagent設定を確認：
  fallback = "codex"
     |
     v
互換 runtime にルーティング
     |
     v
Claudeクールダウン完了 → プライマリルーティングを復元
```

フェイルオーバーはユーザーに透過的です——どのバックエンドが処理しても、ユーザーはレスポンスを受け取ります。ヘルス状態はバックエンドごとに独立して追跡されます：

- **Healthy**：通常動作
- **Rate-Limited**：短いクールダウン（2分）
- **Error**：指数バックオフ
- **Non-Retryable**：手動対応が必要（認証失敗、課金）

## なぜ重要か

### ベンダーロックインなし

DuDuClawは単一AIプロバイダーに賭けません。Claudeが値上げすれば、CodexやGeminiにエージェントを移行できます。Geminiが強力な新機能を追加すれば、インフラを作り直さずに採用できます。

### 各タスクに最適なツール

コード生成はCodexの方が効果的かもしれません。複雑な推論はClaudeの方が強いかもしれません。データ分析はGeminiの大きなコンテキストウィンドウの恩恵を受けるかもしれません。Multi-Runtimeにより、正しいタスクに正しい頭脳をマッチングできます。

### レジリエンス

1つのプロバイダーがダウンしても、他が稼働し続けます。ローカル推論フォールバックと組み合わせることで、DuDuClawはどの単一プロバイダーの障害にも耐えられます。

### コスト最適化

プロバイダーごとに料金が異なります。`LeastCost`ローテーション戦略は、クエリの種類ごとに最も価格性能比の高いプロバイダーへルーティングできます。

## 他システムとの連携

### Codex の非対話承認（2026-09）

Codex 0.156.x は、すべての MCP ツール呼び出しを承認リクエストの背後に置きます。`approval_policy=never` ではそのリクエストが自動拒否され、`mcp_servers.<id>.default_tools_approval_mode` も `projects.<cwd>.trust_level` も結果を変えません。`--approve-for-me`（自動レビュー）がサポートされている非対話の抜け道で、`-s/--sandbox` とは同時に指定できません。エージェントのディレクトリは git リポジトリではないため、`--skip-git-repo-check` を常に渡し、stdin を閉じます。

**ケーパビリティのレベルごとに 1 組のフラグ**（2026-09-28 に変更。エージェントを制限する前に ReadOnly の行を読んでください）：

| `[capabilities]` のレベル | Codex のフラグ | エージェントにできること |
|---|---|---|
| ReadOnly（書き込みツールを付与していない、またはすべて拒否） | `-s read-only -c approval_policy=never` | 読み取りと推論ができます。書き込みは**実際にブロック**されます。**すべての MCP ツール呼び出しが自動拒否**されるため、その回のエージェントは duduclaw のツールを持ちません。spawn ごとに `warn!` を 1 件出力して知らせます。 |
| WorkspaceWrite（デフォルト） | `--approve-for-me -c approval_policy=never -c sandbox_mode="workspace-write"` | ワークスペース内に書き込めます。duduclaw の MCP ツールをすべて使えます。 |
| FullAccess（明示的な `computer_use = true`） | `--dangerously-bypass-approvals-and-sandbox` | 制限なし。オペレーターが明示的に付与した場合のみです。 |

2026-09-28 までは、ReadOnly でも `--approve-for-me` と `-c sandbox_mode="read-only"` を使っていました。これは**フェイルオープン**でした。`--approve-for-me` の自動レビューは workspace-write のサンドボックスで動くため、read-only の宣言は形だけのもので、ケーパビリティを制限したエージェントでもファイルを書けてしまいました。現在は実際に効力のあるフラグを渡しており、その代償が MCP ツールの面です。エージェントにツールを残したい場合は WorkspaceWrite を付与してください。Codex における ReadOnly は「何も変更してはならない」という意味で、ツールもそこに含まれます。

### Codex の MCP 認証情報：0.157 以降は `env_vars`、それより前は `argv` にフォールバック（2026-09-28）

Codex の spawn は、呼び出しごとの `-c` 設定オーバーライドで duduclaw の MCP サーバーを登録します。その登録が運ぶ値のうち 2 つは機密です。`DUDUCLAW_MCP_API_KEY` と `DUDUCLAW_AGENT_TOKEN` です。この登録（と以下の処理すべて）は ReadOnly を含む通常の Codex spawn で行われます（補助呼び出しを除く）。ReadOnly ではサーバーは登録されますが、上の表のとおり、Codex がそのサーバーへの呼び出しをすべて自動拒否します。

**認証情報を環境変数に置くだけでは済まない理由。** 2026-09-28 に実機で確認し、Codex のソースとも突き合わせました。Codex はすべての stdio MCP サーバー子プロセスに `env_clear()` をかけ、11 個の名前のデフォルト許可リスト（`HOME`、`PATH`、`SHELL`、`USER`、`LOGNAME`、`TERM`、`TMPDIR`、`TZ`、`LANG`、`LC_ALL`、`__CF_USER_TEXT_ENCODING`）と、設定で宣言されたものだけを戻します。gateway 自身のプロセス環境は MCP サーバーに届かないため、`Command::env()` だけでは何も渡りません。設定チャネルが唯一のチャネルです。

**DuDuClaw の現在の動作。** 設定チャネルには 2 つの形があり、その Codex バイナリが報告するバージョンから、バイナリごとに決めます。

| Codex のバージョン | 認証情報の形 | `ps` に見えるもの |
|---|---|---|
| **≥ 0.157.0** | `-c mcp_servers.duduclaw.env_vars=["DUDUCLAW_MCP_API_KEY", "DUDUCLAW_AGENT_TOKEN"]`。値は Codex の**プロセス**環境に設定し、Codex がそこから MCP 子プロセスへコピーします | 変数の**名前**のみ |
| **< 0.157.0**、またはバージョンを読み取れない | `-c mcp_servers.duduclaw.env.<K>="<value>"`（従来の動作） | 認証情報の**値** |

認証情報ではない項目（`DUDUCLAW_HOME`、`DUDUCLAW_PORT`、`DUDUCLAW_AGENT_ID`、`DUDUCLAW_INSTANCE`）は、どちらの経路でも `env.<K>="<value>"` の形のままです。機密ではなく、設定テーブルに残しておけば、プロセス環境が将来消去されても登録は機能するからです。「認証情報」かどうかは名前の末尾の完全一致で決めます。`_API_KEY`、`_TOKEN`、`_SECRET`、`_PASSWORD`（ASCII の大文字小文字を区別しない）で、`duduclaw-core` の spawn-env 許可リストが強制するのと同じ形の規約です。

**無条件ではなくバージョンで切り替える理由。** `env_vars` は `codex-cli 0.157.1` で動作を確認済みですが、このキーを受け付ける最小バージョンは未確認で、`RawMcpServerConfig` には `deny_unknown_fields` が付いています。知らないほど古い Codex では、設定の解析時に実行が落ちる（すべての spawn が失われる）か、認証情報が黙って捨てられる（エラーなしにエージェントが duduclaw のツールをすべて失う）かのどちらかです。そこで gateway はバイナリのパスごと、プロセスごとに 1 回だけ `codex --version` を実行し、`codex-cli X.Y.Z` を解析して、`0.157.0` 未満、解析不能、探査不能（spawn 失敗、非ゼロ終了、5 秒のタイムアウト）のいずれも「非対応」として扱い、`warn!` を 1 件出して従来の `argv` の形へフォールバックします。探査の失敗が spawn を失敗させることはありません。

**フォールバック経路にいる場合**（古い Codex、共有またはマルチテナントのホスト）は、露出が現実のものになります。コマンドライン引数は同じホスト上のどのプロセスからも読めます（`ps -ww`、`/proc/<pid>/cmdline`）。Codex CLI を 0.157.1 以降にアップグレードすれば、設定を変えなくても認証情報が `argv` から外れます。

**両方の経路に共通する緩和策。** `argv` に載せてよい env キーの集合は、既知の `DUDUCLAW_*` のブロックにテストで固定されており、新しい機密が黙って加わることはありません。すべてのキーは、展開前に素の TOML キーであることを検証され（`env_vars` 配列内の名前も含む）、すべての値は TOML のクォートが施されます。

### Codex：従業員のその他の MCP サーバー（2026-10-19）

Codex は `.mcp.json` を読まないため、Codex の spawn は duduclaw と同じ方法で従業員のその他のサーバーを登録します。`-c mcp_servers.<name>.…` のオーバーライドです（`<agent_dir>/.codex/config.toml` にも書きます）。以前は duduclaw だけが登録され、`.mcp.json` にある証券会社接続のようなサーバーは Codex では使えませんでした。ルール：

- `.mcp.json` を読めない・解析できない場合、その spawn は止まります（動作の変更：以前の Codex はこのファイルを読みませんでした）。ファイルがない、または DuDuClaw 自身のサーバーだけが載っている場合（チームの役割メンバーのスキャフォールドはまさにこの形）、従来どおり起動し、ゲートの実行も書き込みもしません。Codex の補助呼び出しはこの MCP 設定処理を省略し、前述の制限モードを使います。
- サードパーティサーバーがある場合は、Claude の spawn と同じくまず `.mcp.json` の spawn ゲートを実行します。拒否されると止まり、何も書き込みません。通過した場合はファイル内の DuDuClaw 自身の項目を書き換えることがあります（他の項目はそのまま）。Claude の毎回の spawn や gateway 起動時の修復と同じ処理です。
- サードパーティの stdio サーバーはすべて `duduclaw mcp-proxy --server <name> -- <command> …` として登録されます。常にそうします（Claude では `action_rules` があるときか読み取り専用レーンのときだけ）。Codex は `approval_policy=never` で動き、これらのサーバーは `default_tools_approval_mode = "auto"` で登録されるため、判断するのは proxy のサードパーティツールゲートです。リモートブリッジはそのまま登録します（自身で制御します）。直接の `url`／`type` 項目は取り除かれ、監査 `third_party_remote_entry_dropped` が記録されます。書き換えで包めない項目や、名前が素の TOML キーでない項目は登録されません。
- `.mcp.json` で DuDuClaw の名前（`duduclaw`、`duduclaw-pro`、`duduclaw-<instance>`）を使う項目が、gateway が作るサーバーを置き換えることはありません。
- サードパーティサーバー自身の環境変数（認証情報）は `argv` にも `.codex/config.toml` にも書かず、`<home>/tmp/mcp-proxy-env/`（0700 のディレクトリ）内のその spawn 専用で所有者だけが読めるファイルに置き、`DUDUCLAW_MCP_PROXY_ENV_FILE` がそれを指します。gateway は起動時に 15 分より古いファイルを削除します。そのため `.codex/config.toml` だけで手動で `codex` を実行すると、これらのサーバーは宣言された環境変数なしで起動します。`.codex/config.toml` は作成時点から所有者だけが読める状態で書かれ（一時ファイル＋リネーム）、既存のファイルもその権限に戻されます。`DUDUCLAW_MCP_API_KEY` は上の表のとおりです（0.157 以上は `env_vars`）。
- Codex は MCP 子プロセスの環境をクリアするため、読み取り専用レーンは `env.DUDUCLAW_LANE` として各サードパーティサーバーに渡されます。

### Grok とツールループ：従業員のその他の MCP サーバー（2026-10-20）

MCP サーバーを自分で登録する他のランタイムにも同じ穴があり、Grok ではサーバーが欠けるだけでは済みませんでした。現在はどれも Codex と同じ制御付きの書き換えを通ります。stdio サーバーは `duduclaw mcp-proxy` 経由、リモートブリッジはそのまま、直接の `url`／`type` 項目は取り除かれて監査に記録され、DuDuClaw の名前を使う項目は gateway 自身のサーバーを置き換えられず、英数字・`_`・`-` 以外を含む（または 64 文字を超える）名前は登録されません。

**Grok。** Grok 1.0.62 は作業ディレクトリの `.mcp.json` を自分で読みます（`grok inspect` が読み込み元として表示し、同梱のドキュメントにも書かれています）。従業員の場合それは `<agent_dir>/.mcp.json` なので、従業員のその他のサーバーはすでに Grok が proxy なしで起動していました。つまり `action_rules`、承認、読み取り専用レーンのどれも効かず、`url` 項目は直接接続されていました。Grok が読むのはそれだけではありません（`grok inspect` で確認、同梱の `07-mcp-servers.md`、`05-configuration.md` にも記載）。`<cwd>/.cursor/mcp.json`（Cursor 互換、既定で有効）、そしてディレクトリが git リポジトリ内にあるときは、リポジトリのルートまでの各階層の `.mcp.json` と `.grok/config.toml` も読みます。`<cwd>/.claude.json` や `.claude/settings*.json` の `mcpServers` は読みません。これらはどれも作業ディレクトリの `.grok/config.toml` より優先度が低いため、ランタイムはそこに現れるすべての名前をこのファイルに書くようになりました。従業員自身の `.mcp.json` で制御を通ったサーバーは spawn スコープの proxy（後述）として、それ以外（`duduclaw-pro` のような DuDuClaw 名の余分な項目を含む）は元の項目を隠す無効化された項目として書きます。存在するのに解析できない読み込み元があれば spawn を拒否します。従業員がもう載せていないサーバーのためにランタイムが書いた項目は削除し、管理者が手で追加した項目には触れず、spawn のたびに警告を記録します。従業員ディレクトリの `.cursor/` も `.grok/` と同様に従業員は変更できなくなりました。

**spawn 範囲の proxy（Grok）。** MCP 登録は永続ファイルに置き、上流の認証情報は spawn ごとの所有者専用ディレクトリに保存します。`duduclaw mcp-proxy --spawn-scoped` は `DUDUCLAW_MCP_PROXY_ENV_DIR` に対応するサーバーのファイルがなければ何も起動しません。CLI の終了時にディレクトリを削除し、起動時には 15 分を過ぎた残存ファイルを清掃します。Grok の補助実行は起動前に拒否され、社員の背景処理はサポートされたグローバル補助設定を使います。

**openai-compat、Direct API、ローカル推論。** この 3 つは 1 つのツールループ構築関数（`claude_runner::build_mcp_tool_registry`）を共有しており、これまでは DuDuClaw のサーバーと `agent.toml [[mcp.external]]` だけをマウントしていました。現在は `.mcp.json` のサーバーもマウントします。どれも制御付きの書き換えの結果どおりに、gateway の環境ではなくエージェント CLI 用の許可リストの環境から起動するため、gateway の環境にある他ベンダーのキーがサードパーティサーバーに届くことはありません。この経路では何もディスクに書きません。読み取り専用レーンでも `DUDUCLAW_LANE=explore` 付きでマウントされ、proxy を通るのは読み取り専用のツールだけです（Claude のレーン内 spawn と同じ）。`agent.toml` の外部サーバーは、制御するものがないためレーン内では引き続きマウントしません。両方のファイルで宣言されたサーバー（同じ名前、または同じコマンドと引数）は、ツール許可リストと `secret://` 参照を持つ `agent.toml` 側から 1 回だけマウントされます。

**失敗時は拒否。** 第三者サーバーがある場合、設定を読めない、解析できない、または spawn ゲートが拒否した実行は停止し、フェイルオーバーもしません。Grok の設定を書き込めない場合も起動を拒否します。openai-compat は応答を拒否し、Direct API とローカル推論はツールなしで応答します。Grok は読み取り専用レーンを拒否します。

**未検証。** 実際の `grok -p` の対話（サインイン済みの Grok が必要。設定は一時的な `HOME` で `grok mcp doctor` と `grok inspect` を使って確認）。いずれかのランタイムの実モデルがサードパーティツールを実際に呼ぶこと。承認が必要なサードパーティツールが CLI の制限時間内に承認を待てるか。

### 作業ディレクトリのオーバーライドはすべての CLI バックエンドに届く（2026-09-28）

呼び出し側は、ある spawn をエージェント自身のディレクトリ以外の場所で実行するよう求められます。現在の呼び出し側はチームコンポーザー（team composer）だけで、ロールメンバーを従業員のワークスペースに置きます。こうすると、使い捨ての scaffold がメンバーの終了と同時にガベージコレクトされても、メンバーが書いたファイルは残ります。

対応する CLI バックエンドは共通のヘルパーで作業ルートを決定します。要求されたパスが実在しなければ警告して社員ディレクトリへ戻ります。OS のサンドボックスも同じルートを使います。

オーバーライドが動かすのは**作業ディレクトリだけ**です。エージェントの ID（MCP サーバーの登録、ツールが認証に使うエージェント ID、エージェント自身の設定）はエージェントのディレクトリに残ります。

バックエンド固有の影響があります。見つけてもらうのではなく、先に書いておきます。

- **Grok** は、MCP 登録（`.grok/config.toml`）とサンドボックスプロファイル名（`.grok/sandbox.toml`）の両方を、エージェントのディレクトリではなく作業ディレクトリから解決します。そのためオーバーライドされたルートには両ファイルのコピーが置かれ、そうしなければメンバーはツールなし、解決できないサンドボックスプロファイルで spawn されます。既知の制限：この 2 つのファイルはディレクトリをキーにしているため、1 つのワークスペースを共有する 2 つの Grok ロールメンバーは、互いに宣言済みの env ブロックを上書きします。command/args の部分はメンバー間で同一で、MCP 子プロセスが実際に認証に使うのはプロセスごとの ID なので、影響範囲は宣言されたブロックだけです。

### フォールバックのランタイムが受け取るモデル（2026-09）

別のランタイムへフェイルオーバーするとき、元のモデル id をそのまま転送することはありません（Codex エージェントの `gpt-5.4` を Claude CLI に渡してはいけません）。FailoverManager は、順序のある 4 つの分岐でフォールバック先のモデルを解決し、どれも当てはまらなければ spawn を拒否します。

1. `agent.toml [model] fallbacks` のうち、そのファミリーが確実にフォールバック先のランタイムに属する最初のエントリー（`openai/gpt-5.4` のような修飾付き id は、Direct-API チェーンが使うのと同じ `split_model_id` の規則で修飾を外します）。
2. 元のモデル。すでにフォールバック先のランタイムに属している場合。
3. そのランタイムのカタログ既定値（`fallback_models[0]`。ライブ探索が失敗したときにダッシュボードが提示するのと同じリスト）。
4. いずれでもなければ、この試行は `no model configured for fallback runtime <name>` として失敗扱いになり、spawn しません。

置き換えが起きるたびに、`agent / from_runtime / to_runtime / from_model / to_model` を `warn` レベルで記録します。

**judge と evaluator の実行は通常の会話のクロスファミリー・フェイルオーバーには入りません。** 補助実行の入口は明示した `[dispatch] judge_provider`／`judge_model` を保ち、補助実行モードに非対応のプロバイダーを拒否します。Codex は制限モードを使います。明示した Codex judge の拒否では理由付きで判定を失敗させ、既定の judge で再試行しません。他のプロバイダーは既存の縮退方針を維持します。再試行も対応する補助実行モードに限定します。指定のない社員の補助呼び出しでは、非対応の社員ランタイムを実行前に社員の `[runtime] utility_provider`、設定ファイルに実際に書かれた全体の `[runtime] utility_provider` の順に解決し、どちらもなければスキップします（v1.84.0）。全体のプロバイダーが非対応なら拒否します。

- **Account Rotator**：全プロバイダーの認証情報を管理、クロスプロバイダーフェイルオーバー付き。
- **Confidence Router**：runtimeレイヤーの下位に位置——ローカル vs. クラウドを決定。Runtimeレイヤーは*どの*クラウドかを決定。
- **CostTelemetry**：プロバイダーごとのコストを追跡し、情報に基づくルーティング決定を支援。
- **MCP Server**：ツールはサポートする全バックエンドに公開（ClaudeはネイティブMCP経由、その他はツールインジェクション経由）。
- **Agent Config**：各エージェントの`agent.toml`がruntimeの優先設定とフォールバックチェーンを指定します。

## プロバイダー対応アカウント（WP-A、2026-09）

`accounts.add`——ダッシュボードのアカウントページと OOBE の「AI Runtime 認可」ステップの両方が使う gateway RPC——は、既存の `type`（`api_key` | `oauth`）に加えて `provider` id を受け付けるようになりました。受け付けられる id はプラットフォーム共通の provider 対照表（`duduclaw_core::provider_env::KNOWN_PROVIDER_IDS`）に列挙されたもの——`anthropic`、`openai`、`gemini`/`google`、`deepseek`、`minimax`、`groq`、`together`、`mistral`、`openrouter`、`xai`、`qwen`——です。`provider` を省略すると `"anthropic"` がデフォルトになるため、この機能より前に書かれた呼び出し元は一字一句変わらず動作します。未知の id は黙って受理されず、拒否されます。

認証情報は引き続き `config.toml` の `[[accounts]]` 配列に書き込まれますが、provider が付与されるようになりました。

```toml
[[accounts]]
id = "openai-prod"
type = "api_key"
provider = "openai"
api_key_enc = "..."          # anthropic は従来通り anthropic_api_key_enc フィールドを使う
```

`AccountRotator::select_for_provider`——Claude CLI パスとクロスプロバイダー Direct-API の `duduclaw-llm` provider パスが以前から使っていたのと同じ選択ロジック——がこのフィールドで厳密にフィルタするため、この方法で追加された OpenAI／Gemini／xAI／DeepSeek…のキーは、Anthropic アカウントとまったく同じローテーション・予算管理・クールダウンの仕組みに乗ります。読み取り側で provider ごとのコードパスを新設する必要はありませんでした。`accounts.list` と `accounts.budget_summary` はどちらも各アカウントの `provider` を返すようになり、ダッシュボードのアカウントページでどのベンダーのキーかが分かるようになりました。`AddAccountDialog` にはプロバイダー選択と、各プロバイダーのキー形式のヒント、ベンダー自身のコンソールで API キーを取得するリンクが追加されています。

## サブスクリプションログインのリスク開示

オーナーの決定（2026-10-16）：サブスクリプションログインの機能はそのまま残します（setup-token の取得、OAuth アカウント、ホストログインの自動採用、ローテーション、CLI のワンクリックログイン）。変えたのはリスク開示です。

**通知の内容。** Anthropic の[法務・コンプライアンスページ](https://code.claude.com/docs/en/legal-and-compliance)には、サードパーティの開発者が自社アプリで Claude.ai ログインを提供すること、Free・Pro・Max プランの認証情報でユーザーの代わりにリクエストを中継すること、Claude.ai の認証情報やセッショントークンを収集・保存・仲介することは認められないと書かれています。認められているのは、自分のサブスクリプションで改変されていない Claude Code にサインインすることで、Pro/Max の利用上限は通常の利用を前提としています。消費者向け利用規約では、アカウントを他人に利用させることも禁止されています。Anthropic は事前の通知なく執行できるとしています。アカウント停止は報道やユーザーからの報告で、Anthropic の公式発表ではありません。通知は、規約と衝突する DuDuClaw での使い方を具体的に挙げます。1 つのサブスクリプションで他の人（チャネルの顧客）に対応すること、複数のサブスクリプションをローテーションして上限を避けること、DuDuClaw にトークンを保存させることです。OAuth トークンでの `claude -p` は技術的にはまだ動くため（v1.66.0）、通知は「ブロック」とは書きません。

**ベンダーごとの表示。** 上の全文は Claude のログインと Claude のアカウントで表示します。Codex、Grok のログイン（およびアカウント追加で Anthropic 以外の provider を選んだ OAuth の経路）では、同じチェックボックスとともに、そのベンダー自身の説明と規約へのリンクを表示します。OpenAI は上記の Sign in with ChatGPT プログラムの要点（オープンソースと承認を受けた商用パートナー、トークンはローカルに保存）とその規約へのリンク、xAI は立場が不明で規約が適用されることを示します。不明な provider には、ベンダー名もリンクもない注意を表示します。どの文もベンダーのページに対応しており、一次情報が見つからなかった以前の「Google は 2026-03 以降サーバー側でブロック」の文は削除しました。ベンダーの対応表は `duduclaw_core::subscription_risk::vendor_policy`（gateway、CLI）と `web/src/lib/subscription-risk.ts`（ダッシュボード）にあります。

**表示される場所。** CLI ログインモーダル、案内付き QR コード設定ウィザード、アカウント追加の OAuth Token の経路では、認証情報を扱う前にチェックボックス付きの全文を表示します。ようこそページの Claude サブスクリプションのカード（「サインイン済み」カード、つまりホストログインの自動採用の場合も含む）、runtime 設定カードのサインイン行、アカウントページのサブスクリプション用カード、ワンクリック CLI の選択画面、CLI 認証情報の一覧、エージェント編集の API モードがサブスクリプション CLI のとき、アカウントプールにサブスクリプションアカウントが入っているときには、規約へのリンク付きの 1 行の注意を表示します。

## まとめ

AI領域はマルチプロバイダーです。単一CLIの上に構築するのは、単一OSのためだけにソフトウェアを書くようなもの——動くけど、いつか動かなくなります。`AgentRuntime` traitが差異を抽象化し、DuDuClawがClaude、Codex、そしてOpenAI互換エンドポイントを交換可能なバックエンドとして扱えるようにします。エージェントは常に、利用可能な最良の頭脳を得られます。

## 実行ステップの上限

実行ステップは別に設定します。グローバル `[runtime] default_max_turns` の既定値は **50**、`max_turns_limit` は **200**（整数 **1〜10000**）です。従業員の `[runtime] max_turns` は **1** からグローバル上限まで指定でき、省略時はグローバル既定値を使います。**0 は無制限ではありません**。不正または読み取れない設定は制限付きの既定値に戻し、従業員・設定値・適用上限ごとに重複を除いて警告します。上限超過は実行時に補正し、ダッシュボード保存時には拒否します。増加には管理者権限が必要です。Owner は減らせますが、空欄に戻して既定値を継承する結果増加する場合も管理者が必要です。2 つのグローバルキーの変更も管理者のみで、既存の設定コミットと監査経路を使います。画面では時間上限の隣に表示します。ステップ増加は使用量と実行時間を増やす可能性があります。Claude のチャット、バックグラウンド実行、ターミナルチャットに適用し、保護モードは ネイティブ Linux 保護モードが対応するまで 50 のままです。OpenAI 互換ツールループは従業員が明示した `max_turns` を使い、省略時は 10 回を維持します。使い切ると専用のステップ上限エラーを返します。無人の Claude／Grok 実行では対話型の質問ツールを無効にします。Claude のシステムプロンプトは上限に近づいたら進捗をまとめて終了するよう伝えます。主動チェックの独立した `[proactive] max_turns` は **1〜64** を受け付けます。

Web チャットは対象従業員の実効単回実行タイムアウトに、配信のための 30 秒を加えて待機します。ゴールの `timeout_secs` は **30 秒**から `min(max_timeout_secs, 3600)` まで指定でき、各ラウンドもその上限に従い、最大 1 時間です。

## 進展なしの制限と再開

全体の `[runtime] default_idle_timeout_secs` は既定 **900 秒**です。従業員の `[runtime] idle_timeout_secs` で上書きでき、省略時は全体設定を継承します。**0 は無効化**、それ以外は **60 秒から `max_timeout_secs` まで**です。全体値を省略し、上限が 900 秒未満なら既定値も狭まります。読み取り・解析エラー時は組み込みの 900 秒を使います。従業員の制限を延長・無効化する場合、または削除により長い既定値や無効化を継承する場合は管理者権限が必要です。短縮には不要です。ダッシュボードでは従業員編集と全体の実行制限で、時間上限の隣に表示します。

Claude のチャットとバックグラウンド実行、Codex JSONL、および OpenAI 互換 API の SSE 応答では、指定時間内にイベントが届かなければ停止します。ツールのイベントも進展に含みますが、90 秒ごとの定期通知は含みません。未完了のツールがある場合は最後のツール名を表示します。Grok と非ストリーミングの OpenAI 互換リクエスト／ツールループには、この経路で利用できるイベントストリームがないため総時間上限を使います。

ステップ上限（`max_turns`）、総時間切れ（`timeout_total`）、進展なし（`timeout_no_progress`）はそのターンを終了し、アカウントの健全性を下げず、別のアカウント・モデル・ランタイムで再実行しません。ツールが実行済みでも「制限時間内に最終回答が生成されなかった」と伝えます。通常のチャネル利用者には取得済みの部分回答を先に届け、停止通知を添えます。部分回答を会話のアシスタントターンに保存し、「続けて」でその文脈を引き継げます。Claude のステップ通知には適用済み上限を表示します。公開訪問者には一般的な安全メッセージと参照番号だけを表示し、部分回答、ステップ数、理由コード、運用上の案内は表示しません。

失敗通知の末尾には固定の小文字の理由コードとターン参照番号の先頭 8 文字を付けます。監査記録は `reason_code` と完全な `reference_id` を保持し、バックグラウンドではディスパッチ実行の参照番号を使います。Goal loop はこれらを `max_turns`、`timeout_total`、`timeout_no_progress` として一時停止し、インフラ障害回数に加算しません。
