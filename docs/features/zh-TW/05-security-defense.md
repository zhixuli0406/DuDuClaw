# 安全防線

## 尚未發行的原生 Linux 隔離整合

受保護入口保留已驗證的原始 WebChat／頻道使用者與憑證版本，啟動前重查即時權限。背景排程、提醒、心跳及目標工作現在須綁定紀錄擁有者、確切工作內容與已保存的儀表板 Admin 核准：24 小時內決定，授權最多 30 天。待核准時延後執行，不消耗重試。排程不更新原始憑證版本；只有已驗證使用者儲存心跳設定時，可針對失效授權另提新核准。員工委派從原始、仍有效的已驗證執行取得授權，身分缺漏即拒絕。

綜合就緒檢查新增 PTY 與快取的獨立接線，仍要求同一安裝世代的短效證據。每次執行各自登記並撤銷對外連線身分，同時保留原始對話回合。其他套件仍須提供正式就緒證據；完整 gateway／CLI 編譯、root 驗收及真實 Claude／供應商驗收尚未完成。缺少或失效的證據仍會阻擋受保護 TEAM 工作，不能視為已啟用或已驗收的隔離版本。
Round 6 採用 v1.80.0 延期方案：受保護 TEAM 的 `fork_run`、`merge_or_select`、`terminate_branch` 依設定顯示繁中／英文／日文的下一版開放訊息；一般安裝維持原行為。查詢與已記錄清單比較仍經主機驗證擁有者，未量測的費用回傳 unavailable／null，不顯示成零元。子分支能力、帳號、父預算與不可變成果套用尚未接齊，既有複製／佇列／指標 CAS 元件保留在拒絕後方。A 就緒 hook 排除這三項後檢查其餘已安裝 producer，缺少簽章 helper 仍不會就緒；其他元件閘門、整合編譯及原生／provider 驗收分別追蹤。Round 5 的可選工作區 selector 與保留目錄 fd 合約不變：root 從 H 員工儲存區重開並核對 UID／device／inode 後掛載到 `/work`。

分支狀態、輸出比較與費用查詢會先確認分支擁有者；資料庫讀取失敗不再回傳空的成功結果。尚未發行的隔離轉接把派工入列及部分探索控制接回原本的呼叫者、目標員工與背景准入檢查。隔離環境的探索狀態只讀主機保存的紀錄，不讀取員工產出目錄，產出驗證會標示為不可用。入列成功或任務標記取消，都不代表隔離程序已啟動或退場。程式、Office 建立／抽取與有界程式碼索引已補上條件式簽章執行協定，以及具授權檢查的非同步工作查詢／取消。Office 讀取輸入快照，產出不覆寫既有檔案；缺少簽章、執行設定或工作區授權時拒絕執行。硬體查詢不啟動外部探測程式，模型查詢明示限內建目錄。探索下載會以主機發布的檢查點清單驗證指定檔案，隔離下載上限為 2 MiB；舊檢查點沒有清單時拒絕。分支執行／發布／取消、瀏覽器錄製、正式簽章封裝與原生完整驗收仍未完成，受保護 TEAM 啟動仍維持阻擋。

### 個人專屬員工的資料可見範圍（尚未發行）

僅限受保護模式：個人專屬員工的私人資料（對話與執行紀錄、記憶、SOUL.md／CONTRACT.toml 等設定檔、它自己的 Wiki，以及它的工作紀錄：任務與任務明細、動態、時間軸、待決事項、畫布與審核內容）只屬於它的擁有者。

- **團隊授權：**主管不再透過部屬的綁定取得部屬個人專屬員工的使用權限或團隊對話紀錄；共用員工維持原本的團隊授權。
- **管理員讀取：**不是擁有者的管理員必須先完成新的身分確認（與遷移審核、隔離連線帳號相同的密碼加雙因素驗證，5 分鐘內有效），並在請求中帶入 `step_up_csrf`。每次讀取都會寫入稽核紀錄，記下管理員、員工、擁有者與資料類別；沒有完成身分確認時，請求會被拒絕並說明原因。管理員的跨員工清單與搜尋（對話、執行紀錄、任務、動態、時間軸）不會列出不屬於自己的個人專屬員工。審核中心只顯示卡片的員工、類型、狀態與時間；完成身分確認後開啟單張卡片才看得到內容，並寫入稽核紀錄。開啟或修改它的單一任務也需要同樣的身分確認。附件下載沒有身分確認流程，只限擁有者。總數與統計（任務分頁、動態、流程指標）只計算讀取者看得到的項目；關於個人專屬員工的控制台即時更新只送給它的擁有者。
- **決定與交辦：**個人專屬員工的審核卡（包含郵件寄送確認）由擁有者決定。不是擁有者的管理員只能在控制台以同樣的身分確認與 `step_up_csrf` 決定，每次決定都會寫入稽核紀錄；沒有完成身分確認時，拒絕訊息會說明需要先確認身分。聊天通道（按鈕、文字回覆、Telegram 小程式）無法進行身分確認，只有擁有者本人已驗證的帳號能決定。在控制台交辦工作給個人專屬員工（新任務、改派、目標、共編計畫）只限擁有者，管理員也會被拒絕。
- **AI 工具：**其他 AI 員工不能對個人專屬員工使用 `agent_update`、`agent_update_soul`、`agent_remove`，以及其他指定別的員工的工具（狀態、演化設定、技能、該員工的 Wiki、信箱、人機共駕身分、排程、提醒、回饋、稽核軌跡、可靠度、成本、以 `reports_to` 調整組織位置）；也不能交派工作給它（`spawn_agent`、`send_to_agent`、`create_task` 的步驟、帶 `assigned_to` 的 `tasks_create`／`tasks_update`、探索任務）、讀取它的回覆（`check_responses`）、它的任務、動態或計畫（指定員工，或指定任務／計畫編號），或從其他金鑰讀取它的任務（`task_status`），也不能指定它的記憶命名空間。同一位擁有者的另一位個人專屬員工仍可交辦工作給它。`list_agents` 完全不會把別人的個人專屬員工列給其他 AI 員工。個人專屬員工自己，以及它建立的臨時子員工，仍可照常操作自己。擁有者請在控制台管理。
- **更多涵蓋範圍：**同樣的「擁有者，或管理員完成身分確認」規則也涵蓋設定檔匯出、學到的經驗法則、Wiki 可信度紀錄、員工自己的技能檔、它的郵件（稽核類別 `mail`）、共編計畫與計畫步驟、待審的設定檔變更，以及執行分支。計畫、郵件與執行分支的清單不會列出讀取者不擁有的個人專屬員工。所有交辦途徑都只限擁有者：改派、在控制台委派（包含等待回覆）、目標與探索任務、計畫步驟、子任務與相依任務，以及由伺服器挑選執行技能的員工。其他 AI 員工也不能透過 `tasks_claim`、`tasks_renew`、`tasks_complete`、`tasks_block`、`activity_post`、`capability_request`，或任務與目標的連結碰到它的任務。全員清單（帶 `*` 的 `tasks_list`、`activity_list`，以及 `goals_list`）不會列出它的項目，總數也一致。所有種類的控制台即時更新都依同樣規則過濾；沒有指名任何員工的更新，不會送給有被隱藏個人專屬員工的讀取者，只有一小份已知不含員工資料的更新例外。不是管理員的讀取者，在控制台與聊天通道上，看到別人的個人專屬員工時得到的回覆，和該員工不存在時相同。用戶端代號與員工代號相同的外部 MCP 金鑰會被拒絕。

- **預設拒絕（新的預設）：**在受保護模式下，凡是涉及別人個人專屬員工的操作，除非明確允許，一律拒絕；管理員也一樣，管理員身分不再自動放行。不是擁有者的管理員仍可以做的只有下列管理動作，每一次都會寫入稽核紀錄：查看它的名稱與狀態（`agents.status`、職務組合名稱、頭像，以及員工清單；清單只顯示它的名稱、擁有者與狀態）、暫停與恢復它（包含背景自主運作），以及墓碑化、還原、認領與清除流程（各自維持原本的規則）。它的私人資料與設定、身分，仍需上述的管理員身分確認，每次都會留下稽核紀錄。交辦工作給它只限擁有者，沒有身分確認的例外。這包括控制台對話、排程、提醒、心跳執行、持續職責、技能合成與自建技能生成、把它的工作移交給其他員工、分享它的技能，以及停止或接手它正在進行的電腦操作。觀看該電腦操作需要身分確認。資料匯出一律不含別人的個人專屬員工；先前建立且包含這類員工的匯出，現在無法下載。即時系統紀錄無法逐行過濾，因此有被隱藏的個人專屬員工時不提供。所有清單都不會列出這類員工的項目。排程與排隊中的工作在執行前，會依目前的擁有者再檢查一次。不是為擁有者建立的排程、提醒或排隊請求（包含這次變更前建立的，以及沒有建立者紀錄的），會在那時被拒絕；被拒絕的排程執行會記為失敗，排程交辦也會暫停。
- **聊天頻道與排程工作：**在任何聊天頻道或網頁對話中，用「@」呼叫或用「/交辦」（`/assign`）指派別人的個人專屬員工都會被拒絕，管理員也一樣；對話的預設員工也不例外。擁有者若替它開啟 `[channels] public_trigger`（公開呼叫），其他人仍可和它對話，但只有擁有者能指派工作。沒有用「@」而直接進到它的對話，除非傳訊者是擁有者本人（已驗證的頻道帳號），隔離執行環境會拒絕。**版本說明：**個人專屬員工上沒有記錄建立者的舊排程與提醒，到了執行時間會停止，不再執行，需要由擁有者重新建立。排隊中的工作若記錄的交辦人不是擁有者，不論它聲稱由哪位員工送出，都會在執行前拒絕。管理員調整某個資料來源的授權名單時，看不到的員工原有授權會保留不變，變更紀錄也不會列出它。

- **墓碑化之後：**被移除的個人專屬員工，資料會封存保留 90 天，隱私保護也持續同樣久：別人的清單依然看不到它；不是擁有者的管理員要讀取它的對話、記憶、時間軸或郵件，仍需完成身分確認並留下稽核紀錄；其他 AI 員工依然被拒絕。只有封存資料被清除，或這個代號由其他員工認領後，它才不再屬於任何人。
- **安裝技能：**把技能安裝到某位員工（`skills.install` 的 `scope` 指定員工）屬於設定變更：要安裝到別人的個人專屬員工，管理員需完成身分確認，並留下稽核紀錄。直接安裝或核准後的安裝申請，只會裝進目前存在、未被移除或保留的員工；不會替已移除或不存在的員工建立資料夾。安裝到個人專屬員工的申請，只有由它的擁有者提出才會在核准後執行，並留下稽核紀錄。
- **墓碑化後的審核卡：**移除員工時，它所有尚未使用的審核卡都會作廢，包含已核准但還沒用掉的。受保護模式下建立的審核卡會綁定員工當下的版本（incarnation），員工還原後就不能再用。
- **Google 服務信箱：**任何曾被 DuDuClaw 帳號用來登入的信箱（包含後來改掉的、帳號已移除的）都不能設為服務信箱；工具使用到這類信箱時也會被拒絕。儲存清單需要管理員完成雙因素身分確認，並在變更前寫入稽核紀錄。每次更改登入信箱都會留下稽核紀錄。從未屬於任何 DuDuClaw 帳號的信箱無法辨識，請仔細確認清單。
- **對外連線：**員工的網路存取不會連到這台主機自己的位址（包含公開位址）。位址清單在啟動時讀取，每 30 秒更新；連續 10 分鐘無法更新時，連線一律拒絕。

擁有者紀錄來自 `users.db`，以及（資料仍在保留期內的已移除個人專屬員工）它的移除紀錄：每次控制台請求最多讀取一次；只有在權限版本（每次歸屬變更都會更新）與資料檔都沒有變動時，才沿用先前讀到的結果。讀不到就拒絕；只針對員工自己的操作不需要讀取這份紀錄。未啟用受保護模式的安裝不受影響，只有一點例外：交辦工作時，前後帶空白的員工代號現在會被拒絕，不再自動去除空白。控制台頁面尚未提示管理員進行身分確認。

## v1.80.x 已發行

非管理員成員（Employee、Manager）在側欄、對話篩選、指令面板、WebChat 的 `@` 建議與其他員工選擇器，只會看到 `agents.callable` 明確標示可選取的員工。主 AI 員工預設不顯示，除非該回應明確允許選取。只有 `agents.callable` 依即時 Admin 身分確認 `unrestricted: true` 後，才顯示完整名單，包含個人版的本機管理員。所有帳號在初次載入或讀取失敗時都不顯示員工。頁面可見時每 60 秒、恢復可見及開啟選單時會刷新權限；刷新期間保留同一身分已確認的名單，失敗則清空。檔案與設定選擇器另須直接存取權，團隊呼叫權不會增加檔案或設定權限。新對話仍由伺服器決定指派對象。這次 dashboard 過濾不變更 RPC 授權。

## `code_map` 只掃描員工自己的目錄（v1.81）

v1.81 以前，`code_map` 可以掃描 MCP server 讀得到的任何目錄（預設是它的工作目錄），呼叫者因此能替主機上任何位置的原始碼建地圖、讀到其中的函式簽章。現在：

- 只有辨識得出的 AI 員工可以呼叫：共用的內部金鑰需要 `DUDUCLAW_AGENT_ID`，員工專屬金鑰需要對應的 `agents/<id>/agent.toml`。外部金鑰、管理者金鑰與只帶 scope 的單獨模式金鑰會被拒絕並附上說明；`code_map` 也列入「替員工動作的工具」，這些呼叫者的 `tools/list` 不再列出它（單獨模式的清單從 24 個變成 23 個）。
- `root` 預設是員工自己的目錄，相對路徑也從那裡解析；含 `..` 會被拒絕；解析後的目錄必須落在資料檔工具同一組根目錄內（`<home>/agents/<id>`、其 `attachments`、`<home>/attachments`、`config.toml [files] allowed_roots`）。
- 每個檔案都從審核過的根目錄用檔案描述子逐層開啟（每一層 `O_NOFOLLOW`）。符號連結、非一般檔案、硬連結數超過 1 的檔案、超過大小上限的檔案一律略過；內容從檢查過的那個描述子讀出。走訪不會跨越掛載點：每一層的 `st_dev` 必須相同，Linux 另外比對核心的掛載 id，所以把同一個檔案系統上的其他目錄 bind mount 進來（`st_dev` 相同）也會被拒絕。Linux 在核心支援時使用 `openat2`（`RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS | RESOLVE_NO_XDEV`），並一律比對 `statx` 的 `STATX_MNT_ID`（或 `/proc/self/fdinfo` 的 `mnt_id`）；兩者都拿不到掛載 id 時拒絕掃描。macOS 依靠 `st_dev` 與逐層不跟隨連結的開檔；Windows 拒絕所有 reparse point（符號連結、junction、磁碟區掛載點）與多重連結的檔案。
- 每次拒絕都會在 `tool_calls.jsonl` 寫一列（`refused: true`、要求的根目錄與原因），不記錄其他內容。

## 誰可以建立員工（v1.81）

`[permissions] can_create_agents` 現在只有 `main` 員工預設為 `true`。其他角色、以及角色無法辨識的員工，沒寫這個鍵就是 `false`。MCP 權限閘門對 `create_agent` 與 `spawn_ephemeral` 套用這個實際值，所以從沒寫過這個鍵的非 main 員工不能再建立員工。明確寫出的設定不論 `true` 或 `false` 仍然優先。

- 新員工：儀表板與 `duduclaw agent create` 只對 `role = "main"` 寫 `true`；evaluator 範本與付費團隊套件對所有非 main 角色寫 `false`。
- 員工透過 MCP `create_agent` 建立的員工一律 `can_create_agents = false`。只有目前的 main 員工、且它的 `can_create_agents` 開啟時，才能在那裡建立 `role = "main"` 的員工；其他呼叫者在寫入任何東西前就會被拒絕。
- v1.68 的開機遷移不再把非 main 員工的 `can_create_agents = false` 改成 `true`。
- `agents.update` 的管理員限定欄位檢查也比對同一個實際值，非管理員的 Owner 不能再靠在缺少的鍵上寫 `true`，替非 main 員工開啟建立權限。

**行為變更：** `agent.toml` 沒有 `can_create_agents` 鍵的非 main 員工，v1.81 以前可以建立員工，現在會被拒絕。若要保留，請由管理員在儀表板「工具與權限」開啟。

## 團隊派工沿用員工的限制（v1.81）

- **規劃封包的 `tool_scope` 只能縮小執行角色的工具。** 非空的 `allowed` 會把執行角色限制在這些工具（加上 `team_handoff`）；只要列出員工本身沒有的工具，該次派工就會被拒絕，並寫入 Warning 等級的 `team_tool_scope_escalation` 稽核紀錄。`denied` 會從執行角色的工具中移除，並加入成員的 `denied_tools`。角色成員（以及一般臨時助手）也會繼承員工的 `approval_required_tools`、`irreversible_tools`、`maybe_irreversible_tools`、`action_rules`、`policy`、`egress_guard` 與 `scoped_tools`，與員工面對相同的核准。`grant_ttl_secs` 不繼承，因為員工較長的期限會延長成員的授權。
- **沿用的核准設定不會擋下團隊交接。** 對角色成員，MCP 閘只在 `team_handoff` 略過沿用的 `action_rules`、`policy`、核准清單與 `scoped_tools` 的授權要求（`ephemeral::is_role_member_intrinsic_call`；需要完整的 `[team_member]` 紀錄，且 parent 與 `ephemeral.toml` 一致）。`scoped_tools` 會完整複製（含萬用字元），所以萬用字元涵蓋的其他工具仍需授權。`allowed_tools`、明確的 `denied_tools`、`[permissions]` 與對外傳送防護照常適用。

## 客戶公司識別（v1.80.0）

公司名稱與標誌獨立於經簽章驗證的經銷商品牌。`company.get`、`company.update` 明確要求管理員；`company.update` 只接受名稱與選填的移除標誌操作，拒絕舊的 `logo_base64` 欄位。公司名稱拒絕控制字元、換行分隔字元與 Unicode 格式字元（`Cf`，包含雙向覆寫與隔離控制字元）。更新時在既有設定寫入鎖內再次查核目前身分。`company_info` 稽核記錄操作者、方法與結果，不記錄圖片或名稱。進階設定的導覽與路由也限管理員，搬動控制項不會放寬原有 RPC 權限。

標誌僅透過 `POST /api/company/logo` 上傳，內容為不超過 1 MiB 的原始 PNG、JPEG 或 WebP 二進位檔。通過來源 IP 限流後，端點在讀取內容前驗證 `Authorization: Bearer` access token 並即時重查管理員帳號，未登入或未授權時以 401／403 拒絕，不讀取請求內容；不接受 Cookie 驗證。此路由的 `DefaultBodyLimit` 與串流讀取的硬限制都執行大小上限。每個帳號、每個 TCP 來源 IP 各限 60 秒內六次上傳。IP 限流先於 JWT 驗證，超額時直接回 429，不逐筆產生稽核，避免未登入請求灌滿稽核紀錄；通過此限流的請求與結果才會稽核。帳號限流則在 JWT 與即時管理員驗證之後執行。不採信轉送標頭，因此代理後方的用戶共用該代理 IP 的額度。內容讀取逾時為 30 秒，同時最多兩項上傳工作。全域 WebSocket 訊息上限維持 1 MiB。

宣告的 Content-Type 必須符合實際檔頭。gateway 檢查完整圖片容器，拒絕尾隨附加內容、SVG、GIF 與動畫；在任何解碼器初始化前（包含檔頭與尺寸讀取）就套用 4096 × 4096 尺寸限制與 64 MiB 記憶體上限，再重新編碼成移除中繼資料的 256 × 256 以內 PNG 縮圖。圖片以內容雜湊命名、原子方式發布，設定引用透過既有鎖定 config commit 流程儲存，保留鎖內管理員重查與稽核。

公開 `/api/company` 只顯示公司名稱與標誌網址。`/api/company/logo/{sha256}.png` 僅接受固定小寫雜湊檔名。讀取器只開啟一次檔案（Unix 使用 `O_NOFOLLOW`），在檔案描述符上確認是一般檔案、連結數恰為一且大小符合限制，再從同一描述符有限量地讀取；PNG 驗證也在解碼器初始化前套用 256 × 256 尺寸與 1 MiB 解碼記憶體上限；通過內容與雜湊檢查後，才以 `image/png`、`X-Content-Type-Options: nosniff` 與一年 immutable 快取回應。公開公司請求依 TCP 連線來源限流。移除標誌只停止目前的顯示，舊圖片仍供快取頁面及邀請信使用；這不是私人檔案或資料刪除功能。邀請信 HTML 會跳脫公司名稱，標誌網址只使用已驗證邀請網址的來源與路徑前綴，不改員工權限或經銷商簽章檢查。

此變更的 gateway 測試與真實瀏覽器／寄信驗收仍需在指定建置、測試環境執行；程式實作不代表已通過平台或外部服務驗收。
所有建置的管理功能版本以有效授權為上限。`DUDUCLAW_EDITION` 與嵌入主程式的版本設定都只能縮限權限；要求升級時會忽略該值，每個來源每個行程警告一次。沒有有效授權時使用個人版，`users.*`、`departments.*` 等管理介面也依此拒絕存取。正式判定流程一律禁止升級，即使啟用 Debug assertions 也一樣。獨立測試 API 必須同時啟用非預設的 `test-edition-override` feature 與 Debug assertions；release 建置拒絕該 feature。
官方 GitHub 更新會精確核對 minisign 簽章註解 `duduclaw v{版本} {封存檔名}`，包含平台與架構；Pro 更新則使用 `duduclaw-pro` 及該管道自己的固定公鑰。封存檔簽章與涵蓋註解的全域簽章都必須通過。所有封存檔安裝路徑都必須提供驗證器產生的 `VerifiedReleaseIdentity`，綁定封存檔摘要、版本、檔名與簽章註解，僅通過完整性檢查不能安裝。換檔前還會確認執行檔版本。Linux 受保護升級只讀取編譯時的固定格式標記，不以 root 執行下載的程式：標記必須恰有一筆，header 為 `NUL + DUDUCLAW_RELEASE_ID:V1:`，接穩定版 `X.Y.Z`，suffix 為 `NUL + DUDUCLAW_RELEASE_END + NUL`。每個 `DUDUCLAW_RELEASE_ID` 都必須構成完整標記，缺少、畸形、重複或衝突一律拒絕；沒有標記的舊版封存檔也不接受。發版流程會在簽章前解析實際封存檔內的執行檔，確認標記與 tag 相同，Pro 打包也適用。一般更新則核對 `version` 輸出。任何不符都會在換檔及寫入受保護版本意圖／下限前中止。這些檢查適用於已包含修補的更新程式；舊更新程式仍需先由管理員審查並手動更新。

Provider 整合需改用 `verify_release_archive_with_pubkey(bytes, checksum, signature, pinned_key, expected_version, expected_file)`，並把結果傳給 `install_verified_binary(bytes, &identity)`。預期版本與檔名必須來自選定的發行資訊，不能直接從下載的簽章取值；原本只有一個參數的安裝 API 已移除。
Google Cloud 會議轉錄使用管理員另行安裝、加密儲存的服務帳戶金鑰，不繼承員工或 Workspace 憑證。設定／清除憑證的專屬 RPC 在 extension 路由前驗證即時管理員身分；通用設定更新拒絕憑證欄位，原始編輯器只允許保留遮罩或清除。音訊上傳至指定 GCS 儲存桶前，先以檔案鎖寫入持久化清理紀錄；刪除失敗採有上限的退避重試，並保留待清理紀錄，供啟動及定期掃描重試至成功或 HTTP 404。清理仍需要有效憑證與儲存桶權限，生命週期到期規則提供額外備援。原始音訊上傳前不會遮罩。詳見[會議逐字稿](73-meeting-transcripts.md)。

轉錄設定與原始設定寫入在提交鎖內重查即時管理員權限，使用者資料庫不可用時拒絕寫入。憑證設定／清除嘗試記錄操作者、動作與結果，不記錄秘密。清理僅刪除目前設定的儲存桶物件；不符的紀錄原樣保留，警告只記數量。Unix 清理目錄權限為 0700，紀錄與鎖檔為 0600，開啟時拒絕符號連結及非一般檔案。OAuth token 回應採型別化可清零儲存，並清零可取得所有權的回應緩衝區。
## Gateway A2A 存取（v1.80.0 起）

`POST /a2a` 沿用 Dashboard Bearer JWT 認證，檢查帳號啟用狀態、憑證撤銷與強制換密碼限制，不接受舊版共用管理員 token 或 MCP HTTP-server API key。任務操作經過方法權限表、即時員工權限、輸入檢查、來源 IP 與呼叫者速率限制，以及安全稽核。`[a2a] exposed_agents` 公開名單預設為空，只能縮小存取範圍；設定無效或無法讀取時拒絕存取。

有簽章的公開卡片 `/.well-known/agent-card.json` 只列出明確公開之員工已啟用的技能。簽章驗證卡片完整性，不會授予呼叫者權限。`GetExtendedAgentCard` 需要認證，且不增加存取權。A2A 讀取、列出與取消要求同一登入帳號曾透過 A2A 建立該任務、員工仍在公開名單，且目前員工 ACL 與任務閱覽對象檢查通過。所有者身分保存在任務上，子任務繼承相同所有者。一般 Dashboard 的任務列表、讀取、修改、刪除、停止、留言、附件、活動紀錄與推播同樣受所有者限制；Admin 沒有例外，也未提供另外的管理員覆寫入口。任務刪除後保留所有者紀錄，繼續保護殘留證據。外部 MCP 呼叫者若沒有 Dashboard 所有者身分便會被拒絕；經驗證且受指派執行該任務的員工保留工作所需存取權。取消沿用任務樹停止機制；待確認或不確定的停止狀態，不代表外部程序或副作用已實體中止。這些是產品入口的限制，不能限制直接存取主機或資料庫的行為。

公開探索、認證失敗與已認證 RPC 各自使用獨立的 IP 額度，每個 IP 每分鐘限 120 次；三類全域上限依序為每分鐘 600、600、1,200 次，RPC 另有每個呼叫者每分鐘 60 次的限制。匿名流量不會扣除已認證 RPC 額度。每個 IP／呼叫者限流器最多保存 10,000 個鍵，滿額拒絕新鍵，過期清理另有頻率限制。

`forward.recent` 與 `forward.chain` 也檢查保留的所有者紀錄，包含已刪除的 A2A 任務；Admin 不能繞過別人的所有權。`tasks.flow_metrics` 先排除其他 A2A 所有者的任務，再計算數量、時間與輪數統計。非 A2A 任務的存取規則維持不變。

任務資料庫在任何 schema 遷移前，若已有 A2A 結構或重送紀錄，就必須有可讀取的 `task_access_principals` 表。表格缺失或無法讀取時拒絕開啟，不會從尚存任務重建空表；需從一致的備份還原完整所有者紀錄。全新資料庫及沒有 A2A 痕跡的舊版資料庫仍可遷移。

既有 `keys/a2a-signing.ed25519` 必須是一般檔案，不能是符號連結。Unix 另要求檔案屬於 gateway 的有效執行使用者，且權限精確為 `0600`；Windows 不檢查 Unix owner／mode。不合格的檔案直接拒絕，不會覆寫或自動改權限。限流先檢查並記錄來源 IP 額度，通過後才扣全域額度；來源已超限的請求不會耗掉其他來源的全域容量。

`trusted_proxy_cidrs` 預設為 `[]`，最多接受 32 筆有效 IPv4／IPv6 CIDR，只應填入你控制的直接反向代理。符合名單的代理必須將 `X-Forwarded-For` 覆寫為單一 client IP；缺漏、重複、多層 IP 清單或無效值都會被拒絕。其他來源的標頭不採用。未設定時，同一代理後方的 client 仍在各流量類別內共用代理 IP 額度。例如，僅當 `192.0.2.10` 是你的直接代理時，才使用 `trusted_proxy_cidrs = ["192.0.2.10/32"]`；此設定不授予呼叫權限。

登入帳號與 `messageId` 組成持久化唯一鍵。以相同完整 `params` 重送會回傳原任務；同一 id 搭配不同參數會被拒絕，JSON 物件欄位順序不影響判定。刪除任務不會釋出該 id，也不會因重送而重建任務；重送仍須通過目前授權。

僅接受版本 `1.0`；版本缺漏、為空或不支援時回覆 `-32009`。串流、推播回呼、等待完成才回覆及任務接續均不支援。設定與請求範例見 [ACP 與 A2A](19-agent-client-protocol.md)。
WebChat 等連線可寫入後，再次確認使用者能否使用實際回答的 AI 員工。短暫的 `BEGIN IMMEDIATE` 交易會比對 ACL 版本，並涵蓋同步的 `start_send`，讓權限變更與訊框交付有明確先後；交易不等待連線，也不跨越後續非同步 flush。權限已撤銷或無法讀取時拒絕交付；先獲准交付的資料無法因之後的撤銷收回。

非 Admin 的 Dashboard 回覆在同一個最後屏障內，還會取得設定寫入者共用的 `config.toml.lock` 共享鎖與 registry 讀鎖，重新確認目前的 default 員工、角色、狀態及可呼叫權限，並持鎖到 `start_send` 或助理歷史公開完成。鎖競爭時直接拒絕，不等待；這是持共享鎖重驗的方案，不另外維護 policy 版本計數。`config.toml` 遺失或無效時拒絕非 Admin 的目標授權；新安裝須明確建立有效的最小設定檔。Admin 與匿名 widget 的既有路由規則維持原樣。檔案鎖保護遵循鎖協定的產品寫入路徑，不涵蓋忽略鎖的外部直接改檔。

助理歷史列寫入時帶有待確認的隱藏標記，最後權限與來源檢查通過後才公開。拒絕交付的列即使清除內容失敗，也持續隱藏，日後重新授權不會讓它出現；單純傳送失敗仍保留已授權回覆。使用者訊息會保存 `client_msg_id`，即使 `turn_accepted` 遺失，也能依精確的對話與使用者訊息識別復原，不以文字或前綴配對。
**Codex 外部設定檢查（v1.80.0 起）：** 外部設定不存在或未定義 MCP 時，一般員工、Explore、utility、Task Sandbox 與 Discovery 可執行；偵測到 MCP 或既有設定無法讀取／解析時，回報來源並拒絕。明確指定的 Codex 判官遭拒時，驗收失敗，不改用預設判官。這是啟動前的本機／快取快照檢查，無法保證後續雲端更新的完整隔離；[來源範圍與限制](../../architecture/extension-gates.md)。

企業版[團隊對話 API](68-manager-team-history.md)（v1.76.0）以即時報告線獨立判斷，不放寬原本的員工存取權。外部文字在讀取時遮蔽，每次揭露都要完成雜湊鏈稽核；設定關閉、來源不明、已裝模型故障或稽核失敗都不回對話內容。只跑 regex 時會明示 `ner: false`，姓名與地址仍可能漏遮。直接主機／資料庫存取仍在產品入口保護範圍外。

## 遠端 MCP OAuth 授權（v1.80.0）

OAuth 授權碼交換、刷新及 access token 驗證會重查原始同意金鑰與設定。金鑰被移除、過期、變更或無法讀取時，不能延續授權；無效刷新與重放已使用的 refresh token 會清除整個權杖家族。權限不能超過同意金鑰或前一個刷新權杖。缺少關聯資料的舊憑證須重新授權。RFC 7009 `/oauth/revoke` 沿用 public client 規則，核對客戶端歸屬，並撤銷包含 access token 的整個家族。儀表板清單與撤銷僅限 Admin，變更與發行流程共用交易鎖，清單不回傳憑證。撤銷不取消已在執行的工具呼叫。CLI 的 `ddc_refresh_*` 僅供 stdio，HTTP 與 SSE 會拒絕。詳見[遠端 MCP](../../guides/zh-TW/remote-mcp.md)。共用儲存層測試已通過，CLI／gateway／瀏覽器驗收待執行。

OAuth 每組授權最多保留 2,048 筆存取／刷新紀錄（含已使用的刷新權杖摘要），全域最多 16,384 筆權杖、1,024 組授權，儲存上限為 16 MiB。達上限時拒絕發行，不消耗目前的刷新權杖；已使用摘要保留至到期，維持重播偵測與舊權杖撤銷能力。HTTP 認證前依 TCP 來源 IP 限制每分鐘 120 次、依 Bearer 憑證限制每分鐘 60 次，認證後立即套用原有客戶端限制。不信任轉送 IP 標頭，代理後方的客戶端共用代理的來源額度。權杖交換另有每客戶端每分鐘 12 次限制。限流表與背景儲存工作數均有上限。存取驗證只讀取資料；通過限流後，背景儲存工作每分鐘最多更新一次最後使用時間。授權清單遇到設定錯誤會回報無法使用，不會顯示為空清單。儀表板撤銷會記錄操作者、授權組別、應用程式、權限及結果，不記錄憑證或摘要；稽核寫入失敗會明確回報，即使撤銷已生效。
## MCP 員工身分驗證

`DUDUCLAW_AGENT_TOKEN` 以 HMAC-SHA256 將員工宣告的 `DUDUCLAW_AGENT_ID` 綁定到安裝環境的 `identity.key`。`[delegation] require_identity_token` 預設改為 `true`，既有安裝未填此設定時也適用。缺少或無效權杖會拒絕 MCP 啟動；設定檔讀不到、TOML 格式錯誤或設定值不是布林值時，即使權杖有效也拒絕。共用驗證層同時拒絕系統與保留的佇列寄件者名稱，因此有簽章的 `dashboard`、`cron` 也無法取得員工命名空間或啟動 MCP。

**委派脈絡。** 稽核歸屬與授權分開：臨時員工只繼承已驗證執行員工的能力，團隊交接與人機共駕也依執行員工判斷權限。主機簽章綁定版本、執行員工、委派者、來源、深度、可取得的執行／任務／回合識別、到期時間及隨機 nonce；系統與保留名稱不能作為員工身分。只有深度為零且委派者等於執行員工時，簽章來源才可記錄已知系統名稱；通道與儀表板來源由主機已解析的請求者決定。首跳委派入列前，CLI 會將來源轉成執行員工，讓後續暫停與租約檢查仍追蹤原始員工鏈根。憑證缺少、遭竄改、過期或重播時不能繼續委派，一般工具仍以執行員工身分使用。同一 nonce 只允許一個 MCP 行程領取，該行程可在到期前重複呼叫工具；MCP 子行程重啟後，請重新啟動員工取得新憑證。領取紀錄保存在 `delegation-context-claims/`，目前尚無自動清理。憑證透過秘密環境變數傳遞，不放在命令列參數；第三方 MCP 上游不會收到憑證或委派資訊。Claude 只注入 DuDuClaw MCP 子行程，不支援秘密環境變數傳遞的舊版 Codex 無法委派。這不涵蓋可不受限存取 gateway 作業系統帳號或簽署金鑰的行程。

寬鬆模式必須同時設定 `require_identity_token = false` 與 `[delegation] identity_token_grace_until`：後者須為加引號的 RFC3339 UTC 時間（`Z` 或 `+00:00`），晚於現在且不超過未來 30 天。缺少、無效、非 UTC、過期或超過上限時會恢復嚴格模式，每個行程只記錄一次錯誤。身分驗證會重查期限，即使呼叫端曾快取寬鬆模式也一樣。Unix 另從已開啟的檔案描述元要求擁有者等於有效 UID、硬連結數為 1；macOS 拒絕任何延伸 ACL 項目，ACL 查詢失敗也拒絕（ENOENT 表示沒有 ACL）。其他 Unix 的延伸 ACL 未檢查。一旦觀察到某個 home 的期限過期或無效，該行程就會持續對此 home 強制嚴格模式；回撥時鐘或修改期限都無法重新放寬。此鎖定不會跨行程重啟保存。

**原生遠端 MCP bridge。** `mcp-remote-bridge` 一律要求 `DUDUCLAW_AGENT_ID`／`DUDUCLAW_AGENT_TOKEN` 的有效簽署身分，且必須與 `--agent` 相同，寬鬆模式的寬限期也不能略過。讀取遠端儲存庫前、每個輸入 frame、等待 refresh lock 後與實際送出 HTTP 請求前都會驗證。缺少或偽造 token、使用另一位員工的有效身分都會拒絕。主機會在每次啟動的有效 bridge 設定補入簽署身分，即使不需要 proxy 也一樣；原始第三方設定不得自行提供主機身分。升級後請重啟既有員工行程，重新產生有效設定。

原生 Linux 受保護模式下寬限期一律不適用，所有身分都採嚴格驗證。在該模式中，沒有確認員工紀錄的代號不會取得權杖，它的身分宣告會被拒絕；臨時子員工（`eph-…`）取得的是綁定建立它的員工的 v2 權杖，因此該員工被移除或還原時，子員工的權杖也一併失效。

只有明確設定 `require_identity_token = false` 並提供有效寬限期限才會啟用舊的寬鬆模式，閘道每次啟動都會警告。金鑰可用時，此模式接受未簽章或無效的員工宣告，仍有冒充風險。只有金鑰與初始化標記都不存在時，才停用驗證。閘道啟動會為既有及新建金鑰記錄 `identity.key.initialized`；標記建立後，金鑰遺失在兩種模式都拒絕，也不會重新產生。金鑰讀不到、不是一般檔案、格式或權限錯誤一律拒絕；無法初始化金鑰時，閘道停止啟動。

建立金鑰時會取得跨行程鎖，以不可預測名稱獨占建立暫存檔，在建立當下限制權限，寫入並同步至磁碟後，以不覆寫目的地的原子操作安裝。Unix 要求 `0600`、拒絕最後路徑元件為符號連結，並同步父目錄。Windows 以 `FILE_FLAG_OPEN_REPARSE_POINT` 開啟最後元件，從已開啟的 handle 檢查檔案類型、reparse 屬性、擁有者與 DACL；只接受目前擁有者、SYSTEM 或 Administrators 的存取授權。既有 Windows 金鑰若繼承了過寬的 ACL，需先修復權限才能啟動，不會自動改寫。

**升級與復原**：備份時保留原本的 32 位元組金鑰與初始化標記。先重新啟動閘道，重新產生員工 MCP 設定，再重啟舊的員工行程。沒有明確設定的安裝會立即套用嚴格模式；若需要短暫過渡，請明確設為 `false` 並填入有效寬限期限，完成重啟後改回 `true` 或移除設定。金鑰遺失或損壞時應還原金鑰及權限，不要刪除標記。新金鑰發布前會先同步標記；若在這段期間中斷，會刻意要求管理員復原。只有確認從未使用的全新安裝，才可由管理員移除孤立標記後重試；既有安裝不可用此方式復原。

初始化標記與鎖檔也受身分檔案 hook 保護。這不構成作業系統帳號隔離：與閘道同帳號且有不受限檔案權限的行程仍可改動兩者、讀取金鑰或自行產生權杖。本輪 Windows reparse／ACL 測試已通過交叉編譯，尚未原生執行。
## 遠端 MCP 協定與 OAuth 邊界

雙世代 MCP 用戶端保留原有工具過濾與第三方效果分類。不合法的 `x-mcp-header`
schema 不列入工具清單。初次探測可選擇支援的舊版本；連線建立後 bridge 收到
`-32022` 會拒絕操作並停用連線，不會重送。須重新啟動對話，重新協商、列舉工具
及檢查權限。API 用戶端的 `tools/call` 收到 `-32022` 也會終止呼叫，並拒絕該用戶端
後續所有請求；host 須重新連線、列舉工具及檢查權限。初次握手及獨立列舉工具時的
版本恢復仍保留。舊式 HTTP+SSE 只接受與認證目標同源的 endpoint。每條新的 API HTTP
連線獨立探測，不使用以網址為鍵的全域版本快取；bridge 只保留自身連線的協商狀態。

OAuth 在交換授權碼與顯示錯誤之前驗證 callback 的 issuer。CIMD 使用管理員設定的
公開 HTTPS 文件，要求精確的 client ID 與允許的 callback URI；選中的文件不合法便
拒絕。探測取得及已儲存的 OAuth resource 必須精確符合 MCP 端點的 canonical resource，
包含 path，且不得帶 query 或 fragment；即使同源，其他路徑也會拒絕，不符的舊憑證
須重新連線。PKCE、每伺服器加密憑證與對外網址檢查仍然生效。

API 用戶端的 MRTR 輸入須符合 host 宣告的能力，不會自動代替使用者同意。bridge
不宣告新版互動能力，拒絕所有 `input_required` 回覆（含只有狀態的回覆），也拒絕
下游傳入 `requestState` 或 `inputResponses`。完整續傳資料的外送、審批與原核准呼叫
綁定保護完成前，bridge 不開放 MRTR。詳見
[MCP 用戶端協定版本](../../guides/zh-TW/mcp-tools.md)。
## 公司範本管理（v1.80.0）

管理員可在兩種版本瀏覽員工及團隊範本。詳情與必填審閱步驟會顯示完整的 `SOUL.md`、`CONTRACT.toml` 及每份 `SKILL.md`，包含所有團隊成員；以原始文字呈現，不渲染 HTML。須檢查所有保留文字中的秘密與個資，再勾選確認。若內容有問題，先修正來源員工；公司範本編輯只支援工具與技能收窄。

複製／匯出先以 `templates.copy` 的 `preview: true` 取得預覽，不儲存範本。確認須帶回 `reviewed: true` 與 `review_digest`，伺服器重新擷取來源並拒絕內容變動。`templates.save`、`templates.apply` 也要求布林值 `reviewed: true`；公司範本另須提供審閱時版本。團隊每建立一位員工前都重查版本；變更或無法驗證時，以 `template_changed` 回報已建立名單並停止其餘成員，保留已建立的員工。

複本保留投影後的有效職務設定，以及審閱過的個性、合約、技能文字。不讀取記憶／歷史、`.mcp.json`、通道設定或任意自訂技能附件；有限定帳號池時拒絕複製。執行環境憑證／環境欄位及非可攜區段不保留；保留的政策區段若有憑證欄位則拒絕。整段 `[fork]` 移除，`db_sources`、`recipients` 清空，`git_credentials` 關閉，員工層級 `recipient_guard` 強制為 `ask`；心跳與自主演化預設關閉。文字中的已知格式憑證由既有診斷遮罩器處理，可能保留前後各四碼。**未知格式 token、短密碼、個資及寫在自由文字中的收件者識別資料，無法保證移除。** 必須由管理員審閱，不能視為秘密或個資清除保證。

儲存前掃描每份原始 SOUL、合約與技能文字，建立員工前再掃描實際待寫內容。既有隱藏內容與輸入注入掃描器發現問題即拒絕，短 HTML 註解及單一不可見／零寬字元也拒絕；掃描失敗時同樣拒絕並指出檔名，不複製內容。教學範例也可能命中規則，須修正來源而非繞過掃描。Unix 以 `O_NOFOLLOW` 開檔，對同一 descriptor 檢查大小、一般檔案與 hard-link 數；尚未固定所有祖先目錄，不能防止同一 OS 使用者替換祖先路徑。

五個範本 RPC（`templates.catalog/get/copy/save/apply`）均要求目前具 Admin 身分。公司範本存於 `<home>/company_templates/`，採原子儲存、整隊單一版本，稽核不含文件內文。內建唯讀，付費複本仍需授權。團隊複製包含主管與下屬（最多 50 人），保留內部匯報關係。編輯只允許移除技能／成員、縮減工具允許清單或增加禁止項目；移除主管須一併移除下屬。停用技能維持停用。自訂腳本不複製；未改動的內建辦公技能可復原官方附帶資產。公司複本不含付費包知識附件或評測題庫。

## 授權綁定與更新

MAC 衍生識別分為三種強度。**Hardware** 是全球管理的單播 MAC。**Instance** 是 Linux／Windows 上非已知共用占位值的本機管理單播 MAC，包含 GCP、AWS 與 Docker 網卡；狀態顯示「雲端／容器識別」。兩者都可驗證既有付費綁定，也可用於新啟用與經核准的換綁。主要 MAC 優先選 Hardware，其次 Instance。**Weak** 包含未取得或全零 MAC、共用 `02:00:00:00:00:00` 與 Npcap／KM-TEST `02:00:4C:4F:4F:50`、廣播 `FF:FF:FF:FF:FF:FF`、多播 MAC 與占位 UUID；即使相符，仍維持 OpenSource 直到核准換綁，也不會用於新綁定提案。Linux／Windows 保留舊版 hostname + MAC 雜湊，歷史 Instance 候選仍可驗證（非主要候選時 `legacy = true`）。作業系統管理員仍能複製這些識別；Instance 表示本機取得的識別證據，不代表硬體證明。macOS 歷史本機管理 MAC 在 UUID 可讀或不可讀時都維持 Weak。Windows 選取主要介面時另排除軟體迴路、軟體虛擬及隧道介面類型與已知迴路描述。macOS UUID v2 指紋與 UUID 讀取失敗時的限制維持不變。

為相容既有格式，授權簽章仍不涵蓋 `control_url`，因此它只是未受信任的端點提示。Gateway／CLI 的 refresh、換綁、status、CRL、經銷商品牌與公告請求，送出前都須經共用傳輸層檢查：僅限 HTTPS、443 埠、不得包含使用者資訊／query／fragment，主機名稱必須完整符合固定清單 `api.duduclaw.dudustudio.monster`。自訂簽發端須在客戶端本機明確設定環境變數 `DUDUCLAW_CONTROL_URL=https://issuer.example.com`；只在授權檔內放自訂網址不會獲得允許。此設定只允許該 origin，不放寬 HTTPS、埠、IP literal、localhost 或 DNS 限制。所有 DNS 回傳位址都必須是公開位址，連線固定使用已檢查的結果；停用重新導向與自動代理。驗證失敗不送出授權請求。Owner gateway 在同一個 SQLite `BEGIN IMMEDIATE` 交易內讀取授權狀態並簽署授權與第 2 版回應：撤銷先提交就回 revoked，簽署先取得鎖則撤銷須等待簽署交易完成；交易提交後的網路送達時間不在此保證範圍。

Refresh 接受回應前核對原訂閱、原／提案綁定、nonce、授權簽章及部署型態。active、revoked 與 pending 僅接受回應簽章第 2 版；簽章涵蓋狀態、原因、生效時間、nonce、訂閱、兩個綁定值與完整授權摘要，包含 `control_url`。缺少版本或舊版一律拒絕，撤銷生效時間尚未到達也不套用。Gateway 與 CLI 寫入共用跨程序 advisory lock，網路回應後比對完整授權檔與撤銷標記摘要；Gateway 另比對記憶體 revision。持久化使用唯一暫存檔與 fsync。忽略 advisory lock 的直接寫入仍在保護範圍外。詳見[簽發契約與限制](../../guides/zh-TW/personal-edition-portability.md#macos-授權指紋與重新綁定)。控制平面實際部署／核准／簽章、Windows 原生持久化及客戶遷移仍須另外驗收。
## 擴充功能與第三方工具的權限邊界（v1.80.0 起）

核心 RPC 一律由核心處理。擴充功能必須列出自己提供的方法，且名稱位於 `ext.<extension-id>.<method>`；註冊名稱衝突、重複或不合法時，會停用該擴充功能的 RPC 註冊並記錄警告。未宣告的方法不會交給擴充功能。

擴充 HTTP 路由必須明確宣告，且位於 `/ext/<extension-id>/…`；只接受字面路徑，不得攔截核心路徑。認證、來源檢查與 2 MiB 的請求本文硬上限由擴充處理程式外層執行。所有路由皆須登入並宣告最低角色；`ExtensionRoute::new` 預設要求 Admin。核心以資料庫目前角色判斷，JWT 核發後降權立即生效。已移除 Public 模式。 舊的 `extra_routes()` 不透明路由會在啟動時遭拒，擴充作者須先遷移再升級。

受管理的第三方 MCP 工具都經過 `ThirdPartyGate`，包含 `[[mcp.external]]` 的 stdio 與 HTTP 掛載。工具宣告只能將預設 Modify 提高為 Delete，唯讀宣稱不得降低分類；原有名稱限制與審批規則同時套用於工具清單和呼叫。員工 `.mcp.json` 中直接指定 URL/type 的項目會遭拒，請改用受管理的遠端 MCP 連線。這些限制不構成原生擴充程式碼的沙箱，也不涵蓋操作者自行啟動的獨立 CLI。

受管理的 Claude 啟動一律使用暫存的嚴格 MCP 設定，即使只有內建工具也不讀取其他 MCP 來源。Grok 啟動會拒絕專案內未受管理的 MCP 項目，以及實際 `HOME` 或 `GROK_HOME` 下的全域 MCP 定義；設定讀不到時也不啟動。Grok 實際使用的設定根目錄必須是絕對路徑；`HOME` 或 `GROK_HOME` 若填相對路徑，請先修正再重試。原檔保留，請先將伺服器定義移到員工 MCP 設定再重試。手動執行的獨立 CLI 與原生工具仍在這道邊界之外。

此次未新增全域功能模組開關。Odoo 線上客服輪詢、語音 HTTP 端點、通道音訊、會議背景工作與操作者指令仍各自使用既有防護。[入口盤點](../../architecture/extension-gates.md) 列出程式位置、遷移要求與驗證限制。

## 機器操作與下指令的人

給 AI 員工 Bash 或機器操作工具，就代表綁定這位員工的人可以指揮它使用這些工具。請只綁定應該有這份權限的人。管理員授予一般 AI 員工的原生工具仍可照常使用。

使用 `system-operator` 預設組的員工只供管理員使用。伺服器依解析後的預設組綁定識別，不採信客戶端旗標。非管理員不能綁定、聊天、建立交辦任務或目標，也不能以自己的身分派工給這位員工；`agents.callable` 不會列出它。既有綁定不刪除，但使用時會拒絕。非管理員即使保留 `system-operator` 員工的舊綁定或團隊授權，也讀不到它的對話紀錄、任務、記憶、檔案、自有知識集合與匯出，也收不到即時更新、執行步驟或審批卡片；綁定紀錄保留。非管理員先前建立的交辦排程不再為這位員工建立任務或目標，觸發時自動暫停，恢復時會拒絕。外送審批卡片（CLI 內建工具與 MCP 工具都算）僅供管理員查看，主管不再看到遮罩後的卡片。通道與 Mini App 僅顯示純文字通知，不再顯示外送審批卡片、摘要或操作按鈕。管理員與已授權的無人值守工作維持原有行為。Personal 只有在帳號資料庫不存在、沒有帳號，或僅有一個已完成首次密碼變更的啟用中 Admin 帳號時才適用單一擁有者豁免；停權與離職帳號也計入總數。多帳號部署即使因付費授權到期而回到 Personal，仍須有效管理員身分；帳號資料庫無法讀取時也一樣。

工作的委託人分為 Human、Background、Unknown 三種狀態。已儲存但無法解析的委託人是 Unknown，不能授權機器操作工具；舊資料完全沒有委託人時仍是 Background，既有 cron 排程與自主工作可繼續執行。

MCP cron 排程、agent_callback 提醒與 TaskSpec 計畫會保存主機帶入的 `on_behalf_of`，觸發時還原身分，後續委派也會繼承。非 Admin 可以替一般員工建立排程；Main 角色與設定的預設員工在建立時拒絕，執行時再檢查。cron 未通過會暫停，callback 提醒則標記失敗。舊資料沒有委託人時仍當背景工作。Discovery 保留既有已驗證員工／Operator 權限與審批流程；MCP 建立時檢查受保護目標，但獨立 runner 尚未還原真人身分。

每次讀取有效品牌時都會重查授權期限與離線寬限。授權過期或超過離線寬限就顯示原本的 DuDuClaw 品牌，即使主控台持續連不上、閘道尚未重新啟動也一樣。

## 員工健康資訊（v1.80.0）

唯讀 `agents.health` RPC 需要主管或管理員，並重查目前有效的登入身分。非管理員只能查看直接綁定的 AI 員工，團隊授權不會擴大這份彙整範圍。回應只包含健康次數與狀態資訊，不包含對話本文或服務商的原始錯誤。健康提醒只會透過已驗證的通道身分，送給啟用中的員工擁有者與管理員；設定檔不存在或省略區段時採保守預設值（五次失敗或六小時）；其他讀取錯誤或設定無效時關閉提醒。這些產品入口檢查不改變原本的界線：擁有同一作業系統使用者之無限制檔案存取權的員工，仍可直接存取本機狀態。

## Office 解析器限制與剩餘信任邊界

`office_script` 只執行通過 manifest 驗證的內嵌 Python 包裝程式。每次啟動前（包含改用系統 Python 的備援路徑），它會以不跟隨符號連結的方式重新開啟執行根目錄、工作區、用完即丟的快取、受信任基底與舊版 opt-out 快取，要求擁有者為 gateway 的 uid、權限為 `0700`，並重新檢查腳本是否為僅有單一連結的一般檔案，以及擁有者、`0500` 權限、長度與 SHA-256。已驗證的檔案描述元會一直開啟到啟動為止，但 uv／Python 仍會依路徑名稱重新開啟檔案：這只能縮小競態窗口，無法消除。

所有直接的 PEP 723 相依套件都指定確切版本。uv 會忽略專案、設定與環境變數檔，使用固定的 `2026-03-01T00:00:00Z` 套件上傳截止時間，拒絕從原始碼建置與自動下載 Python，並限制安裝程式的並行數。隔離執行時，只在主機端進行的預熱步驟會在另一個不含使用者檔案的暫存目錄中，以固定的 `--help` 呼叫已驗證的包裝程式；只有這個相依套件步驟可以使用網路。它共用的受信任基底位於 `<home>/.office-execution/uv-base-v1/`，其標記綁定包裝程式摘要與截止時間。舊的、解析器可寫入的 `uv-cache/` 及其標記，永遠不會升格進這個基底。跨行程鎖讓預熱與快照建立依序進行。沙箱以**唯讀**方式取得基底，並使用 `UV_CACHE_DIR=<private-workspace>/uv-cache`，搭配 `UV_LINK_MODE=copy` 與 `UV_OFFLINE=1`。一般檔案會複製成新的 inode；快取內部的符號連結會改指向用完即丟的副本，外部連結與特殊檔案一律拒絕，並略過綁定特定路徑的 `environments-v*`，讓 uv 離線重建環境。沙箱可寫入的快取不會跨執行或跨員工保留。準備好的執行在發布後或失敗／取消時被釋放，工作區、輸出暫存區與快取就會一併移除。清理時透過保留的工作區描述元還原目錄權限，不跟隨符號連結，解析器建立的權限 000 目錄也包含在內；檔案系統或目錄走訪失敗時會發出 `office_workspace_cleanup_failed`，需要操作者手動清理。預熱失敗時不執行文件；相依套件缺少或已被逐出時離線失敗，不會改為線上重試該文件。要重新預熱被逐出的基底，操作者可在下次執行前，從 `uv-base-v1/` 移除受影響的 `office-warm-*` 標記。明確選擇的無沙箱備援會保留舊的 `uv-cache/`、首次執行的下載與成功執行後的離線標記，但永遠不會寫入受信任基底。沒有 uv 時，隔離的系統 Python 會在執行包裝程式前檢查每個直接相依套件的已安裝版本；版本不符或缺少套件就失敗。

**相依套件限制**：未隨附完整的雜湊鎖定檔。產生鎖定檔時，因套件索引的 DNS 無法使用、本機缺少中繼資料而受阻。間接相依的版本與成品雜湊在建置時仍未確定；截止時間只限縮候選版本，無法驗證套件內容的真偽，也不會凍結相依關係圖。系統 Python 及其間接相依／site 套件、uv、LibreOffice 與可變動的快取套件，都不在包裝程式 manifest 的涵蓋範圍內。預熱標記與直接相依的確切版本釘選，都無法確立它們的完整性。

`office_script` 現在只要無法取得檔案系統隔離、網路阻斷與記憶體上限，就拒絕執行。它沿用既有的腳本沙箱逃生出口 **`config.toml [container.sandbox] script_when_unavailable = "run_unsandboxed"`**（預設 `fail`）。設定檔不存在、無法讀取、格式錯誤或填入其他值，一律拒絕（fail closed）。任務沙箱的 `when_unavailable` 與員工的 `sandbox_enabled = false`，都不會讓 office 腳本退出沙箱。明確的退出設定只在無法隔離時生效；此備援在每個主機行程只發出一次 `office_script_unsandboxed` 警告。它保留環境、私有暫存區、管線／行程清理與適用的資源限制，但不保證檔案系統、網路或記憶體隔離。工具會在執行文件前先探測，已開始執行的文件永遠不會改以無沙箱方式重試。

在 Linux 上**必須有 bubblewrap（`bwrap`）**：空的掛載命名空間以唯讀方式開放系統／執行環境路徑，只有用完即丟的 cwd／輸出／快取目錄可讀寫，共用基底唯讀，輸入快照與包裝程式也唯讀。網路與 PID 命名空間為必要條件（`--unshare-all --unshare-net`）；`--die-with-parent` 負責清理沙箱行程樹。建立 Linux 掛載或 macOS 設定檔之前，執行器會把 DuDuClaw home、私有工作區／輸出、輸入、包裝程式、基底快取與單次執行快取，以及每個既有的執行環境允許根目錄轉成正規路徑。任何私有路徑與執行環境根目錄（含其別名與正規化後的目標）只要相同，或任一方向互為上層目錄，就會拒絕，因此 `/usr/local/share/duduclaw` 或 `/opt/homebrew/var/duduclaw` 這類自訂 home，不會因為執行環境的授權而被隱含開放讀取。基底也必須與可寫入的工作區互不重疊，單次執行快取則必須嚴格位於該工作區內。正規化出錯同樣一律拒絕。不授予主機根目錄或整個 home 的存取；只明確開放私有暫存區／快取與選定的執行環境執行檔。這些事前檢查失敗時，適用上述同一個明確退出設定與警告。`RLIMIT_AS` 必須能設下 2 GiB 硬上限。缺少 bwrap、命名空間／掛載設定遭拒或記憶體限制設定失敗時，除非操作者已選擇退出，否則拒絕執行。只有命名空間隔離、沒有檔案系統邊界，並不足夠。參見 [bubblewrap 選項參考](https://github.com/containers/bubblewrap/blob/main/bwrap.xml)。

在 macOS 上，`/usr/bin/sandbox-exec` 會收到動態產生、預設全部拒絕的設定檔，並明確寫入 `deny network*`。讀取權限僅限系統／執行環境路徑、選定的執行環境執行檔、私有 cwd（含輸入快照與用完即丟的快取）以及唯讀基底；寫入只限於用完即丟的 cwd／輸出／快取，且不含包裝程式與輸入。路徑以跳脫後的 SBPL 字串表示，含控制字元、非 UTF-8 或非正規的絕對路徑一律拒絕。設定檔直接以引數傳入，不從檔案重新開啟。子行程會先嘗試設定 2 GiB 的 `RLIMIT_DATA`，若 DATA 無法設定或沒有效果，再改用 `RLIMIT_RSS`。實際啟動時沿用已驗證的那一種資源；若此時重新設定失敗，就拒絕啟動，不會改換資源。由於 [Darwin 的 DATA／RSS 語意](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/setrlimit.2.html)並非整體記憶體配額，另有一個 Python 探測會把已設定的上限降到 32 MiB，並要求 64 MiB 的配置必須遭拒。僅僅接受了限制值並不足夠。兩種限制都無法設定，或設了限制後配置仍然成功，就視為無法提供記憶體隔離，預設拒絕執行。這可能使新版 Darwin 上預設無法執行 office。請勿把這描述成已驗證的整體記憶體上限。

Unix 子行程仍有自己的行程群組，並限制 CPU 120 秒、單一檔案大小 256 MiB、行程數 512、描述元 256，且停用 core dump；既有較低的限制會保留，非記憶體類限制設定失敗時一律拒絕啟動。這些限制會在實際啟動時重新設定並由 Python／LibreOffice 繼承，屬於每個行程／每個檔案的限制，並非 cgroup 的整體配額。`RLIMIT_NPROC` 計算的是實際 uid 的行程數，特權行程可能不受此限。每條 stdout／stderr 管線各有並行讀取的 32 KiB 位元組硬上限。超出上限、讀取／等待失敗、180 秒期限到達與任務取消，都會終止整個行程群組；領頭行程結束也會觸發清理。失敗的執行不發布輸出。

**剩餘邊界**：不受限制的同 UID 主機行程，仍可在路徑名稱重新開啟時搶先競態，或修改共用的 uv 快取。上述間接相依／雜湊鎖定的殘餘風險仍在；只有內嵌的包裝程式位元組經過 manifest 驗證。在 macOS 上，刻意建立新 session 的子孫行程可以逃出行程群組清理（沙箱限制仍會繼承）。要宣稱這些更強的邊界，需要獨立 UID／容器隔離與經驗證的唯讀相依成品。原生沙箱的正向驗收與決策／設定檔測試是兩回事：本開發環境的 `sandbox-exec` 遭拒並回報 `sandbox_apply: Operation not permitted`，DATA／RSS 也無法設定，因此只能走到 fail-closed 路徑。原生 Linux 隔離、macOS 沙箱成功執行、真實 LibreOffice 相容性與 gateway／CLI 整合，仍需另行驗收。乾淨環境下以真實 uv 進行的預熱／複製／離線驗收測試，也因 PyPI 的 DNS 解析失敗而尚未在此驗證；假 uv 與檔案系統回歸測試，不能證明套件索引或原生沙箱已通過驗收。

## 守衛 1 — `agent-file-guard`（PreToolUse，Rust）

`duduclaw hook agent-file-guard` 是真正的子命令而不是 shell 腳本，所以 macOS／Linux／Windows 行為一致。Gateway 以 matcher `Write|Edit|MultiEdit|NotebookEdit|Bash` 把它註冊進 `<agent_dir>/.claude/settings.json`，每次開機重新註冊（`agent_hook_installer`），並且是合併進操作者既有設定，不是整份覆寫。

Grok 員工的這兩個守門來自另一個檔案。DuDuClaw 啟動 Grok 時會關掉 Grok 的 Claude 相容 hook 讀取（作業系統使用者自己 `~/.claude/settings.json` 的 hook 因此不會在員工的回合裡執行），Grok 也就不再讀 `<agent_dir>/.claude/settings.json`。所以每次啟動 Grok 前，gateway 會把 `agent-file-guard` 與 `data-file-guard` 兩個條目原樣寫進 Grok 的專案 hook 目錄 `<cwd>/.grok/hooks/duduclaw-guards-<員工>.json`；Grok 會把 matcher 裡的 Claude 工具名稱對應到自己的工具，並以 Claude 的 `tool_name`／`tool_input` 欄位把輸入交給 hook。每位員工各一個檔，共用借用工作目錄的團隊成員不會互相蓋掉身分；每位成員都會載入那裡所有的檔，任何一個拒絕就擋下。有員工目錄而檔案寫不進去的那次啟動會被拒絕。在員工自己的目錄裡，`.grok/` 屬於凍結的 runtime 設定目錄，員工改不了；員工目錄之外借用的工作目錄沒有凍結，員工若在那裡有寫入權限，可以自己加 hook 檔。

安裝的指令帶著 agent id（`--agent`），v1.68.1 之後的版本也帶著 DuDuClaw 資料目錄（`--home "<路徑>"`）。Claude CLI 的環境變數沒有 `DUDUCLAW_HOME`，所以先前 hook 一律退回 `$HOME/.duduclaw` 判斷；資料目錄不在預設位置的部署，真正資料目錄裡的每個路徑都被當成「資料目錄之外」。安裝器對每個 `<資料目錄>/agents/<id>`（或 `<資料目錄>/agents/.ephemeral/<id>`）形式的員工目錄都寫入 `--home`，路徑含 shell 特殊字元時改用單引號包起來。既有的安裝會在下一次啟動員工或 gateway 開機時就地改寫。

Hook 依序從這些地方取得資料目錄：`--home`（只認絕對路徑）；沒有員工身分的呼叫者（hook 指令沒帶 `--agent`、環境裡也沒有 `DUDUCLAW_AGENT_ID`）照舊用預設位置；hook 環境裡明確設定的絕對路徑 `DUDUCLAW_HOME`。不會從工作目錄推回資料目錄。全部都推不出來時，該員工的每一次 `Write`／`Edit`／`MultiEdit`／`NotebookEdit`／`Bash` 呼叫都拒絕，不會拿猜測的位置判斷。`NotebookEdit` 也在同一次加入 matcher，它的 `notebook_path` 比照 `Write` 的目標判斷。Hook 子命令只在 stderr 回覆，不再寫日誌檔。

以下情況它會 exit 2（Claude Code 讀成「擋掉這次工具呼叫」）：

- Agent 把 **agent 結構檔**（`agent.toml`、`SOUL.md`、`CLAUDE.md`、`.mcp.json`…）寫到正規的 `<home>/agents/<name>/` 樹之外。開新 agent 只能走 `create_agent` MCP 工具，那條路帶著委派授權閘；
- Agent 寫**自己的 `SOUL.md`**，即使位置正確也擋。人格由操作者管理。這個 hook 沒有開放選項：在 `agent.toml [permissions] can_modify_own_soul = true` 明確開啟的 agent，只能透過 `agent_update_soul` MCP 工具改自己的 `SOUL.md`，不能直接寫檔；
- Agent 寫**自己的 `CONTRACT.toml`**，即使位置正確也擋（判定 `BlockedOwnContractWrite`）。契約是操作者給 agent 的界線，所以完全沒有開放旗標；擋下時的訊息會請 agent 去找操作者，由操作者在儀表板修改（`contract.update`，員工的負責人或管理員，經過嚴格檢查，不經過這個 hook）；
- Agent 動**別的 agent** 的檔案，一律擋；
- Agent 寫入 **DuDuClaw 資料目錄**裡的其他任何位置。對帶員工身分（或宣稱的身分驗證失敗）的呼叫者，資料目錄底下能寫的只有自己的 agent 目錄與共用的 `attachments/`。這是允許清單，所以涵蓋稽核紀錄（`tool_calls.jsonl`，佐證檢查、判官摘要與近期行動摘要都讀它）、`evals/`（含留出集與其他員工的評測集）、所有 SQLite 資料庫、斷路器狀態、授權與組織檔、全域 `skills/` 與共用 wiki，日後新增的資料也一開始就受保護。這些資料的正當寫入者是 gateway 與受閘控的 MCP 工具，都不經過這個 hook。只有沒有員工身分的呼叫者不受影響，也就是 hook 指令沒帶 `--agent`、環境裡也沒有 `DUDUCLAW_AGENT_ID`。安裝的 hook 指令一定帶 `--agent`，hook 也優先採用它，所以操作者在某位員工的目錄裡手動執行 `claude`，會以該員工的身分被判斷（要求身分權杖的模式下，則是身分驗證失敗的呼叫者）。操作者要改這些檔案，請用儀表板，或直接用編輯器改；
- 寫入目標是指向上述被擋位置的**符號連結**。Write／Edit 的路徑會判斷兩次：照字面一次、解析到實際落點一次（跟隨連結與連結之後的 `..`；懸空連結一律拒絕），任一次擋下就擋。相對路徑以 hook 輸入裡的工作目錄解析，輸入沒有工作目錄時以員工自己的目錄解析。無法確認實際落點的路徑一律拒絕，訊息為「無法確認這次寫入實際會落在哪裡」；
- Agent 寫入、搬移或刪除 **`agents/_trash/`** 底下的任何東西（被移除的員工存放在那裡；Bash 以啟發式判斷）；
- Agent 在 Bash 執行 **`duduclaw agent create <name>`**，而該名稱因為曾有員工被移除而處於保留狀態（見[委派隔離](37-delegation-isolation.md#被移除員工的名稱仍被保留)）；拒絕會以稽核事件 `agent_name_reserved` 記錄，`path_kind` 為 `cli_bash_agent_create`。

- Agent 寫**自己的 `INSTRUCTIONS.md`**（判定 `BlockedOwnInstructionsWrite`）。這個檔案放的是操作者從其他平台匯入的工作規則（[匯入 AI 員工](../../guides/zh-TW/agent-config-import.md)），每次對話都會帶入，所以和契約一樣沒有開放旗標。它也列在 agent 結構檔清單裡，位置守衛與 `office_script` 對它的處理和 `SOUL.md` 相同。

在 Bash 上，「自己的 `SOUL.md`」、「自己的 `CONTRACT.toml`」與「自己的 `INSTRUCTIONS.md`」三條規則是啟發式判斷：寫入形態的指令只要點名這個檔案就擋下，不論寫成 `agents/<自己>/…`，或是 `CONTRACT.toml`、`./CONTRACT.toml` 這類相對寫法。身分驗證失敗的呼叫者，寫入形態的指令只要點名 `agents/` 底下任何位置就擋，與 Write／Edit 一致。

**Bash 與資料目錄允許清單。** Bash 通道用同一份允許清單判斷指令文字。以下說的「受保護的資料目錄目標」，指資料目錄裡自己的員工目錄與 `attachments/` 以外的位置、別的員工的目錄，以及被移除員工的存放區；身分驗證失敗的呼叫者，連自己的目錄也算。

- 判斷前先照 bash 的讀法還原指令：續行、反斜線跳脫與引號都先還原。把輸出或錯誤輸出丟到 `/dev/null`（`2>/dev/null`、`>/dev/null`），以及把一個描述元複製到另一個（`2>&1`），不算寫入；把輸出與錯誤一起重導到檔案則算寫入。
- 列在已知唯讀指令清單上的指令（列出、讀取、搜尋、比對之類）不檢查參數，但它們的輸出重導照樣檢查。有選項能把輸出寫進檔案、或能執行其他指令的指令，不放進清單，或在帶了那些選項時不算唯讀。員工用清單外的指令讀取資料目錄底下的檔案會被拒絕，請改用清單內的指令或對應的 MCP 工具。
- 複製類指令（複製、安裝、下載、解壓縮封存檔）只看目的地，所以把資料目錄裡的檔案複製到自己的目錄放行。
- 會改動參數所指對象的指令（搬移、刪除、建立連結、改權限、改擁有者或時間戳、同步、資料庫命令列工具等），以及直譯器與 shell，只要任一參數（含行內程式碼）是受保護的資料目錄目標就擋。任何指令把輸出重導到受保護的資料目錄目標也擋。
- 其餘指令（含前綴選項無法解析的情況），只要任一參數是受保護的資料目錄目標就擋，不論指令有沒有寫入。清單外的指令要碰受保護的資料目錄路徑，唯一的出口是已知唯讀指令清單。
- 資料目錄裡、**員工目錄與 `attachments/` 以外**的資料庫檔（`*.db` 及其 `-wal`／`-shm`／journal 檔、`*.sqlite*`），不論出現在指令哪裡，即使只是讀取也擋。員工目錄與 `attachments/` 裡的資料庫不在這條規則範圍內；別的員工的目錄仍然禁止寫入。
- 相對路徑以 hook 輸入裡的工作目錄解析（沒有時以員工自己的目錄解析），並跟著指令裡的 `cd`／`pushd` 移動。工作目錄推算不出來、而指令任何地方提到受保護的資料目錄位置時，受檢位置上的相對路徑一律擋下；完全沒提到時則不判斷。
- 受檢路徑上已存在的符號連結會解析，實際落點也一併判斷；無法解析的受檢路徑（包括懸空連結）一律拒絕。

這是減速帶，不是隔離。真正的隔離是不給 agent Bash；限制列在「這些守衛沒有涵蓋什麼」。

Live fork（`fork_run`）從另一側守住同一批檔案：分支可以讀 agent 的結構檔，但把分支採用回 agent 目錄時，絕不會用分支的版本覆蓋上層的 `SOUL.md`、`CONTRACT.toml`、`agent.toml`、`.mcp.json`、`.claude/` 或其他 agent 結構檔。

## 守衛 2 — `data-file-guard`（PreToolUse，Rust，RFC-23 §14.4）

守衛 1 保護 DuDuClaw 自己的結構檔，這一道保護的是客戶的資料。

`Read` 與 `Bash` 是 Claude Code 內建工具，所以 `cat customers.csv` 永遠不會經過 `file_read`／`csv_read`／`xlsx_read` 必經的 MCP 去識別化收斂點。安裝器把 `duduclaw hook data-file-guard` 註冊到 matcher `Read|Bash`；判斷邏輯放在 `duduclaw_core::data_file_guard`，由 CLI 子命令與 gateway 安裝器測試共用。契約與守衛 1 相同：exit 0 放行、exit 2 加 stderr 阻擋，stderr 會顯示給模型看。

除非 gateway 在 spawn 時設 `DUDUCLAW_DATA_FILE_GUARD`，否則它完全不作用；而 gateway 只在該 agent 的去識別化真的生效時才會設。去識別化關閉的部署，行為與這道守衛存在之前逐位相同。

舊版中，這是放在 `<agent_dir>/.claude/hooks/data-file-guard.sh` 的 POSIX shell 腳本，而且在 `PATH` 上沒有 bash 的 Windows 主機上**完全不作用**。Hook 指令執行失敗，而 Claude Code 把非 2 的結束碼（包含「command not found」）當成*放行*，守門就在最沒人會發現的地方消失。安裝器現在會在升級時刪掉殘留的舊腳本，避免有人把它誤認成現役守衛。

**明講限制**：`Bash` 那道檢查比對的是檔名。動態組路徑的指令（`python -c "open(chr(99)+…)"`）照樣走得過去。真正的保護是 MCP 工具面，這道守衛只是降低模型走上未設防路徑的機率。它是啟發式，不是沙箱。

## 守衛 3 — `input_guard`（提示注入掃描器，Rust 函式庫）

`duduclaw_security::input_guard::scan_input` 以**十一類規則**對文字評 0–100 分，達到或超過 `DEFAULT_BLOCK_THRESHOLD`（60）就擋：

| 規則 | 權重 | 單條即擋 |
|---|---|---|
| `instruction_override` | 40 | 是 |
| `role_hijack` | 35 | 是 |
| `tool_abuse` | 30 | 是 |
| `data_exfiltration` | 25 | 是 |
| `system_prompt_extraction` | 30 | 否 |
| `encoding_bypass` | 25 | 否 |
| `termination_manipulation` | 30 | 否 |
| `authority_escalation` | 每種訊號 35，兩種不同訊號相加 | 否 |
| `memory_poisoning` | 每種訊號 30，兩種不同訊號相加 | 否 |
| `role_provenance` | 每種框架 35，兩種不同框架相加 | 否 |
| `action_binding` | 30 | 否 |

樣式涵蓋英文與中文（繁體與簡體）。文字先做 NFKC 正規化（`unicode_normalizer`），同形異義字與隱形字元的花招因此躲不過樣式比對。

**中文涵蓋範圍（v1.67.1）。** 已發佈的版本只用四個完全相符的字串比對中文的指令覆寫，句子裡多插一個「所有」「之前」「的」就比對不到；實測時有四句這樣的句子經 `user_profile_record` 存進記憶。v1.67.1 起：

- `instruction_override`：覆寫動詞（忽略／無視／忘記／忘掉／不要理會／不用理會／別管，含簡體）之後，同一個子句內、12 個字以內出現指示類名詞（指示／指令／規則／提示詞／系統提示），而且兩者之間有範圍詞（先前／之前／以上／上面／上述／前面／所有／全部／一切／你的／原本／原來）。空白不計；`。！？；` 與換行會結束子句。權重與立即封鎖都和英文片語相同。
- `system_prompt_extraction`：擷取名詞（系統提示詞／系統提示語／你的系統提示／你的指示／你的設定）與輸出動詞（輸出／顯示／告訴我／給我看／洩漏／列出／重複）彼此相距 12 個字以內，順序不限。計分和英文規則相同：權重 30，單獨出現不會封鎖。單獨的「系統提示」不算擷取名詞，因為它也是「系統通知」的意思。
- `role_hijack`：固定片語，例如「你現在是管理員模式」「開發者模式」「越獄模式」「你現在不受限制」「進入越獄模式」，以及單獨的「越獄模式」。和英文相同。
- 門檻與英文清單不變。

**已知誤判。** 這條規則看句型比對，所以一般句子只要在同一個短子句裡有覆寫動詞、範圍詞和指示類名詞，也會被擋，例如「請忽略之前寄的指示，以新版為準」「請忽略以上規則中的第三條，已經取消」「忘記之前的規則了，可以再說一次嗎」（測試 `known_benign_shapes_that_do_match` 固定了這個行為）。提到「越獄模式」也會被擋。解法是不用覆寫動詞換個說法，例如「之前的指示作廢，以新版為準」；相近的「之前的報價單請作廢，以新的指示為準」在「不可比對」的測試清單裡。這個掃描器是片語規則，不是分類模型，也沒有用真實對話資料量測過。

`termination_manipulation`（LoopTrap，arXiv:2605.05846）刻意不設成單條即擋：權重 30 低於門檻，單次命中只警告並留稽核，不阻斷，避免一般的「請繼續」不會被誤殺。

**句型家族（v1.68.0）。** 紅隊帳本量出四種針對 AI 員工的技法原本是零分。現在每一種都有一組英文與一組繁體中文的錨定正則：

- `authority_escalation`：要員工拿自己的權限、不用使用者的權限去做事（"use your own service account / admin role"、"not my permissions"、"the system trusts you more than me"；用你自己的服務帳號／管理員身分、不要用我的權限、系統比較信任你）。
- `memory_poisoning`：要員工把一條長期特權存起來（"remember this permanently"、"as a fact about me"、"I am always allowed to"；永久記住、記在你的記憶裡、以後每次對話都照辦、我一律有權限）。一般的「請記住…」、"remember to…"、"remember my name" 不會比對到。
- `role_provenance`：使用者訊息裡出現假的系統、工具或營運方框架：`[SYSTEM]`、`<tool_result>` 標籤、`approval=granted`、"policy update from the platform operator"、「本次對話已解除…限制」、平台營運方政策更新、引文裡寫給 AI 的附註（給 AI 助理的附註）以及要它隱瞞的指示（不要提到這段附註）。框架只比對完整標籤，"our system sends a tool result" 不會中；一組開頭加結尾標籤算一種框架。
- `action_binding`：把一個核准挪去做別的事（"use that same approval to…"、"use the approval from step 1"；用同一個核准、用第一步的核准去…）。「既然已經核准預算，請安排會議」不會比對到。

權重原則：單一訊號只警告並留稽核（30–35，低於 60）。同一則訊息裡出現同一家族的兩種**不同**訊號，或一種訊號再加上既有規則（例如 `instruction_override`、`system_prompt_extraction`），就會擋。可以自身相加的有三個家族：`authority_escalation`（「用你的服務帳號」加「系統比較信任你」＝70）、`memory_poisoning`（「永久記住」加「我一律有權限」＝60）、`role_provenance`（`[SYSTEM]` 加 `approval=granted`＝70）。`action_binding` 不會自己相加，要搭配其他規則才擋。同一種訊號出現兩次只算一次：單獨一個 `[SYSTEM]` 或一組 `<tool_result>…</tool_result>` 維持 35。已知代價：剛好帶兩種訊號的正常句子也會被擋，例如 "please use your admin account, not my permissions, to fix the shared folder"（測試 `known_benign_shapes_blocked_by_stacking` 固定了這個行為）。換成只帶一種訊號的說法，或請管理員自己處理即可。任何命中就丟棄文字的呼叫端（萃取、使用者側寫寫入）現在也會丟棄含這些句型的文字。每個家族的正例與看起來像但不該中的句子，都在 `input_guard.rs` 的測試裡固定。

比對到時會在哪裡出現（已核對的呼叫端）：

- 聊天收到的訊息（`channel_reply`，`scan_input_with_audit`）：被封鎖的訊息會收到警告回覆，不會交給 AI。
- MCP 工具呼叫（`mcp_dispatch`，對序列化後的參數做 `scan_input_with_audit`）：參數引用了會被封鎖的句子時，呼叫被拒絕並記入稽核。
- 對話事實、使用者輪廓與知識分流的萃取（`wiki_ingest`、`profile_distill`、`knowledge_route`）：只要比對到**任何**規則就丟棄，包括不封鎖的擷取規則。
- `user_profile_record`：predicate 與值都會掃描，達到封鎖等級就拒絕。
- `duduclaw migrate from` 匯入會略過被封鎖的項目；expert pack 安裝會拒絕被封鎖的套件。
- Agent Mail：比對到的來信照樣存下但會加上標記，有標記的信永遠不會觸發 AI 員工。
- 提醒：提示內容被封鎖的提醒不會執行。

## 守衛 4 — `org_field_guard`（組織權威凍結）

A2A 委派判定（`delegation_policy::can_delegate`）靠 `agent.toml` 的 `[agent] reports_to`／`department`／`name` 與 `config.toml` 的 `[delegation]`、`[acp]` 決定誰能命令誰。這兩個都是普通檔案：一個手上有 `Edit` 的 agent 可以把自己的 `reports_to` 改指向受害者，再宣稱「下屬 → 上級」那條規則。被審判的一方握有證據。

`org_field_guard` 跑在同一個 `agent-file-guard` hook 裡，把重建出來的**寫入後內容**逐欄位與磁碟上的現況比對，受保護欄位或區段有變動就拒絕。`[capabilities]` 會凍結**整張表**，未來版本新增的 capability 鍵也會在加入時受保護。

**員工自己的安全設定。** 對帶員工身分（或身分無法驗證）的呼叫者，它自己 `agent.toml` 的其餘部分以允許清單凍結：只有可編輯的區段能改，其他區段一律受保護，日後版本新增的區段也預設受保護。可編輯的區段是 `[agent]`、`[model]`、`[prompt]`、`[heartbeat]`、`[proactive]`、`[research]`、`[goal_intent]`、`[memory]`、`[skills]`、`[sticker]`、`[cultural_context]`、`[preset]` 與 `[planner]`。這些區段裡，`[agent] role`、`[prompt] cli_bare_mode`（它會讓 Claude CLI 略過 hook）與 `[model] account_pool` 仍凍結，組織欄位 `[agent] reports_to`／`department`／`name` 也一樣；`[capabilities]` 整張表凍結。這份允許清單適用於所有帶員工身分的呼叫者，包括在員工目錄裡手動執行 `claude` 的操作者（見 Guard 1）；較早的組織欄位與 `[capabilities]` 規則照舊對所有呼叫者生效。操作者要改這些區段，請用儀表板，或直接用編輯器改。

**員工自己的 `.mcp.json` 與 CLI 設定。** 帶員工身分（或身分無法驗證）的呼叫者，完全不能寫自己目錄裡任何一層的 `.mcp.json`（Write、Edit、MultiEdit、NotebookEdit；最上層那一個 Bash 規則本來就擋）。gateway 啟動 Claude CLI 時會帶這個檔，CLI 會把裡面列的每一個伺服器都啟動起來，所以只要多加一個指令是直譯器的項目，下一次啟動就能以管理者的系統身分執行任意指令，不需要 Bash 權限。所有已出貨的版本都有這個問題：以前員工可以自己新增「無關的」伺服器。現在新增 MCP 伺服器要走儀表板、在儀表板提出的 MCP 安裝申請（`mcp.install_request`，管理者核准後自動安裝）、expert pack，或由管理者直接編輯，這些都不經過 hook。同樣的呼叫者也不能寫自己目錄裡的 CLI 設定：任何一層的 `.claude/` 底下（設定、hook、自訂斜線指令、子代理、skill）與名為 `.claude.json` 的檔案，以及最上層的 Codex、Grok 設定目錄（`.codex/`、`.gemini/`、`.grok/`、`.agents/`），以及 `.cursor/`（Grok 會自己讀工作目錄的 `.cursor/mcp.json`，2026-10-20 起）。檔名比對不分大小寫。行為變更：複製到員工目錄裡的專案也是 CLI 會啟動的地方，所以員工可以讀那個專案的 `.claude/`，但不能寫。管理者維持舊規則（`.mcp.json` 只凍結身分鍵）。gateway 也會在每次把員工的 `.mcp.json` 交給 Claude CLI 之前（通道回覆、派工、heartbeat 主動檢查、`duduclaw eval` 的 live 模式、live fork 複製分支之前的上層目錄）與開機時，整筆重新產生 DuDuClaw 項目（指令、參數、環境變數），其他項目原樣保留；檔案無法確認（不是一般檔、讀不到、不是合法 JSON，或 duduclaw 執行檔路徑不是絕對路徑）時這次不啟動，並寫一筆稽核（`mcp_config_unverified`）。這種拒絕是檔案的問題，不是帳號的問題：帳號不會因此進入冷卻，也不會換下一個帳號重試，通道回覆不會改由本地模型或 Direct API 代答，使用者看到的是說明哪位員工設定無法確認的訊息。所有寫 `.mcp.json` 的程式共用的鎖放在 `<home>/locks/`，不在員工目錄裡，員工在那裡建立的檔案或目錄擋不住它。升級前就加入的項目會保留：`duduclaw doctor` 會列出每一個不是 DuDuClaw 寫入的項目（只顯示名稱與指令的檔名，不顯示參數、環境變數或網址），讓管理者逐一確認或移除。把 live fork 分支採用回員工目錄時，不會帶回 `.claude.json`、`.agents/`、`.codex/`、`.gemini/`、`.grok/`、`.cursor/`，也不會帶回任何一層的 `.claude/`、`.claude.json`、`.mcp.json`。限制：這是 hook，能任意執行 Bash 的員工仍可改檔；Codex 另有下述控制檔鎖，與這個 hook 分開。Grok、其他 CLI runtime 與 Windows 不在該鎖的涵蓋範圍。Claude Code 可能會讀取員工目錄裡的 `.claude.json`，該檔案禁止寫入。

依建構方式 fail-closed：新內容無法解析、既有內容無法解析、寫入意圖無法重建，三者全部拒絕。既有的 `agent.toml`、`config.toml` 或 `.mcp.json` 讀不到時也拒絕（以前當成新檔放行）。檔案還不存在則放行，因為建立走的是 `create_agent`，那裡有自己的閘。

合法變更的既有路徑全部保留：MCP `agent_update` 工具與儀表板 `agents.update` RPC，兩者都不經過這個 hook。

**Codex 員工控制檔（Unix、WorkspaceWrite）。** 一般員工執行時，除了既有沙箱模式，還會套用 `duduclaw-employee` 權限 profile，將員工目錄最上層的 `agent.toml`、`SOUL.md`、`CONTRACT.toml`、`INSTRUCTIONS.md`、`.mcp.json`、`.codex/`、`.grok/`、`.claude/`、`.agents/` 設為唯讀，尚未存在的路徑也不能建立。保護項目使用員工目錄的絕對路徑，工作根目錄被覆寫時仍有效。`MEMORY.md`、`CLAUDE.md`、一般工作檔與暫存檔維持可寫。需要 Codex CLI 0.164.0 以上；版本過舊、無法確認版本或缺少員工目錄時，拒絕啟動。版本探測以執行檔路徑快取。版本過舊或無法確認時，儀表板向 Admin 顯示一鍵更新提示；透過此按鈕更新後會清除支援快取並重新探測，不必重啟 gateway。若優先找到的仍是舊執行檔，會顯示其路徑，不會報成成功。設定仍可透過 `agent_update` 與儀表板修改。ReadOnly、明確授予的 FullAccess、探索與輔助路徑維持原有參數。這項控制檔鎖不涵蓋 Grok、其他 CLI runtime 與 Windows（未驗證）；其他 CLI runtime 除非開啟 `native_sandbox`，否則沒有 OS 沙箱。 Docker 部署需要目前版本的 compose 檔，它會套用窄版 seccomp、`apparmor=unconfined`、`no-new-privileges` 與 `cap_drop: ALL`；Ubuntu 24.04 還要在宿主機載入 AppArmor 設定檔。沙箱起不來時 shell 指令會失敗、檔案不會被改動，DuDuClaw 不會降低沙箱來繞過，`duduclaw doctor` 會回報原因。見 [docker.md](../../guides/zh-TW/docker.md)。 容器本身為了 bubblewrap 而放寬，所以在 Docker 中，gateway 會替其他子行程（Claude、Grok、其他 CLI、MCP server、管理者設定的指令）加上一層 seccomp，還原 Docker 的 namespace 限制並阻擋 `ptrace`；gateway 自己設為不可傾印，同 UID 行程碰不到它的記憶體。只有會執行 bubblewrap 的 Codex 路徑例外。已知限制：Codex 沙箱內仍可建立巢狀 user namespace，Codex 沒有提供關閉的選項；多租戶部署請使用 VM 隔離。

## 依來源忘記需要管理員核准

`duduclaw memory forget-source` 會永久刪除記憶，所以前面有三道關。操作步驟見[忘記對話、排程執行或匯入檔案](../../guides/zh-TW/memory-and-knowledge.md#45-忘記對話排程執行或匯入檔案)，機制見[記憶智能](20-memory-intelligence.md#記憶來源與依來源忘記)。

**儀表板核准。** `plan` 會送出一筆核准請求（`action_kind` 為 `memory_forget_source`），綁定計畫 id 與計畫雜湊。這筆請求只能在儀表板決定，也只有管理員能決定；通道按鈕與回覆一律拒絕。`apply --confirm` 只有在該請求已核准、仍指向同一個計畫雜湊、且計畫未過期時才會執行。請求與計畫一起到期（預設 30 分鐘，最長 24 小時）。卡片只放數量與來源標籤，不放記憶內容，並以固定文字說明這筆請求來自本機指令列、系統無法確認是誰下的指令。沒有任何設定能關掉這道核准；`[memory] forget_source = false` 只會停止建立新計畫與套用。

**Bash 規則。** 對帶員工身分或身分未驗證的呼叫者，`agent-file-guard` 的 Bash 通道會拒絕 `duduclaw`、`duduclaw-pro`（含路徑或 `.exe`）後接 `memory forget-source` 或 `memory migrate-namespace` 的指令，任何子指令都擋，連唯讀的 `list` 也一樣。判定結果是 `BlockedOperatorMemoryCommand`，訊息會請員工去找操作者。`migrate-namespace` 以前不在 Bash 通道的涵蓋內。這是減速帶，不是沙箱，擋不住：

- `memory` 與子指令之間插了全域選項，例如 `duduclaw memory --redact on forget-source …`；
- 用指令替換組出執行檔，例如 `"$(command -v duduclaw)" memory forget-source …`；
- 把指令字串經管線交給執行檔，例如 `echo memory forget-source … | xargs duduclaw`；
- 其他能避開指令名稱比對的寫法，以及「這些守衛擋不住什麼」列出的其他繞法。

**AI session 判斷。** 只要程序環境裡有 gateway 替員工程序設定的任何一個變數（即使是空值），指令本身就會拒絕執行：員工身分與 token、回合與對話 id、該回合的使用者訊息序號與時間、派工的 session 與 run id、委派的發送者／來源／深度、hop 深度、回覆通道、MCP API 金鑰、資料檔守門旗標、goal 回合的任務 id（唯一一份清單 `ai_session_guard::AI_SESSION_ENV_VARS`，2026-10-06 起所有會送出核准的操作者指令共用）。操作者自己的終端機不帶這些變數。這項檢查只是第一道。對直接從員工 Bash 執行的指令並不可靠，因為有 Bash 的員工可以把變數 unset。真正的隔離是不授予 Bash，或讓員工跑在任務沙箱裡。以同一個作業系統使用者執行、能跑任意指令並刻意繞過檔案守門的員工，仍然可以直接改寫本機資料庫（`approvals.db`、`memory.db`）。

## 操作者的員工控制指令

`duduclaw agent pause|resume|freeze|unfreeze <agent>` 只要偵測到共用 AI 工作階段清單中的任一變數（即使為空）就會拒絕執行。`agent-file-guard` 的 Bash 通道也會阻擋員工與未驗證身分呼叫這四個子指令（`BlockedOperatorCommand`），重用共用操作者指令比對器，涵蓋 `duduclaw`／`duduclaw-pro`、絕對路徑、`.exe`、`env`／`npx` 前綴、引號拼接與換行續行。管理者仍可在自己的終端機直接執行，這四個指令不需要儀表板核准。`pause`／`resume` 修改 `[agent] status`；`freeze`／`unfreeze` 修改演化與心跳。寫入使用與 `agent_update`、儀表板相同的共用鎖與保留格式的原子寫入流程，留下檔案版本及 `agent_file_changed` 稽核。成功執行另記 `agent_pause`、`agent_resume`、`agent_freeze` 或 `agent_unfreeze`，拒絕則記 `agent_cli_refused`。這仍是減速帶：清除環境變數、改名的執行檔或動態組合的指令可繞過檢查，非 Claude runtime 不跑 hook，有不受限 Bash 的員工仍能直接改檔。真正的隔離是不授予 Bash，或讓員工跑在任務沙箱裡。

## 指令列的操作者動作共用一道核准

四個指令會從終端機改變狀態：`duduclaw channel-ingress`（LINE 收件匣）、`duduclaw responsibility`（持續任務）、`duduclaw memory forget-source apply`、`duduclaw computer-workspaces`。終端機證明不了是誰下的指令，所以這四個都只會在儀表板建立一筆請求，由目前仍是管理員（Admin）的帳號決定，指令之後只套用一次。v1.70.0 之後的版本起，四者共用一份實作（gateway crate 的 `approval/operator_cli_gate.rs`）和同一張種類表：只有在儀表板做的決定才算數，而且必須是同一筆請求、同一個狀態（LINE 批次除外）；請求等待期間對象狀態變了，等待中的卡片會撤回（`state_changed`）並另建一筆，不會原地改寫；核准用一個條件式更新消耗，搶輸的那次執行什麼都不做、也不另送請求；同一個動作與對象最多 3 筆不同內容的請求在等，同一種類最多 20 筆；每個對象每小時最多推播 2 次（忘記記憶的請求以 AI 員工計）。`approvals.decide` 用同一個檢查擋掉非管理員的決定。四個指令也共用同一份 AI 員工工作階段環境變數清單（CLI crate 的 `ai_session_guard.rs`）。限制不變：Bash 權限不受限的員工仍能直接改本機資料庫。

**升級須知。** 這道閘把綁定資訊存在請求內容的 `gate` 物件裡。v1.70.0 以前建立的請求沒有這個物件，新版本不會比對到、也不會計數。升級前送出的請求，就算已經核准、還沒套用，升級後也不會被套用：再執行一次指令會另建一筆新請求，要重新核准。舊的等待中卡片在過期前照常收到提醒推播（持續任務的請求本來就不提醒），但核准它不會有任何作用。

## 動作規則、探索通道與動作審查

2026-10 新增（v1.72.0）。三層都只會收緊員工能做的事，不會解除其他閘門設下的核准或拒絕。

**動作類型。** 每個 DuDuClaw MCP 工具都有一個副作用類型（`duduclaw_core::tool_effect::effect_of_builtin`）：`read`（讀取）、`draft`（擬稿）、`send`（傳送）、`publish`（發布）、`purchase`（花錢或承諾交易）、`delete`（刪除）、`modify`（修改資料）、`admin`（管理操作）。`read` 與 `draft` 在回覆之外不留下任何東西，其餘六類都有副作用。效果會隨參數改變的工具取較嚴格的類型（`wiki_write` 兩種 scope 都是 `modify`）。`mail_send` 只會建立一份要人核可的草稿，但它歸在 `send`，因為它最後的效果是寄出；`gmail_create_draft` 永遠不寄，歸在 `draft`。表裡沒有的工具名稱當作 `admin`（fail closed），並有測試逐一檢查每個對外宣告的工具，新工具沒分類就無法通過。內建工具目錄（`tools.catalog`）以 `effect` 欄位帶出類型。

**動作規則。** `agent.toml [capabilities] action_rules` 依類型或依工具設定 `allow`、`ask` 或 `block`：

```toml
[capabilities]
action_rules = [
  { effect = "send", verdict = "ask" },
  { tool = "mail_send", verdict = "block" },
]
```

`tool` 規則（與其他 `[capabilities]` 工具清單同一套有錨定的比對，`mcp__duduclaw__mail_send`、`wiki_*` 都可用）優先於 `effect` 規則；同一種規則之間取最嚴格的判定。`block` 在 MCP dispatch 閘與 `denied_tools` 同一處拒絕（JSON-RPC `-32003`，稽核 `error_class` `action_rule`），並從 `tools/list` 隱藏；`ask` 併入核准閘的靜態「一律詢問」集合，所以跟 `approval_required_tools` 一樣走 ApprovalBroker。`allow` 只代表「這一層不加阻力」，不會解除 `denied_tools`、核准清單、能力開關或 scope。九個 `computer_*` 工具與三個 `computer_workspace_*` 工具在 gateway 的電腦操作路由用同一套判定，因為工作階段由 gateway 持有。這個鍵刻意放在 `[capabilities]`：`org_field_guard` 會凍結整張表，員工無法自己改。清單或某一筆格式錯誤（不認得的判定或類型、`effect` 與 `tool` 同時有或都沒有、多出的鍵、不是陣列）不會讓整個檔案失效：原樣保留，並讓每個有副作用的呼叫至少要「先問人」，其中有效的 `block` 仍然擋下。`agent.toml` 存在但讀不到或不是合法 TOML 時也一樣處理。儀表板在員工編輯頁編輯這份清單（依動作類型的規則，加上個別工具的例外），走只限管理員的 `agents.update` capabilities 路徑，每一筆都會檢查，變更記為 `agent_authority_changed`。

**Claude Code 內建工具（2026-10-08 收尾）。** `action_rules` 也會在啟動時套到 Claude CLI 自己的工具。內建工具依名稱精確分類（`duduclaw_core::effect_of_cli_builtin`）：`Read`、`Glob`、`Grep`、`WebFetch`、`WebSearch` 是 `read`；`TodoWrite` 是 `draft`；`Write`、`Edit`、`MultiEdit`、`NotebookEdit` 是 `modify`；`Bash`、`Task`、`Agent` 與其他任何名稱都是 `admin`。內建工具的呼叫不會經過 ApprovalBroker，所以對內建工具說 `ask` 的規則無法照辦，一律當成 `block`（fail closed）：該工具透過 `CapabilitiesConfig::disallowed_tools()` 加入 `--disallowedTools` 並從 `--tools` 移除，凡是已經套用 `denied_tools` 的 Claude CLI 啟動都會讀到（`claude_runner` 的派工、cron、goal 與心跳喚醒、`channel_reply/cli_env.rs` 的通道回覆、心跳主動檢查、eval 與團隊角色成員）。因此格式錯誤的規則清單會讓所有有副作用的內建工具（`Write`、`Edit`、`Bash`…）都拿不到，唯讀工具保留。行為變更：原本為 MCP 工具寫 `{ effect = "modify", verdict = "ask" }` 的操作者，現在 Claude CLI 的 `Write`／`Edit` 也會被拿掉。

**已移除的工具名稱。** 為 v1.69.0 移除的名稱（`shared_wiki_write`、`schedule_task`、`skill_bank_search`…）寫的 `tool` 規則，會繼續管住取代它的呼叫（`scope = "shared"` 的 `wiki_write`、帶 cron `schedule` 的 `tasks_create`、`source = "bank"` 的 `skill_search`），在派工閘的 `block` 與核准閘的 `ask` 都一樣，與 `denied_tools` 相同（`ActionRules::resolve_for_call`、`tool_catalog::removed_name_for_call`）。只有 `tool` 規則會跟著已移除的名稱，結果只會更嚴。

**探索通道。** 以 `DUDUCLAW_LANE=explore` 啟動的 MCP server 只列出、只執行 `read` 與 `draft` 工具，其他呼叫一律以 `-32003` 拒絕，稽核 `error_class` `explore_lane`。變數存在但是其他值（包含空字串）時拒絕所有呼叫。gateway 在心跳的主動檢查（proactive check）設定這個變數，這次 Claude CLI 的內建工具也只剩 `Read`、`Glob`、`Grep`、`WebFetch`、`WebSearch`（再扣掉員工自己的 `denied_tools`）。檢查決定要發的通知仍由心跳根據回覆送出。變數透過 CLI 繼承的環境傳到 MCP 子行程，`.mcp.json` 的項目不設定它。主動檢查只在 Claude CLI 上執行，所以不牽涉其他 runtime。2026-10-08 起，兩種派工也在此通道執行：MCP Events 投遞啟動的工作（除非該訂閱開啟一般模式），以及合約帶 `lane = "explore"` 的持續任務的每一輪。兩者設定同一個旗標（`duduclaw-gateway/src/explore_lane.rs`），規則相同：只有 Claude CLI、Codex 與 OpenAI 相容執行環境的員工能執行（Codex 不論權限等級一律 `-s read-only` 加 `approval_policy=never`，DuDuClaw server 帶通道變數登記；Codex 在該模式下拒絕所有 MCP 呼叫）；其他 runtime（Grok、通用 CLI）或任務沙箱在開始前就被拒絕，MoA 模型與純本機推論也被拒絕。通道內的行程寫出的委派（`spawn_agent`、`spawn_ephemeral`、`send_to_agent`）會在 `bus_queue.jsonl` 項目或 `message_queue` 列帶上 `lane`，派工器與事件通道一樣遵守；通道本來就拒絕這些工具，這是第二道防線。`DUDUCLAW_LANE` 也列入操作者指令拒絕的 AI 工作階段變數清單。

**受限輔助執行。** Claude 輔助呼叫使用 CLI 可用憑證，不進入帳號輪替；一般對話維持輪替。Claude 停用工具，OpenAI 相容 API 只送一次不帶工具的請求。Codex 輔助呼叫使用 `--sandbox read-only`、`--ignore-user-config`（認證仍使用 `CODEX_HOME`）、`--ephemeral`、`--ignore-rules`（只略過 execpolicy `.rules`）、`--skip-git-repo-check` 及 `-c approval_policy=never`。不注入平台 MCP 設定，每次在新建、只有擁有者能存取的空白暫存目錄執行，成功、錯誤與逾時後均刪除。系統提示放進 prompt，從不寫入 `AGENTS.md`。行程只接收 spawn-env 允許清單及 Codex 認證必要資訊，不帶員工 token；員工開啟原生 OS 沙箱時，也以暫存目錄和唯讀權限套用。明確指定 Codex 的 judge 與 verifier 使用同一模式。Grok 與通用 CLI 員工改用支援的全域輔助模式；不支援的全域後端或明確指定會被拒絕。

輔助與其他內部 runtime 呼叫拒收逾時的部分輸出，提前輸出的 `PASS` 不會成為評審結果；只有頻道回覆可顯示已完成的部分文字。Claude 輔助行程套用共用環境白名單及既有 Anthropic 憑證查詢，不繼承其他廠商金鑰或平台員工／MCP token。Windows 受管理 CLI 在暫停的子行程繼續執行前加入 Job Object，主行程退出後仍保有整樹清理能力；Windows 原生執行行為沒有保證。

**Codex 剩餘風險。** 此模式不能證明所有內建工具都已移除。內建讀取工具可能仍存在，因此遭提示注入的輔助呼叫可能讀取 OS 使用者有權讀取的本機檔案，並將內容寫進輸出。Codex 原始碼的唯讀政策停用工具指令網路；供應商模型請求另計，原生 OS 強制效果沒有保證。`--ignore-user-config` 略過使用者設定，空白工作目錄避開員工專案設定，外部設定檢查會拒絕含原生 MCP 的設定，以及無法讀取或解析的既有設定。 查證來源: [tool registry](https://github.com/openai/codex/blob/970111f6cb62cc02fe36a82ea7d71b37a2889c97/codex-rs/core/src/tools/spec_plan.rs#L1425-L1428), [read-only network policy](https://github.com/openai/codex/blob/970111f6cb62cc02fe36a82ea7d71b37a2889c97/codex-rs/protocol/src/protocol.rs#L1315-L1319), [system config loader](https://github.com/openai/codex/blob/970111f6cb62cc02fe36a82ea7d71b37a2889c97/codex-rs/config/src/loader/mod.rs#L274-L293).

**動作審查。** `config.toml [action_review] mode = "off" | "shadow" | "enforce"`，預設 `off`，每次呼叫都重讀（`system.update_config` 接受 `action_review.mode`，變更記為受保護鍵）。只在所有靜態閘門都判定可自動執行、且工具有副作用時才審查。審查者是 utility 模型，透過封閉選項的 `decide()`（`duduclaw-gateway/src/decide.rs`）：回覆必須剛好是 `{"choice":"allow"|"ask"|"block"}` 並符合嚴格 JSON 契約，其他一律視為沒有判定。輸入只有結構化資料：工具名稱、類型、參數的鍵（不像識別字的鍵只計數）、ActionGuard 的封閉 finding token，以及員工 `CONTRACT.toml` 的 `must_not`。參數值不會進入提示。`shadow` 不改變結果，只在 `tool_calls.jsonl` 寫一列，`action_review` 欄位是判定或 `unavailable`。`enforce` 遇到 `block` 拒絕，遇到 `ask` 或沒有判定時透過 ApprovalBroker 問人。不認得的 mode 值，或 `config.toml` 存在但讀不到、無法解析時，視為 `enforce`。2026-10-08 收尾起，審查也會對 OS 動作工具（情境分類器放行之後）、`skill_hub_install`（在它安全掃描後的安裝核准之前），以及 gateway 電腦操作路由中沒有被任何核准清單送去問人的 `computer_*`、`computer_workspace_*` 工具執行；其餘不變（只有結構化輸入、`shadow` 只記錄、`enforce` 遇到 `block` 拒絕，其他問人）。有一個 dispatcher 測試以固定的審查回答（block、ask 後核准、ask 後拒絕、沒有判定）對真實的行程內核准資料庫跑完整流程。

**第三方 MCP 工具（2026-10-08）。** 員工其他 MCP 伺服器的工具，在 DuDuClaw 位於其路徑上的地方分類：`duduclaw mcp-proxy`（`.mcp.json` 啟動的伺服器）與 `duduclaw mcp-remote-bridge`（遠端伺服器），兩者都經閘道內同一道第三方工具閘門。分類預設為 `modify`；`destructiveHint: true` 提高為 `delete`。上游 `readOnlyHint` 不得降低風險，即使伺服器列在舊的 `trusted_read_hint_servers` 設定中也一樣；該設定不再影響分類。目前沒有主機管理的唯讀例外，探索通道不開放第三方工具。`action_rules` 與 DuDuClaw 自己的工具同樣適用（工具規則寫 `<伺服器>.<工具>`、`mcp__<伺服器>__<工具>` 或 `<伺服器>.*`）：`block` 會從員工看到的清單隱藏該工具，呼叫在送到伺服器前以 `-32003` 回覆（稽核 `third_party_tool_refused`）；`ask` 讓呼叫等待 ApprovalBroker 決定，核准系統無法使用、請求失敗、被拒或逾時都會拒絕（稽核 `third_party_tool_approval`）。探索通道中只列出、只能呼叫 `read` 工具。所有受管理的 runtime 都讓 `.mcp.json` 的 stdio 伺服器經過 proxy，不受遮蔽或 `action_rules` 是否啟用影響；受管理的遠端連線走橋接。直接 `url`／`type` 項目遭拒。`[[mcp.external]]` 的 stdio 與 HTTP 掛載透過行程內工具註冊表使用同一閘門，保留 annotations 並檢查清單與執行；utility 與探索通道維持不掛載 `[[mcp.external]]` 伺服器。儀表板（`mcp.tool_effects`）依目前設定重新計算，顯示每個伺服器最近一次列出的工具與類型、決定。說明：[MCP 生態系](../../guides/zh-TW/mcp-ecosystem.md)第 4 節。

**涵蓋範圍。** 其他 MCP server 的工具只經 proxy 與橋接分類（見上）。內建工具的規則只在以 DuDuClaw 工具旗標啟動 Claude CLI 的地方生效；其他 runtime 沒有 Claude Code 內建工具。分類以工具名稱為準，所以效果隨參數改變的工具一律取較嚴格的類型。這幾層都還沒在真的 gateway 與真的模型上跑過，目前只有單元測試與 dispatcher 層級的測試。

## 員工動作的單次核准（ActionGrant）

2026-10-08 新增（v1.72.0）。改動前，每個需要人核准的工具呼叫都會建立自己的請求、等那一筆的決定，所以核准不會被之後的呼叫重複使用；缺的是「綁定」：卡片看不到參數，決定也沒有綁在實際執行的那次呼叫上。現在，工具屬於 `send` 或 `purchase` 類（例如 `mail_send`、`odoo_sale_confirm`），或因 `action_rules` 的 `ask` 而需要人核准的呼叫，請求會帶 `payload.action_grant`（`duduclaw-gateway/src/approval/action_grant.rs`）：

- 員工、工具、動作類別、員工＋工具＋正規化參數（物件鍵排序）的 SHA-256 指紋，以及最多八行 `鍵 = 值` 的摘要（只取識別字形狀的參數鍵與純量值；看起來像機密的鍵與值用 `tool_calls.jsonl` 同一套遮蔽，字串截 60 字，巢狀值只顯示數量）。卡片文字與收件匣詳細面板（「這份核准涵蓋的內容」）都會顯示。
- 核准後，存下的綁定必須與即將執行的呼叫一致（同員工、工具、指紋），並在呼叫前消耗一次（`approved → invalidated`，原因 `consumed:action_grant:<uuid>`）。不一致、搶輸或第二次使用都算拒絕。

2026-10-08 收尾起，另外三條需要人核准的路徑也一律這樣綁定（不只 `send`／`purchase`）：MCP 派工閘的 PolicyKernel `ask`、OS 動作工具的情境閘（`anomaly`／`sensitive`，或動作審查的 `ask`），以及 gateway 電腦操作路由中 `computer_*`／`computer_workspace_*` 的核准清單。電腦工具綁定的是 gateway 自己組出的操作快照（輸入的文字與網址只留雜湊，所以卡片只顯示字數或驗證過的主機，不顯示原文），而且 gateway 在消耗核准後會重跑工具閘。聊天中的電腦操作高風險確認本來就是單次且綁定的（`ExecutionBinding` 綁動作雜湊、截圖雜湊、政策版本與決定情境，以 `claim_operation`／`begin_execution` 只認領一次，並和新的截圖重新比對）。workflow 保留自己的綁定：需要人的步驟只能透過帶綁定的請求核准，請求的 payload 與 `ExecutionBinding` 必須等於該步驟的呼叫，操作在 fence 之下認領，所以本來就只涵蓋那一步。安裝核准不變。未涵蓋：指紋算的是核准閘當下的參數，這時 PolicyKernel 改寫與機密還原已經發生；能存取資料庫的人可以同時改掉存下的內容與卡片。目前只有單元與 broker 測試。

## 用 @ 呼叫員工依發話者權限判斷（v1.76）

v1.76 之前，`[agent] trigger` 的比對是不看發話者、不分邊界的子字串比對：只綁定一位員工的 WebChat 帳號打別人的觸發詞就能叫到別人，任何 LINE 好友也一樣。現在先解析發話的真人（WebChat 用 dashboard 帳號；通訊軟體用**已驗證**的 `channel_identities`，沒有就視為未綁定），只在這個人叫得到的員工裡比對：管理員全部；每個人都叫得到這個對話的預設員工，以及 `[channels] public_trigger = true` 的員工（只有管理員能改，員工自己改不了）；dashboard 帳號與綁定了帳號的通訊軟體使用者另外加上綁定的員工。叫其他員工會在呼叫模型前被拒絕，並以 `trigger_route_refused` 記進 `security_audit.jsonl`（記帳號，或以這台機器的金鑰 `trigger_audit.key` 算出的平台 ID HMAC）。停用中的帳號，綁定不再算數。任何查詢失敗都當成未綁定處理。被叫來的員工在自己的 session 回答，對話紀錄與機密不會在員工之間混用；但在群組裡，回答仍是所有成員都看得到。細節見[用 @ 呼叫 AI 員工](62-calling-ai-staff.md)。

## dashboard 權限每次呼叫即時讀取（v1.76）

v1.76 之前，dashboard 的 WebSocket 連線一直沿用握手時讀到的角色與員工綁定，access token 又有 30 分鐘效期，所以拿掉綁定、降級或停權，要等對方下次登入才生效。現在 RPC 派送的單一入口每次呼叫都從 `users.db` 重建呼叫者的身分；token 只用來證明「是誰」。角色、直接綁定、必須改密碼的旗標，以及下面的主管關係推導，全部以資料庫為準。任何會改到這些的寫入（綁定、解綁、改角色或密碼、改狀態、改主管、通道身分、改 email、離職）都會在同一個交易裡把計數器（`auth_meta.acl_generation`）加一，每次呼叫的快取以這個計數器為鍵，所以快取的結果不會比最後一次這類寫入還舊。帳號不存在或不是在職狀態，回 `account is suspended or offboarded`；讀不到資料庫時這次呼叫回 `authentication service unavailable`，不沿用 token 裡的任何東西，`system.doctor` 會顯示啟動後發生過幾次。資料庫讀取和登入的密碼檢查都在 blocking 執行緒池跑，一陣登入不會拖慢其他連線的呼叫。閘道管理 token（`system`）與鎖定畫面連線不變。

帳號現在可以有一位直屬主管（`users.manager_user_id`，只有多人團隊版，經 `users.create`／`users.update` 設定）。同一次 `users.create`／`users.update` 的所有欄位在一個交易裡寫入，主管或降級被擋時，這次請求的其他修改也不會套用。寫入會擋下繞成一圈（`manager_cycle`）、一條主管鏈超過 8 個人（含最上層，`manager_too_deep`）、主管角色低於主管或不在職（`manager_role`、`manager_inactive`）；還有直屬部屬的人不能降成員工（`manager_has_reports`）；離職時部屬改掛 `transfer_to` 或離職者的主管，每一筆以 `user.reparent` 記稽核；轉給 `transfer_to` 的綁定，若對方原本就綁了同一位員工，保留兩者中較高的等級。系統會算出主管可以碰到部屬綁定的員工（最高 Operator），但這一版還沒有任何地方用到：路由、`agents.list` 與 Operator 等級的 RPC（記憶、對話紀錄、設定）仍然只看直接綁定。

## 人修改 AI 員工設定檔（v1.76.0）

人格設定、自我介紹、工作規則、行為界線（`SOUL.md`、`IDENTITY.md`、`INSTRUCTIONS.md`、`CONTRACT.toml`）可以由員工的負責人與管理員在儀表板修改，每次存檔都先檢查再生效（拍板 D7）。誰能寫，每次呼叫都從 `users.db` 重新讀取，寫入前在檔案鎖內再讀一次，所以檢查進行中被解除綁定也會擋下寫入。先跑固定規則（大小與控制字元、嚴格解析行為界線、隱藏或看不見的內容、新增文字裡的注入句型、像金鑰的文字、人格設定被刪掉大半、行為界線刪掉某條）。接著由部署的輔助模型看差異：被改的文字包在帶隨機 nonce 的標籤裡、先去掉隱藏內容，回覆必須完全符合固定格式。模型只能讓結果更嚴。檢查沒完成至少算警告，不會當成通過，也不能關掉。非管理員遇到高風險只能送管理員審核（`agent_file_change`，只能在儀表板決定，通道只收沒有按鈕的通知）。這個檢查看的是人送出的內容，`agent-file-guard` 照舊擋員工自己寫這些檔。每次寫入都在員工資料夾外留版本並寫 `agent_file_changed`，被拒絕寫 `agent_file_change_refused`。INSTRUCTIONS.md 現在和 SOUL.md 一樣有自己的核可指紋。同一版也擴大只限管理員的 `agent.toml` 欄位（bot token、`[odoo]`、`[runtime] provider`／`fallback`、`[prompt] cli_bare_mode`、`[os_watch]`、`[model] account_pool`、`role = "main"`、放寬預算），見[儀表板設定](../../guides/zh-TW/dashboard-settings.md#設定檔v1760)。

## 工作替誰做（`on_behalf_of`，v1.76.0）

由真人發起的工作（一輪對話、`/交辦`、dashboard 建的任務），gateway 現在會把「這是替誰做的」一路帶下去：員工的 runtime 會拿到 `DUDUCLAW_ON_BEHALF_OF`（所有 runtime，不只 Claude）；`send_to_agent`／`spawn_agent` 把它寫進佇列（`message_queue.on_behalf_of`、`bus_queue.jsonl` 欄位），派工器再套到接手的那一輪；目標任務的每一輪與 heartbeat 喚醒從任務列（`tasks.on_behalf_of`）抄過來；`tasks_create` 建的新任務會記上；這一輪提出的核可也會存（`approvals.on_behalf_of`）。值是 `user:<帳號 id>`（WebChat 帳號或已驗證的通道身分），或 `unmapped:<通道>:<摘要>`（沒有帳號的發話者，用的是 `@` 路由稽核同一把金鑰的 HMAC，不會出現平台原始 id）。來源只有 gateway 寫的東西：spawn 時設定的環境變數，以及 gateway 或 MCP server（依該環境變數）寫的資料列，絕不讀工具參數。系統發送者名稱（`dashboard`、`cron` 等）、保留 id、格式不對的值一律拒收，並記為 `on_behalf_of_rejected`；第一個寫入的值為準，下游不覆寫。各 runtime 設定本次執行的值之前，會先移除繼承來的值。

這一版的作用：

- **記錄**（預設，`[delegation] human_principal = "record"`）：該輪的每一筆 `tool_calls.jsonl`、每一筆 `delegation_denied`、每一張核可都帶著它，通道核可卡片顯示「由 ○○ 交辦」（優先顯示名稱，找不到時用帳號短碼）。不會因此拒絕任何事。
- **強制**（`human_principal = "enforce"`，需自行開啟；值無法辨識或 `config.toml` 讀不到也視為強制）：員工組織樹允許一次委派之後，還要真人也有權限。`send_to_agent`／`spawn_agent` 與派工器的委派閘門要求這個人能呼叫目標（Admin；直接綁定或主管的團隊推導，任何等級；或 `public_trigger` 員工）；`tasks_create`（員工指派給自己也算）、`create_task`、排程、看別人信箱與修改別人的任務要求 Operator 以上。未對應帳號的發話者只能到 `public_trigger` 員工，且不能交辦。帳號不存在或停用、值格式不對、`users.db` 讀不到，一律拒絕（`human_principal_not_permitted`）。目標任務每一輪、heartbeat 喚醒與 cron 沿用建立時的委派授權；main/default 目標限制仍會在執行時檢查。

強制模式下，獨立 MCP 程序會向正在執行的 gateway 查驗真人權限。它只送主機建立、綁定員工與 home 的不透明參照；gateway 以當下帳號資料驗權；團隊授權必須同時有已驗簽的 Enterprise license，且該 home 的 gateway 已解析為 Enterprise。任一條件為 Personal 或未知就不給團隊授權，不接受本文指定的真人或 Enterprise 環境變數當作證明。背景工作也必須有主機明確登記的 None context：缺少、跨員工／home、過期或已釋放的參照都會拒絕；主機紀錄與 MCP 的身分標記不一致也會拒絕。參照在 runtime 返回或 24 小時後失效，同時最多保留 4096 筆。預設記錄模式不需要此路由。這份 context 與知識庫 requester 分開，不會增加文件存取權。

- `[approval] forbid_self_approval = true`（預設關）：AI 員工替某人辦事時提出的核可，不能由同一個人自己同意（dashboard 與通道按鈕都一樣，拒絕仍可以）。綁定式請求不變，只由綁定的那個人決定。

電腦操作 start／action 的核可，依已驗證的員工與 `turn_id`，從主機登記的進行中對話取出真人。請求參數不能指定真人，也不能借用另一位員工的對話。沒有或查不到 turn 時不記真人，因此無法在這些請求辨認自批者；沒有 turn 的工作區、截圖與停止請求也不記真人。

真人檢查只會收窄員工權限。記錄模式仍依賴主機帶入的標記，不強制權限；強制模式下，單改真人環境變數不能改變 gateway context 登記的人。這不是作業系統隔離：同一個 OS 帳號下、有不受限 Bash 的員工，仍可能讀取程序憑證或改寫本機資料庫。用 `tasks_create` 建的排程，之後每次執行不會帶上這個人。`spawn_ephemeral` 及其延後准入佇列也還沒傳遞真人身分。Grok 與已棄用的 Gemini CLI 不保證會把 spawn 環境轉交給 MCP 子程序。

本機已驗證：關閉 dashboard feature 的後端單元、整合與文件測試；原 dispatcher 回歸在預設堆疊通過；以及真實 stdio MCP 子程序呼叫簽名內部路由。native fixture 使用臨時測試 issuer 簽署的 license，涵蓋 Enterprise AND 條件、團隊 Manager 交辦、Viewer 只能呼叫、即時撤權／停權、明確背景 None 與缺少／跨員工／失效／不一致 context。這不代表正式 issuer、真模型呼叫 `send_to_agent` 或實機通道驗收；預設 dashboard feature 另由 CI 檢查。

## 支撐層

**員工預算。** `[budget] daily_cap_cents` 與 `monthly_limit_cents` 分別比對最近 24 小時與 30 天的已記錄花費，`hard_stop = true` 時達上限就拒絕下一次模型呼叫；0 代表不限額，執行中的呼叫仍可能超過上限。檢查涵蓋 Claude 與其他員工後端、派工與排程、提醒、郵件、心跳、輔助工作及 CLI 分支／評測。短期員工的已記錄花費也算進父員工，先以千分之一美分加總，再換算美分。員工設定檔可讀時，`[budget] when_unavailable = "allow"`（未填時的預設值）會在費用資料庫或查詢讀不到時留下明確警告與稽核紀錄並繼續；設成 `"deny"` 則在模型呼叫前拒絕。設定檔本身讀不到或無法解析時，無法確認這項政策，一律拒絕。未知政策值按 `"deny"` 處理並警告。無法檢查會顯示自己的原因與稽核事件，不會說成「花費達上限」，也不會發出斷路器開關通知。預算拒絕不觸發帳號輪替或備援。沒有員工 id 的呼叫不適用此政策。 指定員工目錄的輔助呼叫，以有效設定的 `[agent].name` 檢查預算並記錄後續花費，即使呼叫端原本使用作業名稱。舊有只記在作業名稱下的費用，無法可靠回填到各員工。

**MCP 授權閘** — 每個 MCP 工具都在 scope 表裡逐項列舉；沒被列的工具預設需要 Admin scope。Scope、per-agent capability 授權、`denied_tools` 三者各自在分派總門強制，每次拒絕都帶 `error_class` 落稽核。

**SOUL.md 漂移偵測** — `soul_guard` 在開機與每次 heartbeat tick 以 SHA-256 對每份 `SOUL.md` 取指紋，在 `.soul_history/` 保留最多 10 個版本備份，並連同 Agent Stability Index 一起回報漂移。

**稽核軌跡** — `tool_calls.jsonl` 記錄每次工具呼叫，`result_text`／`input_text` 都經遮罩（三輪秘密遮罩，先遮再截斷），權限 `0600`，行與行之間雜湊串接，16 MB 輪替。`security_audit.jsonl` 另外承載安全事件。這份 log 同時是 grounding precheck 與驗收判官讀的證據來源，弱化它等於弱化驗證。

**每 agent 金鑰隔離** — MCP API key 與連接器憑證都是 per-agent，經 `secret_ref` 解析，所以單一 agent 外洩不等於平台外洩。通道憑證分兩種：LINE、WhatsApp、飛書、Google Chat、Teams、企業微信、釘釘使用 `config.toml [channels]` 裡整個部署共用的憑證；只有 Telegram、Discord、Slack 有員工專屬的 bot token（員工沒有自己的 token 時沿 `reports_to` 往上找，最後用全域 token）。

**Google Chat Pub/Sub（v1.80.0 起）** — Pub/Sub 通知不作為 Chat 傳訊者的身分證明。閘道嚴格驗證訊息資源名稱，先以應用程式的 `chat.bot` 向 Chat API 回讀，再建立回合；傳訊者、聊天室、本文、附件與討論串均取自 API，回應名稱與聊天室必須符合資源及通知聊天室。既有傳訊者存取、配對與核准規則仍生效。回讀失敗（包括 403／404）或沒有訊息的事件不建立回合。匯入與啟動時驗證訂閱指向服務帳戶專案的固定主題，拉取另用只有 `pubsub` scope 的權杖。僅支援 Unix 的持久化收件匣只存資源參照，不存本文、傳訊者資料或附件；以事件類型與資源名稱去重七天，API 建立時間超過七天的訊息在清理後仍拒絕。每個 app stream（員工／共用 app 與專案編號）上限為 1,000 筆、10 筆 pending／queued／running，避免單一 stream 用盡部署容量；全域硬上限仍為 10,000 筆、100 筆待處理或執行中事件，每筆參照 2 KiB、資料庫 64 MiB；正在排隊或執行的紀錄不淘汰，中斷的執行標為 uncertain 且不自動重跑。佇列滿時確認收件並丟棄，不啟動回合。資料庫與附屬檔案均驗證私密權限，其他平台在具備等價防護前拒絕 Pub/Sub。Pub/Sub 建立腳本先驗證雲端資源再建立金鑰，破壞性的復原指令只列出供人工處理。見[設定與投遞限制](../../guides/zh-TW/channels-googlechat-teams.md)。 匯入與 worker 啟動均拒絕啟用 exactly-once（恰好一次投遞）的訂閱，請在 Google Cloud 關閉該選項。ACK 無效或過期（HTTP 400）時只清除舊投遞批次並重新拉取，持久化去重紀錄仍保留；暫時性 ACK 失敗則保留批次重試。

**通道上的聊天指令（v1.68.0）** — `!STOP`、`!STOP ALL`、`!RESUME`、`/model <名稱>` 需要管理員。WhatsApp、飛書、Teams、企業微信、Google Chat、釘釘以前對每位傳訊者都傳 `is_admin = true`，能傳訊給 bot 的人都能停止或恢復它。現在這些通道用該通道的 `admin_users` 設定（全域範圍；Google Chat 與 Teams 也能設定了）完全比對傳訊者 id 或對話 id，沒有清單就沒有人是管理員。WebChat 只有啟用中、角色為管理員的儀表板帳號算數，網站聊天元件的訪客一律不算。

**緊急停止門檻（v1.68.0）** — `KILLSWITCH.toml [triggers]` 的四個門檻以前沒有讀取端。現在只有寫在檔案裡且數值在範圍內的鍵才生效，安全設定頁每個門檻多了一個勾選框（取消勾選會送 `null`，把它移除）。檔案改動後會重讀。`cost_limit_usd` 比對所有員工 24 小時的花費，達到時把全域 failsafe 等級降為受限，直到 failsafe 自行恢復或有人送 `!RESUME`；`max_replies_per_minute` 依對話計算，超出的訊息靜默丟棄；`max_consecutive_errors` 與 `error_rate_threshold`（最近 20 次、至少 10 次）讓該對話的 failsafe 升一級。每次觸發記稽核 `killswitch_trigger`。`KILLSWITCH.toml` 的 `[audit]` 區段不再讀取。

**回覆斷路器與分好幾則傳訊息的人** — 每個通道回覆前、依對話計算的斷路器（`KILLSWITCH.toml [circuit_breaker]`）以前在三種很平常的情況會靜默丟掉訊息：上一則回覆比最近幾則長很多之後的下一則訊息（`token_explosion_multiplier`，這是我們自己輸出的特性）、連續三則相似的訊息（例如等回覆時傳的「在嗎？」）、`frequency_window_secs` 內超過 `frequency_max_replies` 則訊息。斷路之後整個對話在 `cooldown_secs` 內都不回，failsafe 等級還會升一級，反覆斷路最後變成受限回覆或靜音。現在回覆過長只記紀錄；少於 20 個字的訊息不算重複；超過頻率上限的訊息會等到視窗有空位再回答；等了 30 秒仍沒有空位（大量灌訊息）的那則不回答，但仍會計數，發話者每分鐘最多收到一次說明。仍會斷路的有三種：完全照抄我們上一則回覆的訊息、連續三則長而幾乎相同的訊息，以及新增的硬上限：同一個對話在 `hard_window_secs`（預設 60 秒）內超過 `hard_max_messages`（預設 30）則，用來擋兩個機器人互傳短而不同的訊息。通道標示為機器人的發話者（Telegram `is_bot`）維持舊的嚴格規則，短時間窗超過頻率就斷路。原有設定的名稱與範圍不變。管理員可在安全設定頁的緊急停止卡（進階：斷路器門檻）修改這兩個新值；`killswitch.update` 改用共用的設定寫入流程寫 `KILLSWITCH.toml`（檔案鎖、讀取後檔案被改過或無法解析就拒絕、保留註解）。

**去識別化的資料來源保護（v1.68.0）** — 「隱私 / 去識別化」分頁的「資料來源保護」開關開始生效：`user_input` 在通道訊息送進 AI 前遮蔽，`system_prompt` 遮蔽組好的提示（預設只套用標了 `apply_to_system_prompt` 的規則），`cron_context` 遮蔽條件腳本的觸發訊息。出錯時停止這一輪，不送出未遮蔽的內容。`sub_agent`（在同一個分頁或 `config.toml [redaction.sources]` 設定）負責受委派員工的回覆被 gateway 寫進委派方對話紀錄的那條路（`send_to_agent`、`spawn_agent`、`spawn_ephemeral` 的回覆，包含轉寫給發起整條委派鏈那位員工的副本）。設為 `on` 時，回覆先用接收方員工的規則遮蔽再存進紀錄，等那位員工回覆使用者時再還原。預設 `inherit` 照原樣寫入，因為子代理本來就在同一套 `[redaction]` 規則下執行。遮蔽出錯時改存一段固定的提示文字，不寫入原文。不涵蓋：送到使用者通道的那份回覆（那是使用者自己看的）、員工用 `check_responses` 自己去取的回覆（屬於工具結果，依 `tool_results` 處理）、團隊角色之間的交接、Agent Mail。`purge_after_expire_days` 現在決定保管庫清理的天數。

**權限旗標（v1.68.0）** — `agent.toml [permissions]` 的 `can_create_agents`、`can_send_cross_agent`、`can_modify_own_skills`、`can_schedule_tasks` 寫成 `false` 時，MCP 分派閘會拒絕對應工具（稽核 `permission_denied`）。升級後第一次開機會把舊範本的 `false` 改成 `true`，見[儀表板設定對照](../../guides/zh-TW/dashboard-settings.md#ai-員工編輯頁)。

**Rootless 容器引擎（DuDuClaw OS v0.4.0）** — 從 DuDuClaw OS v0.4.0（內嵌平台 v1.73.4）起，閘道以非 root 的 `duduclaw` 帳號執行，容器改用 rootless Podman，閘道經 `DOCKER_HOST`／`CONTAINER_HOST` 連線；v0.3.0 以前的映像，閘道與 Docker 仍以 root 執行。平台這邊配合兩件事：會清空環境變數的容器用戶端（任務沙箱、Discovery 嘗試與評分、清理）在閘道有設這兩個變數時只多帶這兩個，它們不在 AI CLI 的允許清單裡。腳本沙箱在 `mcp-server` 裡執行，所以閘道也會把這兩個變數寫進每位員工 MCP 設定中 DuDuClaw 自己那一項。容器引擎回報 rootless 時，任務沙箱、腳本沙箱、電腦操作與 Discovery 的嘗試和評分容器要先跑一個 32 MiB 記憶體、32 個行程上限的臨時容器，讀回它自己的 `memory.max` 與 `pids.max`；讀到 `max`（cgroup 控制器沒有委派時，引擎接受上限卻不套用）、讀到跟要求不同的值，或檢查沒跑完，這些功能就停用並說明原因（任務沙箱的代碼是 `resource_limits_unenforced`），不會在沒有上限的情況下執行。一般（rootful）Docker 不做這個檢查。結果沿用十分鐘（檢查失敗則一分鐘），容器引擎從無法使用恢復時立刻作廢。

**`duduclaw-sysd` 的呼叫者（DuDuClaw OS v0.4.0）** — DuDuClaw OS v0.4.0 把這個輔助程式的允許 uid 改成閘道的 uid，而這個 uid 也是 AI 員工的 CLI 執行身分，只比對 uid 的話，任何員工都能直接開 socket，繞過閘道的所有核准。這不只是可用性風險：`update_rollback` 會開回上一個系統槽，第一次升級成非 root 之後，那是閘道（連同員工）仍以 root 執行的舊映像；`ssh_service_start` 會打開網路服務。所以輔助程式新增 `--require-main-pid-of <unit>`：呼叫者必須是該 systemd 單元的主行程，透過 pidfd（`SO_PEERPIDFD`，Linux 6.5 以上）確認，閘道重啟後被重複使用的 pid 無法冒充，而且它必須位在該單元自己的 cgroup；同時最多四個檢查、每個最多兩秒，任何一步失敗都拒絕（非 Linux 主機上這個旗標一律拒絕）。這是選擇性開啟，舊的 OS 映像不受影響；v0.4.0 在閘道改成非 root 的同一版把它打開。它的前提是 yama `ptrace_scope` 至少為 1（員工行程是閘道的子孫，不能 ptrace 閘道），以及閘道從不把 sysd 連線交給子行程（每次呼叫開一條連線，建立時就設 close-on-exec）。變更時間設定的操作者終端指令（`duduclaw os system timezone-set`／`ntp-set`）也在獨立行程執行，打開旗標後會失敗並請操作者改用儀表板的系統設定。因此在獨立 `mcp-server` 行程裡執行的 `os_*` MCP 工具不再自己開 socket：在裝置上它們先過完自己的檢查，再經閘道的簽章本機路由（`/api/internal/sysd`）送出，這條路由只接受這些工具需要的指令（沒有 SSH、網路、主機名稱、時區與本地模型），由閘道自己呼叫 sysd。能讀到閘道金鑰檔的同一使用者行程仍可簽章呼叫這條路由，路由把這種呼叫者能做的事限縮在上述指令，其中的回退之所以安全，是因為 sysd 會拒絕舊的目標（見下一段）。帶參數的指令也依「呼叫者不可信」重新檢查：主機名稱改成最長 64 位元組的 RFC 1123 名稱（之前只檢查長度，`-` 開頭的值會被 `hostnamectl` 當成選項）；時區與網路介面名稱必須以英數字開頭；這類值一律放在 `--` 之後。輔助程式另外多了固定的本地模型指令（只能停止或重啟那一個模型服務），閘道不再自己執行 `systemctl`。恢復原廠改成一個指令，連同「一併清除網路設定」的選擇一起送：映像有 `duduclaw-factory-reset.service` 這個 oneshot 時，寫入 `/data/system/factory-reset.pending` 後重開機，由 oneshot 在閘道啟動前清除閘道資料、kiosk 家目錄、閘道的容器儲存區與（有勾選時）Wi-Fi；較舊的映像照舊立即清除，改由 root 端執行。閘道遇到舊版輔助程式時會拒絕恢復原廠、不刪任何東西，裝置上連不到輔助程式時也一樣。閘道與輔助程式必須來自同一版 OS 映像。

**非 root 閘道擋得住什麼、擋不住什麼（DuDuClaw OS v0.4.0）** — 在 DuDuClaw OS v0.4.0 以後的映像上，拿到 shell 的 AI 員工就是以閘道的使用者身分執行。它讀得到閘道的金鑰，所以閘道能做的事它都能做，包括偽造閘道的簽章內部請求與儀表板登入狀態。閘道改成非 root，是讓這樣的員工碰不到 root，不是讓它碰不到閘道本身的權力。原本的規則仍然成立：真正的隔離是不給 Bash，或把工作放進任務沙箱。所以防止取回 root 的關卡不信任任何呼叫者：`duduclaw-sysd --min-rollback-version <版本>`（第一個閘道非 root 的版本 v0.4.0 把它設成自己的映像版本 `1.73.4-y1-bringup`）在回退可能開機的任何項目比這個版本舊、或無法從開機映像本身（內嵌的 `os-release`，並與檔名交叉核對）讀出版本時，拒絕回退。Type #1 開機項目（`loader/entries/*.conf`）無法同樣嚴格地核對，只要存在就拒絕回退。安裝更新原本也是一條回到 root 的路：系統更新程式會安裝來源目錄裡的任何東西、不做檢查，而那個目錄就是閘道自己的下載資料夾，同一使用者的行程可以放進任何映像（包括改名成較高版本的舊簽章映像）。現在安裝改走輔助程式的新指令：以 root 用內建在輔助程式裡的 OS 簽章金鑰驗證版本的簽章校驗清單，只把清單列出的檔案（不跟隨連結、只接受一般檔案、邊複製邊比對雜湊）複製到只有 root 能存取的暫存目錄，挑出綁定目的槽位的開機映像，並且只有在該映像內嵌的版本比目前執行的新、也不低於回退下限時才安裝。閘道自己的檢查保留，用來更早給出清楚的錯誤。原本的安裝指令不再能經閘道內部路由呼叫。清除用盡的開機項目只會刪掉它。輔助程式管不到的部分：開機載入器自己的開機計數，在新項目被標記成功前連續三次開不起來時會退回另一個項目，所以 v0.4.0 在第一次開機被標記成功後，會刪掉比下限舊的開機項目。這讓升級變成單向：v0.4.0 映像成功開機過一次之後，裝置就回不去 v0.3.0 或更早的版本，之後的版本出問題只能裝更新的映像或用救援項目。第一次開機被標記成功之前，舊的 root 閘道項目仍是開機載入器的備援，新映像上的員工可以故意讓試開機失敗回到那裡；這個窗口只有幾次開機。

**維修 SSH 改用專用帳號與臨時金鑰（輔助程式端，v1.75.0，目前還不能用）** — 輔助程式新增 `ssh_maint_open`、`ssh_maint_status` 兩個指令，讓維修登入改用專用帳號（`duduclaw-maint`，uid／gid 4800）加上每個視窗一把公鑰。閘道與 AI 員工是同一個使用者，所以金鑰只由輔助程式決定：只收一把（Ed25519、ECDSA P-256／P-384／P-521、兩種 FIDO 安全金鑰，或 3072–8192 位元、指數為奇數且不超過 64 位元的 RSA），解碼後逐欄檢查型別與長度，拒絕 `authorized_keys` 選項、憑證、私鑰（OpenSSH、PEM、PuTTY）、RFC 4716 區塊，以及多把或多行；寫進檔案的只有固定選項（`no-port-forwarding,no-agent-forwarding,no-X11-forwarding`）加上解碼後位元組的標準編碼。金鑰檔放在 tmpfs（`/run/duduclaw-maint-ssh/authorized_keys`，root:duduclaw-maint 0640），經目錄控制代碼寫入、不跟隨符號連結，以不會覆蓋既有金鑰的 rename 放到定位，再讀回比對。寫入前輔助程式先檢查實際生效的設定（systemd 合併後的單元與已載入的 nftables 規則）：OS 的就緒標記、帳號的 uid 與 gid、dropbear 合併後的指令列與預期值逐個 token 相同、dropbear 的單元綁在輔助程式上（`BindsTo=`）、拒絕這個帳號 loopback 流量的防火牆規則與通往它的跳轉，以及 22 埠只收區網／VPN 來源的集合；任何一項不符就拒絕開窗。視窗在下列情況結束：輔助程式自己的期限到（最多 24 小時，以 `CLOCK_BOOTTIME` 計，改系統時間延長不了）、閘道關閉、輔助程式重啟時發現殘留，或輔助程式停擺時由它開窗時掛上的 systemd 臨時計時器收回（關窗時會撤掉）。輔助程式每 15 秒從 journal 讀登入與登出，只認 journald 自己填的欄位（`_SYSTEMD_SLICE=system-dropbear.slice`、`_UID`），寫進只有 root 能讀寫的稽核檔 `/data/system/maint-ssh-audit.log`；這件事不經過閘道，閘道停掉或被入侵都不會讓這些紀錄停止寫入。輔助程式等稽核檔的鎖最多幾秒：寫不進去時視窗不會打開；關窗時則回報問題，把紀錄（以及還沒讀到的 journal 事件）留著，之後寫進去為止。視窗狀態與 journal 讀取位置存在持久儲存上只有 root 能存取的目錄（`/data/system/maint-ssh/`），視窗期間重開機也抹不掉登入紀錄：下次開機的清理會從存下的位置重讀 journal，並以 `reboot` 寫入關窗紀錄。視窗開著時，每次檢查也會重讀防火牆的維修出站規則，規則不見就關窗。開窗有頻率限制（間隔至少 5 秒、每小時最多 12 次）。事件裡的字串截到 128 字元並去掉控制字元。每個視窗前 50 筆登入逐筆寫，之後只計數；檔案輪替時會把本視窗的開窗紀錄重寫到新檔開頭。映像有這個帳號時，舊的只開埠 `ssh_service_start` 會被拒絕。這兩個指令都不能經閘道給 `os_*` 工具用的內部路由呼叫。要等 OS 映像帶上這個帳號、閘道與儀表板部分也完成後才能使用。

## 文件知識庫

[文件知識庫](63-knowledge-base.md)讓 AI 員工搜尋上傳的文件集合。它的守衛：

- **集合層級、預設拒絕的權限**，由單一函式在 SQL 裡決定：讀取需要授權給員工（或其部門），也要授權給這個 turn 所服務的人；群組對話排除 `personal` 與 `restricted` 集合。讀不到的授權一律不算；不存在的段落與沒權限的段落回應相同（`permission denied`）。
- **解析在子程序裡做**：每份文件由 `duduclaw knowledge-extract` 讀取，有時間上限、CPU 上限、Linux 的位址空間上限，以及 macOS 與 Linux 上禁止寫入、禁止連網、讀取只限該檔案、解析程式與系統函式庫的沙箱；沒有沙箱時預設拒收，除非管理員明確開啟。Office 檔先通過壓縮炸彈檢查，`.xlsx` 逐格讀取並有上限。解析器當掉只會結束那個子程序。
- **文件內容是資料**：匯入時掃描像提示注入的文字並標記；工具結果把內容放在每行以 `│ ` 開頭的標記區塊裡，文件無法偽造結果標題。gateway 沒有登記的 turn 發出的工具呼叫什麼都讀不到。放進回覆 prompt 的段落在 `<knowledge_passages>` 區塊內做 XML 跳脫，疑似指令的段落不會自動帶入，system prompt 也寫明段落是資料；最後這點只是 prompt 規則，模型仍可能不遵守，所以另有 `answer_mode = "kb_only"`。
- **回覆是替誰回答**由 gateway 判斷，不由模型決定：WebChat 用登入的帳號；通訊軟體的發話者只有透過**已驗證**的通道綁定才對應到帳號；其他人（包括公開小工具與網站即時客服的訪客）只算該通道。公開訪客只讀得到 public 集合。排程是系統 turn，只能用授權給員工的 public、internal 集合；從某個人的 turn 派出去的工作沿用那個人的範圍（未綁定發話者的派工仍只有通道授權）；來自無法辨識 session 的回覆什麼都讀不到。
- **群組會看到引用，這是設計如此**：已綁定發話者自己與部門的集合可能在群組裡被引用，回答與來源頁尾群組裡每個人都看得到。personal 與 restricted 集合在群組裡一律不用。
- **從儀表板以外加入一律要有人核准**：`knowledge_add_source` 與聊天指令「加入知識庫」只會開一張只能在儀表板決定的審批單，決定的人在那一刻必須是管理員或該集合的編輯者。審批單存的是內容雜湊、文字預覽與提出的對象；檔案被改過，核准時就會拒絕。只有通道替該發話者存下的檔案才算（在訊息裡打出的檔案參照不算），訪客與未綁定的發話者不能送審，待審數量也依員工與提出者設上限。
- **網址來源**套用公開網頁的抓取規則（不接受內部位址、帳號密碼、轉址，上限 5 MB）。
- **稽核**：每次讀取都寫入知識庫存取紀錄；集合、權限與刪除的變更另外寫進 `security_audit.jsonl`。
- **向量遵守同樣的權限**：計算相似度之前，向量清單就先限縮到允許的集合，所以不能讀的集合佔不到 top-k 的名額。
- **向量模型固定版本**：每個模型檔與 ONNX Runtime 壓縮檔都寫明大小與 SHA-256，並固定在同一個 commit；下載或離線安裝包對不上就拒絕，只有完整驗證通過的安裝才算數。解出來的 ONNX Runtime 執行庫本身也有固定的雜湊，載入前會先比對（去識別化的 AI 偵測也一樣），手動放進去的執行庫一律拒絕。離線安裝包用發行金鑰做 minisign 簽章，解開前先驗簽，解開時只寫入預期的一般檔案。自訂的雲端端點必須是公開的 `https` 位址（每次請求都重新解析並固定連線位址），除非管理員設定 `allow_private_endpoint`；揭露確認紀錄不能在設定檔進階編輯裡新增或修改。本機模型不會讓文件內容離開這台機器。
- **雲端向量需主動開啟，出錯時一律不送**：管理員必須確認哪個供應商與主機會收到段落（綁定供應商、主機與模型，任何變更都要重新確認）。段落與提問先經過 `[redaction]` 規則，命中的內容換成類別標記；去識別化關閉、規則編譯失敗或沒有任何規則時，什麼都不送，搜尋只剩關鍵字。`restricted` 與 `local_only` 集合永遠不送。端點必須是 `https`（純 `http` 只允許連到 `127.0.0.1`），不跟隨轉址，供應商回傳的錯誤內容不保存（只留狀態碼），超過 32 MB 的回應拒收。去識別化的強制關閉開關會立刻停止送出；執行中的向量工作每一批都重新確認供應商、揭露確認與去識別化；切換供應商時，前一家的端點與模型設定會清掉。安裝、移除與切換供應商都寫進 `security_audit.jsonl`。

尚未涵蓋：Windows 上的解析沒有沙箱（預設因此拒收）也沒有記憶體上限；心跳沒有 turn id 也沒有 run id，它的工具呼叫什麼都讀不到。規則式去識別化無法辨認送往雲端向量供應商的段落中的每一個人名（AI 偵測模型表現較好，但也不完美）。

## 指定人的憑證放系統金鑰圈（v1.76.0）

讓 AI 員工代表某一個人（例如同事的 Google 帳號）之後，憑證被偷的代價變高，所以這類憑證另外用一把金鑰。這把「保護金鑰」是 32 bytes 的 AES-256 金鑰；支援的桌面系統放在作業系統的憑證儲存區，Docker／原生 Linux 受保護服務模式則由 root 專用根金鑰包裝保存。代表特定人的憑證用它封存（`pk:v1:<金鑰代號>:…`）。全 home 共用的憑證（`.keyfile` 與它解密的 `*_enc` 值）不變。

- **預設關閉。** 管理員在「安全」頁的「憑證保護」卡片開啟（RPC `security.credential_protection_enable`）；`duduclaw credentials status` 印出同一行狀態。關閉時其他功能都不變，需要代表特定人的功能則拒絕執行。
- **macOS：** 項目放在登入金鑰圈，解密權限只信任建立它的 `duduclaw` 執行檔（以程式碼雜湊識別）。用 Claude 的 `Read`、`cat`、備份、`security` 或 Python 讀這把金鑰都會失敗；有人在 Mac 前面時，macOS 會先跳出詢問。gateway 自己讀取時不會跳對話框。注入 `duduclaw` 行程的程式碼也算 `duduclaw`：測試中把程式碼注入 ad-hoc 簽章的建立者，可以不經詢問讀到金鑰，開了 hardened runtime 就擋下。所以只有執行中的執行檔開了 hardened runtime，卡片才顯示「只有 DuDuClaw 程式讀得到」；目前發布的 CLI 還沒開，會顯示「同一個帳號的程式讀得到」並說明可被注入。升級後新的執行檔雜湊不同，個人帳號會暫停，直到有人在這台 Mac 上執行 `duduclaw credentials authorize` 並允許一次；其他功能照常。
- **Windows：** 金鑰放在認證管理員，不會出現在檔案或備份裡，但同一個 Windows 帳號下的任何程式都讀得到，包括能執行指令的 AI 員工。儀表板照實顯示。
- **一般 Docker 與 Linux 使用者服務：** 沒有隔離金鑰，代表特定人的功能維持拒絕。可改用下方 Docker 疊加設定或[原生 Linux 受保護系統服務](../../guides/zh-TW/linux-protected-service.md)。只有 gateway 收到金鑰，終端機憑證狀態不能代表 gateway。
- **原生 Linux 受保護服務：** v1.79.3 保護 root 提供的憑證金鑰，但員工 Bash／工具仍與 gateway 共用 UID。v1.80 開發中架構將員工身分、逐次執行命名空間、解析與更新分開；安裝器只準備可信元件，保留遷移閘，不會直接啟用完整隔離安裝。遷移平台與首位管理員設定流程仍缺接線。套件層級 root 測試已在 Ubuntu 22.04 kernel 5.15／6.8、Ubuntu 24.04 kernel 6.8、Debian 12 kernel 6.1 通過；GCP Ubuntu 24.04 kernel 7.0／Landlock ABI 8 目前會拒絕 trampoline 執行。這些測試不代表完整安裝或遷移驗收，前提、待完成關卡與復原邊界見[受保護服務指南](../../guides/zh-TW/linux-protected-service.md)。
- **Docker 加上 person-credentials 疊加設定：** 用 `docker compose -f docker-compose.yml -f docker-compose.person-credentials.yml up -d` 啟動（步驟見 [Docker 指南](../../guides/zh-TW/docker.md#74-個人帳號person-credentials-疊加設定)）。容器改以 root 啟動，在 `cap_drop: ALL` 之外只加回 `SETUID`、`SETGID`、`SETPCAP`。一支很短的啟動程式（`container/protected-key-launcher.sh`）把 32 bytes 的根金鑰放在只有 root 讀得到的磁碟區 `/var/lib/duduclaw-protected`，先以 `duduclaw` 身分跑首次設定，再殺掉首次設定留下的所有行程，然後在檔案描述元 3 開啟金鑰，以 `duduclaw` 身分、所有權限集合清空並設 `no_new_privs` 啟動 gateway。gateway 是 PID 1，它一停，容器裡其他行程全部跟著結束。它先把自己設為 non-dumpable 才讀金鑰，讀完關掉描述元，接著檢查：PID 1、使用者與群組都不是 root、所有權限集合是空的、`NoNewPrivs`、non-dumpable、自己打不開金鑰路徑、沒有 Docker 或 Podman socket、沒有 `DOCKER_HOST`。任一項不符就丟掉金鑰，個人帳號維持停用，卡片寫出原因。保護金鑰在 home 裡只以根金鑰包裝後的形式存在（`protected/container-wrapped-key.json`）；包裝檔被改動或來自別處，會顯示「保護金鑰被更換」。卡片顯示「獨立金鑰（AI 員工讀不到）」。
  - 實測環境是 Docker Desktop 7.0（arm64，沒有 Yama）。在同一個容器裡以 uid 1000 測試，也在 `unshare -Ur` 裡重測：開啟金鑰檔、`/proc/1/mem`、`environ`、`fd`、`root`、`maps`、`ptrace`、`process_vm_readv` 全部被拒；從容器內送 SIGKILL、SIGSTOP 停不了 PID 1。掛載 Docker socket、`--init`、少了 `SETPCAP` 都會被拒。還沒實測：完整的伺服器映像、Windows 上的 Docker Desktop、Podman 與 rootless Docker。
  - 代價：持有金鑰期間，gateway 不在自己的行程裡載入 ONNX 模型，因為員工改得到這些模型檔，而模型檔會進到原生的解析程式碼。AI 隱私偵測（NER）去識別化、本機知識庫向量與 Kokoro 語音會停止，知識庫搜尋改用關鍵字。**這時 NER 去識別化規則的行為和沒裝模型一樣：文字不會被這些規則遮蔽。**一定要 NER 去識別化的環境，請改用正規表示式規則，或不要開這個模式。
  - 擋不住：能執行指令的員工仍可以在權限內透過 gateway 使用 Google、讀到自己這一輪拿到的存取權杖、讓 gateway 停止，或在重新啟動後放回較舊的 home 檔案。最後這一項，儀表板的「換一把新金鑰」擋不住，因為根金鑰沒有變。懷疑外洩時，請更換金鑰磁碟區裡的根金鑰（見 Docker 指南）。能進入 Docker 主機或金鑰磁碟區的人讀得到根金鑰；同時備份了金鑰磁碟區與資料磁碟區的備份，就有解開憑證所需的一切。
- **金鑰被換掉就拒絕，不會拿來用。** macOS 上同一個使用者的任何程式都能不經詢問改寫或刪除金鑰圈項目（以暫存金鑰圈實測）。所以 gateway 會用啟用時記下的金鑰代號與加密的檢查值核對金鑰，行程第一次載入的金鑰會被釘住直到結束，封存值帶的金鑰代號不同也算金鑰被換。任一種情況都會停用個人帳號並顯示「保護金鑰被更換」。如果金鑰和記錄一起被換掉，再讓 gateway 重新啟動，前兩項檢查會通過，只剩舊的封存值對不上會露出來。「換一把新金鑰」（一切正常時也可以按）會產生新金鑰，大家要重新連結。
- **只有 gateway 解封。** 只有持有 `<home>/locks/gateway.lock` 的行程拿得到金鑰，MCP server 與 CLI 子命令拿不到。
- **稽核：** `security_audit.jsonl` 記 `credential_protection_enabled`（含先前狀態，重新換金鑰為 Critical）、`credential_protection_enable_failed`、`credential_protection_disabled`，以及 gateway 第一次看到金鑰不見、被換或記錄損壞時的 `credential_protection_broken`。每列記狀態、等級、後端與金鑰代號，不記金鑰。

擋不住的部分：能執行指令的員工仍可以換掉金鑰（會被偵測，見上）、殺掉 gateway 自己起一個，或在發布的 macOS CLI 還沒開 hardened runtime 之前對 `duduclaw` 執行檔注入程式碼。真正的隔離仍是不給 Bash、用任務沙箱，或讓 gateway 用另一個作業系統帳號執行。

## 代表同事使用 Google 帳號（v1.76.0）

內建信箱工具及 Gmail 搜尋／讀信會在郵件文字交給 AI 員工前掃描，將登入連結與附近的一次性驗證碼換成提示文字；郵件識別碼及時間戳記保持不變。此邊界只涵蓋內建信箱與 Gmail 結果欄位，Gmail 的 OAuth、服務帳號與 Apps Script 橋接都適用，不掃描第三方 MCP、Remote MCP 或透過 Bash 讀取的內容。偵測靠規則比對，寫法特殊的驗證碼可能漏掉。

公司授權代表讓 AI 員工以一位指定同事的身分使用 Google。各道守門都在失敗時拒絕：

- **只認已證明的員工。** 身分只依 `DUDUCLAW_AGENT_ID` + `DUDUCLAW_AGENT_TOKEN` 證明的員工決定，絕不看工具參數。宣稱某位員工卻證明不了的行程，只能用公司預設；宣稱的員工若設成其他身分，連預設也不給。
- **只有 gateway 簽發。** MCP 伺服器向 `POST /api/internal/google-token` 要權杖（本機、簽章身分、一次性 nonce、限流，和知識庫路由同一套驗證）。gateway 自己讀員工的 `[google]`、用自己的登錄查這個 turn 是為誰做的，並且只在 `person_identity_gate()` 通過後（憑證保護達到最低等級；一般 Linux 使用者服務與一般 Docker 安裝一律拒絕；原生受保護服務與 Docker person-credentials 疊加設定可通過）才解開委派金鑰。權杖只留在 MCP 伺服器這個 turn 的記憶體裡。
- **金鑰是封存的。** 服務帳號金鑰只以保護金鑰封存的 `pk:v1` 形式保存。用目前的保護金鑰解不開，就當成金鑰被換掉：委派停止、寫一次 `google_delegation_key_unreadable`（Critical），由管理員重設憑證保護後重新匯入。舊紀錄不會被悄悄覆蓋。
- **誰在要求。** 預設只有綁定這位員工的人、管理員和系統工作能用那位同事的帳號；公開訪客在任何設定下都不行。發問者被拒或設定錯誤絕不改用公司共用帳號；其他失敗只有員工設了 `fallback = "home"` 才改用，回覆會說明。
- **每次重讀人員狀態。** 同事的 DuDuClaw 帳號停權或離職後，下一次呼叫就拒絕。
- **設定只有管理員能改。** `[google]` 對員工自己的 Write/Edit 是凍結的（員工檔案守衛），也是權限欄位：非管理員的擁有者只能改得更窄。

限制：`gmail.compose` 讓拿到權杖的人能寄信；有不受限 shell 的員工可以拿自己那位同事的權杖直接呼叫 Google，而且和 gateway 是同一個作業系統帳號。HTTP Google MCP 掛載（`oauth://google`）會使用員工選定帳號，每次呼叫重查發問者權限；個人帳號的 stdio 掛載會拒絕。設定見[連接 Google](../../guides/zh-TW/google-setup.md)。見[每位 AI 員工用不同的 Google 帳號](../../guides/zh-TW/google-workspace.md#每位-ai-員工用不同的-google-帳號公司授權代表v1760)。

## 這些守衛擋不住什麼

明講這一節本身就是防線的一部分。

- **Hook 看得到的是 Claude Code 自己的工具呼叫，不是 MCP 工具呼叫。** MCP 有自己的閘（scope、授權、`denied_tools`）；hook 是內建 `Write`／`Edit`／`Read`／`Bash` 那面的第二道鎖。
- **`agent-file-guard` 的 Bash 通道是啟發式。** 它讀的是指令文字，下列情況都擋不住：由變數（`$DUDUCLAW_HOME`，以及資料目錄在預設位置時的 `~/.duduclaw`、`$HOME/.duduclaw` 除外）、指令替換或其他計算產生的路徑；編碼後的指令；先寫成腳本再執行；把 here-document 餵給直譯器；別名與函式；透過環境變數讓之後啟動的 shell 載入某個檔案；清單內唯讀指令沒有被考慮到的寫檔選項；沒有寫明目的地的解壓縮或下載指令，它們寫進目前的工作目錄，而這條通道不判斷目前目錄，所以先切換進資料目錄再執行就不會被擋；在同一條指令裡先建立連結再透過它寫入；硬連結；以及檢查與實際執行之間的時間差。
- **Bash 通道也會誤擋一些無害的指令。** 受檢位置上的路徑解析失敗時一律拒絕，即使路徑在資料目錄以外；懸空的符號連結即使指向資料目錄以外也會被拒絕。
- **只限操作者的記憶指令靠減速帶與核准把關，不是沙箱。** `memory forget-source` 與 `memory migrate-namespace` 的 Bash 規則擋不住子指令前的全域選項、用指令替換組出的執行檔名稱與經管線傳入的指令，AI session 判斷也能靠 unset 變數繞過。真正的關卡是儀表板核准，見[依來源忘記需要管理員核准](#依來源忘記需要管理員核准)。
- **`agent-file-guard` 不涵蓋 `Read`。** 留出集與稽核紀錄員工仍然讀得到，hook 只擋寫入。
- **系統金鑰圈分不開員工與 gateway。** 兩者是同一個作業系統帳號。macOS 上保護金鑰擋得住其他程式讀取，擋不住被換掉；Windows 上同帳號的任何程式都讀得到。Docker 的 person-credentials 模式裡，根金鑰只在 gateway 行程手上，但 gateway 仍是員工的作業系統帳號：員工可以在權限內請它代辦，也可以讓它停止。見[指定人的憑證放系統金鑰圈](#指定人的憑證放系統金鑰圈v1760)。
- **這些 hook 與 Codex 控制檔鎖是分開的保護。** Unix Codex WorkspaceWrite 會套用上述權限 profile。Grok、其他 CLI runtime 與 Windows 不受該鎖保護；其他 CLI runtime 除非開啟 `native_sandbox`，否則沒有 OS 沙箱。
- **員工自己目錄裡的狀態檔不在保護範圍**，只有 `SOUL.md`、`CONTRACT.toml`、`INSTRUCTIONS.md`、身分檔（`.mcp.json`、`.claude/settings.json`）與 `agent.toml` 受保護。共用的 `attachments/` 每位員工都能寫。
- **`data-file-guard` 是啟發式。** 它比對 `Bash` 指令列裡的檔名，動態組出來的路徑就繞得過去。（目前 Windows 也會以 Rust 子命令執行。）
- **沒有威脅等級狀態機。** `~/.duduclaw/threat_level` 還在，作為 computer use 協調器會輪詢的操作者 kill switch（`RED` 中止、`YELLOW` 暫停），但工作區內已沒有任何東西會寫它。檔案不存在才視為 `GREEN`；檔案存在卻讀不到，或內容不是 `GREEN`／`YELLOW`／`RED` 其中之一，間隔 50 毫秒再讀兩次後仍是如此，就視為 `RED`（fail closed）；開頭的 UTF-8 BOM 與前後空白會略過。
- *（2026-09 移除。）* 本節原本註明 PTY session pool 不在去識別化改寫的涵蓋範圍內。該連線池已不存在。每次 Claude spawn 都會使用單次 spawn，資料改寫 hook 會在這條路徑執行。

四道各自明講失效模式的守衛，勝過一個底下已經沒有程式碼的三層故事。防線被移除時，文件必須跟著移除：一頁描述著不存在的 shell 腳本的文件比沒有文件更糟，因為它會讓操作者停止繼續找。

## 頻道核准的保存與核對

高風險 Computer Use 使用原帳號及原對話或討論串送出確認，回覆 `確認 <完整 UUID>` 或 `取消 <完整 UUID>`；問題使用 `回答 <完整 UUID> <答案>`，不授權工具。單獨的是、A/B 不會選取請求。執行前重驗畫面、視窗、政策與取消狀態，重啟會讓舊畫面核准失效。沒有收據的執行成為 `uncertain`，需 Admin 核對。支援入口及限制見[操作指南](../../guides/durable-channel-decisions.md)。

## 資料外送防護的重啟保護（v1.77.0）

回合污點只存在記憶體；外送 lease 則先存入 `<home>/egress_leases.db`（SQLite WAL，Unix 0600）才授予呼叫端。Gateway 開放 loopback 路由前會復原，並在每次重啟後以單調時鐘重新保護同一員工所有回合的私人讀取完整六小時，不依 UTC 年齡或時鐘跳動縮短。舊回覆不能釋放復原的 lease。資料庫無法讀取時，`ask`／`block` 暫停所有員工的私人讀取與新外送，`shadow` 允許並稽核；每五秒重試、每分鐘最多記錄一次錯誤。新增失敗拒絕強制模式外送，刪除失敗保留保護。此處持久 lease 仍只涵蓋 MCP 呼叫；CLI 事前檢查見下方 說明，跨輪資訊複製不在範圍內，詳見[資料外送防護](69-egress-guard.md)。

Store 在存續期間持有 `<home>/egress_leases.lock` 獨占檔案鎖（Unix 0600）。使用同一 home 的第二個 gateway 會拒絕讀取與新外送並重試，取得鎖後先恢復所有 lease 才接受讀取；`shadow` 仍允許並稽核。Gateway 執行中不可刪除鎖檔。重複的有效 lease ID 會在寫入前拒絕，不會連帶阻擋其他員工。

## CLI 外送檢查

Claude/Grok 網頁工具與 Bash 字面網路指令新增由 gateway 判定的審批 hook；Codex 強制模式在啟動時限制網路與搜尋。背景執行登錄 host 回合。安全頁列出有 Bash、使用 ask/block 且未啟用任務沙箱的員工。Bash 只提供減速帶與遙測：原生讀檔不標記污染、同 OS 使用者的改寫不受此機制隔離，事前檢查也不持有執行全程的 MCP lease。強制模式拒絕 Claude bare mode 與 Grok 共用工作目錄。通用 CLI 原生工具仍未涵蓋。模式表、單次核准重試與限制見[資料外送防護](69-egress-guard.md)。

## 寄信由交辦人在原對話確認

`mail_send` 因收件人或資料外送防護等待核准時，發起該回合、已驗證的公司帳號僅可在一對一對話或已登入的儀表板 WebChat 決定確認卡。交辦人身分必須由 gateway 證實，決定當下仍能對應到 `users.db` 帳號，並有該 AI 員工的 Operator 操作權限。群組對話、外部或未驗證寄件者（包含 LINE OA 與 `odoolivechat:` 訪客）、其他 AI 員工、cron 與 heartbeat 都不適用；儀表板 Admin 仍可核准。

確認卡列出完整收件地址、主旨、內文摘要，以及本回合是否讀過私人資料。確認卡是純文字訊息，沒有按鈕，請以「決定動詞＋完整請求 UUID」回覆；AI 員工自行宣稱「使用者已核准」不生效。沿用綁定最終參數、只能用一次的 ActionGrant，執行前再次核對政策版本與收件人；參數變更須重新核准，第二次使用會拒絕，逾期視為拒絕。紀錄保留實際決定的交辦人或儀表板管理員身分。

`config.toml [security] mail_requester_approval` 為布林值，依擁有者決策預設 `true`。檔案或鍵不存在時使用預設值；設定無法讀取、格式錯誤、值無效或設為 `false` 時，只能由儀表板 Admin 決定。管理員可在安全設定關閉。例外僅限 `mail_send`；訊息、行事曆、第三方 MCP、CLI 外送與工作流程啟用，仍維持原有的管理員外送核准。群組對話與未知聊天類型仍須儀表板 Admin 核准，公開 WebChat 小工具訪客不適用。不符資格的通道通知不含收件人、主旨或內文，完整內容只留在儀表板。

已登入的儀表板 WebChat 可通過 audience 資格檢查，但非 Admin 的 WebChat 確認介面與決策入口尚未接通，目前仍須 Admin 完成核准。

## 斷開連線的刪除審批與收據

斷開連線後，記憶遺忘計畫合成一個七天有效的批次，只開一張限管理員在儀表板核准的卡片。卡片顯示逐員工筆數，不帶記憶內容。規劃失敗不影響已完成的斷開。`[memory] forget_source` 關閉、設定讀不到或值無效時，不建立新計畫，也不套用。

回合帳本在既有污染來源旁記錄連線參照，不改變資料外送政策。通道與 Remote MCP 橋接的參照由 gateway 產生；MCP 伺服器內的原生工具則先宣告，再由 gateway 確認連線存在且已授權給通過驗證的員工。未知參照會丟棄並計數，不會存成連線標記。Google 個人憑證依實際選用的使用者記為 `google:person:<user_id>`。帳本讀不到時，記憶寫入 `unknown` 標記，不猜測連線。

**殘餘風險**：有 Bash 的員工可偽造自己已獲授權連線的標記，影響限於自己的記憶；刪除仍需管理員核准，卡片列出每位員工的筆數。連線標記不提供同一作業系統使用者之間的隔離。

刪除不在審批結果持久化之前同步執行。核准後由帶租約的持久工作列交給背景 worker，失敗重試、開機恢復。套用前重新規劃：純縮小可套用，範圍擴大要重新核准。記憶引擎仍在立即交易中檢查資料庫實例、epoch、有效期與 hash，並阻止已刪列重新寫入。全部成功後才產生收據，並寫入安全稽核事件。

移除全域通道時排除員工專屬 bot 的 `#agent:` 對話；移除某員工 bot 時只選該 bot。系統來源紀錄保留；沒有標記的舊資料、回合帳本讀不到的資料列為無法歸屬。收據按員工與儲存區列出實際刪除數、保留的系統紀錄與歸屬缺口。**不在範圍內**：對話原文、`tool_calls.jsonl`、wiki、備份。還原舊備份可能恢復已刪記憶，並失去較新的刪除墓碑。管理員可透過 `memory.forget_receipts_list`／`memory.forget_receipts_get` 或安全頁查看及下載 JSON。

舊式 dedicated Google 執行若沒有回傳實際選定帳號的紀錄，且委派可能改用備援帳號，會記為 `unknown`。若連線宣告抵達時連線或授權已移除，也會拒絕該參照並計入未知。連線標記會保留回合開始時間，避免已忘記回合的延後擷取重新寫入可歸屬記憶。

連線來源標記會保留來源與角色；單純佐證不會取得刪除所有權。另一個仍連線的來源也提供過同一筆記憶時，該記憶會保留，計畫、管理員核准卡與收據以 `retained_shared` 逐員工列出數量。只有全部擁有來源的連線都已斷開，且沒有其他仍有效的直接來源，才會刪除；因此第二個連線斷開時，才可能選入先前保留的共享記憶。歸屬不明的記憶（包含無法還原角色的舊標記）保留並計入無法歸屬。衍生記憶也逐筆檢查來源。規劃與套用前會重新核對連線狀態；透過平台重新連線時，會先撤銷舊的斷線證據再發布連線。

核准會綁定排序後的孤兒實體向量識別值，不只綁定數量；即使數量相同，替換成其他實體也必須重新核准。未完成工作會持久保存嘗試次數與下次執行時間，以 60／120／240／480 秒退避，並公平選取已到期工作。連續五次失敗或執行中斷後會隔離；管理員可在「資料刪除收據」查看不含記憶內容的失敗原因並按「重試」。重試沿用既有核准並重查範圍，擴大時仍須重新核准。

每筆斷線紀錄都有獨立版本，建立時尚未驗證；連線狀態核對只驗證當時讀到的同一版本，延遲到達的舊斷線通知不能沿用先前的核對結果。

## 對話憑證稽核

[憑證稽核](70-credential-audit.md)只登錄偵測結果的中繼資料。密碼、連線字串不算指紋；高熵類型只有在憑證保護可用時才算帶金鑰的指紋。帳號只保留首字元與網域。每則訊息最多 5 筆、每位寄件者每小時 50 筆、總列數 100,000，超額合併為節流事件。兩種模式都遮罩衍生儲存中偵測到的值；預設 `audit` 仍保留對話明文，`mask` 在交付前遮罩新訊息。沒有語境的單獨密碼不會偵測，真值代換仍在規劃、不承諾版本。Admin 專用 RPC 與 doctor 可檢查稽核鏈；Read 檔案守門也拒絕讀取憑證登錄目錄。

## 雙因素登入

Gateway 支援 [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238) SHA-1 TOTP：160 位元隨機密鑰、6 位數、30 秒週期、前後各一個週期與交易內防重播。密鑰使用通道憑證相同的 AES-256-GCM 與主機 `.keyfile`，金鑰不放入 `users.db`。10 組單次備援碼只顯示一次、以 Argon2 雜湊保存；驗證備援碼不需要解密 TOTP。只要還有啟用或待註冊資料，金鑰遺失就拒絕建立替代金鑰；請還原原金鑰或走主機救援。金鑰輪替不在本階段範圍。

Dashboard 註冊改為 `mfa.enroll_begin {password}`，在 blocking pool 驗證目前密碼並套用登入等級限流。回傳的 `enrollment_token` 綁定使用者、JWT 的 `jti`、這次密碼驗證與 5 分鐘期限；`mfa.enroll_confirm {enrollment_token,code}` 必須來自同一工作階段。只偷到 JWT 不能開始註冊。要替換密鑰，先以新的 TOTP 或備援碼停用，再重新驗證密碼註冊；begin 不會覆寫啟用中的密鑰。

任何版本強制 MFA 期間，首次註冊還需獨立證明。只有已記錄且早於強制啟用時間的已驗證通道綁定，系統透過既有通道服務送出另一組 OTP，以 `proof_code` 提交；沒有綁定者，由另一位目前有效的 Admin 呼叫 `users.mfa_enrollment_code {user_id,challenge_ref}` 核發一次性註冊碼並交給本人。註冊碼綁定帳號及指定的待完成 challenge、雜湊保存、5 分鐘有效、只顯示一次並留下稽核，不能自行核發。最後一位管理員可在主機執行 `duduclaw ops users mfa-enrollment-code <email> <challenge_ref>`。證明綁定該次第一因素 challenge、同時到期、最多 5 次嘗試，成功後不能移用至其他 challenge。若第一因素是通道 OTP，註冊時還必須提供目前 `password`，避免同一通道的兩組碼被當成獨立因素。
Enterprise 強制期間，首次註冊驗證器／通行金鑰還需獨立證明。只有已記錄且早於強制啟用時間的已驗證通道綁定，系統透過既有通道服務送出另一組 OTP，以 `proof_code` 提交；沒有綁定者，由另一位目前有效的 Admin 呼叫 `users.mfa_enrollment_code {user_id,challenge_ref}` 核發一次性註冊碼並交給本人。註冊碼綁定帳號及指定的待完成 challenge、雜湊保存、5 分鐘有效、只顯示一次並留下稽核，不能自行核發。最後一位管理員可在主機執行 `duduclaw ops users mfa-enrollment-code <email> <challenge_ref>`。證明綁定該次第一因素 challenge、同時到期、最多 5 次嘗試，成功後不能移用至其他 challenge。若第一因素是通道 OTP，註冊時還必須提供目前 `password`，避免同一通道的兩組碼被當成獨立因素。

強制期間未註冊者登入只取得 `mfa_enrollment_required`、`enrollment_token` 與 12 字元 `challenge_ref`，沒有 session token。呼叫 `/api/mfa/enroll/begin {enrollment_token,proof_code}` 後，再呼叫 `/api/mfa/enroll/confirm {enrollment_token,code}`；通道 OTP 登入者兩次都要帶 `password`。Dashboard 強制註冊的第一次 begin 回傳 `proof_required`、`enrollment_token` 與 `challenge_ref`，再以 `password`、該 token 及 `proof_code` 重呼 begin，才取得 `secret` 與 `otpauth_uri`。Confirm 才會啟用。註冊憑證不能登入 `/ws`、refresh 或一般 HTTP；dashboard 的註冊憑證也不能拿去 HTTP 註冊路由換 session。

已註冊者的密碼與通道 OTP 登入回傳 `mfa_required`、`challenge_id` 與可用因素資料。`/api/mfa/verify` 接受 challenge 及 `code`／`recovery_code` 二擇一。Challenge 綁定帳號與第一因素，持久保存、單次成功、5 分鐘有效、最多 5 次嘗試。`mfa.status` 查本人狀態；`mfa.recovery_regenerate {code}` 替換全部備援碼；`mfa.disable {code,password}` 需要目前密碼（與註冊密碼驗證共用限流）及新的 TOTP 或未使用備援碼，強制期間不能移除最後一種驗證方式。每帳號因素驗證錯誤最多 5 次／15 分鐘。

新的團隊安裝預設 `[auth] mfa_enforced=true`；既有安裝保留原政策，尚無 MFA 政策紀錄的舊版安裝也不會自動開啟。Admin 可在儀表板「使用者 → 雙因素登入管理」用專用開關啟用或停用強制（`system.update_config` 搭配 `expected_state`）；一般設定寫入、設定檔編輯器與匯入不能變更有效值。新團隊的第一位 Admin 設定帳號與密碼後，登入會要求註冊 MFA；主機操作員須執行 `duduclaw ops users mfa-enrollment-code <email> <challenge_ref>` 核發註冊碼，再於登入畫面輸入並完成驗證器註冊，才會取得工作階段。首次註冊無法只靠儀表板完成。既有未強制的安裝可繼續自願註冊；開啟前請查看 `mfa.overview`、確認通道送達與主機救援。未強制且從未註冊時，既有回應與 epoch 0 JWT 內容不變。所有版本都依儲存的政策強制驗證，授權過期、驗證失敗回退或指定 Personal 啟動都不會停用；只有 Admin 主動關閉才取消強制。沒有政策資料庫的全新 Personal 安裝仍預設不強制；本機自動登入不能略過已啟用的強制驗證。
新的團隊安裝預設 `[auth] mfa_enforced=true`；既有安裝保留原政策，尚無 MFA 政策紀錄的舊版安裝也不會自動開啟。Admin 可在儀表板「使用者 → 雙因素登入管理」用專用開關啟用或停用強制（`system.update_config` 搭配 `expected_state`）；一般設定寫入、設定檔編輯器與匯入不能變更有效值。新團隊的第一位 Admin 設定帳號與密碼後，登入會要求註冊 MFA；主機操作員須執行 `duduclaw ops users mfa-enrollment-code <email> <challenge_ref>` 核發註冊碼，再於登入畫面輸入並完成驗證器註冊，才會取得工作階段。未設定 Email 寄信時，首次註冊無法只靠儀表板完成；已設定者可改用信箱驗證。既有未強制的安裝可繼續自願註冊；開啟前請查看 `mfa.overview`、確認通道送達與主機救援。未強制且從未註冊時，既有回應與 epoch 0 JWT 內容不變。Personal 忽略強制設定，`/api/session/local` 仍免密碼。

單純開啟強制不立即撤銷帳號 access token；未註冊者不能 refresh，原 token 自然到期（預設 30 分鐘）。所有版本的 MFA WebSocket 在到期後的下一次心跳關閉，最多延後 30 秒，不取消執行中工作。強制期間拒絕舊共用 token 的 `/ws` 登入及 RPC；已建立的共用 token 連線在下一次心跳關閉，停止推播訂閱。註冊、停用、重設會增加該帳號的 credential epoch，之後變更／重設密碼也會增加；舊 access／refresh token 失效，既有 dashboard 連線於下一次即時身分檢查拒絕，沿用 ACL 快取失效機制。沒有 claim 的 token 視為 epoch 0；從未註冊者即使變更密碼仍維持 0，以保持既有客戶行為。任何密碼變更都會作廢待註冊 challenge。

MFA 設定在啟動時載入有效的記憶體快照，dashboard 設定寫入後立即更新，外部檔案變更每 30 秒重載。失敗時保留上次有效值，於 `mfa.overview.policy` 及 `system.status.mfa_policy` 顯示 degraded 與警告；任何版本從未取得有效快照都拒絕；啟動時既有政策資料庫無法讀取或已損壞也會拒絕。缺少 `[auth]` 表格或設定鍵時保留資料庫中的政策；新團隊初始化會明確記錄 true。登入不再讀取或解析設定檔。

`users.mfa_reset {user_id,code}` 禁止自我重設，在同一交易內確認操作者仍是有效 Admin、驗證其目前密碼或新的 TOTP／備援碼、清除目標因素與 challenge、增加 epoch 並稽核。主機人員可執行 `duduclaw ops users mfa-reset <email>` 重設任意帳號，包含金鑰遺失時的多位管理員。兩個主機救援指令都拒絕 AI 工作階段及員工／未驗證 Bash 呼叫；稽核標示「本機指令列（身分未驗證）」。這些規則不提供任意主機檔案寫入的 OS 隔離。註冊、證明／註冊碼核發、停用、備援碼使用與驗證失敗均稽核，不記錄密鑰或驗證碼。

啟用前請檢查 `mfa.overview` 各帳號的 `channel_bindings.verified_at` 與政策 `enforced_at`（Unix 微秒）。無法確認的歷史綁定時間為 null，不能作為註冊證明；每次綁定或重新綁定都記錄新時間。強制期間，未註冊帳號不得自行綁定，需另一位有效 Admin 或主機人員核准。仍有一項限制：持有密碼的人在強制啟用前預先植入綁定，系統無法辨識。請將短 `challenge_ref` 讀給 Admin，不要提供完整註冊 token；註冊碼只會對符合的帳號與 challenge 兌換並刪除。

JWT epoch 必須完全相等。Dashboard 每次心跳重查；WebChat 在心跳及每次 user_message 前檢查，沿用共用身分讀取器與兩秒 socket 快取，心跳強制重查 generation，訊息另行檢查適用的到期時間。電腦畫面與接管 ticket 保留原 JWT epoch 及期限，在入場及每 30 秒重驗時拒絕已退休憑證，也不會延長原 JWT 壽命。兩個設定寫入路徑都在設定鎖內重新確認有效 Admin。若最後有效設定是 false，重載失敗仍保留 false 並顯示警告；正常 `system.status` 欄位保持不變。

### Email 驗證碼、通行金鑰與保持登入（v1.80.0 起）

在「設定 → 帳號」可保留原有驗證器 App，再加入 Email 驗證碼或多把具名的通行金鑰（Passkey）。新增或移除前需輸入目前密碼。Email 設定會將六位數代碼寄到帳號信箱，驗證成功才啟用。管理員需先完成既有 `[channels.email]` SMTP 寄信設定（`smtp_host`、`from_addr`，以及寄信服務需要的帳密）；未設定可用的寄信服務時，介面會顯示無法使用。因素變更會留下稽核，已設定寄信時也會通知本人。

輸入密碼後，可選擇已設定的驗證方式，預選上次成功使用的方式。Email 驗證碼限用一次、10 分鐘到期，每次登入挑戰最多嘗試五次；每分鐘可重寄一次，每個帳號每小時最多五次。通行金鑰使用裝置鎖定、指紋、臉部辨識或安全金鑰驗證。管理員需將公開儀表板網址設定於 `[dashboard] public_url`，並以完全相同的 HTTPS 來源開啟儀表板；只有本機 localhost 可用 HTTP。每把金鑰可命名、個別移除，建議另留一種驗證方式，以免失去裝置後無法登入。首次只註冊通行金鑰不會產生復原碼，既有驗證器復原碼維持有效。首次 Email 註冊會顯示一次復原碼，確認保存後才能繼續。

強制兩步驟驗證接受任何一種已設定因素，也會拒絕移除最後一種。原有驗證器與復原碼不需重新註冊。強制首次 Email 註冊以信箱代碼證明收信權；驗證器及通行金鑰仍需獨立的通道／管理員證明。以通道碼完成第一步登入者還需目前密碼。管理員重設會清除所有因素與保持登入的裝置。操作者可用目前密碼或新的驗證器／復原碼確認身分，因此只用通行金鑰的管理員也能執行。

登入頁的「保持登入」預設不勾選。勾選後以輪替的瀏覽器 Cookie 保持登入，預設採 180 天滑動續期：每次成功更新登入，都從該次使用時間重新計算到期日。管理員可在「安全 → 保持登入」設定 1 至 365 的整數，預設 180 天。政策永久存入 `users.db`；讀取失敗或值無效時回到 180 天，不會變成無限期。變更設定不立即改動既有到期日，下次成功續期才改為該次使用時間加上新天數，縮短天數也一樣適用。開發版原有的 `[auth] remember_days` 不再讀取。未勾選時維持原有工作階段行為。帳號設定的「已登入的裝置」列出保持登入的裝置、建立與最近使用日期及已記錄的 IP，可個別撤銷或「登出所有裝置」。密碼、因素、帳號狀態或角色變更、兩步驟驗證重設及刪除帳號都會撤銷保持登入；登出會撤銷目前裝置。

管理員可在「同仁 → 編輯同仁」開啟帳號詳情，按「登出此同仁的所有裝置」並確認，立即撤銷該帳號所有一般及保持登入工作階段。停用或移除同仁也會撤銷登入；既有 access token 會被拒絕，已連線的 WebSocket 在既有即時撤銷檢查（含下一次心跳）停止，不必等到180天到期。僅限管理員的 `sessions.policy`、`sessions.policy_update`、`users.revoke_sessions` 會重查目前權限；變更在認證稽核中記錄操作者、目標與結果，不記錄憑證。

使用 Cookie 驗證的登入請求必須帶有 `X-DuDuClaw-CSRF: 1`，並完整比對 Origin 的通訊協定、主機與有效連接埠。內建 HTTP loopback Origin 只接受閘道的監聽連接埠；反向代理請在 `[gateway] allowed_origins`（或 `DUDUCLAW_ALLOWED_ORIGINS`）列出完整的 `https://主機[:連接埠]` Origin，這些端點不接受只有主機名稱的設定。更新登入與登出會在變更工作階段前，拒絕跨連接埠頁面與一般 HTML 表單。

更新登入以經過簽章驗證的 family 世代編號輪替，每個 family 只保留目前一筆 token 雜湊；重用有效的舊世代憑證會撤銷該裝置，偽造世代編號則無法撤銷。獨立的 `users.remember-key` 簽章金鑰僅限檔案擁有者讀寫，備份與還原時必須與 `users.db` 一起保存；已有世代工作階段卻遺失金鑰，或金鑰損壞時，認證資料庫會拒絕開啟。世代功能前的開發版工作階段會在升級時撤銷。每個帳號最多保留 20 台有效裝置及 100 筆 family 紀錄（含已撤銷裝置）；達到紀錄上限時，請先使用一般登入，等候舊紀錄到期。紀錄在最後續期的到期日再加七天後，於下一次成功的保持登入操作清除。以帳號登入的管理介面與 WebChat 連線最長存活 24 小時，之後須重新連線驗證；原有較短的 MFA 到期限制仍適用，避免舊連線存活超過撤銷紀錄保留期限。


長期憑證不放入 localStorage，JavaScript 也無法讀取：Cookie 使用 HttpOnly、SameSite=Strict，範圍限定 `/api/session`，HTTPS 下加上 Secure。伺服器只保存雜湊，每次使用就輪替；舊憑證重用會撤銷整個憑證家族。Cookie 端點會檢查 Origin，儀表板 WebSocket 升級也會檢查 Origin。

實際 SMTP 送達、各平台瀏覽器的通行金鑰註冊與登入、跨平台 Rust 建置、依賴稽核及完整 gateway 整合測試仍待驗收；介面程式與已撰寫測試不代表上述項目已通過。

### 儀表板雙因素登入

Enterprise 與強制驗證中的 Personal 使用者在「設定 → 帳號」選擇「設定雙因素登入」，輸入目前密碼，以驗證器 App 掃描 QR Code（或手動輸入密鑰），再輸入六位數代碼確認。複製或下載十組復原碼，勾選「我已保存復原碼」後繼續。密鑰與復原碼只保留在元件記憶體，離開畫面即清除；複製及下載需自行按下按鈕。註冊與停用會換發目前工作階段的權杖並保留連線，其他工作階段則失效。復原碼會顯示到你確認保存或離開畫面。權杖簽發與 MFA 變更在同一交易提交；簽發失敗時不會完成註冊或停用，可重試。重產復原碼及停用需提供新的驗證器代碼或未使用復原碼；強制期間無法停用。

## 第三方 MCP 環境變數憑證

第三方 MCP 金鑰會移出員工的設定檔。`.mcp.json` 只保留 `secret://mcp/<server>/<ENV_NAME>` 參照，實際值使用既有 `.keyfile` 加密，存於 `<home>/secrets/mcp/<agent_id>.enc`。第三方伺服器的所有 `env` 項目都存入憑證庫，例外只有 `PATH`、`HOME`、`NODE_ENV`、`LOG_LEVEL` 與既有 `secret://` 參照。DuDuClaw 自身的伺服器項目與其中的 `DUDUCLAW_*` 變數維持不變。

只有精確名稱 `duduclaw`、`duduclaw-pro` 或目前 instance 的 key，且 command 與 args 符合主程式產生的內容，才算內建伺服器；`duduclaw-evil` 仍視為第三方。啟動時拒絕原始設定中的 proxy 項目及 proxy 私有環境變數；帶有員工身分的內建項目必須與主程式產生的完整設定一致。讀取秘密必須有對應憑證庫擁有者的有效 `DUDUCLAW_AGENT_TOKEN` HMAC，即使 delegation 使用寬鬆設定也不能省略，且不會以預設員工身分代替。

Proxy 只解析自己所屬員工的參照，並在啟動上游伺服器前才取得實際值。參照不存在、不合法或無法解密時，該伺服器不會啟動；錯誤只指出伺服器與變數名稱，不含值。需要解析秘密的設定若無法改寫為 proxy 路徑，Claude／Grok 不會退回直接載入原檔。匯出時只留下環境變數名稱與空白佔位值，匯入者必須重新輸入。

Gateway 啟動時會遷移舊有明文 env：先將原檔加密備份至 `<home>/backups/mcp-migrate/<agent>-<timestamp>.enc`，寫入並讀回驗證憑證庫後，才以原子操作替換設定檔。依金鑰、加密備份、憑證庫、設定檔的順序，每一步都須完成父目錄 fsync 才繼續。任一步失敗即停止該員工的遷移；若替換設定後同步失敗，會還原原始明文。還原也失敗時會明確報錯並保留已持久化的加密備份供復原，然後繼續處理其他員工；清理後每位員工最多保留三份遷移備份；清理若因 I/O 錯誤失敗會記錄，並於下次掃描重試。刪除伺服器或員工會移除對應的憑證庫項目，復原已刪除員工後須重新輸入金鑰。

Read 防護會拒絕讀取 `<home>/secrets`。這不是對 Bash 的隔離：員工與 gateway 使用相同 OS 使用者執行時，有 Bash 仍可讀取 gateway 檔案，包括 `.keyfile`；真正隔離需要不授予 Bash，或使用任務沙箱。這項功能只涵蓋 `env`，不涵蓋 `args`／`url` 裡的金鑰，也不涵蓋工具結果回傳的金鑰。既有明文匯出與備份不會被追溯清除。
## 網站登入憑證

管理員在 **系統 → 安全** 透過 `website_credentials.list`、`.upsert`、`.delete` 管理網站登入憑證。Upsert 改收會正規化的 HTTPS `login_url`，來源與登入路徑從網址衍生；選填的 `allowed_paths` 是相同來源第二步可用的確切路徑，預設為空。清單不回傳密碼。紀錄以 `CryptoEngine` 和 gateway 的 `.keyfile` 加密，保存在 `<home>/secrets/website_credentials.enc`；寫入使用檔案鎖、原子替換與 0600 權限。列清單、登入查詢與每次異動都要求所有既有紀錄可解密且通過驗證；任一失敗就回傳無法使用，憑證檔案維持原狀，舊有僅綁來源的紀錄也適用。管理操作的稽核不含憑證值；外層 ACL 拒絕會寫入不含參數的稽核，刪除結果區分 `deleted`、`noop` 與 `refused`。每次使用記錄憑證 id、員工、來源與結果。

`computer_login` 只接受標籤。Gateway 用已驗證的員工身分比對非空的 `allowed_agents` 清單，再執行該工具獨立的工具與 session 閘門。Gateway 先透過既有導覽檢查開啟保存的登入網址。秘密只透過 stdin 送入容器 helper，不放在命令列參數或模型結果。Helper 填寫前須符合確切來源與登入路徑；只有送出第一步後到達、且有可見密碼欄位的第二步才能使用 `allowed_paths`。填寫前、同步 input/change 事件後及 submit 事件後都要求有效提交方式為 POST；原生 `requestSubmit` 與備援路徑都會檢查實際選用送出按鈕的 `formmethod`。網路層也會拒絕查詢參數解碼後的值等於完整帳號或密碼的非 POST 請求。CDP Fetch 會中止每個來源不符的請求與轉址，登入期間也會略過 service worker。解除攔截前，helper 會追蹤 `Network.requestWillBeSent`、`Network.loadingFinished` 與 `Network.loadingFailed`，確認請求已結束。最多等待 3 秒，且須連續兩次命令往返都沒有新請求活動或待完成請求。若無法確認完成，回傳 `failed_uncleared`，在 Fetch 攔截仍啟用時呼叫 `Browser.close`，再由 Gateway 移除 session 與容器。執行期間暫停截圖；若無法確認欄位已清除，Gateway 會停止並移除 session 與容器，要求重新啟動 session。

這項保護無法阻止同來源 JavaScript 讀取已填入的欄位，也不提供對同一 OS 使用者程序的檔案隔離，更不取代網路白名單。登入僅限保存的 HTTPS 來源與允許的登入路徑，localhost 也必須使用 HTTPS。雙因素驗證與驗證碼須由人員透過既有接手流程處理。須重建電腦操作映像以安裝 `duduclaw-fill-login`。結果定義與設定方式見[瀏覽器自動化](08-browser-automation.md)。

## 管理員設定與遷移檢視（未發行）

管理員設定連結有效期限為 30 分鐘，產生新連結會讓舊連結失效。領取首位管理員連結時，確認尚無使用者、建立帳號與使用所有設定連結，會在同一筆 SQLite 交易完成；復原連結保留獨立用途，須明確產生。每分鐘最多嘗試 5 次，累計 20 次失敗會讓目前連結失效。認證資料庫升級時，既有未區分用途的設定連結也會失效。

「系統 → 遷移確認」只接受目前有效的管理員登入。輸入密碼與已註冊驗證器的驗證碼後，可在五分鐘內操作；CSRF 憑證綁定登入工作階段及憑證版本。頁面提供逐項核准、拒絕、重試，低風險提案可整批核准，尚未套用的提案可整批拒絕。部門、待邀請帳號、部分設定、delegation 政策與預算已接到產品寫入及讀回流程；沿用的 API-key 帳號憑證可在頁面更新，通過實際讀回才解除輪替要求。尚未支援的類別仍拒絕套用。核准、套用與 root 完成驗證分開記錄；跨服務遷移仍待整合，本次變更不會宣告員工隔離完成。

尚未發行的匯入器已加入低權限啟動與專用匯入模式。舊帳號與 MCP 設定只進確認清單，不會自動啟用；確認後的 stdio MCP 與員工指示檔會經產品驗證、發布及讀回。含憑證或尚未支援的項目須重新輸入，或維持拒絕；未確認員工的內容先保留在封存中。完整升級仍需要已簽章的平台整合與 Linux 端到端驗收。

技能、hook 與部分政策也會經產品驗證，並以本次操作的收據讀回；一般編輯已替換的檔案或部門，不會被遷移補償刪改。舊核准一律失效。Telegram 綁定、時間排程與資料庫唯讀授權還須確認 Shared 員工的實際配置；缺少隔離平台整合時維持拒絕。

開發中的遷移清單會逐筆列出工作流程版本、自動化規則與待送提醒，重新設定後才可啟用；員工動作規則另列為獨立政策提案。舊連線網址片段中的憑證也會遮罩，不會帶進確認內容。

**原生 Linux 終端機串接（開發中，既有安裝未啟用）**：受保護執行已加入每次工作專用的終端機、啟動前尺寸設定、執行中視窗調整與輸入輸出串流。獨立服務依閘道實際成功傳輸的資料計算閒置時間，查詢狀態與調整尺寸不會延長期限。取消後仍保留員工執行名額，直到服務、程序群組與員工程序確實結束。簽署的執行設定、正式授權入口與 Linux 實機驗收仍須完成，尚不代表 Grok／供應商或完整員工隔離已驗收。

### 受保護 Linux 網頁工具接線（尚未啟用）

原生隔離轉接器會把網頁內容寫入主機持有的檔案，再以檔案描述符交給隔離解析服務；抓取與快取政策留在主機。受保護請求會重查已簽署的網址來源授權，拒絕重新導向與環境代理，使用有大小上限且核對精確網址的獨立快取。抓取與抽取共用整個閘道每分鐘 10 次的上限，快取命中也計入。會議上傳連結、工作狀態／取消及推論路由查詢沿用既有主機處理器，不建立解析輸入。技能、媒體與知識來源流程仍未接齊，綜合啟動檢查仍拒絕受保護執行。這些原始碼變更不代表已部署隔離或通過 Linux 實機驗收。


第二輪接線加入技能掃描、擷取、採用到自己的技能目錄及手動升格，並在主機轉錄／語音合成服務前後，以真正音訊檔進行隔離的 WAV／MP3 結構檢查。技能擷取與原流程共用規則，回傳頁面路徑與連結經檢查後才交給既有知識頁面發佈流程。共享採用暫不更新共享統計，既有目的技能檔不會覆寫。雲端憑證留在主機；這條路徑不提供本機／自訂命令語音合成，生成音訊上限為 128 KiB。知識庫文字／網址提案仍須人工核准，檔案提案在接好檔案授權流程前維持拒絕。錄製蒸餾、技能合成、hub 安裝、curator 強制執行及會議媒體處理仍未完成，尚未通過完整 gateway／CLI 編譯、原生執行或真實供應商驗收。


第三輪接線新增錄製蒸餾的主機控制流程：真正的 HAR／操作／事件快照交給 E 解析，模型輸出也先經 E 掃描，才沿用既有待核准草稿流程。送進模型前會移除或替換網址憑證、片段與查詢值；一般錄製畫面文字仍可能包含敏感內容。Hub 安裝目前僅支援已設定的官方固定版本來源，依序執行有界抓取、E 的 YAML 驗證與掃描、既有安裝核准、鎖定下的信任重查及新檔發布／讀回。受保護會議工作以 E 檢查真正 WAV／MP3 快照，憑證、取消、計費與逐字稿發布留在主機；目前拒絕超過 25 MiB 或 30 分鐘的錄音，不執行主機 ffmpeg／ffprobe。技能合成僅提供隔離事件解析的預覽，完整合成及 curator 維護仍拒絕，兩者的 producer 清單仍列缺少，整體 E 就緒檢查維持未完成。這些接線尚未啟用，不代表完整產品編譯、原生執行或真實供應商驗收通過。


第四輪接線取代上述技能合成與維護限制。受保護模式會保留同一份模型結果與生成時間，由 E 解析 YAML、產生實際發布內容並掃描，再送交管理員於儀表板核准；核准綁定內容與目標，主機端只新增技能，拒絕覆寫，並保留發布收據。技能維護依 loader 的路徑規則辨認技能，略過參考文件、支援無前言的舊技能，且 SKILL.md 優先於同名平面檔案；實際動作清單綁定內容、使用紀錄與設定，核准後重新比對才套用。平面技能透過保留的目錄描述符封存，拒絕覆寫並先保存耐久意圖；巢狀技能只標記無法管理，不移動。報告以新檔發布並讀回。封存結果不明時暫停維護，需管理員人工核對，尚無自動修復或意圖清除。E 就緒改為檢查明確安裝的 launcher、健康主機組裝及新鮮的驗證世代證據，其他總閘仍保留。尚未啟用，也尚未完成完整 gateway／cli 編譯、原生環境、提供者或核准發布活驗。

## 一般自我更新的檔案替換

通過既有簽章與執行檢查後，Unix 自我更新先以硬連結或已同步的副本保留舊版，同步同目錄的新檔，再以一次改名覆蓋安裝路徑並同步目錄。回復也用一次改名；獨立的復原副本會保留到回復後的目錄同步成功。Windows 使用附備份的原生替換 API；執行中程式的先移開再放入後備流程可處理已回報的失敗，但兩次移動間仍有當機空窗。尚無法刪除的執行中舊檔使用固定備份名稱，等行程結束後在下次更新清理；仍被鎖住時拒絕繼續更新。回復失敗會回報保留的復原路徑。這是防中斷保護，不能隔離可寫入安裝目錄的行程。受保護 Linux 服務與桌面版另有安裝流程。詳見[部署指南](../../guides/zh-TW/deployment-guide.md#8-自動更新)。
## 歷史對話附件保護

歷史附件端點會重新檢查目前帳號、員工、對話及產物受眾權限。附件參照不授予任意路徑的讀取權限。Unix 以目錄描述符逐層開啟、不跟隨符號連結，拒絕路徑穿越與多重硬連結。上傳改用隨機 UUID 名稱，僅可建立新檔（`create_new`，Unix 加上 `O_NOFOLLOW`），避免不同使用者同時上傳同名檔案時覆寫內容。

授權檢查綁定已開啟檔案的有限大小快照：其 SHA-256 雜湊必須符合耐久產物來源紀錄及必要的工作流程收據，才會回傳同一份內容。開檔後替換路徑不會改變回應。缺少內容雜湊的舊來源紀錄拒絕受限讀取；Admin／完整歷史模式原有的舊檔規則維持。這項保護不隔離能以相同 OS 帳號改寫 gateway 檔案與紀錄的程序。Windows 與其他非 Unix 系統拒絕此端點。

資源限制涵蓋昂貴處理之前與實際讀取期間：

| 操作 | 限制 |
|---|---|
| 歷史資料庫查詢 | SQL `LIMIT` 直接選取最新訊息；單則最多 1 MiB，每次回應訊息文字合計最多 2 MiB |
| 附件投影 | 每次請求使用一份耐久授權索引，按歸檔名稱與來源路徑查詢；最多檢查 256 個參照、回傳 32 個附件 |
| 歷史請求 | 每位使用者同時 2 個、每分鐘 30 次，全域同時 4 個；同步工作受 semaphore 限制 |
| 下載請求 | 每位使用者同時 2 個、全域同時 4 個；每位使用者每分鐘 120 MiB，依該次大小上限預留額度 |
| 檔案讀取 | 檢查已開啟檔案的 metadata，並以 `take(max + 1)` 限制快照讀取；下載 20 MiB、預覽 2 MiB |
| 附件識別碼 | 獨立快取，每位使用者最多 512 筆，以 LRU 淘汰；全域容量不足時拒絕發出，不回傳無效識別碼 |

回應帶有 `Content-Length`、採 identity 編碼，保留 `nosniff`、sandbox CSP 與 private/no-store 快取設定。瀏覽器拒絕缺少、無效或超額的長度，分段讀取也受大小限制，實際長度不符即拒絕。超過 2 MiB 的圖片不自動下載預覽。可能執行內容的檔案類型仍只提供下載。識別碼到期或遭淘汰後，可在容量允許時重新載入歷史取得。

原生平台行為與實際瀏覽器下載尚未驗收；前端單元測試不代表這些驗證已通過。操作方式見[辦公文件套件](31-office-document-suite.md)。

WebChat 在寫檔或分派工作前驗證整批上傳：每批最多 8 個附件、解碼後合計 20 MiB，檔名最多 255 bytes、MIME 標籤最多 128 bytes。WebSocket 訊息及 frame 上限為 28 MiB；附件解析器會在建立過大的附件陣列前拒絕超量輸入。Base64 不合法或超過限制時，整批拒絕。每位使用者每分鐘最多 8 批、32 個檔案及 80 MiB。持久化預留配額限制新上傳：每位使用者 512 MiB／2,048 個檔案，全域 4 GiB／16,384 個檔案。空檔案仍占用檔案數額度；失敗或中斷的預留仍計入配額，手動刪檔不會自動恢復額度。

下載回應有 30 秒總期限。即使客戶端完全不讀取內容，獨立計時器仍會釋放快照與下載槽。傳輸層每次取得最多 64 KiB 的獨立副本，因此保留一個區塊不會同時保留整份快照。到期的回應會失敗；重試須重新通過授權，並按原有規則扣除請求額度。

歷史附件授權使用有索引的耐久 SQLite 紀錄，保存歸檔名稱、擁有者、內容雜湊、大小及來源路徑。展示／稽核用 JSONL 輪替或截短不再移除既有授權紀錄。資料庫無法使用時拒絕受限存取，WebChat 上傳須成功保存授權紀錄才回報成功。缺少可信內容綁定的舊檔仍不提供受限讀者下載。

首次使用時，會在同一筆交易匯入保留的前一份及目前稽核檔，合計上限 32 MiB、每列上限 64 KiB。來源無法讀取、格式錯誤或超限時，遷移整筆失敗，不產生部分授權；須修復保留紀錄後重試。更早輪替已丟棄的紀錄無法自動重建。匯入後再修改稽核檔，不會覆寫授權資料庫。

Unix 附件寫入會逐層拒絕目錄符號連結，再相對於固定的目錄控制代碼建檔。授權及配額資料庫的父目錄必須是 gateway 使用者擁有、群組及其他使用者不可寫入的實體目錄；主檔與已存在的 journal／WAL／SHM 必須是同一使用者擁有、只有一個硬連結的一般檔案。SQLite 另以 `SQLITE_OPEN_NOFOLLOW` 開啟，新資料庫權限為 `0600`。資料庫直到 `/` 的所有祖先都必須由執行使用者或 root 擁有，且群組／其他使用者不可寫；root 擁有且可寫的 sticky 目錄只在下一層屬於執行使用者時允許。home 在開啟前只解析一次標準路徑，允許 macOS 的系統根別名（`/var`、`/tmp`、`/etc`），拒絕其他符號連結；附件路徑仍需使用實體目錄。新建 home 採 `0700`，既有權限保持不變；CLI 與儀表板健檢會提示可由他人寫入的 home，提供由操作者執行的 `chmod 700` 指令。無法提供這些操作的平台拒絕附件存取與上傳。系統產生的附件標籤會轉換 Markdown 分隔符與換行；格式損壞的舊參照採保守遮蔽，避免留下主機路徑。
### 新增同仁與首次登入進度（v1.80.0）

`users.create_members` 與 `invitation.get/update/preview` 明列為 Admin 權限並重查有效帳號。建立同仁及修改邀請信的寫入交易內會再核對憑證版本。每位同仁的帳號、綁定、主要對象、選用邀請、進度與稽核一起提交。SMTP 在交易外執行，寄送失敗不刪除已建立的帳號，複製與重寄仍限管理員。信件先跳脫所有管理員文字，只解讀粗體與換行；選填課程網址限 HTTPS，不接受內嵌帳密。預覽不產生憑證。`onboarding.get/update` 固定使用目前登入者身分與憑證版本，更新不接受指定他人 ID。連線步驟由伺服器紀錄確認，引導完成不授予任何權限。見[使用指南](../../guides/zh-TW/user-management-and-first-login.md)。

邀請、首次登入與新增同仁 RPC 命名空間中的未知方法，在核心派送前要求 Admin，且不會交給 extension。主要員工的寫入與讀取要求直接 Owner／Operator 綁定；控制台聊天候選與續接目標拒絕僅有 Viewer 的權限。邀請與課程網址一律要求 HTTPS 且不得內含帳密，localhost 亦同；郵件標頭欄位移除控制字元。
## AG-UI 外部前端

[AG-UI HTTP/SSE 端點](74-ag-ui.md)只接受儀表板 access JWT，沿用即時帳號／雙因子檢查與 WebChat 員工授權；非 Admin 呼叫者須有綁定或有效團隊授權，不能存取主要／預設員工。伺服器對話識別隔離呼叫者、員工與 thread，使用 WebChat 所有者命名空間內的獨立 AG-UI 區段；`/ws/chat` 不能續接。只有最後一則 user 文字會進入既有受保護的回覆管線；client history、tools、context、state 與 forwarded properties 不會增加權限，也不能執行前端自訂工具。

核准中斷依 broker 持久保存的對話／回合來源關聯判斷。只有有效 Admin 可在此決定一般、未綁定特定執行身分的 `mcp_call` 或 `mcp_install`，並檢查到期、所有權、限定儀表板與 `forbid_self_approval` 政策。其他種類只通知，限定儀表板的要求不能在此決定；顯示用 metadata 不具授權效力。請求大小、同時執行、生命週期及事件佇列都有上限；斷線會中止進行中的交付並撤回該回合待核准要求。正常送出 interrupt 後只在期限內保留回合。核准紀錄可跨重啟保留，記憶體中的 runtime 續跑狀態不能。SQLite 准入紀錄阻止 24 小時內重複 run ID，最多保留 4,096 筆。重啟後，未完成 thread 在原本 15 分鐘期限內仍被擋住；之後的新 run 須先撤回舊回合待核准要求。同一 process 內的 resume 收據不會重跑工具，也不證明執行成功。

同一次 resume 的決定改為原子提交，任一卡片衝突就回滾整批。原介面已同意或拒絕的卡片，可由仍有員工存取權的呼叫者（包含非 Admin）在新連線確認相同結果後續跑；重新核對原始要求與回合來源，保留外部決定者。未知的孤立 resume 不會新增准入紀錄。每帳號跨員工與 thread 合計最多保留 256 筆 run／thread 紀錄、滾動 60 秒最多准入 32 次，收據請求也計入；配額跨重啟保留，超限回 HTTP 429。未知 JSON 欄位只在 debug 記錄數量，每個 gateway process 最多每分鐘一次，不記名稱或值。

## 企業版合規報表匯出

企業版管理員可在 **稽核日誌 → 合規報表** 產生 CSV、XLSX 與可列印 HTML。閘道重新確認管理員權限與解析出的版本，預設遮罩個資；只有明確勾選才包含來源中未遮罩的值。每次匯出皆先寫入稽核，失敗即拒絕交付。報表只涵蓋已記錄的外送閘門決策、審批、行動審查與資料來源存取；決策不等於成功送出，缺少的欄位留空，零筆也不代表沒有存取。下載副本請依組織保存政策管理。日期邊界、上限與遮罩範圍見 [企業版合規報表](75-compliance-reports.md)。

報表讀取與稽核寫入共用跨程序鎖，涵蓋輪替與追加，避免匯出時因輪替漏讀目前這一代紀錄。保留的兩代工具稽核紀錄皆以報表實際使用的有大小限制快照驗證雜湊鏈；鏈結損壞、紀錄格式錯誤或讀取／鎖定失敗時拒絕匯出。有效的舊格式前綴仍可讀取，但無法獨立驗證真實性。雜湊鏈無法證明尾端完整性，也不提供外部可信錨點的真實性保證。
## 個人 Drive 錄影匯入

Enterprise 會議頁只接受已登入控制台的本人，使用自己的個人 Google 連線，在明確選檔並確認後匯入。員工 MCP 權杖與公開上傳連結不能呼叫這個入口，也沒有新增瀏覽 Drive 或匯入的 MCP 工具。接收員工仍須通過既有上傳的即時授權、工具、核准、資料外送及隱私檢查；需要額外核准的政策仍會拒絕控制台匯入。

Drive／Meet 採增量授權：本人啟用錄影存取時，才要求 `https://www.googleapis.com/auth/drive.file` 與 `https://www.googleapis.com/auth/meetings.space.readonly`；一般初次連線不要求 Drive／Meet 權限。既有較廣的授權會保留至撤銷為止；另外的「啟用員工的 Drive 工具」同意步驟可為既有員工工具與 Google 遠端 MCP 加上 `https://www.googleapis.com/auth/drive.readonly`，仍保留員工使用同意與角色檢查，錄影匯入不需要這個較廣選項。尚未分享給應用程式的檔案由 Google Picker 選取；`drive.file` 本身也允許寫入選取的檔案，但匯入只執行 GET。瀏覽器另外取得短期且僅含 `drive.file` 的 Picker 權杖，不合併先前的範圍、不持久化；gateway 憑證留在受保護的個人憑證庫。

Gateway 驗證檔案 ID，即使連線已有較廣的舊授權，仍要求 Drive 回傳 `isAppAuthorized=true`。這個 Google 旗標可能來自先前授權，不能證明當次 Picker 點擊；匯入另須持有下述綁定使用者、員工與檔案的確認收據。請求使用固定的官方 Google API 位址，拒絕轉址。中繼資料回應有大小上限，媒體沿用既有分段上傳儲存及檔案大小、暫存配額、長度限制。傳輸期間及建立工作前會重查連線本人、實際授權範圍與本機權限；斷線或偵測到撤銷後停止後續存取。本機來源紀錄將上傳連到選取者、Google 帳號、Drive 檔案 ID 與版本；稽核使用雜湊識別，不保存權杖、檔案內容與敏感名稱。

Gateway 分別保存基本服務、會議錄影與員工 Drive 工具的本機用途同意，並綁定封存憑證及其授權紀錄。每項能力都必須同時符合 Google 實際範圍與本機用途同意；會議授權額外回傳 `drive.readonly` 或 `drive`，也不會啟用員工 Drive 工具。增量授權保留先前用途，但必須完整保留舊有 Google 範圍，保存時也會比對原憑證版本；缺少範圍或憑證已被其他操作更新，就拒絕取代舊憑證。沒有本機用途同意的舊紀錄須重新連結。重新連結基本服務會將本機用途重設為基本服務，之後須另行開啟會議錄影與員工 Drive 工具。

每次匯入都需要伺服器簽發的確認收據。它證明經 JWT 驗證的控制台使用者，在最近五分鐘內明確登記並確認將這個確切的 Drive 檔案 ID 交給這位接收員工；員工／MCP 權杖不能登記收據。收據限用一次，綁定該使用者、員工與檔案 ID；同一使用者對同一員工的新確認會取代上一張收據。控制台只在使用者確認匯入時登記檔案。缺少、過期、已用過或綁定不符的收據會遭拒。進入匯入程序後，即使後續檢查失敗也會用掉收據，重試須重新確認。伺服器另以該使用者的 Google 連線檢查 Drive 中繼資料，要求 `isAppAuthorized=true`。收據與這個 Google 旗標都不能證明曾在 Google Picker 點擊；控制台呼叫者可用已知 ID 明確確認先前已授權給應用程式的檔案。

僅供控制台使用的 `POST /api/meeting-drive/selection` 必須提供 `agent_id`、`file_id` 與 `confirm: true`，回傳 `selection_receipt` 及 `expires_in`。每位使用者每分鐘最多登記請求 20 次，最多保留八張未過期收據；`POST /api/meeting-drive/import` 必須附上該收據。

`google_status` 只讀取帳號、狀態與依本機用途篩選的範圍中繼資料，不解封憑證、不更新權杖，也不回傳 bearer。Token 端點使用明確的工具允許清單，個人憑證須同時符合對應本機用途與 Google 範圍；狀態查詢與未知工具不能取得 bearer。

本機 Drive 來源紀錄含選取帳號、Google 信箱、檔案 ID 與版本。取消、失敗及上傳過期時，來源紀錄會與對應狀態變更在同一資料庫交易內刪除。其餘來源紀錄（含成功匯入）自 `imported_at` 起保留 30 天，期限到後由 gateway 執行期間每 60 秒的既有清理程序刪除；停機後於下一輪清理執行。逐字稿檔案與稽核日誌有各自的保存規則，不會隨這項來源中繼資料清理一併刪除。

`user.google_connect` 稽核記錄授權用途、回傳範圍集合的雜湊摘要及非預期範圍；Drive／Meet 清單讀取與早期拒絕也會記錄。這些事件不保存權杖與檔案內容，匯入識別碼使用雜湊。

已匯入副本及完成的逐字稿與 Google 連線分開，不會因斷線自動撤回。Google 端撤銷透過 API 拒絕或更新後的權限資訊偵測，不是即時推播。這是產品入口授權，不是對與 gateway 同 OS 使用者、且不受限制的程序提供隔離。真實 OAuth／Picker 與供應商處理仍須另行驗收。詳見[會議逐字稿](73-meeting-transcripts.md)及[個人連線設定](../../guides/zh-TW/google-personal-connections.md)。
## 一般同仁自動化與最近技能權限（v1.80.0）

Dashboard RPC 最低角色由專屬角色表在 extension 分派之前執行，與 MCP scope 表分開。相關方法逐一登記；未登記的 `cron.*`、`reminders.*`、`assign_schedules.*`、`agents.org_chart.*`、`skills.recent.*` 預設需要 Admin，其餘既有命名空間仍走原分派權限。逐筆處理器保留 Viewer／Operator 與建立者檢查。每次請求重新讀取帳號狀態及直接綁定；無法確認授權時拒絕。

| Dashboard RPC | 範圍 |
| --- | --- |
| `agents.org_chart` | Admin 看全部可列示員工；其餘只看直接 Viewer 以上綁定與 users.db 中本人目前部門的員工。範圍外 reports_to 上級僅含 name、role；隱藏員工仍隱藏，不含聯絡或能力設定，不增加操作權限。 |
| `skills.recent` | 目前登入帳號自己的最多五個不重複技能；須仍可呼叫、已啟用並通過既有技能檢查，不接受客戶端指定其他使用者。 |
| `cron.list` | Admin 保留完整列表；其他帳號僅本人建立或直接 Viewer 以上綁定 AI 員工的紀錄。 |
| `cron.add`、`cron.update`、`cron.resume`、`cron.run_now` | 非 Admin 僅時間型提示排程，須直接 Operator 以上綁定目標；仍檢查主代理、機器員工與執行身分。 |
| `cron.pause`、`cron.remove` | 建立者或直接 Operator；綁定工作流程的紀錄仍受保護。 |
| `cron.templates` | 已登入帳號可讀取內建範本。 |
| `reminders.list`、`reminders.cancel` | 本人提醒或直接綁定目標：Viewer 查看、Operator 取消。不開放客戶端自訂通知路由或建立提醒。 |
| `assign_schedules.list`（`scope: accessible`）、`assign_schedules.pause`、`assign_schedules.resume`、`assign_schedules.remove` | 建立者或直接綁定目標（讀取需 Viewer，修改需 Operator）；恢復時也重新檢查原建立者。 |

最近技能只保存帳號、目標 AI 員工與技能名稱，每帳號最多保留一百筆，不保存訊息或技能內容。紀錄在送出受理後產生，點標籤不會紀錄，也不代表執行成功。組織圖的結構可見性不會放寬對話與設定存取。員工自動化編輯不開放 shell 指令、條件腳本、任意通知目的地或工作流程管理。舊紀錄若沒有可驗證的建立者，只透過既有綁定授權。

Cron admission 是所有帶 `on_behalf_of`、`created_by_user_id` 或 `scoped_by_user_id` 紀錄的共用 store 限制，包含 MCP 新增、更新與恢復。檢查和寫入在同一個 `BEGIN IMMEDIATE` 交易內：每個歸屬人最多 20 筆啟用排程，每位 AI 員工最多 50 筆（包含既有 Admin 排程），Dashboard 與 MCP 紀錄合併計數。每人滾動一小時最多建立或新接管 20 筆，receipt 不受刪除排程或重啟影響；一般修改不再消耗建立次數。單純暫停與刪除仍可執行。沒有來源標記的 Admin 排程維持原行為；MCP 帶人類來源時，即使該帳號是 Admin 仍受限制。最低間隔 15 分鐘，以一天內所有時點及跨午夜間距驗證，保守視選定日期為連續日。Scheduler 載入與執行前重讀都會跳過不合規紀錄，日誌只記錄數量。

員工 `cron.run_now` 在 spawn 前檢查：滑動 10 分鐘內每筆排程最多 3 次、每人最多 10 次受理；每人最多 2 件、全域最多 4 件未完成工作。Semaphore 無可用席位就回覆忙碌，不建立排隊 task。拒絕不消耗次數；已受理但後續失敗仍計次，完成、取消與 panic 都會釋放 outstanding。Admission 資料有容量上限，保存在程序記憶體，gateway 重啟會重置；鎖不可用時拒絕執行。員工 cron 表達式在正規化與解析前限制 256 bytes，store／runtime 驗證也適用。

非 Admin 新增／更新會對完整結果 name＋task 模型提示呼叫 `scan_input_with_audit`，使用對話相同門檻；命中時不寫排程，並寫入 `security_audit.jsonl`。恢復／手動執行也掃描舊 task，不允許更換 agent_id。H2 採限制主機執行對象：員工只能對存在且 `[container] sandbox_enabled = false` 的代理新增、編輯、恢復或手動執行；registry 與磁碟上的有效型別設定都須允許，無法讀取設定則拒絕。執行時依保存的 `created_by_user_id`／`scoped_by_user_id` 及手動呼叫人重新檢查，呼叫 runtime 前再次檢查；目標啟用任務沙箱或不可用時暫停排程並記錄 skipped。既有 host runner 保留代理的 runtime、capabilities 與 native sandbox 設定，本次未實作容器化 cron；未帶員工標記的既有 Admin 排程仍在 host 執行。與一般 runtime 設定載入相同，設定讀取並非涵蓋程序啟動的原子鎖。

員工 cron 僅支援 UTC（含零時差 UTC／GMT 別名）。舊紀錄若指定其他時區，編輯、恢復與手動執行會拒絕，避免日光節約時間縮短實際間隔；仍可讀取，有權限者仍可暫停／刪除，時區排程由 Admin 管理。

帶人類來源的 MCP 新增排程預設 UTC；未帶來源標記的 Admin／背景排程保留本地時區偵測。
