## 在網頁管理範本（v1.80.0）

管理員可在兩種版本瀏覽員工及團隊範本。詳情與必填審閱步驟會顯示完整的 `SOUL.md`、`CONTRACT.toml` 及每份 `SKILL.md`，包含所有團隊成員；以原始文字呈現，不渲染 HTML。須檢查所有保留文字中的秘密與個資，再勾選確認。若內容有問題，先修正來源員工；公司範本編輯只支援工具與技能收窄。

複製／匯出先以 `templates.copy` 的 `preview: true` 取得預覽，不儲存範本。確認須帶回 `reviewed: true` 與 `review_digest`，伺服器重新擷取來源並拒絕內容變動。`templates.save`、`templates.apply` 也要求布林值 `reviewed: true`；公司範本另須提供審閱時版本。團隊每建立一位員工前都重查版本；變更或無法驗證時，以 `template_changed` 回報已建立名單並停止其餘成員，保留已建立的員工。

複本保留投影後的有效職務設定，以及審閱過的個性、合約、技能文字。不讀取記憶／歷史、`.mcp.json`、通道設定或任意自訂技能附件；有限定帳號池時拒絕複製。執行環境憑證／環境欄位及非可攜區段不保留；保留的政策區段若有憑證欄位則拒絕。整段 `[fork]` 移除，`db_sources`、`recipients` 清空，`git_credentials` 關閉，員工層級 `recipient_guard` 強制為 `ask`；心跳與自主演化預設關閉。文字中的已知格式憑證由既有診斷遮罩器處理，可能保留前後各四碼。**未知格式 token、短密碼、個資及寫在自由文字中的收件者識別資料，無法保證移除。** 必須由管理員審閱，不能視為秘密或個資清除保證。

儲存前掃描每份原始 SOUL、合約與技能文字，建立員工前再掃描實際待寫內容。既有隱藏內容與輸入注入掃描器發現問題即拒絕，短 HTML 註解及單一不可見／零寬字元也拒絕；掃描失敗時同樣拒絕並指出檔名，不複製內容。教學範例也可能命中規則，須修正來源而非繞過掃描。Unix 以 `O_NOFOLLOW` 開檔，對同一 descriptor 檢查大小、一般檔案與 hard-link 數；尚未固定所有祖先目錄，不能防止同一 OS 使用者替換祖先路徑。

五個範本 RPC（`templates.catalog/get/copy/save/apply`）均要求目前具 Admin 身分。公司範本存於 `<home>/company_templates/`，採原子儲存、整隊單一版本，稽核不含文件內文。內建唯讀，付費複本仍需授權。團隊複製包含主管與下屬（最多 50 人），保留內部匯報關係。編輯只允許移除技能／成員、縮減工具允許清單或增加禁止項目；移除主管須一併移除下屬。停用技能維持停用。自訂腳本不複製；未改動的內建辦公技能可復原官方附帶資產。公司複本不含付費包知識附件或評測題庫。

套用需填識別名稱與顯示名稱，公司版另提供部門與啟用中使用者的操作權限綁定。沿用產品、建立與授權限制。部分成功會列出已建立名單，不自動整批重試。


## 比喻：餐廳的套餐 vs. 單點

當你開一家新餐廳，有兩個選擇：
- **單點**：每道菜從零設計。最大彈性，最大工作量。
- **套餐**：從經過驗證的組合開始，然後依口味客製化。快速上線，容易迭代。

DuDuClaw 的產業模板就是 Agent 部署的套餐。每個模板包含 Agent 在特定產業運作所需的一切（人格、行為規則、領域知識），開箱即用。

## 產業模板

### 模板內容

每個模板是一個完整的 Agent 入門套件：

```
templates/{industry}/
├── SOUL.md           # 針對產業調校的 Agent 人格
├── CONTRACT.toml     # 產業專屬行為邊界
├── agent.toml        # Agent 設定
└── …                 # 產業附加檔：餐飲 FAQ.json + PROACTIVE.md、
                      # 製造 SOP-template/、貿易 price-list-template.csv
```

**SOUL.md** — Agent 的人格預設了符合產業的溝通風格：
- 製造業 Agent 使用精準、以數據為導向的語言
- 餐飲業 Agent 溫暖、服務導向，自然地處理食物相關查詢
- 貿易業 Agent 簡潔、數字導向、有風險意識

**CONTRACT.toml** — 行為邊界反映產業法規：
- 製造業 Agent 未經人工確認不得核准設備重新啟動
- 餐飲業 Agent 談到菜色時一律附上過敏原警語
- 貿易業 Agent 每份報價都要寫明貿易條件（FOB/CIF/EXW）

**附加檔** — Agent 工作時用的起始資料：餐飲有 FAQ 與主動檢查排程，製造有設備異常 SOP 範本，貿易有價目表範本。請把佔位值換成自己的資料。

### 可用模板

**製造業** — 工廠營運助理：監看生產、以嚴重度標籤回報異常、轉達 SOP 步驟、協調交接班。

**餐飲業** — 客服助理：回答詢問與菜單問題、接受訂位，談到菜色時列出過敏原。

**貿易業** — 國際貿易助理：回覆買家詢價，依價目表報價並附貿易條件與報價有效期，追蹤買賣雙方之間的訂單。

### 客製化流程

模板是起點，不是束縛：

```
步驟 1：部署模板（`duduclaw wizard`，從選單選產業）
步驟 2：客製化人格——編輯 SOUL.md 以符合你的品牌語氣
步驟 3：調整邊界——修改 CONTRACT.toml 以符合特定合規要求
步驟 4：新增領域知識——匯入菜單、供應商、流程到 wiki
步驟 5：讓演化接手：SOUL.md 維持你寫的樣子（Agent 不能修改），
        Agent 學到的是一條條小型 playbook 規則，每條連結一個 eval 案例，
        不再有幫助時單獨退休，全部維持在客製化的契約邊界內（見 features/38）
```

## 一種包格式

產業模板、專家包（一整支團隊）、職務組合（preset），是同一件事的三種形狀：一份宣告，產出已經配置好的 AI 員工。現在它們共用同一份 manifest schema 與同一個指令。

`pack.toml` 用 `kind` 說明自己是哪一種：

```toml
[pack]
schema  = 1
id      = "clinic-team"
kind    = "team"        # "preset" = 一份職務設定｜"team" = 一支團隊｜"template" = 單人產業板模
tier    = "free"        # "free" | "premium"
version = "1.0.0"
label   = "醫美／牙醫診所"
description = "一位前台加五位部門同事"

[[pack.agents]]
name = "clinic-assistant"
role = "front_desk"
```

一個指令讀得懂、也裝得起全部三種：

```bash
duduclaw pack list                 # 已安裝的包、本機職務組合、內建目錄裡可裝的東西
duduclaw pack inspect ./my-team    # 正規化後的樣子，並說明這份檔案是哪一代格式
duduclaw pack install ./my-team    # 依 kind 分流；付費內容只在一處檢查授權
```

`kind` 決定安裝路線：職務組合寫進職務組合庫（`presets/<id>/preset.toml`，再用 `duduclaw preset bind` 綁到某位員工），團隊包與產業板模走 [features/32](32-expert-packs.md) 描述的完整安全管線。`tier` 是唯一的付費判定：以前有四段程式各自從目錄路徑推「這是不是付費內容」，現在包自己帶著 tier，只有一個判斷式讀它。

**三種舊格式仍然讀取。** `expert.toml`、`team.toml`、`preset.toml` 原樣讀取，磁碟上一個字都不改——付費內容樹裡的法規條文是逐字人審過的，不交給機器轉檔。其中 `expert.toml`、`team.toml` 與產業包目錄結構已棄用，會跟改寫後的付費板模一起在之後的版本移除，目前沒有訂版號；`preset.toml` 是職務 preset 的儲存格式，不在棄用範圍。`duduclaw expert install` 已在 v1.69.0 移除，請改用 `duduclaw pack install`。想看舊檔在新 schema 下長什麼樣，跑 `duduclaw pack inspect <dir> --emit-canonical`：它只印出來，不寫檔。

## Odoo ERP 橋接

### 問題

AI Agent 可以*談論*商業運營，但無法*執行*它們。Agent 可能知道客戶需要一張發票，但它無法在你的 ERP 系統中建立一張，除非它有橋接。

### 解決方案

DuDuClaw 包含一個中介軟體，將 Agent 直接連接到 Odoo（全球使用最廣泛的開源 ERP 系統之一）：

```
使用者：「幫我建一張客戶 ABC 的銷售訂單，Widget X 10 個」
     |
     v
Agent 理解意圖
     |
     v
Agent 呼叫 MCP 工具：odoo_sale_create_quotation，再呼叫 odoo_sale_confirm
     |
     v
DuDuClaw Odoo Bridge 轉譯為 JSON-RPC 呼叫
     |
     v
Odoo ERP 系統建立銷售訂單
     |
     v
Bridge 回傳結果（訂單編號、金額）
     |
     v
Agent：「已建立銷售訂單 SO-2024-0042，客戶 ABC。
        Widget X 10 個，合計：$1,500。」
```

### 可用操作（18 個 MCP 工具）

橋接提供以下工具（`crates/duduclaw-cli/src/mcp/tools_def/odoo.rs`）：

- **連線**：`odoo_connect`、`odoo_status`
- **CRM**：`odoo_crm_leads`（列出潛客）、`odoo_crm_create_lead`、`odoo_crm_update_stage`
- **銷售**：`odoo_sale_orders`（列出訂單）、`odoo_sale_create_quotation`、`odoo_sale_confirm`
- **庫存**：`odoo_inventory_products`（搜尋產品）、`odoo_inventory_check`（庫存水位）
- **會計**：`odoo_invoice_list`、`odoo_payment_status`
- **通用**：`odoo_search`（搜尋任一模型）、`odoo_execute`（呼叫模型方法）、`odoo_report`、`odoo_partner_search`、`odoo_schema_fields`、`odoo_schema_overview`

### 結構掃描與欄位相容

重新掃描會涵蓋已儲存的全域連線，以及每位員工合併後的 `[odoo]` 設定與公司範圍。同一連線身分只掃描一次，同時最多掃描兩個連線；畫面逐一顯示各員工「已準備好」或失敗原因。不同 Odoo 使用者的快照各自隔離。兩個儀表板掃描動作共用持久保存的 60 秒手動冷卻時間。成功準備後，只有在所有有效身分都能確認時才清理過期快照資料；清理會持有目錄鎖再刪除閒置鎖檔，執行中的掃描與鎖檔都會保留。

總覽不帶篩選時只列模型名稱與短標籤，上限 16 KiB；指定 `model` 或查詢只命中最多五個有權限的模型時才回傳欄位，上限 32 KiB。回應保留符合條件的模型總數及截斷標記。共享 Wiki 摘要上限 16 KiB；`odoo/schema-fields` 僅作為搜尋用的 `deep` 參考頁，上限 32 KiB，不會自動放入員工上下文。

Odoo 升級或客製後，管理員可以在 Odoo 頁按「**重新掃描 Odoo 結構**」（dashboard RPC `odoo.schema_scan`，限管理員）。掃描只讀伺服器版本、已安裝模組中繼資料、模型目錄及 `fields_get`，不讀業務資料列或二進位內容。快照包含欄位名稱、型別、標籤、關聯、必填／唯讀／儲存屬性，並標記 `x_*` 自訂欄位。 手動掃描每個已存 profile 每 60 秒最多嘗試一次，失敗也計入，重啟不重設。不合法技術名稱會丟棄並計數，標籤經注入篩查、最多 120 字元；員工總覽明示 Odoo 中繼資料不可信。所有 Odoo RPC 回應以串流累計，超過 32 MiB 會在解析前拒絕。

每次最多保留 **400 個模型、每模型 500 個欄位**。中繼資料與欄位探索上限 **5 分鐘**，`fields_get` 同時最多四個；帳號權限探測另外設 30 秒整體上限。優先順序為內建工具模型、已安裝業務模組的模型（CRM、銷售、採購、庫存、會計、專案、人資、製造、客服及網站），其餘按名稱排序。逾時會標記不完整；身分、版本與模組未變時，下輪沿用已取得的完整欄位，接續處理未完成模型。模組／模型目錄各上限 5,000 筆；不完整的差異不代表資料已刪除。

快照帶有格式版本，以原子寫入存到 `<home>/odoo/schema/<effective-profile>.json`，Unix 目錄及檔案僅擁有者可存取。有效 profile 包含端點、資料庫、Odoo 使用者及公司範圍，避免套用其他連線的快照。差異摘要列出模型／欄位增減與伺服器版本變更。這份快照與舊的「解析資料庫」寫入共享 Wiki 流程分開。

`odoo_schema_overview`（`odoo:read`）讀取已存快照；可用 `model` 查看指定模型的欄位，以 `query` 搜尋模型／欄位名稱及標籤。回傳內容會依員工的模型、動作權限、Odoo 功能模組開關，以及套用該員工實際解封清單後的安全封鎖清單過濾。預設封鎖的模型除非已對該員工解封，否則不會回傳其名稱、欄位或關聯；`odoo_schema_fields` 會在連線 Odoo 前直接拒絕。gateway 掃描每個連線時也套用同樣的封鎖清單與功能開關，封鎖或關閉的模型不會被探測或寫入快照。`odoo_status` 顯示快照距今多久、掃描時版本、掃描失敗狀態；版本不同時提示 `re-scan recommended`。

持有執行個體鎖的 gateway 啟動後，每 30 分鐘檢查所有有效連線；快照缺少、不完整、伺服器版本不同、已安裝模組名稱／版本變更或缺少權限中繼資料時，會在背景掃描。掃描成功或明確失敗後才計入每小時一次的自動掃描額度，中途取消不占額度。MCP 對話程序不啟動掃描；準備期間可先用 `odoo_schema_fields` 查詢單一資料表。版本與模組清單都沒變的純欄位客製，仍需手動重新掃描；已連線員工可用 `odoo_connect` 更新即時欄位快取。

儲存連線設定後，資料工具會在第一次使用時自動連線，功能與權限檢查都先於連線，不必每回合呼叫 `odoo_connect`。登入識別、版本與版本類型會在本機快取六小時；更換金鑰立即改用新的快取。狀態查詢顯示連線已有的資訊，不另行探測伺服器。每次資料請求仍會帶入憑證，由 Odoo 驗證身分與權限。憑證錯誤與政策拒絕不會重試；只有傳輸失敗、伺服器錯誤與逾時才會有限次重試登入。

內建工具讀取時，每個連線、每個模型先以 `fields_get` 取得實際欄位名稱，再從原本要求的欄位中移除不存在的項目。例如客戶搜尋保留 `phone`，伺服器沒有 `mobile` 就不要求它，不會擴大原本的安全欄位清單。中繼資料查詢失敗，或過濾後沒有任何欄位時，直接拒絕讀取，避免變成讀取全部欄位。通用查詢的明確欄位清單也使用這個相容過濾；快照不取代這次連線的實際檢查。商品類型優先使用仍存在的 `detailed_type`，缺少時採伺服器的 `type` 欄位；客戶搜尋的安全欄位清單維持不變。

### Odoo 查詢被拒絕時

`allowed_models`、`allowed_actions` 空清單代表不增加員工限制。功能模組關閉、通用工具的內建封鎖清單、MCP scope／工具白名單及 Odoo 自己的 ACL 仍會拒絕。查 `res.partner` 這類預設封鎖模型的業務資料，需要管理員在儀表板選取標示「敏感」的資料表並確認，畫面才會自動加入 `unblock_models`；直接編輯設定檔時，只加入 `allowed_models` 不會解除封鎖。移除最後一個資料表選取或動作規則時，也會移除畫面管理的例外。「查詢與讀取」同時儲存 `read`、`search`；只有其中一個動詞的舊規則會標示「僅部分」，儲存時補齊。員工未設定 `unblock_models` 時會沿用整體清單，只覆寫帳號或金鑰也一樣。明確設定空清單代表不解除任何預設封鎖；明確設定清單則取代整體值。員工編輯頁會顯示目前生效的封鎖項目，並標示是否沿用整體設定。專用 `odoo_partner_search` 維持固定的安全欄位範圍。

動作編輯器提供 `read`／`search`（查詢與讀取）、`create`（新增）、`write`（修改）、`unlink`（刪除）、`action`（按鈕動作）及 `execute`（其他方法）。通用 `odoo_execute` 呼叫的按鈕動作涵蓋確認、驗證、封存等 `action_*`、`button_*`、`toggle_*` 方法，其餘方法使用 `execute`。所有資料表用 `action`，指定資料表用 `action:sale.order`。兩種方法都以修改權限作為提示，實際操作仍由 Odoo 檢查。

DuDuClaw 的拒絕訊息會指出是哪一道關卡與對應設定。唯讀 SQL 連接器的 `allowed_tables` 語義不同：必須非空，儲存 RPC 會拒絕空清單，不能套用 Odoo 模型白名單的解讀。

### 版本偵測

Odoo 有兩個版本：社區版（CE，開源）和企業版（EE，付費）。部分功能僅在 EE 可用。

橋接自動處理：首次連接時偵測 Odoo 版本（CE 或 EE），只暴露偵測到版本支援的 MCP 工具。無需設定。橋接會探測 Odoo 實例並自動適應。

### 事件同步

除了執行操作，橋接還可監聽 Odoo 中的事件。兩條管道餵進同一條自動化匯流排，**兩條都預設關閉**，要自己打開：

| 管道 | 開關 | 運作方式 |
|---|---|---|
| 輪詢 | `config.toml [odoo] poll_enabled`（預設 `false`） | 每隔 `poll_interval_seconds`（60–86400，預設 60）向 Odoo 查詢 `poll_models` 裡 `write_date` 在上一輪之後變動的記錄。 |
| Webhook | `config.toml [odoo] webhook_enabled`（預設 `false`） | Odoo 的 automated action 帶著 `[odoo] webhook_secret` 的共用密鑰 POST 到 `POST /webhook/odoo`。 |

```
Odoo 事件發生：
  - 新潛客建立
  - 訂單狀態變更
  - 發票逾期
     |
     v
輪詢捕捉到變更  或  Odoo 打到 /webhook/odoo
     |
     v
一則 `odoo_event` 進入自動化匯流排
     |
     v
由你的自動化規則決定怎麼辦：
  - 通知銷售團隊新潛客
  - 把後續追蹤派給某個 AI 員工
  - 為逾期發票發送付款提醒
```

規則寫法跟其他觸發事件一樣，觸發事件名稱是 `odoo_event`。除了 `event_type`／`model`／`record_id`，記錄的頂層純量欄位也會直接攤平上來，所以條件可以直接寫 `{"field": "state", "op": "eq", "value": "sale"}`。

v1.67.1 起也可以在儀表板建立這種規則（設定 → 自動化 → 新增規則，觸發事件選「Odoo 資料變動時」），條件欄位直接輸入 Odoo 的欄位名稱，例如 `state`。v1.67.1 之前儀表板表單建不出任何規則。

這個端點對外可達，所以行為刻意保守：

- `webhook_enabled` 關著時整條路由回 **404**——預設安裝不會洩漏這個端點存在。
- 密鑰缺漏或不符回 **401**；**密鑰設成空字串也一律拒絕**，半套設定寧可什麼都不收。
- 輪詢要同時滿足三件事才會啟動：`poll_enabled` 打開、Odoo 連線已設定、`poll_models` 至少有一個合法模型名稱。缺任一項就完全不會起背景工作。

這將 Agent 從被動的工具使用者轉變為主動的商業參與者。

```
製造業模板 + Odoo Bridge：
  Agent 監控庫存水位（Odoo）→
  偵測到關鍵物料庫存不足 →
  自動建立採購訂單 →
  透過設定的通道通知生產經理

餐飲業模板 + Odoo Bridge：
  Agent 收到大型外燴訂單（通道訊息）→
  檢查食材可用性（Odoo 庫存）→
  建立銷售訂單（Odoo 銷售）→
  標記任何過敏原疑慮（wiki 知識）→
  向客戶確認

貿易業模板 + Odoo Bridge：
  Agent 收到市場資料更新 →
  與投資組合部位交叉比對（Odoo）→
  辨識超過風險門檻的部位 →
  發送警報給交易員，附建議操作
```

## 這為什麼重要

### 加速見效

沒有模板時，部署產業專屬 Agent 需要：研究產業術語和流程、撰寫人格檔案、定義行為邊界、建立領域知識庫、測試和迭代。有了模板，這些步驟都已預建。幾分鐘內即可部署。

### 作業深度

Odoo 橋接將 Agent 從對話助手轉變為作業工具。它們不只是*建議*建立發票，而是*建立*發票。彌合 AI 建議與商業行動之間的鴻溝。

### 標準化

模板編碼了產業最佳實踐。從模板建立的 Agent 已經了解品質管控標準、安全規範和庫存管理實務。營運人員不需要重新發明這些知識。

### 可組合性

模板、ERP 橋接和演化系統無縫合作。模板提供起點，ERP 橋接提供作業能力，演化系統基於實際表現持續改進 Agent；這一切都在契約的安全邊界之內。

## 與其他系統的互動

- **演化引擎**：從模板部署的 Agent 像其他 Agent 一樣演化。模板是起點，不是永久狀態。
- **行為契約**：每個模板包含針對產業合規要求量身打造的契約。
- **記憶系統**：wiki 中的領域知識透過記憶系統索引和可搜尋。
- **通道整合**：模板 Agent 支援所有 11 個通訊通道。
- **成本管理**：ERP 橋接操作在 CostTelemetry 中追蹤以供預算可見。

產業模板與 Odoo ERP 橋接解決了 Agent 部署的「最後一哩」問題：從通用 AI 到真正能在現實世界*做事情*的領域專家。模板提供知識和人格；ERP 橋接提供作業能力；演化系統確保持續改進。
