# ADR-006: 機微画像向けローカル OCR

- Status: Accepted(方向性は確定;OCR エンジンの選定は実測待ち)
- Date: 2026-07-09
- Deciders: DuDuClaw maintainers

## Context

顧客はデモの中で(§7、23:30-24:58)次のように提起した:機微画像
(身分証番号、契約書、伝票を含む)がクラウド OCR を経由すると、データが
オンプレミスの外に出てしまい、流出リスクがある。ローカル OCR を要求し、
もしローカル OCR が不安定であれば、機微画像を送出するくらいなら画像
アップロードそのものを直接ブロックしてほしい、とのことだった。

現状のアンカー:**プロジェクトには OCR が一切存在しない。** crates 全体を
grep しても tesseract / mineru / `ocr` の実装は見つからない。
`allow_image_input` という capability フラグもまだ作られていない。
deny-by-default の capability 機構はすでに存在しており
(`CapabilitiesConfig`、`crates/duduclaw-core/src/types.rs:471`)、新しい
フラグを載せることができる。`TODO-feature-gaps` §8 ではすでに PDF 向けに
MinerU(Python bridge 経由)が計画されている。

これは技術選定のスパイクである。厄介なのは、「どの OCR エンジンの繁体字
中国語認識精度が十分か」という問いは、スペックシートを見て答えられる
ものではないという点だ——実際のサンプル画像に依存する。

## Options considered

**(a) MinerU**
すでに計画済み(§8 で PDF 向けにスケジュール済み)、レイアウト認識機能あり
(表 / 複数カラム / 図文混在レイアウトを処理可能)、品質の上限が高い。
欠点は重いことである——Python 依存が多く、モデルが大きく、起動と
メモリのコストが高い。

**(b) Tesseract サブプロセス**
軽量、成熟、クロスプラットフォーム、導入コストが安い。欠点は
**繁体字中国語の品質が未検証**であることである——Tesseract の中国語
モデルは活字体印刷にはまずまずだが、表、手書き、低解像度、縦書きに
対する性能は未知数であり、訓練データだけを根拠に「おそらく大丈夫」と
決めつけることはできない。

**(c) macOS Vision framework**
Apple ネイティブで、繁体字中国語認識の実測評判が良く、追加依存がゼロ。
致命的な欠点はプラットフォームロックインである——macOS でしか動作せず、
gateway を Linux にデプロイすると使えなくなる。

## Decision

**OCR エンジンを事前に選定しない。** まず実際の認識精度テストを行う——
**繁体字中国語のサンプル画像 10 枚**(身分証 / 伝票 / 契約書 / 表など、
実際のシナリオを網羅)を用意し、3 社の認識精度を測定し、数字に基づいて
決定する。プロジェクトの方針は「当てずっぽうをしない / まず測ってから
選ぶ」であり、OCR の品質というものは実測なしに結論を出せない。

選定を確定する前に測定すべき項目:
- 文字単位の認識精度(特に redaction パイプラインが捕捉すべき数字や
  身分証番号などのフィールド)。
- レイアウトの崩れの度合い(表 / 複数カラムが崩れて、後続の redaction が
  捕捉できなくなっていないか)。
- 1 枚あたりのレイテンシとリソース占有(オンプレミスで耐えられる必要が
  ある)。

**どの OCR を選ぶかにかかわらず、block-first フォールバックは先に出す。**
WP12-T12.1 のブロッキングゲートは OCR エンジンとは無関係であり、しかも
安価で fail-closed である:`agent.toml [capabilities] allow_image_input`
(デフォルトは後方互換のため `true`)。`false` に設定すると、各チャネルは
画像を受信してもダウンロードせず、context にも入れず、zh-TW の説明文を
返す。9 つのチャネルにおけるメディアダウンロードの choke point はそれぞれ
異なるため、1 つずつ接続し、1 項目ずつチェックしていく。これを先に届けることで、
「機微画像の流出」という最も鋭いリスクを最も保守的な方法で塞ぎ、OCR の
選定を待たない。

OCR パス自体(T12.3)は、エンジンが選定されてから接続する:画像 → ローカル
OCR → テキストが既存の redaction パイプラインを通り(WP2 のルールがそのまま
適用される)→ その後初めて LLM の context に入る。`allow_image_input=false`
の場合の OCR 失敗 ⇒ ブロック;allow が有効な場合の OCR 失敗 ⇒ 2 つの選択肢
から成る config(`degrade: block | passthrough`、デフォルトは block、
fail-closed)。

## Consequences

**得られるもの:** 選定はスペックシートの想像ではなく実際の数字に基づく;
fail-closed な block-first の経路——安価かつ独立して出荷可能——が先に着地し、
機微画像流出のリスクは OCR 選定を待たずに直ちに収束する。

**支払うもの:** OCR の完全な機能は、10 枚のサンプル画像の実測が完了するまで
着手を待つ——これは意図的な遅延である。少し遅れても正しく選ぶ方が、
早く選んで間違えるよりよい。3 社にはそれぞれ致命的な弱点がある
(MinerU は重い、Tesseract の繁体字中国語は未検証、Vision は
プラットフォームロック)。数字を見ずに選べるものは一つもない。

**デリバリーの等級付け:** WP12 の Definition of Done に従い、OCR の品質が
基準に達していない場合でも、T12.1 のブロッキングゲートを先に出荷すれば
PARTIAL と表示できる。block-first は独立して出荷・受け入れ可能な最小単位
である。

**選定後:** 実測数字に基づいて OCR エンジンが確定した後は、どのエンジンを
選んだか、どの数字を根拠にしたかを、本 ADR の追記または新しい ADR として
記録する。それまでは、本 ADR の OCR エンジン欄は「実測待ち」のままとし、
未測定の傾向をいかなる形でも記載しない。
