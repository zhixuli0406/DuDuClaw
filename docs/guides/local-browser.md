# Dedicated local browser

Existing denied tools, scoped grants, action rules and action-review refusals still apply. If a rule asks about a screenshot or scroll, only the native app can approve it. Local navigation retains the usual Modify restrictions and also checks Send rules. Stop does not wait for approval. Masked local frames are returned to the live runtime in memory; they are not saved as audit screenshots.

This memory-only boundary covers DuDuClaw's local viewport and consent audit paths. Images, text, URLs and key parameters sent to a model may remain in an external runtime's transcripts, provider caches or model replies; replies may also become ordinary conversation records. The dedicated Chrome profile retains website state. This feature does not guarantee that page content is absent from model or other-system storage.

This feature is off by default. It uses a separate Chrome or Edge window and profile on macOS, started by the local desktop app's own gateway. Personal and Enterprise editions use the same controls. Windows and Linux refuse this target; a remote or attached gateway cannot pair a local companion.

An Admin enables both `[computer_use.local_browser] enabled = true` in `config.toml` and `[capabilities.computer_use_config] local_browser = true` for the employee. Enabling the global switch in Settings requires an explicit acknowledgement. Keep `computer_use = true` and the normal container mode; the removed desktop-native mode remains unsupported. Configure exact HTTPS hostnames in the employee's existing `allowed_domains` list. No wildcard or local/private address is accepted.

Call `computer_session_start` with `target: "local_browser"`; omitted target means `container`. The remaining computer tools use that employee's existing session. Local execution additionally needs a live authenticated human conversation and the app's native presence channel. Dispatch, schedules, goal loops, heartbeat, public visitors and an inherited upstream turn or principal cannot supply this proof. Unsupported inbound adapters remain refused. A refusal never falls back to a container.

The macOS app's native “Let AI open a browser…” menu also accepts an employee ID through a system dialog. This single-use start intent expires after sixty seconds and rechecks native pairing, policy and active owner bindings. Its audit actor is “local native user (platform identity unverified)”; it does not identify a named owner, create a chat identity or authorize AI page reads. The actual menu-bar icon changes color while the browser is active and offers Stop.

The first AI read of an existing page requires native consent. This in-memory consent binds the exact human turn and current runtime connection for at most sixty seconds. A new turn, recreated connection, changed requester, owner transfer (including A→B→A), policy change or ended original turn requires consent again. It covers masked screenshots, page text and titles. A standalone native start never preauthorizes these reads.

Approval cards include scrollable, complete action details: text, keys, navigation URL, click coordinates and the page-supplied target description. Treat that description as untrusted and check the thumbnail too. Oversized details are refused rather than truncated for approval. The card explicitly discloses when approving an action also renews the current turn's sixty-second read consent.

Controller liveness is separate from physical presence. A native heartbeat keeps the local session alive using its server receive time, so a manual login or 2FA is not cut off by the container's ordinary 120-second tool-idle limit. The original hard session deadline still applies. A heartbeat supplies no identity, physical-presence proof or read/write consent. Lock, idle, human-input and expired turn/connection gates still refuse AI access. A controller missing for thirty seconds still ends the session.

Sign in yourself in the dedicated window. The AI cannot type into password, file or recognized credential fields. Native approval is required for each click, text entry, key and navigation. Scroll and masked viewport screenshots do not change this approval policy. The menu bar offers Stop and Continue. A screen lock, idle period or human input in the browser freezes AI actions; a native Continue gesture is required to resume. An app heartbeat missing for three seconds blocks actions; thirty seconds ends the session. Closing the dedicated window ends the session. Dashboard accounts, including Admin, have status and stop only: no page snapshot, VNC, control, reset or approval.

Browser state stays in `<home>/local_browser/<employee>/profile`, separate from normal browser data. Chrome uses the operating system's credential storage. CDP uses inherited pipes with no TCP debug endpoint, and Chrome retains its native sandbox. Network requests use a random authenticated CONNECT proxy, exact allowlisted hosts, public IP validation and pinned outbound sockets. Effective per-profile WebRTC preferences are required in addition to launch flags. Downloads, uploads, extra targets, non-HTTPS navigation, permissions and browser/clipboard shortcuts are refused. Local browser data must be excluded from backups. Transferring or deleting an employee invalidates its profile; a narrower allowlist resets it before reuse.

This is a native-host trust boundary, not a separate OS account or VM. An unrestricted process running as the same OS user can bypass application controls. A browser flag or fixture result alone is insufficient evidence about egress. Browser-version support uses an explicit build floor and must be refreshed and tested for each release.

Before launch, the machine lease durably records an unverified browser exit. Only verified termination of the owned process tree clears it. A gateway crash, failed initial inventory or uncertain cleanup blocks subsequent local starts. `duduclaw doctor` reports the lease path. Offline recovery requires stopping the app/gateway, preserving the audit and a lease copy, and checking every dedicated process against its recorded PID, birth and executable. Do not clear uncertainty or kill processes by a Chrome name match. After verification, truncate only the reported existing lease file to zero; do not unlink or replace it or erase the normal browser profile. The product never automatically removes this barrier.

Current acceptance: the synthetic native pipe/proxy/UDP/download spike has passed with Chrome 156, while its earlier STUN leak and invalid cleanup run remain recorded. Full backend/app integration, physical screen-lock behavior, a person signing in to a provider and release approval are separate gates. Do not treat the spike as completed product acceptance.
