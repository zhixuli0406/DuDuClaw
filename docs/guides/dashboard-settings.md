## Skill archive recovery

Automatic skill staleness and archiving have been removed. `[skill_curator]`
is accepted but ignored, with one warning per process. Gateway startup restores
recorded archived skills without overwriting existing destinations; conflicts
remain in `skills-archive` for manual recovery. Linux and macOS restore flat global and agent skills in both modes through directory
descriptors, without following symlinked components. Other platforms retain archives
for manual recovery.


Use `skill_list` to inspect loaded skills. Resolve a destination conflict before
retrying restoration; keep the archived file until recovery succeeds. Gateway startup retries recorded archives on the next start.


## Automation → Run, schedule and file review limits (v1.82.0)

These three cards are Admin-only and save through the locked configuration writer. Changes apply to subsequent runs, checks or approval requests without a restart.

| Card / field | `config.toml` key | Default / allowed range |
|---|---|---|
| Single-run / default seconds | `[runtime] default_timeout_secs` | Optional; 30 up to `max_timeout_secs`. Blank removes the override: every runtime uses 1800 seconds (never above the ceiling). Before v1.84.0, runtimes other than Claude used 300. |
| Single-run / ceiling seconds | `[runtime] max_timeout_secs` | 3600; 60–14400 seconds. Raising it allows long runs to consume more quota. |
| Single-run / default steps | `[runtime] default_max_turns` | 50; 1 up to the step ceiling. More steps can use more quota and time. |
| Single-run / step ceiling | `[runtime] max_turns_limit` | 200; 1–10000. Administrator only. |
| Assignment schedules / active per person | `[goal_defaults] assign_schedule_max_active` | 20; 0–200. Zero prevents creation and resume. |
| Assignment schedules / minimum interval | `[goal_defaults] assign_schedule_min_interval_minutes` | 60; 60–10080 minutes for non-Admins. The Admin minimum stays 5 minutes. |
| File reviews / daily total | `[agent_files] review_daily_limit` | 200; 0–100000. |
| File reviews / daily per person | `[agent_files] review_daily_limit_per_user` | 40; 0–100000. |
| File reviews / daily per employee | `[agent_files] review_daily_limit_per_agent` | 60; 0–100000. |
| File checks / per person per minute | `[agent_files] checks_per_minute` | 10; 1–1000. |
| File approvals / pending per person | `[agent_files] max_pending_per_user` | 20; 1–200. |

The employee's existing `[runtime] timeout_secs` now applies to Claude as well. When no employee value is set, a non-Admin owner can only set 300 seconds or less (and must obey any lower global default or ceiling). The employee page shows the effective seconds and ceiling. Values above the ceiling are rejected on save and clamped at execution. An invalid global timeout configuration logs a warning and restores the hard defaults (1800 seconds for every runtime, ceiling 3600); it never permits unlimited execution. A valid global default replaces the runtime-specific default only when the employee value is absent. The ceiling also bounds an unset default. Task-specific limits and sandbox limits can still shorten a run; goal-specific limits range from 30 seconds to `min(max_timeout_secs, 3600)` (at most one hour).

Web conversations use the target employee’s effective timeout, bounded by the global ceiling, plus 30 seconds for delivery. Routine constants and role overrides are unchanged. Exhausting a review quota still produces at least a warning (or a block), never skips review. There is no temporary relaxation switch.

**Settings → Company information** (`/app/system/settings/company`) sets the customer name (up to 120 characters, excluding controls, line separators and Unicode format/bidi characters) and a PNG, JPG or WebP logo up to 1 MiB. SVG and animated uploads are refused. The server checks the image bytes, limits dimensions to 4096 × 4096, decodes the image, removes metadata and re-encodes a PNG thumbnail within 256 × 256. Saving first updates the name and optional logo removal through RPC, then uploads a selected logo through HTTP. These are separate transactions: if upload fails, the saved name remains, the selected file is retained for retry, and the form does not show full success. A blank name uses the product name; an absent or unloadable logo falls back to the product logo.

The sidebar and login header use customer identity; invitation emails and their preview use the company name and logo. The signed distributor product identity stays on About and in the login footer. This does not edit or override the distributor feed. The setup checklist's company item now reads this company name and links here; the older general display name still controls the gateway's local-network name.

`company.get` and `company.update` require Admin; the latter accepts only `name` and optional `remove_logo`, and rejects `logo_base64`. Logo upload uses `POST /api/company/logo` with the stored access token in `Authorization: Bearer`, without cookies. The gateway validates the JWT and current Admin account before reading the raw binary body. The route and stream each enforce 1 MiB; the content type must match PNG, JPEG or WebP magic bytes. Each account and TCP peer IP has six attempts per 60 seconds (proxy users share its IP budget). The IP limit runs before authentication and returns 429 without an individual audit entry on excess requests; admitted requests and their outcomes are audited. The account limit runs after live Admin validation. The body has a 30-second timeout, with at most two concurrent upload jobs. WebSocket messages retain their global 1 MiB limit. The update uses the existing locked configuration commit path for `[company] name` and `logo_hash`; sanitized files live under `<home>/company_logos/`. The public `/api/company` endpoint exposes only the name and logo URL for sign-in. The public reader opens each logo once, verifies a regular file with exactly one link and a bounded size on that descriptor, then validates the PNG and SHA-256 hash. Logo URLs contain that hash, serve only PNG with `nosniff`, and allow one year of immutable caching. Old thumbnails remain available for previously sent invitations and cached pages, including after removal. Treat these assets as public. Changes refresh immediately in the saving tab and when another tab regains focus or reconnects.

**Codex external configuration gate (since v1.80.0):** Employees, Explore, utility, Task Sandbox and Discovery may run when external layers are absent or define no MCP servers; detected MCP or unreadable/unparseable existing layers refuse launch with the source named. A refused explicit Codex judge fails acceptance without retrying the default judge. This checks a local/cache snapshot before launch, not complete isolation from subsequent cloud refresh. See [checked sources and limits](../architecture/extension-gates.md).

OAuth uses this base only when its origin matches the browser’s validated dashboard origin; LAN access and paste-back flows keep their existing behavior. After upgrading with this fix and updating the registered callback, remove the v1.79.1 workaround rules for unprefixed `/api/me/google/callback` and `/me/connections`.

## Employee health (v1.80.0)

Admins and Managers can open **Employee health** (`/employee-health`) in both editions. The read-only page starts with a summary; expand an employee to see the last recorded reply, failures over the past 24 hours or 7 days, goals waiting for a person or paused, and account availability. Failure groups distinguish empty replies, quota or budget limits, rate limits, invalid authentication, timeouts, gate refusals, delivery failures and other errors. Account availability reflects only accounts matching an employee's explicit `account_pool`; without a pool it is unknown. It does not test the CLI's native sign-in or contact the provider.

The latest successful reply means a non-empty response was generated by the shared channel reply path. It does **not** confirm that the channel delivered it. Older records may not establish this time. Failure totals combine `channel_failures.jsonl` with the separate `employee_health.jsonl` turn log, reading at most the last 4 MiB of each; the result is cached for about 30 seconds. A partial-data notice means records are unavailable or the read limit was reached, so the displayed window may be incomplete. Tool-call success and recorded spending are not proof of a successful reply.

Health reminders use the same shared reply path across channels. By default, an employee triggers one reminder after five consecutive failed turns, or after receiving messages without a successful generated reply for six hours. A successful reply resets the reminder. An active authentication-outage alert suppresses a duplicate authentication-only health reminder. Reminders go to active administrators and employee owners through their verified linked channels and the existing notification and quiet-hours path. The reminder is claimed before sending and is attempted at most once for that failure streak: a failed send is not retried until a successful reply resets it. No linked or reachable destination means delivery is not guaranteed; a reminder attempt is not delivery confirmation.

Administrators can set the thresholds in the existing Advanced config editor (`config.toml`); there is no second settings form on the health page:

```toml
[employee_health]
enabled = true
consecutive_failures = 5 # 1..100
no_success_hours = 6    # 1..168
```

An absent configuration file or omitted section uses these defaults. Read errors other than a missing file, or invalid settings, disable health reminders. Turning reminders off does not grant employee permissions or change task execution. The health page remains read-only.

## Employee edit page → Tools & permissions → Tool permissions (v1.81.0)

The **Tools & permissions** tab of the employee edit page has two sub-tabs: **Tool permissions** and **Permission history**. The table lists every catalog tool by category, with a **Can use** and a **Needs approval** column, a per-category select-all (`N/M can use`) and a search box. Edits stay in a draft: changed rows are marked, a sticky bar offers **Discard changes** / **Save**, and Save opens a confirmation that counts newly allowed, no-longer-allowed and needs-approval tools with a per-tool before → after line. Confirming writes through the normal `agents.update` `capabilities` payload. Only an Admin can change anything; other accounts get the same table read-only, with every checkbox disabled and no select-all or save bar.

How the table maps to `agent.toml [capabilities]`:

- **Can use** = not matched by `denied_tools`, and either `allowed_tools` is empty or matches the tool (the gateway's own rule: denied always wins, a non-empty allow list is allowlist mode). Matching is anchored and wildcard-aware, e.g. `mcp__duduclaw__*`.
- Unticking a tool always **appends it to `denied_tools`**; `allowed_tools` is never shrunk or rewritten, so a wildcard allow list stays exactly as written and every tool it covers shows as allowed. Re-ticking removes that deny entry. A tool covered by a *wildcard* deny entry cannot be turned on here (the row is locked); edit the entry in Advanced settings.
- **Needs approval** = `approval_required_tools` (bare tool names), the list the MCP dispatch gate enforces for every tool. A tool already asked by a wildcard approval entry or an `action_rules` `ask` rule shows as needs-approval but is locked. The checkbox is disabled while **Can use** is off.

The previous Allow list, Block list, Action rules and Approval list blocks now sit in a collapsed **Advanced settings** at the bottom of the tab and stay in sync with the table.

**Permission history** (Admin only) lists changes to this employee's permissions from the `agent_authority_changed` audit rows: time, who, and each tool's old state struck through → new state. Changes not saved from the table are marked **Changed in Advanced settings** (this also covers older changes made before the table existed). The tab is backed by the Admin-only `agents.permission_history` RPC (`agent_id`, `limit` up to 100, `cursor`), which reads the same audit log as `security.audit_log`.

## Optional independent plan review

Set `plan_review = "goldfish"` in `config.toml [goal_loop]` to review a successfully generated plan before it is shown for human approval. The default is `"off"`; a missing or malformed setting also means off. Three fresh calls run concurrently in the current task, each with a 45-second timeout, adding at most 45 seconds: restate the goal and identify unclear parts, remove unnecessary work, and check the decisions, permissions and data needed to execute. Each reviewer receives only the XML-escaped goal, acceptance criteria and plan as data, without conversation, memory, SOUL or employee identity. Each reply asks for Traditional Chinese, at most five bullet points, and is kept to 400 characters.

These calls are system utility spending under `goal-plan-review`, use the existing system provider resolution without an employee directory, and are **not charged to the employee budget**. The versioned `plan_review` JSON is display-only: it never changes `plan_pending` or `judge_feedback`, never enters an execution or judging prompt, and never replaces human approval. Failed, empty or timed-out reviews show **Not run**, including when all three fail; the task still waits in `needs_human`. Both task detail and the Inbox show a collapsed **Independent review (without conversation context)** section. Channels show only the number of completed lenses and a dashboard pointer, never review text. This count is completed lenses, not individual findings.

## Per-employee tool list pruning

In an employee's overview, Admins can open **Tool list pruning** to select a mode, inspect unused tools and estimated token savings, or restore the list while pruning is on. The selector uses the existing employee update path. The status and restore RPCs are Admin-only: `agents.tool_pruning_status {agent_id}` and `agents.tool_pruning_restore {agent_id}`. Estimates use each candidate tool's serialized definition length divided by four; they are not tokenizer measurements or measured provider savings.

```toml
# agent.toml
[capabilities]
tool_pruning = "shadow" # "off" | "shadow" | "on"
```

The default is `shadow`: observe and report, with the same `tools/list` response as `off`. Unknown or malformed values behave as `off` and warn once. Only `on` hides eligible tools, after all existing discovery filters. This never grants or revokes permission: a hidden tool remains callable through the existing dispatch gates. A successful hidden-tool call makes it visible again through `notifications/tools/list_changed`.

The calculation reads at most the last 5 MB of `tool_calls.jsonl`. Missing or unreadable logs, and fewer than ten recorded turns, leave the list intact. A candidate must be unused across at least ten turns spanning two sessions, or five sessions. Memory, tasks, working state, messaging, approvals, wiki reads, tool discovery, Admin/unknown-effect tools and tools with active scoped task grants stay visible. A turn is a distinct host-stamped `(session_id, turn_id)` pair, not a log line. Channel calls use the conversation session and turn; dispatched work uses its own dispatch session and run (one run is one turn). Older rows without these identities do not establish turn samples, but a successful use still resets that tool’s unused window. Thresholds count the turns and sessions since each tool’s last successful use. Results are cached per process for five minutes. Restore writes an employee-specific reset marker; usage before that marker no longer contributes, so the full eligible list returns. Existing permission filters still apply.

Claude CLI `minimal_context` uses `--tools` for built-in CLI tools; it does not prune MCP definitions. Its behavior is unchanged.

## Account roles and visible AI staff

Giving an AI employee Bash or machine tools lets anyone bound to it direct those tools. Review the employee's capabilities before binding people to it; an Admin may still grant native tools to ordinary AI employees.

Employees using the `system-operator` preset are Admin-only. The server checks the resolved preset binding. Non-Admins cannot bind to them, chat with them, create tasks or goals for them, or have work dispatched to them on their behalf; they are excluded from `agents.callable`. Existing bindings stay stored but are refused when used. Assignment schedules previously created by non-Admins no longer create tasks or goals for that employee; firing pauses them automatically, and resume is refused. Outbound approval cards (for both CLI built-in tools and MCP tools) are visible only to Admins; Managers no longer see redacted cards. Channels and the Mini App show only a plain notice, without outbound approval cards, summaries or action buttons. Admin access and authorized unattended work are unchanged. Personal has a single-owner exemption only when users.db is absent, empty, or contains exactly one active Admin account that has completed the first password change; suspended and offboarded accounts count too. Multi-account deployments still require a valid administrator even after a paid license lapses to Personal, as do deployments with an unreadable account store.

Employee accounts see only the AI staff directly bound to them. Managers also see their reports' AI staff in the sidebar, AI staff list, Timeline and Runs, marked as a team member's AI employee. Existing bindings stay as they are; review and remove any grants that should not be there. Shared wiki pages follow the account's department in member settings (`users.db`, `users.department`). Non-admins see company pages and only their own department's pages, including restrictions set with `visible_to_departments`. An account without a department sees company pages only. Lists, search, page reads, statistics and exports use the same rule. Unreadable permissions or invalid visibility settings refuse access. Admins retain company-wide access. Sharing a page still requires the source AI employee's Owner binding or Admin.

Company usage (`billing.usage`) and daily growth reports require Manager. Widget generation and model refresh also require Manager because they use model quota or contact providers. System logs require Admin; employee automations use the record-level scopes described above. Only Admin sees the cost section of Reports and Home, or the upload-and-install action in Experts. Other account roles do not request these restricted sections.

## Codex CLI updates

## How saving works

Enterprise setting (v1.76.0, Manage → Advanced → Members, **Organisation settings** card; the Members page exists only in the Enterprise edition): `users.org_settings.get/update` controls `[people] manager_team_history` (default on for valid config). Inform staff before enabling it. The switch takes effect immediately, advances the activation boundary when re-enabled, and is protected/audited in the raw editor too. See [Read-only team conversations](../features/68-manager-team-history.md).

Conversation storage (v1.81.0, Enterprise edition, Manage → Advanced → Members, **Organisation settings** card, Admin): the same RPC also reads/writes `[sessions] archive_after_days` (default 30; 0 = never archive; max 3650) and `[sessions] purge_after_days` (default 0 = never delete; counted from when a conversation was archived; max 3650). No restart: the 6-hour maintenance task re-reads both on every run, and an unreadable or invalid config archives with the default and never deletes. Both keys are protected/audited in the raw editor, which also refuses values outside 0–3650. Archived conversations leave the normal list but any new message brings one back; staff restore their own from the WebChat history menu (**Archived conversations**, `chat.sessions.restore`), managers from Team conversations (`users.team_history.restore`). **Team conversations start date** (`team_history_since`, between 2020-01-01 and now) sets from when managers can read; moving it earlier exposes older conversations and requires the admin's current password (plus MFA code when enabled), and every change is audited as `team_history_since_changed`. Upgrade note: the previous fixed rule was archive after 3 days and delete 90 days later.

- System settings (`config.toml`) are written through `system.update_config`, which is admin-only. A page sends only the fields you changed; with no change nothing is sent and the page says "Nothing changed, so there is nothing to save."
- The write locks the file and re-reads it. If another writer changed the file after you loaded it, the save is refused; reload and save again.
- When `config.toml` does not parse, `system.update_config`, the live data feed editor and the Advanced config editor refuse to write; fix the syntax in the Advanced config editor first. The other settings pages that write `config.toml` (channels, accounts, Odoo and so on) refuse in the same way.
- A save edits the file in place: only the keys you changed are rewritten. Comments, blank lines, key order and the formatting of every untouched key stay exactly as you wrote them, and a changed value keeps the comment at the end of its line. A new key goes at the end of its section and a new section at the end of the file. This holds for every settings page that writes `config.toml` or `inference.toml`, not only the Advanced config editor.
- Keys that only take effect after a restart come back in `restart_required`. The Settings and Channels pages show "These settings take effect after the gateway restarts" until the gateway has restarted (you can also dismiss it). The Inference page and the employee edit page do not show this banner.
- Each change to one of these keys also writes the audit event `config_protected_key_changed` with the old and new value: `acp.trusted`, `tick.allow_command_sources`, `container.sandbox.when_unavailable`, `container.sandbox.script_when_unavailable`, `memory.supersession_trust_guard`, `dashboard.public_url`.

## Settings → General → Dashboard public URL

Admins set `[dashboard] public_url` here: the full address people use to reach the dashboard, including any reverse proxy sub-path, for example `https://example.com/agents/`. It must use HTTPS; HTTP is allowed only for `localhost`, `127.0.0.0/8` or `::1`. The URL must have no user name or password, query (`?`), fragment (`#`), `..` or encoded `/` / `\`. The gateway refuses anything else on save; a value that was hand-edited into `config.toml` and is invalid makes OAuth sign-ins refuse to start until it is fixed (they never fall back silently to an address without the sub-path). Leave the field empty to clear the key. The change applies immediately and writes `config_protected_key_changed`.

When public_url is set, it is used for every OAuth callback and return link, with the sub-path kept:

| Flow | Callback URL the provider redirects to | Where the browser lands afterwards |
|---|---|---|
| Remote MCP server (Integrations → MCP → Remote servers) | `<public_url>/oauth/mcp/callback` (registered automatically by dynamic client registration) | `<public_url>/manage/integrations?tab=mcp&mcp_tab=remote` |
| Personal Google account (My connections) | `<public_url>/api/me/google/callback` | `<public_url>/me/connections` |
| Built-in Google Workspace, GitHub, Notion and Slack OAuth | `<public_url>/api/mcp/oauth/callback` | The result page links to `<public_url>/manage/integrations?tab=google` (Google) or `?tab=mcp` |

- **Register the new callback URL.** After you set or change public_url, add the new callback URL to each OAuth app you use: Google Cloud Console → Credentials → your OAuth client → Authorized redirect URIs, and the GitHub OAuth App's Authorization callback URL (a GitHub OAuth App has one callback URL, so replace it). Do the same for Notion and Slack apps. The Integrations page shows the exact URL to register. A sign-in that was already in progress finishes with the URL it started with.
- The browser's own origin is still checked first: a direct redirect is only used when the dashboard is opened on a loopback address or on an https origin listed in `[gateway] allowed_origins`. Otherwise the paste-back flow at `http://127.0.0.1:<port>/…` is used as before (that loopback address never has a prefix). If the dashboard is opened on an allowed origin other than public_url, the redirect still goes to public_url, and the gateway logs a warning once.
- Links to the dashboard inside chat messages (notices, decision cards) use the first valid `public_url` of `[dashboard]`, `[general]` and `[gateway]` (http or https, not localhost or loopback, no user name, query or fragment). With none valid, a gateway in a container adds no link and a gateway on an ordinary machine links to `http://localhost:<port>` (v1.84.0). See [Google Chat](channels-googlechat-teams.md#private-dms-decision-buttons-and-dashboard-links-v184).
- Without public_url nothing changes: remote MCP and personal Google sign-ins return to the browser's origin with no path, and the built-in providers use `http://localhost:<port>/api/mcp/oauth/callback`.
- Reverse proxy: forward `<prefix>/oauth/mcp/callback` and `<prefix>/api/…` to the gateway with the prefix removed.
- Limitation: the dashboard app itself is built for the root path. It loads `/assets/…`, calls `/api/…` and `/ws`, and its page routes have no base path. Serving it under a sub-path therefore also needs the proxy to send those root paths to the gateway, or the dashboard needs its own host name. public_url fixes the OAuth callback and return addresses; it does not make the dashboard app prefix-aware. When the page has a same-origin `<base href>` (for example injected by the proxy), the dashboard sends that sub-path with OAuth starts and member invitations; the gateway still validates it.

**Memory language** decides the language of what the system writes into memory by itself: pinned instructions, key facts, conversation summaries, facts kept from conversation distillation, and the title and summary of automatically filed knowledge pages. The language is taken from the employee's memory language, then the global memory language, then the employee's reply language (or the global default language); if none is set, memories follow the language of the conversation. `auto` passes the decision to the next level, so on the employee page "Follow reply language" uses the global memory language first when one is set. Memories saved before v1.84.0 are not changed; to convert existing Simplified-Chinese memories, see [Converting Simplified-Chinese memories](memory-convert-script.md).

**Background work** for an employee (key facts, pinned instructions, conversation summaries, titles, conversation distillation and knowledge filing, situation checks) runs on the employee's own engine when that engine is Claude, Codex or OpenAI-compatible. Grok and the other CLI engines cannot run it. For those employees the work uses the service chosen on the employee page; without one, it uses the global `[runtime] utility_provider` only when that key is actually written in `config.toml` and names one of the three services. Otherwise the work is skipped. Before v1.84.0 such employees silently used Claude. The employee page shows which service is used or that the work is skipped, and the system check **Employees whose background work is skipped** lists them. The conversation text is sent to the chosen service. The model is the employee's `[model] utility` when it belongs to that service, else the global `[runtime] utility_model` when the global provider is the same service, else `claude-haiku-4-5` for Claude or the service's own default.

**Model that does not match the engine.** An employee on another engine that declares model prefixes, whose saved model is a bare Claude name (`opus`, `sonnet`, `haiku`, `fable`), now runs on that engine's default model (in the notice Codex is called 「ChatGPT」). The employee page and the system check **Employee model and engine** show a notice asking you to choose the model again. The notice appears after the employee has run at least once since the service started.

**New engines.** An engine installed from the dashboard can be used at once, without restarting the service. Re-detection (`runtime.detect`) rebuilds the engine list only when the detected engines changed, at most once a minute per data directory; when an employee's engine or fallback engine is missing, the list is checked again at most once a minute.

A per-employee Slack bot also starts when it is added.
- Thinking display in messaging apps (no dedicated control; set in the Advanced config editor, read on every reply): `[thinking] channel_audience` = `internal` (default: a sender whose verified channel identity belongs to an active dashboard account that is an Admin or is bound to the answering employee sees the timer and a masked summary, everyone else the timer only), `all` (every sender of a one-to-one chat sees the summary) or `none` (nothing); `[thinking] channel_group_display` = `status` (default: group chats show the timer only), `summary` or `off`. The stricter of `[thinking] display` and the answering employee's `[model] show_thinking` still caps both. An unreadable `config.toml` or an unknown value shows nothing. Website visitors (Odoo live chat, the WebChat widget) never see thinking. See [Thinking display in messaging apps](../features/66-thinking-in-messaging-apps.md).

### WebChat protocol and concurrent turns

`/ws/chat` accepts the existing `auth` and `user_message` frames. Different sessions on one socket can run concurrently; messages for the same session run in FIFO order, including across sockets. Session ownership and employee access checks still apply. Set the per-user and gateway-wide limits in the Advanced config editor:

```toml
[webchat]
max_in_flight_turns = 3
max_global_turns = 10
```

`max_in_flight_turns` defaults to **3** per user; `max_global_turns` defaults to **10** across the gateway. Both accept **1–64**, and both count active and queued messages, including messages whose sockets have closed. Running and queued counts are reported separately. Cancelled waiting messages and supplements already claimed by a merged dispatch no longer occupy admission capacity. The per-user limit is shared by all of that user's sockets; exceeding either limit receives an immediate `error` with `code: "turn_limit"`. For signed-in operators it also carries `admission: { reason, limit, running, queued }`. Reasons are the closed set `user_limit`, `global_limit`, `cancel_quota`, `store_unavailable`, `config_invalid` (and `duplicate_message` for duplicate IDs, whose outer code remains `duplicate_message`). Limit counts apply to the user or gateway according to the reason; cancellation quota uses its rolling-hour limit. Each refusal writes a structured `webchat_turn_refused` event to the ordinary gateway log with user, employee, reason, limit, running/queued counts and timestamp; these events do not enter the security audit chain. Waiting messages receive `turn_queued` with the same structure and `reason: "conversation_queue"`. The dashboard translates reasons into Traditional Chinese, English or Japanese. Public-widget and `odoolivechat:` sessions receive no operator capacity details. No per-member override or new settings control is added. Invalid values or unreadable configuration refuse new turns. Connections are limited separately: 3 per IP before authentication, 3 per dashboard JWT user afterward, and 10 globally. Widget visitors retain the 3-per-IP connection limit for the entire connection; reconnecting with a fresh visitor identity does not bypass the gateway turn limit.

Admission first reserves a turn slot under the in-memory per-user and global caps, then reads the persistent rolling quota on a blocking worker through a shared broker. A refused quota releases the slot; only accepted turns join the session FIFO. The quota is **100 started-turn cancellations per rolling hour per authenticated account**, or per transport IP for widget visitors. Visitors behind the same NAT share this quota; the restriction lasts at most one hour after the last counted cancellation. Reconnecting or restarting does not reset it. Only that account or IP is limited; the global tombstone count never refuses a new turn, and legacy NULL principals count toward no quota. A quota refusal or unreadable store returns `turn_limit` with the rejected message’s `request_id`. Existing turns can still be cancelled; queued turns cancelled before work starts write no fence and consume no cancellation quota.

When identity checks are temporarily `Unavailable` and the connection can still carry frames, the gateway sends a terminal `error` with `code: "identity_unavailable"` and `msg_id`, `request_id`, `conv`, and `session_id`. It contains fixed text only, with no reply, thinking, attachment, or session lookup result. Before admission the text says the message was not sent; at delivery it says the reply could not be delivered. An unavailable original turn credential still refuses and rolls back delivery, including at the final writer recheck. If only a recipient connection becomes invalid, that connection is skipped and the original turn history remains. Revoked connections keep the existing close behavior and receive no such notice.

Reopening a conversation whose last message is from the user shows an unanswered notice and rereads history every 5 seconds for 2 minutes, then every 30 seconds until 30 minutes. A completion frame for that session triggers an immediate reread. Leaving, unmounting, starting a new turn, or finding a reply or a stored failure stops polling; rereads preserve the draft. After the bound, the notice suggests resending or asking an administrator to check the logs. A streaming turn with no activity for 60 seconds shows a gentle wait hint updated each minute, including after reconnect; keepalive heartbeats do not reset it. Failures in other conversations produce a fixed notification without ending the current turn. Empty-reply and internal-turn failures are saved as display-only warnings when the conversation is reopened.

Progress, thinking and step updates are coalesced to the latest pending update when the client is slow. Thinking redactions are preserved as control frames and clear previously shown text before the terminal frame; each turn displays at most 64 thinking blocks. Terminal frames have a reserved bounded lane; earlier control frames from the same turn still precede its terminal frame. A frame that expires before its write begins is skipped without closing the writer; a socket write failure still closes it. Terminal frames include `progress_dropped` with the number of skipped updates. A completed reply is committed to the conversation history before live delivery. A timeout, closed writer or missing acknowledgement does not revoke that history or its owned archives. Actual source revocation, cancellation and invalid original credentials still refuse delivery and retain the existing rollback behavior.

After authentication, clients can send `{"type":"subscribe","session_id":"<owned session>","conv":"<local conversation>"}` to receive completed replies on a new connection. The existing resume ownership and employee-access checks apply. `session_id: null` clears subscriptions; switching subscriptions also invalidates queued deliveries. Only connections of the same authenticated principal subscribed to that exact session receive the reply. Widgets retain per-connection identities and cannot resume another visitor session. Sending a message automatically subscribes that socket; legacy clients retain at most 64 conversation subscriptions, evicting the oldest, with history available afterwards.

User rows persist the client `msg_id` as `client_msg_id`. After saving, `turn_accepted` returns `user_row_id`, the canonical `session_id`, `conv` and `msg_id`. Recovery first checks the exact session and `user` role, then the acknowledged row ID; if the acknowledgement was lost, it requires a unique user row with that persisted client-message ID in the returned history. Ambiguous IDs refuse automatic recovery. This also covers attachment-only and repeated text, without content or prefix matching. When no exact match exists, the local message is retained. Reconnecting clients retain the server-provided session ID, including `@` routing. If a routed session ID was never received and cannot be derived from the known conversation, automatic recovery cannot find that bucket; the client does not guess the `@` target. Subscription can attach to an owned admitted turn before its history row exists; refusal returns `subscription_unavailable` without erasing the local transcript.

The socket writer rechecks access to the employee who actually answered after socket readiness. It then verifies the ACL generation and calls synchronous `start_send` within a short `BEGIN IMMEDIATE` transaction, ordering frame admission against ACL updates. The transaction does not span readiness waits or asynchronous flushing; data admitted before a later revocation cannot be recalled. Assistant rows are stored with a pending tombstone and remain excluded from history until the final authority and source checks permit publication. Refused rows stay hidden even if content cleanup fails, including after access is restored. A transport failure alone still preserves authorized replies. These changes do not constitute native-platform or real-socket acceptance evidence; backend compilation and those checks remain pending.

Explicit logout or an account switch sends `{"type":"logout"}` before closing the chat socket. When received, the gateway revokes in-flight turns started by that socket, plus turns resumed with the same session and original client `conv`, including replies awaiting delivery. Other tabs use different conversation nonces and are unaffected. Ordinary disconnection does not send this frame. If the transport is already lost, a logout frame cannot reach the gateway; credential checks and conversation ownership still apply.

Both WebChat and the dashboard RPC socket already send protocol ping frames every 30 seconds and count pong as liveness (60 seconds of silence, checked on the heartbeat tick). Browser JavaScript timers are not needed to answer protocol pings; OS sleep can still interrupt networking. Returning to a visible dashboard tab now reconnects immediately, resubscribes to the current conversation and reloads its history. A saved reply replaces the waiting state; an unanswered conversation uses the existing bounded history polling.

WebChat keeps the conversation and its server session across reconnects, including the next message you send; an empty new conversation gets the new connection’s session. The composer shows connecting, reconnecting or disconnected status at all screen sizes. Unsent text and attachments stay in the composer, with a notice if sending fails. If an interrupted turn does not resume within 10 seconds, its waiting indicator stops and a notice explains that the AI may still be processing it. A later reply can still arrive or be recovered from history; the interruption does not cancel the server’s work or resend the message. After automatic retries stop, choose **Reconnect**. Going online, returning to a visible tab or restoring a page from the browser’s back/forward cache resets the retry budget and reconnects immediately.

Existing frame fields are unchanged. Turn frames add `session_id`, `conv` and `msg_id` so clients can route progress, replies and errors to the originating turn. Send a unique `msg_id` with each `user_message`; use the returned session id when targeting a turn:

```json
{"type":"user_message","content":"Hello","conv":"c1","msg_id":"m1"}
{"type":"cancel","conv":"c1","msg_id":"m1"}
```

Commands cannot be cancelled once execution begins. A cancel frame must name `session_id` or `conv`; `msg_id` is optional. Without `msg_id`, it selects the active turn. An ambiguous conversation, another user's session, an unknown or already cancelled turn, or a turn already delivering its reply returns `turn_not_found` without cancelling anything. Control replies use `request_id`, separate from the target turn's `msg_id`; `turn_not_found` and `duplicate_message` do not terminate that target. Admission refusal `turn_limit` identifies the rejected message with `request_id`.

The cancelling socket receives a best-effort `cancel_accepted` with `request_id`, target correlation fields and `cancel_outcome: "waiting" | "running"`; no ordering against the terminal outcome is guaranteed. The final outcome goes to the turn's original socket: an `error` with `code: "cancelled"` carrying the cancel's same `request_id`, or `cancel_failed` if recording, approval cleanup, or delegation queue cleanup fails. Clients can match the cancellation whichever frame arrives first. Cancelling a waiting message releases its admission capacity immediately and performs cancellation cleanup without waiting for its predecessor. A lightweight FIFO link remains until that predecessor finishes, so later messages cannot overtake the running reply. Both the acknowledgement and the final `cancelled` frame distinguish `waiting` from `running` via `cancel_outcome`. The dashboard settles the cancelled message on acknowledgement and localizes the outcome; it never treats `cancel_accepted` as an error. If an approval was already approved before cancellation, `cancelled` includes its ids in `approved_before_cancel`: those previously authorized effects may already have happened.

Cancellation stops the turn's CLI process group and records an internal cancellation marker only when a session already exists. The marker is excluded from conversation history and compression summaries; cancelling a never-started queued turn does not create a session. Pending approvals belonging to the turn are withdrawn atomically with the cancellation fence (`decided_by = system:cancel:webchat_turn`). Fences have a fixed retention window of 24 hours from cancellation, independent of approval TTL; the former 30-day approval TTL cap is removed. The gateway lock holder reuses an hourly maintenance loop to delete at most 1,000 fences per pass, independently of dashboard activity. Above 100,000 rows it also evicts the oldest rows older than one hour and logs a warning; rows younger than one hour are never evicted, so the cap may temporarily be exceeded. Admission performs no sweep or migration. Fences guard late approval inserts and delegation dispatch racing termination: a process that escapes the process group through `setsid` is outside this non-sandbox guarantee. Cancellation markers are retained for the shorter of session retention and 90 days, capped at 1,000 per session, and removed on session purge. Completed actions and created tasks are not undone. Cancellation never bypasses the outbound-send guard: an unsent or confirmed-finished send releases its lease normally; an unconfirmed send, or a lease the killed MCP process could not release, retains the existing protection for up to 6 hours.

WebChat stores empty-reply and internal-turn failure notices so reopening the conversation shows the warning even if its socket frame was missed. These display-only records are credential-masked, capped at 2,000 characters, and excluded from model context, summaries, memory readers, and team history. Cancelled turns, authentication failures, and turn-limit rejections do not create failure notices. A stored failure also ends the unanswered-reply waiting notice.

Cancellation also stops delegations for the exact session and turn that are still queued. The `cancelled` outcome adds `delegations_cancelled`, the number stopped; a delegation queue cleanup failure returns `cancel_failed`. Work already handed to another employee keeps running. A turn awaiting quota admission cannot be cancelled until it passes quota and joins the FIFO; an earlier cancel returns `turn_not_found`.
Cancellation also stops delegations for the exact session and turn that are still queued. The `cancelled` outcome includes their count in `delegations_cancelled`; a delegation queue cleanup failure returns `cancel_failed`. If matching delegated runs are still running, the same `type: error, code: cancelled` frame also carries `downstream_running` and an opaque, single-use `downstream_ref`. Both fields are absent when there is no such work. The client receives counts only, without employee names, task content or message IDs.

An authenticated client may then send `{"type":"cancel_downstream","downstream_ref":"<reference>","request_id":"<optional id>"}`. The gateway checks the live credential again and processes the stop in the background. It waits up to 15 seconds and returns `type: downstream_stopped` with `request_id`, `stopped` and `still_stopping`; work still shutting down is not counted as stopped. The reference belongs to its original user and principal, expires after 10 minutes, and is lost on gateway restart or bounded-store eviction. Unknown, foreign, expired and consumed references all return `downstream_ref_unknown` without stopping work. Credential lookup failure returns the retryable `credential_check_unavailable`; a revoked credential is refused. Widget visitors receive no offer and cannot use `cancel_downstream`. Credential-revocation cancellation automatically requests a stop for the turn's traceable delegated runs, without asking the person.

Sending no frame leaves the running delegations alone; there is no decline frame. The existing cancellation fence still prevents those runs from delegating further or raising new approvals while it remains in force. Stops follow only the exact originating conversation and turn and exclude work attributed to another person. An external action already executed cannot be recalled. Task-board tasks and goals created by the turn are not followed, and a run that drops its origin information cannot be found. A turn awaiting quota admission cannot be cancelled until it passes quota and joins the FIFO; an earlier cancel returns `turn_not_found`. The [terminal control room](tui.md#chat-and-input-focus) offers the follow-up question in list focus.

A host-provided approval origin that is incomplete or invalid refuses the approval request; only a fully absent origin retains legacy unscoped behavior. Approval origin inherited through environment variables is not signed. An employee with unrestricted Bash can forge those variables; the Bash guard is a speed bump, not isolation. Withhold Bash or use the task sandbox when actual containment is required.

Closing the socket does **not** cancel accepted turns, including queued messages. They continue to completion. Signed-in dashboard users can reconnect to resume an owned session or cancel a still-active turn. Widget visitors receive a new identity on reconnect and cannot resume or cancel the previous connection's turns; those turns still count toward the global limit. The dashboard shows queued messages and a cancel action on each waiting message, plus a Stop button for the foreground running turn. Protocol clients can also send `cancel` directly.

## Integrations → Odoo → Schema snapshot

**Re-scan Odoo structure** calls `odoo.schema_scan` and is available only to an administrator; the RPC enforces the same role. Save the connection settings first: this action scans the saved global connection and every employee’s effective overrides. Unsaved form values are not scanned. The page shows the last scan time, scan-time server version, model / field counts, truncation, latest failure and the latest diff summary. A server-version mismatch recommends another scan. It does not change Odoo data, permissions or the shared wiki. Manual attempts, including failures, share a persisted 60-second cooldown for the saved profile; an early retry reports how many seconds to wait. Both dashboard actions (`odoo.schema_scan` and `odoo.discover_schema`) share this cooldown and scan lock. The wiki workflow sanitizes identifiers and labels before writing, marks external metadata as data rather than instructions, and retains technical field types and relations.

Rescan covers the saved global connection and every employee’s effective `[odoo]` settings, including company scope. Authenticated identities are deduplicated, at most two connections scan concurrently, and results show Ready or Failed for each employee. Metadata stays isolated by connection identity; one Odoo user never reuses another user’s snapshot. The dashboard actions share their persisted 60-second manual cooldown. After successful preparation, obsolete profile data is removed only if all effective identities are known. Cleanup holds a catalog lock while deleting idle lock files; an in-progress scan and its lock are preserved.

The long-lived gateway holding the instance lock checks every effective identity every 30 minutes, starting at gateway startup. It scans missing or truncated snapshots, changed server versions, changed installed-module names/versions, or missing access metadata. Completed scans and definitive failures consume the one-hour automatic slot; cancellation does not. MCP turns never launch scans. While preparation is pending, use `odoo_schema_fields` for a specific model. Same-version field-only changes still require a manual scan; reconnect active sessions with `odoo_connect` to refresh live field caches.

The overview without filters returns model names and short labels only, capped at 16 KiB. Fields are included only for a specific `model` or a query matching at most five authorized models, capped at 32 KiB. Responses include total matching model count and truncation. The shared-wiki summary is capped at 16 KiB; `odoo/schema-fields` remains a search-only `deep` reference page capped at 32 KiB and is not automatically injected into context.

## Integrations → Odoo → Personal member connections

Personal Odoo connections require an administrator to opt in with `config.toml`:

```toml
[odoo]
member_credentials = true # default: false
```

A missing key, unreadable configuration or non-boolean value disables personal connections. While disabled, `me.odoo.connect` and `me.odoo.test` refuse before contacting Odoo or decrypting a key. Identity selection skips personal credentials; person-key requests return `odoo_member_credentials_off`. Saved credentials remain stored, and members can still disconnect. Administrators can still list and revoke connections.

The browser-only Admin RPC `odoo.member_credentials.set_enabled {enabled: bool, acknowledge_risk?: bool}` returns `{enabled}`. Enabling requires `acknowledge_risk=true`. It uses the locked, hash-checked, format-preserving config commit path. Before publishing the setting, it writes `odoo_member_credentials_toggled` with the live actor's user ID, the requested value and a timestamp. Audit failure aborts the change. Records with `phase: "before_commit"` are write-ahead intents: a subsequent config write failure may leave an intent without a completed change.

`me.odoo.status` always includes `member_credentials_enabled`; `odoo.member_credentials.list` returns `{credentials: [...], enabled}`. Neither response includes secrets. Credentials are bound to the member's account credential epoch. A password reset or sign-out-everywhere that changes this epoch makes status report `needs_reverify` and prevents both use and testing of the old key. The member must enter the key again through `me.odoo.connect`. Suspended or deleted accounts cannot use stored credentials. Legacy rows without an epoch binding also require re-entry; the existing offboarding cleanup remains in place.

## Integrations → Odoo → Employee permissions

In Engine mode, open an employee's edit page to choose allowed tables and add action rules. No checked tables means no additional table restriction; no action rules means no additional action restriction. Odoo's own ACLs, feature switches and the built-in sensitive-table block list still apply. Each rule chooses a table (or **All tables**) and actions: **Search and read** saves both `read` and `search`; **Create**, **Update**, **Delete**, **Button actions** and **Other methods** save `create`, `write`, `unlink`, `action` and `execute`. For generic `odoo_execute` calls, button actions cover `action_*`, `button_*` and `toggle_*` methods, such as confirm, validate and archive. Grant `action` for all tables or `action:sale.order` for one table; `execute` remains the category for other methods. The stored format remains bare verbs for all tables and `verb:model` for one table, for example `read:hr.employee` and `search:hr.employee`.

Tables marked **Sensitive**, including `hr.employee`, require confirmation because they contain sensitive data. Without a scan or when the connection fails, use the scan button; configured tables and sensitive tables remain visible. An employee using another database may keep configured table names that are absent from the global scan.

Available actions come from the connected Odoo account’s own read, create, write and delete rights, detected on connection/schema scan and cached with a timestamp. Rescan after changing rights in Odoo. Button actions and other methods use write as an availability hint; Odoo decides which operations can actually run and still enforces record rules. Unavailable actions are disabled; unknown rights remain selectable with a hint. Previously saved unavailable actions stay checked with a warning and can be removed. All-table rules stay selectable because rights differ per table. Models blocked by DuDuClaw are not probed. Account-rights availability uses the saved global connection. For an employee with a separate connection, credential or company scope, the editor shows unconfirmed rights instead of applying another account’s denials.

Existing rules are grouped by table. A lone `read` or `search` appears as **Query and read — Partial** and becomes the pair on save. Existing `action` rules appear as editable **Button actions**. Unrecognized entries appear read-only under **Other settings** and are kept exactly until explicitly removed; the server permits preservation of existing entries but still rejects newly supplied invalid rules. The Odoo overview summarizes each rule as **Table: actions**.

| Control | Writes | Effect |
|---|---|---|

Columns: name (with the `ddc_<env>_…<last 4>` hint, client id and scopes — a stored scope that never takes effect for an external key, e.g. `odoo:read` on a migrated key, is struck through and listed), created by, created, expires, last used (from `<home>/mcp_keys_usage.db`, written at most once a minute per key by the MCP servers and read when the list is built; display only), status (active / disabled / expired).

**Upgrade from v1.81.** At its first start the gateway records the fingerprints of the `[mcp_keys.<key>]` entries in `config.toml` (except its own `gateway-internal` key) as *pending*, in one transaction. It then moves each one into `mcp_keys.db` (fingerprint only; an existing `name` or `label` field becomes the name, otherwise `migrated-<id>`; client, external flag, scopes and creation time are kept). The key expires at the instant v1.81 would have started refusing it (creation + 31 days, to the second), so its lifetime is unchanged. The audit record is written before the entry is removed from `config.toml`; the rest of the file stays as it was. An entry whose move or audit record failed stays in `config.toml` and pending, and keeps working; the move is retried at the next start. Once nothing is pending, a *migration complete* marker is written, and from then on `config.toml` is never consulted for a non-internal key. The gateway-internal key stays in `config.toml`, but only the key whose fingerprint the gateway recorded in `mcp_keys.db` is accepted. The one exception is a home where `mcp_keys.db` does not exist yet (no v1.82 gateway has started there): `[mcp_keys]` is then read under the v1.81 rules until the gateway creates the store. If `mcp_keys.db` exists but cannot be read, or has an unexpected schema, every key is refused, the gateway-internal key included.

**Downgrade.** The move is one-way for keys. v1.81 cannot see `mcp_keys.db`, so after a downgrade external keys must be re-issued. Do not restore an old `config.toml` for that purpose: it would bring back keys that were deleted or disabled on v1.82.

- **Check on every save:** fixed rules first (size, control characters, a strict `CONTRACT.toml` parse, hidden or invisible content, injection patterns in the lines this change adds or in new `must_always` entries, key-like text, a persona that loses most of its text, a contract that drops or rewrites a `must_not` / `must_always` entry or raises / removes the tool-call limit; skills additionally: a leading `---` block must read the way the skill loader reads it and its `name` must be a single name, and the skill scanner's findings on the lines this change adds count, with commands, sending data out and injection patterns as high risk (decided by the actual added lines, so a second line of the same kind is still new) and bare links and mentions of a forbidden item as needs attention; high-risk content already in the file is listed as "already in this skill"; a skill changed outside the dashboard since its last save here is checked as a whole against that last saved version), then a short review of the diff by the deployment's utility model (`[runtime] utility_provider` / `utility_model`, override with `[agent_files] review_provider` / `review_model`; billed to the deployment as `agent-file-review`, never to the employee's budget). The model can only make the result stricter. Results: `pass` applies at once; `warn` needs a reason (at least 4 characters) or a request to an admin; `block` can only be sent to an admin by a non-admin, and an admin applies it only with a reason and "I understand the risk" (audited as Critical). If the review cannot finish (no utility model, timeout, an unusable answer, a quota reached) or the change was too long to show in full, the result is at least `warn` (or `block` with `[agent_files] on_analysis_failure = "block"`), a non-admin can only send it to an admin, and an admin confirms it only with "I understand the risk"; it is never a silent pass and cannot be switched off. Quotas per day: 200 per deployment, 40 per person, 60 per employee (`review_daily_limit`, `review_daily_limit_per_user`, `review_daily_limit_per_agent`), plus at most 10 checks per person per minute (`checks_per_minute`); the same change checked again within 15 minutes reuses the result. Confirming does not run the review again; a confirmation must match the same person, file, starting version and content within 15 minutes, the fixed rules are re-run at the person's current permission level (stricter now ⇒ check again), and confirming a `block` re-checks inside the file lock that the person is still an admin. A SOUL.md, IDENTITY.md, USER.md or INSTRUCTIONS.md changed outside the dashboard is checked as a whole and compared with the last approved version (reason "changed outside").
- **Saving:** under the file lock, with the hash the editor read (`base_hash`); a file changed by someone else in between is refused as a conflict. The new text takes effect from the employee's next turn; channels get a one-line notice with the next reply.
- **Versions:** kept outside the employee folder in `<home>/agent_file_history/<employee>/<file>/` (owner-only files), 20 per file by default (`[agent_files] history_keep`, 5–100). The first change also keeps what the file contained before. Restoring a version runs the same check. Removing an employee moves its history to `agent_file_history/_trash/`; a new employee with the same id starts with none.
- **Baselines:** saving SOUL.md, IDENTITY.md, USER.md or INSTRUCTIONS.md updates its approved fingerprint (INSTRUCTIONS.md has one now too, checked by the heartbeat as `_instructions_integrity_drift`). A file changed outside the system shows as changed-outside; restore the approved version or check and accept the current content (save it as it is: the whole file is checked, at least a reason or an approval request is needed, and once confirmed the file is not rewritten; the current text is kept as a version and becomes the approved baseline. Saving an unchanged file that was not changed outside is still "unchanged"). Renaming an employee updates the name inside SOUL.md / IDENTITY.md and keeps an approved SOUL approved, while a SOUL that had already changed outside stays flagged. The name must be plain text (1–64 characters, no line breaks, invisible characters or `< > [ ] { }` / backticks), and a renamed file that trips a fixed rule is left as it was (listed in `identity_files_skipped`).
- **Approval requests:** kind `agent_file_change`, decided in the dashboard by a current admin (or, when [Approve in chat apps](#security--approve-in-chat-apps-v186) is on, from a chat card by a self-confirmed Admin after a second confirmation by default), 3 days to decide (expiry counts as a denial). Channels only get a notice without buttons. The proposed text is stored in `<home>/agent_file_pending/` until the request ends. Approving applies first; if the file changed while the request waited, the request is denied and the requester has to send it again.
- **Audit:** `agent_file_changed`, `agent_file_change_refused`, `agent_file_review_failed`, `agent_file_change_requested` (hashes only, never the text).

### Change an employee's persona after creation (v1.82.0)

The persona you give at creation (the optional Persona box on the blank create form, `agents.create` field `soul_md`, or a template's SOUL.md) is only the starting text. Since v1.82.0 a supplied persona is always written or the create fails; it is never replaced by the default sentence. To change it later:

- **Dashboard:** employee page → Profile files → Persona (`SOUL.md`) → Edit → Save and check.
- **RPC:** first `agent_files.get {agent_id, file: "soul"}`, which returns the current `content` and its `hash`; then `agent_files.save {agent_id, file: "soul", content, base_hash: <that hash>}`. Only the employee's Owner and admins can save, and the AI employee itself can never change its own SOUL.md.
- **The save is reviewed, not applied blindly.** It runs the check on every save described above, and the response `status` tells you what happened: `applied` (takes effect from the employee's next turn), `unchanged`, `needs_confirmation` (send the save again with `action: "confirm"`, the `review.analysis_id` and a `reason` of at least 4 characters), `blocked` (a non-admin sends it again with `action: "request_approval"` and gets `pending_approval` with an `approval_id` that an admin decides in the dashboard; an admin confirms only with a `reason` and `acknowledge_risk: true`), `conflict` (someone saved first: `get` again and redo the edit), or `rejected` (a fixed rule refused the text; fix it).
- Every applied change is kept as a version, so `agent_files.history` / `agent_files.rollback` can restore the earlier persona.

- **Export profile:** Managers and admins can choose Export profile from the employee page menu when they can view that employee. Choose DuDuClaw, OpenClaw, Hermes, AGENTS.md or Claude Code subagent. User introduction is excluded unless explicitly checked. Download the prepared file, or each file into the same folder for OpenClaw/Hermes. Secrets, channels, capabilities, permissions, account pools and memory are never exported. See [Agent File reference](../spec/agent-file-spec.md).
- **User introduction:** saved through the same locked, versioned, reviewed writer. It is injected as a `<user_profile>` data block, explicitly not instructions, and scanned with the same input guard as persona text. Its 4,000-character limit overrides the general Markdown byte limit.

## Manage → Advanced → License: sync and AI employee seats (v1.84.0)

**Refresh.** For an Admin, **Refresh** asks the vendor for the current licence (RPC `license.sync`, Admin only) and shows the outcome under the button: updated, already up to date, the licence has been revoked, waiting for the vendor to approve the machine change, no commercial licence installed, a licence file exists on this host but cannot be read (re-import the licence or have an administrator check the file), vendor unreachable, or the sync did not finish (the last two retry automatically). Syncs are spaced at least 30 seconds apart, shared by the dashboard and the automatic checks; a press inside that window says how many seconds to wait. If the request itself fails, the page keeps showing the current licence. For Managers the button only reloads what is displayed.

**Seats.** The page shows the **AI employee limit** (a number, or **Unlimited**) and **In use** (archived employees count). A row is hidden when the value cannot be determined; the page never shows an estimated number. Anyone who can open the page (Manager or above) sees these rows.

**AI avatars.** Verified Personal avatars of active member Owners do not use employee seats (one per member); archived AI still count. `avatars_exempt` is shown separately from `seats_used`. See [AI avatars and licensed seats](user-management-and-first-login.md#ai-avatars-and-licensed-seats).

**Restart notice.** After an Admin presses **Refresh**, when the sync leaves the service on a different edition than the one it started with, an amber note says a restart is needed to apply the plan fully. AI employee seats and the expiry date apply at once.

**How changes arrive.** A licence that `duduclaw license activate`, `import`, `refresh` or `deactivate` writes on the same data directory is applied by the running service within about a minute, without a restart; `activate` and `refresh` print a line saying so. The service also asks the vendor whether the licence changed: first 2 to 5 minutes after start, then every 25 to 35 minutes, and it downloads and verifies the licence only when the vendor reports a change. A change the vendor makes (for example to the number of seats) therefore reaches the service within about half an hour. If the vendor's service does not offer this check, the service asks again once a day and keeps the plan's regular refresh interval (up to 7 days). Only the running gateway that holds the instance lock performs the check, and only when a licence is installed. When a scheduled sync finds that another sync has just failed or could not reach the vendor, it tries again in about an hour (55 to 65 minutes); when its own request fails, it waits for the regular interval. At start-up the service waits at most 45 seconds for the licence file; past that it starts as if the licence could not be read and applies it as soon as the file can be read. A licence file that cannot be parsed is read again after 15 minutes, when it changes, and on every sync. At most two licence-file operations run at once; others report that the licence file is busy.

**Licence file.** `license.json` may be a symbolic link to a regular file, for example a mounted secret. Other special files and files larger than 64 KiB are refused. When the service or the CLI saves a new licence, it replaces the link with a regular file instead of writing through it, and it keeps no backup copy of the file the link pointed to. Responses from the vendor are limited to 256 KiB.

means. It covers only credentials that let an AI employee act as a specific
person; every other setting keeps working the same way whatever the card
says.

  creates the protected key in the macOS keychain or Windows Credential

## Security → Data deletion receipts

Disconnecting a channel, Google account, database source or Remote MCP automatically prepares a memory-deletion request. A disconnect success and a completed deletion are separate results.

1. Disconnect the service in its settings. The response offers **View approval** when a batch is ready. If `[memory] forget_source` is off or its setting cannot be read, no plan is created; planning failures are also reported separately.
2. An Admin opens the inbox card and reviews the counts for each AI employee. A batch expires after seven days. A deletion scope that grows before execution needs another approval; a smaller scope can proceed.
3. After approval is saved, the gateway queues durable background work. It retries unfinished work and resumes after a restart. There is no receipt while deletion or its required follow-up is incomplete.
4. Open **System → Security → Data deletion receipts**, expand a connection and choose **Download JSON**. Refresh the list to see newly completed work. Counts distinguish deleted memories, key facts and archive copies from unattributed and retained system rows.

Google personal connections are attributed to the user whose credential was used, while the receipt groups deletions by AI employee. Old memories without a connection stamp cannot be assigned retrospectively. Conversation text, `tool_calls.jsonl`, wiki and backups are outside this deletion. Remote MCP's existing `forget` option removes the saved connection entry; the independent `forget_memories` option controls the memory request and defaults to enabled.

Non-Google OAuth revocations currently have no connection attribution and report that forgetting was skipped. Clearing the configured Google credential path does not itself revoke a separately stored OAuth authorization; disconnect that authorization through its own control.

Connection stamps keep their origin and role. Corroboration alone never grants deletion ownership. A memory stays if another connected source also supplied it; plans, the Admin card and receipts report this per employee as `retained_shared`. Deletion requires every owning connector to have been disconnected and no independent live origin. The second disconnect can therefore select a previously shared memory. Unknown ownership (including old stamps whose role cannot be recovered) is retained and counted as unattributed. Derived memories undergo the same ownership check. Connection state is checked again before planning and applying, and reconnecting through the platform invalidates old disconnect evidence before publishing the connection.

Approval binds the sorted identifiers of orphan entity embeddings, not just their count; swapping one entity for another requires a new approval. Unfinished jobs use a durable attempt count and due time, with 60/120/240/480-second backoff. Due jobs are selected fairly. After five consecutive failures or interrupted attempts, a job is quarantined. The Admin can see a content-free failure reason under **Data deletion receipts** and choose **Retry**; retry retains the existing approval and rechecks scope, requiring a new approval if it grows.

## MFA enforcement

```toml
[auth]
mfa_enforced = true
```

New team installs enforce MFA by default. Existing installs keep their current policy, including legacy stores without MFA policy records. An Admin enables or disables enforcement with the dashboard toggle under **Users → Two-factor login management**. On a new team install, after password login, the first Admin can complete first enrollment through mailbox verification when SMTP or licensed relay is available, or finish authenticator / passkey enrollment from the dashboard with **First administrator setup**, which **always needs a one-time setup code**, wherever the dashboard is opened. Get the code on the host: open a terminal on the computer that runs DuDuClaw and run `duduclaw ops users mfa-setup-code` (Docker: run it inside the container, for example `docker exec -it <container> duduclaw ops users mfa-setup-code`). The command prints the code only to an interactive terminal; it refuses when its output is redirected to a file or pipe, and inside AI sessions. The gateway never prints or logs the code: at start it only logs one line saying that first administrator setup is waiting and which command to run, so the code never reaches journald or `docker logs`. The code is valid for 30 minutes and works once; a new code replaces the old one. No enrollment code from another Admin is needed. There is no "this computer" shortcut: a reverse proxy on the same host makes every connection look local, so the peer address proves nothing. This first-time setup is offered only to the first (bootstrap-owner) Admin, only while enforcement is on and no Administrator has any second factor, and **only once per installation**: as soon as an Administrator has a second factor it closes for good (any outstanding setup code is void), and removing that factor, demoting, suspending or deleting Administrators later does not open it again; the host command then refuses to issue codes. After that, recover an Administrator who lost their second factor with `duduclaw ops users mfa-reset <email>` on the host. If none of these works, a host operator can still issue an enrollment code with `duduclaw ops users mfa-enrollment-code <email> <challenge_ref>`. For existing installs with enforcement off, check `mfa.overview`, channel delivery and host recovery before enabling. Both dashboard config writers require a current active Admin. Enrollment and later credential changes invalidate older JWTs through a per-user epoch; enforcement alone lets existing access tokens expire naturally and refuses unenrolled refresh. Legacy shared-token WebSocket login is refused when enforced.

Configuration is an in-memory snapshot, loaded at boot and after dashboard writes; external file changes reload every 30 seconds. A failed reload warns and preserves the last good value; every edition with no valid snapshot fails closed; an existing unreadable or corrupt policy store also refuses boot. A missing `[auth]` table or key retains the durable policy; new team provisioning explicitly records true in both config and the identity store. Enforcement follows the stored policy in every edition, including license expiry, license fallback and an explicit Personal override; only an Admin deliberately turning it off disables it. Fresh Personal installs without a policy store stay unenforced. Local auto-login cannot bypass enforced MFA. Host recovery works under Personal too. See [Security defense](../features/05-security-defense.md) for proof fields, session binding and `duduclaw ops users mfa-reset` / `mfa-enrollment-code` host recovery. Key rotation is out of scope.

Before enabling, review channel binding times in `mfa.overview`; only verified bindings predating enforcement qualify as enrollment proof. A password holder who planted a binding before enforcement cannot be detected. Read the returned 12-character `challenge_ref` to another Admin, who issues a code for that pending challenge (`users.mfa_enrollment_code {user_id,challenge_ref}` or host `duduclaw ops users mfa-enrollment-code <email> <challenge_ref>`). Failed reloads are visible in `mfa.overview.policy` and `system.status.mfa_policy`; a last-good false value remains false. Both config writers re-check Admin under the write lock. CLI imports also check the live database policy before moving data; a team import that replaces users.db or its SQLite sidecar files must retain an explicit, unchanged mfa_enforced key, so the archived database cannot silently change enforcement.

CLI home imports validate and unpack one private snapshot of the compressed archive (maximum 8 GiB). Both phases enforce at most 200,000 tar entries, 2 GiB per entry and 8 GiB total uncompressed content, using the same defaults as backup restore. Raw headers are checked before tar decodes GNU/PAX metadata; each metadata entry is limited to 1 MiB, and effective sizes include PAX overrides. Third-party PAX archives whose size overrides prevent raw-header traversal may be refused; GNU long paths produced by export remain supported. Paths are compared using NFC normalization, then uppercase and lowercase, with trailing dots and spaces removed from each component. NFKC is not used: fullwidth `ｃｏｎｆｉｇ.toml` does not alias `config.toml`. Protected-file aliases (such as `Config.toml.`) and duplicate destinations are rejected on every platform. Only Windows refuses colons (including NTFS alternate streams), DOS reserved names and possible generated 8.3 names such as `CONFIG~1.TOM`; Unix keeps legal names such as `aux` and `notes/2026-11-04T07:00`. Every platform refuses backslashes and non-normal path components. All refusal checks and required durable strict-config publication precede moving existing agents with `--force`; a publication failure leaves `agents/` in place. When replacing the identity database or SQLite sidecars while enforcement is active, the archived configuration is skipped even when its text is identical. Windows uses a write-through replacement.

Dashboard staging accepts only one pending restore. Restart the gateway to apply it before staging another; there is no restore-cancel RPC. Each request extracts and validates in a fresh random directory while holding the per-home restore lock, then syncs every regular file and directory before publishing by rename, syncs the home directory, durably writes the pending marker and syncs home again. Only then is the upload deleted. Windows syncs files only because std does not support directory fsync. Failure removes only that request’s temporary data. If marker publication fails after the directory was published, the data is retained and further overwrites are refused with an administrator-check message.

Every boot attempts singleton ownership exactly once, early, even without a pending marker. A failed early attempt is never retried in that process, including when a marker appears later and the other gateway exits. Pending backup restores require exclusive ownership of the gateway data directory before reading the current policy or changing staged files. If another gateway is running on that directory, the restore is deferred with its pending marker and staged data unchanged. The gateway continues booting in its existing degraded mode, with workflow reconciliation, dispatch and sweep disabled for that process’s entire lifetime. It does not acquire the lock later if the other gateway exits; restart it to apply the pending restore. Restore keeps the current MFA enforcement policy and the live lock directory; archived lock files are not restored. This prevents an Admin toggle from completing between the policy check and the swap.

### Email codes, passkeys and keep me signed in (since v1.80.0)

In **Settings → Account**, you can keep the existing authenticator app and add **Email verification code** or one or more named **Passkeys**. Enter your current password before adding or removing a method. Email setup sends a six-digit code to the account email; the factor is activated only after successful verification. The system prefers the existing `[channels.email]` SMTP sender (`smtp_host`, `from_addr` and, when required, SMTP credentials). Without SMTP, DuDuClaw can relay verification codes for a valid paid license bound to this machine, excluding NFR licenses, when relay is enabled below. Factor changes are audited; security-change notices still use configured SMTP only.

#### Email verification relay configuration

Set this in the gateway's `config.toml`:

```toml
[mfa]
email_relay = true
```

`email_relay` defaults to `true`. Setting it to `false` disables licensed relay only; it does not disable your SMTP sender or MFA enforcement. OpenSource, Hobby trial, Partner, NFR, unbound OEM, invalid and expired licenses cannot use relay. Partner licenses remain excluded even when a legacy license records `nfr = false`. Configure SMTP for these installations. Relay uses the official host compiled into the gateway, independently of license-refresh settings. `DUDUCLAW_CONTROL_URL`, the license's `control_url`, configuration and environment overrides cannot change the relay destination. Its dedicated transport uses HTTPS on port 443, pins public DNS results, refuses proxies and redirects, times out after 10 seconds and caps responses at 4 KiB.

The first eligible send enrolls the installation with a challenge–response exchange: the gateway requests a single-use challenge for its subscription, then sends the signed license, machine fingerprint, challenge and issue time with an Ed25519 signature from the installation key (see below). The server derives the installation ID from the approved public key. When enrollment replaces an existing relay credential, the request also proves possession of that credential with an HMAC over the same signed message. Response bodies are held in fixed-capacity buffers that are cleared on release; copies made inside the HTTP and TLS libraries cannot be cleared. The returned relay credential is saved in `<home>/state/mfa-relay.json` with owner-only access: Unix uses mode 0600, and macOS also rejects extended ACLs; Windows uses a private DACL and pinned handles. Writes use pinned directory handles, refuse symbolic links and publish by atomic rename. Subsequent sends contain only the recipient, code and locale; HMAC request signatures bind the method, path, timestamp, nonce and exact body. They do not send the license again. All enrollment attempts, including failed first enrollments, share a persisted limit of one attempt per hour; restarting the gateway does not reset it. On `403 relay_not_allowed`, a send can re-enroll and retry at most once, if that hourly limit permits it. Each subscription keeps one active relay credential, and only the installation whose key the account owner approved can enroll.

#### Installation key and license-console approval

Each installation has its own Ed25519 key in `<home>/state/installation.key` (a 32-byte seed with the same owner-only protections as the relay credential). It is separate from `identity.key`. The key is created only when the file does not exist: when you activate a license from the CLI, when the license is refreshed (automatically by the gateway or with `duduclaw license refresh`), or by `duduclaw license installation-key`. An unreadable, malformed or unsafe file (wrong owner or permissions, symbolic link, extra hard link, extended ACL) is reported and never replaced; the relay stays unavailable until you fix or restore it. AI employees cannot read anything under `state/` through the file guard. Include the key in home-directory backups.

License refresh and rebind requests send the public key as `installation_pubkey`. The relay is available only after the license carries the same signed public key. A key the license service has not seen creates a pending request in the license console and the account owner is notified. Paid features keep working while the request is pending, and SMTP can still deliver codes; only the relay waits. Every existing installation must be approved once.

Before approving, compare fingerprints. On the gateway host, run:

```bash
duduclaw license installation-key
```

Line 1 is the 16-character fingerprint, for example `1a2b-3c4d-5e6f-7a8b`: the first 16 hexadecimal characters of SHA-256 over the raw 32-byte public key, in groups of four. Details (public key, approval state) go to stderr. While approval is pending, administrators also see the fingerprint under the Email explanation in **Settings → Account**. Approve only when the console shows the same fingerprint. A request you do not recognize means someone else has a copy of the license file; reject it.

If the key is lost (for example after moving to a new machine without the home directory), the next refresh generates a new key and requests approval again. The signed in account owner can pre-authorize one fingerprint in the console for 24 hours so that refresh is approved automatically. If only the relay credential is lost, use **Reset relay credential** in the console; the next enrollment counts as the first one.

When the relay is waiting, the Email explanation says either that the installation awaits approval (no key in the license yet) or that this installation's key differs from the approved key (for example after a restore to another machine).

Relay uses a fixed verification-code template, without custom subjects or body text. Codes and relay secrets are never logged. Gateway recipient logs use a domain-separated HMAC with the existing per-home audit key, or the fixed value `unavailable` when that key cannot be loaded. The control plane applies additional delivery limits. If delivery is too frequent, wait before retrying; for other delivery failures, retry later or contact an administrator. A code already issued locally can still be verified if delivery later becomes unavailable. Local eligibility does not establish delivery; real relay delivery still needs acceptance testing.

When Email is disabled, the dashboard explains that neither a configured sender nor eligible licensed relay is available, that relay is disabled, that the license type does not include relay (NFR or unbound OEM), or that the installation key awaits approval in the license console, and tells an administrator to configure SMTP in the meantime. Disabled passkeys distinguish an insecure connection from an unsupported browser. For an `http://` LAN address, use the configured HTTPS dashboard URL or localhost on the gateway host; for an unsupported browser, switch to one that supports passkeys.

Each option needs the following:

- **Authenticator app**: an app that generates six-digit TOTP codes. Required enrollment also needs the displayed independent channel/Admin proof.
- **Email verification code**: access to the account mailbox and a configured SMTP sender. An Admin opens **Settings → Advanced → Advanced config editor** (`/app/system/settings/advanced#configRaw`) and configures `[channels.email]` (`smtp_host`, `from_addr` and any required SMTP credentials). Without it, the disabled option explains where to configure delivery.
- **Passkey**: a WebAuthn-capable browser and HTTPS, or HTTP on localhost. An `http://` LAN address is not a secure context; the disabled option directs you to HTTPS. An unsupported browser receives a separate explanation. The server must also have its passkey origin/RP configuration, as described below.

The explanations appear at login/enrollment and in account settings. Email availability reports only `no_smtp` when the sender is missing; it does not check whether mail was delivered.

After your password, choose an enrolled verification method; the last successful method is selected by default. Email codes expire in 10 minutes, are single-use and allow five attempts for a challenge. Resending is limited to once per minute and five times per account per hour. Passkeys use your device's screen lock, biometric verification or a security key. Set `[dashboard] public_url` to the public dashboard URL and open that exact HTTPS origin; HTTP only works on localhost. Each passkey has a name and can be removed separately. Keep another method available if you lose access to your device. A first passkey enrollment does not issue recovery codes; existing authenticator recovery codes remain valid. First Email enrollment shows recovery codes once, and you must acknowledge saving them before continuing.

Enforcement accepts any enrolled method and refuses removing the last one. Existing authenticator enrollments and recovery codes do not need migration by the user. A required first Email enrollment proves control of the account mailbox; authenticator and passkey enrollment retain the independent channel/Admin proof requirement. Channel-code-first enrollment also requires the current password. An Admin reset clears every factor and remembered device. Resetting a **staff** account can still be confirmed with the acting Admin's current password or a fresh authenticator/recovery code. Resetting **another Administrator** (including one demoted in the last 7 days) needs the acting Admin's own second factor: a fresh authenticator code or unused recovery code; the password alone is refused. The authenticator check does not accept a passkey, and a first passkey enrollment issues no recovery codes, so an Admin without an authenticator app (passkey-only or Email-only) confirms with **Password and a code sent to your email**: the current password, then a six-digit code mailed to the Admin's own address (valid 5 minutes, single use, bound to that target, same send limits as Email sign-in codes; needs SMTP or the licensed relay). The acting Admin must also have been an eligible Administrator (Admin with a second factor) continuously for the last 7 days according to the Admin eligibility log; a newer Admin, one whose own factor was reset in that window, and every Admin during the first 7 days of a new install are refused. **During the first 7 days of a fresh installation no Administrator can reset another Administrator's two-factor login from the dashboard**; only the host command `duduclaw ops users mfa-reset <email>` can. Later, when the only other Administrator is newer than 7 days, use the same host recovery. These rules are enforced by the gateway for every caller; unreadable factor state or eligibility log refuses. Every attempt, allowed or refused (including the earliest refusals: account data or sign-in settings unreadable, no dashboard session, too many attempts), leaves exactly one record with an attempt ID, actor, target, outcome and reason, never a password or code. The record is first written to an audit outbox in `users.db` (a completed reset and its record are committed together), then delivered to the security audit log and removed only once delivered; if the security audit log cannot be written, the record waits and is delivered after the next reset attempt or at gateway start (a redelivered record carries the same attempt ID). If `users.db` itself is unavailable, the refusal goes straight to the security audit log. The outbox holds at most 1,000 records; when full, new reset attempts are refused.

The login checkbox **Keep me signed in** is unchecked by default. Checking it uses a rotating browser cookie with a default sliding lifetime of 180 days: each successful refresh resets expiry to that use plus the current number of days. In **Security → Keep me signed in**, an Admin can save an integer from 1 to 365 (default 180). The policy is stored durably in `users.db`; missing or invalid reads fall back to 180, never unlimited. Changes leave existing expiry dates intact until the next successful renewal, which sets expiry to last use plus the new value, including when shortened. The prototype `[auth] remember_days` setting is no longer read. Leaving the box unchecked keeps the existing session behavior. **Signed-in devices** in account settings shows remembered devices, their creation and last-use dates and the recorded IP, with individual revocation and **Sign out everywhere**. Password changes, factor changes/reset, account status or role changes and deletion revoke remembered sessions. Signing out revokes the current device.

An Admin can open **Users → Edit user** and confirm **Logout from all devices** to revoke all ordinary and remembered sessions for that account. Disabling or removing the person also revokes sessions. Existing access tokens are rejected and open sockets stop at their existing live revocation checks (including the next heartbeat); there is no wait for the 180-day expiry. The Admin-only RPCs `sessions.policy`, `sessions.policy_update` and `users.revoke_sessions` recheck current authority; mutations record actor, target and outcome without credentials in the auth audit log.

| Control | Storage / RPC | Takes effect |
|---|---|---|
| Security → Keep signed in for (days), Admin only | `users.db` → `remembered_policy_state.days`; `sessions.policy` / `sessions.policy_update` | No restart. New sign-ins and the next successful renewal; 1–365, default 180. |
| Users → Edit user → Logout from all devices, Admin only | `users.revoke_sessions`; credential epoch and remembered-family revocation, auth audit | Revocation commits immediately; open sockets enforce it at their existing checks. Confirm before applying. Self-sign-out uses the existing HTTP account endpoint so the success response survives socket revocation. |

Cookie-authenticated session requests require `X-DuDuClaw-CSRF: 1` and an exact Origin match, including scheme and effective port. Built-in HTTP loopback origins use the gateway's listening port; reverse proxies must list their complete `https://host[:port]` Origin in `[gateway] allowed_origins` (or `DUDUCLAW_ALLOWED_ORIGINS`). Bare host entries are insufficient for these endpoints. Refresh and logout reject cross-port pages and ordinary HTML forms before changing a session.

Refresh uses an authenticated family generation, with one current token hash per family; authentic older generations revoke the family, while forged generations cannot revoke it. The separate owner-only `users.remember-key` signing key must be backed up and restored together with `users.db`; a missing key with generation sessions or an invalid key fails closed. Prototype sessions created before generation support are revoked on migration. Each account may retain at most 20 active devices and 100 total family records, including revoked devices. At the retained-record limit, use ordinary sign-in until records expire. Records are pruned on the next successful remembered sign-in after their most recently renewed expiry plus seven days. Account-authenticated dashboard and WebChat sockets have a maximum 24-hour lifetime and reconnect to authenticate again; existing shorter MFA expiry checks still apply. This bound prevents old sockets from surviving the revocation-retention window.


The persistent credential is not available to JavaScript or stored in localStorage: the cookie is HttpOnly, SameSite=Strict, scoped to `/api/session` and Secure on HTTPS. The server stores only hashes, rotates on use and revokes a family on reuse of an older credential. Cookie endpoints check Origin; dashboard WebSocket upgrades also validate Origin.

Acceptance remains pending for real SMTP and licensed-relay delivery, browser/platform passkey registration and login, cross-platform Rust builds, dependency audit and full gateway integration tests. UI code and written tests alone do not establish those results.

For existing installs that still have it off, verify enrollment, channel delivery and host recovery before an Admin enables it. Personal supports voluntary enrollment; local auto-login remains unchanged.

The calling connection now receives new tokens with the successful enrollment/disable response and is rebound before the normal send gate runs. HTTP enrollment also issues its tokens before the enrollment transaction commits. Release acceptance still requires live browser/WebSocket verification, including keeping codes visible beyond a heartbeat and retiring another session; in-process handler and frontend tests do not establish that acceptance.

## Voice synthesis

`auto` tries installed Piper → installed Kokoro → MiniMax → OpenAI → Azure, subject to product policy. Explicit providers use only that provider; `off` disables synthesis. `duduclaw doctor` lists available providers without making synthesis requests.

Download Kokoro from **Settings → Voice** (about 134 MB, Apache-2.0). Assets and the shared ONNX Runtime are verified during installation; an interrupted or cancelled download starts over on the next attempt. Weights are not bundled in the binary. The model lives under `<home>/models/kokoro-zh/`. Default voice: `zf_001`; alternatives: `zm_010` and `af_maple` for pure English. Chinese speech has a mainland accent; polyphonic words may be mispronounced. Traditional characters and numbers are normalized, but the pronunciation rules do not cover every word. Input is capped at 2,000 characters and split into chunks of at most 500 tokens, joined with 150 ms silence. Kokoro produces 24 kHz WAV; Telegram receives it as `reply.wav` through `sendAudio`.

Azure sends the text to Microsoft. Set `AZURE_SPEECH_KEY` and `AZURE_SPEECH_REGION` in the gateway environment. Default Chinese voice: `zh-TW-HsiaoChenNeural`; default English voice: `en-US-AriaNeural`. Azure returns MP3. `tts_voice` can select a supported provider voice.

Admin RPCs: `voice.kokoro_status` reports installation, missing files, size, runtime readiness, progress and errors; `voice.kokoro_install` starts an idempotent background install. The Voice download card polls the status and displays install errors.

## Send another WebChat message during a reply

You can keep typing and send another message while an AI staff member replies. In the same conversation, supplementary messages show “Queued — supplements will be handled together after this reply”. When the running reply ends, the waiting supplements are dispatched together in arrival order as one following turn. Each original message keeps its own history row and client message ID; no text is injected into the reply already in progress. A batch contains at most **32,000 characters**, including `\n\n---\n` separators, and at most the existing eight attachments. Messages that do not fit remain whole for the next batch. A single message over 32,000 characters runs alone without truncation. Commands keep their own turn, and a different login session or employee starts a separate batch. Public widgets and `odoolivechat:` sessions retain their previous dispatch behaviour. The queued label clears when dispatch begins. `turn_merged` identifies supplements claimed by the leading message; each follower also receives a terminal `turn_consumed` with `outcome: "done" | "failed" | "cancelled"` on its original connection, so another tab can settle its waiting state. An `@` call routed to another staff member can use a separate processing lane.

Use **Cancel queued message** on a waiting message to cancel that message, or **Stop current reply** beside Send to stop the active reply. The server acknowledgement clears the waiting indicator and distinguishes a cancelled waiting message from a stopped reply. Once supplements have been claimed by one dispatch, they are stopped together through the leading turn; they cannot be cancelled individually. Existing attachment support is unchanged.

By default, the server allows up to three in-flight messages per user, including queued messages. If the limit is reached, the message shows a localized explanation with the applicable limit and separate running/queued counts, and retains its text. Each refusal is recorded in the gateway log. Use **Copy to composer** to edit and send it again after a reply finishes.

## Invite a teammate

An Admin can select **Send invitation email** under **Manage → Members → Add member**, review the email preview, and create the account. The invited account has no usable password. For an existing active account with no password, use **Resend invitation**. The list shows pending and expired invitations.

Set `[gateway] public_url = "https://ai.example.com"` in `config.toml` to the dashboard's externally reachable base URL. If absent, the dashboard supplies its own browser origin as the Admin's `public_url` parameter. The gateway never builds links from HTTP Host or Origin headers. A missing URL returns `public_url_required`; an invalid configured URL is refused. Every invitation public URL requires HTTPS, including `localhost`, `127.0.0.1` and `::1`.

Invitation email uses the existing SMTP configuration under `[channels.email]`, including encrypted SMTP credentials. This repository has no Resend or SendGrid transport. The message contains a single-use link valid for seven days. If sending is unavailable or fails, the Admin sees a copyable link once; successful delivery does not return the link. Close the result to remove the displayed link. Reissuing revokes earlier unused links and retains their audit rows.

The recipient opens `/invite#<token>`, sets and confirms a password (at least eight characters, at most 1,024 UTF-8 bytes), then signs in normally. The page does not sign the recipient in; existing MFA enrollment and verification requirements still apply. Expired, used, revoked and unknown links all show the same invalid-link result. Disabled accounts cannot redeem invitations. Changing the account email or password, or disabling it, revokes unused invitations.

Employee accounts see an **A few steps left** connections card on Home when personal connections remain incomplete. It shares its title with the first-login onboarding card but tracks only personal connections. Each item links to **My connections**. The card hides when all connections are complete or loading fails, and can be dismissed in that browser. Invitation creation, delivery outcome, use and revocation are recorded without tokens or links. The token is read from the URL fragment and immediately removed from browser history; it remains only in component state. The public `/invite` page bypasses authentication and FirstRunGate. Only `POST /api/invite/check` with `{token}` (returning `{valid,email_masked?}`) and `POST /api/invite/redeem` with `{token,password}` are supported; token-bearing API paths are removed. Do not log request bodies. Each TCP peer and token SHA-256 prefix (16 hex characters) shares 10 attempts per 15 minutes across both endpoints. There is no peer-wide limit, so users behind a reverse proxy do not share an allowance. The in-memory table holds at most 10,000 buckets; at capacity, an expired bucket is evicted first, or the oldest insertion if none has expired. Ordered indexes avoid whole-table scans. Forwarded headers are ignored.

## Users → Verify identity: channel identities (v1.82)

**Verify identity** on a person's row (Admin only) ties an account on a messaging app to that dashboard account. Once bound, messages from that account are treated as coming from this person: which AI employees they may call with `@`, and who may use a company delegate or the person's own Google account through an employee (`[google] requesters`).

| Channel | Bindable | Receives login / two-factor codes |
|---|---|---|
| Telegram, LINE, Discord, Slack | yes | yes |
| Google Chat (v1.82) | yes | **no** |

- **Google Chat** — enter the Chat user id as `users/` followed by digits, or just the digits; it is stored as `users/<digits>`. Anything else (an e-mail address, `users/app`) is refused. Your Google Workspace administrator can usually see the number at the end of the address when opening the person's account in the Admin console.
- **By default only manual bindings count.** A Google Chat sender is recognised as a colleague only when an administrator has bound their Chat user id here.
- **Optional: recognise automatically from their own Google account (off by default, unverified).** An administrator can turn on **Manage → Integrations → Google → Recognise Google Chat senders by their connected Google account** (`config.toml [google] chat_identity_from_account = true`; default `false`; a missing setting counts as off, while an unreadable `config.toml` or a non-boolean value is treated as an error and no Google Chat sender is recognised until it is fixed). When on, a person who connected their Google account under **My connections** is recognised in Google Chat without a manual binding: the system compares the Chat sender's id with the id of the Google account that person connected and treats a match as that person. **This has not yet been verified against a real Google Workspace**: if Google's Chat user id and the sign-in account id turn out to be different kinds of number, an accidental match could recognise the wrong person, which is why it is off by default. Leave it off unless you have confirmed in your own Workspace that the two ids match. While on, the automatic identity appears on their row with a link mark and cannot be removed here: it ends when they disconnect Google, when their account is suspended, offboarded or deleted, or when the setting is turned off. Changing the setting is recorded in the security audit log as `config_changed`.
- **One Chat user, one person** — binding a Chat id that is already bound to someone else is refused with an explanation; while automatic recognition is on, so is binding a Chat id that another person's own Google account already stands for. If the manual binding and someone's own Google account ever name different people, neither is used and the sender is treated as unknown. If the record of linked Google accounts cannot be read while automatic recognition is on, Google Chat senders are treated as unknown.
- **Inactive accounts cannot be bound** — binding any channel identity to a suspended, offboarded or deleted account is refused (HTTP 409, or 404 for an account that does not exist).
- **A Google Chat identity is for recognition only.** Notifications, approval cards, digests and other messages DuDuClaw sends on its own initiative are never addressed to a Google Chat user id; they still go to the person's Telegram / LINE / Discord / Slack (and other DM) links. A person with only a Google Chat binding is recognised when they write in Google Chat but receives no proactive messages there. Messages from another Chat app (sender type other than a person) are ignored.
- **Remove** — hover a Google Chat identity and press ×. Only administrator-made Google Chat bindings can be removed from this page; other channels keep their existing behaviour.
- Binding and removing a Google Chat identity are written to the security audit log (`googlechat_identity_bound`, `googlechat_identity_unbound`) as well as the account audit log.

APIs (Admin JWT): `POST /api/channel-identity/bind {user_id, channel, channel_user_id}`, `POST /api/channel-identity/unbind {user_id, channel: "googlechat", channel_user_id}`, `GET /api/channel-identity/list?user_id=` (a Google-account-derived entry carries `"source": "google_account"`, and is listed only while automatic recognition is on). The setting is read by `google.credentials.get` (`chat_identity_from_account`) and written, Admin only, by `google.integration.set {chat_identity_from_account: bool}`. No self-service path creates a Google Chat binding.

## Run step budgets

The step budget is configured separately: global `[runtime] default_max_turns` defaults to **50**, and `max_turns_limit` defaults to **200** (integer **1–10000**). An employee may set `[runtime] max_turns` from **1** up to that ceiling; leaving it unset uses the global default. Zero never means unlimited. Unexpected read, parse or type errors cap the resolved budget at 50 (10 for OpenAI-compatible tool loops), preserving lower valid limits, with warnings deduplicated per employee, configured value and applied cap (at most 256 distinct entries per process); missing files or keys use defaults; values above the ceiling are clamped during execution and rejected on dashboard save. Raising an employee's limit requires an administrator; owners may lower it, and clearing it requires an administrator if the inherited default raises the effective budget. Changing either global key also requires an administrator and is audited through the existing config commit path. The dashboard places these fields beside the time limits. More steps can consume more quota and extend runs. Claude chat, scheduled or dispatched employee work and terminal chat use this budget. Internal helpers such as evolution, summarisation and evaluation retain a maximum of 50 steps, preserving lower configured limits. Protected Claude gateway calls remain capped at 50 until native Linux protected mode supports it. OpenAI-compatible tool loops use an explicit employee `max_turns`, otherwise retain 10; exhaustion returns a distinct max-turns error. Headless Claude/Grok runs disable interactive question tools. Claude receives a system-prompt reminder to summarise progress and stop near its step budget. Proactive checks retain their separate `max_turns`, accepted from **1 to 64**.

Web chat uses the target employee’s effective timeout, bounded by global `max_timeout_secs`, plus 30 seconds for delivery (1830 seconds for the default 1800-second employee). Goal task `timeout_secs` ranges from **30 seconds** to `min(max_timeout_secs, 3600)`; the goal limit stays at one hour even if the global maximum is higher.

## Event-silence limits and continuation

The global `[runtime] default_idle_timeout_secs` defaults to **900 seconds**. An employee may override it with `[runtime] idle_timeout_secs`; absent means inherit, **0 disables**, and other values must be **60..=max_timeout_secs**. With an omitted global value, a lower global maximum also narrows the default. Read or parse failures use the built-in 900 seconds. Raising or disabling an employee limit, including clearing it to a larger or disabled global default, requires administrator authority; lowering does not. The dashboard places both fields next to the execution time limits, in the employee editor and global run limits.

Claude chat and background runs, Codex JSONL runs, and OpenAI-compatible SSE responses stop when no event arrives within that window. Any parsed event counts, including tool events; the periodic 90-second keep-alive notice does not. The last unfinished tool is named when known. Grok and non-streaming OpenAI-compatible requests/tool loops retain their total timeout because these paths do not expose a live event stream here.

A step limit (`max_turns`), total timeout (`timeout_total`), or event-silence timeout (`timeout_no_progress`) ends the current turn without marking an account unhealthy, changing accounts, or retrying another model/runtime. A timeout reports that **no final answer was produced before the time limit**, even when tools ran. For signed-in channel users, captured assistant text is delivered before the notice and saved as an assistant turn; reply “continue” to resume with that context. Claude step-limit notices include the applied step count. Public visitors receive only the visitor-safe generic message and reference number, with no partial text, counts, reason code, or operator hints.

Failure notices end with a stable lowercase reason code and the first eight characters of the turn reference. The audit record retains `reason_code` and the full `reference_id`; background results use the dispatch run reference. Goal-loop work limits pause with `max_turns`, `timeout_total`, or `timeout_no_progress`, without accumulating infrastructure dispatch failures.

## Knowledge self-add and Owner approvals

In **System → Security**, administrators can enable **Allow owners to enable AI self-add** (`[knowledge] owner_self_add`, default `false`). This does not enable automatic imports by itself. The actual collection Owner must enable **Let my AI add without approval** in the collection's Settings tab; the toggle is hidden while the master switch is off or the viewer is not an Owner.

During the verified Owner's own turn, their assigned AI can add to its own opted-in collection without approval, regardless of content source: pasted text, URLs, current or earlier attachments, tool output, or an AI-written summary. Text must be nonempty; there is no eight-character minimum. System runs, delegated work and other members' turns do not qualify.

Each new automatic import durably queues one Owner notification containing only the title and source reference, without document content or preview. Delivery retries to the Owner's verified DM; repeated submissions of the same source do not create another notification. Without a reachable verified DM, the notice remains pending.

Known risk: enabling this option accepts a medium risk that content fetched during the Owner's turn, such as a web page, can steer the AI into adding material without an approval card. Owners can turn the collection switch off.

Only a verified request from that Owner to their assigned avatar AI qualifies, with exactly those two principals in the collection ACL. The import transaction rechecks authorization and the limit of 10 automatic imports per collection per rolling hour. All other cases require approval. Turn identity is supplied by the gateway; callers cannot override it in tool arguments.

Pending requests send a decision card with up to 300 escaped preview characters only to the Owner's verified DMs. Reply `確認 <full request UUID>` or `取消 <full request UUID>`. Editors use the dashboard. `[approval] forbid_self_approval` applies on both surfaces. Owner/Editor notifications are deduplicated and contain no preview outside the Owner card. Google Chat bound decisions require JWT-verified HTTP one-to-one DMs; Pub/Sub is not eligible. See [Document knowledge base](../features/63-knowledge-base.md).
