# ダッシュボード設定の対応表（v1.86.0）

## 部門権限とメイン利用者の設定（エンタープライズ、v1.86.0）

| 場所 | 操作と現在の対応状況 |
|---|---|
| メンバー（`/manage/users`）→ マネージャー行 → 部門管理権限 | スケジュール、自動化ルール、スキル、使用量、外部送信審査の５種類。追加には確認が必要で、取り消しても既存スケジュールは継続します。 |
| メイン AI スタッフ編集 → 利用できる人 | 初期状態で空の会話・通常業務の利用者リストを管理します。隔離実行する保護モードだけで有効で、それ以外ではこの入口は管理者専用です。 |
| 自動化（`/routines`） | 権限を持つマネージャーは部門ごとの定期業務、リマインダー、予約依頼を管理し、プロンプトのみの定期業務を作成できます。「部門の自動化ルール」のトリガーはタスク作成・更新・状態変更だけです。メンバーには読み取り専用の「自分の AI スタッフに作用するルール」があり、スケジュールには「作成者は権限を失っています」を表示できます。 Admin の組織同期が必要なスタッフ数を通知に表示します。 |
| スキル | 権限を持つ Manager は有効化、無効化、削除、復元とスタッフ向けのインストール申請ができます。インストールは Admin の承認が必要です。 |
| 予算／請求 → 部門使用量 | 部門と７日・３０日・９０日を選び、スタッフ別使用量、合計、最近の記録を閲覧できます。この権限で予算は変更できません。 |

権限の追加・拡大やメイン利用者の追加前に、リスク説明を読み「理解しました」にチェックします。変更は監査記録に残ります。部門権限はダッシュボードへのログイン中だけ有効で、個人 API キーやチャットアプリには適用されません。有効な Manager でなくなると自動失効します。メイン利用者リストでは、Admin との会話を含む記憶を質問できる可能性を案内します。個人 API キーはメインスタッフを利用できません。メインスタッフの予約、スタッフ作成、設定変更は Admin 専用です。

詳しい権限、ルールの実行制限、取り消し後の既存業務は[部門マネージャー](../../features/ja-JP/79-department-managers.md)を参照してください。全社の分析と請求の集計は、引き続きすべての Manager に表示されます。

`agents.main_access.get {}`／`agents.main_access.set {user_ids, expected_hash, acknowledged?}` は `users[]` の各項目に `granted_by_name` と `granted_at` を返し、許可した人と日時を表示できます。名前を取得できない場合は `null` です。

Get と成功した set の応答にはトップレベルの文字列 `hash` も含まれます。Set の必須項目 `expected_hash` には、管理者が表示した get の `hash` を渡します。これは `users.db` の `main_agent_users` 行を `user_id` 順に並べ、`[user_id, granted_by, granted_at]` タプル配列としてコンパクト JSON にした SHA-256 の小文字16進ダイジェストです。表示と hash は同じ読み取りスナップショット、比較と置換は同じ IMMEDIATE 書き込みトランザクションで処理します。欠落、文字列以外、古い hash は保存を拒否し、リストを変更しません。競合時は再読み込みして内容を確認してください。

```javascript
const snapshot = await rpc('agents.main_access.get', {});
await rpc('agents.main_access.set', {
  user_ids: selectedUserIds, acknowledged: true, expected_hash: snapshot.hash,
});
```

自動化権限を持つ部門管理者は `autopilot.template_fields {trigger_event}` を利用できます。対象は `task_created`、`task_updated`、`task_status_changed` のみで、`sequence` は指定できません。`autopilot.runs.list {rule_id, limit?}` は自動化権限のある部門のルールに限定されます。`autopilot.template_fields` は `{fields:[...]}`、`autopilot.runs.list` は `{runs:[...]}` を返します。`limit` は既定 20、範囲 1～100 です。`autopilot.runs.cancel` は管理者専用のままです。管理者または当該部門の権限を持つ部門管理者は `autopilot.notify_destinations {owner_department}` を呼び出せます。応答は `{destinations:[{channel, chat_id, kind, agent_id, label}]}` で、`kind` は `self` または `agent`、`agent_id` は `null` も返します。呼び出した人が作成する部門ルールから通知できる宛先だけを返します。表示には `label` を使います。`autopilot.list` と `autopilot.affecting_me` のルールには `creator_access_lost`（`true`／`false`／判定できない場合の `null`）が加わります。表示専用で、認可の判断には使いません。

## スキルのアーカイブ復元

未使用期間によるスキルの stale 化と自動アーカイブは削除されました。`[skill_curator]` は読み取れますが全設定が無効で、プロセスごとに一度警告します。Gateway 起動時に記録済みのアーカイブを元の場所へ戻し、Active にします。既存ファイルは上書きせず、競合したアーカイブは `skills-archive` に残します。Linux と macOS は両モードでディレクトリ FD を使ってグローバルと社員の平面形式スキルを復元します。シンボリックリンクはたどりません。他の OS はアーカイブを残し、手動復元が必要です。


読み込まれたスキルは `skill_list` で確認してください。同名の競合を解消してから復元を再試行し、成功までアーカイブを保管してください。次回の gateway 起動時に記録済みアーカイブの復元を再試行します。


## 自動化 → 実行・スケジュール・ファイルレビュー制限（v1.82.0）

3 つのカードは管理者のみ保存できます。既存のロック付き設定書き込みを使い、再起動せず次の実行・チェック・申請から反映します。

| カード／項目 | `config.toml` キー | 既定値／範囲 |
|---|---|---|
| 実行時間／既定秒数 | `[runtime] default_timeout_secs` | 省略可。30 秒から `max_timeout_secs` まで。空欄で上書きを削除し、すべてのランタイムで 1800 秒になります（最大上限を超えません）。v1.84.0 より前は Claude 以外のランタイムが 300 秒でした。 |
| 実行時間／最大秒数 | `[runtime] max_timeout_secs` | 3600。60〜14400 秒。上限を上げると長時間実行で利用枠を多く消費する場合があります。 |
| 1 回の実行／既定ステップ | `[runtime] default_max_turns` | 50。1 からステップ上限まで。増加は使用量と時間を増やす可能性があります。 |
| 1 回の実行／最大ステップ | `[runtime] max_turns_limit` | 200。1〜10000。管理者のみ変更可能。 |
| スケジュール／1 人の有効数 | `[goal_defaults] assign_schedule_max_active` | 20。0〜200。0 は作成と再開を禁止します。 |
| スケジュール／最短間隔 | `[goal_defaults] assign_schedule_min_interval_minutes` | 60。管理者以外は 60〜10080 分。管理者の最短間隔は 5 分のままです。 |
| レビュー／1 日の総数 | `[agent_files] review_daily_limit` | 200。0〜100000。 |
| レビュー／1 人の 1 日上限 | `[agent_files] review_daily_limit_per_user` | 40。0〜100000。 |
| レビュー／社員ごとの 1 日上限 | `[agent_files] review_daily_limit_per_agent` | 60。0〜100000。 |
| チェック／1 人の毎分上限 | `[agent_files] checks_per_minute` | 10。1〜1000。 |
| 承認／1 人の承認待ち上限 | `[agent_files] max_pending_per_user` | 20。1〜200。 |

社員の既存の `[runtime] timeout_secs` は Claude にも適用され、社員ページに実効秒数と最大上限を表示します。上限超過は保存時に拒否し、実行時に上限へ補正します。グローバル設定が検証に失敗すると警告を記録し、固定既定値（すべてのランタイムで 1800 秒、最大 3600 秒）に戻ります。無制限にはなりません。有効なグローバル既定値は個別設定のない社員だけに適用され、省略時の既定値も最大上限に従います。タスクとサンドボックスの制限で早く終了することもあります。個別ゴールは 30 秒から `min(max_timeout_secs, 3600)` まで設定でき、最大 1 時間です。

Web 会話は対象従業員の実効タイムアウト（グローバル上限に従う）に配信の余裕 30 秒を加えます。ルーティンの定数と役割別の上書きは変更しません。レビュー枠を使い切っても警告またはブロックとなり、レビューを省略しません。一時的な制限緩和スイッチはありません。従業員の個別値が未設定の場合、管理者ではない所有者は 300 秒以下のみ設定でき、より低いグローバル既定値や上限にも従う必要があります。

## 詳細設定と会社情報（v1.80.0）

両エディションの管理者は「設定 → 詳細」（`/app/system/settings/advanced`）を開けます。使用頻度の低い設定を一つのページの四つのグループに集約しました。検索は選択中の言語（日本語、英語、繁体字中国語）の項目名、説明、フィールド名を即時に絞り込みます。該当項目を展開して編集でき、既存の保存処理、再起動通知、RPC 権限を使用します。一般、アカウント、音声、能動的な通知は日常設定に残ります。管理者以外は新しい二つのページのナビゲーションも直接アクセスも利用できません。

| グループ | 設定と固定アンカー |
|---|---|
| システムと請求 | システム `#system`、アカウント切替 `#rotation`、診断 `#doctor`、請求 `#billing`、設定エディター `#configRaw` |
| セキュリティと記録 | サンドボックス、ファイルアクセス、信頼、トレース、シークレット `#security`、ログレベル `#logging`、コンテナー `#container`、委任 `#delegation`、秘匿化 `#redaction`、ブラウザー `#browser` |
| AI モデル | バックグラウンドモデル `#utility`、ナレッジ検索 `#knowledgeSearch` |
| 実験機能 | ハートビート `#heartbeat`、自動化 `#automation`、校正 `#calibration`、自動運転 `#autopilot`、スキル合成 `#skillSynthesis` |

従来の `?tab=system`、`?tab=automation`、`?tab=configRaw` などは対応するアンカーへ転送されます。一般設定のアカウント切替とログレベルは新しい場所へのリンクに変わります。以下の表は同じ設定キーの説明で、編集場所だけがこのページに集約されます。

「設定 → 会社情報」（`/app/system/settings/company`）では最大 120 文字の会社名（制御文字、行区切り文字、Unicode 書式・双方向制御文字を除く）と、1 MiB 以下の PNG、JPG、WebP ロゴを設定できます。SVG とアニメーションは拒否します。サーバーは画像の実際の内容と最大 4096 × 4096 の寸法を確認し、デコードしてメタデータを除去した後、256 × 256 以内の PNG に再エンコードします。保存時はまず RPC で名前と任意のロゴ削除を更新し、その後に選択した画像を HTTP でアップロードします。単一のトランザクションではありません。アップロードが失敗しても保存済みの名前は残り、選択ファイルは再試行用に保持され、全体の保存成功は表示されません。空の会社名は製品名に、未設定または読み込みに失敗したロゴは製品ロゴに戻ります。

サイドバーとログイン画面上部、招待メールと送信前プレビューは会社名とロゴを表示します。署名検証済みの販売代理店の製品情報は「製品情報」とログイン画面下部に残り、会社設定では変更しません。セットアップ一覧の会社名はこの会社情報を読み、ここへリンクします。従来の一般表示名は gateway のローカルネットワーク名に使用します。

`company.get` と `company.update` は管理者専用です。後者は `name` と任意の `remove_logo` だけを受け付け、`logo_base64` を拒否します。ロゴは `POST /api/company/logo` で生バイナリーを送信し、保存済み access token を `Authorization: Bearer` に設定します。Cookie は使用しません。gateway は本文を読む前に JWT と現在の管理者アカウントを検証します。ルートとストリーム読み取りでそれぞれ 1 MiB を上限とし、Content-Type は PNG、JPEG、WebP のマジックバイトと一致する必要があります。各アカウントと TCP 接続元 IP につき 60 秒間で六回までです（プロキシ配下はその IP の枠を共有）。IP 制限は認証より先に適用し、超過時は個別監査なしで 429 を返します。この制限を通過したリクエストと結果を監査します。アカウント制限は現在の管理者権限の検証後に適用します。本文読み取りは 30 秒でタイムアウトし、同時処理は二件までです。全体の WebSocket 上限は 1 MiB のままです。既存のロック付き設定保存処理で `[company] name` と `logo_hash` を保存し、処理済み画像は `<home>/company_logos/` に置きます。公開 `/api/company` はログイン画面向けの会社名とロゴ URL だけを返します。公開読み取りではファイルを一度だけ開き、同じファイル記述子で通常ファイル、単一リンク、サイズ上限を確認した後、PNG 内容と SHA-256 ハッシュを検証します。画像 URL はそのハッシュを含み、PNG と `nosniff` で配信し、1 年間の immutable キャッシュを許可します。削除後も過去の招待メールとキャッシュのため旧画像を保持するので、公開素材として扱ってください。保存したタブは即時更新され、他のタブは再フォーカスまたは再接続で更新します。

**Codex の外部設定検査（v1.80.0 から）：** 外部設定がないか MCP を定義していなければ、通常の社員、Explore、utility、Task Sandbox、Discovery は実行できます。MCP の検出、既存設定の読み取り・解析失敗ではソース名を示して拒否します。明示した Codex judge の拒否は判定失敗となり、既定の judge では再試行しません。起動前のローカル／キャッシュのスナップショット検査であり、その後のクラウド更新を完全に隔離する保証はありません。[検査対象と制限](../../architecture/extension-gates.md)。

ダッシュボードをパスのプレフィックス配下で公開する場合は、`config.toml` に `[dashboard] public_url = "https://host/agents"` を設定し、パスも含めてください。nginx の例：`location /agents/ { proxy_pass http://127.0.0.1:18889/; }`。Google Cloud には `https://host/agents/api/me/google/callback` を登録します（リモート MCP は `https://host/agents/oauth/mcp/callback`）。公開 URL とブラウザーの検証済みダッシュボード origin が一致する場合だけ、このプレフィックスを OAuth に使用します。LAN アクセスと URL の貼り付けフローの動作は変わりません。修正を含むバージョンへの更新と登録済みコールバック URL の変更後は、v1.79.1 用に追加したプレフィックスなしの `/api/me/google/callback` と `/me/connections` の nginx 回避ルールを削除できます。

Enterprise設定（v1.76.0、管理 → 詳細設定 → メンバーの「組織の設定」カード。メンバーページは Enterprise 版のみ）：`users.org_settings.get/update` が `[people] manager_team_history`（有効な設定では既定オン）を管理します。即時反映され、再有効化で期間をリセット。詳細エディターでも監査対象の保護キーです。有効にする前に職員へ通知してください。[チーム会話の閲覧](../../features/ja-JP/68-manager-team-history.md)を参照。

会話の保存（v1.81.0、Enterprise 版、管理 → 詳細設定 → メンバーの「組織の設定」カード、管理者）：同じ RPC で `[sessions] archive_after_days`（やり取りがない会話をしまうまでの日数。既定 30、0＝しまわない、最大 3650）と `[sessions] purge_after_days`（しまった会話の内容を削除するまでの日数。既定 0＝削除しない、しまった時点から数える、最大 3650）も読み書きします。再起動は不要で、6 時間ごとの整理処理が毎回読み直します。設定を読めない・値が不正な場合は既定どおりしまい、削除は一切しません。どちらのキーも詳細エディターで監査対象の保護キーで、0〜3650 以外は拒否されます。しまった会話は通常の一覧から消えますが、新しいメッセージが届くと自動で戻ります。職員は WebChat の過去の会話メニュー「しまった会話」から自分の会話を元に戻せます（`chat.sessions.restore`）。上司は「チーム会話」から戻せます（`users.team_history.restore`）。「チーム会話の閲覧開始日」（`team_history_since`、2020-01-01 から現在まで）で上司が閲覧できる開始時点を決めます。前に戻すとより古い会話が見えるようになるため、管理者本人の現在のパスワード（MFA 有効時はコードも）が必要で、変更は毎回監査イベント `team_history_since_changed` に記録されます。アップグレード時の注意：以前は 3 日でしまい、その 90 日後に削除する固定ルールでした。

v1.68.0 からダッシュボードで設定できる項目について、どのページにあるか、どの設定キーに書き込むか、保存後に gateway の再起動が必要かをまとめます。最後の節では、専用のコントロールがないキーを編集する「設定ファイルの詳細編集」を説明します。

他の言語：[English](../dashboard-settings.md) · [繁體中文](../zh-TW/dashboard-settings.md)

**保護モードの公開ウェブ（ネイティブ Linux の隔離構成、今後のバージョンで提供予定。設定ファイルのみ）：** AI スタッフの保護モードでの実行が `web_fetch_cached` と `web_extract` を使えるかどうかは、スタッフごとに `agents/<id>/agent.toml` の `[isolation] public_web = true` で設定します（既定は `false`、ウェブアクセスなし）。ダッシュボードの専用コントロールはまだありません。ファイルを直接編集するか、管理者向けの設定エディター（`agent:<id>`）を使用してください。このエディターはこのキーを保護された変更として通知します。スタッフフォームのキー／値エディターは `[isolation]` セクションを拒否し、管理者以外の `agents.update` では変更できず、スタッフ自身によるファイル編集でのこのセクションの変更も拒否されます。このスイッチは、スタッフフォームの**ネットワークアクセス**（`[container] network_access`）とは別で、後者は引き続きタスクサンドボックスのネットワークだけを制御します。有効にしても、保護モードでの取得は公開 HTTPS サイトにしか届きません（IP アドレス、内部名、リダイレクトは不可）。保護モードでないインストールではこのキーは無視されます。

ゴール費用と連続呼び出しのガードは現在「設定ファイルの詳細編集」で設定し、自動化の専用コントロールはありません。`config.toml [goal_loop]` の `default_cost_cap_cents = 0` は個別上限のないゴールの既定上限（米セント、`0`＝上限なし）、`tool_streak_pause = 8` は終了した1ラウンド内の同一ツール・同一引数の連続呼び出しによる停止回数（`0`＝無効）です。詳細編集で保存するとゴールループが再読み込みされます。`config.toml` を直接編集した場合は gateway を再起動してください。`tool_streak_advisory` は既存ヒントを独立して制御します。個別上限はゴールの依頼時に指定できます。`/goals` は費用を表示し、権限のある操作者が一時停止ゴールの上限を引き上げて再試行できます。


## 会社の設定チェックリストとAI分身

Enterprise の管理者は、管理メニューまたはホームのカードから「設定チェックリスト」（`/setup`）を開けます。Personal 版と他のロールには表示されません。「会社・メンバー・機能」の各項目は既存の設定ページに移動します。チェックリスト自体は読み取り専用です。必須項目は会社名、ナレッジのコレクション、AI アカウント、アーカイブされていない AI スタッフ、2 人以上の有効なユーザー、接続済みチャンネル、すべての Employee ユーザーへの AI スタッフの割り当て、スキルです。Google、Odoo、自動化は任意で、「完了 N / M」の集計に含みません。読み取りに失敗した項目は「確認できません」と表示され、完了に数えません。必須項目をすべて完了するとホームのカードが消えます。カードを閉じた場合は、このブラウザーのローカルストレージに保存されます。管理メニューからは引き続き開けます。

管理者以外の新しいWebChat会話では、オーナーまたは操作権限の紐付けが有効で、呼び出せる、読み込み済みの非メインAI分身を優先します。利用できなければ従来の紐付け済みメインAI、次に唯一呼び出せる非メインスタッフを使います。候補が0人または複数なら会話を開始しません。AI分身の設定は管理者に依頼してください。分身のないメンバーはサイドバーで「既定のAIスタッフに設定」を利用でき、分身がある場合は自分で切り替えられません。分離機能が有効な保護モードでは、管理者は個人 AI スタッフをその所有者の分身にのみ指定できます。

会社共用のTelegram Botは、認証済みダッシュボードアカウントとの1対1のチャットでAI分身を優先し、有効な分身がなければ従来の紐付け済みメインAIを使います。スタッフ紐付けリンクが優先され、グループは従来のチャネルルートを維持します。WebChatと同じ利用条件を満たさない場合は、従来のチャネル既定を使います。詳しくは[`@` で AI スタッフを呼ぶ](../../features/ja-JP/62-calling-ai-staff.md)を参照してください。

管理者以外のメンバー（Employee、Manager）は、サイドバー、会話フィルター、コマンドパレット、WebChat の `@` 候補、その他のスタッフ選択欄で、`agents.callable` が選択可能と明示したスタッフだけを表示します。メイン AI は、その応答が明示的に選択を許可した場合を除き表示しません。全一覧は、`agents.callable` が現在の Admin 権限に基づいて `unrestricted: true` を返した場合のみ表示します。Personal のローカル管理者も含みます。初回読み込み中や取得失敗時は、すべてのアカウントで空になります。ページ表示中は 60 秒ごと、再表示時、および選択メニューを開く際に権限を更新します。更新中は同じユーザーの確認済み一覧を保持し、失敗した場合は消去します。ファイルと設定の選択欄には直接のアクセス権も必要で、チームの呼び出し権はファイルや設定の権限を追加しません。新しい会話は引き続きサーバーが担当を決定します。この dashboard の表示制限は RPC の認可を変更しません。

## スタッフの健康状態（v1.80.0）

Admin と Manager は、どちらのエディションでも「スタッフの健康状態」（`/employee-health`）を開けます。読み取り専用のページには最初に概要を表示し、スタッフを展開すると、最後に記録された応答、過去24時間または7日間の失敗内訳、人の判断待ち・一時停止中の目標、アカウントの利用状況を確認できます。失敗は空の応答、利用枠・予算の上限、リクエストの頻度制限、認証の失効、タイムアウト、権限チェックによる拒否、送信失敗、その他に分かれます。アカウントの状況は、スタッフが明示した `account_pool` に一致するアカウントだけを反映します。プールの指定がなければ不明です。CLI 自体のログイン状況やプロバイダーとの接続はテストしません。

最後の成功応答は、共通のチャンネル応答処理が空でない内容を生成したことを意味し、**チャンネルへの配信完了を保証しません**。古い記録では時刻を確認できない場合があります。失敗件数は `channel_failures.jsonl` と独立した `employee_health.jsonl` のターン記録を統合し、それぞれ末尾の最大4 MiBを読み取り、約30秒キャッシュします。データが不完全との表示は、記録を取得できないか読み取り上限に達したことを示し、選択期間の件数が不足している可能性があります。ツールの成功や費用の記録は、応答成功とは見なしません。

健康状態の通知は、各チャンネルで共通の応答処理を利用します。既定では5回連続で応答に失敗した場合、またはメッセージを受信してから6時間、正常な応答を生成できなかった場合に一度通知し、成功するとリセットします。認証障害の通知が有効な間は、認証の失敗だけによる健康通知を重複させません。有効な管理者と、そのスタッフの Owner に紐付く検証済みチャンネルへ、既存の通知・おやすみ時間の処理で送信します。送信前に通知済みと記録するため、同じ連続障害についての送信試行は最大1回です。送信に失敗しても再試行せず、正常な応答でリセットするまで再通知しません。紐付け済み、または到達可能な宛先がなければ配信は保証されません。通知の試行は配信完了の確認ではありません。

管理者は既存の「設定ファイルの詳細編集」で `config.toml` のしきい値を変更できます。健康ページに別の設定フォームはありません。

```toml
[employee_health]
enabled = true
consecutive_failures = 5 # 1..100
no_success_hours = 6    # 1..168
```

設定ファイルが存在しない場合やセクションを省略した場合は、上記の既定値を使います。ファイルがない場合以外の読み取りエラーや、無効な設定では健康通知を停止します。通知を停止してもスタッフの権限やタスクの実行は変わらず、健康ページは読み取り専用です。

## スタッフ編集ページ → ツールと権限 → ツール権限（v1.81.0）

スタッフ編集ページの「ツールと権限」タブには、**ツール権限**と**権限の変更履歴**の 2 つのサブタブがあります。表にはカタログのすべてのツールがカテゴリ別に並び、「使用可」と「要承認」の列、カテゴリごとの全選択（`N/M 使用可`）、検索ボックスがあります。編集は下書きとして保持され、変更した行には印が付き、下部の固定バーに「変更を破棄」／「保存」が表示されます。保存を押すと確認ダイアログが開き、使用可に追加・使用可から削除・要承認の件数と、ツールごとの変更前 → 変更後が表示されます。確認すると通常の `agents.update` の `capabilities` で書き込まれます。変更できるのは管理者だけで、それ以外のアカウントには同じ表が読み取り専用で表示され、チェックボックスはすべて無効、全選択と保存バーはありません。

表と `agent.toml [capabilities]` の対応：

- **使用可**＝`denied_tools` に一致せず、かつ `allowed_tools` が空またはそのツールに一致する状態（ゲートウェイ自身の規則と同じ。拒否が常に優先し、空でない許可リストは許可リストモード）。照合は完全一致基準でワイルドカード対応です（例：`mcp__duduclaw__*`）。
- チェックを外すと常にそのツールが **`denied_tools` に追加**されます。`allowed_tools` は縮小も書き換えもされないため、ワイルドカードの許可リストはそのままで、対象のツールはすべて使用可と表示されます。再度チェックするとその拒否エントリが削除されます。*ワイルドカード*の拒否エントリに含まれるツールはここで有効にできません（行はロック）。「詳細設定」でそのエントリを編集してください。
- **要承認**＝`approval_required_tools`（ツールの短い名前）。MCP のディスパッチゲートがすべてのツールに対して実際に適用するリストです。承認リストのワイルドカードや `action_rules` の `ask` ルールがすでに承認を求めているツールは、要承認として表示されますがロックされます。「使用可」がオフの間、このチェックボックスは無効です。

従来の許可リスト・ブロックリスト・アクションルール・承認リストのブロックは、タブ下部の折りたたまれた「詳細設定」に移り、表と同期します。

**権限の変更履歴**（管理者のみ）は、`agent_authority_changed` の監査記録から、このスタッフの権限変更を表示します：日時、操作した人、ツールごとの旧状態（取り消し線）→ 新状態。表から保存していない変更には「詳細設定から変更」と表示されます（表の導入前の古い変更も同様）。このタブは管理者専用の `agents.permission_history` RPC（`agent_id`、最大 100 の `limit`、`cursor`）で提供され、`security.audit_log` と同じ監査ログを読みます。

## 一般従業員のサイドバー

Personal 以外の Employee アカウントには、ダッシュボード、受信トレイ、自動化、スキル、メモリ、AI バーチャルオフィス、閲覧専用の組織図、紐付けられた AI スタッフ、会話履歴を表示します。検索は既存のコマンドパレットを開きます。AI分身（未設定なら従来のメインAI）が先頭で、残りは Owner、Operator、Viewer の順に最大8人です。受信トレイの入口は1つです。ユーザーメニューには登録メール、マイ接続、設定、外観、言語、ヘルプ、ログアウトがあります。言語はアカウント設定の選択欄を開きます。サーバーに販売代理店の案内がある場合、ヘルプはその入口を開き、ない場合は製品ガイドを開きます。Employee 画面のバージョン表示は「この製品について」に集約します。Admin、Manager、Personal のナビゲーションは従来どおりです。

自動化はサーバーが記録ごとに権限を確認します。自分が作成した記録と、直接紐付けられた AI スタッフの記録を閲覧でき、Viewer は閲覧のみ、Operator と Owner は管理できます。作成には対象スタッフの操作権限が必要です。紐付けの解除は次のリクエストから反映されます。組織図は構造の項目のみを返し、モデル、予算、認証情報、連絡先、編集操作を含みません。

メンバーが作成する cron ルーティンは、タイムゾーンを省略すると夏時間のない会社タイムゾーンを使います。会社タイムゾーンに夏時間がある場合は UTC で保存し、その旨を通知します。タスクサンドボックスが無効な host 実行の AI スタッフに限定します。有効予定は利用者ごとに 20 件、スタッフごとに 50 件、作成は直近一時間に 20 件、最短間隔は 15 分です。追加・更新メッセージはチャットの入力防護を通り、拒否を監査に記録します。組織図は直接紐付いたスタッフと本人の部署を表示し、範囲外の祖先は名前とロールのみです。Admin の既存動作は維持します。

これらの制限は MCP で作成・編集した人間由来の予定にも適用します。メンバー由来の MCP ルーティンでタイムゾーンを省略した場合、夏時間のない会社タイムゾーンを使い、夏時間があれば UTC で保存して通知します。夏時間のあるタイムゾーンを明示指定した場合は引き続き拒否し、それを持つ既存予定は Admin が変更するまでスキップします。スキップされた予定は「自動化」ページに「スキップ済み」と理由が表示され、管理者に一度だけ通知されます。新しい Admin／バックグラウンド予定は、タイムゾーンを省略すると会社タイムゾーンを使い、未設定または無効なら UTC を使います。既存予定の動作は変わりません。手動実行は 10 分間で予定ごとに 3 回、アカウントごとに 10 回まで受理し、未完了はアカウントごとに 2 件、全体で 4 件までです。busy の場合は直ちに拒否します。手動実行の窓は gateway 再起動でリセットします。従業員の cron 式は 256 bytes までです。

新しい会話には、ログイン中のアカウントが最近送信し、現在も利用できるスキルを最大5件、短い説明付きで表示します。複数のチップを選ぶと `/skill-name` が下書きに入り、詳細を追加してから送信できます。選択だけでは実行しません。履歴は会話やタスクの受理後にサーバーが保存し、閲覧時に利用権限を再確認します。AI がスキルを正常に実行したことを示す記録ではありません。タスク依頼ページが有効な場合も同じ履歴を使います。

タスクボード（`/tasks`）、目標（`/goals`）、タスク依頼（`/assign`）の入口は、管理者と Personal を含むすべてのロールで非表示です。サイドバーの主要ボタンとスマートフォン下部中央の ＋ は新しい会話を開き、引き継いだ文章は未送信の下書きになります。`/assign` は `/chat` に転送します。`/tasks`、`/tasks/:id`、`/goals` は通知やタスクカードなどの直接リンクから引き続き開けます。既存の権限、タスクデータ、予約、バックエンド API は変わりません。責務（`/responsibilities`）と先読み（`/foresight`）は従来の表示条件と権限を維持します。

`config.toml [dashboard] employee_tasks` は引き続き解析され、`system.status` で返されますが、タスクボード・目標・タスク依頼の入口は復元しません。責務と先読みへの既存の効果は残ります。専用の設定ページはありません。

```toml
[dashboard]
employee_tasks = false
```
## WebChat のスタッフへのアクセス

すべてのエディションで、管理者以外には会話上部のスタッフ選択欄を表示しません。ヘッダー、履歴、会話一覧はサーバーが決めたスタッフに対応します。`@` 一覧には呼び出せるスタッフを表示しますが、main ロールのスタッフと gateway の既定スタッフは含みません。明示的な紐付けがあっても、管理者以外はこれらを操作できません。各メッセージで再確認し、紐付けの変更は既存の60秒の権限キャッシュの範囲内で反映します。主エージェントとの古い会話の再開は、ほかの利用できないスタッフと同じメッセージで拒否し、別のスタッフへ自動転送しません。担当を解決できなければ入力欄を無効にします。管理者（Personal の単一ユーザーを含む）と旧式の管理者トークン接続のチャット動作は従来どおりです。どのエディションでも、管理者以外のアカウントは `agents.callable` やダッシュボードの作業 RPC から主エージェントを利用できません。主エージェントの有効化、その承認要求の決定、コンピューターセッションの再開や操作の返却もできません。

送信者のないキュー処理は拒否し、監査記録を残します。主エージェントまたは gateway の既定スタッフへの処理に利用者の身元がない場合、cron や heartbeat など既定のシステム送信者のみを受け付けます。この制限は `[delegation]` のモードに依存しません。既知の制限：キュー行は未署名のため、同じ OS ユーザーとして無制限のファイルアクセスを持つスタッフはシステム送信者を偽装できます。gateway による受け入れ署名は v1.80 で対応する予定です。

## 任意の独立プランレビュー

`config.toml [goal_loop]` に `plan_review = "goldfish"` を設定すると、計画の生成に成功した後、人の承認に提示する前に独立レビューを追加できます。既定は `"off"` で、未設定や不正な値も無効になります。新規の呼び出しを現在のタスク内で三つ並行して実行し、それぞれ 45 秒でタイムアウトするため、追加の待ち時間は最大 45 秒です。視点は、目標の言い換えと不明点、不要な作業の削減、実行に必要な判断・権限・データの確認です。各レビュアーが受け取るのは XML エスケープ済みの目標・受け入れ基準・計画というデータだけで、会話・記憶・SOUL・社員の身元は渡しません。回答は繁体字中国語で最大五つの箇条書きを要求し、各視点で 400 文字まで保存します。

呼び出しは `goal-plan-review` のシステムユーティリティ利用として扱い、社員ディレクトリを渡さず既存のシステム側プロバイダー解決を使います。**社員の予算には計上しません**。バージョン付きの `plan_review` JSON は人が読むためだけの情報です。`plan_pending` や `judge_feedback` を変更せず、実行・判定のプロンプトにも入れず、人の承認を置き換えません。失敗・空白・タイムアウトは「未実行」と表示し、三つとも失敗してもタスクは `needs_human` で待機します。タスク詳細と受信箱に、既定で閉じた「独立レビュー（会話の文脈なし）」欄を表示します。チャネルには完了した視点の数と dashboard への案内だけを表示し、レビュー本文は送りません。この数は個々の指摘数ではありません。

## 社員ごとのツール一覧の整理

Admin は社員の概要にある「ツール一覧の整理」でモードを選び、未使用ツールと推定節約量を確認できます。オンのときは一覧を復元できます。モード選択は既存の社員更新処理を使います。`agents.tool_pruning_status {agent_id}` と `agents.tool_pruning_restore {agent_id}` は Admin 専用です。推定値は候補ツールのシリアライズ済み定義の長さを四で割った値で、tokenizer の実測値やプロバイダーで確認した節約量ではありません。

```toml
# agent.toml
[capabilities]
tool_pruning = "shadow" # "off" | "shadow" | "on"
```

既定の `shadow` は観測と報告のみで、`tools/list` の応答は `off` と同一です。不明または不正な値は `off` と扱い、一度警告します。`on` の場合だけ、既存の全フィルターの後で条件に合うツールを非表示にします。権限の付与や取り消しは行いません。非表示でも既存のディスパッチゲートを通して呼べます。呼び出しに成功すると `notifications/tools/list_changed` により一覧に戻ります。

計算では `tool_calls.jsonl` の末尾 5 MB だけを読みます。ログがない、読めない、または記録済みターンが十未満なら整理しません。十ターン以上かつ二セッション以上、または五セッション以上にわたって未使用のツールが候補です。記憶、タスク、作業状態、メッセージ、承認、wiki 読み取り、ツール探索、Admin／不明な効果のツール、有効なタスク限定許可のあるツールは残ります。ターンはホストが記録する `(session_id, turn_id)` の一意な組であり、ログの行数ではありません。チャネル呼び出しは会話の session と turn、ディスパッチ作業は自身の dispatch session と run を使い、一回の run を一ターンと数えます。これらの項目がない古い行はターンのサンプルにはなりませんが、成功した使用はそのツールの未使用期間をリセットします。各ツールの最後の成功後のターンとセッションで条件を判定します。各プロセスで五分間キャッシュします。復元は社員ごとのリセットマーカーを書き込み、それ以前の使用履歴を計算から外すため、既存の権限で利用できる一覧に戻ります。権限フィルターは引き続き適用されます。

Claude CLI の `minimal_context` は `--tools` で内蔵 CLI ツールを制御し、MCP ツール定義には影響しません。この経路は変更していません。

## アカウントのロールと表示される AI スタッフ

AI スタッフに Bash やマシン操作ツールを与えると、紐づく人は誰でも、それらのツールを使うよう指示できます。紐づける前にスタッフの能力を確認し、その権限を持つべき人だけに許可してください。管理者は通常の AI スタッフに引き続きネイティブツールを許可できます。

`system-operator` プリセットを使うスタッフは Admin 専用で、サーバーが解決済みのプリセット紐づけを確認します。Admin 以外は紐づけ、チャット、タスクやゴールの作成、自分の依頼としてのディスパッチができず、`agents.callable` にも表示されません。既存の紐づけは保持し、利用時に拒否します。Admin 以外は古い紐づけやチーム権限が残っていても、そのスタッフの会話履歴、タスク、記憶、ファイル、専用ナレッジコレクション、エクスポートを閲覧できず、リアルタイム更新、実行ステップ、承認カードも受信できません。紐づけの記録は保持します。Admin 以外が以前作成した依頼スケジュールは、そのスタッフのタスクやゴールを作成せず、実行時に自動停止し、再開も拒否します。外部送信の承認カード（CLI 組み込みツールと MCP ツールの両方）は Admin だけが閲覧でき、Manager にマスキング済みカードは表示されません。チャネルと Mini App にはテキスト通知だけを表示し、外部送信の承認カード、要約、操作ボタンは表示しません。Admin と許可済みの無人実行は従来どおりです。Personal の単一所有者の例外は、users.db が存在しない、アカウントがない、または初回のパスワード変更を完了した有効な Admin アカウントが一つだけの場合に限ります。停止中・退職済みのアカウントも数えます。複数アカウントの環境は、有料ライセンスの期限切れで Personal に戻っても有効な管理者が必要です。アカウント情報を読み取れない場合も同様です。

一般社員には、自分に直接紐付いた AI スタッフだけを表示します。マネージャーには、サイドバー、AI スタッフ一覧、タイムライン、実行履歴で部下の AI スタッフも表示し、チームメンバーの AI スタッフと明記します。チーム経由では閲覧のみです。タイムラインは仕事のカードと日時、実行履歴は状態と日時を表示し、会話本文やツールの手順は含めません。記憶、スタッフ設定、人格ファイルにはアクセスできません。チーム経由の権限は Operator までです。直接の紐付けは既存の権限を保ち、組織メニューの人数条件では直接とチームの両方を数えます。

「管理 → メンバー」には各アカウントの AI スタッフ、権限、紐付けの削除操作があります。追加時は AI スタッフを自分で選びます。最初のスタッフは自動選択しません。既定の権限は Operator で、`users.bind_agent` の `access_level` を省略した場合も同じです。既存の紐付けは自動変更しないため、不要な権限を確認して削除してください。削除は次の RPC とファイル要求から反映され、古い token のダウンロードやプレビューにも適用します。

共有 Wiki はメンバー設定のアカウントの部署（`users.db` の `users.department`）で判断します。管理者以外は会社共通ページと自分の部署のページを閲覧でき、`visible_to_departments` の制限にも従います。部署がない場合は会社共通ページだけです。一覧、検索、本文、統計、エクスポートに同じ規則を適用します。権限を読めない場合や表示設定が壊れている場合は拒否します。管理者は全社のページを閲覧できます。ページの共有には引き続き元の AI スタッフの Owner または管理者権限が必要です。

会社全体の利用量（`billing.usage`）と日次成長レポートには Manager が必要です。ウィジェット生成とモデル更新も、モデル枠の消費やプロバイダーへの接続があるため Manager が必要です。システムログには Admin が必要です。従業員の自動化には上記の記録ごとの権限を適用します。レポートとホームの費用欄、エキスパートのアップロード・インストール操作は Admin のみに表示し、他のロールでは要求しません。

## Codex CLI の更新

macOS と Linux で、通常の従業員を WorkspaceWrite 権限で実行するには Codex CLI 0.164.0 以降が必要です。インストール済みのバージョンが古い、または確認できない場合、Admin には各ページ上部に現在のバージョンと「**Codex CLI を更新**」ボタンが表示されます。押すとゲートウェイのパソコンで `npm install -g @openai/codex` を実行し、進行状況を表示します。更新を確認すると通知は消え、ゲートウェイの再起動は不要です。

npm がない場合やインストールに失敗した場合は、手動コマンドとコピーボタンを表示します。Homebrew などの古い実行ファイルが優先される場合はそのパスを表示します。そのバージョンを更新または削除してから、再検出してください。バージョンを確認できない場合も成功とは区別して表示します。Windows はこの要件の対象外です。

## 保存の共通ルール

- システム設定（`config.toml`）は `system.update_config` で書き込まれ、管理者だけが使えます。ページは変更した項目だけを送ります。変更がなければ何も送りません。
- 書き込み時にファイルをロックして読み直します。読み込んだ後にほかの書き込みでファイルが変わっていた場合、保存は拒否されます。再読み込みしてから保存してください。
- `config.toml` が解析できない場合、`system.update_config`、常駐センシングのデータソース編集、設定ファイルの詳細編集は書き込みを拒否します。先に設定ファイルの詳細編集で構文を直してください。`config.toml` に書き込むほかの設定ページ（チャネル、アカウント、Odoo など）も同じく書き込みを拒否します。
- 保存はファイルをその場で書き換え、変更したキーだけを書き直します。コメント、空行、キーの順序、変更していないキーの書式はそのまま残り、値を変えた行の行末コメントも残ります。新しいキーはそのセクションの末尾に、新しいセクションはファイルの末尾に追加されます。設定ファイルの詳細編集だけでなく、`config.toml` や `inference.toml` に書き込むすべての設定ページで同じです。
- 再起動後に有効になるキーは応答の `restart_required` に入ります。システム設定ページとチャネル管理ページには、gateway が再起動するまで「再起動後に有効になる設定」の案内が表示されます（手動で閉じることもできます）。推論ページと AI 社員の編集ページには表示されません。
- 次のキーを変更すると、変更前後の値を含む監査イベント `config_protected_key_changed` も記録されます：`acp.trusted`、`tick.allow_command_sources`、`container.sandbox.when_unavailable`、`container.sandbox.script_when_unavailable`、`memory.supersession_trust_guard`、`dashboard.public_url`。

## システム設定 → 一般 → 会社タイムゾーン（v1.86.0）

管理者はシステム設定 → 一般の「会社タイムゾーン」（`[general] company_timezone`）に `Asia/Taipei` のような IANA 名を設定できます。新しいルーティン、割り当て予定、チャット予定の既定値となり、ダッシュボードの時刻表示、リマインダー確認、チャネル通知、AI の起動コンテキスト、データ書き出しの日付にも使われます。未設定または無効の場合、新しい予定は UTC となり確認にも明記します。ダッシュボードの時刻は各利用者のブラウザータイムゾーンで表示します。

v1.86 の gateway 初回起動時に `config.toml` があり、この設定が未指定なら、ホストのタイムゾーンを一度だけ自動入力し「自動入力済み、確認してください」と表示します。検出できない場合は未設定のままです。管理者が消去した場合も含め、再検出はしません。夏時間のある会社タイムゾーンでメンバーがルーティンを作成すると UTC で保存し、その旨を通知します。メンバーが明示指定できるタイムゾーンの制限は変わりません。既存予定は移動しません。タイムゾーンなしのルーティンは UTC のまま、v1.86 より前に作成されたタイムゾーンなしの割り当て予定はホストのタイムゾーンを使い続けます。

Heartbeat の `cron_timezone`、digest の `timezone`、通知の quiet-hours 用 `[proactive] timezone` は別設定で、空欄は会社タイムゾーンを意味しません。

## システム設定 → 一般 → ダッシュボード公開 URL

管理者はここで `[dashboard] public_url` を設定します。外部からダッシュボードにアクセスする完全な URL で、リバースプロキシのサブパスも含めます（例: `https://example.com/agents/`）。HTTPS が必須です。HTTP は `localhost`、`127.0.0.0/8`、`::1` のみ利用できます。ユーザー名・パスワード、クエリ（`?`）、フラグメント（`#`）、`..`、エンコードされた `/`・`\` を含めないでください。それ以外は保存時に gateway が拒否します。`config.toml` に手で書かれた無効な値があると、修正されるまで OAuth の開始を拒否します（サブパスのない URL に黙って切り替えることはありません）。空欄にするとキーを削除します。変更は即時に反映され、`config_protected_key_changed` が記録されます。

public_url を設定すると、すべての OAuth コールバックと戻りリンクにサブパス付きで使われます。

| フロー | プロバイダーが戻すコールバック URL | 完了後にブラウザが戻る先 |
|---|---|---|
| リモート MCP サーバー（連携 → MCP → リモートサーバー） | `<public_url>/oauth/mcp/callback`（動的クライアント登録で自動登録） | `<public_url>/manage/integrations?tab=mcp&mcp_tab=remote` |
| 個人の Google アカウント（自分の接続） | `<public_url>/api/me/google/callback` | `<public_url>/me/connections` |
| 組み込みの Google Workspace、GitHub、Notion、Slack OAuth | `<public_url>/api/mcp/oauth/callback` | 結果ページから `<public_url>/manage/integrations?tab=google`（Google）または `?tab=mcp` へのリンク |

- **新しいコールバック URL を登録してください。** public_url を設定・変更したら、使っている各 OAuth アプリに新しいコールバック URL を追加します。Google Cloud Console → 認証情報 → OAuth クライアント → 承認済みのリダイレクト URI、GitHub OAuth App の Authorization callback URL（GitHub OAuth App のコールバック URL は 1 つなので置き換えます）。Notion と Slack のアプリも同様です。連携ページに登録すべき URL が表示されます。すでに進行中のサインインは開始時の URL で完了します。
- ブラウザ自身のオリジンは引き続き先に確認されます。直接リダイレクトはループバックアドレス、または `[gateway] allowed_origins` にある https オリジンで開いた場合だけです。それ以外は従来どおり `http://127.0.0.1:<port>/…` への貼り付けフローになります（このループバックアドレスにはサブパスを付けません）。public_url 以外の許可済みオリジンで開いた場合も public_url に戻り、gateway は警告を 1 回だけ記録します。
- チャットメッセージ（通知、判断カード）内のダッシュボードへのリンクには、`[dashboard]`、`[general]`、`[gateway]` の順で最初に有効な `public_url` を使います（http または https、localhost やループバックではない、ユーザー名・クエリ・フラグメントを含まない）。どれも有効でない場合、コンテナ内の gateway はリンクを付けず、通常のマシン上の gateway は `http://localhost:<port>` にリンクします（v1.84.0）。[Google Chat](channels-googlechat-teams.md#ダイレクトメッセージ判断ボタンダッシュボードへのリンクv184) を参照してください。
- public_url が未設定なら動作は変わりません。リモート MCP と個人 Google はブラウザのオリジン（パスなし）に戻り、組み込みプロバイダーは `http://localhost:<port>/api/mcp/oauth/callback` を使います。
- リバースプロキシ: `<サブパス>/oauth/mcp/callback` と `<サブパス>/api/…` をサブパスを外して gateway に転送してください。
- 制限: ダッシュボードのアプリ自体はルートパス向けにビルドされています。`/assets/…` を読み込み、`/api/…` と `/ws` を呼び出し、ページのルートにもベースパスがありません。そのためサブパスで公開する場合は、プロキシでこれらのルートパスも gateway に転送するか、専用のホスト名を使う必要があります。public_url が直すのは OAuth のコールバックと戻り URL で、アプリ自体をサブパス対応にするものではありません。ページに同一オリジンの `<base href>`（プロキシが挿入したものなど）があれば、ダッシュボードは OAuth 開始とメンバー招待でそのサブパスを送り、gateway が再度検証します。

| ゴールループとディスパッチ → ディスパッチ方針に「1人の社員に4つの役割」を追加 | `[dispatch] policy = "role_team"` | 即時（ディスパッチエンジンを再起動） |

定型のエラー・機器操作拒否メッセージは繁体字・簡体字中国語、英語、日本語に対応します。スタッフが `auto` の場合、入力言語を検出できないため全体の言語を使い、未設定または非対応なら繁体字中国語に戻ります。その他のシステム通知（チャネルの `@` ルーティング通知を含む）は現在、繁体字中国語・英語・日本語のみ対応し、簡体字指定時も繁体字中国語になります。

### 記憶の言語とバックグラウンド処理（v1.84.0）

**会話のタスクメモ**は設定ファイルで指定します。`config.toml [memory] pinned_task = "first_message"` が既定値で、`"off"` は抽出と注入を次のメッセージから停止します。社員の `agent.toml` の同じキーでも無効にできますが、グローバルの `"off"` は解除できません。不明な値は off とし、プロセスごとに一度警告します。設定の読み取りや解析に失敗した場合も無効です。有効なメモは 1 対 1 の会話だけで信頼できない参考データとして使い、最終更新から 24 時間で期限切れになります。無効な既存メモは書き換えず無視します。[会話メモリ](../../features/ja-JP/16-session-memory-stack.md)を参照してください。

| ページ → コントロール | キー | 反映 |
|---|---|---|
| システム設定 → 一般 → 記憶の言語（既定の返信言語の下） | `config.toml [memory] language`：`auto`（「返信言語に従う」）、`zh-TW`、`zh-CN`、`en`、`ja-JP` | 即時 |
| AI スタッフの編集 → 一般 → 基本情報 → 記憶の言語（返信言語の下） | `agent.toml [memory] language`、選択肢は同じ。`agents.update` の `memory_language` でも設定可（空文字で解除） | 即時 |
| AI スタッフの編集 → 頭脳とエンジン → 使う実行エンジン → バックグラウンド整理に使うサービス（社員のエンジンがバックグラウンド処理に対応していない場合か、すでに値が設定されている場合だけ表示） | `agent.toml [runtime] utility_provider`：`claude`、`codex`、`openai_compat`、または使わない。`agents.update` の `runtime.utility_provider` でも設定可（空文字で解除） | 次のバックグラウンド処理 |

この 3 つの設定は管理者だけが変更できます。ほかのアカウントでは選択欄が無効になり、RPC も変更を拒否します。AI スタッフは `agent_update` や自分の `agent.toml` の編集で自分の記憶の言語を変えられません。

**記憶の言語**は、システムが自分で記憶に書き込む内容の言語を決めます。対象は、固定された指示、重要な事実、会話の要約、会話の整理で残す事実、自動で作成したナレッジページのタイトルと要約です。言語はスタッフの記憶の言語、全体の記憶の言語、スタッフの返信言語（または全体の既定の言語）の順に決まり、どれも設定がなければ会話の言語に従います。`auto` は次の段階に判断を渡すため、スタッフページの「返信言語に従う」は、全体の記憶の言語があればそちらを先に使います。結果が繁体字中国語の場合は、簡体字が残っている内容を保存前に同梱の OpenCC フレーズ辞書で台湾繁体字へ変換します（言い回し、コード、URL、ファイルパスは変えません。詳細と制限は[変換ガイド](memory-convert-script.md)を参照）。設定がなくても、会話が主に繁体字中国語で日本語の仮名を含まない場合は繁体字中国語を使います。v1.84.0 より前に保存された記憶は変わりません。既存の簡体字の記憶を変換するには[簡体字の記憶を繁体字に変換する](memory-convert-script.md)を参照してください。

**バックグラウンド処理**（重要な事実、固定された指示、会話の要約、タイトル、会話の整理とナレッジの作成、状況の判定）は、スタッフの実行エンジンが Claude、Codex、OpenAI 互換のいずれかなら、そのエンジンで行います。Grok やほかの CLI エンジンではこの処理ができません。そうしたスタッフでは、スタッフページで選んだサービスを使います。選んでいない場合は、`config.toml` に `[runtime] utility_provider` が実際に書かれていて、その値が 3 つのサービスのどれかであるときだけ、それを使います。それ以外は処理をスキップします。v1.84.0 より前は、こうしたスタッフは通知なしに Claude を使っていました。スタッフページには使用中のサービスかスキップ中であることが表示され、システムチェックの「バックグラウンド整理をスキップしている社員」にも一覧が出ます。会話内容は選んだサービスに送られます。モデルは、スタッフの `[model] utility`（そのサービスのモデルの場合）、全体の `[runtime] utility_model`（全体のサービスが同じ場合）、Claude なら `claude-haiku-4-5`、ほかのサービスならそのサービスの既定、の順に決まります。

**エンジンに合わないモデル。** モデルの接頭辞を宣言している別のエンジンで動くスタッフに Claude の短い名前（`opus`、`sonnet`、`haiku`、`fable`）が保存されている場合、そのエンジンの既定モデルで実行するようになりました（案内では Codex を「ChatGPT」と表記します）。スタッフページとシステムチェックの「社員のモデルと実行エンジン」に、モデルを選び直すよう案内が出ます。この案内は、サービス起動後にそのスタッフが一度以上実行されてから表示されます。

**新しくインストールしたエンジン。** ダッシュボードからインストールしたエンジンは、サービスを再起動せずにすぐ使えます。再検出（`runtime.detect`）は検出結果が変わった場合だけエンジン一覧を作り直し、データディレクトリごとに最大で 1 分に 1 回です。スタッフの実行エンジンや予備エンジンが見つからない場合は、最大で 1 分に 1 回確認し直します。

## 設定 → 詳細 → セキュリティと記録 → 記憶：個人的な話題

| 項目 | キー | 反映タイミング |
|---|---|---|
| 自動記憶に記録しない内容（1.81 新機能）→ 健康／家族／個人の財務／給与 | `[memory_privacy] excluded_categories`（`health`、`family`、`personal_finance`、`salary`） | すぐ（書き込みごとに読み込み、次のメッセージから適用） |
| 自動記憶に記録しない内容 → カスタムキーワード（カテゴリごと） | `[memory_privacy.custom_keywords]` | すぐ |

4 つのスイッチは既定ですべてオンです。`config.toml` に `[memory_privacy]` セクションがない既存インストールも同じです。オンにしたカテゴリは、自動記憶では一切保存されません。対象は会話の蒸留、プロフィール特性、フットプリントの蒸留、Reflexion のルール、persona-induction のブリッジです。同僚が AI 社員に明示的に覚えるよう頼んだ内容は保存されます。キーワードで判定するため、話題に触れた業務内容も除外されることがあります（例：「健康診断レポートのテンプレート」）。保存には管理者権限が必要です。このカードの変更はすぐに保存されます（「保存しました」と表示され、ゲートウェイが拒否した場合は元の状態に戻ってメッセージが表示されます）。ページ下部の「保存」ボタンの対象ではありません。社内の言い回しを足すには、カテゴリ内の「カスタムキーワード」を開き、入力して「追加」を押します。キーワード横の × で削除できます。`config.toml` で設定したカスタムカテゴリはそのまま保持されます。

### 自分の記憶（ログインしているすべてのユーザー）

**自分の記憶**（サイドバーの「設定」グループ、`/me/memory`。従業員はアカウントメニューから開きます）には、AI 社員がログイン中の本人について覚えている内容が一覧表示されます。各行に内容、AI 社員、時刻、ソースのタグ（会話、覚えるよう依頼、その他）が表示されます。ソースや AI 社員で絞り込み、「さらに読み込む」で古い項目を表示し、覚えてほしくない内容を削除できます。確認後は、AI 社員がその内容を自動で覚え直すことはありません。あとで明示的に覚えるよう頼んだ場合は、あらためて記録されます。絞り込みは読み込み済みの項目が対象で、「N 件を表示中」は読み込み済みの件数です。

カスタムカテゴリと追加キーワードは、詳細設定エディターの `[memory_privacy.custom_keywords]` で設定し（例：`legal_dispute = ["訴訟", "lawsuit"]`）、`excluded_categories` に加えます。未知のカテゴリ名は保存時に拒否されます。`config.toml` が読めない、またはセクションが無効な場合、ゲートウェイは既定の 4 カテゴリを適用して警告を記録し、`system.config` は `memory_privacy.load_state = "failed_closed"` を返します。詳細と「自分の記憶」RPC は[記憶インテリジェンス](../../features/ja-JP/20-memory-intelligence.md)の「自動記憶に保存しない個人的な話題」を参照してください。

## 設定 → 詳細 → セキュリティと記録 → 委任権限

管理者のみ（`delegation.get`／`delegation.set`）。保存すると次の委任判断から反映され、再起動は不要です。

RPC を直接呼び出す場合、対応する `delegation.get` または `google.drive_write.get` のスナップショットを読み込んで内容を確認し、保存時にその `hash` を `expected_hash` に渡します（v1.86.0）。以下の `rpc` は認証済みの RPC クライアントです。この例では Drive の書き込みをすべて無効にするため、現在の設定を確認してから変更を選んでください。競合時は再読み込みして変更を確認し、無条件に再試行しないでください。`delegation.effective` の `configured_policy` は管理者だけに返し、他の閲覧者にはキー自体を含めません。管理者専用の `delegation.get` は引き続き元の値を返します。

```javascript
const delegation = await rpc('delegation.get', {});
await rpc('delegation.set', {
  policy: 'hierarchy', allow: [], expected_hash: delegation.hash,
});

const drive = await rpc('google.drive_write.get', {});
await rpc('google.drive_write.set', {
  create: false, modify: false, move: false, trash: false,
  approval: { create: 'member', modify: 'member', move: 'member', trash: 'member' },
  folders: [], acknowledge_risk: false, expected_hash: drive.hash,
});
```

| コントロール | 設定キー | 反映 |
|---|---|---|
| 委任モード → 部門モード（既定）／階層モード／オープンモード／委任しない（v1.82） | `config.toml [delegation] policy` = `department`／`hierarchy`／`open`／`none` | 次の委任 |
| 部門をまたぐ協働 → ペア | `[delegation] allow = [["a", "b"], …]` | 次の委任 |

**委任しない（`none`、v1.82.0）。** 以下の v1.86.0 のロールによる例外が適用されない場合、 AI 社員どうしで委任、メッセージ送信、呼び出し、社員の作成、仕事の割り当てはできません。`send_to_agent`、`spawn_agent`、`spawn_ephemeral`、`create_agent`、他の社員を指定した `tasks_create`／`create_task`、タスクの付け替え、他の社員向けの予約、作業キューのディスパッチゲートがすべて拒否します。最初の 4 つのツールは社員のツール一覧に表示されません。`tasks_create`、`create_task` は社員自身の仕事のために表示されたままです。部門をまたぐペアは保存されたまま適用されません（ページに表示されます）。人と設定したスケジュール（ダッシュボード、cron、heartbeat、ゴールループ）は引き続き社員に仕事を渡せます。チームモード（1 人の社員の計画・実行・確認の役割が同じラウンド内でタスクパケットを受け渡す流れ）はそのまま動きます。

**委任範囲の制限を受けないロール（v1.86.0）。** 管理者・マネージャーを選べます。既定ではすべて未選択です。管理者がメンバー管理で本人に割り当てた AI アバターは、本人がその会話で直接依頼した場合に、任意の AI 社員に委任し、誰に対してもタスク・スケジュール・リマインダーを作成できます。受け手に逆方向の委任権限は与えません。アカウントの状態とロールは毎回確認します。この例外は、本人がその会話で直接依頼している間だけ適用されます。その AI のスケジュール、リマインダー、その他のバックグラウンド処理には、保護モードを含むすべてのモードで通常の委任ルールが適用されます。

対象は管理者とマネージャー（`admin`／`manager`）だけです。一般メンバーを選択すると、すべての一般メンバーの AI 分身が委任範囲の制限を受けなくなるため、この選択肢は提供しません。既存の `unrestricted_roles` にある `employee` は無視されます。役割を追加する際は、リスクの説明を読み「理解しました」を選択してから保存します。`delegation.set` と設定ファイルエディターの `config.raw.set` も、追加時に `acknowledge_risk: true` を要求します。`delegation_config_changed` 監査ログには、追加した役割（`roles_added`）、有効化したユーザー ID（`acknowledged_by`）、サーバーが生成した RFC3339 の日時（`acknowledged_at`）が記録されます。役割の削除にはリスク確認は不要ですが、監査ログは残ります。

例外は「委任しない」でも有効で、ロールを選ぶと警告を表示します。このモードでは双方向・一方向ペアとも無効です。自分への委任、別の所有者の個人社員、管理者以外の依頼に対するメインエージェントの境界、マシン社員、通信許可がオフの社員への制限は残ります。人間の依頼者の確認も引き続き必要です。判定順はこれらの境界、ロールによる例外、ペア、委任モードです。

**部門横断ペア。** 各行で双方向または一方向 A → B を選び、入れ替えボタンで方向を反転できます。既存のペアは双方向のままです。一方向は A → B だけを許可し、B → A の権限を与えません。ほかの適用ルールで逆方向が許可される場合はあります。

**保存と拒否の説明。** 委任設定を保存すると、その設定に紐付く承認待ちカードが失効し、有効なワークフローは次の実行まで一時停止します。拒否時には AI と利用者に、適用中のルール、このペアを拒否した理由、次にできることを一貫した説明で返します。

ダッシュボードで人が作成したスケジュール・タスク・スキル、および webhook・タイマー・自動化ルールはオペレーターの指示であり、AI 社員間の委任範囲の制限を受けません。

**認識できない値は委任しない扱い（v1.82.0 の動作変更）。** `policy` が 4 つの値以外（入力ミス、数値）、`[delegation]` がセクションでない、または `config.toml` が存在するのに読めない・形式が誤っている場合は、すべて `none` として扱います。v1.82.0 より前はより広い `department` になっていました。ゲートウェイはプロセスごとに 1 回だけ警告を記録します。ページの警告欄に表示され、`delegation.get` は元の値を `configured_policy` として返します。ファイルを解析できない場合、`delegation.get` と `delegation.set` はエラーを返し、何も書き込みません。設定ファイルの詳細編集で修正してください。

**読み込み失敗で設定が上書きされない（v1.82.0）。** 現在の設定を読み込めない場合、ページはエラーを表示し、「もう一度試す」が成功するまですべての選択肢と「保存」を無効にします。読み込んでいない内容は送信しません。

**警告ペイロード（v1.86.0 RPC 契約）。** `delegation.get.warnings` は `{code, message}` オブジェクトの配列です。メッセージに設定内容や社員識別子は含まれません。コードは `section_invalid`、`policy_unknown`、`policy_not_string`、`allow_not_list`、`allow_pair_invalid`、`allow_pair_same_agent`、`allow_one_way_not_list`、`allow_one_way_pair_invalid`、`allow_one_way_pair_same_agent`、`allow_one_way_limit`、`exempt_roles_unknown` です。ペアに関するメッセージには 1 から始まる位置が含まれる場合があります。`delegation.effective {agent_id}` は同じポリシー分類を `policy_warning: null | {code, message}` で返します。`allow_warning_count` は従来どおりで、詳細な `allow_warnings` と `config_error_detail` は管理者だけが参照できます。

**AI 社員ページ → 概要 → 委任範囲（v1.82.0）。** 読み取り専用のカードで、その社員に実際に適用される内容を表示します。有効な委任モード、全社設定によるものか社員自身の「エージェント間通信を許可」スイッチによるものか（`[permissions] can_send_cross_agent = false` でその社員は `none` 扱い）、社員や一時アシスタントを作成できるか、その社員を含むペア（現在のモードで適用されないものは別に表示）、設定の問題です。管理者と、その社員を閲覧できるマネージャーに表示されます（`delegation.effective {agent_id}`、読み取り専用）。誤りのため無視されたペア設定がある場合、カードには件数だけが表示されます（「委任設定に N 件の警告があります。管理者が「設定」で確認できます。」）。変更はこのページか社員の編集ページで行います。

カードにはロールによる例外と、一方向ペアの送信先・受信元も表示します。各依頼では現在のアカウントと仕事の開始元を確認します。

`delegation.effective {agent_id}` は担当者の `owner_display_name` も返します。取得できない場合は `null` です。カードには内部のアカウント識別子ではなく、この名前を表示します。

**管理者 AI。** 有効化する場所は **設定 → 詳細設定 → 委任権限 → 管理者 AI（最下部）** です。`admin_ai.get {}` は `config_state: "ok" | "unreadable" | "malformed"` を返し、`ok` 以外では `enabled` は `false` です。`enabled_ack` がある場合、`by_name`（`null` 可）と `at` で有効にした人と日時を表示できます。[管理者 AI による設定変更](../../features/ja-JP/79-admin-ai-settings.md)を参照してください。

## チャネル管理

- グループの「メンションのみ」（`mention_only`、グループごと）：v1.76 から、LINE グループでオンにすると、`@` で AI スタッフを呼ぶメッセージ（または @ 一覧の要求）と、呼ばれたスタッフが待っている 1 件にだけ返信します。以前はグループ全体が無反応になっていました。Telegram の共有 bot もスタッフ名を受け付けます。[@ で AI スタッフを呼び出す](../../features/ja-JP/62-calling-ai-staff.md)を参照。
- Web サイト用チャットウィジェット：公開の切り替えは `[webchat] public_widget`、ウィジェットキーは `[webchat] widget_key` に書き込みます（可視 ASCII 16〜256 文字、生成ボタンあり。公開するにはキーが必要。キーは応答に含まれません）。即時反映。ウィジェットキーは `config.toml` に平文で保存されます。Web サイトのページソースに現れる公開キーなので、シークレットとしては扱いません。**公開する前に、応答を担当する AI 社員を確認してください。** 訪問者のメッセージはその社員が処理し、使えるツールはその社員自身のツールと権限の設定で決まります。相手が訪問者であることを理由に、システムがその社員のコマンド実行やファイル操作のツールを追加で制限することはありません（ナレッジと会社アカウントの利用には訪問者向けの制限が別にあります）。外部に公開する社員には、コマンド実行（Bash）やファイル書き込みなど不要なツールを許可しないでください。
- WhatsApp、Feishu、Google Chat、Teams、WeCom、DingTalk：6 つの webhook ルートは常にマウントされています。チャネルが設定されるまでは 404 を返し、設定後はプラットフォームの署名を検証して、署名が不正なら 401 を返します。`channels.add` は再起動なしでチャネルを起動します。`channels.add` は `hot_started` と `restart_required: false` を返し、認証情報が足りないときは `not_started_reason` を付けます。従業員ごとの Slack bot も追加時に起動します。
- メッセージングアプリでの思考表示（専用の設定項目はなく、設定ファイルの詳細編集で設定。返信ごとに読み直します）：`[thinking] channel_audience` = `internal`（既定：チャネル ID が検証済みで、有効な dashboard アカウントが管理者または回答する社員に紐付いている送信者はタイマーと伏せ字化した要約、それ以外はタイマーのみ）、`all`（1 対 1 チャットのすべての送信者が要約を見られる）、`none`（何も表示しない）。`[thinking] channel_group_display` = `status`（既定：グループチャットはタイマーのみ）、`summary`、`off`。`[thinking] display` と回答する社員の `[model] show_thinking` のうち厳しい方が、引き続き両方の上限になります。`config.toml` が読めない、または不明な値のときは何も表示しません。Web サイトの訪問者（Odoo ライブチャット、WebChat ウィジェット）には思考は表示されません。詳しくは[メッセージングアプリでの思考表示](../../features/ja-JP/66-thinking-in-messaging-apps.md)。

### WebChat プロトコルと並行ターン

`/ws/chat` は既存の `auth` と `user_message` フレームを使います。1 本の接続でも異なる session は並行実行でき、同じ session のメッセージは受信順に実行します。複数の接続から送った場合も同じです。session の所有者と社員へのアクセス権は引き続き確認します。ユーザーごとと gateway 全体の上限は設定ファイルの詳細編集で指定します。

```toml
[webchat]
max_in_flight_turns = 3
max_global_turns = 10
```

`max_in_flight_turns` はユーザーごとに既定 **3**、`max_global_turns` は gateway 全体で既定 **10** です。どちらも **1～64** を指定でき、実行中・待機中・接続終了後も継続するターンを数えます。ユーザー上限は全接続で共有し、どちらかを超えたメッセージには直ちに `error`／`turn_limit` を返します。値が不正、または設定を読み取れない場合は新しいターンを拒否します。接続数の上限は別で、認証前は IP ごとに 3 本、dashboard JWT 認証後はユーザーごとに 3 本、全体で 10 本です。Widget 訪問者は接続中ずっと IP ごとの 3 本の枠を使います。再接続して新しい訪問者 ID を得ても、gateway 全体のターン上限は迂回できません。

新しいターンでは、まずメモリー内のユーザー別・全体の枠を原子的に確保し、共有 broker を使って blocking pool で永続化されたキャンセル枠を確認します。拒否時は枠を解放し、受け付けたターンだけが会話の FIFO に入ります。ログイン済みアカウントごと、Widget 訪問者は接続元 IP ごとに、直近 1 時間の開始済みターンのキャンセル記録が **100 件**に達すると拒否します。同じ NAT の訪問者は枠を共有し、制限は最後に数えたキャンセルから最大 1 時間で解除されます。再接続や再起動ではリセットされません。対象アカウントまたは IP だけを制限し、全体のフェンス件数で新しいターンを拒否しません。旧版の NULL principal はどの枠にも数えません。枠の超過や記録の読み取り失敗には `turn_limit` と拒否したメッセージの `request_id` を返します。受け付け済みのターンは引き続きキャンセルでき、未開始の待機ターンはフェンスを作らず、この枠にも数えません。

ログイン状態を一時的に確認できない（`Unavailable`）場合、接続がまだ送信可能なら終端 `error`／`identity_unavailable` を返します。`msg_id`、`request_id`、`conv`、`session_id` と固定の案内文のみを含み、返信・思考・添付・session の照会結果は含みません。受付前はメッセージが送信されなかったこと、配信時は返信を配信できなかったことを案内します。元のターンの認証情報を確認できない場合は、writer の最終確認も含めて配信拒否とロールバックを維持します。受信側の接続だけが失効した場合は、その接続を飛ばして履歴を残します。失効した接続にはこの通知を送らず、接続を閉じます。

最後がユーザーメッセージの会話を開き直すと未返信の案内を表示し、最初の 2 分間は 5 秒ごと、その後は 30 秒ごとに履歴を読み直します。上限は 30 分です。同じ session の完了フレームでは直ちに読み直します。会話から離れた時、画面を閉じた時、新しいターンを開始した時、返信が見つかった時にポーリングを停止し、下書きは変更しません。期限後は再送または管理者へのログ確認を案内します。送信後、再接続を含めて 60 秒間ターンの動きがない場合は、毎分更新の穏やかな待機案内を表示します。keepalive は活動として数えません。別の会話の失敗は固定通知のみで、現在のターンを終了しません。失敗文は会話履歴に保存されません。

クライアントの読み取りが遅い場合、進捗・思考・ステップ更新は最新の待機中の更新にまとめます。思考文字の拒否通知は制御フレームとして保持し、終端より先に表示済みの文字を消します。1 ターンで表示する思考ブロックは最大 64 個です。終端には容量を予約した別の有界キューを使い、同じターンの先行制御フレームは終端より先に送ります。書き込み前に期限切れになったフレームはそのターンだけを未配信とし、writer は継続します。socket の書き込み失敗時は閉じます。終端の `progress_dropped` で省略数を知らせます。返信は履歴への保存を確認してから現在の接続へ送ります。送信のタイムアウト、writer の終了、確認応答の欠落だけでは履歴とアーカイブを取り消しません。実際のソース失効、ターンのキャンセル、元の認証情報の失効では配信拒否とロールバックを維持します。

認証後に `{"type":"subscribe","session_id":"<所有する session>","conv":"<ローカル会話 ID>"}` を送ると、新しい接続で完了した返信を受信できます。既存の再開時の所有権・社員アクセス検査を使います。`session_id: null` は購読を解除し、購読の切り替えはキュー内の古い配信も無効にします。同一の認証ユーザーで、同一 session を購読する接続だけに送信します。Widget の身分は接続ごとに変わり、別の訪問者の session は再開できません。メッセージ送信は自動的に購読します。旧クライアントの購読は最大 64 会話で、超過時は最古の購読を外します。履歴は残ります。

ユーザー行にはクライアントの `msg_id` を `client_msg_id` として保存します。保存後の `turn_accepted` は `user_row_id`、実際の `session_id`、`conv`、`msg_id` を返します。復元では session と `user` ロールの完全一致を確認し、確認済みの行 ID を照合します。確認応答が失われた場合は、返された履歴内で保存したクライアントメッセージ ID に一致するユーザー行が一つだけであることを要求します。複数ある場合は自動復元しません。添付のみや同じ文章でも本文や前方一致で推測せず、一致する行がなければローカルのメッセージを保持します。再接続には `@` ルーティングを含め、サーバーが返した session ID を使います。ルーティング後の session ID が一度も届かず、既知の会話から確定できない場合、その会話は自動復元できません。`@` の宛先を推測しません。所有する受付済みターンは履歴行の作成前でも購読でき、拒否は `subscription_unavailable` を返します。ローカルの会話表示は消さないでください。

socket が書き込み可能になってから、writer は実際に回答した AI 社員へのアクセス権を再確認します。続いて短い `BEGIN IMMEDIATE` トランザクション内で ACL の世代を確認し、同期的に `start_send` を呼び、権限変更とフレームの受け渡しを順序付けます。トランザクション中に接続の準備や非同期 flush を待ちません。先に配信を認めたデータは、後の失効で取り戻せません。アシスタント行は確認待ちの非表示マーカー付きで保存し、最後の権限・ソース検査を通過してから公開します。配信を拒否した行は本文の消去に失敗しても、後で権限を戻しても履歴に表示しません。通信の失敗だけでは認可済みの返信を取り消しません。バックエンドのコンパイル、ネイティブ環境、実際の socket による検証は未完了であり、この変更自体は検証成功の証拠ではありません。

明示的なログアウトやアカウント変更では、チャット接続を閉じる前に `{"type":"logout"}` を送ります。受信すると、その接続が開始したターンと、同じ session・元の `conv` で再開した進行中・配信待ちのターンを取り消します。他のタブは別の `conv` を使うため影響しません。通常の切断では送りません。すでに通信が失われている場合、この通知は届きませんが、認証情報と会話の所有権の検査は維持されます。

WebChat と dashboard RPC は従来から 30 秒ごとに protocol ping を送り、pong を生存確認として扱います。60 秒以上応答がないと心拍確認時に切断します。ブラウザーの protocol pong は JavaScript のタイマーに依存しませんが、OS のスリープで通信が止まる場合はあります。タブが前面に戻ると直ちに再接続して現在の会話を購読し、履歴を再読込します。保存済みの返信があれば待機表示を終了し、未返信なら既存の期限付き履歴ポーリングを使います。

WebChat は再接続後も元の会話とサーバー側セッションを保持し、次のメッセージも同じ会話を続けます。空の新規会話は新しい接続のセッションを使います。入力欄の横には画面サイズを問わず接続中・再接続中・切断状態が表示されます。送信できなかった場合は通知し、入力した文章と添付ファイルを入力欄に残します。切断された返信が 10 秒以内に再開しない場合は待機表示を止め、AI がまだ処理中の可能性を案内します。後から届く返信や履歴からの復元は引き続き受け付け、サーバーの処理を取り消したり自動再送したりはしません。自動再試行が停止した場合は「再接続」を押してください。オンラインへの復帰、タブの前面表示、ブラウザーの戻る・進むキャッシュからの復元でも試行回数をリセットして直ちに再接続します。

既存のフレームのフィールドは変更しません。ターンのフレームに `session_id`、`conv`、`msg_id` を追加し、進捗・返信・エラーを送信元のターンに対応付けられます。各 `user_message` には一意の `msg_id` を付けてください。session でターンを指定する場合は、サーバーが返した session id を使います。

```json
{"type":"user_message","content":"こんにちは","conv":"c1","msg_id":"m1"}
{"type":"cancel","conv":"c1","msg_id":"m1"}
```

コマンドは実行開始後にキャンセルできません。キャンセルには `session_id` または `conv` が必要です。`msg_id` を省略すると実行中のターンを選びます。会話を一意に特定できない場合、他のユーザーの session、存在しないターン、キャンセル受付済みのターン、返信の配信を開始したターンには `turn_not_found` を返し、何もキャンセルしません。制御要求への応答には対象ターンの `msg_id` と別の `request_id` を使います。`turn_not_found` と `duplicate_message` は対象ターンの終了を意味しません。`turn_limit` は拒否したメッセージを `request_id` で示します。

キャンセルを送った接続には `request_id` 付きの `cancel_accepted` をベストエフォートで返します。終端との到着順序は保証しません。最終結果はターンの元の接続へ、同じキャンセル要求の `request_id` を持つ `error`／`cancelled` として送ります。記録や承認の後処理に失敗した場合は `cancel_failed` です。クライアントはどちらのフレームが先に届いても要求を対応付けられます。待機中のメッセージの後処理は先行ターンの終了後に完了します。キャンセル前に承認済みのカードがあれば、`cancelled` の `approved_before_cancel` にその id を列挙します。先に許可された操作は実行済みの場合があります。

キャンセルはターンの CLI プロセスグループを停止します。既存の session にだけ内部のキャンセル記録を保存し、会話履歴と圧縮要約には含めません。未開始の待機ターンをキャンセルしても session を新しく作りません。そのターンの未決定の承認は、キャンセルのフェンスと同じトランザクションで取り下げます（`decided_by = system:cancel:webchat_turn`）。フェンスはキャンセル時刻から固定 24 時間保存し、承認の TTL では延長しません。ターン由来の承認に対する 30 日の TTL 上限も撤去します。gateway lock を保持するプロセスが既存の毎時メンテナンスループで削除します。ダッシュボードの操作に依存せず、1 回最大 1,000 件を削除し、100,000 件を超える場合は 1 時間より古い記録を古い順に削除して警告を残します。1 時間未満の記録は削除しないため、一時的に上限を超える場合があります。ターン受付時には migration やスイープを実行しません。フェンスは停止と競合する遅延承認の挿入と、委任キューに遅れて追加された仕事の実行を防ぎます。`setsid` でプロセスグループから逃れたプロセスは、この非サンドボックスの保証対象外です。会話のキャンセル記録は session の保存期間と 90 日の短い方まで、session ごとに最大 1,000 件を保存し、session の完全削除時に一緒に削除します。完了済みの操作や作成済みのタスクは元に戻しません。外部送信ガードも迂回しません。未送信または終了確認済みの送信は通常どおり保護を解除しますが、結果未確認の送信や、停止した MCP プロセスが解除できなかった保護は、既存の規則に従って最大 6 時間維持します。

キャンセルは、同じ session とターンに属し、委任キューで待機中の仕事も停止します。`cancelled` の `delegations_cancelled` にその件数を含め、委任キューの後処理に失敗した場合は `cancel_failed` を返します。同じ出所の委任実行がまだ動いている場合、同じ `type: error, code: cancelled` フレームに `downstream_running` と一回限りの不透明な `downstream_ref` を追加します。対象がなければ両フィールドを省略します。クライアントには件数のみを渡し、スタッフ名、作業内容、メッセージ ID は渡しません。

認証済みクライアントは続けて `{"type":"cancel_downstream","downstream_ref":"<参照値>","request_id":"<省略可能な ID>"}` を送れます。ゲートウェイは現在の資格情報を再確認し、停止をバックグラウンドで処理します。最大 15 秒待ち、`type: downstream_stopped` と `request_id`、`stopped`、`still_stopping` を返します。停止処理中の作業を停止済みには数えません。参照値は元のユーザーと主体に結び付けられ、10 分で失効します。ゲートウェイの再起動や保存上限による古い項目の削除でも失われます。未知、他人のもの、期限切れ、使用済みの参照値はすべて `downstream_ref_unknown` を返し、作業を停止しません。資格情報の照会失敗は再試行可能な `credential_check_unavailable`、失効済み資格情報は拒否となります。Widget の訪問者には質問を返さず、`cancel_downstream` も拒否します。資格情報の失効によって元のターンを取り消した場合は質問せず、出所を追跡できる委任実行の停止を自動的に要求します。

フレームを送らなければ実行中の委任作業を続行し、拒否用フレームはありません。既存のキャンセルフェンスが有効な間は、その実行から新たに委任したり承認を作成したりできません。停止対象は元の会話とターンが一致するものだけで、他の人に帰属する作業は除外します。実行済みの外部操作は取り消せません。ターンが作成したタスクボードのタスクや目標は追跡せず、出所情報を失った実行も見つけられません。割り当て上限の確認中で FIFO に入る前のターンはキャンセルできず、`turn_not_found` を返します。[ターミナルのコントロールルーム](tui.md#チャットと入力フォーカス)では一覧フォーカスで質問に回答できます。

環境変数から継承する承認の出所は署名されていません。制限のない Bash を持つ社員はこれらの変数を偽装できます。Bash のガードは迂回を難しくするだけで、隔離ではありません。実際の隔離が必要な場合は Bash を許可しないか、タスクサンドボックスを使ってください。

接続を閉じても、受け付けたターンは**キャンセルされません**。待機中のメッセージも完了まで実行します。ログイン済みのダッシュボードユーザーは再接続して自分の session を再開したり、実行中のターンをキャンセルできます。Widget の訪問者は再接続時に新しい ID を取得するため、以前の接続のターンを再開・キャンセルできません。そのターンも全体の上限に数えます。ダッシュボードには待機中の各メッセージのキャンセルボタンと、現在の返信の停止ボタンがあります。対応クライアントは `cancel` を直接送信することもできます。


## 連携 → Odoo → 接続設定

「社内ネットワーク上の Odoo への接続を許可」は `[odoo] allow_private_network` に書き込まれます（管理者のみ、既定はオフ。接続設定と一緒に `odoo.configure` で保存され、「接続テスト」は画面上のスイッチ値を使います）。オフの間は、Odoo の URL（全体でも従業員ごとでも）は公開ホストへの HTTPS が必須です（`http://` は `localhost` のみ）。オンにすると 192.168.x.x や 10.x.x.x などの社内アドレスに HTTPS・HTTP のどちらでも接続できます。ローカルマシン、リンクローカル、クラウドのメタデータアドレス（169.254.169.254、`metadata.google.internal`）は常に拒否され、接続は検査済みの解決結果に固定され、プロキシは使いません。アップグレード後の初回起動で、設定済みの Odoo URL が社内アドレスに解決される場合は自動でオンになり（監査イベント `odoo_allow_private_network_auto_enabled`）、既存の環境は切断されません。次回の接続から有効です。

## 連携 → Odoo → 構造スナップショット

「**Odoo の構造を再スキャン**」は `odoo.schema_scan` を呼び出し、管理者だけが利用できます。RPC も同じロールを検査します。先に接続設定を保存してください。保存済みの全体接続と各社員の有効な設定をスキャンします。未保存のフォーム値は使いません。画面には最終スキャン時刻、取得時のサーバーバージョン、モデル／フィールド数、打ち切り、直近の失敗、差分の要約を表示します。バージョンが異なると再スキャンを勧めます。Odoo データ、権限、共有 Wiki は変更しません。 手動スキャンは失敗も含め保存済み profile ごとに 60 秒に 1 回まで。再起動でも保持し、再試行までの秒数を返します。 2 つの dashboard 操作（`odoo.schema_scan`、`odoo.discover_schema`）はこの制限とスキャンロックを共有します。Wiki への書き込み前に識別子とラベルを検査し、外部メタデータは指示ではなく参照データであると明示します。技術名、型、関連先は保持します。

再スキャンは保存済みの全体接続と、会社範囲を含む各社員の有効な `[odoo]` 設定を対象にします。同じ認証済み接続はまとめて処理し、同時スキャンは最大 2 接続です。画面に社員ごとの準備完了または失敗理由を表示します。異なる Odoo ユーザーのスナップショットは共有しません。2 つの dashboard 操作は永続化された 60 秒の手動クールダウンを共有します。準備成功後、すべての有効な接続を確認できた場合だけ古いデータを削除します。一覧のロックを保持して待機中のロックファイルを削除し、実行中のスキャンとロックは保持します。

実行インスタンスのロックを保持する gateway が起動時から 30 分ごとにすべての有効な接続を確認します。スナップショットの欠落・打ち切り、サーバーバージョンの変更、インストール済みモジュール名／バージョンの変更、権限情報の欠落があればバックグラウンドでスキャンします。成功または確定した失敗の完了後に、1 時間に 1 回の自動スキャン枠を記録します。中断は枠を消費せず、MCP の会話プロセスはスキャンを起動しません。準備中は `odoo_schema_fields` で個別のモデルを確認できます。バージョンとモジュール一覧が変わらないフィールドだけの変更には手動スキャンが必要です。接続中の社員は `odoo_connect` でフィールドキャッシュを更新できます。

絞り込みのない概要はモデル名と短いラベルだけを返し、上限は 16 KiB です。特定の `model`、または許可されたモデルが最大 5 件の検索に限りフィールドを返し、上限は 32 KiB です。一致したモデルの総数と打ち切りを表示します。共有 Wiki の要約は 16 KiB、`odoo/schema-fields` は検索用の `deep` 参照ページとして 32 KiB に制限し、社員のコンテキストには自動挿入しません。

## 連携 → Odoo → 従業員の権限

従業員の編集ページで許可するテーブルを選び、操作ルールを追加します。テーブルが未選択なら追加のテーブル制限なし、操作ルールがなければ追加の操作制限なしです。Odoo 自体の ACL、機能スイッチ、組み込みの機密テーブルのブロックは引き続き有効です。各ルールでテーブル（または「すべてのテーブル」）と操作を選択します。「検索と読み取り」は `read` と `search` の両方を保存し、「作成」「更新」「削除」「ボタン操作」「その他のメソッド」はそれぞれ `create`・`write`・`unlink`・`action`・`execute` を保存します。汎用 `odoo_execute` 呼び出しでは、ボタン操作は確認・検証・アーカイブなどの `action_*`・`button_*`・`toggle_*` メソッドに対応します。全テーブルには `action`、個別テーブルには `action:sale.order` を指定し、それ以外のメソッドは引き続き `execute` を使います。保存形式は従来どおり、全テーブルには動詞のみ、個別テーブルには `verb:model`（例：`read:hr.employee`、`search:hr.employee`）です。

`hr.employee` など「機密」表示のあるテーブルは機密情報を含むため、選択時に確認が必要です。テーブル一覧または操作ルールで選択して確認すると、その従業員のブロック例外に自動追加されます。最後の使用箇所を削除すると例外も削除されます。従業員用の独立した解除入力欄はありません。`ir.model`・`ir.model.fields`・`ir.attachment` は確認後も読み取り専用です。全体の Odoo ページも同じ確認付きのチェックボックスを使います。従業員の上書き設定がある場合、その例外一覧が全体設定を置き換えます。

選択肢は保存済みの全体接続の `odoo.schema_scan` スナップショットを使用します。管理者専用の `odoo.permission_options` RPC は接続認証後に既存キャッシュを読み取り（接続待ちは最大 10 秒）、テーブル名、ラベル、キャッシュ済みのアカウント権限を返します。`odoo.config` もサーバー側の機密・読み取り専用一覧を返します。編集ページではキャッシュを再利用します。初回接続で権限情報がなければ、バックグラウンドスキャンを予約します。未スキャンまたは接続失敗時はスキャンボタンを使えます。設定済みテーブルと機密テーブルは引き続き表示されます。別のデータベースを使う従業員も全体スキャンにない設定済みテーブル名を保持できます。

利用可能な操作は、接続した Odoo アカウント自身の読み取り・作成・更新・削除権限から取得し、接続時または構造スキャン時に確認して日時とともにキャッシュします。Odoo 側で権限を変更した場合は再スキャンしてください。ボタン操作とその他のメソッドは更新権限を目安とし、実際に実行できる操作とレコードルールは Odoo が判断します。権限のない操作は選択不可、不明な操作は注記付きで選択可能です。保存済みで利用不可になった操作は警告付きでチェックを保持し、チェックを外して削除できます。「すべてのテーブル」はテーブルごとに権限が異なるため選択を制限しません。DuDuClaw が読み取りを禁止したテーブルは照会しません。 操作の権限情報は保存済みの全体接続に基づきます。個別の接続、認証情報、会社範囲を使う従業員には、別アカウントの拒否結果を適用せず未確認と表示します。

既存ルールはテーブルごとにまとめます。`read` または `search` だけなら「検索と読み取り／一部のみ」と表示し、保存時に両方へ正規化します。既存の `action` ルールは編集可能な「ボタン操作」として表示します。不明な項目は読み取り専用の「その他の設定」に表示し、個別に削除するまでそのまま保持します。サーバーは既存の値の保持だけを許し、新しい不正なルールは拒否します。Odoo 一覧では「テーブル：操作、操作」と表示します。

`agents.update` の `odoo.allowed_actions` は `activity:<model>`、`note:<model>`、`message:<model>`、`attach:<model>` を受け付けます。この 4 操作の新しい項目には完全一致するモデル名が必要で、動詞だけの指定やワイルドカードは使えません。汎用設定書き込みは社員の Odoo 権限を広げる変更を拒否し、その社員の編集ページへ案内します。

個人 Odoo 接続は既定で無効で、`[odoo] member_credentials` が厳密に `true` の場合だけ有効です。無効時は保存済み個人認証情報を使わず、個人キーの要求は `odoo_member_credentials_off` を返します。アバターまたは `act_as_requester` 社員に利用可能な自己認証情報も許可済み会社認証情報もない場合、社員の認証経路も同じコードを返し、会社が個人 Odoo 接続を許可していないため管理者に連絡するよう案内します。有効時に接続がない場合は `odoo_not_connected` です。

## AI 社員の編集ページ

このページは `agents.update` でその社員の `agent.toml` に書き込み、変更した項目だけを送ります。そのため、保存してもハートビートのスケジュール（`[heartbeat] cron`）が消えることはなくなりました。

### スキル内容の予算

`[evolution] skill_budget_unlimited` の既定値は `false` で、既存ファイルにキーがない場合も同じです。管理者は社員の「スキル」設定で「スキル内容を無制限にする」を有効にできます。有効時は選択済みの Layer 2（全文）と Layer 1（要約）を `skill_token_budget` に関係なく含めます。レイヤー選択規則は変わりません。無効時の `skill_token_budget` は既定 2500 トークンで、0 は Layer 1/2 の内容を含めないことを意味します。Layer 0 の名前一覧には上限がありません。予算に収まらなかった選択済みスキルは一行の「Skills omitted for length」に最大 10 件の名前と「and N more」で表示します。従来の全文読み込み経路は `max(10_000, skill_token_budget * 4)` バイトを上限とし、以前の 10 KB より厳しくしません。無制限時は上限を適用せず、省略時の案内は社員設定を示します。無制限ではトークン費用と応答時間が増え、モデルのコンテキスト上限を超えると返信に失敗する場合があります。

| タブ → セクション | キー |
|---|---|
| 予算 → 1日の上限 | `[budget] daily_cap_cents` |
| 予算 → 費用データを取得できない場合 | `[budget] when_unavailable`（`allow` / `deny`） |
| スキル → この社員のスキル（v1.76.0） | 設定キーではない：オン／オフは `<home>/skill_state/<agent_id>.json`（`skills.set_enabled`）、削除したスキルは `<home>/skill_archive/<agent_id>/`（`skills.remove`／`skills.restore`）に移る。社員の担当者または管理者。[スキルライブラリ画面](../../features/ja-JP/15-skill-lifecycle.md)参照 |

**社員の予算。** `[budget] daily_cap_cents` と `monthly_limit_cents` は、それぞれ直近 24 時間と 30 日間の記録済み費用を比較し、`hard_stop = true` で上限に達すると次のモデル呼び出しを拒否します。0 は上限なしで、実行中の呼び出しは上限を超える場合があります。Claude とその他の社員ランタイム、委任・定期実行、リマインダー、メール、ハートビート、補助処理、CLI の fork／評価を対象とします。一時社員の記録済み費用も親社員に含め、ミリセントで合算してからセントに換算します。社員設定ファイルを読み取れる場合、`[budget] when_unavailable = "allow"`（省略時の既定値）は費用データベースや照会を利用できないときに警告と監査記録を残して続行し、`"deny"` はモデル呼び出し前に拒否します。設定ファイル自体の読み取りや解析に失敗すると方針を確認できないため、必ず拒否します。未知の方針の値は警告して `"deny"` として扱います。確認不能には独自の説明と監査イベントがあり、上限到達やブレーカーの状態変更として通知しません。予算による拒否はアカウントローテーションやフェイルオーバーを起こしません。社員 id のない呼び出しはこの方針の対象外です。 社員ディレクトリを指定した補助呼び出しは、処理名が渡されても有効設定の `[agent].name` で予算を確認し、今後の費用を記録します。過去に処理名のみで記録された費用を社員ごとに正確に割り当て直すことはできません。

1 回の実行時間の上限は、コンテナのタスクタイムアウトと別に保存します。サーバーは整数以外、または 30 秒からグローバル最大上限までの範囲外の値を拒否します。手動編集したファイルでは、範囲外の整数を境界に補正し、型が違う値には既定値を使い、どちらも警告を記録します。OpenAI 互換 API の社員は `utility` または `preferred` にモデルの指定が必要です。Codex は CLI の既定モデルも使えます。Grok、汎用 CLI はグローバルのバックグラウンド設定を使います。ユーティリティモデルとランタイムのベンダー系統が異なる場合、会話圧縮や事実抽出などのバックグラウンド処理が失敗する旨を画面に表示します。

`timeout_secs` の実効上限を増やすには管理者権限が必要です。Owner は上限を下げられます。設定を空にするとグローバル既定値（未設定ならすべてのランタイムで 1800 秒。Claude を含め、この既定値より低い値を設定していた社員では、空にすると引き上げになります）に戻り、現在の実効上限より増える場合は管理者が必要です。

Claude の補助呼び出しは CLI が使える認証情報で軽量パスを実行し、アカウントローテーションには入りません。通常の会話は既存のローテーションを維持します。

分類と評価を含む補助呼び出しは、専用の実行モードを使います。Claude はツールなしの単一ターンの軽量パス、OpenAI 互換 API はツールなしの単一 completion を使い、ツールループには入りません。Codex は制限モードで実行します：読み取り専用サンドボックス、プラットフォームの MCP 設定を追加しない、毎回新規作成する所有者だけがアクセスできる空の一時作業ディレクトリ、ユーザー設定の無視、セッション保存なし。一時ディレクトリはエラーやタイムアウトを含め呼び出し終了後に削除します。システムプロンプトは prompt 内で渡し、`AGENTS.md` は書きません。Codex を明示した judge とチーム verifier も同じモードです。Grok、汎用 CLI は補助実行に非対応のため、社員のバックグラウンド処理はグローバルの補助プロバイダー／モデル（既定 Claude／`claude-haiku-4-5`）を使い、社員とランタイムの組み合わせごとに一度警告します。グローバルでは Claude、Codex、OpenAI 互換 API が使えます。非対応のグローバルプロバイダーや明示指定は拒否します。上位の評価処理が非対応の指定なしで再試行する場合も同じモードを適用します。Codex には内蔵の読み取りツールが残る可能性があります。残るリスクは[セキュリティ防御](../../features/ja-JP/05-security-defense.md)を参照してください。

**管理者だけが変更できる項目。** `[agent] reports_to`、`department`、`name`、`[capabilities]` 全体、`[container] sandbox_enabled`、`network_access`、`readonly_project`、`[permissions]` の 5 つのフラグ（`can_modify_own_soul`、`can_create_agents`、`can_send_cross_agent`、`can_schedule_tasks`、`can_modify_own_skills`）と（v1.76.0）`[permissions] allowed_channels`、`[guardrails] enabled` と `block_secrets`、（v1.76）`[channels] public_trigger`、そして（v1.76.0）社員ごとの bot トークン `[channels.discord]`、`[channels.telegram]`、`[channels.slack]`、`[channels.googlechat]`、`[odoo]` 全体、`[runtime] provider` と `fallback`、`[prompt] cli_bare_mode`、`[os_watch]` 全体、`[model] account_pool`、`role = "main"` への変更とその解除、予算の緩和（`monthly_limit_cents` や `daily_cap_cents` の引き上げ、上限の撤廃（0 は上限なし）、`hard_stop` のオフ、スキル内容の無制限化（`[evolution] skill_budget_unlimited`）のオン、`when_unavailable` の `deny` から `allow` への変更）。社員のオーナーは上限の追加や引き下げ、`hard_stop` のオン、スキル内容の無制限化のオフは引き続き行えます。管理者以外からの変更は拒否され、管理者による変更が成功すると監査イベント `agent_authority_changed` が、拒否された試みには `agent_authority_refused` が記録されます。モデルの変更で実行環境が自動的に切り替わる場合、管理者以外にはその旨が表示されます。`org.toml` は `reports_to` か `department` が実際に変わったときだけ更新されます。`agents.inspect` は対応するフォーム項目を `admin_only_fields` として返し、編集ページは管理者以外に対してそれらを無効にします。

**保存できる人（v1.76.0、動作の変更）。** `agents.update` は保存のたびに呼び出し元のロールと社員への紐付けをアカウントデータベースから読み直し、書き込み直前にファイルロック内でもう一度確認します。紐付けの解除、アカウントの停止、パスワード変更の要求は、セッションの期限を待たず次の保存から有効です。どの経路からの `agent.toml` の書き込みも（このページ、チャットの `/model`、設定ファイルの詳細編集、自動の変更）コメントとキーの順序を保ち、版を残し（[設定ファイル](#設定ファイルv1760)を参照）、`agent_file_changed` を記録します。保存後に社員一覧を再読み込みできなかったときのメッセージは「已儲存，但暫時無法立即套用；請稍後重新整理，仍未生效請重新啟動服務」です（定期的な再読み込みはありません）。

**権限フラグが有効に（動作の変更）。** `can_create_agents`、`can_send_cross_agent`、`can_modify_own_skills`、`can_schedule_tasks` には以前は読み取り側がありませんでした。v1.68.0 からは `false` と書かれたフラグが、MCP のディスパッチゲートで対応するツールを止めます（`create_agent`。`send_to_agent`、`spawn_agent`。`create_reminder`、`schedule` 付きの `tasks_create`。`skill_hub_install`、`shared_skill_adopt`、`skill_graduate`、`skill_from_recording`）。未記載や型の誤りは許可扱いです。ただし `can_create_agents` は例外です。v1.81.0 から、このキーがない場合に `true` とみなすのは `main` 社員だけで、それ以外の社員は `false` です。v1.68 の起動時移行は main 以外の社員でこれをオンにしなくなり、MCP `create_agent` で作成された社員は常に `false` です（[セキュリティ防御](../../features/ja-JP/05-security-defense.md)を参照）。v1.82.0 から、このページのスイッチはゲートが実際に適用する値を表示します（`agents.inspect` の `effective_permissions`。MCP ゲートと同じ読み取り関数）。main 以外の社員で `can_create_agents` がない場合はオフ、`agent.toml` を読めない場合や、古い gateway が `effective_permissions` を返さない場合はすべてオフと表示されます（ファイルの値は使いません）。触れていないスイッチは保存時に送信されないため、変更していないフォームで権限が変わることはありません。古いテンプレートはこれらを `false` と書いていることが多いため、アップグレード後の最初の起動で全社員に一度だけ移行を行います。`permissions_enforced_since` の印がない `[permissions]` では、4 つのフラグのうち `false` のものを `true` に変え、`permissions_enforced_since = "1.68.0"` を追加し、リセットごとに監査イベント `permission_flags_reset` を記録します。その後このページや設定ファイルの詳細編集で書いた `false` はオペレーターの判断として扱われます。一時的な役割メンバー（`agents/.ephemeral/`）は移行の対象外で、最小権限のままです。

## 組織 → マイチーム（Enterprise 版、1.76.0）

ロールがマネージャーか管理者の人だけに表示されます（サイドバーの「組織」）。あなたに報告する人（最大 8 階層下まで。停止中の人は含み、退職者は含まない）と、各人を通じて呼び出せる AI スタッフを一覧にします。

- 「依頼できる」「会話のみ」のタグ：部下の紐付けが Owner か Operator なら Operator を得て仕事を依頼できます。Viewer なら会話のみです。
- 「進行中 N 件」：そのスタッフに割り当てられ、完了・取消・失敗していないタスクの数。
- **会話**：WebChat を開き、入力欄に `@名前 ` を入れた状態にします。スタッフが停止中のときは押せません。
- **新しい会話**：以前の依頼ボタンに代わり、新しい WebChat 会話を開きます。タスクは作成しません。

データは RPC `users.my_team` から取得し、毎回の呼び出しや依頼と同じ判断を使うので、一覧にあるものはすべて呼び出せます。Personal 版と一般社員のロールでは拒否されます。

## 連携 → ツールサーバー：MCP API キー（v1.82）

管理者のみ。キーは `<home>/mcp_keys.db` に保存され、保存されるのは各キーの SHA-256 指紋だけです。完全なキーは作成直後に一度だけ表示されます。このページの操作は `config.toml` に書き込みません。以下の変更はすべて操作者とともにセキュリティ監査ログ（`security_audit.jsonl`）に記録され、管理者以外の試行が拒否された場合も記録されます。

- **版：** 社員フォルダーの外の `<home>/agent_file_history/<社員>/<ファイル>/`（所有者のみ読み取り可）に、既定でファイルごとに 20 版（`[agent_files] history_keep`、5〜100）。最初の変更では変更前の内容も残します。版の復元にも同じチェックが走ります。社員を削除すると版は `agent_file_history/_trash/` に移り、同じ ID の新しい社員は版なしで始まります。
- **承認済みの基準：** SOUL.md、IDENTITY.md、USER.md、INSTRUCTIONS.md を保存すると承認済みの指紋が更新されます（INSTRUCTIONS.md にも指紋ができ、ハートビートが `_instructions_integrity_drift` として報告）。システム外で変更されたファイルは表示で分かり、承認済みの版に戻すか、確認して現在の内容を受け入れられます（そのまま保存すると全体をチェックし、理由を書いて確定するか審査を依頼します。確定してもファイルは書き換えず、現在の内容を版として残して承認済みの基準にします。システム外で変更されていないファイルをそのまま保存した場合は「変更なし」のままです）。社員の名前を変えると SOUL.md／IDENTITY.md 内の名前も更新され、承認済みの SOUL はそのまま承認済み、すでにシステム外で変更されていた SOUL は表示されたままです。名前はプレーンテキスト（1〜64 文字、改行・見えない文字・`< > [ ] { }`・バッククォートなし）で、名前を置き換えた結果が固定ルールに引っかかる場合は同期しません（`identity_files_skipped` に表示）。
- **審査依頼：** 種類 `agent_file_change`。現在も管理者である人がダッシュボードで判断します（[チャットアプリで承認](#セキュリティ--チャットアプリで承認v186)が有効なら、本人確認済みの管理者がチャットカードからも判断でき、既定でもう一度の確認が必要です）。期限は 3 日（期限切れは拒否扱い）。チャネルにはボタンのない通知だけが届きます。提案された内容は依頼が終わるまで `<home>/agent_file_pending/` に保存されます。承認時はまず適用し、待っている間にファイルが変わっていた場合は拒否され、依頼者が送り直す必要があります。
- **監査：** `agent_file_changed`、`agent_file_change_refused`、`agent_file_review_failed`、`agent_file_change_requested`（記録するのはハッシュだけで、内容は記録しません）。

### 作成後に社員のペルソナを変更する（v1.82.0）

作成時に渡したペルソナ（空白から作成するフォームの任意の「ペルソナ」欄、`agents.create` の `soul_md` フィールド、またはテンプレートの SOUL.md）は出発点にすぎません。v1.82.0 以降、ペルソナを渡した場合は必ず書き込まれ、書き込めなければ作成全体が失敗します。既定の一文に置き換わることはありません。あとから変えるには：

- **ダッシュボード：** 社員ページ →「設定ファイル」→「ペルソナ（`SOUL.md`）」→「編集」→「保存してチェック」。
- **RPC：** まず `agent_files.get {agent_id, file: "soul"}` で現在の `content` とその `hash` を取得し、次に `agent_files.save {agent_id, file: "soul", content, base_hash: <取得した hash>}` を呼びます。保存できるのはその社員のオーナーと管理者だけで、AI 社員自身が自分の SOUL.md を変えることはできません。
- **保存は審査を通り、そのまま適用されるわけではありません。** 上の「保存のたびのチェック」が走り、応答の `status` で結果が分かります：`applied`（社員の次の対話から有効）、`unchanged`、`needs_confirmation`（`action: "confirm"`、`review.analysis_id`、4 文字以上の `reason` を付けて送り直す）、`blocked`（管理者以外は `action: "request_approval"` で送り直すと `pending_approval` と `approval_id` が返り、管理者がダッシュボードで判断。管理者は `reason` と `acknowledge_risk: true` を付けたときだけ確定）、`conflict`（ほかの人が先に保存した：もう一度 `get` してから編集し直す）、`rejected`（固定ルールで拒否：内容を直す）。
- 適用された変更はすべて版として残るので、`agent_files.history`／`agent_files.rollback` で以前のペルソナに戻せます。

- **プロフィールの書き出し：** Manager と管理者は、閲覧可能な社員のメニューから書き出せます。DuDuClaw、OpenClaw、Hermes、AGENTS.md、Claude Code subagent に対応します。利用者紹介は初期状態では含まれず、明示的に選択します。OpenClaw／Hermes は各ファイルを同じフォルダーに保存してください。秘密情報、チャネル、能力、権限、アカウントプール、記憶は書き出しません。[Agent File リファレンス](../../spec/ja-JP/agent-file-spec.md)を参照してください。
- **利用者紹介：** 同じロック、版管理、レビュー経路で保存します。プロンプトでは `<user_profile>` データブロックとして扱い、指示ではないと明記し、人格と同じ入力検査を行います。一般の Markdown バイト制限より優先して最大 4,000 文字です。

## 予約して依頼する（v1.76.0）

チャットの依頼コマンドや RPC で単発または繰り返しの予約を作成でき、管理者は cron も使えます。dashboard の作成フォームは非表示です。設定時にはタスクを作成せず、予定時刻に作成者の権限を確認し直して依頼します。

## システム → システム更新（v1.76.2）

このページはインストール全体を一つの順序で更新します。デスクトップアプリが自分で起動していない gateway（launchd／systemd／Enterprise の gateway、またはリモートの gateway）に接続しているとき、ページには二つのコンポーネントが並びます。gateway の現在のバージョンと更新先、デスクトップアプリの現在のバージョンとダウンロード済みのバージョンです。ボタン一つで gateway を先に更新し、再起動を待ってからアプリを更新します。アプリは gateway のバージョンまでしか更新しません。より新しいアプリがダウンロード済みの場合は待機し、その理由をページに表示します。アプリが自分の gateway サイドカーを持つ場合は、これまでどおり両方を一緒に更新します。

より新しい gateway のバイナリがディスク上にあるのにまだ動いていない場合（npm インストール、手動の差し替え、再起動されなかった更新）、ボタンは「gateway を再起動して v… を適用」になり、`system.restart_pending_update`（管理者）を呼びます。gateway はディスク上のバージョンが実行中のものと本当に異なるときだけ受け付け、コンテナとデスクトップのサイドカーでは拒否します（それぞれの所有者が再起動します）。デスクトップアプリを再起動しても外部の gateway は再起動されません。

### macOS：DuDuClaw Gateway.app（v1.81.0）

macOS の gateway は署名済みのアプリ「DuDuClaw Gateway.app」（識別子 `ai.duduclaw.gateway`、コミュニティ版と Enterprise 版で共通）になりました。macOS はアプリのフォルダ、オートメーション、フルディスクアクセスの許可をアップデート後も保持するため、リリースごとに許可し直す必要はなく、一度だけで済みます。アプリのインストールは、リリースの署名済み `duduclaw-darwin-<arch>.app.zip` からのみ更新されます。入れ替える前に、gateway は署名が DuDuClaw の開発者のものか、インストール済みアプリの署名と合っているかを確認し、アプリの識別子・バージョン・エディションが署名済みリリースと一致することも確かめます。新しいアプリはアトミックに入れ替え、一度実行（`version`）して確認します。どれか一つでも通らなければ更新は行わず、インストール済みのアプリはそのまま残すか元に戻します。

単体バイナリ（スタンドアロンまたは npm）のまま動いている gateway は、次の三つの方法でアプリに移行できます。

- 自動更新がオンで、ログインサービス（launchd）から起動している場合、v1.81 の初回起動時に一度だけ自動で移行します。
- このページの「DuDuClaw Gateway.app に移行」（`system.migrate_bundle`、管理者）。
- ターミナルで `duduclaw service migrate-bundle` を実行し、続けて `duduclaw service restart` を実行します。

移行するとアプリは `~/Applications/`（npm の場合は npm のプラットフォームパッケージ内）にインストールされ、元のバイナリはアプリへのリンクに置き換わるので、今までのコマンドはそのまま使えます。ログインサービスもアプリを起動するように変わり、gateway はアプリから再起動します。その後、macOS が新しいアプリについてフォルダへのアクセスを一度だけ確認します。ページには移行後に一度だけこの案内が表示されます。

## 管理 → 詳細設定 → ライセンス：同期と AI 社員の枠（v1.84.0）

**再読み込み。** 管理者が**再読み込み**を押すと、開発元から現在のライセンスを取得し（RPC `license.sync`、管理者のみ）、ボタンの下に結果を表示します。表示される結果は、更新しました、最新の状態です、ライセンスは取り消されました、開発元によるマシン変更の承認待ち、商用ライセンス未インストール、このホストにライセンスファイルはあるが内容を読み取れない（ライセンスを再インポートするか、管理者にファイルの確認を依頼）、開発元に接続できない、今回の同期は完了しなかった、のいずれかです（最後の 2 つは自動的に再試行します）。同期の間隔は最低 30 秒で、ダッシュボードと自動チェックで共有します。間隔内に押すと、あと何秒待てばよいかを表示します。リクエスト自体が失敗した場合は、現在のライセンスを表示したままにします。マネージャーが押した場合は、画面の情報を読み込み直すだけです。

**枠数。** ページには「AI 社員の上限」（数値または「無制限」）と「使用中」（アーカイブした社員も含む）を表示します。値を確定できない行は表示せず、推測の数値は出しません。このページを開ける人（マネージャー以上）なら誰でも枠の情報を見られます。

**AI 分身は枠を消費しません。** 有効なメンバー本人が Owner として所有する検証済み Personal AI が１人１体だけ対象です。アーカイブした AI は枠を使います。`avatars_exempt` と `seats_used` は別表示です。[AI 分身とライセンス枠](user-management-and-first-login.md#ai-分身とライセンス枠)を参照してください。

**再起動の案内。** 管理者が**再読み込み**を押し、その同期でサービス起動時と異なるエディションになった場合、プランを完全に適用するには再起動が必要だという黄色の案内を表示します。AI 社員の枠数と有効期限はすぐに反映されます。

**変更が届くまで。** 同じデータディレクトリで `duduclaw license activate`、`import`、`refresh`、`deactivate` が書き込んだライセンスは、実行中のサービスが約 1 分以内に自動で適用し、再起動は不要です。`activate` と `refresh` はその旨を表示します。サービスは開発元にライセンスの変更有無も問い合わせます。起動後 2〜5 分で最初に確認し、その後は 25〜35 分ごとに確認して、開発元が変更を返したときだけライセンスをダウンロードして検証します。そのため、開発元側の変更（枠数など）は約 30 分以内に届きます。開発元のサービスがこの確認に対応していない場合は 1 日 1 回確認し直し、ライセンスはプラン本来の更新間隔（最長 7 日）で更新します。この確認を行うのはインスタンスロックを持つ実行中のゲートウェイだけで、ライセンスがインストールされている場合に限ります。定期同期で、別の同期が直前に失敗した、または開発元に接続できなかったと分かった場合は、約 1 時間後（55〜65 分）に再試行します。定期同期自身のリクエストが失敗した場合は、通常の更新間隔まで待ちます。起動時はライセンスファイルを最大 45 秒待ち、それを過ぎるとライセンスを読めない状態として起動し、読めるようになった時点で適用します。解析できないライセンスファイルは、15 分後、ファイルが変わったとき、同期のたびに読み直します。ライセンスファイルの操作は同時に 2 件までで、それ以外はファイルが使用中だと返します。

**ライセンスファイル。** `license.json` は通常ファイルを指すシンボリックリンク（マウントしたシークレットなど）でもかまいません。それ以外の特殊ファイルと 64 KiB を超えるファイルは拒否します。サービスやコマンドが新しいライセンスを保存するときは、リンク先に書き込まず、リンクを通常ファイルに置き換え、リンク先のファイルのバックアップも作りません。開発元からの応答は 256 KiB までです。

## 設定ファイルの詳細編集

場所：システム設定 → 詳細設定 → 設定ファイルの詳細編集。管理者だけに表示され、RPC は `config.raw.get` / `config.raw.set` です。

- **対象ファイル**：システム設定（`config.toml`）、推論設定（`inference.toml`）、各 AI 社員の `agent.toml`（`agents/` 配下の実ディレクトリで、シンボリックリンクは不可）。
- **シークレットの伏せ字**：キー名が `_enc` で終わる、`key` そのものか `_key` で終わる、token・secret・password・passwd・api_key・apikey・widget_key・private_key・credential・service_account_json を含む値、`headers`・`otlp_headers`・`env` テーブルのすべての値、パスワード付き URL は `«set»` と表示されます。`«set»` のまま保存すると元の値が保たれ、値がないのに `«set»` と書くと拒否されます。`[mcp_keys]` は表示されません（v1.82 以降、ここにあるのはゲートウェイ自身の内部キーだけで、ダッシュボードのキーは `mcp_keys.db` にあります）。
- **検証**：まず TOML 構文を確認し、エラーは行と列で示します。次に型の確認（`config.toml` は各セクションの検証、`InferenceConfig`、`AgentConfig`）を行い、失敗すると書き込みません。社員の `[agent] name` はここでは変更できません。
- **競合**：開いたときに内容のハッシュを受け取り、保存時に送り返します。その間にファイルが変わっていれば拒否されるので、再読み込みしてから編集してください。
- **バックアップ**：書き込み前に `<ファイル名>.bak-<Unix 時刻>`（権限 0600）へコピーし、新しい 5 つを残します。
- **監査**：書き込みごとに `config_raw_edited` を記録します。`[delegation]`、`[acp]`、または社員の `[agent]`、`[capabilities]`、`sandbox_enabled`、`network_access`、`can_modify_own_soul` に触れた場合は Warning です。
- **ドキュメントナレッジベース**：コレクション、資料、共有、閲覧記録はサイドバーの「会社 → ドキュメントライブラリ」で管理します。全体の上限 `[knowledge]` にはまだ設定ページがなく、各キー（`enabled`、`max_source_bytes`、`max_source_chars`、`max_sources_per_collection`、`max_collections`、`max_chunks_total`、`extract_timeout_secs`、`extract_memory_mb`、`access_log_retention_days`、`max_collection_bytes`、`max_total_bytes`、`extract_when_unavailable` = `refuse`／`run_unsandboxed`、`auto_retrieve`、`inject_budget_chars_max`）はここで型を検査します。`[knowledge.embedding]` の各キー（`provider` = `local`／`openai`／`gemini`／`none`、`local_model`、`cloud_model`、`cloud_account`、`cloud_base_url`、`allow_private_endpoint`、`batch_size`、`threads`、`max_vector_rows`、`idle_unload_minutes`）も同様です。開示の確認記録 `cloud_disclosure_ack` はここでは変更できず（保存は拒否されます）、「ナレッジベース検索」の開示ダイアログからのみ書き込まれます。社員の `[knowledge] collections` は「Agent 管理 → 設定を編集 → ツールと権限 → ドキュメントライブラリ」で設定します（共有されたコレクションだけ選べます）。その社員の `agent.toml` を直接編集することもできます。返信に関する `auto_retrieve`、`answer_mode` = `assist`／`kb_only`、`top_k`、`inject_budget_chars` もそこにあります。詳しくは[ドキュメントナレッジベース](../../features/ja-JP/63-knowledge-base.md)。
- **再起動の一覧**：保存後に再起動が必要な部分を表示します。`config.toml` の `[gateway]`、`[server]`、`[telemetry]`、`[logging]`、`[channels]`、`[wiki]`、`[relay]`、`[decision]` は起動時にだけ読まれます。`general.name`、`rotation.health_check_interval_seconds`、`goal_loop.resume_on_restart`、`knowledge.max_source_bytes`（アップロードルートのサイズ上限を決める）も再起動が必要です。ログレベル、常駐センシング、秘匿化はその場で反映できた場合は一覧に出ません。`inference.toml` の保存は常にその場で推論エンジンをリセットします。社員ファイルで再起動が必要なのは `heartbeat.max_concurrent_runs` だけです。

のみ許可し、グローバル IPv6 は拒否します。範囲内でも信頼できる
接続元とは限りません。メニューは指定の診断とモデル・ゲートウェイの
再起動に限定され、ゲートウェイの再起動で終了・切断します。

終了を確認できない場合は警告を表示し続けます。履歴には最近の
鍵の指紋と接続イベントを表示します。状態を 30 秒ごとに取得するため、
期限切れやデバイス側の終了表示は次の取得まで遅れる場合があります。
完全な OS イメージ、実際の SSH、通知配信はまだ検証していません。
メンテナンス用アカウントを含む OS イメージでのみ動作し、組み立てたデバイスの受け入れ完了を意味しません。

## セキュリティ → 認証情報の保護（v1.76.0）

「セキュリティ」ページの「認証情報の保護」カード（管理者、両エディション）は 1 行で
「認証情報の保護：ファイル」または「認証情報の保護：システムのキーチェーン（…）」と表示し、その意味を説明
します。対象は AI 社員が特定の人として動くための認証情報だけで、カードの表示に
かかわらずほかの設定はこれまでどおり動きます。

- **システムのキーチェーンへ移す**（`security.credential_protection_enable`）は
  macOS のキーチェーンまたは Windows 資格情報マネージャーに保護キーを作ります。
  通常の Docker や Linux のインストールでは「ファイル（ここでは個人アカウントを利用できません）」と表示され、ボタンはありません。
- **認証情報の保護を有効にする**：person-credentials オーバーレイで起動した Docker ではこのボタンが表示されます
  （[Docker ガイド](docker.md#74-個人アカウントperson-credentials-オーバーレイ)）。キーは起動時に gateway へ渡される独立したルートキーで、
  行の表示は「独立した鍵（AI 社員は読み取れません）」です。起動時の確認に失敗するとカードに理由（例：Docker ソケットのマウント）が表示され、
  ボタンはありません。このキーを持っている間、NER の匿名化、ローカルのナレッジベース埋め込み、Kokoro 音声は止まります。
  ここでの「キーを新しくする」はルートキーを交換しません。ルートキーの交換は Docker ガイドを参照してください。
- **再承認が必要**：macOS でアップグレード後やキーチェーンがロック中に表示されます。
  その Mac のターミナルで `duduclaw credentials authorize` を実行し、ダイアログを
  一度許可してください。
- **保護キーが見つからない／置き換えられた／設定エラー**：個人アカウントは停止します。
  **再度有効にする**（`reset: true`）と新しいキーが作られ、保存済みの個人の認証情報は
  無効になり、各自が再接続します。
- **キーを新しくする**（同じく `reset: true`）は問題がないときも表示され、キーと記録が
  一緒に置き換えられた疑いがあるときに使います。効果は再度有効にするのと同じです。
  hardened runtime のない macOS の実行ファイルでは、DuDuClaw に注入したコードがキーを
  読めるため「同じユーザーアカウントのプログラムは読み取り可能」と表示します。
- **無効にする**（`security.credential_protection_disable`、`confirm: true`、確認文字の
  入力が必要）はキーを削除し、保存済みの個人の認証情報は無効になります。

[保護されたネイティブ Linux サービス](linux-protected-service.md#エンジン制御ソケットの公開後に復旧する)では、カードに直近のルートキー失効、UTC 時刻、具体的なエンジンソケットの検出結果も表示します。公開中は個人アカウントを停止します。自動復旧は既定で有効で、60 秒間隔の検査が 3 回連続で成功すると通常の終了処理を経て再起動し、root ランチャーから鍵を再度受け取ります。復旧再起動は直近 1 時間に最大 4 回で、状態ファイルの読み書きに失敗すると復旧を止めます。今回はダッシュボードに切り替えボタンを追加しません。手動で再起動する場合は `config.toml` に `[credential_protection] auto_recover = false` を設定してください。

ターミナルでは `duduclaw credentials status`（スクリプト用に `--json`）で同じ状態を
確認できます。詳細は[セキュリティ防御](../../features/ja-JP/05-security-defense.md#特定の人の認証情報をシステムのキーチェーンに置くv1760)。

直接バインドの履歴プライバシー：`[people] bound_history_privacy = true` が既定で、欠落・不正値でも制限を維持します。移行時に Admin が詳細エディターで明示的に `false` を指定すると、従来の Viewer／Operator の広い履歴アクセスを復元できます。Owner／Admin とチャット・呼び出し権限は維持します。検索・エクスポート・添付・NER の制限は機能 68 を参照。

## セキュリティ → 送信データの保護（v1.77.0）

セキュリティページでは `config.toml [security] egress_guard` を 4 つの値から選べます：**オフ**（`off`）、**記録のみ**（`shadow`、既定）、**送信前に確認**（`ask`）、**送信をブロック**（`block`）。保存は既存のロック付き `system.update_config` で行い、呼び出しのたびにガードが設定を読みます。スタッフごとの `agent.toml [capabilities] egress_guard` は制限を強める方向にしか変えられません（`off < shadow < ask < block`）。`config.toml` がない場合は既定の「記録のみ」になり、設定が無効または読めない場合はその呼び出しをブロックします。

AI スタッフが同じターンで非公開データの読み取りに成功した後、送信系の呼び出しはガードを通ります。「記録のみ」は監査に `would_ask` と読み取ったツールを記録して実行を許可します。「送信前に確認」は宛先・展開した全文・読み取ったツール・有効期限を示す一回限りの承認を作成し、現在 Admin 権限を持つダッシュボードアカウントが承認できます。以下の条件を満たす `mail_send` の依頼者も一対一の会話または認証済みダッシュボード WebChat でのみ確認できます。「送信をブロック」は拒否します。対象はプラットフォームの MCP 呼び出しとサードパーティ MCP プロキシで、Claude CLI の組み込みツールや他のランタイムのネイティブツールは対象外です。追跡はターン単位です。詳しくは[送信データの保護](../../features/ja-JP/69-egress-guard.md)を参照してください。

この設定の下に Admin 専用の観測レポートがあります。7 日／30 日を選び、重複を除いた承認件数、スタッフ・ツール・情報源・日付別の内訳、CLI 組み込み／MCP 入口別の件数を確認できます。拒否の観測は承認件数を増やしません。記録がない場合や収集の失敗は安全の証明ではありません。`duduclaw doctor` で lease の状態を確認できます。すべての gateway と送信を停止してから `duduclaw egress-leases list` の確認 token を使って `clear` でオフライン復旧します。詳しくは送信データ保護の復旧手順を参照してください。

## セキュリティ → メール依頼者の承認

**依頼者が会話でメール送信を確認** は、Admin 専用のロック付き `system.update_config` を通じて `config.toml [security] mail_requester_approval` を保存します。真偽値のみを受け付け、既定値は `true` です。ファイルやキーがない場合は既定値を使います。設定の読み取り失敗、構文・値の不正、または `false` では、ダッシュボードの Admin だけが承認できます。

有効な場合、gateway が身元を証明した、そのターンを開始した確認済みの社内アカウントだけが、一対一の会話または認証済みダッシュボード WebChat でのみ承認待ちの `mail_send` を確認できます。決定時にもその AI スタッフへの Operator 権限が必要です。カードには完全な宛先、件名、本文要約と非公開データの読み取り状態を表示します。グループ会話、外部・未確認のユーザー、自動ターンは決定できません。ダッシュボードの Admin も引き続き決定できます。ほかの送信ツールの規則は変わらず、最終引数への束縛、一回限りの使用、送信直前の再確認、期限切れの拒否を維持します。[完全な規則](../../features/ja-JP/05-security-defense.md#依頼者による元の会話でのメール確認)を参照してください。 対象はチャネルが証明した一対一の会話または認証済みダッシュボード WebChat のみです。グループ会話と種類不明の会話には引き続きダッシュボード Admin の承認が必要で、公開 WebChat ウィジェットの訪問者は対象外です。対象外のチャネル通知に宛先、件名、本文は含めず、完全な内容はダッシュボードにのみ表示します。

## セキュリティ → チャットアプリで承認（v1.86）

「セキュリティ設定 → チャットアプリで承認」で Telegram と Google Chat を設定します。追加確認の種類は既定ですべて選択済みで、解除にはリスク確認が必要です。カードの有効期間は１〜720時間です。個人版では読み取り専用です。管理者は「自分の接続 → チャットアプリの連携（管理者）」でワンタイムコードによる本人確認を行います。「チャット承認資格を取り消す」は証明だけを消去します。「メンバー」のチャット ID には「本人確認済み／管理者が入力」を表示します。カードのリンクは `/approvals/confirm` を開き、必要なら先にログインし、パスワードと認証アプリのコードで承認します。却下にパスワードは不要です。処理済みの受信箱カードには決定者と決定時刻を表示します。

既定で無効、管理者のみです。このセクションは専用の設定呼び出しでのみ書き込めます。設定ファイルの詳細編集と一般の設定書き込みは `[approval.chat_admin]` への変更をすべて拒否するため、リスク画面を経ずに有効にすることはできません。有効にするにはリスクの確認（「理解しました」）だけが必要で、パスワードは不要です。詳しい規則は[セキュリティ防御](../../features/ja-JP/05-security-defense.md#チャットアプリでの管理者承認v186)を参照してください。

| 項目 | `config.toml [approval.chat_admin]` | 説明 |
|---|---|---|
| チャットアプリで承認 | `enabled`（既定 `false`）と `enabled_ack = { by, at }` | `enabled_ack` は設定呼び出しが書き込み、リスクを確認した管理者を記録します。ない場合やその人がもう有効な管理者でない場合は無効扱いです |
| チャネル | `channels`（既定 `["telegram", "googlechat"]`） | このバージョンは Telegram と Google Chat のみ。その他の値は警告して無視します |
| もう一度の確認が必要な区分 | `step_up_exempt_kinds`（既定は空＝T2 のすべての区分で必要） | 各項目は確認を免除する T2 区分です。免除には区分ごとのリスク確認が必要で監査され、戻す操作も監査されます |
| 確認方法 | `step_up_methods`（既定 `["web"]`、`"dm_totp"` を追加可能） | web＝ダッシュボードへの一回限りのリンクでパスワードと認証アプリのコードを入力。`dm_totp`＝Telegram の個別チャットで 6 桁のコードを入力（Google Chat では提供しません。コードを含むメッセージは削除されます） |
| カードの有効時間 | `card_valid_hours`（既定 `168`、1〜720） | 承認自体の期限を超えません |

読み取りや解析の失敗、不明なキーや値があると機能は無効扱いになり、画面は T2 のすべての区分を確認必要として表示し、設定ファイルが直るまで保存を拒否します。変更のたびに設定変更記録と監査 `approval_chat_admin_settings_changed` を書き込みます。このセクションには、まだ本人確認をしていない管理者と、確認リンクが使えるか（外部の https アドレスが必要）も表示します。

**マイ接続 → チャットアカウント（管理者）。** コードを発行し、10 分以内に表示されたボットまたは Chat アプリとの個別チャットに貼り付けてから、ここに戻って「本人です」を押します。管理者が代わりに登録した紐付けはメンバーページで「本人未確認」と表示されます。「チャット承認の資格を取り消す」は本人確認だけを消します。

`approvals.list {status?, limit?, agent_id?, action_kind?}` は `status: "pending"`（既定）または `"decided"` を受け付けます。処理済み履歴は現在も権限のある管理者専用で、既定は 50 件、新しい順です。`limit` は 1～100 で、未処理は未指定なら件数制限なしです。`approvals.list` と `approvals.get {id}` の閲覧可能な項目には `decided_at` と `execution_result` が加わります。管理者 AI 設定カードの実行結果は `{outcome, reason, completed, not_executed, message, items:[{seq,result,error}]}` で、`outcome` は `complete`、`partial`、`voided` です。他の種類は `null`、制限されたカードでも `null` になる場合があります。

`approvals.chat_admin.get {}` の `kinds[]` は `admin_ai_settings` を含み、`label` に `zh-TW`、`en`、`ja` の名前、`impact` に複数社員の設定変更が今後の動作に影響する旨を返します。現在の `impact` は繁体字中国語の単一文字列です。

`POST /api/me/approvals/step-up` の成功応答は `{status:"done", decision:"approve"|"reject", decided_by_display:string|null}` です。従来の `decided_by` は削除されました。表示には `decided_by_display` を使います。

## 完了報告のチェック（設定ファイルの詳細編集でのみ変更）

`config.toml [action_claims] mode` には設定ページのスイッチがなく、管理者が「システム設定 → 詳細設定 → 設定ファイルの詳細編集」で変更します。値は `"notice"`（既定）または `"shadow"` です。ファイル、セクション、キーがない場合は既定値を使います。エディターはそれ以外の値を拒否し、手で書き込んだ不明な値は `"shadow"` として扱い、gateway のログに一度だけ警告を記録します。返信ごとに読み直すため、再起動は不要です。

- `notice`：チャットの返信が「メールを送信した」「カレンダーの予定やタスクを作成した」「スプレッドシートや Google ドキュメントに書き込んだ」と述べているのに、この会話に対応する成功記録がない場合、返信の最後に短いお知らせを 1 つ追加します。表示されるのは社内スタッフだけです（WebChat でサインインしたダッシュボードアカウント、およびメッセージアプリの一対一の会話で、本人確認済みの Admin またはこのスタッフに紐付いたアカウント）。訪問者、グループ会話、未確認の送信者には返信をそのまま送ります。
- `shadow`：記録のみ。返信は変更しません。

どちらのモードでも、成功記録のない主張は gateway のログとセキュリティ監査ログに記録します。[完了報告のチェック](../../features/ja-JP/78-action-claim-check.md)を参照してください。

## セキュリティ → データ削除の受領記録

チャネル、Google アカウント、データベースのソース、Remote MCP を解除すると、記憶の削除依頼を自動的に準備します。接続解除と記憶削除の完了は別の結果です。

1. サービスの設定画面で接続を解除します。バッチが準備できると「承認依頼を見る」が表示されます。`[memory] forget_source` が無効、または設定が読み取れない場合、計画は作成しません。計画の失敗も別に報告します。
2. 管理者が受信箱のカードで AI 社員ごとの件数を確認します。バッチは 7 日で期限切れになります。実行前に削除範囲が広がった場合は再承認、狭くなった場合は続行します。
3. 承認結果を保存した後、gateway は永続的なバックグラウンド処理を作成します。未完了の処理を再試行し、再起動後も再開します。削除や必要な後処理が未完了の間は、受領記録を作成しません。
4. **システム → セキュリティ → データ削除の受領記録**で接続を展開し、「JSON をダウンロード」を選びます。更新すると新しく完了した処理を確認できます。削除した記憶、重要事実、アーカイブと、帰属不明、保持したシステム記録を別々に表示します。

Google の個人接続は実際に使った認証情報のユーザーに帰属し、削除件数は AI 社員別に表示します。接続の印がない古い記憶を後から確実に帰属させることはできません。会話の原文、`tool_calls.jsonl`、wiki、バックアップは対象外です。Remote MCP の既存の `forget` は保存済み接続の削除、新しい `forget_memories` は記憶の削除依頼を制御し、後者は既定で有効です。

Google 以外の OAuth 取り消しには現在接続の帰属情報がなく、忘却はスキップとして報告します。Google の設定済み認証経路を消しても、別に保存された OAuth 授権は取り消されません。その授権の解除操作を使ってください。

接続の出所マークは出所と役割を保持します。単なる再確認は削除の所有権になりません。他の接続中の出所も同じ記憶を提供している場合、その記憶は保持され、計画・管理者の承認カード・受領書に従業員別の `retained_shared` 件数が表示されます。所有する接続がすべて切断済みで、他に有効な直接の出所がない場合のみ削除します。そのため、共有されていた記憶は二つ目の接続の切断時に対象になる場合があります。所有権が不明な記憶（役割を復元できない旧マークを含む）は保持し、帰属不明として数えます。派生した記憶も個別に確認します。計画・適用の前に接続状態を再確認し、プラットフォームで再接続する場合は接続を公開する前に古い切断記録を無効にします。

承認は孤立したエンティティ埋め込みの件数だけでなく、並べ替えた識別子にも結び付けます。同数でも別の識別子への入れ替えには再承認が必要です。未完了ジョブは試行回数と次回実行時刻を保存し、60／120／240／480 秒の待機を入れ、実行時刻を迎えたジョブを公平に処理します。連続五回の失敗または中断で隔離します。管理者は「データ削除受領書」で記憶内容を含まない失敗理由を確認し、「再試行」を選択できます。再試行は既存の承認を保持して範囲を再確認し、範囲が広がった場合は再承認を求めます。

## 会話の認証情報

Admin は「システム → セキュリティ → 認証情報の監査」でメタデータの確認、絞り込み、サービス編集、誤検出指定、監査付きの現在ページの CSV 出力を行えます。隣の一覧はシステム設定を読み取り専用で表示します。`system.update_config` の `security.chat_credentials` または設定エディターで `[security] chat_credentials = "audit" | "mask"` を指定します。既定は `audit`、不明な値は `mask` です。監査モードは会話原文を残し、マスクモードは新規メッセージで検出した値のみを変更します。過去の履歴は変更しません。両モードで派生ストアの検出値をマスクします。[認証情報監査](../../features/ja-JP/70-credential-audit.md)に検出限界と登録上限を記載しています。サービス名やメモに実際の認証情報を入力しないでください。

## 管理 → 連携 → Google 設定

管理者は `/manage/integrations?tab=google` の再開可能なウィザードで、会社委任、Internal OAuth、Apps Script、個人 External OAuth を選べます。詳細フォームも利用できます。有効経路の切り替えは保存前に確認し、OAuth トークンは明示的な切断まで保持します。テストはサービス別で、スコープのみの Sheets/Docs は未検証です。Console、SSH 転送、Testing 期限は [Google 接続](google-setup.md)を参照してください。

## 受信トレイと作業タイムライン

受信トレイの「要対応」には、まだ判断や対応が必要な項目が並びます。期限の近い項目、リスクの高い項目、従業員の質問や判断待ちのタスク、予算通知の順に表示します。「長く待っている」は 1 日以上待っている要対応項目です。クリックやキーボードで選択したときだけ開いて既読にし、ポインターの移動では切り替わりません。同意待ち、インストール申請、判断待ちのタスクは対応してから保管できます。他の項目は未完了の作業も含め、どのタブでも保管できます。受信トレイのどこからでも ⌘Z または Ctrl+Z で保管を取り消せます。文字入力中は通常の取り消しを使います。U で未読にします。対応後は結果が表示され、判断ボタンは消えます。判断ボタンはパソコンとモバイルの両方で詳細の下部に固定されます。一覧と詳細は画面内で個別にスクロールし、別の項目を選ぶと詳細の先頭から表示します。ホームも期限とリスクを含む同じ優先順を使います。サイドバー、モバイルのベル、受信トレイの見出し、ホームの件数は共通で、対応済みと保管済みを除きます。0 件でもベルから開けます。質問の確認は最初の 12 人が対象で、対象範囲と読み込みエラーを表示します。

作業タイムラインは、期間内に誰が何を完了し、どこで困り、何があなたの判断を待っているかを示します。完了、進行中、判断待ち、未完了の件数を選ぶと従業員カードを絞り込めます。判断待ちの中では最終更新から最も長く待っている従業員を先に表示し、その後に未完了、進行中、記録なしの順に並び、タスク名から詳細を開けます。最終更新からの経過時間は待ち時間の目安であり、状態が始まった正確な時刻ではありません。「時間の分布を見る」は最初は閉じています。色と異なる形状で状態を示し、棒はタスクが開いていた期間を表します。実際の作業時間ではありません。タスクの棒はキーボードとタッチでも開けます。

## MFA強制設定

```toml
[auth]
mfa_enforced = true
```

新規チームではMFA強制が既定で有効です。既存環境は、MFAポリシー記録のない旧版を含め、現在の設定を維持します。Adminはダッシュボードの「ユーザー → 二要素ログイン管理」の専用スイッチで有効・無効にできます。新規チームの最初のAdminはパスワードでログイン後、「最初の管理者の初期設定」を使って認証アプリ、パスキー、メール（SMTP またはライセンス代理送信が必要）をダッシュボードで登録できます。**どのコンピューターからダッシュボードを開いても、1回限りの初期設定コードが必ず必要です**。コードはホストで取得します。DuDuClaw を動かしているコンピューターでターミナルを開き、`duduclaw ops users mfa-setup-code` を実行してください（Docker の場合はコンテナー内で実行します。例: `docker exec -it <コンテナー> duduclaw ops users mfa-setup-code`）。このコマンドは対話式ターミナルにだけコードを表示し、出力がファイルやパイプに向けられている場合や AI セッション内では拒否します。gateway 自身はコードを表示も記録もしません。起動時には「最初の管理者の初期設定を待っています」という1行と実行するコマンドだけをログに書くため、コードが journald や `docker logs` に出ることはありません。コードは30分間有効で1回だけ使え、新しいコードを発行すると古いコードは無効になります。別のAdminによる登録コードの発行は不要です。「このコンピューターで操作しています」という近道はありません。同じホスト上のリバースプロキシを通ると、どの接続もローカルからに見えるため、接続元では何も証明できないからです。この初期設定は最初の（bootstrap owner の）Adminだけに、強制が有効で、どの管理者もまだ認証方法を設定していない間だけ、そして**インストールごとに1回だけ**提供されます。いずれかの管理者が認証方法を持った時点で恒久的に閉じ（未使用の設定コードも無効になります）、その後に認証方法を削除したり、管理者を降格・停止・削除したりしても再び開くことはなく、ホストのコマンドもコードの発行を拒否します。その後、管理者が2段階認証を失った場合は、ホストで `duduclaw ops users mfa-reset <email>` を実行してください。これらが使えない場合は、引き続きホスト操作員が `duduclaw ops users mfa-enrollment-code <email> <challenge_ref>` で登録コードを発行できます。既存の強制無効環境では任意登録を続けられます。有効化前に `mfa.overview`、チャネル配信、ホスト復旧を確認してください。両Dashboard書込経路は現在有効なAdminが必要です。登録と以後の認証情報変更はepochで古いJWTを無効にします。強制の切替だけではaccess tokenの自然な期限切れを待ち、未登録者のrefreshを拒否します。強制中の旧共有token WebSocketログインは拒否します。

設定は起動時のメモリスナップショットを使い、Dashboard保存後と外部ファイルの30秒ごとの確認で更新します。失敗は警告して最後の有効値を保持し、有効値を一度も得ていない場合は全エディションで拒否します。起動時に既存のポリシーストアを読み取れない場合や破損している場合も拒否します。`[auth]` または設定キーがない場合は永続ポリシーを維持します。新規チームの初期化では設定ファイルとアカウントDBの両方にtrueを記録します。すべてのエディションで保存済みポリシーに従い、ライセンス失効、検証失敗によるフォールバック、明示的なPersonal指定では強制を解除しません。Adminによる意図的な解除だけが無効にします。ポリシーストアのない新規Personalは引き続き強制無効です。ローカル自動ログインでも強制中のMFAを回避できず、Personalでもホスト復旧を利用できます。証明フィールド、セッション限定、`duduclaw ops users mfa-reset` / `mfa-enrollment-code` によるホスト復旧は[セキュリティ](../../features/ja-JP/05-security-defense.md)を参照してください。鍵ローテーションは対象外です。

有効化前に `mfa.overview` のチャネル時刻を確認します。強制開始前の検証済みバインドだけが証明になります。パスワード保有者が開始前に仕込んだバインドは検出できません。12文字の `challenge_ref` を別のAdminに伝え、`users.mfa_enrollment_code {user_id,challenge_ref}` またはホストの `duduclaw ops users mfa-enrollment-code <email> <challenge_ref>` で発行します。再読取失敗は `mfa.overview.policy` と `system.status.mfa_policy` に表示し、最後のfalseを保持します。設定ロック内でAdmin権限を再確認します。CLIインポートもデータ移動前に現在のDBポリシーを確認します。チーム環境でusers.dbまたはSQLiteの付随ファイルを置換する場合、設定に現在と同じmfa_enforced値を明示する必要があります。バックアップDBによる強制設定の変更を防ぐためです。

CLIのホームインポートは、圧縮バックアップの同じ非公開スナップショットを検証して展開します（上限8 GiB）。両段階でバックアップ復元と同じ既定値を使い、tar項目数200,000、単一項目2 GiB、非圧縮合計8 GiBを上限とします。GNU／PAXメタデータの解析前に生のヘッダーを検査し、メタデータは単一項目1 MiBまで、サイズ検査はPAXによる上書き後の値も対象にします。サイズ上書きにより生ヘッダーを走査できない外部PAXバックアップは拒否される場合があります。本製品のエクスポートが生成するGNU長形式パスは対応しています。各パス要素の末尾のピリオドと空白を除き、NFC正規化後に大文字化・小文字化したキーで比較します。NFKCは使わないため、全角の `ｃｏｎｆｉｇ.toml` は `config.toml` の別名ではありません。保護対象の別名（`Config.toml.` など）と重複先は全環境で拒否します。コロン、DOS予約名、`CONFIG~1.TOM` などの8.3短縮名を拒否するのはWindowsのみで、Unixで有効な `aux` や `notes/2026-11-04T07:00` はエクスポート後にインポートできます。バックスラッシュと通常名以外のパス要素は全環境で拒否します。`--force` で既存社員を移動する前に拒否条件の確認と必要な強制設定の永続化を完了し、設定の公開に失敗した場合は `agents/` を移動しません。MFA強制中にアカウントDBやSQLite付随ファイルを置換する場合、同一内容でもアーカイブ内の設定を展開せず、Windowsでも書込完了を待つ置換を使います。

ダッシュボードは一度に一つの保留中復元だけを受け付けます。先に再起動して適用してください。復元取消RPCはありません。各要求は専用のランダムな一時ディレクトリで展開・検証し、データディレクトリごとの復元ロックを全工程で保持します。検証後、通常ファイルと全ディレクトリを同期してから改名・公開し、ホームディレクトリを同期します。その後マーカーを永続化してホームを再同期し、すべて成功してからアップロードを削除します。Windows は std がディレクトリ同期に対応しないため、ファイルのみ同期します。失敗時はその要求の一時データだけを削除します。公開後にマーカー書込が失敗した場合はデータを保持して以後の上書きを拒否し、管理者に確認を求めます。

起動時には保留マーカーの有無にかかわらず、早い段階で一度だけ実行ロックの取得を試みます。失敗後にマーカーが作成され、別のゲートウェイが終了しても、そのプロセスでは再試行しません。保留中のバックアップ復元は、現在のポリシーを読む前、ステージングを書き換える前に、データディレクトリを排他的に確保します。同じディレクトリで別のゲートウェイが実行中なら、復元を延期し、保留マーカーとステージングデータをそのまま保持します。ゲートウェイは従来の縮退モードで起動を続け、そのプロセスの存続中はワークフローの復旧・ディスパッチ・スイープを実行しません。別のゲートウェイが終了しても再取得せず、保留中の復元を適用するには再起動が必要です。現在のMFA強制設定と実行中のロック用ディレクトリを保持し、バックアップ内のロックは復元しません。これにより、ポリシー確認とデータ置換の間に完了したAdminの変更が上書きされることを防ぎます。

### メール確認コード、パスキーとログイン状態の保持（v1.80.0 から）

「設定 → アカウント」で既存の認証アプリを残し、メール確認コードや名前付きのパスキーを複数追加できます。追加・削除には現在のパスワードが必要です。メール設定ではアカウントのメールアドレスに 6 桁のコードを送り、確認成功後に有効にします。既存の `[channels.email]` SMTP 送信設定（`smtp_host`、`from_addr` と必要な認証情報）を優先します。SMTP 未設定の場合、この端末に紐付いた有効な有料ライセンスで DuDuClaw による確認コードの代理送信を利用できます。NFR ライセンスは対象外で、以下の代理送信設定を有効にする必要があります。認証方法の変更は監査します。セキュリティ設定の変更通知は、設定済み SMTP のみを使用します。

#### メール確認コードの代理送信設定

gateway の `config.toml` に設定します。

```toml
[mfa]
email_relay = true
```

`email_relay` の既定値は `true` です。`false` はライセンスによる代理送信だけを無効にし、自前の SMTP や MFA の必須化は無効にしません。OpenSource、Hobby 試用版、Partner、NFR、端末に紐付いていない OEM、無効または期限切れのライセンスは対象外です。Partner は旧ライセンスで `nfr = false` と記録されていても対象外です。これらの環境では SMTP を設定してください。代理送信はコンパイル時に固定した公式ホストを使い、ライセンス更新設定から独立しています。`DUDUCLAW_CONTROL_URL`、ライセンス内の `control_url`、設定ファイルや環境変数で宛先を変更できません。専用の通信処理は HTTPS の 443 番ポートを使い、公開 DNS の解決結果を固定し、プロキシとリダイレクトを拒否します。タイムアウトは 10 秒、応答の上限は 4 KiB です。

対象ライセンスでの初回送信時に、チャレンジ・レスポンス方式で登録します。gateway はサブスクリプションごとに使い捨てのチャレンジを取得し、署名付きライセンス、端末フィンガープリント、チャレンジ、発行時刻を、インストール鍵（次の節を参照）による Ed25519 署名とともに送信します。インストール ID はサーバーが承認済みの公開鍵から導出します。既存の代理送信認証情報を置き換える登録では、同じ署名対象に対する HMAC でその認証情報の保持も証明します。応答本文は固定容量で解放時にゼロ化されるバッファーに保持します。HTTP と TLS ライブラリ内部のコピーは消去できません。認証情報は `<home>/state/mfa-relay.json` に所有者だけがアクセスできる状態で保存します。Unix は 0600 権限を使い、macOS ではさらに拡張 ACL を拒否します。Windows は非公開の DACL と固定したハンドルを使います。書き込みではディレクトリハンドルを固定し、シンボリックリンクを拒否して、アトミックな名前変更で公開します。以後の送信本文は宛先、コード、言語だけを含み、HMAC 署名でメソッド、パス、時刻、nonce と実際の本文を結び付けます。ライセンスは再送しません。すべての登録試行は、永続保存される 1 時間に最大 1 回の上限を共有します。初回登録の失敗も数え、gateway を再起動しても上限はリセットしません。`403 relay_not_allowed` を受けた場合、この上限の範囲内で、その送信について再登録と再送をそれぞれ最大 1 回行います。各サブスクリプションで有効な認証情報は一つだけで、登録できるのはアカウント所有者が鍵を承認したインストールだけです。

#### インストール鍵とライセンスコンソールでの承認

各インストールは `<home>/state/installation.key` に独自の Ed25519 鍵（32 バイトのシード。代理送信の認証情報と同じ所有者限定の保護）を持ちます。`identity.key` とは別の鍵です。鍵はファイルが存在しない場合にだけ作成されます。作成されるのは CLI でライセンスを有効化したとき、ライセンス更新時（gateway の自動更新または `duduclaw license refresh`）、`duduclaw license installation-key` の実行時です。読み取れない、形式が不正、または安全でないファイル（所有者や権限の不一致、シンボリックリンク、複数のハードリンク、拡張 ACL）はエラーとして報告し、決して置き換えません。修正または復元するまで代理送信は利用できません。AI 社員はファイルガードにより `state/` 以下を読み取れません。ホームディレクトリのバックアップにはこの鍵も含めてください。

ライセンスの更新と再バインドの要求は、公開鍵を `installation_pubkey` として送信します。代理送信は、ライセンスに同じ署名付き公開鍵が含まれてから利用できます。ライセンスサービスが知らない鍵はライセンスコンソールに承認待ちの申請を作成し、アカウント所有者に通知します。承認待ちの間も有料機能はそのまま使え、SMTP による確認コード送信も利用できます。待つのは代理送信だけです。既存のインストールはそれぞれ一度承認が必要です。

承認する前にフィンガープリントを照合してください。gateway ホストで次を実行します。

```bash
duduclaw license installation-key
```

1 行目は 16 文字のフィンガープリント（例：`1a2b-3c4d-5e6f-7a8b`）です。32 バイトの公開鍵そのものに対する SHA-256 の先頭 16 桁の 16 進数を 4 文字ずつ区切ったものです。公開鍵や承認状態などの詳細は stderr に出力します。承認待ちの間は、管理者は「設定 → アカウント」のメールの説明の下でもこのフィンガープリントを確認できます。コンソールに同じフィンガープリントが表示されている場合だけ承認してください。心当たりのない申請は、誰かがライセンスファイルのコピーを持っていることを意味します。拒否してください。

鍵を失った場合（例：ホームディレクトリを移さずに別のマシンへ移行した場合）、次回の更新で新しい鍵を作成し、改めて承認を申請します。ログイン済みのアカウント所有者はコンソールで一つのフィンガープリントを 24 時間有効で事前承認でき、その間の同じ鍵による更新は自動承認されます。代理送信の認証情報だけを失った場合は、コンソールの「代理送信の認証情報をリセット」を使うと、次回の登録は初回として扱われます。

代理送信が承認待ちの場合、メールの説明には、このインストールが承認待ちであること（ライセンスにまだ鍵がない）、またはこのインストールの鍵が承認済みの鍵と異なること（例：別のマシンへの復元後）が表示されます。

代理送信は確認コードの固定テンプレートのみを使用し、件名や本文は指定できません。コードと認証情報の秘密値はログに残しません。gateway の宛先ログはホームごとの既存監査鍵で用途を分離した HMAC を計算し、鍵を取得できない場合は固定値 `unavailable` だけを記録します。コントロールプレーンには追加の送信制限があります。送信頻度のエラーが出た場合は待ってから再試行し、その他の送信失敗は後で再試行するか管理者に連絡してください。ローカルで発行済みのコードは、後から送信サービスが利用できなくなっても検証できます。ローカルでの利用資格は配信成功を保証せず、実際の代理送信は別途検証が必要です。

メールが無効な場合は、利用可能な送信方法がないこと、代理送信が無効であること、ライセンスの種類が対象外であること（NFR または端末未紐付けの OEM）、またはインストール鍵がライセンスコンソールで承認待ちであることを示し、それまでの間は SMTP を設定するよう管理者に案内します。パスキーが無効な場合は、安全でない接続とブラウザー非対応を区別します。`http://` の LAN アドレスで開いている場合は設定済みの HTTPS URL、または gateway ホストの localhost を使用してください。非対応の場合はパスキー対応ブラウザーに切り替えてください。

各方式に必要な条件：

- **認証アプリ**：6 桁の TOTP コードを生成するアプリ。必須登録では、画面に表示される独立したチャネル／管理者の証明も必要です。
- **メール確認コード**：アカウントのメールを受信でき、サーバーの SMTP が設定されていること。管理者は「設定 → 詳細設定 → 設定ファイルの詳細編集」（`/app/system/settings/advanced#configRaw`）の `[channels.email]` で `smtp_host`、`from_addr` と必要な SMTP 認証情報を設定します。未設定の場合、無効な選択肢の横に設定場所を表示します。
- **パスキー**：WebAuthn 対応ブラウザーと HTTPS。localhost では HTTP も使えます。`http://` の LAN アドレスは安全なコンテキストではないため、HTTPS の利用を案内します。ブラウザーが非対応の場合は別の理由を表示します。サーバー側のオリジン／RP 設定も下記のとおり必要です。

ログイン、登録、アカウント設定で無効な理由を表示します。メール送信設定がない場合の理由コードは `no_smtp` のみで、利用可能という表示は実際の配信成功を示すものではありません。

パスワード入力後に登録済みの認証方法を選択できます。前回成功した方法を既定で選びます。メールコードは一度だけ使用でき、10 分で失効し、一つのログインチャレンジにつき最大 5 回試行できます。再送は 1 分に 1 回、アカウントごとに 1 時間で最大 5 回です。パスキーは端末の画面ロック、生体認証またはセキュリティキーを使用します。管理者は `[dashboard] public_url` に公開 URL を設定し、その完全一致する HTTPS オリジンで開いてください。HTTP は localhost のみ利用できます。各キーに名前を付けて個別に削除できます。端末を失った場合に備えて別の方法も残してください。パスキーだけを初めて登録した場合はリカバリーコードを発行しません。既存の認証アプリのリカバリーコードは維持します。初回メール登録ではリカバリーコードを一度だけ表示し、保存確認後に続行します。

認証の必須化は登録済みのいずれの方法でも満たせますが、最後の方法の削除は拒否します。既存の認証アプリとリカバリーコードは再登録不要です。MFA の強制中は、初回メール登録にも認証アプリやパスキーと同じ独立したチャネル／管理者の証明、または条件を満たす最初の管理者の初期設定コードが必要です。登録の証明を `proof_code` として提出してからメールコードを送信します。メールを受信できるだけでは初回登録を完了できません。認証方法の有効化とセッショントークンの発行を行う同じトランザクションで証明を再確認し、期限切れ、再利用、未確認、認証情報の変更があれば拒否します。MFA 確認済みのセッションからメールを追加する場合は別の登録コードは不要で、強制なしの任意登録も従来どおりです。Google ログインでは引き続きメールを第二要素にできません。チャンネルコードで最初のログインを行った場合は現在のパスワードも必要です。管理者のリセットはすべての認証方法と保持されたログインを取り消します。**一般メンバー**のリセットは、引き続き操作者の現在のパスワードまたは新しい認証アプリ／リカバリーコードで確認できます。**別の管理者**（過去7日以内に一般メンバーへ降格された人を含む）のリセットには、操作者自身の第二要素（新しい認証アプリのコードまたは未使用のリカバリーコード）が必要で、パスワードだけでは拒否されます。コードの確認はパスキーを受け付けず、パスキーの初回登録ではリカバリーコードが発行されないため、認証アプリを持たない管理者（パスキーのみ、またはメールコードのみ）は「パスワードとメールで届くコード」で確認します。現在のパスワードを入力したあと、自分のメールアドレスに届く6桁のコード（5分間有効、1回限り、リセット対象に紐付け、メールログインコードと同じ送信回数制限。SMTP またはライセンス代理送信が必要）を入力します。さらに操作者は、管理者資格記録で7日間続けて管理者資格（管理者であり第二要素を設定済み）を持っている必要があります。管理者になったばかりの人、7日以内に自分の認証方法をリセットされた人、新規インストール後7日以内のすべての管理者は拒否されます。**新規インストール後の最初の7日間は、どの管理者もダッシュボードから別の管理者の2段階認証をリセットできません**。この期間はホストのコマンド `duduclaw ops users mfa-reset <email>` だけが使えます。その後も、ほかに管理者が一人しかおらず、その人も7日未満の場合は同じホスト復旧を使ってください。これらのルールは gateway がすべての呼び出し元に対して強制し、認証情報や管理者資格記録を読めない場合は拒否します。成功・拒否を問わず、すべての試行（アカウントデータやログイン設定を読めない、ダッシュボードのセッションがない、試行回数が多すぎる、といった最初期の拒否を含む）について、試行 ID、操作者、対象、結果、理由を含む記録がちょうど1件残り、パスワードやコードは含みません。記録はまず `users.db` の監査送信待ち領域に書かれ（完了したリセットとその記録は同じトランザクションで書き込まれます）、その後セキュリティ監査ログに送られ、届いてから削除されます。セキュリティ監査ログに書き込めない間は記録が残り、次のリセット試行時か gateway の起動時に再送されます（再送された記録は同じ試行 ID を持ちます）。`users.db` 自体を使えない場合、拒否の記録は直接セキュリティ監査ログに書かれます。送信待ち領域は最大1,000件で、満杯のときは新しいリセット試行を拒否します。

ログイン画面の「ログイン状態を保持」は既定で未選択です。選択するとローテーションする Cookie で既定180日間保持し、更新が成功するたびに、その利用時点から設定日数分だけ有効期限を更新します。管理者は「セキュリティ → ログイン状態の保持」で1～365の整数を保存できます（既定180日）。設定は `users.db` に永続保存され、読取失敗や不正な値では180日に戻り、無期限にはなりません。変更時点では既存の有効期限を維持し、次回の更新成功時に、その利用時点と新しい日数から計算し直します。日数を短縮した場合も同じです。開発版の `[auth] remember_days` 設定は読み取られません。未選択では従来のセッション動作を維持します。アカウント設定の「ログイン中の端末」は保持中の端末、作成日、最終利用日、記録済み IP を表示し、個別の取消と「すべての端末からログアウト」に対応します。パスワード、認証方法、アカウント状態・役割の変更、認証のリセット、アカウント削除で保持されたセッションを取り消します。ログアウトは現在の端末を取り消します。

管理者は「メンバー」のアカウント詳細で「このユーザーのすべての端末からログアウト」を選び、確認すると通常ログインと保持ログインをすべて取り消せます。アカウントの無効化・削除でも取り消されます。既存のアクセストークンは拒否され、接続中の WebSocket は既存の取消確認（次のハートビートを含む）で停止し、180日の期限を待ちません。管理者専用の `sessions.policy`、`sessions.policy_update`、`users.revoke_sessions` は現在の権限を再確認し、変更では操作者・対象・結果を認証監査ログに記録します。認証情報は記録しません。

| 操作 | 保存先／RPC | 反映時期 |
|---|---|---|
| セキュリティ → ログイン状態を保持する日数、管理者のみ | `users.db` → `remembered_policy_state.days`、`sessions.policy` / `sessions.policy_update` | 再起動不要。新規ログインと次回の更新成功時。1～365、既定180。 |
| メンバーの編集 → このユーザーのすべての端末からログアウト、管理者のみ | `users.revoke_sessions`、認証情報の世代・端末の取消・認証監査 | 確認後すぐに取消を保存し、既存接続は従来の検査で停止します。自分のログアウトは既存の HTTP エンドポイントを使い、接続取消後も成功応答を受け取れます。 |

Cookie 認証のセッション要求には `X-DuDuClaw-CSRF: 1` と、スキーム・ホスト・実効ポートを含む完全一致の Origin が必要です。組み込みの HTTP loopback Origin はゲートウェイの待受ポートのみを許可します。リバースプロキシでは `[gateway] allowed_origins`（または `DUDUCLAW_ALLOWED_ORIGINS`）に完全な `https://host[:port]` Origin を指定してください。これらのエンドポイントではホスト名だけの設定は不十分です。更新とログアウトは、別ポートのページと通常の HTML フォームを状態変更前に拒否します。

更新には認証済みの family 世代番号を使い、family ごとに現在のトークンハッシュを一件だけ保存します。正当な旧世代の再使用は端末を取り消し、偽造した世代番号では取り消せません。所有者のみ読み書き可能な署名鍵 `users.remember-key` は `users.db` と一緒にバックアップ・復元してください。世代セッションがある状態で鍵を失った場合や鍵が破損した場合、認証データベースは開けません。世代機能より前の開発版セッションは移行時に取り消されます。アカウントごとに有効端末は最大20台、取消済みを含む family 記録は最大100件です。記録上限では通常ログインを使い、古い記録の期限切れを待ってください。最後に更新した有効期限の七日後以降、次の保持ログイン成功時に記録を削除します。アカウント認証のダッシュボードと WebChat 接続は最長24時間で再接続・再認証が必要です。既存の短い MFA 期限も適用され、古い接続が取消記録の保持期間を超えて残ることを防ぎます。


長期認証情報は localStorage に保存せず、JavaScript からも読み取れません。Cookie は HttpOnly、SameSite=Strict、`/api/session` に限定し、HTTPS では Secure を設定します。サーバーはハッシュだけを保存し、使用ごとに更新します。古い認証情報の再使用は同じファミリーをすべて無効にします。Cookie を使うエンドポイントとダッシュボードの WebSocket アップグレードは Origin を検証します。

実際の SMTP／ライセンス代理送信による配信、各プラットフォームでのブラウザーのパスキー登録・ログイン、Rust の各 OS ビルド、依存関係の監査、完全な gateway 統合テストは未検証です。UI 実装とテストコードの作成だけでは受け入れ完了にはなりません。

### ダッシュボードの二要素ログイン

Enterprise と強制中の Personal では「設定 → アカウント」で「二要素ログインを設定」を選び、現在のパスワードを入力し、認証アプリで QR コードをスキャン（またはシークレットを手動入力）して、6 桁のコードで確認します。10 個のリカバリーコードをコピーまたはダウンロードし、「リカバリーコードを保存しました」にチェックして続行します。シークレットとコードはコンポーネントのメモリだけに保持し、画面を離れると破棄します。コピーとダウンロードは明示的な操作です。登録と無効化では現在のセッションのトークンを更新して接続を維持し、ほかのセッションは無効になります。保存を確認するか画面を離れるまで、リカバリーコードを表示します。トークン発行と MFA の変更は同じトランザクションで確定し、発行に失敗した場合は登録や無効化を適用せず、再試行できます。再発行と無効化には新しい認証コードまたは未使用のリカバリーコードが必要です。無効化には現在のパスワードも必要で、必須化中は無効にできません。

パスワードとチャンネルコードのログインは、gateway が二要素認証を要求するまで従来のフォームを維持します。認証アプリのコードまたは一度限りのリカバリーコードを使えます。ログイン要求は 5 分間有効で最大 5 回試行できます。必須登録には独立したチャンネル／管理者コードと現在のパスワード（チャンネルログイン時に必須）が必要です。管理者には表示された登録識別番号だけを伝え、登録トークンを渡さないでください。新規インストールの最初の管理者には代わりに「最初の管理者の初期設定」が表示されます（上記参照）。画面にはホストで実行するコマンドが表示され、そのコマンドが表示した設定コードを入力すると、登録コードの入力欄は表示されなくなります。

Admin は「ユーザー → 二要素ログイン管理」で登録状況とチャンネル認証日時を確認し、他のアカウントをリセット（確認方法は上記のルール。フォームにはそのアカウントで認められる確認方法だけが表示されます）したり、相手の登録識別番号に対するワンタイムコードを発行できます。自分へのリセットと発行はできません。リセット後、対象者にはメール（SMTP）と認証済みのチャンネル連携で通知されます。どちらも届かない場合は、管理画面に30日間警告が表示されるので直接連絡してください。失敗はセキュリティ監査ログにも記録されます。管理者が一人だけの場合、管理画面はもう一人追加するよう勧めます。必須化のスイッチは未登録数とログイン制限の警告を示し、表示された確認文の入力を要求します。確認を開いた時点で操作を固定し、再読込すると確認を消去します。切替RPCは `expected_state` が必須で、設定ロック内で不一致を拒否します。設定の再読み込みが縮退状態の場合は警告してスイッチを無効にします。新規チームでは最初から強制が有効です。既存の無効環境では、登録、チャネル配信、ホスト復旧を確認してからAdminが有効にしてください。Personal でも登録が必須、または登録済みならアカウントのMFA設定を表示します。強制無効かつ未登録なら引き続き非表示です。強制中のPersonalでは、Adminが「システム → セキュリティ → 二要素ログイン管理」から同じ管理画面と専用スイッチを使い、意図的に強制を解除できます。全エディションでホスト操作員の `duduclaw ops users mfa-reset <email>` による復旧を利用でき、アカウントのリセットは強制ポリシーを解除しません。
Enterprise では「設定 → アカウント」で「二要素ログインを設定」を選び、現在のパスワードを入力し、認証アプリで QR コードをスキャン（またはシークレットを手動入力）して、6 桁のコードで確認します。10 個のリカバリーコードをコピーまたはダウンロードし、「リカバリーコードを保存しました」にチェックして続行します。シークレットとコードはコンポーネントのメモリだけに保持し、画面を離れると破棄します。コピーとダウンロードは明示的な操作です。登録と無効化では現在のセッションのトークンを更新して接続を維持し、ほかのセッションは無効になります。保存を確認するか画面を離れるまで、リカバリーコードを表示します。トークン発行と MFA の変更は同じトランザクションで確定し、発行に失敗した場合は登録や無効化を適用せず、再試行できます。再発行と無効化には新しい認証コードまたは未使用のリカバリーコードが必要です。無効化には現在のパスワードも必要で、必須化中は最後の認証方法を削除できません。

## 音声合成

`auto` はインストール済み Piper → インストール済み Kokoro → MiniMax → OpenAI → Azure の順に試し、製品ポリシーを適用します。プロバイダーを指定した場合はそのプロバイダーのみ使用し、`off` は音声合成を無効にします。`duduclaw doctor` は合成リクエストを送らずに利用可能なプロバイダーを表示します。

**設定 → 音声** から Kokoro をダウンロードします（約 134 MB、Apache-2.0）。インストール時にファイルと共有 ONNX Runtime を検証し、中断またはキャンセルしたダウンロードは、次回最初からやり直します。モデルの重みはバイナリに含まれません。保存先は `<home>/models/kokoro-zh/`。既定音声は `zf_001`、ほかに `zm_010` と英語専用の `af_maple` を選べます。中国語は中国大陸のアクセントで、多音字を誤読する場合があります。繁体字と数値を正規化しますが、すべての単語の発音を網羅するものではありません。入力上限は 2,000 文字、各チャンクは最大 500 tokens、間に 150 ms の無音を追加します。Kokoro は 24 kHz WAV を出力し、Telegram には `sendAudio` で `reply.wav` を送ります。

Azure はテキストを Microsoft に送信します。gateway 環境に `AZURE_SPEECH_KEY` と `AZURE_SPEECH_REGION` を設定してください。中国語の既定音声は `zh-TW-HsiaoChenNeural`、英語は `en-US-AriaNeural` で、MP3 を返します。`tts_voice` でプロバイダーの対応音声を指定できます。

Admin 専用 RPC：`voice.kokoro_status` はインストール、欠落ファイル、サイズ、ランタイム、進捗、エラーを返します。`voice.kokoro_install` は冪等なバックグラウンドインストールを開始します。音声のダウンロードカードは状態をポーリングし、エラーを表示します。

## WebChat の返信中に次のメッセージを送る

AI スタッフの返信中も、入力して次のメッセージを送信できます。同じ会話で送ったメッセージには「待機中 — 現在の返信が終わってから処理します」と表示されます。現在の返信が終わった後に処理され、進行中の返信には追加されません。そのメッセージの進捗や返信が届くと、待機表示が消えます。`@` で別のスタッフを呼び出した場合は、別の処理キューで実行されることがあります。

待機中のメッセージの「待機中のメッセージをキャンセル」でそのメッセージを取り消せます。送信ボタンの横の「停止」は現在の返信を停止します。キャンセルはサーバーの確認を待ってください。リクエストの送信だけでは完了していません。添付ファイルの使い方は変わりません。

デフォルトでは、ユーザーごとに処理中と待機中を合わせて最大3件まで送れます。上限に達すると、そのメッセージにエラーが表示され、元の文章は残ります。現在の返信が終わった後、「入力欄に戻す」で編集して再送できます。

## メンバーを招待する

管理者は「管理 → メンバー → メンバーを追加」で「招待メールを送信」を選び、メールのプレビューを確認してアカウントを作成します。招待アカウントには使用可能なパスワードがありません。既存の有効なアカウントでパスワードが未設定の場合は再送信できます。一覧には招待中と期限切れの状態が表示されます。

`config.toml` に `[gateway] public_url = "https://ai.example.com"` を設定し、メンバーがアクセスできるダッシュボードの URL を指定します。未設定の場合、ダッシュボードは管理者のブラウザーのオリジンを `public_url` として送信します。HTTP Host や Origin ヘッダーからリンクを生成しません。URL がなければ `public_url_required` を返し、設定済み URL が不正なら拒否します。招待に使う公開 URL はすべて HTTPS が必須です。`localhost`、`127.0.0.1`、`::1` も例外ではありません。

メールは既存の `[channels.email]` SMTP 設定と暗号化済み認証情報を使用します。このリポジトリには Resend または SendGrid の送信実装はありません。リンクは7日間有効で1回だけ使用できます。送信未設定または失敗時に限り、管理者にコピー可能なリンクを一度表示します。送信成功時にはリンクを返しません。結果を閉じると表示を消去します。再送信すると以前の未使用リンクを失効させ、監査用の行を保持します。

受信者は `/invite#<token>` を開き、パスワードを設定・確認して通常のログインに進みます。パスワードは8文字以上、UTF-8で1,024バイト以下です。このページではログインせず、既存の MFA 登録・確認フローが引き続き適用されます。期限切れ、使用済み、失効済み、不明なリンクは同じ無効な結果を返します。無効化されたアカウントでは利用できません。メールアドレスやパスワードの変更、アカウントの無効化でも未使用リンクが失効します。

従業員のホームには、個人接続に未完了の項目があれば「あと少し」カードが表示され、「自分の接続」に移動できます。すべて完了した場合や読み込み失敗時には非表示になり、ブラウザーごとに閉じることもできます。作成、配信結果、使用、失効はトークンやリンクを含めずに監査記録へ保存します。ページは URL フラグメントからトークンを読み取り、直ちに履歴から消去してコンポーネントの状態だけに保持します。公開 `/invite` ページは認証と FirstRunGate の対象外です。API は `POST /api/invite/check`（本文 `{token}`、応答 `{valid,email_masked?}`）と `POST /api/invite/redeem`（本文 `{token,password}`）のみで、トークン付き API パスは削除されました。リクエスト本文をログに保存しないでください。同じ TCP 接続元 IP とトークンの SHA-256 先頭16桁は両 API で15分間に10回までです。リバースプロキシ配下の利用者が互いに制限されないよう、接続元 IP 全体の上限は設けません。メモリー内の表は最大10,000バケットで、満杯になると期限切れのバケットを優先して削除し、期限切れがなければ最も古い挿入を削除します。順序付き索引により表全体の走査を避けます。転送ヘッダーは使用しません。

## ユーザー → 本人確認を設定：メッセージアプリの ID（v1.82）

メンバーの行で **本人確認を設定**（管理者のみ）を押すと、メッセージアプリのアカウントをこのダッシュボードアカウントに対応付けます。紐付け後、そのアカウントからのメッセージは本人からのものとして扱われます。`@` で呼べる AI スタッフ、および AI スタッフを通じて会社の委任や本人の Google アカウントを使えるか（`[google] requesters`）に影響します。

| チャネル | 紐付け | ログイン／2 段階認証コードの受信 |
|---|---|---|
| Telegram、LINE、Discord、Slack | できる | できる |
| Google Chat（v1.82） | できる | **できない** |

- **Google Chat**：`users/` に続く数字、または数字だけを入力します。保存時は常に `users/<数字>` になります。それ以外（メールアドレス、`users/app`）は拒否されます。通常は Google Workspace 管理者が管理コンソールでこのメンバーのアカウントを開くと、アドレスの末尾に数字が表示されます。
- **既定では手動の紐付けだけを使います**：管理者がここで Chat のユーザー ID を紐付けた場合にだけ、送信者をメンバーとして見分けます。
- **任意：本人の Google アカウントから自動で見分ける（既定はオフ、未検証）**：管理者は「管理 → 連携 → Google」で **接続済みの Google アカウントで Google Chat の送信者を識別する** をオンにできます（`config.toml [google] chat_identity_from_account = true`。既定は `false` で、設定がない場合はオフ扱い。`config.toml` が読めない・値が真偽値でない場合はエラーとして扱い、直すまで Google Chat の送信者を誰も見分けません）。オンにすると、本人が **自分の接続** で Google アカウントを連携していれば、手動で紐付けなくても Google Chat で本人と見分けます。Chat の送信者の ID と、メンバーが接続した Google アカウントの ID を照合し、一致すれば本人とみなします。**この照合は実際の Google Workspace ではまだ検証されていません**。Google Chat のユーザー ID とログイン用アカウント ID が別の種類の番号だった場合、偶然一致すると別の人を本人と見なすおそれがあるため、既定はオフです。ご自身の Workspace で 2 つの ID が一致することを確認していない限り、オフのままにしてください。オンの間、自動で見分けた ID は行にリンクの印付きで表示され、ここでは解除できません。本人が Google の連携を解除する、アカウントが停止・退職・削除される、または設定をオフにすると無効になります。設定の変更はセキュリティ監査ログに `config_changed` として記録されます。
- **1 人の Chat ユーザーは 1 人のメンバーだけ**：すでに別のメンバーに紐付いている Chat ID の紐付けは理由付きで拒否されます。自動照合がオンのときは、別のメンバー自身の Google アカウントから見分けられている Chat ID も拒否されます。手動の紐付けと誰かの Google アカウントが別の人を指す場合は、どちらも使わず、送信者は不明として扱います。自動照合がオンで Google アカウントの連携記録を読めない場合も、Google Chat の送信者は不明として扱います。
- **有効でないアカウントには紐付けられません**：停止・退職・削除されたアカウントには、どのチャネルの ID も紐付けられません（HTTP 409。アカウントが存在しない場合は 404）。
- **Google Chat の ID は本人確認専用です**：DuDuClaw から送る通知・承認カード・ダイジェストなどは Google Chat のユーザー ID には送られず、引き続き本人の Telegram／LINE／Discord／Slack などの DM に届きます。Google Chat だけを紐付けたメンバーは、Google Chat で発言すると本人と見分けられますが、そこで通知は受け取りません。人ではない送信者（別の Chat アプリ）からのメッセージは無視されます。
- **解除**：Google Chat の ID にカーソルを合わせて × を押します。このページで解除できるのは管理者が作った Google Chat の紐付けだけです。他のチャネルは従来どおりです。
- Google Chat の紐付けと解除はセキュリティ監査ログ（`googlechat_identity_bound`、`googlechat_identity_unbound`）とアカウント監査ログに記録されます。

API（管理者 JWT）：`POST /api/channel-identity/bind {user_id, channel, channel_user_id}`、`POST /api/channel-identity/unbind {user_id, channel: "googlechat", channel_user_id}`、`GET /api/channel-identity/list?user_id=`（Google アカウントから見分けた項目には `"source": "google_account"` が付き、自動照合がオンのときだけ表示されます）。設定は `google.credentials.get`（`chat_identity_from_account`）で読み取り、管理者だけが `google.integration.set {chat_identity_from_account: bool}` で書き込めます。セルフサービスで Google Chat の紐付けを作る方法はありません。

`GET /api/channel-identity/list?user_id=` は `identities[]` の各項目に `proof_status` と `proven_at` を返します。本人が確認済みなら `self_confirmed`、それ以外は `admin_prefilled` です。`proven_at` は RFC 3339 の日時または `null` です。Google アカウントから自動認識された項目は `admin_prefilled`、`proven_at: null` となります。

## メンバーのAI分身

Admin は「ユーザー → 編集 → AI分身」で、そのメンバーのオーナーまたは操作権限のあるAI、または「なし」を選び、「AI分身を設定」を押します。同じAIを複数のメンバーの分身にはできません。このボタンは分身だけを保存し、他の項目は別途「保存」で変更します。分身の指定時にはメインAIも同じスタッフに設定し、分身の解除時はメインAIを保持します。退職処理では分身を解除して再割り当て可能にし、既存の紐付け移管は維持します。会話やメモリの閲覧権限は変更しません。

アップグレードでは、有効なメンバー1人だけが選び、オーナーまたは操作権限の紐付けが残っているメインAIのみを分身に引き継ぎます。複数人が共有する設定はそのまま残し、管理者の「AI分身の競合」に表示します。各メンバーを編集し、異なる分身を指定してください。この引き継ぎは1回だけで、解除した分身を再起動時に復元しません。

`users.set_avatar {user_id, agent_id: string|null}` と `users.avatar_conflicts {}` はAdmin専用です。競合は `{conflicts: [{agent_id, user_ids}]}` で返します。AIの存在、現在の紐付け、重複を確認し、監査記録と接続中の設定更新を行います。`users.me`、`users.list`、ログイン／セッションのユーザーデータには nullable な `avatar_agent_id` を追加し、既存の `primary_agent_id` 出力は維持します。メンバー追加RPCでは `avatar_agent_id` は任意です。画面のフォームは選択した分身と操作権限を同時に作成します。

ネイティブ Linux の社員分離（今後のバージョンで提供予定、現在のバージョンでは利用できません）が有効な場合、管理者は、メンバーに現在割り当てられている AI 分身の会話と記憶を、追加のパスワードや TOTP 確認なしで直接閲覧できます。会話一覧、会話・記憶の検索、関連するリアルタイム更新も対象です。管理者による閲覧ごとに、閲覧者、分身、所属メンバー、操作を監査記録に残し、記録できなければ閲覧を拒否します。他のメンバーの権限は増えません。現在の分身ではない個人専用社員には、引き続き5分以内のパスワード＋TOTP 確認と `step_up_csrf` が必要です。分身の解除、有効な所有者の紐付けの喪失、分身状態の読み取り失敗が起きた場合は、直ちに厳しい従来の規則へ戻ります。書き込み、会話の復元、仕事の割り当て、設定、ファイル、Wiki の権限は変わりません。

`users.set_primary_agent {agent_id: string|null, user_id?: string}` は互換性のため維持します。分身があるアカウントには `avatar_primary_locked` と中国語・英語の説明を返し、管理者による変更が必要です。分身のないアカウントは従来どおりで、サイドバーの「既定のAIスタッフに設定」を利用できます。他人の設定には現在有効なAdmin権限が必要です。

従来のメインAI修復は分身の指定とは別です。最初の対話的なオーナー／操作権限の紐付けは空のメイン設定を補えますが、migration、restore、個人スタッフの作成では補いません。Admin専用の `users.repair_primary_agents` は `{}` で `{members, preview_digest, excluded_personal_count, changed:false}` を取得し、`{preview_digest}` で書き込みトランザクション内の同じ順序付き一覧を確認して適用します。分身は設定しません。保護モードでは個人専用スタッフを修復候補から除外し、管理者が代行できない紐付けも選択肢から除外します。`users.list` は紐付けを読めない場合に一覧全体を拒否します。`users.update` は `primary_agent_id` と `avatar_agent_id` を受け付けないため、専用メソッドを使ってください。

### Google Chat の返信とプレビューリンク

DM は既定でメイン画面に返信します。スレッド内のメッセージ（`threadReply = true`）には同じスレッドで返信し、スペースの動作は従来どおりです。「チャンネル → Google Chat → 動作 → DM の返信先」で「メイン画面」（既定）または「常にスレッド内」を選択できます。変更はダッシュボードの管理者のみ可能で、設定はチャンネル設定データベースに保存されます。`config.toml` に追加しないでください。会話セッションは引き続きスペース全体で共有します。

Google ドキュメント／スプレッドシートのプレビューリンクは信頼できないメッセージ本文として AI に渡されます。重複を除き HTTPS リンクを最大 10 件、各 2048 バイトまで保持し、制御文字を含むリンクは除外します。ゲートウェイはリンクにアクセスしません。読み取りツールの `links` 配列もスキャン対象です。名前がない場合は読みやすい代替名を使います。リソース名と保存パスはツール操作専用で、利用者には元の添付ファイル名を表示します。OAuth 権限の追加は不要です。

## 実行ステップの上限

実行ステップは別に設定します。グローバル `[runtime] default_max_turns` の既定値は **50**、`max_turns_limit` は **200**（整数 **1〜10000**）です。従業員の `[runtime] max_turns` は **1** からグローバル上限まで指定でき、省略時はグローバル既定値を使います。**0 は無制限ではありません**。設定の読み取り・解析・型エラー時は有効な低い制限を維持しつつ最大 50 ステップ（OpenAI 互換ツールループは最大 10 回）に制限し、従業員・設定値・適用上限ごとに重複を除いて警告します（プロセスごとに最大 256 組）。ファイルやキーの省略は既定値を使います。上限超過は実行時に補正し、ダッシュボード保存時には拒否します。増加には管理者権限が必要です。Owner は減らせますが、空欄に戻して既定値を継承する結果増加する場合も管理者が必要です。2 つのグローバルキーの変更も管理者のみで、既存の設定コミットと監査経路を使います。画面では時間上限の隣に表示します。ステップ増加は使用量と実行時間を増やす可能性があります。Claude のチャット、従業員のスケジュール・委任タスク、ターミナルチャットに適用します。進化、要約、評価などの内部処理は最大 50 ステップとし、それより低い設定は維持します。ネイティブ Linux 保護モードが対応するまで、保護された Claude gateway 呼び出しは最大 50 です。OpenAI 互換ツールループは従業員が明示した `max_turns` を使い、省略時は 10 回を維持します。使い切ると専用のステップ上限エラーを返します。無人の Claude／Grok 実行では対話型の質問ツールを無効にします。Claude のシステムプロンプトは上限に近づいたら進捗をまとめて終了するよう伝えます。主動チェックの独立した `[proactive] max_turns` は **1〜64** を受け付けます。

Web チャットの実行時間は対象従業員の実効タイムアウト（グローバル `max_timeout_secs` が上限）に配信の余裕 30 秒を加えます。既定の 1800 秒なら 1830 秒です。ゴールの `timeout_secs` は **30 秒**から `min(max_timeout_secs, 3600)` まで指定でき、グローバル上限を増やしても最大 1 時間です。

## 進展なしの制限と再開

全体の `[runtime] default_idle_timeout_secs` は既定 **900 秒**です。従業員の `[runtime] idle_timeout_secs` で上書きでき、省略時は全体設定を継承します。**0 は無効化**、それ以外は **60 秒から `max_timeout_secs` まで**です。全体値を省略し、上限が 900 秒未満なら既定値も狭まります。読み取り・解析エラー時は組み込みの 900 秒を使います。従業員の制限を延長・無効化する場合、または削除により長い既定値や無効化を継承する場合は管理者権限が必要です。短縮には不要です。ダッシュボードでは従業員編集と全体の実行制限で、時間上限の隣に表示します。

Claude のチャットとバックグラウンド実行、Codex JSONL、および OpenAI 互換 API の SSE 応答では、指定時間内にイベントが届かなければ停止します。ツールのイベントも進展に含みますが、90 秒ごとの定期通知は含みません。未完了のツールがある場合は最後のツール名を表示します。Grok と非ストリーミングの OpenAI 互換リクエスト／ツールループには、この経路で利用できるイベントストリームがないため総時間上限を使います。

ステップ上限（`max_turns`）、総時間切れ（`timeout_total`）、進展なし（`timeout_no_progress`）はそのターンを終了し、アカウントの健全性を下げず、別のアカウント・モデル・ランタイムで再実行しません。ツールが実行済みでも「制限時間内に最終回答が生成されなかった」と伝えます。通常のチャネル利用者には取得済みの部分回答を先に届け、停止通知を添えます。部分回答を会話のアシスタントターンに保存し、「続けて」でその文脈を引き継げます。Claude のステップ通知には適用済み上限を表示します。公開訪問者には一般的な安全メッセージと参照番号だけを表示し、部分回答、ステップ数、理由コード、運用上の案内は表示しません。

失敗通知の末尾には固定の小文字の理由コードとターン参照番号の先頭 8 文字を付けます。監査記録は `reason_code` と完全な `reference_id` を保持し、バックグラウンドではディスパッチ実行の参照番号を使います。Goal loop はこれらを `max_turns`、`timeout_total`、`timeout_no_progress` として一時停止し、インフラ障害回数に加算しません。

### v1.85 の Google ID 選択

社員の接続タブでは `delegate:owner`（管理者が主担当者のメールを確認、既定は `owner_only`、共用アカウントへのフォールバック不可）、個人接続の管理者テスト、任意の 120 文字サーバー名を持つ `external` を選べます。Google 連携ページには現在の担当者と確認状態を表示し、確認には管理者の追加認証が必要です。ウィザードは Chat 読み取りを事前選択しますが、保存するまで変更しません。設定の既定値はオフです。Chat 権限が不足する接続済みメンバーには再接続を案内します。サービス別スコープ、確認手順、テストの制限は [Google Workspace](google-workspace.md) を参照してください。

## ナレッジへの承認不要の追加

管理者が `[knowledge] owner_self_add`（既定はオフ）を有効にしたうえで、コレクション所有者が設定画面で承認不要の追加を有効にします。権限は所有者本人とその AI アバターのみに限定され、コレクションごとに 1 時間あたり最大 10 件です。インポートのトランザクション内で権限と現在の依頼者の身元を再確認し、読み取れない場合は承認カードを表示します。

検証済みの所有者本人のターンでは、自分の分身 AI が設定済みの専用コレクションに承認不要で追加できます。貼り付けたテキスト、URL、今回または以前の添付、ツールの結果、AI 自身が書いた要約など、内容の出所は問いません。空のテキストは拒否しますが、8 文字以上という制限はありません。システム実行、委任された作業、他のメンバーのターンには適用しません。

自動追加された新しいソースごとに、所有者への通知を 1 件永続化します。通知にはタイトルとソース ID だけを含め、本文やプレビューは含めません。所有者の検証済み DM に配信し、失敗時は再試行します。同じソースの再送信で通知を追加しません。到達可能な検証済み DM がなければ配信待ちで保持します。

既知のリスク：この機能を有効にすると、所有者のターン中に取得したウェブページなどが AI を誘導し、承認カードなしで資料を追加させる中程度のリスクを受け入れることになります。所有者はコレクションのスイッチをオフにできます。

## 会社の Google ログイン

`[google_signin]` は `google.signin.set` で管理します。「連携 → Google → 会社 Google アカウントでのログイン」でドメイン、管理者承認または直接作成、１日の上限、アバターテンプレート、承認時の MFA 登録事前許可を設定します。登録用のリダイレクト URI とチェックリストも表示します。無効化以外の保存には毎回パスワードと認証アプリのコードが必要です。有効で公開 URL が設定済みなら、ログイン画面に「会社 Google アカウントでログイン」が表示されます。「メンバー」（`/manage/users`）の「開通待ち」で申請を承認・却下し、複数選択で「Google ログインを一括確認」、行メニューで「Google ログインを解除」を使います。Google ログイン、Odoo、AI アバターのバッジも表示します。本人は「自分の接続 → Google ログイン」でパスワードを入力して有効・無効を切り替えます。Google から開通したメンバーのホームには５段階の案内があり、Odoo の項目は「自分の接続」を開きます。パスワードのないアカウントは、アカウント画面で Google による再認証を済ませてから２段階認証を変更します。個人版では利用できません。ログインの有効化、直接作成への切り替え、承認時の MFA 登録許可の有効化には、明示的なリスク確認が必要です。ログインには会社の Google OAuth クライアントと有効な `[dashboard] public_url` も必要です。

`google.signin.get {}` は `{settings, checks, redirect_uri, hash}`、保存成功時の `google.signin.set` は `{settings, hash}` を返します。文字列 `hash` は読み取った `config.toml` 全文のダイジェストです。Set は既存の設定項目、`step_up_csrf`、リスク確認に加えて、その get の `expected_hash` が必須です。単純な無効化も含め、設定コミットロック内で書き込みと一体で比較します。欠落、文字列以外、古い hash は書き込みを拒否します。再認証の免除、リスク確認、テンプレートのリビジョン確認は引き続き適用されます。

```javascript
const snapshot = await rpc('google.signin.get', {});
await rpc('google.signin.set', { ...signinForm, expected_hash: snapshot.hash });
```

| キー | 既定値／用途 |
|---|---|
| `enabled` | `false`。Google ログインの有効化を要求します。確認記録と空でない有効なドメインリストが必要です。 |
| `enabled_ack` | 既定では未設定。`{ by, at }` に管理者と時刻を記録します。両方とも空白でない文字列が必要で、専用設定メソッドだけが書き込みます。 |
| `allowed_hd` | 空リスト。設定メソッドは ASCII ドメインを 1～50 件受け付け、前後の空白除去、小文字化、重複除去を行います。検証済み ID トークンの `hd` と完全一致で照合し、サブドメインを含めません。 |
| `approval` | `"admin"` は承認申請、`"direct"` は直接作成。 |
| `daily_new_accounts` | `20`、範囲 1～200。直近 24 時間の新規上限で、承認待ち申請も含みます。 |
| `avatar_template` | 未設定または `""` は空白の分身。`"company:<key>"` は非有料の会社の単一社員テンプレート。 |
| `avatar_template_revision` | 会社テンプレートには正の整数リビジョンが必要です。不一致は管理者待ちになります。 |
| `approval_grants_mfa_enrollment` | `false`。管理者が承認時に初回 MFA 登録を明示的に許可できます。72 時間以内に 1 回限り。このキーだけでは許可を発行しません。 |

開始、コールバック、完了時に設定を読み直します。ファイルを読めない、または解析できない場合はログインを無効にします。`enabled` の欠落・型不正、確認記録の欠落・空白、空または無効な `allowed_hd` も無効になります。ドメインが一つでも不正ならリスト全体が無効です。`"direct"` の完全一致だけが直接作成を選び、他の値は管理者承認になります。上限の省略時は 20、不正な値は 0 となり、新規受付を拒否します。不正なテンプレートは分身作成を止め、空白へ切り替えません。MFA 事前許可は boolean の `true` のみ有効です。生の設定エディターはログインの無効化、確認記録の削除、セクションの削除だけを許可し、有効化や範囲拡大はできません。

管理者専用の `users.list {}` は `users[]` の各項目に `google_signin_linked`（真偽値）、`google_signin_linked_at`、`google_signin_last_signin_at`（日時または `null`）、`has_password`（真偽値）を返します。`signin_avatar` は `null` または `{state, reason, retry_allowed}` です。`state` は `pending`、`creating`、`retrying`、`waiting_admin`、`done`、`reason` は `done`、`name_taken`、`policy_changed`、`failed`、`protected_mode`、`template_changed`、`template_invalid`、`seats_full`、`not_eligible`、`unknown` または `null` です。再試行の表示は理由から推測せず、真偽値の `retry_allowed` に従います。

## 個人キーと Odoo 権限の設定（v1.86.0）

メンバーは「外部アクセス」（`/me/external-access`）でキーを作成する際、「自分の会話内容を含める」と外部ツールのスコープを選択します。作成後は範囲を狭める変更だけが可能です。管理者には同じ画面に２つの全体スイッチがあります。「連携 → Odoo」にはアップグレード通知、権限モード（エンジンのテーブル設定／Odoo アカウントに従う、リスク確認が必要）、「常に拒否」（既定項目を分類表示、削除には確認が必要、５つの固定拒否は維持）、「会社アカウントを使える AI」、既定で無効の「メンバー本人の Odoo アカウント」と資格情報一覧があります。「スタッフ編集 → 連携 → Odoo」の「権限を狭める」「現在の依頼者の Odoo アカウントを使う」と、テーブルごとの活動／内部メモ／フォロワー通知／添付は、それぞれ確認が必要です。本人は「自分の接続 → Odoo」で自分のログイン名とキーを入力します。管理者が許可するまでは「管理者が設定」と表示されます。管理者は「メンバー → 行メニュー → Odoo アカウントを取り消す」で資格情報を取り消せます。

| セクション／キー | 既定値と動作 |
| --- | --- |
| `[member_api_keys] allow_conversation_content` | `false`。`include_conversations=true` での作成を許可します。既存の付与は削除しません。旧キーは会話権限を保持し、移行済みと表示します。 |
| `[member_api_keys] allow_mcp_scopes` | `[]`。`tasks:read`、`agents:status`、`odoo:read`、`odoo:write` のみ。キーのスコープとの共通部分を毎回適用します。 |
| `[odoo] member_credentials` | `false`。メンバー本人の Odoo 接続を許可します。`odoo.member_credentials.set_enabled` で有効にするには `acknowledge_risk=true` が必要です。 |
| `[odoo_access] permission_mode` | 既定 `"engine"`。`"follow_odoo_account"` も選べます。後者は確認記録のある個人認証主体にのみ適用し、AI／会社アカウントは Engine のままです。 |
| `[odoo_access] permission_mode_ack` | 既定はなし。管理者 RPC が操作人と RFC 3339 時刻の `{by, at}` を記録します。欠落・無効時は Engine に戻ります。 |
| `[odoo_access] company_key_agents` | `[]`。会社アカウントを使用できる AI 社員 ID の一覧です。 |
| `[odoo_access] company_key_agents_migrated` | 移行前は空。システム管理の完了マーカーです。 |
| `[odoo_access] upgrade_notice_pending` | 既定 `false`。移行時に `true`。権限 RPC の `dismiss_upgrade_notice=true` で解除します。 |
| `[odoo_access] always_refuse` | 既定リストは下記。全モードに適用し、削除にはリスク確認が必要です。固定拒否 F1–F5 は残ります。 |
| `[odoo_access] attachment_max_mb` | `10` MiB、範囲 1–25。元ファイルと再エンコード後の両方に適用します。 |
| 社員 `[odoo] permission_override` | 既定 `"inherit"`。`"engine"`、`"read_only"` で制限を強められます。未知の値は読み取り専用です。 |
| 社員 `[odoo] act_as_requester` | `false`。確認済み依頼者の個人 Odoo 認証を使用します。アバターが別の人のアカウントを借用することはできません。 |

Engine モードでは、`odoo_execute` とボタン操作（`odoo_sale_confirm` を含む）の承認動作は v1.85 と同じです。従業員の承認リスト、操作ルール、効果分類は引き続き適用し、追加の強制承認はありません。「Odoo アカウントに従う」モードでは、読み取り以外の `odoo_execute` とすべての `action_*`、`button_*`、`toggle_*` 操作（`odoo_sale_confirm` を含む）に人の承認が必要です。フォロワーへのメッセージ（`odoo_message_send`）は全モードで常に承認が必要です。Allow ルールではこれらの強制承認を省略できず、承認はツールと正確な引数に結び付き、一度だけ使えます。

`[odoo_access] permission_mode` の `follow_odoo_account` への変更、`permission_mode_ack` の追加・変更、有効な `always_refuse` 項目の削除、`[odoo] member_credentials` の有効化は、Odoo 設定ページまたは専用 RPC（`odoo.access_set`／`odoo.member_credentials.set_enabled`）でリスクを確認してから行い、生の設定エディターや汎用設定書き込みでは変更できません。

バックアップ復元と CLI インポートでは、復旧を拒否せず権限を制限して続行します。Follow は Engine に戻り、確認記録は削除され、無効だったメンバーの Odoo アカウント設定は有効になりません。`always_refuse` は現在の環境とバックアップの有効なルールの和集合を保持し、リスト省略時は既定値を使います。AI の `act_as_requester` は無効化し、`permission_override` は `engine`／`read_only` のみを保持します。バックアップで省略された現在の制限も補います。制限した場合は Odoo 設定ページでの再確認を案内し、変更不要の設定は元の書式を保持します。

`always_refuse` の既定値：`unlink:*`, `create:ir.*`, `write:ir.*`, `execute:ir.*`, `create:res.users`, `write:res.users`, `create:res.groups`, `write:res.groups`, `method:execute_import`, `method:signal_workflow`。

管理者のブラウザー RPC `odoo.access_get {}` と `odoo.access_set` で読み取り・更新します。Set は `expected_hash` が必須で、`permission_mode`、`company_key_agents`、`always_refuse`、`attachment_max_mb`、`dismiss_upgrade_notice`、`acknowledge_risk` を受け付けます。Follow の選択、会社アカウント AI の追加、拒否ルールの削除には `acknowledge_risk=true` が必要です。変更は監査し、監査失敗時は書き込みません。不正な権限設定では Odoo 操作を拒否します。Engine の新ツールは `allowed_models` の明示的な対象モデルと、`allowed_actions` の正確な `activity:<model>`、`note:<model>`、`message:<model>`、`attach:<model>` が必要です。空リストでは許可しません。

正常な get/set 応答には `config.toml` 全文のダイジェストを表すトップレベルの文字列 `hash` が含まれます。Set は get の `hash` を `expected_hash` として渡す必要があり、設定コミットロック内で比較と書き込みを行います。`{readable:false, message}` に hash はありません。欠落または文字列以外は「設定頁的資料已過期，請重新整理後再儲存。」、古い hash は「設定已被其他人變更，請重新整理後再儲存。」を返し、設定を書き込みません。このガイドの3組の設定 RPC は同じ拒否メッセージを使います。競合時は再読み込みして内容を確認してください。

```javascript
const snapshot = await rpc('odoo.access_get', {});
await rpc('odoo.access_set', { attachment_max_mb: 5, expected_hash: snapshot.hash });
```

従業員ごとの変更には管理者のブラウザー RPC `odoo.agent_access_set {agent_id, permission_override?, act_as_requester?, acknowledge_risk?}` を使います。override は `inherit`、`engine`、`read_only` のみ受け付け、依頼者の ID の有効化や制限の緩和には `acknowledge_risk=true` が必要です。この 2 項目だけを変更し、有効な管理者セッションを再確認して書き込み前に監査します。監査失敗時は変更しません。`odoo.agent_config_get` は両項目を返し、生の設定やプロフィールの書き込みでは権限拡大を拒否します。操作画面は「スタッフ編集 → 連携 → Odoo」にあります。

会社 Odoo URL／データベースが設定済みの場合、アップグレード時に自分の Odoo アカウントを持たない既存の通常 AI を一度だけ `company_key_agents` に追加し、完了マーカーと通知を記録します。権限モードは変更しません。自分の Odoo アカウント設定が不完全な AI は追加されず、管理者による明示的な割り当てが必要です。 新規 AI は自動追加しません。移行後にリストを確認してください。

本人の接続はブラウザー限定の `me.odoo.status`、`me.odoo.connect {login, api_key}`、`me.odoo.test {}`、`me.odoo.disconnect {}` で管理します。先に status でサーバー／データベースを確認し、変更後は同じブラウザーセッションで読み直して再検証します。Connect と test は失敗・不正入力を含め、メンバーごとに毎分 5 回を共有します。パスワード変更、全端末サインアウト、利用停止後はキーの再入力が必要です。管理者は `odoo.member_credentials.list`、`.revoke {user_id}` で一覧・取り消しができますが、他人の秘密は設定できません。

v1.85.x に戻す前に `[member_api_keys]` の `allow_conversation_content`、`allow_mcp_scopes` を削除してください。旧版は未知のキーを含むセクションを無効と判断し、全個人キーを停止します。v1.85 は `[odoo_access]` を無視してグローバル Odoo アカウントに戻るため、新しい会社アカウント一覧や拒否ポリシーは適用されません。

管理者がダッシュボードのブラウザーにログインしている場合、`member_keys.policy_get {}` と `member_keys.policy_set {allow_conversation_content?: bool, allow_mcp_scopes?: string[], acknowledge_risk?: bool}` を利用できます。個人キーが無効でも操作可能です。正常応答はどちらも `{readable:true, enabled, allow_conversation_content, allow_mcp_scopes, available_mcp_scopes, risk:{conversation,mcp_scopes}}` です。設定の読み取り失敗や形式不正では get は `{readable:false, message}` を返し、set は拒否します。`[member_api_keys]` がテーブルでない場合も読み取り不能としてキーを無効にします。不明なフィールドと明示的な `null` は拒否します。

会話内容の許可やスコープの追加には `acknowledge_risk:true` が必要で、縮小には不要です。保存前に `member_keys_policy_changed` を監査記録へ書き、記録できなければ保存しません。`config.raw.set`、`system.update_config`、`google.integration.set` と通常の設定保存経路は、この 2 項目の権限拡大を拒否します。バックアップ復元と CLI インポートでは拡大部分を除去し、管理者に専用設定での確認を案内します。

`me.member_keys.list {limit?, cursor?}` は `policy:{allow_conversation_content,allow_mcp_scopes}` も返します。会話内容の許可は作成時のみ適用します。MCP は保存済みキースコープと現在の `allow_mcp_scopes` の共通部分を毎回適用し、スコープを再追加すると作成時にそのスコープがあった既存キーも再び利用できます。

`odoo.access_get {}` は権限設定が読み取れない、または形式不正の場合に `{readable:false, message}` を返し、その状態では `odoo.access_set` は保存を拒否します。正常な get/set は `readable:true` と `follow_mode_impact:{avatars_with_personal_credentials,agents_acting_as_requester}` を返します。値はそれぞれ、アバターが割り当てられ個人 Odoo 認証情報を保存している有効なメンバー数（再検証が必要なものも含む）、依頼者として操作する設定の AI 社員数です。 この件数は参考情報です。集計に失敗した場合は `follow_mode_impact` が `null` となり、get/set は引き続き成功し、有効な設定変更は通常どおり保存されます。
