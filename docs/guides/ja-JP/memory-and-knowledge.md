# 記憶とナレッジベース利用ガイド

AI社員は自分で物事を記憶しますが、あなたの指示どおりに知識をページとして整理することもできます。この2つはダッシュボードの同じ「記憶とナレッジ」ページに表示されますが、裏側ではまったく別の2つのシステムが動いており、使い方もタイミングも異なります。このページで両方の使い方を詳しく説明します。

一言で言うと:

- **記憶**：AI社員が自分で記録するもの。何も言わなくても、内容のある会話は自動的に要点を抽出して保存されます。
- **ナレッジベース**：まるごと残しておく文書。定款、SOP、仕様書のような長期的な参照資料を貼り付けると自動的に1ページへ整理されます。「ナレッジベースに記録して」と明示的に伝えることもできます。ナレッジベースはwikiと同じもので、呼び方が違うだけです。

---

## 1. 両者の違い

| | 記憶 | ナレッジベース（wiki） |
|---|---|---|
| 蓄積のされ方 | 自動的に蓄積、指示不要 | 定款／SOP／仕様書のような文書を貼ると自動作成；「ナレッジベースに書いて」と明示することも可能 |
| 保存形式 | 1件ずつの事実 | 1ページずつのMarkdown文書 |
| 分類方法 | システムが内容からトピックを自動分類 | ディレクトリ（フォルダ）＋あなたが指定するページパス |
| 古い情報の扱い | 同じ事実の新バージョンが自動的に置き換わり、履歴は保持される。古いほうの出典がより信頼できる場合は審査に回る | ページ全体を上書き；自動作成されたページはページ末尾に1行の改訂履歴を残す（2.4参照）、手動作成のページには残らない |
| 思い出されるタイミング | 3種類が自動的に注入される、それ以外は能動的に調べる必要あり | L0/L1は毎回自動注入、L2/L3は能動的な検索が必要 |
| 閲覧できる範囲 | このAI社員だけ | 個人ナレッジベースは本人のみ；共有ナレッジベースは全社員が閲覧可能 |
| 向いている内容 | 会話中にふと出てくる断片的な事実・好み・決定事項 | 返品ルール、見積もりフロー、製品仕様など長期的に参照する内容 |

選び方はシンプルです。**検索できる、編集できる、他人に見せる必要がある内容はナレッジベースへ。それ以外は記憶に任せておけばよい。**

---

## 2. ナレッジベースの使い方

### 2.1 ページの作成：会話でそのまま伝える

ダッシュボードを開いて編集する必要はなく、構文を覚える必要もありません。接続済みの任意のチャネル（LINE／Telegram／Discord／Slack／Web チャット）でAI社員にこう伝えるだけです。

```
幫我把退貨規則記到知識庫：七天內未拆封可退，運費由買方負擔。
```

```
今天查到的三篇論文重點整理成一頁放知識庫，標題叫「RAG 檢索方法比較」。
```

AI社員は1つのMarkdownページを作成し、インデックス `_index.md` を自動更新し、`_log.md` に1件の操作記録を残します。

**「ナレッジベース」と言わなかったらどうなるか？** 内容次第です。貼り付けた内容が定款、標準作業手順、仕様書、規程のような長期的な参照資料であれば、AI社員が自分で判断してページを作成します（2.4参照）。通常の会話、質問、その場限りの指示は記憶としてのみ保存されます。この判断は保守的です。雑談を文書化してしまうより、ページを作らずあなたにもう一言頼ませるほうを選びます。「ナレッジベースに記録して」と明示すれば常に有効です。この経路は変わっていません。

### 2.2 分類：自動選択、または指定可能

すべてのナレッジベースにはデフォルトで4つのディレクトリがあり、AI社員は書き込み時に内容から自動で選びます。

| ディレクトリ | 保存する内容 | 例 |
|---|---|---|
| `entities/` | 人物、企業、製品、顧客 | `entities/wang-ming.md` |
| `concepts/` | ドメイン概念、プロセス、原則 | `concepts/return-policy.md` |
| `sources/` | 一次資料の要約 | `sources/2026-07-30-rag-papers.md` |
| `synthesis/` | 複数トピックにまたがる分析・比較・傾向 | `synthesis/vendor-comparison.md` |

自分で指定したいときは「`concepts/` の下に、ファイル名は return-policy で」のように伝えます。指定がなければ上表のとおりに分類され、ファイル名はkebab-caseになります。

### 2.3 レイヤー：ページが「どれだけ思い出されるか」を決める

すべてのページのYAML frontmatterには `layer` フィールドがあり、これがナレッジベース全体で最も重要な設定です。

| レイヤー | 値 | 動作 |
|---|---|---|
| L0 Identity | `identity` | 毎回の会話に自動注入 |
| L1 Core | `core` | 毎回の会話に自動注入 |
| L2 Context | `context` | 自動注入されない、検索時のみ使われる |
| L3 Deep | `deep` | 自動注入されない、検索時のみ使われる（**デフォルト**） |

`layer` が指定されていないページは一律L3扱いになります。「書き込んだのに使われている様子がない」ページの多くは、L3のまま止まっているケースです。毎回思い出させたいときは、会話で「このページをコア層に設定して」または「layer を core にして」と伝えてください。

すべてのページには `trust`（0.0〜1.0の信頼度スコア）もあり、検索順位はこのスコアで重み付けされるため、人手でレビュー済みの内容が上位に来ます。

### 2.4 自動作成：何も言わなくても進むルート

文書を貼り付け、AIが「了解しました、記録しました」と返す。これまでは、それだけで何も残りませんでした。今はまず、そのテキストが長期的な参照資料かどうかを判断し、そうであれば自動的に1ページへ整理します。

**判断基準**（すべて満たしたときのみ作成、あえて高めのハードルに設定）：文書性のある名詞（定款、規程、規範、SOP、仕様書、マニュアル…）、条項番号や箇条構造、十分な長さ、タイトル行。逆に、一人称の好み（「私は〜が好き」）、時限的な依頼（「明日リマインドして」）、連続した質問はすべて減点対象になり、文書としては扱われません。

**自動作成されたページの保存先**：このAI社員自身のナレッジベース内、`auto/` の下にタイプ別で5つのディレクトリに分かれます。定款 `auto/charter/`、手順 `auto/sop/`、仕様 `auto/spec/`、規程 `auto/policy/`、その他 `auto/reference/`。あなたが手動で整理するディレクトリ（`entities/`、`concepts/`、`sources/`、`synthesis/`）に自動作成が触れることは決してありません。

**自動作成ページと確認済みページの違い**：

- ページの冒頭に、これが自動整理されたもので人の確認を経ていない旨の注記が入ります。
- 内容は原文をそのまま保持し、書き換えられることはありません（定款や契約書のような文書は、文言が変わることの代償が大きすぎるためです）。
- **会話に自動注入されることは一切ありません。** 自動作成ページはL2 Contextレイヤーに留まるため、AIが能動的に検索しなければ見えません。判断を誤っても、毎回の回答が汚染されることはありません。
- 検索順位の重みも、人手で書いたページよりはるかに低く設定されます。

**同じ文書を2回目に貼った場合**は同じページが更新されるだけで、2つ目のページは作られません。末尾の「改訂履歴」に1行追加されます。

**管理場所**：ダッシュボード「記憶とナレッジ → キュレーション → 自動作成」。各ページで次の操作ができます。

| 操作 | 効果 |
|---|---|
| 表示 | ページ全体の内容と改訂履歴を確認 |
| 正式な知識として承認 | このページが承認済みコンテンツに昇格し、毎回自動的に会話へ注入されるようになる |
| 共有ナレッジベースへ共有 | 共有エリアへ複製し、他のAI社員も読めるようにする |
| 削除 | ナレッジベースから消え、アーカイブへ移動する（復元可能） |

自動作成を完全に無効化したい場合：そのAI社員のナレッジベースディレクトリに `.scope.toml` を置き、`[namespaces.auto] mode = "operator_only"` を宣言します。これ以降は手動での書き込みのみが通ります。

### 2.5 個人ナレッジベースと共有ナレッジベース

- **個人ナレッジベース**：`~/.duduclaw/agents/<社員>/wiki/`、このAI社員だけが読めます。
- **共有ナレッジベース**：`~/.duduclaw/shared/wiki/`、全社のAI社員が読めます。社内規程、共通SOP、製品仕様はここに置きます。

共有エリアに書き込みたいときは明示的に伝えます。「これは共有ナレッジベースに置いて、みんなが見られるようにして」のように。

パーソナル版はナレッジベースが1つしかないため、ダッシュボードに「個人／共有」タブの切り替えは表示されません。

## 3. ナレッジベースがいつ使われるか

ここが最も誤解されやすい部分です。取得経路は2種類あります。

**自動注入（L0 + L1）**：会話が始まるたびに、システムはIdentityレイヤーとCoreレイヤーのページを現在の質問との関連度で並べ替え、6 KBの予算内でシステムプロンプトに詰め込みます。同じ会話セッション内では、選ばれたページは15分間固定され、変わりません。こうすることでprompt cacheが効きます。あなたは何もする必要がありません。

**能動検索（L2 + L3）**：それ以外のページは、AI社員自身が「この質問はナレッジベースを調べるべきだ」と判断し、検索ツールを呼び出すことに依存します。検索は全文検索で、信頼度スコアと情報源の種類で重み付けされます。

**では、こちらから念押しすべきか？** 通常は不要です。L0/L1の内容は毎回AI社員に見えていますし、L2/L3の内容も、質問にキーワードが含まれていれば大抵は自分から調べに行きます。

念押しする価値があるのは次の2つの場合です。

1. **回答が間違っている、あるいは曖昧なとき**、かつナレッジベースに正しい答えがあると分かっているとき → 「ナレッジベースを調べてから答えて」と伝えます。
2. **質問の言い回しがページの言い回しとかけ離れているとき**（例えば、ページには「返品ポリシー」と書いてあるのに「これいらなくなったらどうすればいい？」と聞く場合）→ ページ名を直接伝えるのが一番早い方法です。

## 4. 記憶の使い方

### 4.1 自動的に記憶される内容

| ソース | 記憶する内容 | ダッシュボード上の分類 |
|---|---|---|
| 会話蒸留 | 実質的な会話中の事実、決定、好み | 内容に応じて「仕事／顧客／好み」（工作／客戶／偏好）に分類 |
| キーファクト | 複数の会話にまたがって繰り返し出てくる要点 | 「観察とインサイト」（觀察洞察）タブ |
| 学習シグナル | 期待と実際の結果のズレ（回答の出来を示す） | 「学習シグナル」（學習訊號） |
| 利用フットプリント | アプリの利用時間とアクティブな時間帯（オプトイン） | 「利用フットプリント」（使用足跡） |
| ミス汎化 | 同種のミスが積み重なって導き出されたルール | 「ルールと意思決定」（規則與決策） |

**記憶されないもの**：挨拶、「了解」「OK」のような短い相づち、実質的な内容のない雑談。コストゼロの分類器がまずこれらを除外します。

**重複も二度と記憶されません**（v1.53以降）：セマンティック層への新しい書き込みは、まず既存の記憶と類似度を比較され、ほぼ同じ内容であれば書き込みが拒否されテレメトリとして記録されます。これにより、同じ事実が何十件もの近似記憶として積み重なり検索品質を薄めることを防ぎます。既存の記憶への通常の更新（言い直しによる置き換え、再確認）はこの影響を受けません。あなたがダッシュボードで手動整理する記憶もこのゲートを通りません。無効化したい場合は `config.toml` に `[memory] novelty_gate = false` を設定します（デフォルトは有効）。

### 4.2 いつ思い出されるか

3種類の内容が毎回の会話でシステムプロンプトに自動注入されます。

- **あなたに関するキーファクト**（プライベートな会話でのみ注入。グループで共有されるセッションではブロックされ、個人情報が公開の場に持ち込まれるのを防ぎます）
- **過去に犯したミス**（未解決の同種のミス）
- **学習済みルール**（ミスから汎化され、観察期間を通過したルール、最大3件。v1.53以降、実際のツール実行の証拠が伴うミス記録のみが汎化の対象になります。AI社員が「それは自分のミスだった」と自己申告しても、対応するツール記録が見つからなければルール生成には使われません）

それ以外の記憶は、AI社員が必要と判断して検索を実行する必要があります。検索順位は関連度、重要度、「最後に思い出されてからの経過時間」を総合的に見ており、頻繁に参照される記憶ほど長く生き残ります。

### 4.3 記憶は自動的に更新される

同じテーマについて新しい発言があると、古いほうは「取って代わられた」とマークされ、新しいほうに引き継がれます。どの記憶を展開しても完全な置き換えチェーンを確認でき、「ある時点での答えは何だったか」を調べることもできます。そのため、言い直すときに古いものを先に削除する必要はなく、新しいことをそのまま伝えるだけで構いません。

例外があります（v1.67.1 から）。チャットでの発言は、より信頼できる出典の事実（ダッシュボードで承認した内容や `migrate from` で取り込んだ内容など）を置き換えられません。新しい発言は保留され、ダッシュボードの受信箱（收件匣）に、現在の内容と新しい発言を並べた審査項目が現れます。承認すれば新しい発言が古いものを置き換え、却下すれば破棄されます。これらの項目はダッシュボードでのみ、24 時間以内に決定できます。詳しくは[メモリインテリジェンス](../../features/ja-JP/20-memory-intelligence.md#置き換え時の信頼度チェックv1671)を参照してください。

### 4.4 記憶の削除

記憶一覧で任意の項目にマウスを乗せると右側にゴミ箱アイコンが現れ、2回クリック（2回目が確認）すると削除されます。削除された記憶は検索、閲覧、会話への注入から即座に消えます。

内部的には論理削除です。データはアーカイブテーブルへ移動し、管理者はデータベースから復元できますが、保持期間を過ぎると完全に消去されます。

### 4.5 会話、スケジュール実行、インポートファイルを忘れる

AI 社員に、誰かが言ったことを忘れさせたいとき、あるいはスケジュール実行やインポートが入れるべきでない内容をメモリに入れてしまったときに使います。1件ずつの削除（4.4）では、目に見える項目しか消せません。この手順は、1つの出典から生まれたメモリをすべて、そこから派生したものも含めて削除し、同じ出典から再び学習されないようにします。以下のコマンドはすべてご自身のターミナルで実行します。社員のセッション内では実行できません。

始める前に：コマンドが把握しているのは、出典記録の機能が入ったあとに書かれたメモリだけです。それより前のメモリには出典記録がなく、プランは件数を表示しますが（`沒有完整來源紀錄的記憶`）削除はしません。この件数には、ディスパッチ実行のうち、バスメッセージが上流の会話の識別情報を半分しか運んでこなかったものが書いたメモリも含まれます。それらは実行そのものを出典として持ちますが、上流の会話を忘れても届きません。

1. 出典を一覧する。

```bash
duduclaw memory forget-source list --agent sales-rep
```

出力は会話ごとに1行です（スケジュール実行の系列、インポートファイルもそれぞれ1行）。セッションキー、角括弧内の出典の種類（`聊天訊息` チャネルのメッセージ、`員工自行存入` 社員が1ターンの中で自分で保存したもの、`排程／派工執行` スケジュールまたはディスパッチの実行、`外部 MCP 用戶端`、`匯入`、`足跡`）、その出典を持つメモリの件数、最新の書き込み時刻が出ます。1件のメモリは、その会話に出典がいくつあっても1行につき1回だけ数えます。1つのセッションの個々のメッセージや実行を見るには：

```bash
duduclaw memory forget-source list --agent sales-rep --session <session>
```

この場合は各行が1件のメッセージまたは1回の実行で、行末の `→ --message <値>` が `--message` に渡す値です。社員が1ターンの中で自分で保存したメモリは、そのターンを始めたユーザーのメッセージの下にまとめて表示されます（`含員工在這一輪自行存入的記憶`）。そのメッセージを忘れるとターンも一緒に忘れるためです。記録上きっかけのメッセージが分からないターンだけが、単独の `turn:` の行になります。

`--agent` は社員 id です。MCP クライアントが使うメモリの名前空間なら `external/<client>` または `internal/<client>` を指定します。

2. プランを作る。 忘れたいものに合う形を選びます。

| 忘れたいもの | コマンド |
|---|---|
| 特定のメッセージ | `duduclaw memory forget-source plan --agent sales-rep --session <session> --message 812,815` |
| 会話全体（現時点まで） | `duduclaw memory forget-source plan --agent sales-rep --session <session>` |
| スケジュールまたはディスパッチの1回の実行 | `duduclaw memory forget-source plan --agent sales-rep --session <session> --message run:<key>` |
| インポートしたファイル | `duduclaw memory forget-source plan --agent sales-rep --session import:/path/to/file` |

`--message` には `list --session` の矢印の後ろの値を指定します。メッセージ番号（`812` と `m:812` は同じメッセージです）か、`run:<key>` のようなキーです。`turn:`、`call:`、`item:`、`day:` のキーも同じように指定できます。ユーザーのメッセージを忘れると、同じターンの社員の返信も一緒に忘れます。返信はユーザーの発言を繰り返すことが多いためです。そのターンに社員が自分で保存したものも同じで、ターンは同じ出典として扱われ、あとでターンだけを名乗る書き込みもブロックされます。会話全体を忘れると、その中のすべてのターンが対象になります。`--show-snippets` は各メモリの先頭 60 文字を画面に表示します（保存はされません）。`--max-rows` と `--ttl-minutes` で、件数の上限（既定 50,000 件）とプランの有効時間（既定 30 分、最大 1,440 分）を変えられます。

`plan` は何も削除しません。プランを記録し、承認リクエストを出し、プランを表示します。次の部分を読んでください（コマンドの出力は中国語です。以下に引用する語句はその原文です）。

- `將刪除 N 筆記憶、N 筆關鍵事實、N 份封存副本、N 個自動建檔頁面`：削除される内容です。各対象の行には、メモリ id、種類とレイヤー、そしてどう見つかったかが出ます。`直接`（そのメモリ自体がその出典から来た）か、`衍生`（その出典に由来するものから派生した）です。
- `同一輪的員工回覆也一併忘記` と `個回合也一併設為不再學到`：同じターンの返信と、そのターンに社員が自分で保存したものは、同じ出典の一部です。`show` と `apply` のプレビューにも同じ行が出ます。
- `壓縮摘要`：圧縮サマリーは会話ごとに1つで、1件のメッセージや1回の実行の分だけを取り除くことはできません。そのため、どのプランでも会話全体のサマリーを消します（スケジュール実行なら `cron:<社員>` の会話全体）。出力にもその旨が出ます。
- `連帶影響`：削除予定のメモリを同時に支えている他の出典です。そのメモリは丸ごと削除されるため、別の出典が言ったことも一緒に消えます。忘れる出典に再度言及されただけのメモリは残ります（`保留，僅移除佐證紀錄`）。
- `需要人工檢視`：社員が自分で書いた wiki ページのうち、記録された出典が一致するものです。削除はされません。開いて判断してください。
- `對話紀錄`：社員が以後見なくなるメッセージの数です。原文は会話記録に残ります。
- `其他命名空間也記錄了同一段對話`：同じ会話を記録していた他の社員向けの、そのまま実行できる `plan` コマンドです。それぞれ別にプランと承認が必要です。このターンから仕事を引き受けた社員が保存したメモリにも、最初のプランを適用したあとでも、このコマンドで届きます。
- `套用時會設下 N 筆防止再學到的紀錄`：適用時に書かれるブロック記録の件数です。長い会話を忘れると、社員が何かを保存したターンごとに1件ずつ書かれるため、数千件になることがあります。
- `不在範圍內`：このコマンドが届かないものです。毎回読んでください（この節の最後の一覧を参照）。

3. ダッシュボードで承認する。 管理者がダッシュボードのやることリストを開き、プランの出力に示されたリクエストを承認します。カードには件数と出典のラベルだけが表示され、メモリの内容は表示されません。このリクエストがローカルのコマンドラインから来たことも明記されます。承認はこのプランそのものに結び付いています。チャネルのボタンでは承認できません。

適用せずに状況を確認するには：

```bash
duduclaw memory forget-source apply --plan <plan-id>
```

`--confirm` なしでは、プランをもう一度表示し、さらに `核准狀態：` という行で、承認が待機中か、通っているか、無効になっているかを示します。

4. 適用する。

```bash
duduclaw memory forget-source apply --plan <plan-id> --confirm
```

成功すると、削除したメモリ、キーファクト、アーカイブコピーの件数に続けて、後続ステップの結果が表示されます。後続ステップはメモリデータベースの外で行われます。自動作成された wiki ページの削除、レビューカードの取り下げ、忘れたメッセージを社員から見えなくすること、その会話の圧縮サマリーの消去です。

5. 後続ステップが終わらなかったとき。 結果が `DEGRADED`（終了コード 3）なら、メモリはすでに削除されブロック記録も設定済みですが、一部の後続ステップが失敗しています。次を実行します。

```bash
duduclaw memory forget-source resume --plan <plan-id>
```

稼働中の gateway も、起動時とその後 10 分ごとに、未完了のステップを再試行します。再実行するものが残っていなければ、`resume` はそう表示します（`沒有需要補跑的後續步驟`）。

プランが期限切れ、またはデータが変わったとき。 適用が `計畫已過期` で拒否された場合、またはプラン作成後にデータが変わったというメッセージで拒否された場合は、何も削除されていません。古くなったことによる拒否では、同時に当てはまる理由がすべて列挙されます。同じ名前空間で別の忘却が行われた、メモリが追加・消失・変更された、プランの他の部分（レビューカードや会話記録など）が変わった、といったものです。古いメモリのバックグラウンドでのアーカイブや、別の社員が同じ会話を記録したことのように、適用の内容を変えない書き込みではプランは古くなりません。適用結果には、2つの参考値（`沒有完整來源紀錄的記憶` と他の名前空間の参照数）のプラン時と適用時の値が並んで表示されます。その社員を一時停止し、`plan` をやり直して、新しい承認を取ります。承認はプランと一緒に期限切れになるため、期限切れのプランは必ず作り直しになります。

大きなプラン。 プランの対象が 5,000 件を超えると、`apply` は数秒間メモリストアをロックし、プランの出力にもその旨が出ます。適用する前にその社員を一時停止してください。

この手順がしないこと。

- 出典から派生したメモリを削除し、同じ出典から再び学習することを防ぎます。会話の原文（社員が見なくなるだけです）、送信済みメッセージ、バックアップ、他の社員が受け取った内容は削除しません。
- このコマンドが触れない場所を通じて、内容が社員の手元に戻ることがあります。毎ターンプロンプトに入るツール呼び出しの記録とエラーノート、タスクボードと `/goal` の文章、ワーキングステート、Agent Mail、ゴールの状態と審査のフィードバック、引き継ぎのコピー、社員間で受け渡された返信、他の種類のレビューカード、ユーザーのホームディレクトリにある Claude CLI 自身の会話記録、返信のたびに書かれる強化学習の軌跡ファイル（`rl_trajectories.jsonl` と `rl_trajectories/` ディレクトリ。会話全体の原文が入っており、どのメッセージを消すべきかを特定できる番号がありません）、共有 wiki のコピー、そして社員が自分で書いた wiki ページです。このページは削除されません。この機能が入ったあとに書かれたページはレビュー用に一覧され、それより前のページは出典が記録されていないため、一覧にもなりません。Gemini CLI ランタイム経由で保存されたメモリは会話に結び付いておらず、対象外です。Grok の社員のメモリが会話に結び付くかどうかは未検証です。
- ターンがきっかけのユーザーメッセージと結び付くのは、そのターンで社員が少なくとも1件メモリを保存した場合です（既存のメモリの言い直しも含みます）。そのターンで何も保存していなければ対応が記録されず、そのメッセージを忘れても、あとでそのターンだけを名乗る書き込みには届きません。会話全体を忘れた場合は対象になります。
- チャネルの返信をまずローカルモデルで処理する設定（`inference_mode = local`）では、その段階で社員がツール経由で保存したメモリは会話に結び付いておらず、会話を忘れても届きません。
- 社員があとで新しい会話で同じ内容を知り直した場合は新しい情報として扱われ、ブロックされません。
- 忘却より前のバックアップから復元すると、削除したメモリが戻り、ブロック記録も消えます。この機能を使ったあとは、この機能のないバージョンへダウングレードしないでください。
- `config.toml` の `[memory] forget_source = false` で、新しいプランの作成と適用を止められます。ダッシュボードの承認にスイッチはなく、これで無効にはなりません。

## 5. どちらを使うべきか

| やりたいこと | 方法 |
|---|---|
| 短い返答を好むことを覚えさせたい | そのまま伝える。自動的に記憶される |
| 毎回同じ返品ポリシーに従わせたい | ナレッジベースに書き、`layer: core` を設定する |
| 今日調べた論文の要点を整理したい | ナレッジベースに書き、`sources/` に置く |
| 全社のAI社員が従うべき規程 | 共有ナレッジベースに書く |
| 覚え違いを訂正したい | 正しい内容を伝えるだけ。古いものは自動的に置き換わる。古いほうの出典がより信頼できる場合は、ダッシュボードの受信箱で審査項目を承認する |
| 誤った記憶を1件削除したい | 記憶一覧でマウスを乗せてゴミ箱アイコンをクリック |
| ある文書全体を忘れさせたい | ナレッジベースからそのページを削除する |
| 会話、スケジュール実行、インポートファイルを忘れさせたいと頼まれた | 出典単位の忘却。4.5 を参照 |
| 会社の定款を貼って後で調べられるようにしたい | そのまま貼るだけで自動作成される。キュレーションで正式な知識として承認すれば毎回注入される |
| 自動作成されたページを1件削除したい | キュレーション → 自動作成 → 削除 |

## 6. よくある質問

**Q：ナレッジベースとwikiは別物ですか？**
同じものです。インターフェース上は「ナレッジベース」と表示されますが、内部のファイル構造とMCPツール名は引き続き「wiki」を使っています。

**Q：AI社員に「ナレッジベースに書いて」と言う必要はありますか？**
定款、SOP、仕様書のような文書であれば不要です。自動的に作成されます（2.4参照）。それ以外の場合は伝える必要があります。判断に迷うときは作成しない方向に傾くため、確実にページを残したいなら明示的に伝えるのが一番早い方法です。

**Q：ナレッジベースは分類できますか？それとも自動分類ですか？**
両方成り立ちます。4つのデフォルトディレクトリは内容から自動的に選ばれますが、パスを自分で指定することもできます。レイヤー（L0〜L3）はデフォルトでL3ですが、明示すれば変更できます。

**Q：どんなときにナレッジベースが使われますか？念押しは必要ですか？**
L0/L1は毎回の会話に自動注入され、L2/L3はAI社員が自分で検索するかどうかに委ねられます。通常は念押し不要です。回答が間違っているときや言い回しが大きくずれているときは「ナレッジベースを調べて」と一言伝えるのが最も効果的です。

**Q：記憶とナレッジベースの内容が重複したらどうなりますか？**
ナレッジベースが優先されます。内容を注入する際にシステムが重複を確認し、すでにナレッジベースのページに含まれている事実は記憶から重ねて注入されません。

**Q：記憶は際限なく増え続けますか？**
いいえ。長期間思い出されず重要度の低い記憶は徐々にアーカイブされていきます。頻繁に参照される記憶は残り続けます。
