# 員工使用分析：以使用者為單位的 AI 用量

老闆想問的問題很單純：哪個員工在用 AI、用來做什麼、花了多少錢？DuDuClaw 用它原本就在蒐集的 token 用量遙測資料回答這個問題，現在多了依終端使用者與依頻道歸戶的能力。

## 隱私邊界（請先讀這一段）

這個功能揭露的是公司 AI 資源的使用狀況，跟公司稽核企業信箱或 VPN 存取紀錄是同一類事。有兩條規則讓它不至於變成監控：

- **先看總量。** 預設畫面顯示的是每個使用者的總計（請求次數、token 數量、費用）。使用報表裡不會出現任何人的個別訊息內容。
- **看細節要有操作者權限。** 要往下鑽看某個人具體問了什麼，屬於操作者層級的動作，而且這個動作本身也會被稽核。

任何會對個人評分或標記的下游功能（提問品質輔導、私人用途偵測）都是選用（opt-in）、預設關閉，並且文件上明白寫著「僅供提醒，絕不能作為懲處依據」。

## 依使用者歸戶的成本

現在每一次頻道回覆都會連同 agent 與 token 數量一起，記下終端使用者 id 與頻道。`token_usage` 資料表透過一次冪等的 migration 新增了兩個欄位（`user_id`、`channel`）；既有的資料列照常運作，只是讀出來會顯示為未歸戶。

查詢方式：

```text
> cost_users            # MCP 工具，admin 權限範圍
{ "hours": 24 }
```

回傳結果會依費用排序列出每個使用者：

```json
[
  { "user_id": "u-alice", "total_requests": 42, "total_input_tokens": 130000,
    "total_output_tokens": 8000, "total_cost_millicents": 5400 },
  { "user_id": "(system)", "total_requests": 12, ... }
]
```

`(system)` 這個桶子裝的是沒有終端使用者的非人類流量（sub-agent dispatch、evolution、utility 呼叫）。

## 目前已經歸戶的範圍

Channel-reply 路徑（大多數頻道共用的入口）會歸戶使用者與頻道。沒有真人使用者的路徑（sub-agent dispatch、cron、evolution）依設計一律記成 `(system)`。把各頻道剩下的媒體／工具子路徑接上同一套歸戶機制，是一項還在進行中的清查工作；還沒接上的路徑，花費依然會算在該 agent 頭上，只是還沒歸到特定使用者。

## 路線圖（選用，預設關閉）

- **提問品質輔導。** 定期批次用一個便宜的模型，對每個使用者的部分訊息取樣評分（清晰度、有沒有明確可執行的目標），產出一份「建議受訓」名單。只有彙總分數，名單裡不含任何訊息內容。
- **用量異常標記。** 沿用既有的燒錢速率異常演算法，當某個使用者的花費偏離自己的基準線達 N 個標準差就會被標記。完全不做語意判斷，因此沒有誤指控的風險。
- **私人用途偵測（語意層）。** 防止誤判的機制已經實作完成（`workforce_private.rs`）：沒有操作者定義的業務範圍基準線就拒絕執行（fail-closed），只標記高信心度的「疑似私人用途」（絕不標記「無法判斷」），尊重豁免名單，未確認的標記 30 天後自動失效。標記只是建議性質（「建議關注」），員工本人看不到，也明白寫著不能作為懲處依據。Haiku 分類批次與僅限操作者使用的審核介面，都是建立在這些防護機制之上的。
