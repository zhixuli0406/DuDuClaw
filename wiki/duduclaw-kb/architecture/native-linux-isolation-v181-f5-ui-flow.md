# F5：受保護模式管理介面流程（v1.81.0，待 owner 確認）

狀態：流程草稿，2026-11-08。照「流程確認 → 設計畫布 → 實作」的順序，這份只定流程與資訊，不定版面。
後端都已實作（A4、C3、C5、C6、E4、SR2），本頁只列畫面要接哪些 RPC。

## 誰會用到

| 角色 | 要做的事 |
|---|---|
| 管理員 | 建立受保護員工、核准同仁的申請、設定連接器帳號、匯入舊帳號、撤銷、註銷員工、設定 Google 租戶來源 |
| 一般同仁 | 申請自己的「個人 AI 員工」、看申請進度、核准自己個人員工的委派請求 |
| 個人員工的主人 | 同上的委派核准（個人員工要把工作交給共用員工時） |

## 入口

1. 受保護模式啟用後，「設定」群組新增一頁 **受保護模式**（newIn 1.81.0；個人版不顯示，受保護模式只在企業版）。
2. 頁首沿用 F4 的就緒狀態列；F3 的每個原因都連到下面對應的分頁。
3. 同仁端放在「我的帳號」底下新分頁 **我的個人 AI 員工**。

## 管理員：受保護模式頁（四個分頁）

### 分頁一：AI 員工
- 清單：員工名稱、類型（個人／共用）、主人（個人員工才有）、狀態（運作中／待核准／已註銷）、就緒原因。RPC `isolation.employee_list`。
- 「同仁的申請」區塊：列出待處理申請（申請人、想要的名稱、申請時間）。
  - 按「準備」→ 確認對話框（顯示將建立的員工與主人）→ 身分再驗證（step-up，密碼＋兩步驟）→ `isolation.employee_propose`（帶 request_id）。
  - 準備好的申請出現在既有的「核准中心」卡片（`migration.confirmations` 流程），按「同意／拒絕」。和 B 畫布一致：過時的只能拒絕。
- 「新增共用員工」：按鈕 → 名稱 → step-up → `isolation.employee_propose`（binding_kind=shared）→ 同樣進核准中心。
- 註銷：員工列的選單 →「註銷」→ 說明「資料會移到隔離區，無法再使用，這個名稱之後也不會沿用舊資料」→ step-up → `isolation.employee_tombstone`。
- 清理：「清除已拒絕／已過期的申請」→ step-up → `isolation.employee_purge_requests`。

### 分頁二：連接器帳號
- 依員工分組的清單：服務（Google／Notion／GitHub／Odoo／資料庫／網站登入／通道）、帳號名稱、歸屬（個人：某同仁／共用）、狀態（可用／需要設定／已撤銷）。RPC `isolation.connector_list`。
- 「新增連接器」精靈：選員工 → 選服務 → 依服務填參照（資料庫來源名稱、網站憑證、通道與範圍、權杖來源 home/agent）→ 預覽 → step-up → `isolation.connector_provision`。只能選系統裡已登記的來源，畫面上不輸入任何密碼或權杖。
- 撤銷：列選單 →「撤銷」→ 說明「正在進行的工作會在下一次呼叫被拒」→ step-up → `isolation.connector_revoke`。
- 「匯入舊版帳號」：按鈕 → 說明會產生待核准提案、不會直接生效 → step-up → `isolation.connector_import_legacy` → 結果摘要（產生幾筆、幾筆因無法證明擁有者而略過）→ 連到核准中心。

### 分頁三：Google 租戶來源
- 顯示目前來源：未設定／網域委派／服務帳號（只顯示狀態與金鑰指紋，不顯示金鑰）。
- 編輯「服務信箱」清單與「允許的權限範圍」清單（E4 的 `service_mailboxes`、`tenant_scopes`）。存檔走既有 `google_identity` 設定 RPC。
- 說明文字：委派只能代表提出要求的同仁本人，或這裡列的服務信箱。

### 分頁四：紀錄
- 連接器建立／撤銷、員工核准／註銷、委派核准的稽核紀錄（沿用既有稽核查詢，篩選這幾類）。

## 同仁：我的個人 AI 員工（「我的帳號」分頁）
- 若已有個人員工：顯示名稱、狀態、可用的個人連接（Google 等）與「重新連結」入口（沿用既有個人 Google 連線流程）。
- 若沒有：「申請個人 AI 員工」→ 填想要的名稱與顯示名稱 → 送出 → `me.isolation.request_personal_employee`。說明「需要管理員核准」。每人同時最多 3 筆、24 小時內最多 10 筆，超過時顯示原因。
- 申請紀錄：`me.isolation.list_personal_employee_requests`（待處理／已核准／已拒絕／已過期）。
- **委派請求**：個人員工想把工作交給共用員工時出現卡片，顯示「哪位個人員工 → 哪位共用員工、任務內容（截 200 字）」，按「同意／拒絕」→ `me.isolation.decide_personal_delegation`；清單 `me.isolation.list_personal_delegations`。說明「同意後，任務內容可能被其他能使用該共用員工的同仁看到」。卡片 24 小時過期。

## 共通規則
- 所有會改變狀態的管理動作都要 step-up（5 分鐘內有效），沿用遷移頁已有的再驗證對話框。
- 錯誤訊息用白話：不出現 binding、generation、catalog、tenant id 等內部詞。
- 不顯示任何秘密值；金鑰只顯示指紋。
- 鍵盤可操作、WCAG AA、深淺色主題，沿用 Calm Glass 元件。

## 要 owner 確認的流程點
1. 受保護模式頁放在「設定」群組，分四個分頁（AI 員工／連接器帳號／Google 租戶來源／紀錄）。
2. 同仁端放在「我的帳號」的新分頁，委派核准也放在這裡（不放進管理員的核准中心）。
3. 「匯入舊版帳號」只產生待核准提案，管理員在既有核准中心逐筆核准。
4. 註銷員工後資料移到隔離區，介面不提供還原（要還原請找原廠支援）。

確認後依此畫設計畫布（沿用 v1.81 已核准畫布的風格），再實作。

## Owner 決定（2026-11-08）
1. 照草稿：「設定」群組一頁「受保護模式」，四個分頁。
2. 同仁端放「我的帳號 → 我的個人 AI 員工」，委派核准卡也在這裡。
3. 「匯入舊版帳號」產生的提案**可整批核准**：核准中心多一個「全部同意」（仍逐筆顯示服務、歸屬、參照；整批前再 step-up 一次，並列出將生效的筆數）。
4. **註銷要提供還原**：需要新增後端流程（從隔離區還原到同一員工 ID、原主人仍須在職且同意、還原前不得有同名新員工；個人員工還原給原主人，不能轉給別人），先寫設計並送安全審查再實作（新任務 F6）。
