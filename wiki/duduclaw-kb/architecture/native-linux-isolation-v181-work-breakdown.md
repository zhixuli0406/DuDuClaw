## Decisions
- D-1 Personal employee creation: no path creates one today (`duduclaw-migration/src/import_manifest.rs:173`
  stages proposals only from import; importer maps legacy bindings to `shared:` at
  `duduclaw-import/src/authority.rs:207`; `binding_plan` accepts only `shared:` at
  `handlers/migration_authority_bindings.rs:17`; `agents_create.rs` has no allocation path).
  Proposed: admin-only `isolation.employee_propose` with `binding_kind` + `owner_id` through the existing
  approval → allocation flow (A4).
- D-2 One connector account store: `ConnectorCatalog` (`isolation_connectors.rs:14-55`) becomes the only
  production store with binding + generation; standalone `BindingStore` stays a test double.
- D-3 Google sources: bridge supports Personal + Home OAuth; delegate / service-account refused at
  `google_identity/isolation_bridge.rs:76-78`; Apps Script has no connector tool.
- D-4 29 non-connector tools without production selectors (`mcp_isolation_parity_tests.rs:97-105`:
  file_read, execute_program, web_extract, …) are outside A–G.
- D-5 (E4, new rule) Google tenant-source subject in protected mode. Tenant sources are the existing admin
  config only: domain-wide delegation = sealed `protected/google-service-account.sealed` + the employee's
  `agent.toml [google] identity = "delegate:<S>"`; service account = `config.toml
  [integrations.google_service_account]` (`key_file` + `subject = S`) on the `home` identity. Both are served
  only through the Shared employee's own SharedTenant Google route of its pinned tenant. The subject S comes
  only from that config (never employee arguments, env or run metadata; argument keys that name an identity
  are refused) and is admitted only if, comparing normalized emails by exact equality with users.db:
  (a) S ∈ `[integrations.google_identity] service_mailboxes` AND no users.db account has email S ⇒ Shared
  action, any requester the Shared employee's authority admitted (Human or System); or (b) delegate only:
  exactly one users.db account has email S, it is Active, and the authenticated requester (capability
  principal + verified run association) is that account by exact user id ⇒ Personal-like action. Everything
  else refuses (undesignated non-person S, a person's S for anyone else or for System, ambiguous S, a person
  listed as a service mailbox, a service account acting as a person). Personal employees never use tenant
  sources. Tools are limited to `[integrations.google_identity] tenant_scopes` (each must be a minted
  scope; empty ⇒ status only). No home fallback: `fallback = "home"` on a delegate, or an Apps Script bridge
  beside the service account, refuses.

Shared→anything is unchanged.
