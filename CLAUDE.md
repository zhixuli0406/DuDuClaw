# DuDuClaw Project Guidelines

## Highest directive: every new feature and every fix gets its own branch

Owner instruction, 2026-10-03: 「每次有新功能與修復時都開分支」. It outranks every other workflow rule in this file.

- Before starting a feature or a fix, create a branch from the latest `origin/main` (`feat/…`, `fix/…`, `docs/…`, `chore/…`). Feature and fix commits never go on `main` directly.
- The change reaches `main` through a pull request. `main` requires five checks on a PR merge: Rust ubuntu-latest, Rust macos-latest, Dashboard, Python, Security Audit (`cargo audit`, required since 2026-10-08). The ECC Tools app comments on PRs (security evidence, risk taxonomy and other audits); its results are advisory and not required checks.
- When another session is using the main checkout, work in a separate `git worktree` instead of switching branches there.
- When several open PRs touch the same files, merge them in the order the owner gives; the later one rebases.
- Opening a branch is not permission to merge or release. Merging a PR and cutting a release stay the owner's decision.

DuDuClaw is a **Multi-Runtime AI Agent Platform** — supporting **Claude Code / Codex / Gemini (deprecated, removal scheduled for v1.72.0)** CLI as AI backends via a unified `AgentRuntime` trait with auto-detection and per-agent configuration. DuDuClaw provides the plumbing: channel routing, session management, memory, evolution, multi-account rotation, local LLM inference, and browser automation.

Key architectural decisions:
- **Multi-Runtime** (`AgentRuntime` trait) — Claude / Codex / Gemini (deprecated, removal scheduled for v1.72.0) / Antigravity (`agy`) / OpenAI-compat five backends, `RuntimeRegistry` auto-detection, per-agent config in `agent.toml [runtime]`. **Runtime parity (v1.33)**: `RuntimeContext` carries `CapabilitiesConfig`; codex/gemini spawn with capability-derived sandbox flags (`SandboxLevel` ReadOnly/WorkspaceWrite/FullAccess — no more blanket `--full-auto`/`yolo`; antigravity maps ReadOnly/WorkspaceWrite to `--sandbox` and FullAccess to `--dangerously-skip-permissions`, never both); PTY-pooled sessions inject per-agent `--allowedTools`/`--disallowedTools` (previously zero restrictions reached the pool); codex/gemini/antigravity `execute()` register the duduclaw MCP server in each CLI's native config (codex `-c` overrides, gemini settings.json per-key merge, antigravity `<work_root>/.agents/mcp_config.json` with identity forwarded through the spawn env — see the v1.67.0 block) so non-Claude agents get the full MCP tool surface; `agent create --runtime` scaffolds `AGENTS.md`/`GEMINI.md` and rejects typo'd providers; `model_matches_provider()` warns on `[model] preferred` ↔ `[runtime] provider` mismatches
- **Unified LLM provider layer** (`duduclaw-llm` crate, v1.33): the API-level twin of the CLI-level `AgentRuntime` — one normalized `ChatRequest`/`ContentPart`/`StreamEvent`/`NormalizedUsage` shape over four native protocols: Anthropic Messages (layered `cache_control`, thinking replay, real SSE), OpenAI **Responses API**, Gemini `generateContent` (`thoughtSignature` echoed verbatim), OpenAI-compat chat/completions (8 presets: deepseek/minimax/groq/together/mistral/openrouter/xai/qwen + local; DeepSeek `reasoning_content`, real SSE). `ModelRegistry` vendors ~15 models with millicent/MTok prices + price-cliff math + capability flags (user override via `~/.duduclaw/models.toml`). Tool-call args are always parsed `serde_json::Value` at the boundary; errors classify into a ten-way `LlmError` aligned with `FailureReason`. **MCP client + tool-loop** (`mcp_client.rs` behind default-on `mcp-client` feature, `tool_loop.rs` always-on): a stdio JSON-RPC MCP client + provider-agnostic `run_tool_loop` so the direct-API, local-inference, **and the multi-runtime openai-compat `AgentRuntime` dispatch path** get the full MCP tool surface (previously tools were CLI-backend-only; the openai-compat `AgentRuntime` used by API-mode Grok/DeepSeek/MiniMax agents sent tools-less messages and could only narrate "I'll go look that up" — now `execute()` drives `run_tool_loop` with a capability-filtered `ToolRegistry` over a spawned duduclaw `mcp-server`, degrading to plain messages only when no tools are reachable) — `ToolRegistry` aggregates N MCP servers, the loop feeds `ToolResult` back until the model stops (max-iters cap, per-call errors fed back as `is_error`). Real SSE streaming on all four providers. **Local inference folded in (2026-09-29 / T5-O11)**: `duduclaw-inference` no longer keeps its own reqwest chat/completions client — the capability that kept it alive (per-token `logprobs`/`top_logprobs` capture for the UCCI cascade) is now `ChatRequest::{top_p, stop, logprobs, top_logprobs}` plus `OpenAiCompatProvider::complete_with_logprobs()`, absent from the wire body when unset. The local backend is a thin `InferenceBackend` shell that carries two local-only settings explicitly rather than inheriting them: a 300s request timeout (CPU generation routinely exceeds the shared 120s singleton) and `with_verbatim_model_id()` (a local server's `qwen/qwen3-4b` is a name, not a `provider/model` qualifier — the shared `split_model_id` would send a model the server does not have). The UCCI margin computation deliberately stayed on the inference side: the shared provider transports the signal, it does not score it.
- **MCP Server** (`duduclaw mcp-server`) exposes channel, memory, agent, skill, task, shared wiki, and autopilot tools to AI Runtime via JSON-RPC 2.0 over stdin/stdout. Registered per agent in `<agent_dir>/.mcp.json`, created and repaired at every gateway boot by `mcp_template::ensure_mcp_absolute_paths_all` (the Claude CLI in `-p` mode does not read MCP servers from the global `~/.claude/settings.json`; the global-registration helper `ensure_global_mcp_server` has no caller)
- **Agent directories** are Claude Code compatible: each contains `.claude/`, `SOUL.md`, `CLAUDE.md`. The DuDuClaw MCP server and any agent-specific MCP server (e.g. Playwright) both live in the per-agent `.mcp.json`

- **Autopilot rule engine**: Event-driven automation built on a `tokio::broadcast` event bus (capacity 8192). `AutopilotEngine` subscribes to `TaskCreated` / `TaskStatusChanged` / `ChannelMessage` / `AgentIdle` / `CronTick` events, evaluates per-rule conditions (`all`/`any` + `eq/neq/in/not_in/gt/gte/lt/lte/contains` ops), and dispatches three action types: `delegate` (enqueue bus task for target agent), `notify` (send to channel), `run_skill` (invoke skill — skill name + target agent validated via alphanumeric allowlist + `canonicalize()` path containment). - **Resident sensing** (`tick_config.rs` / `tick_source.rs` / `tick_source_poll.rs` / `tick_source_ws.rs` / `autopilot_screen.rs`): external data streams — `http_poll` / `command` / `file_tail` / `websocket`, declared under `config.toml [tick]` / `[[tick.sources]]`, **default off** — join the autopilot bus as a new `AutopilotEvent::Tick` (`event_name() = "tick"`, also a legal CEP `first`/`then` name), one task per source with a per-source `max_events_per_minute` cap (floor 1s) and reserved-field-name/prefix rejection at config-load time (fail-closed per source, never aborts gateway boot); `websocket` is the one push-based kind (each text frame is a payload through the identical pipeline): `ws`/`wss` only, plaintext `ws://` restricted to loopback while every other host must be `wss://` and re-passes the shared `web_fetch::validate_url` SSRF gate scheme-mapped to https, optional ≤8×4KB verbatim `subscribe` frames, exponential reconnect backoff (start `interval_secs`, ×2, cap 60s, +≤25% jitter, reset after a ≥60s session), binary frames dropped and counted as `non_text`; every numeric extracted field automatically grows deterministic `prev_<f>`/`delta_<f>`/`pct_<f>` companions so a rule writes `{"field":"pct_price","op":"gt","value":2}` with no new condition operator. Recent observations live in an in-process `TickHub` ring buffer (256/source — ticks are NOT persisted to `events.db` by default; opt-in `persist_every_n` for an audit trail) that both the `delegate` wake-up prompt (`context_ticks`, default 10, cap 50) and an optional per-rule local-model screening layer (`action.screen`) read from. Screening is local-only (never escalates to cloud) and fail-open by default (unavailable/timeout/unparseable verdict → dispatch anyway unless `on_unavailable = "drop"`; verdict parsing strips edge ASCII punctuation from the first token before matching YES/NO). Dashboard: `ticks.sources`/`ticks.recent` RPCs feed a read-only "即時監控來源" card on the Autopilot settings tab; `tick_events_total`/`tick_dropped_total`/`tick_screen_total`/`tick_wakes_total` Prometheus counters. **D5-W2 hardening**: `http_poll` + `websocket` accept custom `headers` (≤8, transport-owned names and CR/LF-bearing values refused at config load; values never logged, never serialized — `TickSourceConfig` has a hand-written `Debug` and no `Serialize`, and `ticks.sources` exposes only `headers_count`); `websocket` gains an idle watchdog + client ping (`idle_timeout_secs` default 300 / floor 30, `ping_interval_secs` default 30 / floor 5, `0` disables either, `idle > ping` enforced — any inbound frame resets both clocks, an idle recycle redials immediately and is deliberately not counted as a drop); and every `http_poll` request plus every non-loopback `wss` dial re-resolves DNS at request time through the shared `web_fetch::resolve_public_addrs` (all resolved addresses must be public or the whole answer is refused, then pinned — reqwest `resolve_to_addrs` for HTTP, a `TcpStream` dialled at the vetted addresses with hostname-derived SNI for WS), which also replaced and hardened the single-address re-pin previously inlined in `web_fetch_cached`. **Third live-fire round (real Kraken wss feed)** corrected three pipeline defects: the D2 delta baseline is now **per-field last-seen** (`prev_<f>` compares against the last tick in which `f` actually appeared — wholesale map replacement let interleaved heartbeat frames erase it, measured at ~90% of ticks producing no delta); extracted **numeric strings are coerced to JSON numbers** (`"63669.60000"` → `63669.6`, integers staying `i64` — every mainstream feed ships string prices, so `gt` and the delta trio were silently dead; leading zeros / leading `+` / non-finite stay strings, and the coercion is confined to the tick extraction layer, never the global rule-engine `number_pair`); and a payload that resolves **none** of a source's configured `json_fields` is dropped as `DropReason::NoFields` rather than emitted as a field-less tick (checked before the rate cap so control frames cannot starve the emission budget; sources with no `json_fields`, and non-JSON payloads, keep the `raw_len` behavior). A fourth round added `round6` to `delta_<f>` (it had only ever been applied to `pct_<f>`): float subtraction of two decimal prices leaves last-bit noise that, post-F2, reached rule comparisons and wake-up prompts directly and flipped thresholds like `delta_price gt 0.1`; `prev_<f>` stays verbatim (a reported value, not a derived one) and the integral path bypasses rounding entirely (`round6` scales by 1e6 and stops being exact past ~9×10⁹). Two residual settings close the round out: per-source `baseline_max_age_secs` (default 3600, `0` = never) gives each field's delta baseline a shelf life — past it the baseline is forgotten, the observation reads as a first tick (no delta trio) and re-establishes the baseline, so a field that stopped reporting for a day cannot manufacture a giant fictional move; and global `[tick] dns_ttl_secs` (default 60, `0` = per-request) lets each source task reuse its already-screened address set for the TTL (lock-free, task-local, keyed `host:port`), which strengthens rather than weakens the rebinding defence — what is cached is a vetted public address set, and flipping an answer requires a *fresh* resolution. `web_fetch_cached` keeps its own semantics. **Knob presets (T5/O15, 2026-09)**: `[tick] preset = "conservative" | "aggressive"` supplies defaults for the keys a source (or a rule's `action.screen`) did NOT write — `max_events_per_minute` 30/600, `baseline_max_age_secs` 900/21600, and `on_unavailable` `drop`/`pass`; presence is read from the raw TOML table (not from "the parsed value equals the default"), so an explicit key always wins even when its value equals the old default, an unknown preset is warned about and ignored, and omitting the key is byte-identical to before. The dashboard card shows the active preset; since v1.68.0 the `[tick]` settings and `[[tick.sources]]` are edited on Settings → Advanced → Automation → 常駐感知 (`tick.sources.*`, hot respawn). The v1.33 ban on automatic wiki writes is lifted, with each of its three original objections answered structurally: ① *duplication* → **single sink**: the document's full text exists ONLY as the wiki page, memory keeps a ≤200-char pointer triple (`subject = wiki:auto/<doc_type>/<slug>`, `predicate = documented_in`) that `store_temporal` supersedes automatically; ② *curation dilution* → **four locks** (`auto/{charter,sop,spec,policy,reference}/` is the only writable prefix; `author: auto-distill` + `auto-distilled` tag self-label every page — no new frontmatter key is invented because `parse_wiki_page → serialize_page` silently drops unknown keys; `.scope.toml` is consulted before every write and, unlike the shared-wiki fail-safe, an existing-but-malformed policy **stops** the auto write; `layer: context` keeps auto pages out of `collect_by_layer_with_meta` so they cost 0 bytes of the injection budget and human curation's injected bytes are unchanged — `do_not_inject` is deliberately NOT set, since `WikiStore::search` drops such pages and auto pages must stay findable); ③ *no supersession* → **deterministic page key** (`resolve_slug` validates an LLM slug against `^[a-z0-9][a-z0-9-]{0,63}$`, else `<doc_type>-<sha8(NFKC title)>`), identical content is a no-op, different content overwrites and appends a revision-log line. ## Design Context

### Users
DuDuClaw is a **Multi-Runtime AI Agent Platform** for individual developers and power users, primarily in Taiwan (zh-TW). It supports Claude Code / Codex / Gemini CLI (deprecated) as interchangeable AI backends. Users interact through a web dashboard to manage AI agents, monitor channels (LINE/Telegram/Discord/Slack/WhatsApp/Feishu), track API budgets, and observe agent self-evolution. They expect a tool that feels like a trusted companion — not a cold enterprise console.

### Brand Personality
**Professional · Efficient · Precise** — with a warm, approachable surface.

Like a skilled engineer who happens to be your close friend: reliable, sharp, but never cold. The paw print (🐾) icon reflects a pet-like companionship — the AI is loyal, attentive, and delightful to interact with.

### Aesthetic Direction
- **Primary references**: Claude.ai (warm sand/beige tones, generous whitespace, soft typography) + Raycast (macOS-native polish, frosted glass effects, refined dark theme)
- **Anti-references**: Grafana (too dense), Discord (too playful), enterprise dashboards (too cold)
- **Color palette**:
  - Primary: warm amber (`amber-500` / `#f59e0b`) — evokes warmth and trust
  - Accent: soft orange (`orange-400` / `#fb923c`) — for highlights and CTAs
  - Surface light: warm stone (`stone-50` / `#fafaf9`) with subtle warm undertones
  - Surface dark: deep stone (`stone-900` / `#1c1917`) — warm dark, not cold blue-black
  - Success: emerald, Warning: amber, Error: rose — standard semantic colors
- **Theme**: Follow system preference (auto dark/light), with manual toggle
- **Typography**: System font stack for performance; generous line-height; larger body text (16px base)
- **Border radius**: Rounded (0.75rem default) — soft, approachable
- **Spacing**: Generous padding — the interface should breathe
- **Motion**: Subtle fade-in/slide transitions (150-200ms); respect `prefers-reduced-motion`
- **Glass effects**: Subtle backdrop-blur on sidebars and overlays (Raycast influence)

### Design Principles
1. **Warmth over sterility** — Every surface should feel inviting. Prefer warm neutrals over cold grays. Use color strategically to create emotional connection.
2. **Clarity over density** — Show what matters, hide what doesn't. Progressive disclosure: summary first, details on demand. Never overwhelm.
3. **Real-time without anxiety** — Status indicators should inform, not alarm. Use gentle transitions for state changes. Green means "all is well" and should be the dominant state color.
4. **One binary, one experience** — The dashboard is embedded in the Rust binary. It should feel native and instant, like a local app, not a remote web service.
5. **Accessible by default** — WCAG 2.1 AA compliance. Semantic HTML. Keyboard navigation. Respect motion preferences. Sufficient color contrast in both themes.

## Coding Conventions (security-relevant, from 2026-06 deep review)

These conventions exist to prevent classes of bugs surfaced by the 2026-06 whole-project review. Shared helpers live in `duduclaw-core`.

1. **Never slice strings by raw byte index.** `&s[..n]` panics when `n` lands mid-char on multi-byte UTF-8 (any CJK/emoji input). Use `duduclaw_core::truncate_bytes(s, max_bytes)` (byte budget, walks back to a char boundary) or `truncate_chars(s, max_chars)` (codepoint count). Applies to every channel/log snippet and id prefix.
2. **No unanchored `contains` / `starts_with` for security or routing decisions.** Substring checks let `http://localhost.evil.com` pass a `localhost` allowlist and the keyword `hi` match inside `this`. Use `duduclaw_core::origin_host_matches(origin, &allowed)` for Origin/CORS allowlists and `word_contains_ci(haystack, needle)` for keyword matching; use exact/token equality for id routing.
3. **Cross-process file appends must hold an advisory lock.** Shared JSONL (`bus_queue.jsonl`, audit logs) is appended by both the Rust gateway and Python adapters; records over `PIPE_BUF` interleave and corrupt lines. Wrap the write in `duduclaw_core::with_file_lock(path, || …)`.
4. **Security gates fail closed.** Missing config, a detection error, or an unenumerated tool/method must DENY, never fall through to allow. MCP authorization is enumerated explicitly; any tool not in the scope table defaults to requiring Admin scope. Validate the *artifact that actually takes effect* (the written `patch.content`, the final screenshot), not just the proposal/narrative.

## Documentation Classification & Placement (from 2026-06-20 doc reorg)

Every document (`.md`, design notes, reports, specs) MUST be filed by **TYPE × CONFIDENTIALITY**. When creating or moving a doc, pick the matching cell below — do not drop loose files at a tree root, and never co-locate a higher-confidentiality doc inside a lower-confidentiality tree.

### Confidentiality tiers (3 levels)

| Tier | Meaning | Git state | Lives in |
|------|---------|-----------|----------|
| **L1 Public** | Product / developer docs intended for the public repo, website, npm/PyPI README | Committed, externally published | root `README*.md`, `CHANGELOG.md`, `ARCHITECTURE.md`, `SECURITY.md`, `LICENSING.md`, `docs/`, `templates/`, `marketing/press-kit/` |
| **L2 Internal** | Dev/ops material — committed but not product-facing | Committed (visible to repo collaborators), **not** polished docs | `wiki/` (knowledge base + reports), `team/`, `ISSUES.md`, `marketing/{blog,social-templates,threads-drafts}/` |
| **L3 Confidential** | Commercial plans, competitive analysis, pricing, research notes, secrets, build output | **gitignored — never committed to the public repo** | `commercial/` (own nested git), `research/`, `artifacts/`, `.env*`, anything under a secret manager |

**Hard rule:** L3 lives ONLY in gitignored trees. Before committing, confirm no `commercial/`, `research/`, pricing, or secret content is staged. `commercial/` and `research/` are in `.gitignore`; if `git ls-files <tree>` ever returns rows, untrack them with `git rm --cached -r <tree>` (files stay on disk).

### Type taxonomy → canonical home

**L1 Public — `docs/` only (one subdir per type, never loose at `docs/` root):**
- `docs/architecture/` — system architecture & engine design (`overview.md`, `evolution-engine.md`)
- `docs/rfc/` — Request-for-Comments proposals (`RFC-NN-*.md`, plus their operator guides)
- `docs/adr/` — Architecture Decision Records (`ADR-NNN-*.md`)
- `docs/todo/` — public planning / tracking (`TODO-*.md`)
- `docs/spec/` — open format specs (SOUL.md, CONTRACT.toml, JSON Schema)
- `docs/features/` — feature deep-dives (+ `ja-JP/`, `zh-TW/` translations)
- `docs/guides/` — user & developer how-tos (deployment, development, docker, MCP tools)
- `docs/api/` — protocol / OpenAPI reference

**L2 Internal — operational, under `wiki/` (single report home) + `team/`:**
- `wiki/reports/tl-daily/<YYYY-MM-DD>.md` — daily reports (date-only filename; **never** `daily-report-*` and **never** in `docs/`, `reports/`, or `artifacts/`)
- `wiki/reports/skill-pipeline/<YYYY-MM>/`, `wiki/reports/memory-quality/<YYYY-MM>/` — automated pipeline/eval outputs
- `wiki/sprint-reports/`, `wiki/pm/` — sprint logs & PM tracking
- `wiki/duduclaw-kb/{architecture,decisions,specs,drafts,w19,sprint-n}/` — internal knowledge base
- `wiki/{eval,impl,research}/` — evaluation sets, implementation notes, internal design feedback
- `team/` — team roster & role docs

**L3 Confidential — gitignored trees (do NOT add to `docs/` or `wiki/`):**
- `commercial/docs/` — business plans, pricing, competitive analysis, SI methodology, commercial design docs (e.g. PTY-pool design, runtime TODOs)
- `research/` — AI paper / repo research notes (auto-mirrored to the shared wiki at runtime)
- `artifacts/` — build output (tarballs, generated bundles)

### When in doubt
1. **Is it secret / commercial / competitive / a research note?** → L3 gitignored tree. Stop.
2. **Is it a daily/sprint/eval/PM report or internal KB?** → L2 under `wiki/` (reports → `wiki/reports/…`).
3. **Is it polished product/dev documentation safe to publish?** → L1 under the matching `docs/<type>/` subdir.
4. Update `docs/README.md` (the public index) whenever a `docs/` file is added, moved, or removed; update in-repo links (READMEs, `CLAUDE.md`, code comments, `CONTRACT.toml`) in the same commit.
